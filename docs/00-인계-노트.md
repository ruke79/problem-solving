## 3. 핵심 설계 (새 케이스를 추가할 때 반드시 지킬 것)

증거를 **세 종류로 구분**하는 것이 이 랩의 전부다.

| 메서드 | 의미 | 깨졌을 때 |
|---|---|---|
| `evidence.fact(k, v)` | 판정 무관 관측값 | 리포트에 기록만 |
| `evidence.expect(설명, 조건)` | 반드시 성립할 명제 | `REFUTED` = **답변을 고쳐야 함** |
| `evidence.expectFlaky(설명, 조건)` | JIT/GC/옵티마이저 의존 | `INCONCLUSIVE` (테스트 실패 아님) |

- `expect` 를 남발하면 테스트가 자주 깨져 신뢰를 잃고,
  `expectFlaky` 를 남발하면 아무것도 검증하지 않는 문서가 된다. **이 경계가 핵심.**
- 환경 의존 케이스는 `nondeterministic()` 을 `true` 로 둔다.
- 케이스는 `VerificationCase` 를 상속한 `@Component` 하나면 끝. 자동 수집된다.
- 케이스는 **자기 뒷정리**를 한다(임시 테이블 DROP, 캐시 clear, 스레드 풀 shutdown, 데몬 스레드 + 타임아웃).

## 5. ★ 답변 원고에서 발견한 수정 사항

### 사실 오류 (반드시 고칠 것)

**Q64 — Base62 7자리 용량이 100배 틀렸다**

- 원고: 「7桁のBase62でおよそ350億通り」 / "7자리 Base62로 약 350억 가지"
- 실제: 62⁷ = **3,521,614,606,208 ≈ 3.5조**
- 350억대에 해당하는 것은 **6자리** (62⁶ = 568억)
- → 케이스 `API-02` 가 이 계산을 매번 검증한다.

수정 문장 예:
> 7자리 Base62로 약 3.5조 가지를 커버할 수 있으니 당분간 규모에는 충분합니다.

## 7. 파일 첨부 문제 (다음 채팅에서 주의)

한 채팅에 PDF 를 6개째 올리면 "이 채팅의 첨부 상한에 도달" 에러가 난다.
개수(20개)가 아니라 **누적 내용량**으로 걸리는 것으로 보인다.

**대응**

1. 남은 PDF 는 **프로젝트 지식 베이스**에 올린다 (채팅 첨부와 별도 저장소, 개수 제한 없음).
2. 같은 프로젝트에서 **새 채팅**을 연다.
3. 새 채팅 첫 메시지에는 **zip 과 이 노트만** 첨부한다 (텍스트 추출량이 적어 부담이 작음).
4. PDF 대신 **텍스트/마크다운으로 변환**해서 올리면 훨씬 많이 들어간다.
