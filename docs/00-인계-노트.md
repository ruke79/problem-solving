## 그대로 유효한 것

**§3 핵심 설계**(`fact` / `expect` / `expectFlaky` 삼분법)는 지금도 이 랩의 전부다.
노트가 경고한 **"`expectFlaky` 를 남발하면 아무것도 검증하지 않는 문서가 된다"** 가
실제로 가장 값비싼 교훈이었다.

- `expectFlaky` 는 `verify-labs` 기준 **40곳**이다(아래 수치는 그 40곳에 대한 것이다 —
  2026-08-26 에 붙은 `verify-labs-perfbook` 은 별도이고, 그쪽 방침은 `docs/02` §9-5 에 있다).
  전수 점검해 보니
  **5곳은 '환경 의존'이 아니라 측정 하네스 결함**이었다 — 오토박싱, 워밍업 부재, 몰아서 재기,
  `acquire` 를 `usage` 에 섞어 재기, 밀리초로 잘라 `<=` 로 비교하기(`docs/05` §20~§22).
- 특히 마지막 것이 노트의 경고 그대로였다. `after <= before` 는 **둘 다 0이면 조용히 통과**한다 —
  흔들려서 INCONCLUSIVE 가 나는 것보다 나쁘다. 리포트에 아무 흔적이 남지 않기 때문이다.
- 남은 20곳은 결과를 정하는 것이 옵티마이저·근사 알고리즘·JIT/GC·락 타이밍이라 손댈 수 없다.
  이건 `expectFlaky` 가 맞는 자리다.

**§8 정직성 우선**도 그대로 지켰다. "검증한 척"을 만들지 않기 위해 **만들지 않은 것**이 둘 있다.

- **Kubernetes** — k3s 컨트롤 플레인까지는 실제로 띄웠지만 이 환경에서 파드가 뜨지 않았다.
  API 레벨만 보는 케이스를 올리면 `K8S-01 CONFIRMED` 가 찍히는데 정작 문항이 묻는
  런타임 동작은 확인하지 않은 상태가 된다(`docs/05` §18).
- **`Q160`~`Q164` LLM 품질·SSE** — 실제 모델이 있어야 의미가 생긴다(`docs/09` §7).

**2026-08-26 에 같은 원칙을 두 번 더 적용했다.**

- **책 1장을 요약하지 않았다.** 업로드 자료에 없었다. 목차만 보고 채워 넣을 수도 있었지만
  안 읽은 것을 읽은 척하는 셈이라 하지 않았고, `notes/java-performance/README.md` 머리에
  고지로 남겼다.
- **`PERF-10C` 를 루프백에서 통과시키지 않았다.** 조건이 안 맞는데 CONFIRMED 를 찍으면
  그게 §1-2 의 헛통과다. **로컬·CI 에서 영영 INCONCLUSIVE 로 남는 케이스를 일부러 만들었다** —

## 외부 기준으로 랩 자신을 검사했다 (2026-08-26)

이 랩은 **자기 원고만 검증 대상으로 삼고 있었다.** 그러면 "무엇을 재기로 했는가"를 랩 자신이
정하게 되고, 빠뜨린 것은 빠뜨렸다는 사실조차 남지 않는다. 그래서 외부 기준을 하나 붙였다 —
Scott Oaks, *Java Performance: The Definitive Guide*.

### (1) 책을 요약했다 — `notes/java-performance/` 13개 파일

2장~12장 + 부록 A. **1장(Introduction)은 업로드 자료에 없어서 요약하지 않았다** — 안 읽은 것을
읽은 척하지 않는다는 §8 을 그대로 적용했다. 장마다 끝에 **"이 장을 우리 랩에 비춰 보면"** 표를
붙였는데, 이건 자랑이 아니라 **구멍 목록**이다.

### (2) 구멍을 전수 분류했다 — `docs/02` §9

그 표에서 "검증 케이스 없음"으로 남은 줄이 **25개**였다. 넷으로 갈랐다.

| 갈래 | 건수 | 뜻 |
|---|---|---|
| **못 하는 것** | 3 → **2** | 조건을 만들 수 없다 (32GB 힙 / JDK 6). 하나는 아래 (5) 에서 빠졌다 |
| **사라진 것** | 2 | JDK 가 없앴다 — 편향 락 기본 비활성, `AggressiveOpts` 제거, `StringTableSize` 1009→65536 |
| **별도 JVM 필요** | 3 | §8 이 이미 제외한 영역. "못 하는 것"이 아니라 **하네스를 키우기로 결정하지 않은 것** |
| **안 한 것** | 14 | **지금 이 환경에서 잴 수 있는데 안 재고 있었다** |

> **이 분류 자체가 이번 작업의 요점이다.** §1-3 「검증하지 못한 것」에는 Kubernetes 와 LLM 품질
> 둘뿐이었고 §8 은 의도적으로 뺀 것의 목록이었다. **그 사이에 14개가 있었는데 어느 목록에도
> 없었다** — 없다는 사실조차 적혀 있지 않았다. **"못 하는 것"과 "안 한 것"을 같은 칸에 넣지
> 않는 것**이 §8 정직성 원칙의 대칭이다.

### (3) "안 한 것"을 케이스로 만들었다 — `verify-labs-perfbook` 15건

`PERF-<장번호>`. 측정 원칙은 랩 공통 규칙 그대로 — **셀 수 있는 것은 결정적 `expect`,
시간 비교만 `expectFlaky`**. 그래서 지연 스트림은 시간이 아니라 람다 호출 횟수를 세고,
버퍼드 I/O 는 하부 `read` 호출 횟수(524,288 → 65)를 센다.

**만들면서 겪은 것이 §1-1 의 목록과 같은 종류였다.**

| 케이스 | 처음 결과 | 실제 원인 | 조치 |
|---|---|---|---|
| `PERF-12B` 예외 비용 | INCONCLUSIVE | 던지기·되감기까지 섞어 쟀다 — 되감기는 스택을 꺼도 깊이에 비례해 남는다 | 임계값을 풀지 않고 **측정을 명제("생성 시 수집")에 맞게 좁혔다** |
| `PERF-11C` L2 캐시 | **REFUTED** | 명제가 아니라 검증식의 전제가 틀렸다 — **`persist` 는 커밋 시점에 이미 L2 에 넣는다**(쓰기 경유) | 캐시를 비우고 시작하도록 고치고, 발견을 note 에 남겼다 |
| `PERF-09B` 암달 | INCONCLUSIVE | 작업량이 작아 스레드 생성 오버헤드가 병렬 이득을 먹었다 | 작업량을 키웠다 |

**셋 다 답변(명제)이 아니라 랩 쪽 문제였다.** REFUTED 를 보고 "책이 틀렸다"로 가지 않은 것이
중요하다 — 먼저 의심할 것은 언제나 우리 측정이다.

### (4) 자동 실행을 붙였다 — `.github/workflows/` 3종, `docs/11`

| 워크플로 | 언제 | 무엇 |
|---|---|---|
| `ci.yml` | 커밋마다 | compose 로 실물 인프라를 띄우고 110건 전부, 리포트를 아티팩트로 |
| `deploy-ec2.yml` | 수동 | EC2 프리티어에 rsync 배포 → 그 장비에서 실행 → 리포트 회수 |
| `remote-network.yml` | 수동 | 서버는 EC2 에, 측정은 러너에서 — 그 사이가 WAN |

EC2 는 프리티어(RAM 1GB)를 전제로 **스왑 2GB** 를 붙이고 빌드는 러너가 하게 했다.
**1 vCPU 에서 `PERF-09A`·`PERF-09B` 가 INCONCLUSIVE 로 남는 것은 정상 결과**라는 것도
`docs/11` §4 에 미리 적어 뒀다 — 나중에 보고 "깨졌다"고 오해하지 않도록.

### (5) 그 결과 §9-1 이 3건 → 2건이 됐다 — `PERF-10C`

"못 하는 것"에 있던 **10장 "출력을 줄여라"** 가 해소됐다. 막고 있던 것은 실제 광역 네트워크였고,
EC2 배포가 그 조건을 만들었다. **이 케이스만 방향이 반대다** — 서버를 EC2 에 두고 클라이언트를
러너에서 돌려야 그 사이가 WAN 이 된다. 인스턴스 안에서 돌리면 루프백이라 조건이 사라진다.

> **여기서도 예상이 실측과 달랐다.** "루프백이면 두 응답의 시간 차이가 사라질 것"으로 보고
> 케이스 주장에 그렇게 써 뒀는데, 재 보니 **루프백에서도 3.19배가 벌어졌다.** 남아 있는 것은
> 대역폭이 아니라 **서버가 큰 응답을 만들어 소켓에 복사하는 비용**이었다. 주장에서 그 문장을
> 빼고 note 를 "루프백에서는 링크 대역폭 성분만 사라진다"로 고쳤다.
> **§1-1 에 한 줄 더 붙는 셈인데, 이번에는 하네스 결함이 아니라 주장 문장이 과했던 경우다.**

### (스프링 쪽) 만들다 여섯 번 틀렸고, 하나는 레슨이 됐다

자세한 목록은 `spring-tutorial/README.md` §4. 넷은 레슨·주석으로
승격했다: ①`ApplicationContextRunner` 는 이름과 달리 **Boot 기본값을 적용**한다(→레슨 1-8),
②기록용 트랜잭션 매니저에 `SmartTransactionObject` 가 없으면 rollback-only 전염(4-7)이
재현되지 않는다, ③레슨 3-5 에 써 놓은 'CGLIB 프록시 필드는 비어 있다'를 **레슨 7 에서
내가 그대로 밟았다**(필드 직접 접근 → NPE), ④`@EnableTransactionManagement` 가 없으면
`@TransactionalEventListener` 가 **조용히 일반 리스너로 강등**된다(7-5). 나머지 둘은
Boot 가 평소 대신해 주던 것들이다 — Spring 6.1 의 `-parameters` 요구,
`StringHttpMessageConverter` 의 ISO-8859-1 기본값.

**선정 기준은 두 모듈 모두 커버리지가 아니라 판정 가능성이다.** 290문항 중 106개만
레슨이 됐고(자바 54/145 · 스프링 52/145), 나머지는 실행으로 판정할 수 없거나
(설계 논의·용어 설명) 모듈의 범위를 벗어난다 — DB 가 있어야 성립하는 스프링 문항
(Part 4 대부분)은 `verify-labs` 의 `SPRING-*`·`JPA-*`·`DB-*` 가, 시간 측정은
`verify-labs-perfbook` 이 실행 근거다. 의존은 자바 쪽이 JUnit·AssertJ 둘,
스프링 쪽이 스타터 넷(web·aop·cache·validation)+spring-tx 뿐이다.

### `observe` — 이 모듈판 `expectFlaky`

`Lesson` 클래스의 도구 셋 중 **`observe` 는 환경에 좌우되는 값을 출력만 하고
단정하지 않는다.** 저장소의 `expect`/`expectFlaky` 구분과 같은 발상이다(§3).
`java-tutorial` 에 5곳(레슨 5 에 4, 레슨 2 에 1). **테스트가 초록이라고 해서 그 줄까지
증명된 것은 아니라는 뜻**이고, README §5 에 그렇게 적어 뒀다.
`spring-tutorial` 은 0곳이다 — 다루는 명제가 전부 결정적이어서 쓸 일이 없었을 뿐,
원칙이 다른 게 아니다(그 사실도 저쪽 README §5 에 적었다).

레슨 5-1 이 대표적이다. 단정한 것은 「`AtomicInteger` 는 정확하다」와
「일반 `int` 는 기대값을 넘지 못한다」 둘뿐이고, **「반드시 갱신 손실이 난다」는
단정하지 않았다** — 스케줄링은 우리가 정하지 못하기 때문이다.
5-6 의 **반대 순서 데드락은 아예 재현하지 않았다**(재현하면 테스트가 영원히 멈춘다).
안 한 것이고, 안 했다고 README 에 적었다.

### (자바 쪽) 만들다 두 번 틀렸고, 한 번은 레슨이 됐다

- **레슨 4** — `["a","b","c"]` 에서 `"b"`(끝에서 두 번째)를 지우게 짰더니 CME 가
  나지 않아 테스트가 실패했다. `remove` 후 `size=2, cursor=2` 라 `hasNext()` 가
  먼저 false 가 되어 `next()` 의 변경 검사를 지나간다. 조건을 `"a"` 로 고치는 데서
  끝내지 않고, **밟은 함정 자체를 `4-4b`「fail-fast 는 보장이 아니다」라는
  새 레슨으로 남겼다.** 실패가 교재가 된 사례다.
- **레슨 6-2** — `remainingCapacity()` 가 `Integer.MAX_VALUE` 를 돌려줄 거라
  단정했는데 실제로는 `용량 - 현재 크기`(2,147,482,647)였다. 자바의 놀라움이 아니라
  **내 주장이 틀린 것**이라, 주장을 `쌓인 것 + 남은 것 == Integer.MAX_VALUE` 로
  고치고 **틀렸던 사실을 코드 주석에 남겼다.**

### (공통) 시간을 재지 않은 이유

자바 3-6(예외 비용)·7-2(지연 순회)는 성능 이야기지만 **시간이 아니라 호출 횟수로 쟀고**,

## 3. 핵심 설계 (새 케이스를 추가할 때 반드시 지킬 것)

증거를 **세 종류로 구분**하는 것이 이 랩의 전부다.

| 메서드 | 의미 | 깨졌을 때 |
|---|---|---|
| `evidence.fact(k, v)` | 판정 무관 관측값 | 리포트에 기록만 |
| `evidence.expect(설명, 조건)` | 반드시 성립할 명제 | `REFUTED` = **답변을 고쳐야 함** |
| `evidence.expectFlaky(설명, 조건)` | JIT/GC/옵티마이저 의존 | `INCONCLUSIVE` (테스트 실패 아님) |

- `expect` 를 남발하면 테스트가 자주 깨져 신뢰를 잃고,
  `expectFlaky` 를 남발하면 아무것도 검증하지 않는 문서가 된다. **이 경계가 핵심.**
- 환경 의존 케이스는 `nondeterministic()` 을 `true` 로 둔다.
- 케이스는 `VerificationCase` 를 상속한 `@Component` 하나면 끝. 자동 수집된다.
- 케이스는 **자기 뒷정리**를 한다(임시 테이블 DROP, 캐시 clear, 스레드 풀 shutdown, 데몬 스레드 + 타임아웃).
