# 정직한 고지 — 이 랩이 증명하는 것과 증명하지 못하는 것

## 1. 실행 현황 (2026-08-11 갱신)

- **이제 실제로 컴파일·실행된다.** `./gradlew :verify-labs:test` 로 52건 전부 돌렸고 결과는
  **CONFIRMED 48 / REFUTED 0 / INCONCLUSIVE 4 / ERROR 0**(Java 17.0.19, Linux, 4코어).
  연속 4회 실행에서 REFUTED 는 한 번도 나오지 않았고 INCONCLUSIVE 만 4~5건 사이에서 흔들렸다.
  그 과정에서 실제로 고친 문제는 `docs/05-개발-중-문제와-해결.md` 에 전부 적어 두었다.
- **`gradle/wrapper/gradle-wrapper.jar` 는 이제 저장소에 있다.** `gradle wrapper` 선행 실행 없이
  바로 `./gradlew` 를 쓰면 된다.
- **성능 수치는 장비에 좌우된다.** 리포트의 소요 시간은 위 환경 기준이며 그대로 인용하면 안 된다.

## 2. 검증 강도가 다른 케이스들

| 강도 | 케이스 | 성격 |
|---|---|---|
| **결정적** | SPRING-01~07, JPA-01~04, JPA-06, CON-04, JVM-01~03, JVM-05, DB-02, DB-04, MSA-01~05, RES-01, RES-02(sync 쪽), RES-04, RES-06, RES-07, API-01, API-02, AI-01, AI-02, AI-05, AI-06 | 실행하면 항상 같은 결과가 나온다. REFUTED 가 나오면 답변이 틀린 것이다. |
| **거의 결정적** | JPA-05, DB-01(READ COMMITTED 쪽), RES-03, RES-05(윈도 계산 쪽) | 구현체 버전에 따라 숫자가 달라질 수 있어 일부 항목만 `expectFlaky` 로 둔다. |
| **환경 의존** | CON-01~03, CON-05, JVM-04, JVM-06, JPA-07, DB-01(RR 쪽), DB-03, DB-05, DB-06, DB-07, RES-05(경쟁 상태 쪽), AI-03, AI-04 | JIT·GC·코어 수·옵티마이저·락 타이밍에 좌우된다. `INCONCLUSIVE` 가 정상 결과일 수 있다. |

`nondeterministic()` 이 `true` 인 케이스는 `INCONCLUSIVE` 여도 테스트가 실패하지 않는다.
**결과를 못 냈다는 사실 자체를 리포트에 남기는 것**이 이 설계의 목적이다.

## 3. H2 를 쓴 대가

DB-01(격리 수준)과 DB-03(실행계획)은 H2 인메모리에서 돈다. 이건 타협이다.

- H2 의 MVCC 구현과 격리 수준 의미는 PostgreSQL·MySQL InnoDB 와 다르다.
  특히 **팬텀 리드 방지 메커니즘**(PostgreSQL 의 스냅샷 vs InnoDB 의 gap lock)은 재현되지 않는다.
- H2 옵티마이저는 PostgreSQL 만큼 정교하지 않다. **인덱스↔풀스캔 전환점의 실제 값은 H2 에서 재면 의미가 없다.**
  그 측정은 PostgreSQL 에서 `EXPLAIN (ANALYZE, BUFFERS)` 로 해야 한다.
- 따라서 DB-01/DB-03 이 증명하는 것은 **"현상이 존재한다"** 까지이고,
  **"내 운영 DB 에서 어떤 숫자가 나오는가"** 는 증명하지 못한다.

면접에서 이 차이를 그대로 말할 수 있으면 오히려 강점이 된다:
"H2 로 현상은 재현했고, 전환점 수치는 PostgreSQL 에서 따로 쟀습니다."

## 4. 벤치마크가 아니다

CON-02(카운터 비교)는 **JMH 가 아니다.** 단발 벽시계 측정이라

- 워밍업이 부족해 JIT 컴파일 시간이 섞여 있고,
- GC 발생 여부에 따라 값이 흔들리고,
- 실행마다 순위가 뒤집힐 수 있다.

그래서 정확성(합계 일치)만 `expect` 로 두고, 처리 시간은 `fact` 로만 기록한다.
"LongAdder 가 더 빠르다"는 `expectFlaky` 라서, 뒤집혀도 `REFUTED` 가 아니라 `INCONCLUSIVE` 가 된다.
**절대값이 아니라 자릿수만 신뢰할 것.**

## 5. 단일 JVM 의 한계

RES-01(멱등성)과 RES-02(스탬피드)는 `ConcurrentHashMap` 과 로컬 캐시로 검증한다.
이것은 **단일 프로세스 안에서만 유효한 보장**이다.

- 멱등성의 진짜 근거는 Redis `SET NX` + TTL 이나 DB 유니크 제약이다.
- `@Cacheable(sync=true)` 는 인스턴스마다 독립이라, N대면 원본 호출이 최대 N회다.

분산 환경 검증은 이 랩의 범위 밖이다. Redis·다중 인스턴스를 붙이려면
`docker-compose` 와 통합 테스트가 필요하고, 그 시점에 "컴팩트"라는 전제가 깨진다.

## 6. AI 케이스가 증명하는 것과 못 하는 것

`AI-01`~`AI-06` 은 **실제 임베딩 모델도 LLM 도 쓰지 않는다.** 랜덤 벡터와 손으로 만든 가짜 검색기로,
"알고리즘의 성질"만 검증한다.

- 증명하는 것: PSI 가 분포 변화에 단조 증가한다 / RRF 가 순위만으로 두 검색기를 합친다 /
  nprobe 를 넓히면 재현율이 오른다 / 양자화가 메모리를 1/4 로 줄인다 / 권한 전필터와 후필터의 결과 차이.
- 증명하지 못하는 것: **실제 검색 품질**. Recall@k 의 절대값, 리랭커의 효과, 청킹 전략의 우열은
  실제 문서·실제 임베딩·사람 평가가 있어야 나온다.
- 특히 `AI-04` 의 "단순 절단 시 재현율 붕괴"는 랜덤 벡터라서 더 극단적으로 나온다.
  이 결과는 "마트료시카는 학습 기법이지 공짜 연산이 아니다"라는 **명제의 방향**만 뒷받침한다.

## 7. 스키마·격리 수준의 H2 한계 (추가)

- `DB-05`(UUID PK): H2 인메모리는 InnoDB 같은 클러스터 인덱스가 아니고 디스크 페이지 분할도 없다.
  **삽입 시간 차이는 방향만 참고**하고, 실제 수치는 MySQL 에서 재야 한다. UUIDv7 의 정렬 가능성만이 결정적 검증이다.
- `DB-07`(데드락): H2 의 데드락 감지·락 타임아웃 동작은 InnoDB 와 다르다.
  "순서를 통일하면 사라진다"는 명제는 DB 독립이지만, 오류 코드와 회복 방식은 제품마다 확인이 필요하다.
- `MSA-05`(Expand/Contract): H2 의 `ALTER TABLE DROP COLUMN` 은 즉시 완료된다.
  PostgreSQL·MySQL 에서는 이 DDL 이 락과 재작성 비용을 동반하므로, 실제 운영 절차에는 그 시간이 추가된다.

## 8. 커버하지 않는 영역

의도적으로 넣지 않은 것들:

- **GC 튜닝·힙 덤프 분석** — 실행 시간이 길고 결과가 장비에 크게 좌우된다.
- **네트워크 타임아웃/서킷브레이커 실측** — 외부 의존이 필요하다. RES-03 은 로컬 흉내에 그친다.
- **Kafka·분산 트랜잭션·합의 알고리즘** — 별도 프로젝트가 있다면 그쪽 랩이 적합하다.
- **JVM 플래그별 동작 비교** — 별도 JVM 을 띄워야 해서 하네스 구조가 커진다.

이 항목들이 필요해지면 `verify-core` 를 그대로 쓰고 케이스만 다른 모듈에 추가하면 된다.
그것이 core/labs 를 나눠 둔 이유다.
