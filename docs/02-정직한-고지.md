# 정직한 고지 — 이 랩이 증명하는 것과 증명하지 못하는 것

## 1. 실행 현황 (2026-08-11 갱신)

- **이제 실제로 컴파일·실행된다.** `./gradlew build` 로 **63건**(verify-labs 58 + verify-labs-kafka 5)을
  전부 돌렸고 결과는 **REFUTED 0**(CONFIRMED 60 / INCONCLUSIVE 3, Java 17.0.19, Linux, 4코어).
  반복 실행에서 REFUTED 는 한 번도 나오지 않았고 INCONCLUSIVE 만 1~3건 사이에서 흔들렸다.
  DB 는 컨테이너(`postgres:16` = 16.14)와 네이티브 설치본(16.13) 양쪽에서 각각 확인했다.
  그 과정에서 실제로 고친 문제는 `docs/05-개발-중-문제와-해결.md` 에 전부 적어 두었다.
- **DB 는 PostgreSQL 16 실물이다.** H2 인메모리를 걷어냈으므로 **DB 없이는 테스트가 돌지 않는다** —
  `docker compose up -d` 가 선행돼야 한다(`compose.yaml` 은 실제로 기동·검증했다). 무설치로 돌던 이전 상태와 바뀐 점이다.
- **`gradle/wrapper/gradle-wrapper.jar` 는 이제 저장소에 있다.** `gradle wrapper` 선행 실행 없이
  바로 `./gradlew` 를 쓰면 된다.
- **성능 수치는 장비에 좌우된다.** 리포트의 소요 시간은 위 환경 기준이며 그대로 인용하면 안 된다.

## 2. 검증 강도가 다른 케이스들

| 강도 | 케이스 | 성격 |
|---|---|---|
| **결정적** | SPRING-01~07, JPA-01~04, JPA-06, CON-04, JVM-01~03, JVM-05, DB-01, DB-02, DB-04, DB-09, DB-12, MSA-01~05, RES-01, RES-02(sync 쪽), RES-04, RES-06, RES-07, API-01, API-02, AI-01, AI-02, AI-05, AI-06 | 실행하면 항상 같은 결과가 나온다. REFUTED 가 나오면 답변이 틀린 것이다. |
| **거의 결정적** | JPA-05, RES-03, RES-05(윈도 계산 쪽) | 구현체 버전에 따라 숫자가 달라질 수 있어 일부 항목만 `expectFlaky` 로 둔다. |
| **환경 의존** | CON-01~03, CON-05, JVM-04, JVM-06, JPA-07, DB-03, DB-05, DB-06, DB-07, DB-08, DB-10, DB-11, RES-05(경쟁 상태 쪽), AI-03, AI-04 | JIT·GC·코어 수·옵티마이저·락 타이밍에 좌우된다. `INCONCLUSIVE` 가 정상 결과일 수 있다. |

`nondeterministic()` 이 `true` 인 케이스는 `INCONCLUSIVE` 여도 테스트가 실패하지 않는다.
**결과를 못 냈다는 사실 자체를 리포트에 남기는 것**이 이 설계의 목적이다.

## 3. PostgreSQL 16 을 쓴다 — 얻은 것과 남은 한계

DB 케이스는 **PostgreSQL 16 실물**에서 돈다. H2 인메모리를 걷어내면서 달라진 점:

- `DB-01`(격리 수준): PostgreSQL 의 REPEATABLE READ 는 **스냅샷 격리**라 재읽기 값이 결정적으로 고정된다.
  H2 시절 `expectFlaky` 로 물러서 있던 항목을 `expect` 로 올렸고, 케이스의 `nondeterministic()` 도 껐다.
- `DB-03`(실행계획): 진짜 옵티마이저의 계획 문자열과 비용 추정치를 그대로 읽는다.
  `Seq Scan` → `Index Only Scan using idx_scan_demo_k` 전환이 매 실행에서 관측된다.
- `DB-07`(데드락): `SQLState=40P01`(deadlock detected)과 `55P03`(lock_not_available)을 구분할 수 있다.
  "데드락이 났다"와 "락 타임아웃이 났다"를 섞지 않는다 — 이 구분이 실제로 랩의 버그 하나를 잡아냈다.

그래도 **남는 한계**는 분명하다.

- **MySQL InnoDB 가 아니다.** gap lock 기반 팬텀 방지, 클러스터 인덱스, `SHOW ENGINE INNODB STATUS` 는
  여기서 재현되지 않는다. InnoDB 특성을 말해야 하면 MySQL 에서 따로 재야 한다.
- **운영 규모가 아니다.** 10만 행 / 로컬 디스크 / 기본 설정이라 `shared_buffers`, `work_mem`,
  `random_page_cost` 같은 실제 튜닝 변수의 영향은 관측되지 않는다.
- **버전 의존이 생겼다.** 계획 문자열과 SQLState 는 PostgreSQL 16 기준이다.
  메이저 버전이 바뀌면 계획 표현이 달라질 수 있다.

면접에서는 이 경계를 그대로 말하는 편이 강하다:
"PostgreSQL 16 으로 계획 전환까지 실측했고, InnoDB 의 gap lock 은 별도 확인이 필요합니다."

## 4. 벤치마크가 아니다

CON-02(카운터 비교)는 **JMH 가 아니다.** 단발 벽시계 측정이라

- 워밍업이 부족해 JIT 컴파일 시간이 섞여 있고,
- GC 발생 여부에 따라 값이 흔들리고,
- 실행마다 순위가 뒤집힐 수 있다.

그래서 정확성(합계 일치)만 `expect` 로 두고, 처리 시간은 `fact` 로만 기록한다.
"LongAdder 가 더 빠르다"는 `expectFlaky` 라서, 뒤집혀도 `REFUTED` 가 아니라 `INCONCLUSIVE` 가 된다.
**절대값이 아니라 자릿수만 신뢰할 것.**

## 5-0. MSA 케이스: 어디까지가 실물인가 (2026-08-12 갱신)

`verify-labs` 의 MSA 케이스는 여전히 **절반이 모사**다. 무엇이 실물인지 구분해 둔다.

| 케이스 | 실물 | 모사 |
|---|---|---|
| `MSA-01` Outbox | PostgreSQL 트랜잭션 | 브로커(`FlakyBroker`) |
| `MSA-05` Expand/Contract | PostgreSQL DDL (락 비용은 `DB-11`) | — |
| `MSA-02` 이벤트 순서 | — | 전부 인메모리 모델 |
| `MSA-03` 큐 부하 평준화 | — | 전부 인메모리 모델 |
| `MSA-04` 헤드 오브 라인 블로킹 | — | 전부 인메모리 모델 |

인메모리 모델은 엄밀히 말하면 **"내 모델이 내 모델과 일치한다"**를 확인하는 것이다.
그래서 같은 명제를 실물 브로커로 다시 검증하는 `verify-labs-kafka` 모듈을 만들었다 —
`KAFKA-01`(순서), `KAFKA-02`(랙), `KAFKA-03`(HoL) 이 각각 `MSA-02`·`MSA-03`·`MSA-04` 의 실물 판이다.
**둘 다 남겨 둔 이유**는, 인메모리 판은 브로커 없이도 돌아 이식성이 있고 실물 판은 진짜 증거라서다.

## 5. 단일 JVM 의 한계

RES-01(멱등성)과 RES-02(스탬피드)는 `ConcurrentHashMap` 과 로컬 캐시로 검증한다.
이것은 **단일 프로세스 안에서만 유효한 보장**이다.

- 멱등성의 진짜 근거는 Redis `SET NX` + TTL 이나 DB 유니크 제약이다.
  → **이 부분은 해소됐다.** `DB-12` 가 PostgreSQL 유니크 제약으로 같은 명제를 검증한다.
  커넥션 20개가 동시에 같은 멱등 키로 들어와도 정확히 1건만 통과(23505)하며,
  이 보장은 인스턴스 수와 무관하다. RES-01 은 "단일 JVM 판", DB-12 는 "분산 판"이다.
- `@Cacheable(sync=true)` 는 인스턴스마다 독립이라, N대면 원본 호출이 최대 N회다. (이건 그대로 한계다)

분산 환경 검증은 이 랩의 범위 밖이다. Redis·다중 인스턴스를 붙이려면
`docker-compose` 와 통합 테스트가 필요하고, 그 시점에 "컴팩트"라는 전제가 깨진다.

## 6. AI 케이스가 증명하는 것과 못 하는 것

`AI-01`~`AI-06` 은 **실제 임베딩 모델도 LLM 도 쓰지 않는다.** 랜덤 벡터와 손으로 만든 가짜 검색기로,
"알고리즘의 성질"만 검증한다.

- 증명하는 것: PSI 가 분포 변화에 단조 증가한다 / RRF 가 순위만으로 두 검색기를 합친다 /
  nprobe 를 넓히면 재현율이 오른다 / 양자화가 메모리를 1/4 로 줄인다 / 권한 전필터와 후필터의 결과 차이.
- 증명하지 못하는 것: **실제 검색 품질**. Recall@k 의 절대값, 리랭커의 효과, 청킹 전략의 우열은
  실제 문서·실제 임베딩·사람 평가가 있어야 나온다.
- 특히 `AI-04` 의 "단순 절단 시 재현율 붕괴"는 랜덤 벡터라서 더 극단적으로 나온다.
  이 결과는 "마트료시카는 학습 기법이지 공짜 연산이 아니다"라는 **명제의 방향**만 뒷받침한다.

## 7. 케이스별 남은 제품 의존성 (추가)

- `DB-05`(UUID PK): PostgreSQL 은 힙 테이블 + 별도 B-tree 라, PK 순서가 곧 물리 저장 순서인 InnoDB 와 다르다.
  여기서 재는 것은 **PK 인덱스에 랜덤 삽입할 때의 비용**이고, InnoDB 특유의 페이지 분할 비용은 아니다.
  UUIDv7 의 정렬 가능성만이 제품 무관하게 결정적이다.
- `DB-07`(데드락): PostgreSQL 은 `deadlock_timeout`(기본 1s)이 지난 뒤 순환을 탐지해 한쪽을 40P01 로 끊는다.
  탐지 시점과 희생자 선택 규칙은 제품마다 다르므로, **"순서를 통일하면 사라진다"는 명제만** 제품 독립이다.
- `MSA-05`(Expand/Contract): PostgreSQL 의 `ALTER TABLE ... DROP COLUMN` 은 카탈로그만 갱신하는 즉시 연산이다.
  MySQL 은 버전과 알고리즘에 따라 테이블 재작성이 걸릴 수 있으므로 실제 운영 절차에는 그 시간이 추가된다.
- `DB-02`·`DB-06`(풀): PostgreSQL 의 커넥션은 프로세스라 **서버 쪽 `max_connections` 상한이 실재한다.**
  풀 크기를 크게 잡으면 애플리케이션이 아니라 DB 가 먼저 거절할 수 있다 — 인메모리에서는 없던 제약이다.
- `DB-10`(CDC): **서버가 `wal_level=logical` 이어야 한다.** `compose.yaml` 은 그렇게 띄우지만,
  직접 띄운 PostgreSQL 이 기본값(`replica`)이면 이 케이스는 판정을 내리지 않고 `INCONCLUSIVE` 로 남는다.
  "설정이 없어서 검증 못 했다"를 리포트에 남기는 것이 조용히 통과시키는 것보다 낫다.
- `DB-11`(DDL 락): 측정하는 것은 **락 대기 시간**이지 DDL 자체의 성능이 아니다.
  재작성 소요(350ms)는 20만 행 기준이라 운영 규모에서는 자릿수가 달라진다.

## 8. 커버하지 않는 영역

의도적으로 넣지 않은 것들:

- **GC 튜닝·힙 덤프 분석** — 실행 시간이 길고 결과가 장비에 크게 좌우된다.
- **네트워크 타임아웃/서킷브레이커 실측** — 외부 의존이 필요하다. RES-03 은 로컬 흉내에 그친다.
- **Kafka·분산 트랜잭션·합의 알고리즘** — 별도 프로젝트가 있다면 그쪽 랩이 적합하다.
- **JVM 플래그별 동작 비교** — 별도 JVM 을 띄워야 해서 하네스 구조가 커진다.

이 항목들이 필요해지면 `verify-core` 를 그대로 쓰고 케이스만 다른 모듈에 추가하면 된다.
그것이 core/labs 를 나눠 둔 이유다.
