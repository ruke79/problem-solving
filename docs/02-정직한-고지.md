# 정직한 고지 — 이 랩이 증명하는 것과 증명하지 못하는 것

## 1. 실행 현황 (2026-08-13 갱신)

```
$ ./scripts/random-ports.sh && docker compose up -d && ./gradlew test

- 합계 88건 | CONFIRMED 88 | REFUTED 0 | INCONCLUSIVE 0 | ERROR 0   (verify-labs)
- 합계  7건 | CONFIRMED  7 | REFUTED 0 | INCONCLUSIVE 0 | ERROR 0   (verify-labs-kafka)
```

**검증 케이스 95건 · 12개 분류** — db 25 / resilience 11 / spring 7 / kafka 7 / jvm 7 / jpa 7 /
ai 7 / security 5 / msa 5 / concurrency 5 / api 5 / observability 4.
실행 환경은 Java 17.0.19 / Linux / **4코어**다.

- **케이스마다 독립된 테스트로 돈다.** 예전에는 전건이 테스트 하나였다. 지금은 95개 노드가 생겨
  어느 케이스가 통과·실패했는지 목록에서 바로 보이고, `-Dverify.only=DB-14` 로 하나만 다시 돌릴 수 있다
  (`docs/05` §19).
- **REFUTED 는 지금까지 0 이다.** 한 번 나왔던 `KAFKA-05` REFUTED 는 답변이 아니라
  **컨슈머 그룹 이름이 실행 간에 공유된 것**이 원인이었다. 인위적으로 재현해 증상을 일치시킨 뒤
  그룹 이름에 실행 단위 접미사를 붙여 해결했다(`docs/05` §14).
  **거짓 REFUTED 였다는 점이 중요하다** — 이 랩에서 REFUTED 는 "원고를 고쳐야 한다"는 신호이므로,
  격리 실패가 그 신호를 만들어서는 안 된다.
- **INCONCLUSIVE 는 최근 연속 실행에서 0 이다.** 다만 **"항상 0"을 보장하지는 않는다** — 아래 §2 참고.

### 1-1. 흔들리던 항목을 어디까지 추적했나

INCONCLUSIVE 를 줄이는 과정에서 **"환경 의존이라 어쩔 수 없다"고 적었던 것이 여섯 번 틀렸다.**
전부 측정 하네스 쪽 결함이었다.

| 케이스 | 겉보기 원인 | 실제 원인 | 근거 |
|---|---|---|---|
| `DB-14` | 옵티마이저 변덕 | `VACUUM` 누락(visibility map) + **판별식 오류** | `docs/05` §13 |
| `JVM-06` | 측정 해상도 | **교과서 패턴이 JDK 에서 최적화됨** | §13 |
| `RES-05` | 타이밍 운 | 4코어에서 경쟁 자체가 미발생 | §13 |
| `CON-02` | 4코어라 경합 부족 | **오토박싱** + 워밍업 없음 + 몰아서 재기 | §20 |
| `CON-03` | JIT 은 원래 비결정적 | 워밍업 없음 + 신호가 컴파일보다 빠름 | §21 |
| `DB-06` | 풀 타이밍은 원래 흔들림 | **acquire(대기)를 usage 에 섞어 잼** | §21 |

`DB-24`(복제 지연)만 진짜 인프라 문제였고, 레플리카에 `recovery_min_apply_delay=2s` 를 걸어 해소했다.

### 1-2. 흔들림보다 나쁜 것 — 헛통과

이어서 `expectFlaky` **40개를 전수 점검**했다(`docs/05` §22). 6회 전건에서 흔들린 항목은 없었지만
`DB-03`·`DB-15`·`DB-22` 가 성능 비교를 **밀리초로 잘라 `<=` 로** 하고 있었다.

```java
long millisAfter = (System.nanoTime() - began) / 1_000_000L;   // 0 이 되기 쉽다
evidence.expectFlaky("인덱스 적용 후가 더 빠르다", millisAfter <= millisBefore);   // 0 <= 0 → 통과
```

실제로 `DB-15` 의 전방 일치와 `DB-03` 의 인덱스 후가 `0ms` 로 찍히고 있었다.
**둘 다 0이면 근거 없이 CONFIRMED 가 찍힌다** — 흔들려서 INCONCLUSIVE 가 나는 것보다 나쁘다.
INCONCLUSIVE 는 리포트에 흔적이 남지만 헛통과는 아무것도 남기지 않기 때문이다.
마이크로초 측정 + 최소 여유 요구로 고쳤다.

> 성능을 비교하는 검증은 **해상도**와 **최소 여유**를 함께 정해야 한다.
> 이 랩이 이번 점검에서 얻은 가장 쓸모 있는 규칙이다.

### 1-3. 검증하지 못한 것

- **Kubernetes.** k3s 컨트롤 플레인까지는 실제로 띄웠지만(노드 Ready, API 정상)
  **모든 파드가 runc 단계에서 실패**해 `Q70`·`Q74`·`Q110` 을 확인할 수 없었다.
  API 레벨만 보는 케이스를 올리면 "검증한 척"이 되므로 **만들지 않았다**(`docs/05` §18).
- **`Q160`~`Q164` LLM 품질·SSE.** 실제 모델이 있어야 의미가 생긴다. 가짜로 대체하면
  "성질"만 보는 케이스가 되는데 이 문항들이 묻는 것은 **품질**이다(`docs/09` §7).

### 1-4. 실행 전제

- **인프라 4종이 필요하다.** PostgreSQL 16(+pgvector) · 스트리밍 레플리카 · Kafka 3.9 · Redis 7.
  H2 를 걷어냈으므로 **DB 없이는 테스트가 돌지 않는다.**
  없는 인프라에 해당하는 케이스는 **REFUTED 가 아니라 INCONCLUSIVE** 로 남고 나머지는 정상 동작한다.
- **호스트 포트는 고정하지 않는다.** 5432·9092·6379 는 개발 장비에서 충돌하기 쉬워,
  도커가 배정하거나 `scripts/random-ports.sh` 가 빈 포트를 고른다. 테스트는 실제 포트를 자동 감지한다(`docs/05` §15).
- **`gradle/wrapper/gradle-wrapper.jar` 는 저장소에 있다.** `gradle wrapper` 선행 실행 없이 `./gradlew` 를 쓰면 된다.
- **성능 수치는 장비에 좌우된다.** 리포트의 소요 시간은 위 환경 기준이며 그대로 인용하면 안 된다.

## 2. 판정 강도 — `expectFlaky` 40개를 어떻게 나눴나

케이스가 아니라 **검증 항목 단위**로 센다. 코드에 `expectFlaky`·`expectEqualsFlaky` 호출은
**40곳**이고, 나머지는 전부 결정적 `expect` 다.

| 성격 | 항목 수 | 뜻 |
|---|---|---|
| 하네스 결함이라 고침 | 5 | `CON-02` `CON-03` `DB-03`(속도) `DB-15` `DB-22` — 더는 흔들리지 않는다 |
| **인프라·조건 게이트** | 8 | `expectFlaky(..., false)` 로 "검증 못 했다"를 남기는 정상 용법 |
| 여유가 수십 배라 그대로 둠 | 7 | 단발 측정이지만 실측 차이가 10~500배라 실질 위험이 없다 |
| **본질적 비결정** | 20 | 결과를 정하는 것이 우리 손 밖에 있다 |
| 합계 | 40 | |

> 게이트 8곳: `AI-07`(pgvector) · `DB-10`(wal_level) · `DB-13`·`DB-25`(롤 생성 권한) ·
> `DB-24`(레플리카 접속) · `RES-11`(Redis) · `DB-24`(재생 지연이 없는 환경이면 단정하지 않는 폴백) ·
> `KafkaAvailability`(브로커 부재 — `KAFKA-01`~`06` 이 공유하는 헬퍼 한 곳).
> 마지막 둘은 **인프라가 갖춰진 실행에서는 아예 실행되지 않는다** — 그래서 평소 관측되는 flaky 항목은 32개다.

**본질적 비결정 20개**는 여섯 갈래다(항목별 상세는 `docs/05` §22).

| 갈래 | 개수 | 대표 |
|---|---|---|
| 옵티마이저가 계획을 고른다 | 3 | `DB-03` 선택도별 인덱스 사용, `AI-07` HNSW 전환 |
| 근사 알고리즘의 확률적 성질 | 4 | `AI-03` 재현율, `OBS-03` 샘플링에서 희귀 오류 소실 |
| JVM 런타임(JIT·GC) | 3 | `CON-01` HashMap 갱신 손실, `JVM-04` Weak/Soft 회수 |
| 스레드·락 타이밍 | 7 | `DB-07` 데드락 성립, `CON-05` 탐지 시점, `RES-02` 미스 겹침 |
| DB 내부 상태 | 2 | `DB-08` autovacuum 시점, `DB-10` 체크포인트 |
| 구현체 버전 의존 | 1 | `JPA-05` 배치 SQL 수가 이론값과 일치 |

> 옵티마이저 항목은 `SET enable_seqscan = off` 로 강제할 수 있다. 하지만 그러면
> **"옵티마이저가 고른다"는 명제 자체를 검증하지 못한다** — 우리가 고른 것을 확인하는 셈이다.
> 그래서 강제하지 않는다.

`nondeterministic()` 이 `true` 인 케이스는 `INCONCLUSIVE` 여도 테스트가 실패하지 않는다.
**결과를 못 냈다는 사실 자체를 리포트에 남기는 것**이 이 설계의 목적이다.
반대로 말하면 **더 느리거나 코어가 적은 장비에서는 INCONCLUSIVE 가 날 수 있고, 그것이 정상 결과다.**

## 2-1. 부록 — INCONCLUSIVE 4건을 추적한 기록 (2026-08-13)

"인프라를 추가하면 CONFIRMED 로 바뀌는가"를 확인하려고 PostgreSQL·레플리카·Kafka·Redis 4종을
전부 올린 상태에서 재실행했다. **결과는 '아니오'였다.** 4건 모두 인프라가 아니라 각기 다른 이유로 막혀 있었고,
그중 둘은 답변이 아니라 **랩 자신의 버그**였다.

| 케이스 | 막혀 있던 진짜 이유 | 조치 | 결과 |
|---|---|---|---|
| `DB-24` 복제 지연 | 프라이머리와 레플리카가 같은 도커 호스트라 복제가 수 ms 만에 따라잡아 '옛 값이 보이는' 창이 열리지 않았다 | 레플리카에 `recovery_min_apply_delay=2s` — WAL 재생을 실제로 늦추는 PostgreSQL 정식 기능 | CONFIRMED |
| `DB-14` 커버링 인덱스 | `ANALYZE` 만 했다. Index Only Scan 은 **visibility map** 이 세팅돼야 선택되고, 그건 `VACUUM` 이 한다 | `VACUUM (ANALYZE)` 추가 | CONFIRMED |
| `JVM-06` ReDoS | 랩이 고른 교과서 예제 `^(a+)+$` 가 **Java 17 에서는 폭발하지 않는다**(반복 몸통이 단일 문자 클래스라 결정적) | 몸통이 비결정적인 `(.*a){12}b` 로 교체 + 마이크로초 측정 + JIT 워밍업 | CONFIRMED |
| `RES-05` Rate Limit 경쟁 | 32스레드를 동시에 풀어 놓아도 4코어에서는 앞선 스레드가 확인·소비를 끝내 버려 경쟁이 일어나지 않았다 | '전원 확인 → 배리어 → 전원 소비' 최악 인터리빙을 명시적으로 고정 | CONFIRMED |

이 과정에서 **랩의 판별식 두 개가 틀렸다는 것**이 드러났고, 그 자체를 검증 항목으로 승격했다.

1. **`Index Cond` 유무로 '인덱스를 제대로 탔는가'를 판별할 수 없다.** PostgreSQL 16 은 후행 컬럼만 준
   `WHERE b = 42` 에도 `Index Only Scan ... Index Cond: (b = 42)` 라고 찍는다. 트리를 좁혀 내려간 게 아니라
   인덱스 전체를 훑으며 조건을 인덱스 안에서 확인한 것뿐이다. 실측 비용은 선행 컬럼 8.41 대 후행 컬럼 3706.93 —
   **같은 'Index Cond' 인데 441배**다. 그래서 판별을 비용 비교로 바꿨다.
2. **'중첩 수량자를 쓰면 지수적으로 터진다'는 Java 17 에서 그대로 재현되지 않는다.**
   `^(a+)+$`·`^(a*)*$`·`^(a|aa)+$`·`(x+x+)+y` 를 입력 길이 60 까지 올려도 전부 즉시 끝났다.
   폭발한 것은 반복 몸통이 비결정적인 `(.*a){12}b` 뿐이다(길이 16 에서 3.1ms → 22 에서 142ms, 45.9배).
   조건은 '중첩 수량자'라는 모양이 아니라 **'반복되는 그룹의 몸통이 비결정적인가'** 다.
   `(?>.*a){12}b` 로 원자적 그룹을 씌우면 같은 입력이 51us 에 끝난다.

덤으로 `DB-05`(UUID PK)도 같은 방식으로 다시 짰다. 삽입 '시간' 비교는 2만 행 규모에서 캐시·WAL 잡음에
묻혀 실행마다 뒤집혔으므로, 주장의 메커니즘인 **페이지 분할의 결과(인덱스 크기)** 를 직접 재도록 바꿨다.
그러다 또 하나가 나왔다 — 이 랩의 UUIDv7 은 2만 개를 **3~4개의 밀리초 안에** 만들어 버려서
같은 타임스탬프를 가진 수천 개가 서로 랜덤이었다. 즉 **타임스탬프만 쓰는 v7 은 고빈도 생성에서 v4 에 가까워진다.**
RFC 9562 6.2절의 단조 카운터를 넣고 나서야 인덱스가 제대로 조밀해졌다(v4 ÷ v7 = 1.25~1.30배,
타임스탬프만 쓴 v7 ÷ 카운터판 v7 = 1.14~1.34배).

> 이 절의 결론: INCONCLUSIVE 는 "인프라가 없어서"보다 **"랩이 현상을 관측할 조건을 못 갖춰서"** 인 경우가 더 많았다.
> 그리고 그 조건을 갖추는 과정에서 나온 것들(VACUUM 과 visibility map, Index Cond 의 함정, Java 17 의 정규식 최적화,
> UUIDv7 의 카운터)이 원래 검증하려던 명제보다 실무에 더 쓸모 있는 내용이었다.

## 3. PostgreSQL 16 을 쓴다 — 얻은 것과 남은 한계

DB 케이스는 **PostgreSQL 16 실물**에서 돈다. H2 인메모리를 걷어내면서 달라진 점:

- `DB-01`(격리 수준): PostgreSQL 의 REPEATABLE READ 는 **스냅샷 격리**라 재읽기 값이 결정적으로 고정된다.
  H2 시절 `expectFlaky` 로 물러서 있던 항목을 `expect` 로 올렸고, 케이스의 `nondeterministic()` 도 껐다.
- `DB-03`(실행계획): 진짜 옵티마이저의 계획 문자열과 비용 추정치를 그대로 읽는다.
  `Seq Scan` → `Index Only Scan using idx_scan_demo_k` 전환이 관측된다.
  다만 **계획 선택은 옵티마이저의 몫**이라 이 항목들은 `expectFlaky` 다(§2) —
  "항상 이렇게 나온다"가 아니라 "이 데이터에서는 이렇게 골랐다"가 정확한 표현이다.
- `DB-07`(데드락): `SQLState=40P01`(deadlock detected)과 `55P03`(lock_not_available)을 구분할 수 있다.
  "데드락이 났다"와 "락 타임아웃이 났다"를 섞지 않는다 — 이 구분이 실제로 랩의 버그 하나를 잡아냈다.

그래도 **남는 한계**는 분명하다.

- **MySQL InnoDB 가 아니다.** gap lock 기반 팬텀 방지, 클러스터 인덱스, `SHOW ENGINE INNODB STATUS` 는
  여기서 재현되지 않는다. InnoDB 특성을 말해야 하면 MySQL 에서 따로 재야 한다.
- **운영 규모가 아니다.** 10만 행 / 로컬 디스크 / 기본 설정이라 `shared_buffers`, `work_mem`,
  `random_page_cost` 같은 실제 튜닝 변수의 영향은 관측되지 않는다.
- **버전 의존이 생겼다.** 계획 문자열과 SQLState 는 PostgreSQL 16 기준이다.
  메이저 버전이 바뀌면 계획 표현이 달라질 수 있다.

면접에서는 이 경계를 그대로 말하는 편이 강하다:
"PostgreSQL 16 으로 계획 전환까지 실측했고, InnoDB 의 gap lock 은 별도 확인이 필요합니다."

## 4. 벤치마크가 아니다 (다만 하네스는 고쳤다)

시간을 재는 케이스는 **JMH 가 아니다.** 벽시계 측정이라 절대값이 아니라 **자릿수만** 신뢰해야 한다.

다만 "벤치마크가 아니니 흔들려도 어쩔 수 없다"로 넘기지는 않았다.
`CON-02`(카운터 비교)는 원래 이 절에 "워밍업이 부족하다"고 적혀 있었는데, 그것이 실제 결함이었다.

| 무엇이 문제였나 | 조치 |
|---|---|
| 작업을 `Consumer<Integer>` 로 받아 **반복마다 오토박싱**(8스레드 × 20만 = 160만 개) | `Runnable` 로 교체 |
| 워밍업 없이 한 번만 측정 | 워밍업 후 5회 측정, 최소값 사용 |
| 세 방식을 **몰아서** 순차 측정 → 부하가 바뀌면 한쪽만 손해 | 회차마다 번갈아 측정 |

고친 뒤 LongAdder 가 AtomicLong 보다 **5.8~10.2배** 빠른 것이 안정적으로 관측된다.
정확성(합계 일치)은 여전히 `expect`, 속도 비교는 `expectFlaky` 라 뒤집혀도 `INCONCLUSIVE` 가 된다.

**여전히 남는 한계**: GC 발생 여부, 코어 수, 다른 프로세스의 부하는 통제하지 못한다.
JMH 가 하는 포크·죽은 코드 제거 방지·통계 처리도 없다. 자릿수만 읽을 것.

## 5-0. MSA 케이스: 어디까지가 실물인가 (2026-08-12 갱신)

`verify-labs` 의 MSA 케이스는 여전히 **절반이 모사**다. 무엇이 실물인지 구분해 둔다.

| 케이스 | 실물 | 모사 |
|---|---|---|
| `MSA-01` Outbox | PostgreSQL 트랜잭션 | 브로커(`FlakyBroker`) |
| `MSA-05` Expand/Contract | PostgreSQL DDL (락 비용은 `DB-11`) | — |
| `MSA-02` 이벤트 순서 | — | 전부 인메모리 모델 |
| `MSA-03` 큐 부하 평준화 | — | 전부 인메모리 모델 |
| `MSA-04` 헤드 오브 라인 블로킹 | — | 전부 인메모리 모델 |

인메모리 모델은 엄밀히 말하면 **"내 모델이 내 모델과 일치한다"**를 확인하는 것이다.
그래서 같은 명제를 실물 브로커로 다시 검증하는 `verify-labs-kafka` 모듈을 만들었다 —
`KAFKA-01`(순서), `KAFKA-02`(랙), `KAFKA-03`(HoL) 이 각각 `MSA-02`·`MSA-03`·`MSA-04` 의 실물 판이다.
**둘 다 남겨 둔 이유**는, 인메모리 판은 브로커 없이도 돌아 이식성이 있고 실물 판은 진짜 증거라서다.

## 5. 단일 JVM 의 한계

RES-01(멱등성)과 RES-02(스탬피드)는 `ConcurrentHashMap` 과 로컬 캐시로 검증한다.
이것은 **단일 프로세스 안에서만 유효한 보장**이다.

- 멱등성의 진짜 근거는 Redis `SET NX` + TTL 이나 DB 유니크 제약이다.
  → **이 부분은 해소됐다.** `DB-12` 가 PostgreSQL 유니크 제약으로 같은 명제를 검증한다.
  커넥션 20개가 동시에 같은 멱등 키로 들어와도 정확히 1건만 통과(23505)하며,
  이 보장은 인스턴스 수와 무관하다. RES-01 은 "단일 JVM 판", DB-12 는 "분산 판"이다.
- `@Cacheable(sync=true)` 는 인스턴스마다 독립이라, N대면 원본 호출이 최대 N회다. (이건 그대로 한계다)

분산 환경 검증은 이 랩의 범위 밖이다. Redis·다중 인스턴스를 붙이려면
`docker-compose` 와 통합 테스트가 필요하고, 그 시점에 "컴팩트"라는 전제가 깨진다.

## 6. AI 케이스가 증명하는 것과 못 하는 것

`AI-01`~`AI-06` 은 **실제 임베딩 모델도 LLM 도 쓰지 않는다.** 랜덤 벡터와 손으로 만든 가짜 검색기로,
"알고리즘의 성질"만 검증한다.

- 증명하는 것: PSI 가 분포 변화에 단조 증가한다 / RRF 가 순위만으로 두 검색기를 합친다 /
  nprobe 를 넓히면 재현율이 오른다 / 양자화가 메모리를 1/4 로 줄인다 / 권한 전필터와 후필터의 결과 차이.
- 증명하지 못하는 것: **실제 검색 품질**. Recall@k 의 절대값, 리랭커의 효과, 청킹 전략의 우열은
  실제 문서·실제 임베딩·사람 평가가 있어야 나온다.
- 특히 `AI-04` 의 "단순 절단 시 재현율 붕괴"는 랜덤 벡터라서 더 극단적으로 나온다.
  이 결과는 "마트료시카는 학습 기법이지 공짜 연산이 아니다"라는 **명제의 방향**만 뒷받침한다.

## 7. 케이스별 남은 제품 의존성 (추가)

- `DB-05`(UUID PK): PostgreSQL 은 힙 테이블 + 별도 B-tree 라, PK 순서가 곧 물리 저장 순서인 InnoDB 와 다르다.
  여기서 재는 것은 **PK 인덱스에 랜덤 삽입할 때의 비용**이고, InnoDB 특유의 페이지 분할 비용은 아니다.
  UUIDv7 의 정렬 가능성만이 제품 무관하게 결정적이다.
- `DB-07`(데드락): PostgreSQL 은 `deadlock_timeout`(기본 1s)이 지난 뒤 순환을 탐지해 한쪽을 40P01 로 끊는다.
  탐지 시점과 희생자 선택 규칙은 제품마다 다르므로, **"순서를 통일하면 사라진다"는 명제만** 제품 독립이다.
- `MSA-05`(Expand/Contract): PostgreSQL 의 `ALTER TABLE ... DROP COLUMN` 은 카탈로그만 갱신하는 즉시 연산이다.
  MySQL 은 버전과 알고리즘에 따라 테이블 재작성이 걸릴 수 있으므로 실제 운영 절차에는 그 시간이 추가된다.
- `DB-02`·`DB-06`(풀): PostgreSQL 의 커넥션은 프로세스라 **서버 쪽 `max_connections` 상한이 실재한다.**
  풀 크기를 크게 잡으면 애플리케이션이 아니라 DB 가 먼저 거절할 수 있다 — 인메모리에서는 없던 제약이다.
- `DB-10`(CDC): **서버가 `wal_level=logical` 이어야 한다.** `compose.yaml` 은 그렇게 띄우지만,
  직접 띄운 PostgreSQL 이 기본값(`replica`)이면 이 케이스는 판정을 내리지 않고 `INCONCLUSIVE` 로 남는다.
  "설정이 없어서 검증 못 했다"를 리포트에 남기는 것이 조용히 통과시키는 것보다 낫다.
- `DB-11`(DDL 락): 측정하는 것은 **락 대기 시간**이지 DDL 자체의 성능이 아니다.
  재작성 소요(실측 230~520ms)는 20만 행 기준이라 운영 규모에서는 자릿수가 달라진다.

## 7-1. 원고 지적도 '검증'이다 — 한 건은 철회했다 (2026-08-13)

이 랩은 케이스 판정만 고지 대상으로 삼고 있었다. 그런데 **원고 지적도 관측 결과**이고,
같은 기준을 적용하면 하나가 남지 못한다.

**지적 ⑧ 을 철회했다.** "원고의 ReDoS 예제 `^(a+)+$` 가 Java 17 에서 재현되지 않는다"였는데,
Part 5 원문을 받아 보니 **원고에 그 예제가 없었다.** 예시 자체가 없고 "애매한 패턴을 대면
입력 길이에 대해 지수적으로 처리 시간이 늘어"라고만 쓰여 있다.
`JVM-06` 의 측정은 정확했다 — 틀린 것은 **원고가 무엇을 썼는지에 대한 가정**이었다.

| | 지적 ⑧ | 랩의 `expectFlaky` |
|---|---|---|
| 실행해서 관측했나 | 예 (`JVM-06`) | 예 |
| 관측이 정확했나 | 예 | 예 |
| **비교 대상이 실재했나** | **아니오** | 예 |

세 번째 줄이 이 랩이 놓치고 있던 칸이다. 케이스에는 "재 본 것만 적는다"를 지켰으면서,
원고 지적에는 "아마 이렇게 쓰여 있을 것"을 근거로 삼았다.
`docs/10` 에 「원문 대조 필요」 표시를 붙여 두긴 했지만, **표시를 붙였다는 것이
지적을 확정 목록에 올릴 근거는 되지 않는다.** 확정 9건 → **8건**이다.

경위는 `docs/05` §23, 철회 기록은 `docs/10` §B-⑧ 에 지우지 않고 남겼다.

## 8. 커버하지 않는 영역

의도적으로 넣지 않은 것들:

- **GC 튜닝·힙 덤프 분석** — 실행 시간이 길고 결과가 장비에 크게 좌우된다.
- ~~**Kafka**~~ — **해소됐다.** `verify-labs-kafka` 가 실물 브로커(KRaft)에서 7건을 검증한다.
- ~~**서킷브레이커**~~ — **해소됐다.** `RES-04`·`RES-08` 이 resilience4j 실물로,
  `API-04` 가 WireMock 실물 HTTP 로 검증한다. 다만 `RES-03`(재시도 백오프)은 여전히 로컬 흉내다.
- **분산 트랜잭션·합의 알고리즘** — 노드를 여럿 띄워야 한다. 별도 프로젝트가 있다면 그쪽 랩이 적합하다.
- **Kubernetes** — 시도했으나 이 환경에서 파드가 뜨지 않았다(§1-3, `docs/05` §18).
- **JVM 플래그별 동작 비교** — 별도 JVM 을 띄워야 해서 하네스 구조가 커진다.

이 항목들이 필요해지면 `verify-core` 를 그대로 쓰고 케이스만 다른 모듈에 추가하면 된다.
그것이 core/labs 를 나눠 둔 이유다.

**§8 은 "안 넣기로 한 것"의 목록이다. 그런데 그 목록에 없으면서도 안 재고 있는 것들이 있다.**
아래 §9 가 그것이다.

## 9. 외부 기준과 대조해 드러난 목록 — '못 하는 것'과 '안 한 것' (2026-08-25)

`notes/java-performance/` 에 *Java Performance: The Definitive Guide* 2~12장과 부록 A 를
요약하면서, 장마다 **"이 장을 우리 랩에 비춰 보면"** 표를 붙였다.
그 표에서 **"검증 케이스 없음"** 으로 남은 줄이 **25개**다
(4장 1 · 5장 1 · 6장 1 · 7장 2 · 8장 1 · 9장 3 · 10장 3 · 11장 4 · 12장 6 · 부록 A 3).

**이 절을 쓰는 이유는 그 17개를 다 채우겠다는 것이 아니다.**
`docs/00` §8 의 원칙은 "검증한 척을 만들지 않는다"인데, 여기에는 대칭이 하나 더 있다 —
**못 하는 것과 안 한 것을 같은 칸에 넣지 않는다.** §1-3 과 §8 은 전자만 적고 있었다.
25개를 다시 나눠 보니 **대부분이 후자였다.**

> 계산이 맞는지 먼저 적어 둔다: 25줄 중 **1줄은 중복**이다(깊은 스택 예외 비용이 12장 표와
> 부록 A 표에 각각 있다). 남은 24줄은 이렇게 나뉜다 — §9-1 못 하는 것 **3**,
> §9-2 사라진 것 **2**(AggressiveOpts 와 7장 인터닝 줄. 편향 락은 표에 "없음" 줄로 잡히지 않아
> 여기 수에는 안 들어간다), §9-3 별도 JVM **3**(6장 CMS/G1, 7장 라이브 데이터,
> 5장 풀 GC 30% 경험칙), §9-4 안 한 것 **14**, 그리고 **분류하지 않은 2** —
> 9장 "스레드 우선순위는 믿을 수 없다"(부정 명제라 관측 몇 번으로 확정할 수 없다)와
> 12장 "로깅 `isLoggable()`"(잴 수는 있으나 자명해서 뒤로 미뤘다). 3+2+3+14+2 = 24.

### 9-1. 못 하는 것 — 이 환경에서 조건을 만들 수 없다

| 명제 | 책의 수치 | 왜 못 하나 |
|---|---|---|
| **압축 oop 의 32 GB 경계** (부록 A, 8장) | 힙 33 GB 가 31 GB 보다 실질 용량이 작다 | **32 GB 이상 힙을 띄울 수 없다.** 컨테이너 메모리가 그만큼 없다 |
| ~~**출력을 줄여라** (10장)~~ | ~~같은 페이지가 LAN 20ms vs WiFi 1003ms~~ | **해소됐다 (2026-08-26).** `PERF-10C` 가 EC2 배포본을 러너에서 재는 방식으로 조건을 만들었다 — 아래 §9-6 |
| **클래스로더 병렬성** (12장) | JDK 6 → 7 에서 7배 | **JDK 6 이 없다.** 병렬 클래스로더가 기본인 JDK 에서는 비교군을 만들 수 없다 |

> 이 셋을 EC2 프리티어 배포로 열 수 있는지는 `docs/11` §3 에 갈라 적었다 — **실제 네트워크는
> 열렸고**(§9-6), 32GB 는 돈의 문제로 바뀔 뿐이며, JDK 6 은 그대로 안 된다.
> **셋 중 하나가 빠져서 §9-1 은 이제 2건이다.**

### 9-2. 사라진 것 — 책이 쓰인 뒤 JDK 가 없애 버렸다

**이 세 줄은 실행해서 확인했다**(실행 환경의 `java-17-openjdk-amd64` = **17.0.19**).

```
$ java -XX:+PrintFlagsFinal -version | grep -i "UseBiasedLocking\|StringTableSize"
    uintx StringTableSize     = 65536   {product} {default}
     bool UseBiasedLocking    = false   {product} {default}

$ java -XX:+UseBiasedLocking -version
OpenJDK 64-Bit Server VM warning: Option UseBiasedLocking was deprecated in version 15.0
and will likely be removed in a future release.

$ java -XX:+AggressiveOpts -version
Unrecognized VM option 'AggressiveOpts'
```

| 항목 | 책의 권고 | 지금 |
|---|---|---|
| **편향 락** (9장, 부록 A-8) | "스레드 풀 애플리케이션에서는 `-XX:-BiasedLocking` 이 도움 되는 경우가 많다" | **JDK 15 에서 기본 비활성 + 폐기 예고.** 우리 런타임(17)에서 이미 `false` 다 — **끄라는 권고를 따를 것이 남아 있지 않다.** (제거 시점을 "JDK 18"이라고 적었었으나 **실행으로 확인한 적 없는 숫자였다.** 확인한 것은 17 에 경고와 함께 남아 있고 21 에서 인식되지 않는다는 것뿐이다 — `notes/java-performance/00-JDK-17-차이.md` §4-2) |
| **`AggressiveOpts`** (부록 A-9) | "테스트해 볼 수는 있다" | **JDK 12 에서 제거되어 옵션 자체가 인식되지 않는다** |
| **`StringTableSize`** (7장, 부록 A-7) | 기본 1009 이라 인터닝이 많으면 2.3시간까지 늘어난다 | **JDK 17 기본값이 65536 이다.** 책의 극적인 수치는 **기본값이 1009 이던 시절의 것**이라 그대로 재현되지 않는다 |

> **이 표가 §9 에서 가장 쓸모 있는 부분이라고 본다.**
> "안 재 봤다"가 아니라 **"재려고 보니 명제의 전제가 사라져 있었다"** 이기 때문이다.
> §2-1 에서 `^(a+)+$` 가 Java 17 에서 폭발하지 않는다는 것을 발견한 것과 같은 종류의 결과다.
> **유명한 책의 권고라도 런타임 버전을 확인하지 않으면 틀린 말을 하게 된다.**

### 9-3. 별도 JVM 이 필요한 것 — §8 이 이미 제외한 영역

| 명제 | 필요한 것 |
|---|---|
| CMS 동시 모드 실패 / G1 대피 실패 재현 (6장) | GC 플래그를 달리한 별도 JVM |
| 라이브 데이터 양이 힙 크기보다 GC 시간을 좌우 (7장) | 같음 |
| TLAB 할당 효율 (`-XX:+PrintTLAB`) (6장, 부록 A-7) | 같음 |

§8 의 **"JVM 플래그별 동작 비교 — 별도 JVM 을 띄워야 해서 하네스 구조가 커진다"** 에 해당한다.
`ProcessBuilder` 로 자식 JVM 을 띄우면 **원리상 가능하다.** 즉 이것도 엄밀히는 "못 하는 것"이
아니라 **"하네스를 키우기로 결정하지 않은 것"** 이다. 그렇게 적는 편이 정확하다.

### 9-5. 이 절이 바꾼 것 — 그리고 §9-4 가 케이스가 됐다 (같은 날 갱신)

**이 랩이 "안 재고 있는 것"의 목록을 처음으로 명시적으로 갖게 됐다.**

- §1-3 「검증하지 못한 것」에는 Kubernetes 와 LLM 품질 **둘뿐**이었다. 둘 다 진짜 "못 하는 것"이다.
- §8 「커버하지 않는 영역」은 **의도적으로 뺀 것**의 목록이다.
- **그 사이에 §9-4 의 14개가 있었다.** 어느 목록에도 없어서 **"없다는 사실조차 적혀 있지 않았다."**

> **무엇을 재기로 했는지를 누가 정했는지는 그 숫자에 안 나온다.**

### 9-6. §9-1 에서 한 건이 빠졌다 — `PERF-10C` (2026-08-26)

§9-1 「못 하는 것」에 있던 **"출력을 줄여라"(10장, LAN 20ms vs WiFi 1003ms)** 가 해소됐다.
막고 있던 것은 실제 광역 네트워크였고, EC2 배포(`docs/11`)가 그 조건을 만들었다.

**이 케이스는 다른 케이스와 방향이 반대다.** 다른 것들은 대상 장비 위에서 돌리면 되지만,
이건 **서버를 EC2 에 두고 클라이언트(케이스)를 러너에서 돌려야** 그 사이가 WAN 이 된다.
인스턴스 안에서 돌리면 루프백이라 명제의 조건 자체가 사라진다.

판정 규칙을 셋으로 갈랐다 — **어디서 무엇을 단정할 수 있는지가 이 케이스의 설계 전부다.**

| 항목 | 어디서 단정하나 |
|---|---|
| 두 응답의 정보가 같다 (행 수·가격 합계·경계 심볼) | 어디서든 — 결정적 `expect` |
| 표현만 다듬어 전송량이 5배 이상 준다 (실측 **20.2배**) | 어디서든 — 결정적 `expect` |
| 다듬은 판이 유의미하게 빠르다 | **원격 링크에서만.** 루프백/사설망이면 INCONCLUSIVE 로 남긴다 |

**그래서 이 케이스는 로컬과 CI 에서 항상 INCONCLUSIVE 다. 그것이 정상이고 설계다.**
`nondeterministic()` 이 `true` 라 테스트는 실패하지 않되, **"검증 못 했다"가 리포트에 남는다** —
§2 가 말한 게이트의 정상 용법이다. 루프백에서 통과시키면 그게 §1-2 의 헛통과다.

> **설계할 때의 예상이 실측과 달랐다.** "루프백이면 두 응답의 시간 차이가 사라질 것"으로 보고
> 케이스 주장에 "루프백에서는 이 차이가 보이지 않는다"를 넣어 뒀는데, 재 보니
> **루프백에서도 3.19배가 벌어졌다**(644,009 → 31,809 bytes / 24,051us → 7,548us).
> 남아 있는 것은 대역폭이 아니라 **서버가 큰 응답을 만들어 소켓에 복사하는 비용**이다.
> 주장에서 그 문장을 빼고, note 를 **"루프백에서는 링크 대역폭 성분만 사라진다"** 로 고쳤다.
> **§1-1 의 목록에 한 줄 더 붙는 셈이다 — "환경 때문에 안 보일 것"이라는 예상이 또 틀렸다.**
> 다만 이번에는 하네스 결함이 아니라 **주장 문장이 과했던 경우**다.
