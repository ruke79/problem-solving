# 원고 수정 지시서 — 확정된 지적 9건을 한 장으로

이 랩이 Q1~Q200 원고를 전수 대조해 찾은 지적을 **적용 가능한 형태로** 모았다.
원고 파일(PDF/MD)은 이 저장소 밖에 있으므로 랩이 직접 고칠 수 없다 — 아래를 그대로 옮기면 된다.

## 읽는 법

각 항목은 두 상태 중 하나다.

| 표시 | 뜻 |
|---|---|
| **원문 대조 완료** | 원고 원문을 직접 읽고 전후를 확정했다. 그대로 치환하면 된다. |
| **원문 대조 필요** | 랩 실행으로 사실관계는 확정했지만 원문 문장을 다시 확인해야 한다. 수정 방향과 넣을 문장은 아래에 있다. |

## A. 사실 오류 — 반드시 고칠 것

### ① Q64 — Base62 7자리 용량이 100배 틀렸다 · Part 5 · **원문 대조 완료**

`62^7 = 3,521,614,606,208` 이므로 **약 3.5조**다. 원고의 "약 350억"은 100배 작다.
전후 문장과 일본어판까지 → **`docs/06-원고-수정본-Part5.md` §1**

### ⑦ Q70 — SIGKILL 시점이 한 답변 안에서 30초와 25초로 어긋난다 · Part 5 · **원문 대조 완료**

`terminationGracePeriodSeconds` 기본값은 30초다. 앞 문단은 30초, 뒤 문단은 "기본값 그대로 25초"라
자기모순이다. 예시 수치를 바꾸는 수정문 → **`docs/06-원고-수정본-Part5.md` §3**

### ⑥ Q87 — 에러 버짓의 기준을 SLA 로 잡았다 · Part 6 · **원문 대조 완료**

에러 버짓의 기준은 SLO다. Q142 는 같은 개념을 SLO 기준으로 설명하고 있어 파트 간 모순이기도 하다.
수정문 → **`docs/07-원고-수정본-Part6.md` §3**

> **랩이 숫자로 뒷받침한다** (`OBS-04`). 30일 창에서 SLO 99.9% 의 에러 버짓은 **43분 12초**,
> SLA 99.5% 로 잡으면 **3시간 36분**이다. 같은 25분 장애의 소진율이 **58% → 12%** 로 보인다.
> 즉 SLA 를 기준으로 삼으면 **계약을 어기기 직전까지 아무 조치도 하지 않게 된다.**
> 이 대비를 한 줄 덧붙이면 답변이 훨씬 단단해진다:
>
> > "SLO 를 SLA 보다 빡빡하게 두는 이유가 이 완충 구간입니다. 99.9% 기준이면 30일에 43분인데,
> > 계약선인 99.5% 로 재면 3시간 36분이라 같은 장애가 절반 소진에서 10% 소진으로 보입니다."

## B. 실물에서 재현되지 않는 예제

사실 오류는 아니지만 **면접에서 "직접 재 보셨나요"를 받으면 가장 곤란해지는** 형태다.

### ⑧ Q67 — ReDoS 예제 `^(a+)+$` 가 Java 17 에서 폭발하지 않는다 · Part 5 · **원문 대조 필요**

랩 실측(`JVM-06`, Java 17.0.19):

| 패턴 | n=20 | n=30 | n=40 | n=60 |
|---|---|---|---|---|
| `^(a+)+$` | 144us | 155us | 252us | 344us |
| `^(a*)*$` | 91us | — | — | 즉시 |
| `^(a\|aa)+$` | 615us | 192us | 166us | 79us |
| `(x+x+)+y` | 1441us | 1670us | 2980us | 1577us |
| **`(.*a){20}b`** | **48ms** | **1060ms** | **>4s** | **>4s** |

교과서 예제는 전부 즉시 끝난다. 폭발 조건은 '중첩 수량자'라는 **모양**이 아니라
**반복되는 그룹의 몸통이 비결정적인가**다. `a+` 는 단일 문자 클래스라 결정적이어서
엔진이 되돌아갈 필요가 없다.

**넣을 문장 (KR)**

> "예를 들어 `(.*a){12}b` 처럼 반복되는 그룹 안이 `.*` 로 열려 있으면, 입력이 조금만 길어져도
> 시간이 배로 뜁니다. 실제로 재 보면 길이 16에서 3밀리초, 22에서 142밀리초로 46배가 됩니다.
> 다만 교과서에 흔히 나오는 `^(a+)+$` 는 최신 JDK 에서 최적화돼 재현되지 않습니다 —
> 반복 몸통이 단일 문자라 엔진이 되돌아갈 필요가 없기 때문입니다.
> 그래서 저는 '중첩 수량자'라는 모양보다 **반복 그룹의 몸통이 비결정적인가**로 판단합니다.
> 방어는 원자적 그룹 `(?>...)` 이나 소유 수량자 `*+` 로 백트래킹을 막는 것이고,
> 같은 입력이 51마이크로초로 끝납니다."

**넣을 문장 (JP)**

> 「例えば `(.*a){12}b` のように、繰り返すグループの中が `.*` で開いていると、入力が少し長くなるだけで
> 時間が倍に跳ね上がります。実測では長さ16で3ミリ秒、22で142ミリ秒と46倍になりました。
> ただし教科書によく出る `^(a+)+$` は最新のJDKでは最適化されて再現しません。
> 繰り返しの中身が単一文字クラスで決定的なため、エンジンが戻る必要がないからです。」

> **적용 시 확인**: 원고에서 `^(a+)+$` 를 언급한 위치를 찾아 위 문장으로 교체한다.
> 이 항목은 랩 실측으로 사실관계를 확정했으나 원고 원문 문장은 다시 대조해야 한다.

### ⑨ Q106 · Q107 — UUIDv7 설명에 '단조 카운터'가 빠져 있다 · Part 8 · **원문 대조 필요**

원고는 "UUIDv7 은 앞부분이 타임스탬프라 시간순 정렬이 되므로 페이지 분할 문제를 피한다"고 말한다.
맞지만 **고빈도 생성에서는 성립하지 않는다.** 랩 실측(`DB-05`):

```
20000개를 만드는 동안 바뀐 밀리초 수 = 3~4
밀리초당 생성 개수 = 5000~6666
```

| 방식 | 카운터판 v7 대비 PK 인덱스 크기 |
|---|---|
| UUID v4 (완전 랜덤) | 1.25~1.30배 |
| UUIDv7 (타임스탬프만) | 1.14~1.34배 |
| UUIDv7 (RFC 9562 단조 카운터) | 기준 |

같은 밀리초를 공유하는 수천 개가 서로 랜덤이므로, 타임스탬프만 쓰는 v7 은 v4 에 가깝게 부푼다.

**덧붙일 문장 (KR)**

> "다만 v7 이라고 다 같지는 않습니다. 초당 수천 건을 만들면 같은 밀리초 안에 수천 개가 몰리고
> 그 안은 랜덤이라 v4 와 비슷해집니다. 실제로 2만 건을 3~4밀리초 안에 만들어 보면
> 인덱스 크기가 카운터판보다 1.2배 부풀었습니다. RFC 9562 6.2절이 규정한
> **밀리초 내 단조 카운터**를 구현한 라이브러리인지 확인해야 합니다."

**덧붙일 문장 (JP)**

> 「ただしv7なら同じというわけではありません。秒間数千件を生成すると同じミリ秒に数千個が集中し、
> その中はランダムなのでv4と大差なくなります。RFC 9562の6.2節が定める
> **ミリ秒内の単調カウンタ**を実装したライブラリかどうかを確認する必要があります。」

## E. 적용 순서 제안

1. **A 의 3건**을 먼저 고친다 — 숫자가 틀린 것이라 지적당하면 바로 신뢰를 잃는다.
2. **C 의 표현 오류**를 일괄 치환한다 — 기계적이라 빠르다.
3. **B 의 2건**은 원문을 다시 열어 위치를 찾은 뒤 문장을 교체한다.
4. **D 의 보강**은 시간이 남을 때. 넣으면 "외운 답변"과 "재 본 답변"의 차이가 드러난다.

> 이 지시서는 랩의 실행 결과에 근거한다. 각 항목의 근거 케이스를 `./gradlew test` 로 다시 돌려
> 숫자를 직접 확인할 수 있고, 리포트는 `verify-labs/build/reports/verification.md` 에 남는다.
