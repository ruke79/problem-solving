# CI/CD 와 EC2 프리티어 배포 검증

## 1. 무엇이 추가됐나

| 파일 | 하는 일 |
|---|---|
| `.github/workflows/ci.yml` | 커밋마다 실물 인프라(compose)를 띄우고 **109건 전부** 실행, 리포트를 아티팩트로 남긴다 |
| `.github/workflows/deploy-ec2.yml` | **수동 실행** — 저장소를 EC2 에 rsync 로 올리고, 그 장비에서 스위트를 돌린 뒤 리포트를 회수한다 |
| `scripts/ec2-setup.sh` | 인스턴스 1회 초기 설정 (Java 17 · Docker · Compose · **스왑 2GB**) |
| `scripts/ec2-run-verify.sh` | 인스턴스 위에서 스위트 실행 (`perfbook` 기본 / `full` 선택) |

CI 는 "빌드가 된다"가 아니라 **"명제가 이 환경에서도 재현된다"** 를 확인한다.
그래서 서비스 컨테이너 흉내 없이 로컬과 같은 절차(`random-ports.sh` → `compose up --wait` →
`gradlew test`)를 그대로 쓴다.

## 2. EC2 프리티어 설정 절차 (한 번만)

1. **인스턴스 생성** — Amazon Linux 2023, `t2.micro` 또는 `t3.micro`(RAM 1GB), 키 페어 생성.
   보안 그룹은 **22(SSH)만 인바운드 허용**. GitHub Actions 러너의 IP 는 고정이 아니므로
   소스를 좁히려면 [GitHub 의 공개 IP 대역](https://api.github.com/meta)을 등록해야 한다 —
   키 인증만으로 갈 거면 0.0.0.0/0 이 편하지만 그만큼 스캔 트래픽을 받는다.
2. **초기 설정 스크립트 실행**
   ```bash
   scp -i <키.pem> scripts/ec2-setup.sh ec2-user@<호스트>:~
   ssh -i <키.pem> ec2-user@<호스트> 'bash ec2-setup.sh'
   # 재접속 후: docker info >/dev/null && echo OK
   ```
3. **저장소 시크릿 등록** — Settings → Secrets and variables → Actions:
   `EC2_HOST`(퍼블릭 IP/DNS) · `EC2_USER`(`ec2-user`) · `EC2_SSH_KEY`(PEM 전문).
4. **실행** — Actions 탭 → `deploy-ec2` → Run workflow. 스위트 선택:
   - `perfbook`(기본): PostgreSQL 만 띄우고 14건. **1GB 인스턴스에서 완주하도록 설계한 쪽이다.**
   - `full`: 109건. Kafka·Redis·레플리카까지 띄우므로 **RAM 2GB(t3.small) 이상**에서만 돌 것이다.

끝나면 워크플로 아티팩트 `ec2-verification-reports` 에 그 장비의 판정 리포트가 담긴다.

> **요금에 대한 정직한 고지**: "프리티어면 공짜"를 이 문서가 보장하지 않는다. AWS 는 2025년
> 이후 신규 계정의 프리티어를 크레딧 방식으로 바꿨고, EBS·트래픽 등 부대 비용은 계정 조건에
> 따라 다르다. **인스턴스를 쓰지 않을 때는 중지(stop)해 두는 것**까지가 배포 테스트의 일부다.

## 3. §9-1 과의 관계 — 무엇이 열리고, 무엇은 여전히 안 되나

이 배포 환경은 `docs/02` §9-1(못 하는 것 3건)을 겨냥해 만들었다. **정직하게 갈라 적는다.**

| §9-1 항목 | 프리티어 배포로 열리나 |
|---|---|
| **실제 네트워크** (10장 "출력을 줄여라", LAN 20ms vs WiFi 1003ms) | **열렸다 — 케이스가 생겼다(`PERF-10C`).** 아래 §5 참고. 단, **CONFIRMED 는 원격 링크에서만** 나온다 — 로컬/CI 에서는 게이트로 INCONCLUSIVE 로 남는다 |
| **압축 oop 32GB 경계** (부록 A) | **여전히 안 된다.** 프리티어는 RAM 1GB — 32GB 힙은 r5.xlarge 급(프리티어 밖, 유료)이 필요하다. 배포 방식의 문제가 아니라 돈의 문제로 바뀌었을 뿐이다 |
| **클래스로더 병렬성** (JDK 6 대비 7배) | **여전히 안 된다.** EC2 라고 JDK 6 이 생기지 않는다 |

즉 이 CI/CD 가 §9-1 에서 실제로 여는 것은 **셋 중 하나(실제 네트워크)의 전제 조건**이고,
나머지 둘은 배포로 풀리는 문제가 아니다.

## 4. EC2 실행 결과를 읽을 때

- **1 vCPU 에서 `PERF-09A`(거짓 공유)·`PERF-09B`(암달)는 INCONCLUSIVE 가 정상이다.**
  스레드 4개가 코어 1개를 나눠 쓰면 경합·병렬성 명제의 관측 조건 자체가 성립하지 않는다
  (`docs/02` §2 — "코어가 적은 장비에서는 INCONCLUSIVE 가 날 수 있고, 그것이 정상 결과다").
- 반대로 **결정적 케이스(PERF-10A·12C·A01, 11B·11C 의 카운터 판정)는 장비와 무관하게
  CONFIRMED 여야 한다.** EC2 에서 이것들이 깨지면 그건 환경 탓이 아니라 조사 대상이다.
- 다른 장비에서 돌려 보는 것 자체가 책 2장의 원칙이다 — **"측정은 목표 환경과 같은
  하드웨어에서"**. 리포트 머리의 실행 환경(코어 수)을 함께 읽어야 수치가 의미를 가진다.

## 5. PERF-10C — 원격 네트워크 케이스

§9-1 의 "실제 네트워크"를 실제로 재는 케이스다. **다른 케이스와 방향이 반대다** —
스위트를 인스턴스 *안에서* 돌리면 루프백이라 명제의 조건이 사라진다. 그래서
**서버를 EC2 에 두고, 케이스는 러너(또는 로컬)에서 돌린다.** 그 사이가 진짜 WAN 이다.

```
GitHub 러너 (클라이언트 = 케이스)  ──── 진짜 WAN ────>  EC2 (서버 = 페이로드 엔드포인트)
```

### 구성 요소

| | 무엇 |
|---|---|
| 서버 | `PayloadController` — `perfbook` 모듈의 앱이 직접 서빙한다. `/payload/full`(장황판)과 `/payload/trimmed`(다듬은 판)가 **같은 정보**를 담는다 |
| 클라이언트 | `RemoteOutputTrimmingCase`(`PERF-10C`) — `VERIFY_REMOTE_BASE_URL` 이 가리키는 배포본을 HTTP 로 잰다 |
| 자동화 | `.github/workflows/remote-network.yml` — 빌드는 러너가(1GB 인스턴스에 Gradle 빌드를 시키지 않는다), 배포·기동·측정·서버 종료까지 한 번에 |

### 실행

1. **보안 그룹에 서버 포트(기본 8080) 인바운드를 연다.** 22 만 열려 있으면 러너가 서버에 닿지
   못하고, 워크플로가 그 지점에서 명시적으로 실패한다(조용히 INCONCLUSIVE 로 넘어가지 않는다).
2. Actions → `remote-network` → Run workflow.
3. 아티팩트 `remote-network-report` 에 판정이 담긴다.

손으로 확인하려면:

```bash
# EC2 에서
java -jar perfbook-payload.jar --server.port=8080

# 로컬/러너에서
VERIFY_REMOTE_BASE_URL=http://<EC2호스트>:8080 \
  ./gradlew :verify-labs-perfbook:test -Dverify.only=PERF-10C
```

### 판정 규칙 — 무엇을 어디서 단정하나

| 항목 | 어디서 단정하나 |
|---|---|
| 두 응답의 **정보가 같다** (행 수·가격 합계·경계 심볼) | **어디서든** — 결정적 `expect` |
| 표현만 다듬어 **전송량이 5배 이상 준다** | **어디서든** — 결정적 `expect` |
| **다듬은 판이 유의미하게 빠르다** | **원격 링크에서만.** 대상이 루프백/사설망이면 `expectFlaky(false)` 로 INCONCLUSIVE 를 남긴다 |

**루프백에서 통과시키지 않는 것이 이 케이스 설계의 핵심이다.** 조건이 안 맞는데 통과하면
그게 §1-2 가 말한 헛통과다.

> **로컬 실측에서 하나 배웠다.** 설계할 때는 "루프백이면 두 응답의 시간 차이가 사라질 것"으로
> 봤는데, 실제로 재 보니 **루프백에서도 3.19배가 벌어졌다**(644,009 → 31,809 bytes,
> 24,051us → 7,548us). 남아 있는 것은 대역폭이 아니라 **서버가 큰 응답을 만들어 소켓에
> 복사하는 비용**이다. 그래서 케이스의 주장에서 "루프백에서는 이 차이가 보이지 않는다"를
> 빼고, note 에 **"루프백에서는 링크 대역폭 성분만 사라진다"** 로 고쳐 적었다.
> 방향이 같아 보여도 원인이 다르면 근거로 쓸 수 없다.
