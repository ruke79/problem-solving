# 실물 인프라로 늘어난 검증 범위 (PostgreSQL 16 · Kafka 3.9)

H2 인메모리를 걷어내고 실물 PostgreSQL 16 을 쓰면서, "인프라가 없어서 못 한다"고 미뤄 둔 질문들이 풀렸다.
**케이스 5개를 새로 만들어 52 → 57건**이 됐고, 전부 `CONFIRMED` 로 통과했다.
이어서 **Kafka 3.9 실물 브로커**를 붙여 MSA 케이스의 "인메모리 모사" 한계도 걷어냈다(§4) —
현재 **63건**(verify-labs 58 + verify-labs-kafka 5)이다.

> 범위 주의: 이 문서는 **Q31~Q115**(원고를 받은 범위) 기준이다.
> Q1~Q30 과 Q116~Q200 은 아직 원고를 받지 못해 분류 자체가 없다 — 그 범위에도 후보가 더 있을 수 있다.

## 1. 새로 만든 케이스 5개

| ID | 질문 | 이전 상태 | H2 로는 왜 못 했나 | 지금 무엇을 관측하나 |
|---|---|---|---|---|
| `DB-08` | **Q47** 파티셔닝 전략 | B(이론 전용) | 선언적 파티셔닝과 프루닝이 없다 | 파티션 키가 있으면 **1개 파티션만** 읽고, 빠지면 **전 파티션**을 훑는다. DROP PARTITION 은 즉시, 같은 양의 DELETE 는 **dead tuple 을 남긴다** |
| `DB-09` | **Q97** 락 전략 | A(부분) | H2 에 SSI 가 없다 | write skew 를 REPEATABLE READ 는 **통과시키고**(당직 0명), SERIALIZABLE 은 **40001 로 차단**(당직 1명) |
| `DB-10` | **Q51** CDC | C(Debezium+Kafka 필요) | 논리 복제 슬롯 자체가 없다 | 논리 슬롯의 변경 스트림에서 **DELETE 는 기본 PK 만**, `REPLICA IDENTITY FULL` 이면 삭제된 행 전체. 미소비 슬롯이 **WAL 402KB 를 붙잡음** |
| `DB-11` | **Q40·Q73** 무중단 스키마 변경 | A(논리 단계만) | DDL 이 즉시 끝나 락 비용이 안 보인다 | 상수 기본값 ADD COLUMN **1ms** vs 타입 변경 재작성 **350ms**. DDL 이 락을 기다리는 동안 **뒤에 줄 선 일반 SELECT 가 1.7초 정지** |
| `DB-12` | **Q61·Q100** 멱등성 | A(단일 JVM 한정) | 프로세스 밖의 보장을 못 만든다 | 커넥션 20개가 같은 멱등 키로 동시 진입 → 유니크 제약이 **정확히 1건**만 통과(23505). 조회 후 삽입은 **중복 실행** |

### 특히 값어치가 큰 두 개

**`DB-11` — DDL 락 큐.** Q73 답변은 "Expand/Contract 로 각 단계를 롤백 가능하게"까지 말하는데,
실제 사고는 **절차가 아니라 타이밍**에서 난다. 긴 읽기 트랜잭션 뒤에 DDL 이 서면 그 DDL 이
`ACCESS EXCLUSIVE` 를 기다리고, **그 뒤에 도착한 평범한 SELECT 까지 같이 멈춘다**(FIFO 락 큐).
"DDL 은 1ms 면 끝나는데 왜 장애가 났는가"의 답이 이것이고, 이제 숫자로 보여줄 수 있다.

**`DB-12` — 멱등성의 근거를 DB 로.** `docs/02-정직한-고지.md` §5 는 "RES-01 의 보장은 단일 프로세스
안에서만 유효하다. 진짜 근거는 DB 유니크 제약이나 Redis SET NX 다"라고 **한계를 고백**하고 있었다.
그 고백한 부분을 실제로 검증하게 됐다 — 랩이 스스로 인정한 구멍 하나가 메워졌다.

## 2. 아직 못 하는 것 (정직하게)

새 케이스를 만들면서 "가능해 보였지만 안 되는 것"도 확인했다.

| 질문 | 필요한 것 | 왜 아직인가 |
|---|---|---|
| Q65 리플리케이션 vs 샤딩 | PostgreSQL **인스턴스 2대** | 복제 지연(replica lag)과 "쓰기 직후 레플리카 읽기"의 stale read 는 프라이머리·레플리카가 있어야 한다. `compose.yaml` 에 서비스를 하나 더 얹고 스트리밍 복제를 걸면 **가능하다** — 확장 1순위 |
| Q18·Q44·Q68 풀 고갈 (서버 측) | 슈퍼유저 권한 | PostgreSQL 은 커넥션이 프로세스라 `max_connections` 상한이 실재한다. `ALTER ROLE … CONNECTION LIMIT` 로 재현할 수 있지만 권한이 필요해, 사용자가 직접 띄운 DB 에서는 실패한다 |
| ~~Q41 Kafka vs RabbitMQ~~ | ~~Kafka~~ | **§4 에서 해소됨** — Kafka 3.9 를 compose 에 추가해 실물로 검증한다 |
| Q33 분산 트레이싱 / Q35 mTLS / Q70·Q74 K8s | 각각의 인프라 | PostgreSQL·Kafka 로는 대체되지 않는다 (Q110 의 리밸런스 부분만 `KAFKA-05` 로 해소) |
| Q56·Q60·Q111~Q113 LLM·GPU | 모델 | `AI-*` 는 랜덤 벡터로 알고리즘 성질만 본다 — 이 성격은 그대로다 |

또한 **PostgreSQL 이 생겼다고 이론 전용(B) 질문이 검증 가능해지지는 않는다.**
Q49(정규화 판단), Q50(OLTP/OLAP 분리), Q57(ETL vs ELT)은 설계 판단이라 참/거짓이 갈리지 않는다.
DB 가 있다고 억지로 케이스를 만들면 "검증한 척"이 된다 — 이 랩이 피하려는 것이 정확히 그것이다.

## 3. 다음에 만든다면 (우선순위)

1. **Q65 복제 지연** — `compose.yaml` 에 레플리카 1대 추가. "쓰기 직후 레플리카를 읽으면 옛 값이 보인다"와
   "결제 직후 잔고 확인은 프라이머리로 읽어야 한다"는 원고(Part 5 Q65)의 주장을 그대로 실측할 수 있다.
2. **Q46 심화** — `EXPLAIN ANALYZE` 의 **추정 행수 vs 실측 행수 괴리**. 통계가 낡으면 계획이 어떻게
   무너지는지, 복합 인덱스의 선두 컬럼 규칙이 어떻게 인덱스를 무력화하는지.
3. **VACUUM·bloat** — 긴 트랜잭션이 VACUUM 을 막아 dead tuple 이 쌓이는 과정. `DB-08` 이 이미
   dead tuple 을 관측하고 있으니 그 연장선이다. 다만 대응되는 질문 번호가 미수령 범위에 있을 수 있다.
4. **Q104 심화** — PreparedStatement 가 다중 구문(`; DROP TABLE`)을 어떻게 거절하는지. `DB-04` 확장.

1번만 해도 `compose.yaml` 몇 줄과 케이스 하나다. 나머지는 질문 원고(Q1~Q30, Q116~Q200)를 받은 뒤
분류를 다시 돌려 보는 편이 낫다 — 지금 없는 범위에 더 좋은 후보가 있을 수 있다.

## 4. Kafka 3.9 — MSA 케이스를 실물 브로커로

`MSA-02`·`MSA-03`·`MSA-04` 는 브로커를 자바 코드로 흉내 낸 인메모리 모델이었다.
엄밀히 말하면 "내 모델이 내 모델과 일치한다"를 확인하는 것이라, 같은 명제를 실물로 다시 검증하는
`verify-labs-kafka` 모듈을 만들었다.

| ID | 질문 | 인메모리 판 | 실물에서 새로 보이는 것 |
|---|---|---|---|
| `KAFKA-01` | **Q41** Kafka vs RabbitMQ (C→A) | 없음 | 같은 키는 한 파티션에만 들어가 키 안에서는 순서 유지, **토픽 전체는 역전**. 오프셋을 되감아 전건 재소비 |
| `KAFKA-02` | Q42·Q45 컨슈머 랙 | `MSA-03` | AdminClient 로 브로커에 직접 물은 랙 — 미소비 500 → 부분 처리 후 400 → 전량 처리 후 0 |
| `KAFKA-03` | Q43 헤드 오브 라인 블로킹 | `MSA-04` | 실제 파티션에서 재시도가 뒤를 세우는 시간, 재시도 토픽 전략에서 그 메시지가 맨 뒤로 밀리는 순서 |
| `KAFKA-04` | Q100 Exactly-Once | `RES-01`(부분) | `enable.idempotence` 기본 **true**(Kafka 3.0+), abort 된 메시지는 `read_committed` 에만 안 보이고 **기본값 `read_uncommitted` 로는 보인다** |
| `KAFKA-05` | Q45·Q110 리밸런스 | 없음 | 파티션 2개에 컨슈머 3대 → 1:1 재할당 후 3번째는 **아무것도 못 받고 논다**(오토스케일 상한) |

**인메모리 판을 지우지 않은 이유**: 브로커 없이도 돌아 이식성이 있고, 실물 판이 없는 환경에서도
명제의 방향은 확인할 수 있기 때문이다. 대신 `docs/02` §5-0 에 무엇이 실물이고 무엇이 모사인지 표로 남겼다.

**브로커가 없으면**: 5건 전부 `INCONCLUSIVE` 로 리포트에 남고 테스트는 **건너뛴다**(실패가 아니다).
"검증하지 못했다"와 "답변이 틀렸다"를 구분하는 이 랩의 규칙을 모듈 경계에서도 지킨다.

### 함께 추가한 것 — `RES-08` 재시도 × 서킷브레이커

`RES-04` 는 서킷브레이커 단독의 상태 전이를 본다. 실무 사고는 그다음에 난다 —
**두 패턴을 겹치는 순서**에 따라 원격지에 실제로 가는 호출 수가 달라진다.

| 구성 | 원격 호출 수 | 서킷 개방 |
|---|---|---|
| `Retry(CircuitBreaker(call))` — 재시도가 바깥 | **6** | 2번째 요청에서 열림 |
| `CircuitBreaker(Retry(call))` — 서킷이 바깥 | **12** | 같은 요청 수 안에서는 안 열림 |

라이브러리 설정 한 줄처럼 보이지만 실제로는 "원격지를 빨리 쉬게 할 것인가, 순간 장애를 사용자에게
감출 것인가"를 고르는 설계 결정이다.
