## 1. 기존 프로젝트 구조와의 충돌

**증상** — 기존 저장소는 `src/main/java` 하나짜리 단일 모듈(Spring Boot 3.4.10 + Kotlin JVM 플러그인,
카카오 SMS 데모)이었고, 랩은 `verify-core` / `verify-labs` 2모듈이다. 두 `settings.gradle` 의
`rootProject.name` 도 `demo` 와 `interview-verify-lab` 으로 달랐다. 그대로 얹으면 루트 프로젝트가
소스 없는 껍데기인데도 기존 `build.gradle` 의 의존성(Kafka, MySQL, OAuth2)을 계속 끌고 온다.

**원인** — 단일 모듈 레이아웃과 멀티 모듈 레이아웃은 루트 `build.gradle` 의 역할 자체가 다르다.
단일 모듈에서 루트는 애플리케이션이고, 멀티 모듈에서 루트는 **공통 규약만 선언하는 빈 컨테이너**다.

**해결** — 기존 `src/`, `build.gradle`, `settings.gradle` 을 통째로 제거하고 랩의 것으로 교체했다.
루트 `build.gradle` 은 `subprojects { }` 로 툴체인·저장소·BOM·테스트 규약만 배포하고,
`org.springframework.boot` 플러그인은 `apply false` 로 두어 실행 가능한 모듈(`verify-labs`)에서만 적용한다.
`verify-core` 는 `java-library` 라 부트 플러그인이 붙지 않으므로 실행 가능한 jar 가 만들어지지 않고,
그래서 다른 프로젝트에 그대로 이식된다. 기존 저장소에서 살린 것은 **wrapper 관련 파일과 `.gitattributes` 뿐**이다.

## 2. `gradle-wrapper.jar` 가 zip 에 없음

**증상** — 인계 노트에 적힌 대로 zip 에는 `gradle/wrapper/gradle-wrapper.properties` 만 있고 jar 가 없다.
`./gradlew` 를 먼저 쓸 수 없으니 "wrapper 를 만들려면 gradle 이 이미 깔려 있어야 한다"는 순환이 생긴다.

**원인** — jar 는 바이너리라 네트워크 없는 환경에서 생성할 수 없었다.

**해결** — 기존 저장소에 있던 `gradle-wrapper.jar` / `gradlew` / `gradlew.bat` 를 그대로 재사용했다.
운 좋게 기존 저장소도 `distributionUrl` 이 **gradle-8.14.3-bin.zip** 이어서 목표 버전과 정확히 일치했고,
jar 는 배포판 버전과 독립이라 교체할 필요가 없었다. 이제 저장소만 클론하면 Gradle 설치 없이 `./gradlew` 가 돈다.

> `gradle-wrapper.jar` 는 저장소에 커밋하는 것이 정석이다. `.gitignore` 에서 실수로 걸러지지 않는지
> 확인해 두면 이 문제 자체가 생기지 않는다.

## 3. `./gradlew: Permission denied`

**증상** — `./gradlew --version` 이 `Permission denied` 로 끊겼다.

**원인** — 실행 비트가 없다. zip 압축·해제나 파일 복사 과정에서 흔히 날아간다.

**해결**

```bash
chmod +x gradlew
git update-index --chmod=+x gradlew   # 파일 모드를 Git 에 기록 (100755)
```

`chmod` 만 하면 내 로컬에서만 고쳐지고 클론한 사람은 같은 문제를 다시 겪는다.
`git update-index --chmod=+x` 로 **모드 자체를 커밋**해야 끝난다.

## 4. Java 17 툴체인을 찾지 못함

**증상**

```
> Could not resolve all dependencies for configuration ':verify-core:compileClasspath'.
   > Failed to calculate the value of task ':verify-core:compileJava' property 'javaCompiler'.
      > Cannot find a Java installation on your machine matching: {languageVersion=17, ...}.
        Toolchain download repositories have not been configured.
```

**원인** — 머신에는 JDK 21 만 있었고 빌드는 `languageVersion = 17` 을 요구한다.
여기서 중요한 점은, Gradle 툴체인은 **"없으면 현재 JVM 으로 대충 컴파일"로 물러서지 않는다**는 것이다.
정확히 일치하는 JDK 가 없고 다운로드 저장소도 설정돼 있지 않으면 그냥 실패한다.
이 엄격함이 "내 로컬은 21, CI 는 17" 같은 미묘한 차이를 원천 봉쇄해 준다.

**해결** — `settings.gradle` 에 툴체인 자동 프로비저닝 리졸버를 붙였다.

```groovy
plugins {
    id 'org.gradle.toolchains.foojay-resolver-convention' version '1.0.0'
}
```

이건 Gradle 8.x + Spring Initializr 의 기본 구성이기도 하다. 이제 JDK 17 이 없는 머신에서도
빌드가 필요한 툴체인을 스스로 내려받는다. **`java { toolchain { ... } }` 을 쓴다면 이 플러그인은 사실상 필수**다.

## 5. foojay 자동 다운로드가 프록시에 막힘 (폐쇄망)

**증상** — 4번을 고쳤는데도 실패했다.

```
Some toolchain resolvers had internal failures:
  foojay (Unable to tunnel through proxy. Proxy returns "HTTP/1.1 403 Forbidden").
```

**원인** — 이 환경의 아웃바운드는 허용 목록 기반 프록시를 지나는데 `api.foojay.io` 가 목록에 없다.
Maven Central(`repo1.maven.org`)은 뚫려 있어서 **의존성은 받아지는데 JDK 만 못 받는** 상태였다.

**해결** — 툴체인을 다운로드하는 대신 **JDK 17 을 OS 패키지로 직접 설치**했다.

```bash
apt-get update && apt-get install -y openjdk-17-jdk-headless
```

설치 후에는 Gradle 의 자동 탐지가 `/usr/lib/jvm/java-17-openjdk-amd64` 를 찾아내고,
로컬에 일치하는 툴체인이 있으면 리졸버는 아예 호출되지 않는다.

**교훈** — 자동 프로비저닝은 **편의 장치이지 전제 조건이 아니게** 만들어야 한다.
`settings.gradle` 의 리졸버는 그대로 두는 게 맞다(네트워크가 열린 곳에서는 그게 제일 편하다).
다만 폐쇄망 CI 라면 이미지에 JDK 17 을 미리 굽거나 `org.gradle.java.installations.paths` 로 경로를 지정하는
쪽이 안정적이다. 첫 실패 메시지(`Toolchain download repositories have not been configured`)와
두 번째 실패 메시지(`resolvers had internal failures`)는 **원인이 전혀 다르다** — 전자는 설정 누락,
후자는 네트워크 차단이다.

## 6. ★ DB-07 이 REFUTED — 답변이 아니라 검증 코드가 틀렸다

여기서부터가 이 랩의 본론이다. 컴파일이 통과하고 52건이 처음으로 전부 실행됐을 때 결과는
**CONFIRMED 46 / REFUTED 1 / INCONCLUSIVE 5 / ERROR 0**, 유일한 REFUTED 가 `DB-07`(데드락) 이었다.

**증상**

```
- DB-07 [REFUTED] 락 획득 순서가 엇갈리면 데드락이 난다. 갱신 순서를 통일하면 ...
    실패: 순서를 통일하면 아무도 실패하지 않는다 [기대=0 / 실제=1]
```

리포트의 관측값이 결정적인 단서였다.

| 시나리오 | 실패 수 | 오류 |
|---|---|---|
| 엇갈린 순서 (1→2 / 2→1) | 1 | `JdbcSQLTransactionRollbackException (errorCode=40001)` ← 진짜 데드락 |
| 통일된 순서 (1→2 / 1→2) | 1 | `JdbcSQLTimeoutException (errorCode=50200)` ← **락 타임아웃** |

오류 코드가 다르다. 통일된 순서에서 난 것은 데드락(40001)이 아니라 **락 타임아웃(50200)** 이었다.
즉 "순서를 통일해도 데드락이 난다"가 아니라 **애초에 데드락이 아닌 것을 실패로 세고 있었다.**

**원인** — 두 시나리오가 같은 랑데부 배리어를 공유한 것이 문제였다. 원래 코드는 각 워커가

1. 첫 행을 잠그고 → 2. `bothStarted` 배리어에서 상대를 기다리고 → 3. 두 번째 행을 잠근다

는 순서로 돌았다. 엇갈린 순서에서는 두 스레드의 첫 행이 **서로 다르므로**(1번과 2번) 둘 다 첫 락을
잡을 수 있고 배리어에서 정상적으로 만나 교착이 성립한다. 그런데 통일된 순서에서는 첫 행이 **같다.**
뒤 스레드는 1번 행 락을 기다리느라 `countDown()` 에 도달하지 못하고, 앞 스레드는 1번 행을 **쥔 채로**
배리어에서 5초를 기다린다. 그 사이 뒤 스레드의 `LOCK_TIMEOUT 2000` 이 먼저 터진다.
**검증 하네스가 자기가 만든 교착에 걸린 것**이지, 명제가 틀린 게 아니었다.

**해결** — 배리어를 시나리오별로 갈랐다(`DeadlockOrderingCase.java`).

- **엇갈린 순서**: '둘 다 첫 락 보유' 배리어를 유지한다. 교착을 확실히 만들려면 이 동기화가 필요하다.
- **통일된 순서**: 배리어를 걸지 않는다. 대신 `startGate` 로 출발 시점만 맞추고 자연스럽게 경합시킨다.
  뒤 스레드는 앞 트랜잭션이 커밋할 때까지(UPDATE 두 번, 수 ms) 기다렸다가 진행한다.
- 락 타임아웃은 2초 → 5초로 올렸다. 엇갈린 순서는 H2 가 타임아웃과 무관하게 교착을 **감지**해서
  40001 로 즉시 끊으므로 값을 올려도 검출력이 떨어지지 않고, 통일된 순서만 느린 장비에서 여유가 생긴다.

수정 후 통일된 순서의 실패 수는 0, 판정은 CONFIRMED 로 바뀌었다.

**교훈** — 세 가지가 남았다.

1. **오류 코드를 `fact` 로 남겨 둔 설계가 이 버그를 잡았다.** 실패 건수만 셌다면 "H2 라서 그런가 보다"로
   넘어갔을 것이다. 판정에 쓰지 않는 관측값을 굳이 리포트에 남기는 이유가 여기 있다.
2. **동시성 테스트의 배리어는 그 자체가 버그의 원천이다.** "두 스레드가 각자 첫 락을 잡을 수 있다"는
   전제는 시나리오에 따라 성립하지 않는다.
3. **REFUTED 가 나왔을 때 답변부터 고치면 안 된다.** 검증 코드가 명제를 제대로 재현했는지 먼저 본다.
   이번 건은 답변이 옳았고 랩이 틀렸다.

## 7. Gradle 9.0 에서 제거될 기능 경고

**증상**

```
The automatic loading of test framework implementation dependencies has been deprecated.
This is scheduled to be removed in Gradle 9.0.
```

**원인** — `useJUnitPlatform()` 만 선언하면 Gradle 이 `junit-platform-launcher` 를 테스트 런타임
클래스패스에 몰래 얹어 준다. 이 암묵적 동작이 Gradle 9.0 에서 사라진다. 지금은 경고지만
9.x 로 올리는 순간 테스트가 실행조차 되지 않는다.

**해결** — 루트 `build.gradle` 의 `subprojects` 에 런처를 명시했다. 버전은 Spring Boot BOM 이 관리한다.

```groovy
dependencies {
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}
```

`./gradlew build --warning-mode all` 이 경고 없이 통과한다.

## 최종 결과

```
$ ./gradlew :verify-labs:test

- 합계 52건 | CONFIRMED 48 | REFUTED 0 | INCONCLUSIVE 4 | ERROR 0
```

연속 4회 실행에서 **REFUTED 는 0으로 고정**, INCONCLUSIVE 만 4~5건 사이에서 흔들렸다.
흔들린 케이스는 `CON-02`(카운터 성능), `DB-03`(옵티마이저 선택), `DB-05`(UUID 삽입 시간),
`JVM-06`(ReDoS 시간 증가), `RES-05`(레이트 리밋 경쟁) — 전부 `nondeterministic()` 로 선언해 둔 것들이고,
**INCONCLUSIVE 는 실패가 아니라 "이번 실행에서는 결론을 못 냈다"를 정직하게 남긴 상태**다.
설계가 의도대로 동작했다는 뜻이다.

인계 노트 §6-(1) 이 "손볼 가능성이 있다"고 지목했던 곳들(`JPA-06` StatementInspector,
`JPA-07` H2 락 타임아웃, `DB-06` HikariPoolMXBean 타이밍, `AI-03/04` 힙 사용량)은
**전부 수정 없이 첫 실행에서 통과**했다. 실제로 터진 것은 예상 목록에 없던 `DB-07` 한 건이었다.
