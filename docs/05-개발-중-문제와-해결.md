# 1부 — 기존 저장소를 Gradle 8.14.3 검증 랩으로 교체

## 1. 기존 프로젝트 구조와의 충돌

**증상** — 기존 저장소는 `src/main/java` 하나짜리 단일 모듈(Spring Boot 3.4.10 + Kotlin JVM 플러그인,
카카오 SMS 데모)이었고, 랩은 `verify-core` / `verify-labs` 2모듈이다. 두 `settings.gradle` 의
`rootProject.name` 도 `demo` 와 `interview-verify-lab` 으로 달랐다. 그대로 얹으면 루트 프로젝트가
소스 없는 껍데기인데도 기존 `build.gradle` 의 의존성(Kafka, MySQL, OAuth2)을 계속 끌고 온다.

**원인** — 단일 모듈 레이아웃과 멀티 모듈 레이아웃은 루트 `build.gradle` 의 역할 자체가 다르다.
단일 모듈에서 루트는 애플리케이션이고, 멀티 모듈에서 루트는 **공통 규약만 선언하는 빈 컨테이너**다.

**해결** — 기존 `src/`, `build.gradle`, `settings.gradle` 을 통째로 제거하고 랩의 것으로 교체했다.
루트 `build.gradle` 은 `subprojects { }` 로 툴체인·저장소·BOM·테스트 규약만 배포하고,
`org.springframework.boot` 플러그인은 `apply false` 로 두어 실행 가능한 모듈(`verify-labs`)에서만 적용한다.
`verify-core` 는 `java-library` 라 부트 플러그인이 붙지 않으므로 실행 가능한 jar 가 만들어지지 않고,
그래서 다른 프로젝트에 그대로 이식된다. 기존 저장소에서 살린 것은 **wrapper 관련 파일과 `.gitattributes` 뿐**이다.

## 2. `gradle-wrapper.jar` 가 zip 에 없음

**증상** — 인계 노트에 적힌 대로 zip 에는 `gradle/wrapper/gradle-wrapper.properties` 만 있고 jar 가 없다.
`./gradlew` 를 먼저 쓸 수 없으니 "wrapper 를 만들려면 gradle 이 이미 깔려 있어야 한다"는 순환이 생긴다.

**원인** — jar 는 바이너리라 네트워크 없는 환경에서 생성할 수 없었다.

**해결** — 기존 저장소에 있던 `gradle-wrapper.jar` / `gradlew` / `gradlew.bat` 를 그대로 재사용했다.
운 좋게 기존 저장소도 `distributionUrl` 이 **gradle-8.14.3-bin.zip** 이어서 목표 버전과 정확히 일치했고,
jar 는 배포판 버전과 독립이라 교체할 필요가 없었다. 이제 저장소만 클론하면 Gradle 설치 없이 `./gradlew` 가 돈다.

> `gradle-wrapper.jar` 는 저장소에 커밋하는 것이 정석이다. `.gitignore` 에서 실수로 걸러지지 않는지
> 확인해 두면 이 문제 자체가 생기지 않는다.

## 3. `./gradlew: Permission denied`

**증상** — `./gradlew --version` 이 `Permission denied` 로 끊겼다.

**원인** — 실행 비트가 없다. zip 압축·해제나 파일 복사 과정에서 흔히 날아간다.

**해결**

```bash
chmod +x gradlew
git update-index --chmod=+x gradlew   # 파일 모드를 Git 에 기록 (100755)
```

`chmod` 만 하면 내 로컬에서만 고쳐지고 클론한 사람은 같은 문제를 다시 겪는다.
`git update-index --chmod=+x` 로 **모드 자체를 커밋**해야 끝난다.

## 4. Java 17 툴체인을 찾지 못함

**증상**

```
> Could not resolve all dependencies for configuration ':verify-core:compileClasspath'.
   > Failed to calculate the value of task ':verify-core:compileJava' property 'javaCompiler'.
      > Cannot find a Java installation on your machine matching: {languageVersion=17, ...}.
        Toolchain download repositories have not been configured.
```

**원인** — 머신에는 JDK 21 만 있었고 빌드는 `languageVersion = 17` 을 요구한다.
여기서 중요한 점은, Gradle 툴체인은 **"없으면 현재 JVM 으로 대충 컴파일"로 물러서지 않는다**는 것이다.
정확히 일치하는 JDK 가 없고 다운로드 저장소도 설정돼 있지 않으면 그냥 실패한다.
이 엄격함이 "내 로컬은 21, CI 는 17" 같은 미묘한 차이를 원천 봉쇄해 준다.

**해결** — `settings.gradle` 에 툴체인 자동 프로비저닝 리졸버를 붙였다.

```groovy
plugins {
    id 'org.gradle.toolchains.foojay-resolver-convention' version '1.0.0'
}
```

이건 Gradle 8.x + Spring Initializr 의 기본 구성이기도 하다. 이제 JDK 17 이 없는 머신에서도
빌드가 필요한 툴체인을 스스로 내려받는다. **`java { toolchain { ... } }` 을 쓴다면 이 플러그인은 사실상 필수**다.

## 5. foojay 자동 다운로드가 프록시에 막힘 (폐쇄망)

**증상** — 4번을 고쳤는데도 실패했다.

```
Some toolchain resolvers had internal failures:
  foojay (Unable to tunnel through proxy. Proxy returns "HTTP/1.1 403 Forbidden").
```

**원인** — 이 환경의 아웃바운드는 허용 목록 기반 프록시를 지나는데 `api.foojay.io` 가 목록에 없다.
Maven Central(`repo1.maven.org`)은 뚫려 있어서 **의존성은 받아지는데 JDK 만 못 받는** 상태였다.

**해결** — 툴체인을 다운로드하는 대신 **JDK 17 을 OS 패키지로 직접 설치**했다.

```bash
apt-get update && apt-get install -y openjdk-17-jdk-headless
```

설치 후에는 Gradle 의 자동 탐지가 `/usr/lib/jvm/java-17-openjdk-amd64` 를 찾아내고,
로컬에 일치하는 툴체인이 있으면 리졸버는 아예 호출되지 않는다.

**교훈** — 자동 프로비저닝은 **편의 장치이지 전제 조건이 아니게** 만들어야 한다.
`settings.gradle` 의 리졸버는 그대로 두는 게 맞다(네트워크가 열린 곳에서는 그게 제일 편하다).
다만 폐쇄망 CI 라면 이미지에 JDK 17 을 미리 굽거나 `org.gradle.java.installations.paths` 로 경로를 지정하는
쪽이 안정적이다. 첫 실패 메시지(`Toolchain download repositories have not been configured`)와
두 번째 실패 메시지(`resolvers had internal failures`)는 **원인이 전혀 다르다** — 전자는 설정 누락,
후자는 네트워크 차단이다.

## 6. ★ DB-07 이 REFUTED — 답변이 아니라 검증 코드가 틀렸다

여기서부터가 이 랩의 본론이다. 컴파일이 통과하고 52건이 처음으로 전부 실행됐을 때 결과는
**CONFIRMED 46 / REFUTED 1 / INCONCLUSIVE 5 / ERROR 0**, 유일한 REFUTED 가 `DB-07`(데드락) 이었다.

**증상**

```
- DB-07 [REFUTED] 락 획득 순서가 엇갈리면 데드락이 난다. 갱신 순서를 통일하면 ...
    실패: 순서를 통일하면 아무도 실패하지 않는다 [기대=0 / 실제=1]
```

리포트의 관측값이 결정적인 단서였다.

| 시나리오 | 실패 수 | 오류 |
|---|---|---|
| 엇갈린 순서 (1→2 / 2→1) | 1 | `JdbcSQLTransactionRollbackException (errorCode=40001)` ← 진짜 데드락 |
| 통일된 순서 (1→2 / 1→2) | 1 | `JdbcSQLTimeoutException (errorCode=50200)` ← **락 타임아웃** |

오류 코드가 다르다. 통일된 순서에서 난 것은 데드락(40001)이 아니라 **락 타임아웃(50200)** 이었다.
즉 "순서를 통일해도 데드락이 난다"가 아니라 **애초에 데드락이 아닌 것을 실패로 세고 있었다.**

**원인** — 두 시나리오가 같은 랑데부 배리어를 공유한 것이 문제였다. 원래 코드는 각 워커가

1. 첫 행을 잠그고 → 2. `bothStarted` 배리어에서 상대를 기다리고 → 3. 두 번째 행을 잠근다

는 순서로 돌았다. 엇갈린 순서에서는 두 스레드의 첫 행이 **서로 다르므로**(1번과 2번) 둘 다 첫 락을
잡을 수 있고 배리어에서 정상적으로 만나 교착이 성립한다. 그런데 통일된 순서에서는 첫 행이 **같다.**
뒤 스레드는 1번 행 락을 기다리느라 `countDown()` 에 도달하지 못하고, 앞 스레드는 1번 행을 **쥔 채로**
배리어에서 5초를 기다린다. 그 사이 뒤 스레드의 `LOCK_TIMEOUT 2000` 이 먼저 터진다.
**검증 하네스가 자기가 만든 교착에 걸린 것**이지, 명제가 틀린 게 아니었다.

**해결** — 배리어를 시나리오별로 갈랐다(`DeadlockOrderingCase.java`).

- **엇갈린 순서**: '둘 다 첫 락 보유' 배리어를 유지한다. 교착을 확실히 만들려면 이 동기화가 필요하다.
- **통일된 순서**: 배리어를 걸지 않는다. 대신 `startGate` 로 출발 시점만 맞추고 자연스럽게 경합시킨다.
  뒤 스레드는 앞 트랜잭션이 커밋할 때까지(UPDATE 두 번, 수 ms) 기다렸다가 진행한다.
- 락 타임아웃은 2초 → 5초로 올렸다. 엇갈린 순서는 DB 가 타임아웃과 무관하게 교착을 **감지**해서
  40001 로 즉시 끊으므로 값을 올려도 검출력이 떨어지지 않고, 통일된 순서만 느린 장비에서 여유가 생긴다.

수정 후 통일된 순서의 실패 수는 0, 판정은 CONFIRMED 로 바뀌었다.

**교훈** — 세 가지가 남았다.

1. **오류 코드를 `fact` 로 남겨 둔 설계가 이 버그를 잡았다.** 실패 건수만 셌다면 "H2 라서 그런가 보다"로
   넘어갔을 것이다. 판정에 쓰지 않는 관측값을 굳이 리포트에 남기는 이유가 여기 있다.
2. **동시성 테스트의 배리어는 그 자체가 버그의 원천이다.** "두 스레드가 각자 첫 락을 잡을 수 있다"는
   전제는 시나리오에 따라 성립하지 않는다.
3. **REFUTED 가 나왔을 때 답변부터 고치면 안 된다.** 검증 코드가 명제를 제대로 재현했는지 먼저 본다.
   이번 건은 답변이 옳았고 랩이 틀렸다.

## 7. Gradle 9.0 에서 제거될 기능 경고

**증상**

```
The automatic loading of test framework implementation dependencies has been deprecated.
This is scheduled to be removed in Gradle 9.0.
```

**원인** — `useJUnitPlatform()` 만 선언하면 Gradle 이 `junit-platform-launcher` 를 테스트 런타임
클래스패스에 몰래 얹어 준다. 이 암묵적 동작이 Gradle 9.0 에서 사라진다. 지금은 경고지만
9.x 로 올리는 순간 테스트가 실행조차 되지 않는다.

**해결** — 루트 `build.gradle` 의 `subprojects` 에 런처를 명시했다. 버전은 Spring Boot BOM 이 관리한다.

```groovy
dependencies {
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}
```

`./gradlew build --warning-mode all` 이 경고 없이 통과한다.

# 2부 — H2 인메모리에서 PostgreSQL 16 으로

1부까지 끝낸 뒤 DB 를 실물 **PostgreSQL 16** 으로 교체했다.
"H2 로 현상만 재현한다"는 타협을 없애는 작업이라 `docs/02-정직한-고지.md` §3 이 통째로 바뀐다.
교체하면서 **H2 에서만 통하던 것 3종류**가 드러났다.

바뀐 설정은 두 줄이 전부다.

```groovy
// verify-labs/build.gradle
- runtimeOnly 'com.h2database:h2'
+ runtimeOnly 'org.postgresql:postgresql'
```

```yaml
# application.yml — 접속 정보는 환경변수로 덮어쓸 수 있게 둔다
url: ${DB_URL:jdbc:postgresql://localhost:5432/verifylab}
```

그런데 **케이스 코드는 두 줄로 끝나지 않았다.**

## 8. H2 전용 SQL 4종

**증상** — 컴파일은 통과하는데 실행하면 `DB-01`, `DB-03` 이 SQL 문법 오류로 죽는다.

**원인과 해결** — 표준 SQL 로 보이던 문장에 방언이 섞여 있었다.

| 케이스 | H2 | PostgreSQL 16 | 성격 |
|---|---|---|---|
| DB-01 | `MERGE INTO iso_demo KEY(id) VALUES (1, 100)` | `INSERT ... ON CONFLICT (id) DO UPDATE SET val = EXCLUDED.val` | upsert 문법이 제품마다 다르다 |
| DB-03 | `SYSTEM_RANGE(1, 100000)` | `generate_series(1, 100000)` | 연번 생성 함수는 비표준 |
| DB-03 | `EXPLAIN` 이 **한 행** | `EXPLAIN` 이 계획 트리 **여러 행** | `queryForObject` → `queryForList` |
| DB-03 | `ANALYZE` (전체) | `ANALYZE scan_demo` (대상 지정) | 통계 갱신 범위 |

`EXPLAIN` 이 특히 조용한 함정이었다. H2 는 계획을 한 행 문자열로 주지만 PostgreSQL 은 트리를 여러 행으로 준다.
`queryForObject` 를 그대로 두면 `IncorrectResultSizeDataAccessException` 이 난다 —
SQL 은 유효한데 **결과 모양이 달라서** 깨지는 종류의 실패다.

**교훈** — "표준 SQL 만 썼다"는 감각은 못 믿는다. upsert·연번 생성·실행계획 조회는
**거의 항상 방언**이고, 이 셋이 이식할 때 제일 먼저 걸린다.

## 9. 락 타임아웃이 접속 URL 에 박혀 있었다

**증상** — H2 시절 `application.yml` 의 접속 URL 은 이랬다.

```
jdbc:h2:mem:verifylab;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE;LOCK_TIMEOUT=10000
```

`LOCK_TIMEOUT=10000` 은 `JPA-07`(비관적 락 대기)과 `DB-07`(데드락)이 **영원히 매달리지 않게** 하는 안전장치인데,
PostgreSQL URL 로 갈아끼우면 이 설정이 조용히 사라진다. 잃어버려도 아무 경고가 없고,
평소에는 통과하다가 락이 안 풀리는 순간 테스트가 무한정 멈춘다.

**해결** — 접속 문자열이 아니라 **커넥션 초기화 SQL** 로 옮겼다.

```yaml
spring.datasource.hikari.connection-init-sql: SET lock_timeout = '10s'
```

`DB-07` 은 세션 단위로 다시 `SET lock_timeout = 5000` 을 걸어 자기 값을 쓴다(세션 설정이 풀 설정을 덮는다).
H2 의 `SET LOCK_TIMEOUT 5000` 과 PostgreSQL 의 `SET lock_timeout = 5000` 은 **문법이 다르다**는 점도 함께 고쳤다.

**교훈** — JDBC URL 에 박아 둔 동작 설정은 DB 를 바꾸는 순간 **소리 없이 증발한다.**
안전장치는 URL 이 아니라 설정 항목으로 두고, 주석으로 왜 필요한지 남겨야 한다.

## 10. PostgreSQL 은 벤더 errorCode 를 쓰지 않는다

**증상** — `DB-07` 의 실패 오류 표기가 전부 `errorCode=0` 으로 나왔다.
1부에서 이 랩의 버그를 잡아낸 결정적 단서가 **오류 코드**였는데(40001 vs 50200),
PostgreSQL 로 옮기자 그 단서가 통째로 사라진 것이다.

**원인** — PostgreSQL JDBC 드라이버는 `SQLException.getErrorCode()` 를 채우지 않는다(항상 0).
오류 구분은 **SQLState** 로 한다.

**해결** — `getErrorCode()` → `getSQLState()` 로 바꾸고, 판정도 하나 추가했다.

```java
error.set(e.getClass().getSimpleName() + " (SQLState=" + e.getSQLState() + ")");

// 실패의 '종류'까지 본다. 락 타임아웃(55P03)으로 실패하는 것은 데드락 재현이 아니다.
evidence.expectFlaky("엇갈린 순서의 실패는 락 타임아웃이 아니라 데드락(40P01)이다",
        crossError.get().contains("40P01"));
```

관측값은 이렇게 나온다.

| 항목 | 값 |
|---|---|
| 엇갈린 순서 실패 수 | `1` |
| 엇갈린 순서에서 발생한 오류 | `PSQLException (SQLState=40P01)` ← deadlock detected |
| 통일된 순서 실패 수 | `0` |

**교훈** — 1부에서 배운 "실패의 종류를 구분하라"를 **판정으로 승격**시켰다.
이제 락 타임아웃(55P03)이 데드락으로 오독되면 케이스가 스스로 알려 준다.
그리고 이식성 관점에서는, **오류 식별은 벤더 코드가 아니라 SQLState 로 하는 것이 원칙**이다.

## 12. 이관으로 얻은 것 — 판정 2건이 올라갔다

문제만 생긴 게 아니다. H2 때문에 물러서 있던 검증 2건이 실물에서 결론이 났다.

| 케이스 | H2 | PostgreSQL 16 |
|---|---|---|
| `DB-01` 격리 수준 | `INCONCLUSIVE` (RR 항목이 `expectFlaky`) | **`CONFIRMED`** — 스냅샷 격리라 결정적이어서 `expect` 로 승격, `nondeterministic()` 도 껐다 |
| `DB-03` 실행계획 | `INCONCLUSIVE` (H2 옵티마이저로는 전환 관측이 불안정) | **`CONFIRMED`** — 계획 문자열과 비용 추정치를 그대로 관측 |

```
인덱스 전: Seq Scan on scan_demo (cost=0.00..1791.00 rows=1) Filter: (k = 42)
인덱스 후: Index Only Scan using idx_scan_demo_k on scan_demo (cost=0.29..8.31 rows=1)
```

## 11. Docker 데몬이 없어 compose.yaml 을 검증하지 못했다

**증상** — `compose.yaml` 을 써 놓고도 실행해 보지 못했다. 검증은 네이티브로 설치한
PostgreSQL 16.13 에서 했고, compose 파일은 "아마 될 것"인 채로 남아 있었다.

```
$ docker ps
failed to connect to the docker API at unix:///var/run/docker.sock:
  dial unix /var/run/docker.sock: connect: no such file or directory
```

**원인** — 두 가지를 구분해야 한다.

1. **데몬 미기동** — `docker` CLI 는 있는데 `dockerd` 가 떠 있지 않다. 소켓 자체가 없다.
   컨테이너 안에서 작업할 때 흔하다. 이것이 실제 원인이었다.
2. **레지스트리 차단** — 데몬은 떠 있는데 Docker Hub 로 못 나가는 경우. 증상이 전혀 다르다
   (`pull` 단계에서 타임아웃이나 401/403). 폐쇄망이나 Hub 레이트 리밋에서 겪는다.

1번을 2번으로 오진하면 미러만 붙이다 시간을 버린다. **소켓이 없으면 레지스트리 문제가 아니다.**

**해결** — 데몬을 직접 띄우고, 그 김에 레지스트리 미러도 함께 걸었다.

```bash
cat > /etc/docker/daemon.json <<'JSON'
{ "registry-mirrors": ["https://mirror.gcr.io"] }
JSON

dockerd &        # 소켓이 없으면 데몬부터 띄운다
docker compose up -d
```

`mirror.gcr.io` 는 Docker Hub 의 풀 스루 캐시다. Hub 가 막혔거나 익명 pull 레이트 리밋에 걸리는
환경에서는 이 한 줄이 실제로 문제를 없앤다. 이번 환경에서도 `postgres:16` 이 미러를 통해 받아졌다.

**결과** — `compose.yaml` 이 실제로 검증됐다.

```
$ docker compose ps
NAME                 IMAGE         STATUS                    PORTS
verifylab-postgres   postgres:16   Up (healthy)              0.0.0.0:5432->5432/tcp

$ ./gradlew :verify-labs:test
- 합계 52건 | CONFIRMED 50 | REFUTED 0 | INCONCLUSIVE 2 | ERROR 0
```

컨테이너 이미지는 **PostgreSQL 16.14**(Debian), 네이티브 설치본은 **16.13**(Ubuntu)이었다.
같은 52건이 두 인스턴스에서 모두 REFUTED 0 으로 통과했으므로,
계획 문자열·SQLState·격리 수준 동작이 **패치 버전과 배포판에 걸쳐 재현된다**는 것까지 확인됐다.
compose 의 `command: max_connections=200` 도 컨테이너 안에서 적용되는 것을 확인했다.

**교훈** — "인프라 파일을 써 뒀다"와 "그 파일이 동작한다"는 다르다.
`compose.yaml` 은 코드와 함께 검증돼야 하는 산출물이지 문서가 아니다.

---

**대신 잃은 것도 명확히 적어 둔다.** 이 랩은 이제 **DB 없이 돌지 않는다.**
`docker compose up -d` 가 선행돼야 하고, "클론 후 `./gradlew test` 한 방"이라는 성질은 사라졌다.
검증의 신뢰도와 실행 편의를 맞바꾼 것이고, 이 랩의 목적(말이 아니라 실행 결과로 증명)에는 신뢰도 쪽이 맞다.

## 13. ★ INCONCLUSIVE 4건 추적 — 인프라가 아니라 랩의 관측 조건이 문제였다

**증상.** 88건 중 4건(`DB-14` `DB-24` `JVM-06` `RES-05`)이 INCONCLUSIVE 로 남았다.
"인프라가 없어서"라고 짐작하고 PostgreSQL·스트리밍 레플리카·Kafka·Redis 4종을 전부 올린 뒤 재실행했다.

**결과는 예상과 달랐다.** 4건이 그대로 INCONCLUSIVE 였고, 오히려 `CON-02`·`DB-05` 가 새로 흔들려 6건이 됐다.
인프라는 이미 충분했던 것이다. 하나씩 파 보니 원인이 전부 달랐다.

### (1) DB-24 — 로컬 복제가 너무 빨라서 관측 창이 안 열렸다

"쓰기 직후 레플리카를 읽으면 옛 값이 보인다"를 확인해야 하는데,
프라이머리와 레플리카가 같은 도커 호스트에 있으니 복제가 수 ms 만에 따라잡았다.
현상이 없는 게 아니라 **볼 수 있는 창이 없었다.**

```yaml
# compose.yaml — postgres-replica
exec postgres -c max_connections=200 -c hot_standby=on -c recovery_min_apply_delay=2s
```

`recovery_min_apply_delay` 는 WAL 재생을 실제로 늦추는 PostgreSQL 정식 기능이다.
결과를 만든 것이 아니라 실무에서 불규칙하게 나타나는 지연을 관측 가능한 크기로 고정한 것이고,
케이스는 이 값을 읽어(`SHOW recovery_min_apply_delay`) **지연이 설정된 환경에서만 단정**하고
아니면 INCONCLUSIVE 로 남기도록 했다. 판정 근거를 환경에 맞춰 스스로 낮춘다.

### (2) DB-14 — Index Only Scan 은 ANALYZE 가 아니라 VACUUM 이 필요했다

`ANALYZE` 만 돌리고 Index Only Scan 을 기대했다. PostgreSQL 은 인덱스 엔트리만으로 답할 수 있어도
**"그 행이 이 트랜잭션에 보이는가"** 를 알아야 하고, 그 정보는 힙에 있다.
`VACUUM` 이 visibility map 에 '이 페이지의 행은 전부 보인다'를 기록해야 비로소 힙 접근을 건너뛴다.
방금 대량 적재한 테이블에서 Index Only Scan 이 안 나오는 이유가 이것이다.

```java
jdbc.execute("VACUUM (ANALYZE) composite_demo");   // ANALYZE 만으로는 부족하다
```

**그런데 이걸 고치자 다른 항목이 깨졌다** — 이쪽이 더 중요한 발견이다.
VACUUM 후 후행 컬럼만 준 `WHERE b = 42` 의 계획이 이렇게 나왔다:

```
Index Only Scan using idx_composite_ab on composite_demo
  (cost=0.42..3706.42 rows=200 width=0)
  Index Cond: (b = 42)          ← 후행 컬럼인데 Index Cond 로 찍힌다
```

랩은 `Index Cond` 가 있으면 '트리를 좁혀 내려간 진짜 인덱스 스캔'으로 판별하고 있었다. **그 판별식이 틀렸다.**
Index Cond 로 나와도 인덱스 전체를 훑으면서 조건을 인덱스 안에서 확인한 것일 수 있다.
실측 비용은 선행 컬럼 `8.41` 대 후행 컬럼 `3706.93` — **같은 'Index Cond' 인데 441배**다.
판별을 비용 비교로 바꾸고, 이 함정 자체를 케이스의 메모로 승격했다.

### (3) JVM-06 — 교과서 예제 `^(a+)+$` 가 Java 17 에서는 폭발하지 않는다

밀리초 해상도가 문제인 줄 알고 마이크로초로 바꾸고 JIT 워밍업을 넣었더니, 배수가 **1.0** 으로 나왔다.
지수 증가가 아예 없었다. 패턴을 넓게 훑어 봤다(입력 길이 60까지, 20초 상한):

| 패턴 | n=20 | n=30 | n=40 | n=60 |
|---|---|---|---|---|
| `^(a+)+$` | 144us | 155us | 252us | 344us |
| `^(a*)*$` | 91us | — | — | 즉시 |
| `^(a\|aa)+$` | 615us | 192us | 166us | 79us |
| `(x+x+)+y` | 1441us | 1670us | 2980us | 1577us |
| **`(.*a){20}b`** | **48ms** | **1060ms** | **>4s** | **>4s** |

**터진 것은 마지막 하나뿐이다.** 조건은 '중첩 수량자'라는 모양이 아니라
**반복되는 그룹의 몸통이 비결정적인가**였다. `a+` 는 단일 문자 클래스라 결정적이어서 엔진이 되돌아갈 필요가 없고,
`.*a` 는 어디까지 먹을지 정해지지 않아 바깥 반복이 그 분할을 전부 시도한다.

패턴을 `(.*a){12}b` 로 교체하니 길이 16 에서 3.1ms, 22 에서 142ms — **45.9배**로 깔끔하게 벌어졌다.
원자적 그룹 `(?>.*a){12}b` 를 씌우면 같은 입력이 **51us** 에 끝난다. 이 대비도 검증 항목으로 넣었다.

> 답변 원고의 주장("중첩 수량자는 지수적으로 늘어난다")은 방향이 맞다. 다만 **교과서 예제를 그대로 들고 가면
> 최신 JDK 에서 재현되지 않는다.** 면접에서 "그럼 직접 재 보셨나요"를 받으면 곤란해지는 지점이다.

### (4) RES-05 — 스레드를 풀어 놓는 것만으로는 경쟁이 일어나지 않는다

32스레드를 래치로 동시에 풀어 '확인 후 소비' 안티패턴을 재현하려 했는데, 4코어에서는
앞선 몇 개가 확인·소비를 다 끝낸 뒤에야 나머지가 깨어나 통과 수가 제한(10) 이하로 나왔다.
**경쟁이 안 보였다는 것이 안전하다는 뜻은 아니다.**

우연을 기다리는 대신 최악의 인터리빙을 지정했다 — 전원이 먼저 읽고(확인), 배리어, 전원이 쓴다(소비).
실제 스케줄러가 만들 수 있는 정당한 실행 순서 중 하나이고, 결과는 결정적으로 32/32 통과다.
스케줄러에 맡긴 쪽은 판정에서 빼고 **관측값으로 남겨** 둘의 차이를 보이게 했다.

### (5) 덤 — DB-05 에서 UUIDv7 의 함정이 나왔다

`DB-05`(UUID PK)도 같이 흔들려서 손을 댔다. 삽입 '시간' 비교는 2만 행 규모에서 캐시·WAL 잡음에 묻혀
실행마다 순서가 뒤집혔으므로, 주장의 메커니즘인 **페이지 분할의 결과(인덱스 크기)** 를 직접 재도록 바꿨다.
그런데도 판정이 오갔다. 원인을 재 보니:

```
20000개를 만드는 동안 바뀐 밀리초 수 = 3~4
밀리초당 생성 개수 = 5000~6666
```

**타임스탬프만 쓰는 UUIDv7 은 고빈도 생성에서 v4 에 가까워진다.** 같은 밀리초를 공유하는 수천 개가
서로 랜덤이기 때문이다. RFC 9562 가 6.2절에서 밀리초 안의 단조 카운터를 규정하는 이유가 이것이다.
28비트 카운터를 넣고 나서야 인덱스가 제대로 조밀해졌다.

| 방식 | v7(카운터) 대비 인덱스 크기 |
|---|---|
| UUID v4 (완전 랜덤) | 1.25~1.30배 |
| UUIDv7 (타임스탬프만) | 1.14~1.34배 |
| UUIDv7 (단조 카운터) | 기준 |

라이브러리를 고를 때 "UUIDv7 지원"이 아니라 **"카운터를 구현했는가"** 를 봐야 한다는 뜻이다.

핵심 명제(v4 대 카운터판 v7 = 1.25~1.30배)는 반복 실행에서 안정적이지만,
보조로 붙인 '타임스탬프판 v7 대 카운터판 v7' 비교는 20000개가 몇 개의 밀리초에 몰리느냐에 따라
1.1~1.4 사이에서 움직이고 장비가 바쁘면 더 내려간다. 10회에 1회꼴로 하한을 밑돌았다.
이건 원고의 주장이 아니라 이 랩이 덤으로 찾은 관찰이므로 `expectFlaky` 로 내렸다 —
못 봤을 때 REFUTED(원고가 틀렸다)가 아니라 INCONCLUSIVE(이번엔 못 봤다)로 남는 것이 맞다.

| DB-05 | 측정 잡음 | **UUIDv7 구현에 카운터 없음** | 랩 버그 |

4건 중 **인프라로 해결된 것은 DB-24 하나뿐**이고, 나머지는 전부 랩 쪽 문제였다.
그리고 고치는 과정에서 나온 것들(VACUUM 과 visibility map, Index Cond 의 함정,
Java 17 의 정규식 최적화, UUIDv7 의 카운터)이 원래 검증하려던 명제보다 실무에 더 쓸모 있었다.

## 14. ★ Kafka REFUTED 1건 — 답변이 아니라 '남의 컨슈머'가 원인이었다

**증상.** §13 의 반복 실행 중 `verify-labs-kafka` 에서 REFUTED 1건이 딱 한 번 나왔다.
직후 3회 재실행에서 재현되지 않았고 리포트가 덮여 **어느 케이스였는지도 몰랐다.**
REFUTED 는 "답변이 틀렸다"는 가장 무거운 판정이라 그냥 넘길 수 없었다.

### 추적 — 브로커 로그가 남아 있었다

실패 시각은 로그 파일 mtime 으로 `01:33:28`. 컨테이너의 브로커 로그에서 그 창을 봤다.

```
01:31:18  Stabilized group verify-rebalance-group generation 1 with 1 members   ← 앞 실행의 KAFKA-05
01:31:21  Stabilized group verify-rebalance-group generation 2 with 2 members
01:31:24  Dynamic member ... joins group verify-rebalance-group in Stable state
01:32:09  Stabilized group verify-rebalance-group generation 3 with 2 members   ← 아직 살아 있다
01:32:13  Dynamic member ... joins group verify-ordering-group in Empty state   ← 다음 실행의 KAFKA-01 시작
01:32:50  Dynamic member ... joins group verify-rebalance-group
             in CompletingRebalance state (old generation 3)                    ← 다음 실행의 KAFKA-05
01:32:54  Stabilized group verify-rebalance-group generation 4 with 2 members
```

`01:32:50` 이 결정적이다. 다음 실행의 `KAFKA-05` 가 **컨슈머 1대만 붙인 단계**인데,
그룹이 `Empty` 가 아니라 **`CompletingRebalance` 상태에 이전 실행의 멤버를 달고 있었다.**
그래서 `01:32:54` 에 2명으로 안정화됐고, 우리 컨슈머는 파티션을 하나만 받았다.

원인은 그 앞 단계에 있었다. 반복 실행 루프가 도구 타임아웃(10분)으로 끊겼는데,
**Gradle 데몬은 살아남아 그 실행을 계속 진행했다.** 즉 앞 실행과 다음 실행이
같은 브로커·같은 컨슈머 그룹 이름 위에서 겹쳐 돌았다.

### 재현 — 외부 컨슈머를 그룹에 하나 붙였다

추정을 확정하려고, 같은 그룹(`verify-rebalance-group`)에 붙어 poll 만 하는
컨슈머를 하나 띄워 둔 채 스위트를 돌렸다.

```
합계 7건 | CONFIRMED 6 | REFUTED 1 | INCONCLUSIVE 0 | ERROR 0

KAFKA-05
- [ ] 컨슈머가 1대면 모든 파티션을 혼자 받는다  [기대=2 / 실제=1]
- [ ] 컨슈머가 늘면 파티션이 나눠진다
| 컨슈머 1대일 때 할당      | p1                  |
| 2대가 된 뒤 consumer-2 할당 | (없음 — 놀고 있음)  |
```

**증상이 정확히 일치한다.** 답변("한 파티션은 그룹 안에서 컨슈머 하나에만 할당된다")은
오히려 이 결과로 다시 확인된 셈이다 — 남의 컨슈머 하나가 파티션을 가져갔으니까.
틀린 것은 답변이 아니라 **랩이 관측 환경을 독점한다고 가정한 것**이었다.

### 조치 — 그룹 이름을 실행마다 고유하게

```java
// Brokers.java
private static final String RUN_SUFFIX = "-" + UUID.randomUUID().toString().substring(0, 8);

public String groupId(String base) {
    return base + RUN_SUFFIX;
}
```

`Brokers.consumer(...)` 가 모든 그룹 이름에 이 접미사를 붙인다.
AdminClient 로 같은 그룹을 조회하는 `KAFKA-02` 만 `brokers.groupId(GROUP)` 으로 실제 이름을 얻도록 바꿨다.

**검증**: 위와 똑같이 외부 컨슈머를 붙여 둔 채 다시 돌렸더니 **7건 전부 CONFIRMED**.
이어서 전체 88건을 2회 연속 돌려 회귀가 없음을 확인했다.

### 남는 교훈

- **거짓 REFUTED 가 진짜 REFUTED 보다 위험하다.** "답변이 틀렸다"고 적히는 순간
  원고를 고치러 가게 되는데, 실제로는 랩의 격리가 깨진 것이었다.
- 공유 인프라(브로커·DB)를 쓰는 검증은 **이름 충돌이 곧 오염**이다.
  컨슈머 그룹처럼 '이름이 곧 정체성'인 자원은 실행 단위로 고유해야 한다.
- 실행을 강제로 끊어도 **Gradle 데몬은 작업을 계속한다.** 반복 실행 스크립트를 중간에 끊으면
  다음 실행과 겹칠 수 있다는 것을 전제로 랩을 설계해야 한다.

## 15. 고정 포트가 기동을 막는다 — 그리고 Kafka 만 다르게 풀어야 했다

**증상.** `compose.yaml` 이 네 서비스의 호스트 포트를 전부 고정하고 있었다 —
5432(PostgreSQL) · 5433(레플리카) · 9092(Kafka) · 6379(Redis). 전부 개발 장비에 이미 떠 있기 쉬운 번호다.
로컬 설치본, 다른 프로젝트의 compose, 사내 도구. **하나만 충돌해도 4종 인프라 전체가 안 뜬다.**

**조치 (1) — 대부분은 도커에게 맡기면 된다.**

```yaml
ports:
  - "${DB_PORT:-0}:5432"      # 0 = 도커가 비어 있는 포트를 배정
  - "${REPLICA_PORT:-0}:5432"
  - "${REDIS_PORT:-0}:6379"
```

**조치 (2) — Kafka 는 이 방법이 통하지 않는다.**

Kafka 클라이언트는 bootstrap 주소로 한 번 접속한 뒤, 브로커가 알려 주는
**advertised listener 주소로 다시 접속한다.** 그래서 그 주소가 호스트에서 실제로 열린 포트와
같아야 하고, 브로커는 그 값을 *기동 시점에* 알고 있어야 한다.
도커가 고른 포트를 나중에 알아내는 방식으로는 늦는다.

리스너를 둘로 나누고, 포트를 우리가 먼저 골라 넘기는 방식으로 풀었다.

```yaml
ports:
  - "${KAFKA_PORT:-9092}:19092"
environment:
  # INTERNAL(9092): 도커 네트워크 안 — 헬스체크·브로커 간 통신
  # HOST(19092)   : 호스트에서 들어오는 리스너
  KAFKA_LISTENERS: INTERNAL://:9092,CONTROLLER://:9093,HOST://:19092
  KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:9092,HOST://localhost:${KAFKA_PORT:-9092}
```

포트를 미리 고르는 일은 `scripts/random-ports.sh` 가 한다. 커널에게 빈 포트를 물어
(`socket.bind(("", 0))`) `.env` 에 적어 두면 `docker compose` 가 자동으로 읽는다.

**조치 (3) — 앱이 포트를 알아야 한다.**

여기서 끝내면 `./gradlew test` 한 줄로 돌던 성질이 깨진다. 그래서 테스트 태스크가
실행 직전에 *지금 실제로 열려 있는* 포트를 도커에게 물어 넘기도록 했다.

```groovy
// build.gradle (루트 — 두 모듈에 공통 적용)
doFirst {
    publishedPorts(rootDir).each { name, port ->
        if (System.getenv(name)) return      // 직접 지정했으면 존중
        environment name, port
    }
}
```

`docker compose port <서비스> <포트>` 의 출력(`0.0.0.0:32768`)에서 호스트 포트만 뽑아
`DB_PORT` / `REPLICA_PORT` / `KAFKA_PORT` / `REDIS_PORT` 로 넣는다.
안 떠 있는 서비스는 그냥 빠지고, 해당 케이스가 스스로 INCONCLUSIVE 를 남긴다 —
브로커 없이 DB 케이스만 돌리는 것이 정상 사용법이기 때문이다.

여기서 한 번 걸렸다. `Brokers` 의 `@Value` 기본값만 고쳤더니 여전히 `localhost:9092` 로 붙었다.
`verify-labs-kafka/src/main/resources/application.yml` 이 `verify.kafka.bootstrap-servers` 를
이미 정의하고 있어서 **@Value 의 기본값이 애초에 쓰이지 않았다.** 설정 우선순위를 확인하지 않고
기본값만 고치면 이렇게 조용히 무시된다.

**검증.** 두 경로를 다 확인했다.

| 경로 | 배정 포트 (DB / 레플리카 / Kafka / Redis) | 결과 |
|---|---|---|
| `.env` 있음 (전부 랜덤) | 52939 / 40491 / 39283 / 60625 | **88건 전부 CONFIRMED** |
| `.env` 없음 (폴백) | 32769 / 32770 / 9092 / 32768 | **88건 전부 CONFIRMED** |

폴백 경로에서 Kafka 만 9092 로 남는 것이 이 설계의 유일한 비대칭이고, 그 이유는 위 (2) 다.
`psql` 로 직접 붙어 볼 일이 많은 DB 는 `.env` 를 손으로 고쳐 고정하면 된다.

덤으로 붙인 보조 항목(타임스탬프판 v7 대 카운터판 v7)만 생성 속도에 따라 흔들려 `expectFlaky` 로 두었다.
**INCONCLUSIVE 는 실패가 아니라 "이번 실행에서는 결론을 못 냈다"를 정직하게 남긴 상태**다.

인계 노트 §6-(1) 이 "손볼 가능성이 있다"고 지목했던 곳들(`JPA-06` StatementInspector,
`JPA-07` 락 타임아웃, `DB-06` HikariPoolMXBean 타이밍, `AI-03/04` 힙 사용량)은
**전부 수정 없이 첫 실행에서 통과**했고, PostgreSQL 이관 후에도 손대지 않았다.
실제로 터진 것은 예상 목록에 없던 `DB-07` 한 건과, 이관에서 드러난 H2 방언들이었다.
