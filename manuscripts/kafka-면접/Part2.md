### Q26. DB 更新とイベント発行を確実に一致させるには？
(DB 갱신과 이벤트 발행의 일치)

**🇯🇵 回答**

DB とブローカーは別のシステムなので、一つのトランザクションにはできません。Outbox パターンを使います。業務データと同じトランザクションで送信予定を専用テーブルに書き、別のプロセスが読んで発行します。

こうすれば「DB は変わったのにイベントが飛ばない」も「イベントは飛んだのに DB が戻った」も起きません。発行は重複しうるので、**受信側を冪等に作る**のがセットです。

**🇰🇷 답변**

DB 와 브로커는 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없습니다. Outbox 패턴을 씁니다. 업무 데이터와 같은 트랜잭션에서 발행 예정을 전용 테이블에 쓰고, 별도 프로세스가 읽어 발행합니다.

이렇게 하면 "DB 는 바뀌었는데 이벤트가 안 나가는" 것도 "이벤트는 나갔는데 DB 가 롤백된" 것도 없습니다. 발행은 중복될 수 있으므로 **받는 쪽을 멱등하게 만드는 것**이 세트입니다.

### Q27. 受信側の冪等性はどう実装しますか？
(수신 측 멱등성 구현)

**🇯🇵 回答**

イベントに一意な ID を持たせ、処理済みの ID を記録して二回目は捨てます。記録と業務処理を同じトランザクションに入れるのが要点です。

もう一つの方法は、そもそも結果が同じになる操作にすることです。「加算する」ではなく「この値にする」と書けば、何回来ても同じです。可能ならこちらの方が単純です。

**🇰🇷 답변**

이벤트에 고유 ID 를 갖게 하고 처리한 ID 를 기록해 두 번째는 버립니다. 기록과 업무 처리를 같은 트랜잭션에 넣는 것이 요점입니다.

또 하나의 방법은 애초에 결과가 같아지는 조작으로 만드는 것입니다. "더한다"가 아니라 "이 값으로 한다"로 쓰면 몇 번 와도 같습니다. 가능하면 이쪽이 단순합니다.

### Q28. イベントが順不同で届いたらどうしますか？
(이벤트가 순서 없이 도착하면)

**🇯🇵 回答**

同じキーなら同じパーティションなので順序は保たれますが、リトライや再処理で崩れることがあります。

対策は、イベントにバージョンやタイムスタンプを持たせ、**古いものを適用しない**ことです。無条件に上書きすると、遅れて届いた古いイベントが新しい状態を消してしまいます。ここは受信側の責任として設計します。

**🇰🇷 답변**

같은 키라면 같은 파티션이라 순서는 유지되지만, 재시도나 재처리로 깨질 수 있습니다.

대책은 이벤트에 버전이나 타임스탬프를 갖게 해 **오래된 것을 적용하지 않는** 것입니다. 무조건 덮어쓰면 뒤늦게 도착한 옛 이벤트가 새 상태를 지워 버립니다. 여기는 받는 쪽의 책임으로 설계합니다.

### Q29. イベントには何を載せますか？
(이벤트에 무엇을 담나)

**🇯🇵 回答**

二つの流儀があります。必要な情報を全部載せる方式と、ID だけ載せて受信側が問い合わせる方式です。

全部載せると受信側は自己完結できますが、スキーマの結合が強くなります。ID だけだと結合は弱いですが、問い合わせが増え、**そのときには状態が変わっている**可能性があります。私は、業務上の事実として意味のある最小限を載せる方針にしています。

**🇰🇷 답변**

두 가지 방식이 있습니다. 필요한 정보를 전부 담는 방식과 ID 만 담고 받는 쪽이 조회하는 방식입니다.

전부 담으면 받는 쪽이 자기 완결적이지만 스키마 결합이 강해집니다. ID 만 담으면 결합은 약하지만 조회가 늘고 **그때는 상태가 바뀌어 있을** 가능성이 있습니다. 저는 업무상 사실로서 의미 있는 최소한을 담는 방침으로 합니다.

### Q30. トピックの粒度はどう決めますか？
(토픽 단위 결정)

**🇯🇵 回答**

消費のされ方で決めます。同じ消費者が同じように扱うものは同じトピック、独立に増減するものは別トピックです。

細かく分けすぎると管理と運用が増え、まとめすぎると要らないメッセージを読む消費者が出ます。**イベントの種類ごとではなく、対象の集約ごとに**まとめると順序も保ちやすいです。

**🇰🇷 답변**

소비되는 방식으로 정합니다. 같은 소비자가 같은 방식으로 다루는 것은 같은 토픽, 독립적으로 늘고 주는 것은 다른 토픽입니다.

너무 잘게 나누면 관리와 운영이 늘고, 너무 뭉치면 필요 없는 메시지를 읽는 소비자가 생깁니다. **이벤트 종류별이 아니라 대상 애그리게이트별로** 묶으면 순서도 지키기 쉽습니다.

### Q31. トラフィックの急増を Kafka でどう吸収しますか？
(트래픽 급증 흡수)

**🇯🇵 回答**

瞬間的なピークならキューが吸収します。ラグは一時的に増えますが、処理が続いていれば戻ります。

**戻らないなら容量不足です。**ラグの傾きを見て、減っていくのか増え続けるのかで判断します。増え続けるなら、コンシューマを増やす、処理を速くする、あるいは上流でレート制限をかけます。キューは時間を稼ぐだけで、処理能力そのものは増やしません。

**🇰🇷 답변**

순간적인 피크라면 큐가 흡수합니다. 랙은 일시적으로 늘지만 처리가 계속되면 돌아옵니다.

**돌아오지 않으면 용량 부족입니다.** 랙의 기울기를 보고 줄어드는지 계속 느는지로 판단합니다. 계속 늘면 컨슈머를 늘리거나 처리를 빠르게 하거나 상류에서 레이트 리밋을 겁니다. 큐는 시간을 벌 뿐 처리 능력 자체를 늘리지는 않습니다.

### Q32. コンシューマの処理が遅いとき、どこから直しますか？
(컨슈머 처리가 느릴 때)

**🇯🇵 回答**

まず何で時間を使っているかを見ます。多くは外部 I/O、つまり DB か API です。ここを直さずに並列度だけ上げても、相手が詰まります。

具体的には、一件ずつの DB アクセスをバッチにまとめる、不要な同期呼び出しを外す、といった順です。それでも足りなければパーティションとコンシューマを増やします。**順番を間違えると、負荷を下流に押し付けるだけ**になります。

**🇰🇷 답변**

먼저 무엇으로 시간을 쓰는지 봅니다. 대부분 외부 I/O, 즉 DB 나 API 입니다. 여기를 고치지 않고 병렬도만 올리면 상대가 막힙니다.

구체적으로는 한 건씩의 DB 접근을 배치로 묶고, 불필요한 동기 호출을 걷어내는 순입니다. 그래도 부족하면 파티션과 컨슈머를 늘립니다. **순서를 틀리면 부하를 하류에 떠넘길 뿐**입니다.

### Q33. コンシューマの並列度を上げる別の方法はありますか？
(컨슈머 병렬도를 올리는 다른 방법)

**🇯🇵 回答**

パーティションを増やす以外に、一つのコンシューマの中で処理を並列化する方法があります。ただしオフセット管理が複雑になります。

順序が要らないなら有効ですが、**どこまでコミットしてよいかの管理**を自前でやることになります。ライブラリに任せられるならそれを使い、そうでなければパーティションを増やす方が単純で安全です。

**🇰🇷 답변**

파티션을 늘리는 것 외에, 한 컨슈머 안에서 처리를 병렬화하는 방법이 있습니다. 다만 오프셋 관리가 복잡해집니다.

순서가 필요 없다면 유효하지만 **어디까지 커밋해도 되는지의 관리**를 직접 하게 됩니다. 라이브러리에 맡길 수 있으면 그걸 쓰고, 아니면 파티션을 늘리는 편이 단순하고 안전합니다.

### Q34. Kafka Streams や Connect はどんなときに使いますか？
(Kafka Streams·Connect 사용 시점)

**🇯🇵 回答**

Connect は DB や外部システムとの入出力を、コードを書かずに構成で済ませたいときです。CDC で DB の変更を流すのが典型です。

Streams はトピック間の変換・集計・結合をアプリとして書きたいときです。状態を持つ処理では内部で状態ストアを使います。運用が増えるので、**単純な変換なら普通のコンシューマで十分**かを先に考えます。

**🇰🇷 답변**

Connect 는 DB 나 외부 시스템과의 입출력을 코드 없이 구성만으로 끝내고 싶을 때입니다. CDC 로 DB 변경을 흘리는 것이 전형입니다.

Streams 는 토픽 간 변환·집계·조인을 애플리케이션으로 쓰고 싶을 때입니다. 상태를 갖는 처리에서는 내부적으로 상태 저장소를 씁니다. 운영이 늘어나므로 **단순한 변환이면 평범한 컨슈머로 충분한지**를 먼저 생각합니다.

### Q35. CDC を Kafka で流すときの注意点は？
(CDC 를 Kafka 로 흘릴 때의 주의점)

**🇯🇵 回答**

アプリを変えずに変更を配れるのが利点ですが、**DB のスキーマがそのまま下流に伝わる**ので結合が強くなります。テーブル構造を変えると下流が壊れます。

もう一つ、削除イベントに主キーしか載らない設定があります。他の列が必要な下流は困るので、設定を確認します。順序と重複、そして初回のスナップショットの負荷も設計に入れます。

**🇰🇷 답변**

애플리케이션을 고치지 않고 변경을 배포할 수 있는 것이 장점이지만, **DB 스키마가 그대로 하류에 전달되어** 결합이 강해집니다. 테이블 구조를 바꾸면 하류가 깨집니다.

또 하나, 삭제 이벤트에 기본키만 실리는 설정이 있습니다. 다른 컬럼이 필요한 하류는 곤란하므로 설정을 확인합니다. 순서와 중복, 그리고 최초 스냅샷의 부하도 설계에 넣습니다.

### Q36. トピックのレプリケーション設定はどうしますか？
(토픽 복제 설정)

**🇯🇵 回答**

本番は replication factor 3 が基本です。1 だとブローカーが落ちた瞬間にそのパーティションが読み書きできなくなります。

合わせて `min.insync.replicas` を 2 にします。こうすると一台落ちても書き込みを続けられ、二台落ちたら書き込みを止めて**壊れたデータを作らない**選択ができます。可用性と一貫性のどちらを取るかを、ここで明示的に決めます。

**🇰🇷 답변**

운영은 replication factor 3 이 기본입니다. 1 이면 브로커가 죽는 순간 그 파티션을 읽고 쓸 수 없게 됩니다.

함께 `min.insync.replicas` 를 2 로 둡니다. 이러면 한 대가 죽어도 쓰기를 계속할 수 있고, 두 대가 죽으면 쓰기를 멈춰 **깨진 데이터를 만들지 않는** 선택을 할 수 있습니다. 가용성과 일관성 중 무엇을 취할지를 여기서 명시적으로 정합니다.

### Q37. unclean leader election とは何ですか？
(unclean leader election 이란)

**🇯🇵 回答**

ISR に入っていない、つまり遅れているレプリカをリーダーに昇格させる設定です。可用性は上がりますが、**追いついていない分のデータが失われます**。

既定は無効で、通常はそのままにします。有効にするのは、データの欠損よりも止まらないことが重要な限られた用途だけです。面接では「可用性と一貫性のトレードオフを設定で選ぶ例」として説明します。

**🇰🇷 답변**

ISR 에 들어 있지 않은, 즉 뒤처진 레플리카를 리더로 승격시키는 설정입니다. 가용성은 올라가지만 **따라잡지 못한 만큼의 데이터가 사라집니다.**

기본은 비활성이고 보통 그대로 둡니다. 켜는 것은 데이터 결손보다 멈추지 않는 것이 중요한 제한된 용도뿐입니다. 면접에서는 "가용성과 일관성의 트레이드오프를 설정으로 고르는 예"로 설명합니다.

### Q38. Kafka の監視では何を見ますか？
(Kafka 모니터링 지표)

**🇯🇵 回答**

コンシューマラグ、ISR から外れたレプリカの数、リーダーのいないパーティション、ブローカーのディスクとネットワークです。

一番効くのはラグです。**値そのものより傾き**を見て、増え続けているかを判断します。加えて、リバランスの頻度と、リトライ・退避トピックの流入量を見ます。退避が増えているのは、静かに壊れている合図です。

**🇰🇷 답변**

컨슈머 랙, ISR 에서 빠진 레플리카 수, 리더 없는 파티션, 브로커의 디스크와 네트워크입니다.

가장 효과적인 것은 랙입니다. **값 자체보다 기울기**를 보고 계속 늘고 있는지를 판단합니다. 여기에 리밸런스 빈도와 재시도·대피 토픽의 유입량을 봅니다. 대피가 늘고 있는 것은 조용히 깨지고 있다는 신호입니다.

### Q39. コンシューマが止まっていることにどう気づきますか？
(컨슈머가 멈춘 것을 어떻게 아는가)

**🇯🇵 回答**

ラグの増加と、コミットの停止で分かります。プロセスが生きていても、リバランスで割り当てを失っていたり、一件で詰まっていたりすることがあります。

なので「プロセスが生きているか」ではなく「**進んでいるか**」を監視します。最後にコミットしたオフセットの時刻を見るのが確実です。ヘルスチェックも同じ考え方で作ります。

**🇰🇷 답변**

랙 증가와 커밋 정지로 알 수 있습니다. 프로세스가 살아 있어도 리밸런스로 할당을 잃었거나 한 건에서 막혀 있을 수 있습니다.

그래서 "프로세스가 살아 있는가"가 아니라 "**진행하고 있는가**"를 모니터링합니다. 마지막으로 커밋한 오프셋의 시각을 보는 것이 확실합니다. 헬스체크도 같은 사고방식으로 만듭니다.

### Q40. ラグが急に増えたら、どう調べますか？
(랙이 갑자기 늘면)

**🇯🇵 回答**

まず入力が増えたのか、処理が遅くなったのかを分けます。発行レートを見れば分かります。

処理側なら、外部 I/O の遅延、リバランスの発生、毒メッセージによる詰まりを順に見ます。特定のパーティションだけ遅れているならキーの偏りです。**全部か一部か**を最初に切り分けると、その後が速いです。

**🇰🇷 답변**

먼저 입력이 늘었는지 처리가 느려졌는지를 나눕니다. 발행 레이트를 보면 알 수 있습니다.

처리 쪽이면 외부 I/O 지연, 리밸런스 발생, 독이 든 메시지로 인한 막힘을 순서대로 봅니다. 특정 파티션만 밀리면 키 편중입니다. **전부인지 일부인지**를 먼저 가르면 그다음이 빠릅니다.

### Q41. 過去のイベントを再処理したいときはどうしますか？
(과거 이벤트 재처리)

**🇯🇵 回答**

新しいコンシューマグループで最初から読むのが基本です。既存のグループのオフセットを動かす方法もありますが、運用中のものに触るのはリスクがあります。

注意点は、**再処理で下流に副作用が二度出ないか**です。冪等でないなら、出力先を分けて後から切り替えるか、副作用を止めた状態で流します。保持期間を超えた分は戻せないので、必要ならその前提で保持を決めます。

**🇰🇷 답변**

새 컨슈머 그룹으로 처음부터 읽는 것이 기본입니다. 기존 그룹의 오프셋을 옮기는 방법도 있지만 운영 중인 것을 건드리는 건 위험합니다.

주의점은 **재처리로 하류에 부수효과가 두 번 나가지 않는가**입니다. 멱등하지 않다면 출력 대상을 나눠 나중에 전환하거나, 부수효과를 끈 상태로 흘립니다. 보존 기간을 넘긴 것은 되돌릴 수 없으므로 필요하면 그 전제로 보존을 정합니다.

### Q42. コンシューマのデプロイはどうしますか？
(컨슈머 배포)

**🇯🇵 回答**

再起動のたびにリバランスが起きるので、停止時間を短くする工夫をします。静的メンバーシップを使うと、短い再起動ではリバランスを避けられます。

順序としては、**スキーマの互換性を確認してから**です。プロデューサとコンシューマのどちらを先に上げるかで必要な互換性が変わるので、そこを決めてから手順にします。

**🇰🇷 답변**

재시작할 때마다 리밸런스가 일어나므로 정지 시간을 줄이는 궁리를 합니다. 정적 멤버십을 쓰면 짧은 재시작에서는 리밸런스를 피할 수 있습니다.

순서로는 **스키마 호환성을 확인한 뒤**입니다. 프로듀서와 컨슈머 중 어느 쪽을 먼저 올리느냐로 필요한 호환성이 달라지므로, 그걸 정하고 나서 절차를 만듭니다.

### Q43. マイクロサービス間の通信を同期にするか非同期にするか、どう判断しますか？
(동기 vs 비동기 통신 판단)

**🇯🇵 回答**

その場で結果が要るなら同期、通知や波及でよいなら非同期です。

非同期にすると相手の障害に強くなり、ピークも吸収できますが、**結果整合性を受け入れる**必要があります。画面上で「すぐ反映されない」ことをどう見せるかまで設計に含めます。何でも非同期にすると、追跡が難しいシステムになります。

**🇰🇷 답변**

그 자리에서 결과가 필요하면 동기, 통지나 파급이면 비동기입니다.

비동기로 하면 상대 장애에 강해지고 피크도 흡수하지만 **결과적 일관성을 받아들여야** 합니다. 화면에서 "바로 반영되지 않는" 것을 어떻게 보여줄지까지 설계에 포함합니다. 무엇이든 비동기로 하면 추적이 어려운 시스템이 됩니다.

### Q44. Saga パターンとは何ですか？
(Saga 패턴)

**🇯🇵 回答**

サービスをまたぐ処理を、一つの分散トランザクションではなく**ローカルなトランザクションの連鎖**で実現する方式です。失敗したら補償操作で打ち消します。

注文・在庫・決済のような流れが典型です。設計の要点は、補償が本当に可能かを先に確認することです。取り消せない副作用があるなら、その順序を最後に置きます。

**🇰🇷 답변**

서비스를 넘는 처리를 하나의 분산 트랜잭션이 아니라 **로컬 트랜잭션의 연쇄**로 구현하는 방식입니다. 실패하면 보상 조작으로 상쇄합니다.

주문·재고·결제 같은 흐름이 전형입니다. 설계의 요점은 보상이 정말 가능한지를 먼저 확인하는 것입니다. 취소할 수 없는 부수효과가 있다면 그 순서를 마지막에 둡니다.

### Q45. 分散トレーシングは Kafka をまたいでも繋がりますか？
(분산 트레이싱이 Kafka 를 넘어 이어지나)

**🇯🇵 回答**

そのままでは切れます。HTTP と違って自動で伝播しないので、**メッセージのヘッダにトレース情報を載せて**運ぶ必要があります。

計装ライブラリが対応していれば自動でやってくれます。載せておくと、非同期の先で起きた失敗を元のリクエストまで辿れます。ログにも同じ ID を出しておくと調査が一気に楽になります。

**🇰🇷 답변**

그대로 두면 끊깁니다. HTTP 와 달리 자동으로 전파되지 않으므로 **메시지 헤더에 트레이스 정보를 실어** 옮겨야 합니다.

계측 라이브러리가 대응한다면 자동으로 해 줍니다. 실어 두면 비동기 뒤에서 일어난 실패를 원래 요청까지 추적할 수 있습니다. 로그에도 같은 ID 를 남기면 조사가 훨씬 편해집니다.

### Q46. セキュリティはどう設定しますか？
(보안 설정)

**🇯🇵 回答**

通信は TLS で暗号化し、認証は SASL、権限は ACL でトピック単位に絞ります。

よくある問題は、開発の便利さのまま本番に持っていくことです。**誰でも全トピックを読める状態**は、個人情報が流れていれば重大な事故になります。クライアントごとに最小の権限を与えます。

**🇰🇷 답변**

통신은 TLS 로 암호화하고 인증은 SASL, 권한은 ACL 로 토픽 단위로 좁힙니다.

흔한 문제는 개발의 편의를 그대로 운영에 가져가는 것입니다. **누구나 전 토픽을 읽을 수 있는 상태**는 개인정보가 흐르고 있다면 중대한 사고가 됩니다. 클라이언트마다 최소 권한을 줍니다.

### Q47. 個人情報を含むイベントはどう扱いますか？
(개인정보를 포함한 이벤트)

**🇯🇵 回答**

そもそも載せないのが一番です。必要なら参照 ID にして、実データは管理された場所に置きます。

載せる場合は、保持期間を短くし、暗号化とアクセス制御をかけます。削除要求への対応が難しいのが Kafka の特徴です。ログは追記専用なので、**個別に消せない**。鍵を消すことで実質的に復号不能にする方法もありますが、設計時に決めておく必要があります。

**🇰🇷 답변**

애초에 담지 않는 것이 최선입니다. 필요하면 참조 ID 로 두고 실제 데이터는 관리되는 곳에 둡니다.

담는다면 보존 기간을 짧게 하고 암호화와 접근 제어를 겁니다. 삭제 요청 대응이 어려운 것이 Kafka 의 특징입니다. 로그는 추가 전용이라 **개별로 지울 수 없습니다.** 키를 지워 실질적으로 복호 불가로 만드는 방법도 있지만 설계 시점에 정해 둬야 합니다.

### Q48. テストはどう書いていますか？
(테스트 작성)

**🇯🇵 回答**

ロジックは普通の単体テストにして、Kafka との結合は**実際のブローカーを立てて**確認します。埋め込みブローカーやコンテナを使います。

モックだけで済ませると、シリアライズやリバランス、コミットの挙動といった一番壊れやすいところが検証されません。特にオフセット管理と再処理の挙動は、実物でないと確かめられないと考えています。

**🇰🇷 답변**

로직은 평범한 단위 테스트로 하고, Kafka 와의 결합은 **실제 브로커를 띄워** 확인합니다. 임베디드 브로커나 컨테이너를 씁니다.

목으로만 끝내면 직렬화나 리밸런스, 커밋 동작 같은 가장 깨지기 쉬운 곳이 검증되지 않습니다. 특히 오프셋 관리와 재처리 동작은 실물이 아니면 확인할 수 없다고 봅니다.

### Q49. Kafka を入れるべきでないのはどんなときですか？
(Kafka 를 넣지 말아야 할 때)

**🇯🇵 回答**

規模が小さく、単純なキューで足りるときです。Kafka はブローカーの運用、パーティション設計、スキーマ管理と、**運用の負担が実装より大きい**技術です。

またリクエスト・レスポンス型の処理にも向きません。「非同期にすれば速くなる」と考えて入れると、追跡が難しくなるだけです。導入するときは、順序・再処理・複数消費者・スループットのどれが必要なのかを言えるようにします。

**🇰🇷 답변**

규모가 작고 단순한 큐로 충분할 때입니다. Kafka 는 브로커 운영, 파티션 설계, 스키마 관리까지 **운영 부담이 구현보다 큰** 기술입니다.

또 요청·응답형 처리에도 맞지 않습니다. "비동기로 하면 빨라진다"고 생각해 넣으면 추적만 어려워집니다. 도입할 때는 순서·재처리·다중 소비자·처리량 중 무엇이 필요한지를 말할 수 있어야 합니다.

### Q50. 障害が起きたとき、まず何を確認しますか？
(장애 시 첫 확인)

**🇯🇵 回答**

影響範囲です。全トピックか、特定のトピック・パーティションか。ブローカー側か、コンシューマ側か。

順番としては、ブローカーの生死とリーダー不在のパーティション、次に ISR、そしてコンシューマのラグとリバランスの履歴を見ます。**その場の復旧と、後からの再発防止を分けて話す**ようにしています。復旧を優先しつつ、後で読み返せるように時刻と操作を記録します。

**🇰🇷 답변**

영향 범위입니다. 전 토픽인지 특정 토픽·파티션인지, 브로커 쪽인지 컨슈머 쪽인지.

순서로는 브로커의 생사와 리더 없는 파티션, 다음으로 ISR, 그리고 컨슈머의 랙과 리밸런스 이력을 봅니다. **그 자리의 복구와 이후의 재발 방지를 나눠 말하도록** 하고 있습니다. 복구를 우선하되 나중에 되짚을 수 있게 시각과 조작을 기록합니다.
