### Q1. Kafka はどんなときに使いますか？
(Kafka 를 언제 쓰나)

**🇯🇵 回答**

送り手と受け手を時間的に切り離したいとき、そして**同じデータを複数の用途で使いたいとき**です。ログを保持するので、後から別の消費者を足して最初から読み直せます。

単純なタスクキューが欲しいだけなら、もっと軽い選択肢もあります。Kafka を選ぶのは、順序保証、再処理、複数コンシューマ、高スループットのどれかが要るときです。

**🇰🇷 답변**

보내는 쪽과 받는 쪽을 시간적으로 떼어놓고 싶을 때, 그리고 **같은 데이터를 여러 용도로 쓰고 싶을 때**입니다. 로그를 보관하므로 나중에 다른 소비자를 붙여 처음부터 다시 읽을 수 있습니다.

단순한 작업 큐만 필요하다면 더 가벼운 선택지도 있습니다. Kafka 를 고르는 것은 순서 보장, 재처리, 다중 컨슈머, 높은 처리량 중 하나가 필요할 때입니다.

### Q2. トピック・パーティション・オフセットの関係を説明してください。
(토픽·파티션·오프셋의 관계)

**🇯🇵 回答**

トピックは論理的な名前で、その実体が複数のパーティションです。各パーティションは追記専用のログで、メッセージには連番のオフセットが付きます。

並列度はパーティション数で決まり、順序が保証されるのもパーティションの中だけです。この三つの関係が、Kafka のほとんどの制約の出発点になります。

**🇰🇷 답변**

토픽은 논리적인 이름이고 그 실체가 여러 파티션입니다. 각 파티션은 추가 전용 로그이고 메시지에는 연번인 오프셋이 붙습니다.

병렬도는 파티션 수로 정해지고, 순서가 보장되는 것도 파티션 안에서뿐입니다. 이 셋의 관계가 Kafka 의 거의 모든 제약의 출발점입니다.

### Q3. 順序保証はどこまでされますか？
(순서 보장의 범위)

**🇯🇵 回答**

**同じパーティションの中だけ**です。トピック全体での順序は保証されません。

なので、順序が必要な単位をキーにします。同じキーは常に同じパーティションへ行くので、たとえば注文 ID をキーにすればその注文の中では順序が保たれます。全体の順序が必要ならパーティションを一つにするしかなく、それは並列度を捨てることになります。

**🇰🇷 답변**

**같은 파티션 안에서만**입니다. 토픽 전체의 순서는 보장되지 않습니다.

그래서 순서가 필요한 단위를 키로 잡습니다. 같은 키는 항상 같은 파티션으로 가므로, 예를 들어 주문 ID 를 키로 하면 그 주문 안에서는 순서가 지켜집니다. 전체 순서가 필요하면 파티션을 하나로 할 수밖에 없고, 그것은 병렬도를 버리는 일입니다.

### Q4. パーティション数はどう決めますか？
(파티션 수 결정)

**🇯🇵 回答**

必要なスループットと、コンシューマの最大並列度から決めます。**コンシューマ数はパーティション数を超えられない**ので、将来の増加を少し見込んで多めにします。

ただし増やしすぎると、ブローカーのファイル数とリバランスの時間が増えます。そして**後から減らせません**。増やすとキーの割り当ても変わるので、順序が必要な設計では影響を確認してから行います。

**🇰🇷 답변**

필요한 처리량과 컨슈머의 최대 병렬도에서 정합니다. **컨슈머 수는 파티션 수를 넘을 수 없으므로** 앞으로의 증가를 조금 감안해 넉넉히 잡습니다.

다만 너무 늘리면 브로커의 파일 수와 리밸런스 시간이 늘어납니다. 그리고 **나중에 줄일 수 없습니다.** 늘리면 키 할당도 바뀌므로 순서가 필요한 설계에서는 영향을 확인하고 진행합니다.

### Q5. コンシューマグループはどういう仕組みですか？
(컨슈머 그룹의 구조)

**🇯🇵 回答**

同じグループ ID のコンシューマでパーティションを分担します。一つのパーティションはグループ内の一つのコンシューマだけが読みます。

だからコンシューマを増やすと分担が細かくなりますが、**パーティション数を超えた分は何も割り当てられず遊びます**。別のグループを作れば、同じデータを独立して最初から読めます。

**🇰🇷 답변**

같은 그룹 ID 의 컨슈머끼리 파티션을 나눠 맡습니다. 하나의 파티션은 그룹 안의 한 컨슈머만 읽습니다.

그래서 컨슈머를 늘리면 분담이 잘게 나뉘지만 **파티션 수를 넘은 만큼은 아무것도 할당받지 못하고 놉니다.** 다른 그룹을 만들면 같은 데이터를 독립적으로 처음부터 읽을 수 있습니다.

### Q6. リバランスは何をきっかけに起きて、何が問題ですか？
(리밸런스의 계기와 문제)

**🇯🇵 回答**

コンシューマの参加・離脱、パーティション数の変更、あるいはハートビートが途切れたときに起きます。その間は**処理が止まります**。

一番多い原因は、一回の処理が長すぎてポーリングの間隔を超えることです。`max.poll.records` を減らすか処理を速くします。停止時間を減らしたいなら協調的なリバランスの方式を使い、計画的な再起動では静的メンバーシップを使います。

**🇰🇷 답변**

컨슈머의 참가·이탈, 파티션 수 변경, 또는 하트비트가 끊겼을 때 일어납니다. 그동안은 **처리가 멈춥니다.**

가장 많은 원인은 한 번의 처리가 너무 길어 폴링 간격을 넘는 것입니다. `max.poll.records` 를 줄이거나 처리를 빠르게 합니다. 정지 시간을 줄이려면 협조적 리밸런스 방식을 쓰고, 계획된 재시작에는 정적 멤버십을 씁니다.

### Q7. `acks` の設定はどう選びますか？
(acks 설정 선택)

**🇯🇵 回答**

`acks=0` は送りっぱなし、`1` はリーダーが書いたら成功、`all` は同期レプリカ全部が書いたら成功です。

データを失いたくないなら `all` です。ただしそれだけでは足りず、`min.insync.replicas` を 2 以上にして初めて意味を持ちます。レプリカが 1 つしか生きていない状態で `all` にしても、その 1 つが落ちれば失われます。

**🇰🇷 답변**

`acks=0` 은 보내고 끝, `1` 은 리더가 쓰면 성공, `all` 은 동기 레플리카 전부가 쓰면 성공입니다.

데이터를 잃고 싶지 않으면 `all` 입니다. 다만 그것만으로는 부족하고 `min.insync.replicas` 를 2 이상으로 해야 비로소 의미가 있습니다. 레플리카가 하나만 살아 있는 상태에서 `all` 로 해도 그 하나가 죽으면 잃습니다.

### Q8. ISR とは何ですか？
(ISR 이란)

**🇯🇵 回答**

リーダーに追いついているレプリカの集合です。遅れたレプリカは ISR から外れ、追いつけば戻ります。

`acks=all` が待つのは ISR の全部です。ここで注意なのは、ISR が縮むと**待つ相手が減って保証も弱くなる**ことです。だから `min.insync.replicas` を決めて、それを下回ったら書き込みを失敗させる設定にします。

**🇰🇷 답변**

리더를 따라잡고 있는 레플리카의 집합입니다. 뒤처진 레플리카는 ISR 에서 빠지고 따라잡으면 돌아옵니다.

`acks=all` 이 기다리는 것은 ISR 전부입니다. 여기서 주의할 점은 ISR 이 줄면 **기다릴 상대가 줄어 보장도 약해진다**는 것입니다. 그래서 `min.insync.replicas` 를 정하고 그 아래로 내려가면 쓰기를 실패시키는 설정으로 둡니다.

### Q9. プロデューサの冪等性とは何ですか？
(프로듀서 멱등성)

**🇯🇵 回答**

再送によってブローカー上でメッセージが重複しないようにする仕組みです。プロデューサ ID とシーケンス番号で、ブローカーが重複を捨てます。

Kafka 3.0 以降は既定で有効です。ただしこれが守るのは**リトライによる重複だけ**で、アプリが二回送った場合や、コンシューマ側の重複処理は別問題です。

**🇰🇷 답변**

재전송으로 브로커 위에 메시지가 중복되지 않게 하는 장치입니다. 프로듀서 ID 와 시퀀스 번호로 브로커가 중복을 버립니다.

Kafka 3.0 이후는 기본으로 켜져 있습니다. 다만 이것이 지키는 것은 **재시도에 의한 중복뿐**이고, 앱이 두 번 보낸 경우나 컨슈머 쪽 중복 처리는 별개 문제입니다.

### Q10. Exactly-Once は何を保証しますか？
(Exactly-Once 가 보장하는 것)

**🇯🇵 回答**

保証されるのは **Kafka の中で完結する範囲**です。トランザクションで「読んで、処理して、書いて、オフセットをコミットする」を一つの単位にでき、コンシューマ側は `read_committed` にすればコミット済みだけを見ます。

外部の DB や API への副作用までは保証されません。そこは冪等キーなど、アプリ側の設計で守ります。「Exactly-Once があるから重複対策は不要」は誤解です。

**🇰🇷 답변**

보장되는 것은 **Kafka 안에서 완결되는 범위**입니다. 트랜잭션으로 "읽고, 처리하고, 쓰고, 오프셋을 커밋"을 한 단위로 만들 수 있고, 컨슈머는 `read_committed` 로 두면 커밋된 것만 봅니다.

외부 DB 나 API 로의 부수효과까지는 보장되지 않습니다. 거기는 멱등 키 같은 애플리케이션 설계로 지킵니다. "Exactly-Once 가 있으니 중복 대책은 필요 없다"는 오해입니다.

### Q11. オフセットのコミットはどう扱いますか？
(오프셋 커밋 취급)

**🇯🇵 回答**

自動コミットは、処理が終わる前にコミットされて**失敗したメッセージを取りこぼす**ことがあります。確実にやるなら自動を切って、処理が終わってから手動でコミットします。

処理後にコミットすると、コミット前に落ちた場合に再処理されます。つまり at-least-once です。だから**処理は冪等に作る**のが前提になります。

**🇰🇷 답변**

자동 커밋은 처리가 끝나기 전에 커밋되어 **실패한 메시지를 놓칠 수** 있습니다. 확실히 하려면 자동을 끄고 처리가 끝난 뒤 수동으로 커밋합니다.

처리 후에 커밋하면 커밋 전에 죽었을 때 재처리됩니다. 즉 at-least-once 입니다. 그래서 **처리를 멱등하게 만드는 것**이 전제가 됩니다.

### Q12. コンシューマラグは何を意味しますか？
(컨슈머 랙의 의미)

**🇯🇵 回答**

発行された最新のオフセットと、コンシューマが処理済みのオフセットの差です。処理が追いついていない量を示します。

見方の要点は**傾き**です。一時的に増えても減っていくならピークを吸収できています。増え続けているなら処理能力が足りていないので、コンシューマかパーティションを増やすか、処理そのものを速くします。

**🇰🇷 답변**

발행된 최신 오프셋과 컨슈머가 처리한 오프셋의 차이입니다. 처리가 못 따라간 양을 나타냅니다.

보는 요령은 **기울기**입니다. 일시적으로 늘어도 줄어들면 피크를 흡수하고 있는 것입니다. 계속 늘고 있다면 처리 능력이 부족하므로 컨슈머나 파티션을 늘리거나 처리 자체를 빠르게 합니다.

### Q13. コンシューマを増やせばその分速くなりますか？
(컨슈머를 늘리면 그만큼 빨라지나)

**🇯🇵 回答**

パーティション数までは効きます。それを超えたコンシューマは割り当てを受けられず、ただ待つだけです。

なのでオートスケールの上限はパーティション数です。それ以上必要ならパーティションを増やしますが、増やすとキーの割り当てが変わる点に注意します。処理が遅い原因が外部 API なら、コンシューマを増やしても相手が詰まるだけです。

**🇰🇷 답변**

파티션 수까지는 효과가 있습니다. 그것을 넘은 컨슈머는 할당을 받지 못하고 그냥 기다리기만 합니다.

그래서 오토스케일의 상한은 파티션 수입니다. 그 이상 필요하면 파티션을 늘리지만, 늘리면 키 할당이 바뀌는 점에 주의합니다. 처리가 느린 원인이 외부 API 라면 컨슈머를 늘려도 상대가 막힐 뿐입니다.

---

### Q14. 特定のキーに偏ってしまったらどうしますか？
(키 편중이 생기면)

**🇯🇵 回答**

一つのパーティションだけが重くなり、他が遊びます。まず本当に偏っているかを、パーティションごとのラグで確認します。

対策は、キーに小さな接尾辞を足して分散させることです。ただしそれで**そのキー内の順序保証は失われる**ので、順序が要らない処理に限ります。順序が要るなら、その顧客だけ別トピックにするなどの設計判断になります。

**🇰🇷 답변**

한 파티션만 무거워지고 나머지는 놉니다. 먼저 정말 편중됐는지를 파티션별 랙으로 확인합니다.

대책은 키에 작은 접미사를 붙여 분산시키는 것입니다. 다만 그러면 **그 키 안의 순서 보장은 사라지므로** 순서가 필요 없는 처리에만 씁니다. 순서가 필요하면 그 고객만 별도 토픽으로 빼는 등의 설계 판단이 됩니다.

### Q15. 処理に失敗したメッセージはどうしますか？
(처리 실패 메시지 처리)

**🇯🇵 回答**

その場で無限に再試行すると、**後ろのメッセージが全部止まります**。一つの毒メッセージでパーティションが詰まる、というのが典型的な障害です。

なので回数を決めて再試行し、超えたら別のトピックに退避します。リトライ用トピックと最終的な退避先を分ける構成が一般的です。退避したものは監視して、原因を直してから戻します。

**🇰🇷 답변**

그 자리에서 무한히 재시도하면 **뒤의 메시지가 전부 멈춥니다.** 독이 든 메시지 하나로 파티션이 막히는 것이 전형적인 장애입니다.

그래서 횟수를 정해 재시도하고 초과하면 다른 토픽으로 대피시킵니다. 재시도용 토픽과 최종 대피처를 나누는 구성이 일반적입니다. 대피시킨 것은 모니터링해서 원인을 고친 뒤 되돌립니다.

---

### Q16. リトライを別トピックに逃がす方式の欠点は？
(재시도를 별도 토픽으로 넘기는 방식의 단점)

**🇯🇵 回答**

**順序が崩れます。**失敗したメッセージが後回しになるので、同じキーの後続が先に処理されることがあります。

なので、順序が意味を持つ処理では使えません。その場合はパーティション内で止めて再試行し、詰まることを受け入れるか、そもそも失敗しない設計にします。どちらを取るかは業務要件次第です。

**🇰🇷 답변**

**순서가 깨집니다.** 실패한 메시지가 뒤로 밀리므로 같은 키의 후속이 먼저 처리될 수 있습니다.

그래서 순서가 의미를 갖는 처리에는 쓸 수 없습니다. 그 경우는 파티션 안에서 멈춰 재시도하고 막히는 것을 받아들이거나, 애초에 실패하지 않는 설계로 갑니다. 어느 쪽을 취할지는 업무 요건에 달렸습니다.

### Q17. メッセージの保持期間はどう決めますか？
(메시지 보존 기간 결정)

**🇯🇵 回答**

再処理をどこまで遡りたいかと、ディスク容量から決めます。障害からの復旧や、新しいコンシューマの追加を考えると、数日は欲しいことが多いです。

キーごとの最新値だけが要るなら、compaction を使って古いものを畳む選択肢もあります。設定を変えるときは、**保持期間を短くした瞬間に過去が消える**ので影響を確認します。

**🇰🇷 답변**

재처리를 어디까지 거슬러 올라가고 싶은지와 디스크 용량에서 정합니다. 장애 복구나 새 컨슈머 추가를 생각하면 며칠은 필요한 경우가 많습니다.

키별 최신값만 필요하면 컴팩션으로 옛것을 접는 선택지도 있습니다. 설정을 바꿀 때는 **보존 기간을 줄이는 순간 과거가 사라지므로** 영향을 확인합니다.

### Q18. log compaction はどんなときに使いますか？
(로그 컴팩션의 사용 시점)

**🇯🇵 回答**

キーごとの**最新の状態**だけを保ちたいときです。設定値やマスタの現在値を配るトピックに向いています。

新しいコンシューマが最初から読めば、全キーの最新状態が手に入ります。削除は値を `null` にした墓標で表現します。履歴そのものが要るイベントには向きません。

**🇰🇷 답변**

키별 **최신 상태**만 유지하고 싶을 때입니다. 설정값이나 마스터의 현재값을 배포하는 토픽에 맞습니다.

새 컨슈머가 처음부터 읽으면 전 키의 최신 상태를 얻습니다. 삭제는 값을 `null` 로 둔 툼스톤으로 표현합니다. 이력 자체가 필요한 이벤트에는 맞지 않습니다.

### Q19. スキーマの進化にはどう対応しますか？
(스키마 진화 대응)

**🇯🇵 回答**

スキーマレジストリで互換性を強制します。**既定値のあるフィールド追加**なら、前方にも後方にも互換なので、プロデューサとコンシューマのどちらを先にデプロイしても壊れません。

危険なのはフィールドの削除や型変更、必須フィールドの追加です。互換性のモードを決めて CI で検証し、破壊的変更が必要なら新しいトピックに切り替えます。

**🇰🇷 답변**

스키마 레지스트리로 호환성을 강제합니다. **기본값이 있는 필드 추가**라면 전방·후방 모두 호환되므로 프로듀서와 컨슈머 중 어느 쪽을 먼저 배포해도 깨지지 않습니다.

위험한 것은 필드 삭제나 타입 변경, 필수 필드 추가입니다. 호환성 모드를 정해 CI 에서 검증하고, 파괴적 변경이 필요하면 새 토픽으로 전환합니다.

### Q20. 前方互換と後方互換の違いは？
(전방 호환과 후방 호환의 차이)

**🇯🇵 回答**

後方互換は、**新しいスキーマで書いたデータを古い読み手が読める**こと。前方互換はその逆で、古いデータを新しい読み手が読めることです。

どちらが要るかはデプロイ順で決まります。コンシューマを先に上げるなら後方互換、プロデューサを先に上げるなら前方互換が要ります。両方満たす変更だけを許すのが一番安全です。

**🇰🇷 답변**

후방 호환은 **새 스키마로 쓴 데이터를 옛 읽는 쪽이 읽을 수 있는** 것, 전방 호환은 그 반대로 옛 데이터를 새 읽는 쪽이 읽을 수 있는 것입니다.

어느 쪽이 필요한지는 배포 순서로 정해집니다. 컨슈머를 먼저 올리면 후방 호환, 프로듀서를 먼저 올리면 전방 호환이 필요합니다. 양쪽을 다 만족하는 변경만 허용하는 것이 가장 안전합니다.

### Q21. メッセージのサイズが大きい場合はどうしますか？
(메시지가 클 때)

**🇯🇵 回答**

大きなペイロードを直接流すのは避けます。ブローカーのメモリとレプリケーションに効くうえ、上限の設定を送信側・ブローカー・受信側の三箇所で合わせる必要があります。

実務では、本体をオブジェクトストレージに置いて**参照だけを流す**方式を取ります。どうしても大きいまま送るなら圧縮を有効にします。圧縮はスループットにも効きます。

**🇰🇷 답변**

큰 페이로드를 그대로 흘리는 것은 피합니다. 브로커의 메모리와 복제에 영향을 주고, 상한 설정을 보내는 쪽·브로커·받는 쪽 세 군데에서 맞춰야 합니다.

실무에서는 본체를 오브젝트 스토리지에 두고 **참조만 흘리는** 방식을 씁니다. 굳이 크게 보내야 하면 압축을 켭니다. 압축은 처리량에도 효과가 있습니다.

### Q22. プロデューサのスループットはどう上げますか？
(프로듀서 처리량 향상)

**🇯🇵 回答**

まとめて送ることです。`linger.ms` を少し待たせ、`batch.size` を大きくすると、往復とオーバーヘッドが減ります。圧縮も併用します。

代わりに `linger.ms` の分だけ遅延が増えます。スループットと遅延はここでトレードオフになるので、**要件のどちらが重いか**を決めてから調整します。

**🇰🇷 답변**

묶어서 보내는 것입니다. `linger.ms` 로 조금 기다리게 하고 `batch.size` 를 키우면 왕복과 오버헤드가 줄어듭니다. 압축도 함께 씁니다.

대신 `linger.ms` 만큼 지연이 늘어납니다. 처리량과 지연이 여기서 트레이드오프가 되므로 **요건에서 어느 쪽이 무거운지**를 정한 뒤 조정합니다.

### Q23. Kafka はなぜ速いのですか？
(Kafka 가 빠른 이유)

**🇯🇵 回答**

追記専用のログなのでディスクへの書き込みが順次アクセスになること、OS のページキャッシュをそのまま使うこと、そしてバッチと圧縮でネットワークの往復を減らしていることです。

コンシューマがオフセットを自分で管理するので、ブローカーがメッセージごとの状態を持たなくてよい点も効いています。ブローカーの仕事が単純だから速い、という理解をしています。

**🇰🇷 답변**

추가 전용 로그라 디스크 쓰기가 순차 접근이 되는 것, OS 의 페이지 캐시를 그대로 쓰는 것, 그리고 배치와 압축으로 네트워크 왕복을 줄이는 것입니다.

컨슈머가 오프셋을 스스로 관리하므로 브로커가 메시지별 상태를 갖지 않아도 되는 점도 큽니다. 브로커의 일이 단순하니까 빠르다고 이해하고 있습니다.

---

### Q24. Kafka と RabbitMQ はどう使い分けますか？
(Kafka 와 RabbitMQ 구분)

**🇯🇵 回答**

Kafka はログを保持して複数の消費者が独立に読める、再処理ができる、高スループットです。RabbitMQ は柔軟なルーティングと、メッセージ単位の確認・優先度が得意です。

イベントを配って後から使い道が増えるなら Kafka、ワークキューとして一件ずつ確実に捌くなら RabbitMQ、という選び方をしています。

**🇰🇷 답변**

Kafka 는 로그를 보관해 여러 소비자가 독립적으로 읽고 재처리가 가능하며 처리량이 높습니다. RabbitMQ 는 유연한 라우팅과 메시지 단위 확인·우선순위가 강합니다.

이벤트를 배포해 나중에 쓰임새가 늘어난다면 Kafka, 작업 큐로 한 건씩 확실히 처리한다면 RabbitMQ 라는 식으로 고릅니다.

### Q25. ZooKeeper から KRaft に変わって何が違いますか？
(ZooKeeper 에서 KRaft 로 바뀌며 달라진 것)

**🇯🇵 回答**

メタデータの管理を Kafka 自身が Raft で行うようになり、外部の ZooKeeper が不要になりました。運用するコンポーネントが減り、メタデータの伝播も速くなっています。

新しく作るなら KRaft です。既存の環境を移行するときは、バージョンの前提と手順を確認します。**まだ ZooKeeper 構成が現役の現場も多い**ので、面接では両方を知っている前提で話します。

**🇰🇷 답변**

메타데이터 관리를 Kafka 자신이 Raft 로 하게 되어 외부 ZooKeeper 가 필요 없어졌습니다. 운영할 구성요소가 줄고 메타데이터 전파도 빨라졌습니다.

새로 만든다면 KRaft 입니다. 기존 환경을 이행할 때는 버전 전제와 절차를 확인합니다. **아직 ZooKeeper 구성이 현역인 현장도 많으므로** 면접에서는 양쪽을 아는 전제로 이야기합니다.
