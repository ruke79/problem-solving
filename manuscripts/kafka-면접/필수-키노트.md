# Kafka 면접 — 필수 문항 지정과 키노트

> **시간이 부족할 때 이 파일만 보면 된다.** 50문항을 세 등급으로 나누고,
> S급에는 **일본어 한 문장**을 붙였다. 그 문장만 외워도 답이 성립한다.
>
> `KAFKA-01` 처럼 표시된 것은 **실물 브로커(Kafka 3.9) 위에서 돌려 확인한 것**이다 —
> `./gradlew :verify-labs-kafka:test` 로 직접 돌려 볼 수 있다.

## 1. S급 — 반드시 나온다 (10문항)

### ① 파티션과 순서 — 여기가 모든 제약의 출발점

**Q3. 순서 보장은 어디까지 되나** ★가장 자주 ✅`KAFKA-01`
> **同じパーティションの中だけ**です。トピック全体では保証されません。だから順序が必要な単位をキーにします。同じキーは常に同じパーティションへ行くので、その中では順序が保たれます。

**Q5. 컨슈머 그룹은 어떤 구조인가** ★가장 자주 ✅`KAFKA-05`
> 同じグループ ID のコンシューマでパーティションを分担し、一つのパーティションはグループ内の一つのコンシューマだけが読みます。別のグループを作れば、同じデータを独立して最初から読めます。

**Q13. 컨슈머를 늘리면 그만큼 빨라지나** ★함정 ✅`KAFKA-05`
> パーティション数までは効きますが、**それを超えたコンシューマは割り当てを受けられず待つだけ**です。だからオートスケールの上限はパーティション数になります。

---

### ② 신뢰성 — 오해가 가장 많은 영역

**Q10. Exactly-Once 는 무엇을 보장하나** ★함정 · 변별력 최고 ✅`KAFKA-04`
> 保証されるのは **Kafka の中で完結する範囲**です。外部の DB や API への副作用までは保証されないので、そこは冪等キーなどアプリ側の設計で守ります。「EOS があるから重複対策は不要」は誤解です。

**Q11. 오프셋 커밋은 어떻게 다루나** ★실무
> 自動コミットは処理が終わる前にコミットされて**失敗したメッセージを取りこぼす**ことがあります。処理後に手動でコミットすると at-least-once になるので、**処理は冪等に作る**のが前提です。

**Q7. `acks` 설정은 어떻게 고르나**
> データを失いたくないなら `acks=all` です。ただしそれだけでは足りず、**`min.insync.replicas` を 2 以上にして初めて意味を持ちます**。レプリカが一つしか生きていない状態で `all` にしても、それが落ちれば失われます。

---

### ③ 운영 — 장애가 나는 자리

**Q15. 처리에 실패한 메시지는 어떻게 하나** ★실무 함정 ✅`KAFKA-03`
> その場で無限に再試行すると、**後ろのメッセージが全部止まります**。一つの毒メッセージでパーティションが詰まるのが典型的な障害なので、回数を決めて再試行し、超えたら別のトピックに退避します。

**Q12. 컨슈머 랙은 무엇을 뜻하나** ★가장 자주 ✅`KAFKA-02`
> 発行された最新のオフセットと処理済みのオフセットの差で、追いついていない量を示します。見方の要点は**傾き**で、一時的に増えても減っていくならピークを吸収できています。

**Q31. 트래픽 급증을 어떻게 흡수하나** ★실무 ✅`MSA-03`
> 瞬間的なピークならキューが吸収しますが、**戻らないなら容量不足**です。ラグの傾きを見て、増え続けるならコンシューマを増やすか処理を速くします。キューは時間を稼ぐだけで処理能力は増やしません。

**Q26. DB 갱신과 이벤트 발행을 확실히 일치시키려면** ★설계 ✅`MSA-01`
> DB とブローカーは別のシステムなので一つのトランザクションにはできません。Outbox パターンで、**業務データと同じトランザクションで送信予定を専用テーブルに書き**、別プロセスが読んで発行します。

## 2. A급 — 자주 나온다 (15문항)

| Q | 한 줄 | 근거 |
|---|---|---|
| Q1 | 보내는 쪽과 받는 쪽을 떼어놓고, **같은 데이터를 여러 용도로** 쓸 때 | |
| Q2 | 토픽 = 논리 이름, 실체는 파티션. 오프셋은 파티션 안의 연번 | |
| Q4 | 파티션 수는 **나중에 줄일 수 없다**. 컨슈머 상한이 여기서 정해진다 | ✅`KAFKA-05` |
| Q6 | 리밸런스 중에는 처리가 멈춘다. 원인 1위는 **폴링 간격 초과** | |
| Q8 | ISR = 리더를 따라잡은 레플리카. 줄면 보장도 약해진다 | |
| Q9 | 프로듀서 멱등성은 3.0+ 기본. 막는 건 **재시도 중복뿐** | ✅`KAFKA-04` |
| Q16 | 재시도 토픽 방식은 **순서가 깨진다** | ✅`KAFKA-03` |
| Q17 | 보존 기간 = 재처리를 어디까지 거슬러 갈지 | |
| Q19·Q20 | 기본값 있는 필드 추가는 전방·후방 모두 호환 | ✅`KAFKA-07` |
| Q21 | 큰 페이로드는 참조만 흘리고 본체는 오브젝트 스토리지에 | |
| Q22 | `linger.ms`·`batch.size` 로 묶어 보낸다 → **처리량과 지연의 트레이드오프** | |
| Q23 | 순차 쓰기 + 페이지 캐시 + 배치. 브로커의 일이 단순해서 빠르다 | |
| Q27 | 수신 측 멱등성 — 처리한 ID 기록을 **업무 처리와 같은 트랜잭션에** | ✅`RES-01` |
| Q32 | 컨슈머가 느리면 대개 외부 I/O. 병렬도부터 올리면 하류가 막힌다 | |
| Q39 | "프로세스가 살아 있는가"가 아니라 "**진행하고 있는가**"를 본다 | |

## 4. 면접 30분 전 최종 점검 — 이것만은

**여섯 개의 "아니오"** 를 기억하면 함정 질문은 대부분 막힙니다.

| 질문의 유혹 | 정답 |
|---|---|
| Kafka 는 토픽 전체의 순서를 보장하나? | **아니오** — 파티션 안에서만 (Q3 ✅`KAFKA-01`) |
| 컨슈머를 늘리면 계속 빨라지나? | **아니오** — 파티션 수가 상한 (Q13 ✅`KAFKA-05`) |
| Exactly-Once 면 중복 대책이 필요 없나? | **아니오** — 외부 부수효과는 별개 (Q10 ✅`KAFKA-04`) |
| `acks=all` 이면 무조건 안 잃나? | **아니오** — `min.insync.replicas` 가 있어야 (Q7) |
| 실패한 메시지를 계속 재시도해도 되나? | **아니오** — 뒤가 전부 막힌다 (Q15 ✅`KAFKA-03`) |
| 파티션 수는 나중에 조정하면 되나? | **아니오** — **줄일 수 없다** (Q4) |

**그리고 하나의 "예"** — *Outbox 없이는 DB 와 발행의 일치를 보장할 수 없습니다.* (Q26 ✅`MSA-01`)
