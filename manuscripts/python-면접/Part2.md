### Q26. CPython のメモリ管理はどうなっていますか？
(CPython 의 메모리 관리)

**🇯🇵 回答**

基本は参照カウントです。参照が 0 になった瞬間に解放されるので、多くの場合は決定的に回収されます。

ただし循環参照は参照カウントでは消えないので、世代別のガベージコレクタが補います。`gc` モジュールで状況を見られますし、循環を作らない設計なら `gc.disable()` が選択肢になることもあります。

**🇰🇷 답변**

기본은 참조 카운팅입니다. 참조가 0 이 되는 순간 해제되므로 대부분 결정적으로 회수됩니다.

다만 순환 참조는 참조 카운팅으로 사라지지 않아서 세대별 가비지 컬렉터가 보완합니다. `gc` 모듈로 상황을 볼 수 있고, 순환을 만들지 않는 설계라면 `gc.disable()` 이 선택지가 되기도 합니다.

### Q27. Python でメモリリークはどんな形で起きますか？
(파이썬에서 메모리 누수의 형태)

**🇯🇵 回答**

多いのは、グローバルなキャッシュやリストに入れっぱなしにするケースです。参照が生きているので GC の対象になりません。

他には、循環参照に `__del__` が絡む場合、C 拡張側の解放漏れ、`lru_cache` を無制限で使ってしまう場合です。調査には `tracemalloc` でスナップショットを取り、差分で増えている割り当て箇所を見ます。

**🇰🇷 답변**

많은 것은 전역 캐시나 리스트에 계속 담아 두는 경우입니다. 참조가 살아 있으니 GC 대상이 되지 않습니다.

그 밖에는 순환 참조에 `__del__` 이 얽힌 경우, C 확장 쪽의 해제 누락, `lru_cache` 를 무제한으로 쓴 경우입니다. 조사는 `tracemalloc` 으로 스냅샷을 떠서 차분으로 늘어나는 할당 지점을 봅니다.

### Q28. 遅い処理の原因をどう特定しますか？
(느린 처리의 원인 특정)

**🇯🇵 回答**

まず全体のどこが遅いのかを切り分けます。DB なのか、外部 API なのか、Python のコードなのか。ここを飛ばして最適化を始めるのが一番の失敗です。

Python のコードだと分かったら `cProfile` で関数単位の内訳を見ます。本番の稼働中のプロセスを見たいときは `py-spy` が便利です。プロセスを止めずにサンプリングできます。

**🇰🇷 답변**

먼저 전체 중 어디가 느린지를 가릅니다. DB 인지, 외부 API 인지, 파이썬 코드인지. 이걸 건너뛰고 최적화를 시작하는 게 가장 큰 실패입니다.

파이썬 코드라고 판명되면 `cProfile` 로 함수 단위 내역을 봅니다. 운영 중인 프로세스를 보고 싶을 때는 `py-spy` 가 편합니다. 프로세스를 멈추지 않고 샘플링할 수 있습니다.

### Q29. 大きなファイルを処理するときの注意点は？
(큰 파일 처리 시 주의점)

**🇯🇵 回答**

`readlines()` で全部読むとファイルサイズ分のメモリを使います。ファイルオブジェクトはそのままイテレートできるので、行ごとに処理すれば一定メモリで済みます。

CSV なら `csv.reader`、巨大な JSON なら行区切りの JSONL にするか、ストリーミングパーサを使います。メモリに乗せる前に「本当に全部同時に必要か」を疑うのが先です。

**🇰🇷 답변**

`readlines()` 로 전부 읽으면 파일 크기만큼 메모리를 씁니다. 파일 객체는 그대로 순회할 수 있으므로 행 단위로 처리하면 일정 메모리로 끝납니다.

CSV 라면 `csv.reader`, 거대한 JSON 이라면 행 구분의 JSONL 로 바꾸거나 스트리밍 파서를 씁니다. 메모리에 올리기 전에 "정말 전부 동시에 필요한가"를 의심하는 게 먼저입니다.

### Q30. `functools.lru_cache` を使うときの注意点は？
(lru_cache 사용 시 주의점)

**🇯🇵 回答**

引数がハッシュ可能である必要があり、返り値が可変オブジェクトだと呼び出し側で書き換えられてキャッシュが汚れます。

それから `maxsize=None` は無制限なので、引数の種類が多い関数に付けるとそのままメモリリークになります。インスタンスメソッドに付けると `self` を掴んでオブジェクトが解放されない点も要注意です。

**🇰🇷 답변**

인자가 해시 가능해야 하고, 반환값이 가변 객체면 호출하는 쪽에서 고쳐 캐시가 오염됩니다.

그리고 `maxsize=None` 은 무제한이라 인자 종류가 많은 함수에 붙이면 그대로 메모리 누수가 됩니다. 인스턴스 메서드에 붙이면 `self` 를 잡아 객체가 해제되지 않는 점도 주의해야 합니다.

### Q31. 文字列の連結で気をつけることは？
(문자열 연결에서 주의할 점)

**🇯🇵 回答**

ループの中で `+=` を繰り返すと、文字列が不変なので毎回新しいオブジェクトが作られます。要素を集めて最後に `"".join()` する方が速く、意図も明確です。

ログやクエリを組み立てるときは、そもそも f-string やパラメータバインディングを使います。速度以前に、文字列結合でクエリを作ると SQL インジェクションの入口になります。

**🇰🇷 답변**

루프 안에서 `+=` 를 반복하면 문자열이 불변이라 매번 새 객체가 만들어집니다. 요소를 모아 마지막에 `"".join()` 하는 편이 빠르고 의도도 분명합니다.

로그나 쿼리를 조립할 때는 애초에 f-string 이나 파라미터 바인딩을 씁니다. 속도 이전에, 문자열 결합으로 쿼리를 만들면 SQL 인젝션의 입구가 됩니다.

### Q32. `collections` でよく使うものは何ですか？
(collections 에서 자주 쓰는 것)

**🇯🇵 回答**

`defaultdict` は初期化の分岐を消せますし、`Counter` は集計を一行にできます。両端の出し入れがあるキューには `deque` を使います。

`deque` は特に重要で、リストの先頭から `pop(0)` すると O(n) ですが、`deque.popleft()` は O(1) です。キューをリストで書いているコードは見つけたら直します。

**🇰🇷 답변**

`defaultdict` 는 초기화 분기를 없애 주고, `Counter` 는 집계를 한 줄로 만들어 줍니다. 양끝에서 넣고 빼는 큐에는 `deque` 를 씁니다.

`deque` 는 특히 중요합니다. 리스트의 앞에서 `pop(0)` 하면 O(n) 이지만 `deque.popleft()` 는 O(1) 입니다. 큐를 리스트로 짠 코드는 발견하면 고칩니다.

### Q33. `pickle` を使うときのリスクは？
(pickle 의 위험)

**🇯🇵 回答**

**信頼できないデータを `pickle.loads` すると任意のコードが実行されます。**外部から来たデータには絶対に使いません。

用途を内部のキャッシュやプロセス間通信に限り、外部とのやり取りは JSON や MessagePack のようなデータだけの形式にします。バージョン間の互換性が壊れやすい点も、永続化に向かない理由です。

**🇰🇷 답변**

**신뢰할 수 없는 데이터를 `pickle.loads` 하면 임의 코드가 실행됩니다.** 외부에서 온 데이터에는 절대 쓰지 않습니다.

용도를 내부 캐시나 프로세스 간 통신으로 한정하고, 외부와의 교환은 JSON 이나 MessagePack 처럼 데이터만 담는 형식으로 합니다. 버전 간 호환이 잘 깨지는 점도 영속화에 맞지 않는 이유입니다.

### Q34. ロギングで気をつけていることは？
(로깅에서 주의하는 것)

**🇯🇵 回答**

`print` は使わず `logging` を使います。出力先とレベルを後から変えられて、本番では構造化して出せるからです。

それから、文字列を先に組み立てないことです。`logger.debug("%s", obj)` と書けば、DEBUG が無効なときにフォーマットのコストがかかりません。個人情報や資格情報をログに出さないことも徹底します。

**🇰🇷 답변**

`print` 는 쓰지 않고 `logging` 을 씁니다. 출력 대상과 레벨을 나중에 바꿀 수 있고, 운영에서는 구조화해 내보낼 수 있기 때문입니다.

그리고 문자열을 미리 조립하지 않습니다. `logger.debug("%s", obj)` 로 쓰면 DEBUG 가 꺼져 있을 때 포매팅 비용이 들지 않습니다. 개인정보나 자격증명을 로그에 남기지 않는 것도 철저히 합니다.

### Q35. テストはどう書いていますか？
(테스트 작성 방식)

**🇯🇵 回答**

pytest を使い、fixture で準備を共有します。パラメータ化テストで入力の組み合わせを増やすのも pytest の強みです。

方針としては、外部依存はモックにしますが**モックしすぎないようにしています**。全部モックにすると、実際の結合が壊れていても緑になるからです。DB が絡むところは実物を立てて確かめます。

**🇰🇷 답변**

pytest 를 쓰고 fixture 로 준비를 공유합니다. 파라미터화 테스트로 입력 조합을 늘리는 것도 pytest 의 강점입니다.

방침으로는 외부 의존을 목으로 만들되 **너무 많이 목으로 만들지 않으려 합니다.** 전부 목으로 하면 실제 결합이 깨져 있어도 초록이 되기 때문입니다. DB 가 얽힌 곳은 실물을 띄워 확인합니다.

### Q36. WSGI と ASGI の違いは？
(WSGI 와 ASGI 의 차이)

**🇯🇵 回答**

WSGI は同期のインターフェースで、一リクエストを一スレッドやプロセスが最後まで持ちます。ASGI は非同期に対応していて、WebSocket や長時間接続も扱えます。

Django や Flask は WSGI が基本、FastAPI は ASGI です。ASGI にしても**中でブロッキング処理を呼べば意味がない**ので、DB ドライバまで非同期対応かを確認します。

**🇰🇷 답변**

WSGI 는 동기 인터페이스로 한 요청을 한 스레드나 프로세스가 끝까지 붙잡습니다. ASGI 는 비동기에 대응해 WebSocket 이나 장시간 연결도 다룰 수 있습니다.

Django 나 Flask 는 WSGI 가 기본, FastAPI 는 ASGI 입니다. ASGI 로 바꿔도 **안에서 블로킹 처리를 부르면 의미가 없으므로** DB 드라이버까지 비동기 대응인지 확인합니다.

### Q37. gunicorn のワーカー数はどう決めますか？
(gunicorn 워커 수 결정)

**🇯🇵 回答**

出発点はコア数の 2 倍プラス 1 とよく言われますが、実際にはワークロード次第です。CPU バウンドならコア数前後、I/O 待ちが長いならワーカーを増やすかスレッドや非同期ワーカーを併用します。

大事なのは、ワーカー数 × 各ワーカーの DB コネクション数が**データベース側の上限を超えないこと**です。アプリだけ見て増やすと DB が先に倒れます。

**🇰🇷 답변**

출발점은 흔히 코어 수의 2배 더하기 1 이라고 하지만 실제로는 워크로드에 달렸습니다. CPU 바운드면 코어 수 근처, I/O 대기가 길면 워커를 늘리거나 스레드·비동기 워커를 함께 씁니다.

중요한 것은 워커 수 × 워커당 DB 커넥션 수가 **데이터베이스 쪽 상한을 넘지 않는 것**입니다. 앱만 보고 늘리면 DB 가 먼저 쓰러집니다.

### Q38. Django ORM の N+1 はどう防ぎますか？
(Django ORM 의 N+1 방지)

**🇯🇵 回答**

`select_related` は正方向の外部キーを JOIN で、`prefetch_related` は多対多や逆参照を別クエリでまとめて取ります。

まず `django-debug-toolbar` や `CaptureQueriesContext` で**実際に何回クエリが飛んでいるかを数えます**。想像で直すのではなく、回数を見て減ったことを確認します。

**🇰🇷 답변**

`select_related` 는 정방향 외래키를 JOIN 으로, `prefetch_related` 는 다대다나 역참조를 별도 쿼리로 묶어 가져옵니다.

먼저 `django-debug-toolbar` 나 `CaptureQueriesContext` 로 **실제로 쿼리가 몇 번 나가는지를 셉니다.** 짐작으로 고치지 않고 횟수를 보고 줄었는지 확인합니다.

### Q39. トランザクションはどう扱いますか？
(트랜잭션 취급)

**🇯🇵 回答**

Django なら `transaction.atomic`、SQLAlchemy ならセッションのスコープで囲みます。範囲は短くして、外部 API 呼び出しは中に入れません。

コミット後にメールや通知を送りたい場合は `transaction.on_commit` を使います。トランザクションの中で送ると、ロールバックしたのに通知だけ飛ぶという事故になります。

**🇰🇷 답변**

Django 라면 `transaction.atomic`, SQLAlchemy 라면 세션 스코프로 감쌉니다. 범위는 짧게 하고 외부 API 호출은 안에 넣지 않습니다.

커밋 후에 메일이나 알림을 보내고 싶으면 `transaction.on_commit` 을 씁니다. 트랜잭션 안에서 보내면 롤백했는데 알림만 나가는 사고가 됩니다.

### Q40. 外部 API を呼ぶときに必ず設定することは？
(외부 API 호출 시 반드시 설정하는 것)

**🇯🇵 回答**

タイムアウトです。`requests` はデフォルトで無期限なので、指定しないと相手が応答しないだけでこちらのワーカーが枯渇します。

その上で、リトライは指数バックオフとジッターを入れ、**冪等な操作にだけ**適用します。連続して失敗する相手にはサーキットブレーカーで早く諦める仕組みを入れます。

**🇰🇷 답변**

타임아웃입니다. `requests` 는 기본이 무기한이라, 지정하지 않으면 상대가 응답하지 않는 것만으로 이쪽 워커가 고갈됩니다.

그 위에 재시도는 지수 백오프와 지터를 넣고 **멱등한 조작에만** 적용합니다. 계속 실패하는 상대에게는 서킷 브레이커로 빨리 포기하는 장치를 넣습니다.

### Q41. 設定値や機密情報はどう管理しますか？
(설정값과 기밀정보 관리)

**🇯🇵 回答**

コードに書かず、環境変数か秘密管理サービスから読みます。リポジトリに `.env` を入れないのは基本で、代わりに `.env.example` でキーの一覧だけ共有します。

読み込みは Pydantic Settings のように**型と必須チェックが効く形**にしておくと、設定漏れが起動時に分かります。実行してしばらく経ってから落ちるのが一番困ります。

**🇰🇷 답변**

코드에 쓰지 않고 환경변수나 비밀 관리 서비스에서 읽습니다. 저장소에 `.env` 를 넣지 않는 것은 기본이고, 대신 `.env.example` 로 키 목록만 공유합니다.

읽어들이는 쪽은 Pydantic Settings 처럼 **타입과 필수 검사가 되는 형태**로 두면 설정 누락이 기동 시점에 드러납니다. 한참 돌다가 죽는 게 가장 곤란합니다.

### Q42. 日時はどう扱いますか？
(날짜·시간 취급)

**🇯🇵 回答**

保存と内部処理は UTC の aware な datetime に統一し、表示のときだけタイムゾーンを変換します。

naive な datetime を混ぜないことが肝心です。比較や差分で例外になったり、暗黙にサーバのタイムゾーンで解釈されて、夏時間や海外リージョンで事故になります。Django なら `USE_TZ=True` を前提にします。

**🇰🇷 답변**

저장과 내부 처리는 UTC 의 aware datetime 으로 통일하고, 표시할 때만 시간대를 변환합니다.

naive datetime 을 섞지 않는 것이 핵심입니다. 비교나 차분에서 예외가 나거나, 암묵적으로 서버 시간대로 해석되어 서머타임이나 해외 리전에서 사고가 납니다. Django 라면 `USE_TZ=True` 를 전제로 합니다.

### Q43. 依存関係はどう管理していますか？
(의존성 관리)

**🇯🇵 回答**

仮想環境を必ず切り、ロックファイルでバージョンを固定します。`requirements.txt` にバージョンを書かないと、ビルドのたびに違うものが入って再現できません。

最近は poetry や uv を使うことが多いです。どれを使うにせよ、**「開発と本番で同じものが入る」ことが目的**です。加えて依存の脆弱性スキャンを CI に入れます。

**🇰🇷 답변**

가상환경을 반드시 만들고 락 파일로 버전을 고정합니다. `requirements.txt` 에 버전을 안 적으면 빌드할 때마다 다른 게 들어와 재현이 안 됩니다.

요즘은 poetry 나 uv 를 많이 씁니다. 어느 쪽이든 **"개발과 운영에 같은 것이 들어간다"가 목적**입니다. 여기에 의존성 취약점 스캔을 CI 에 넣습니다.

### Q44. コード品質はどう保っていますか？
(코드 품질 유지)

**🇯🇵 回答**

フォーマッタとリンタを CI で強制します。最近は ruff 一つでリントとフォーマットを賄えるので、設定が単純になりました。

その上で mypy を段階的に導入します。全部に型を付けるのは現実的でないので、新しく書くコードと壊れやすい境界から入れていきます。レビューで指摘するより機械に任せる方が続きます。

**🇰🇷 답변**

포매터와 린터를 CI 에서 강제합니다. 요즘은 ruff 하나로 린트와 포맷을 다 할 수 있어 설정이 단순해졌습니다.

그 위에 mypy 를 단계적으로 도입합니다. 전부에 타입을 붙이는 건 현실적이지 않아서, 새로 쓰는 코드와 깨지기 쉬운 경계부터 넣습니다. 리뷰에서 지적하기보다 기계에 맡기는 편이 오래갑니다.

### Q45. `eval` や `subprocess` の危険性は？
(eval 과 subprocess 의 위험)

**🇯🇵 回答**

`eval` や `exec` に外部入力を渡すと任意コード実行になります。設定を評価したいだけなら JSON や専用のパーサを使います。

`subprocess` は `shell=True` が危険です。文字列としてシェルに渡るので、入力に `;` や `|` が入ると別のコマンドが動きます。引数はリストで渡し、シェルを介さないのが基本です。

**🇰🇷 답변**

`eval` 이나 `exec` 에 외부 입력을 넘기면 임의 코드 실행이 됩니다. 설정을 평가하고 싶을 뿐이라면 JSON 이나 전용 파서를 씁니다.

`subprocess` 는 `shell=True` 가 위험합니다. 문자열로 셸에 넘어가므로 입력에 `;` 나 `|` 가 들어가면 다른 명령이 실행됩니다. 인자는 리스트로 넘기고 셸을 거치지 않는 것이 기본입니다.

### Q46. 文字コードで困った経験はありますか？
(문자 인코딩 관련 경험)

**🇯🇵 回答**

ファイルを開くときに `encoding` を明示しないと、実行環境の既定に依存します。Windows と Linux で挙動が変わり、CI では通るのに本番で落ちるということが起きます。

なので `open(..., encoding="utf-8")` を必ず書きます。それから Unicode の正規化も注意点です。見た目が同じでもコードポイントが違うと比較が一致しないので、入力の段階で正規化しておきます。

**🇰🇷 답변**

파일을 열 때 `encoding` 을 명시하지 않으면 실행 환경의 기본값에 의존합니다. 윈도우와 리눅스에서 동작이 달라져, CI 는 통과하는데 운영에서 죽는 일이 생깁니다.

그래서 `open(..., encoding="utf-8")` 을 반드시 씁니다. 그리고 유니코드 정규화도 주의점입니다. 겉보기가 같아도 코드포인트가 다르면 비교가 일치하지 않으므로 입력 단계에서 정규화해 둡니다.

### Q47. 数値計算で気をつけることは？
(수치 계산에서 주의할 점)

**🇯🇵 回答**

浮動小数点は二進数なので、`0.1 + 0.2` が `0.3` になりません。金額のように誤差が許されないものは `Decimal` を使うか、整数の最小単位で持ちます。

比較も `==` ではなく `math.isclose` を使います。集計を繰り返すと誤差が積み上がるので、どこで丸めるかを設計時に決めておきます。

**🇰🇷 답변**

부동소수점은 이진수라서 `0.1 + 0.2` 가 `0.3` 이 되지 않습니다. 금액처럼 오차가 허용되지 않는 것은 `Decimal` 을 쓰거나 정수의 최소 단위로 갖습니다.

비교도 `==` 가 아니라 `math.isclose` 를 씁니다. 집계를 반복하면 오차가 쌓이므로 어디서 반올림할지를 설계 시점에 정해 둡니다.

### Q48. パッケージの循環インポートはなぜ起きて、どう直しますか？
(순환 import 의 원인과 해결)

**🇯🇵 回答**

A が B を、B が A を読み込むと、初期化の途中で未定義の名前を参照して失敗します。

回避策として関数の中でインポートする手はありますが、根本の原因は**モジュールの責務が絡み合っていること**です。共通部分を第三のモジュールに切り出すか、依存の向きを一方向に整理します。型注釈だけが理由なら `TYPE_CHECKING` で十分です。

**🇰🇷 답변**

A 가 B 를, B 가 A 를 읽으면 초기화 도중에 아직 정의되지 않은 이름을 참조해 실패합니다.

함수 안에서 import 하는 회피책도 있지만, 근본 원인은 **모듈의 책임이 얽혀 있는 것**입니다. 공통 부분을 제3의 모듈로 떼어내거나 의존 방향을 한쪽으로 정리합니다. 타입 주석만이 이유라면 `TYPE_CHECKING` 으로 충분합니다.

### Q49. Python のバージョンアップにはどう追随していますか？
(파이썬 버전 업 추종)

**🇯🇵 回答**

まずサポート期限を見て、EOL になる前に上げる計画を立てます。上げる前に依存ライブラリの対応状況を確認するのが実務では一番の関門です。

手順としては、CI に新しいバージョンのジョブを並行で足して、通ることを確認してから本番を切り替えます。3.11 以降は性能改善が大きいので、上げること自体に効果があります。

**🇰🇷 답변**

먼저 지원 기한을 보고 EOL 전에 올릴 계획을 세웁니다. 올리기 전에 의존 라이브러리의 대응 상황을 확인하는 것이 실무에서 가장 큰 관문입니다.

절차로는 CI 에 새 버전 잡을 병행으로 추가해 통과를 확인한 뒤 운영을 전환합니다. 3.11 이후는 성능 개선이 커서 올리는 것 자체에 효과가 있습니다.

### Q50. GIL がなくなるという話がありますが、どう見ていますか？
(GIL 제거 논의를 어떻게 보는가)

**🇯🇵 回答**

自由スレッド版が実験的に入り始めていますが、当面は**既存の前提が変わらないものとして設計します**。C 拡張の対応やシングルスレッド性能の影響がまだ見えないからです。

なので今は、CPU バウンドはプロセス分割、I/O バウンドは非同期という判断を変えていません。新しい選択肢が安定したら、まず測ってから採用を考える立場です。

**🇰🇷 답변**

프리스레디드 버전이 실험적으로 들어오기 시작했지만, 당분간은 **기존 전제가 바뀌지 않는다고 보고 설계합니다.** C 확장의 대응이나 싱글스레드 성능 영향이 아직 보이지 않기 때문입니다.

그래서 지금은 CPU 바운드는 프로세스 분할, I/O 바운드는 비동기라는 판단을 바꾸지 않았습니다. 새 선택지가 안정되면 먼저 재 보고 채택을 검토하는 입장입니다.
