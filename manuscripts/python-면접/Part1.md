### Q1. リストとタプルの違いは何ですか？
(리스트와 튜플의 차이)

**🇯🇵 回答**

一番の違いは可変か不変かです。リストは要素を追加・変更できますが、タプルは作った後は変えられません。

そのためタプルは辞書のキーや集合の要素にできますし、意図しない変更を防げます。実務では「後で変わるもの」はリスト、「一組の値として固定したいもの」はタプル、と使い分けています。

**🇰🇷 답변**

가장 큰 차이는 가변이냐 불변이냐입니다. 리스트는 요소를 추가·변경할 수 있지만 튜플은 만든 뒤에는 바꿀 수 없습니다.

그래서 튜플은 딕셔너리의 키나 집합의 원소가 될 수 있고, 의도치 않은 변경을 막아 줍니다. 실무에서는 "나중에 바뀌는 것"은 리스트, "한 묶음의 값으로 고정하고 싶은 것"은 튜플로 구분해 씁니다.

### Q2. デフォルト引数にリストを指定すると何が起きますか？
(기본 인자에 리스트를 지정하면 생기는 문제)

**🇯🇵 回答**

デフォルト値は関数の定義時に一度だけ評価されるので、呼び出しをまたいで同じオブジェクトが使い回されます。リストを渡すと、前の呼び出しで追加した要素が残ってしまいます。

対策は `None` を既定にして、関数の中で `if x is None: x = []` とすることです。これは面接でもよく出る典型的な落とし穴です。

**🇰🇷 답변**

기본값은 함수 정의 시점에 한 번만 평가되므로, 호출을 넘나들며 같은 객체가 재사용됩니다. 리스트를 넘기면 이전 호출에서 추가한 요소가 그대로 남습니다.

대책은 기본값을 `None` 으로 두고 함수 안에서 `if x is None: x = []` 로 만드는 것입니다. 면접에서도 자주 나오는 전형적인 함정입니다.

### Q3. 浅いコピーと深いコピーの違いは？
(얕은 복사와 깊은 복사의 차이)

**🇯🇵 回答**

浅いコピーは一段目だけを新しく作り、中の要素は元と同じオブジェクトを参照します。深いコピーは再帰的にすべて複製します。

ネストしたリストや辞書を浅くコピーすると、内側を変更したときに元も変わってしまいます。必要なときだけ `copy.deepcopy` を使います。深いコピーはコストが高いので、そもそも不変にする設計の方が安全です。

**🇰🇷 답변**

얕은 복사는 한 겹만 새로 만들고 안쪽 요소는 원본과 같은 객체를 참조합니다. 깊은 복사는 재귀적으로 전부 복제합니다.

중첩된 리스트나 딕셔너리를 얕게 복사하면 안쪽을 바꿨을 때 원본도 바뀝니다. 필요할 때만 `copy.deepcopy` 를 씁니다. 깊은 복사는 비용이 크므로 애초에 불변으로 설계하는 편이 안전합니다.

### Q4. `is` と `==` はどう違いますか？
(is 와 == 의 차이)

**🇯🇵 回答**

`is` は同一オブジェクトかどうか、`==` は値が等しいかどうかを見ます。

小さい整数や短い文字列はインターンされていて `is` が偶然 `True` になることがありますが、それに依存してはいけません。`is` を使うのは `None` の判定のように「唯一のオブジェクト」と比べるときだけです。

**🇰🇷 답변**

`is` 는 같은 객체인지, `==` 는 값이 같은지를 봅니다.

작은 정수나 짧은 문자열은 인터닝되어 있어 `is` 가 우연히 `True` 가 되기도 하지만, 거기에 의존하면 안 됩니다. `is` 를 쓰는 건 `None` 판정처럼 "유일한 객체"와 비교할 때뿐입니다.

### Q5. 辞書の内部構造と、順序が保証されるのはいつからですか？
(딕셔너리 내부 구조와 순서 보장)

**🇯🇵 回答**

ハッシュテーブルです。キーのハッシュ値でスロットを決め、衝突したら別のスロットを探します。平均的な検索は O(1) です。

挿入順の保持は CPython 3.6 の実装詳細として入り、**3.7 から言語仕様として保証**されました。それ以前を想定するなら `OrderedDict` を使います。

**🇰🇷 답변**

해시 테이블입니다. 키의 해시값으로 슬롯을 정하고, 충돌하면 다른 슬롯을 찾습니다. 평균 조회는 O(1) 입니다.

삽입 순서 유지는 CPython 3.6 에서 구현 세부로 들어왔고 **3.7 부터 언어 사양으로 보장**됩니다. 그 이전을 상정한다면 `OrderedDict` 를 씁니다.

### Q6. 辞書のキーにできるものとできないものは？
(딕셔너리 키가 될 수 있는 것과 없는 것)

**🇯🇵 回答**

ハッシュ可能なオブジェクトだけです。具体的には不変で、`__hash__` と `__eq__` が一貫しているものです。

リストや辞書はキーにできません。自作クラスをキーにするときは `__eq__` を定義したら `__hash__` も必ず一緒に定義します。片方だけ変えると、同じはずのキーで値を取り出せなくなります。

**🇰🇷 답변**

해시 가능한 객체만 됩니다. 구체적으로는 불변이고 `__hash__` 와 `__eq__` 가 일관된 것입니다.

리스트나 딕셔너리는 키가 될 수 없습니다. 직접 만든 클래스를 키로 쓸 때는 `__eq__` 를 정의했다면 `__hash__` 도 반드시 함께 정의합니다. 한쪽만 바꾸면 같은 키인데도 값을 못 꺼냅니다.

### Q7. リスト内包表記はループより速いですか？
(리스트 컴프리헨션이 루프보다 빠른가)

**🇯🇵 回答**

多くの場合は速いです。`append` のメソッド解決と呼び出しが省かれ、バイトコードのレベルで最適化されるからです。

ただし速さより可読性を優先します。三重のネストや条件が複雑になるなら、普通のループの方が読めます。内包表記は副作用のない変換に使う、と決めています。

**🇰🇷 답변**

대체로 빠릅니다. `append` 의 메서드 해석과 호출이 생략되고 바이트코드 수준에서 최적화되기 때문입니다.

다만 속도보다 가독성을 우선합니다. 삼중 중첩이거나 조건이 복잡해지면 평범한 루프가 더 읽힙니다. 컴프리헨션은 부수효과 없는 변환에만 쓴다고 정해 두고 있습니다.

### Q8. ジェネレータは何が嬉しいのですか？
(제너레이터의 장점)

**🇯🇵 回答**

値を一度に全部作らず、必要になったときに一つずつ返すので、**メモリを要素数に比例させずに済みます**。巨大なファイルの行処理や、無限に続く数列を扱えます。

`yield` を書くだけで作れます。ただし一度しか回せないので、二度使いたい場合はリストに落とすか、生成関数をもう一度呼びます。

**🇰🇷 답변**

값을 한꺼번에 만들지 않고 필요할 때 하나씩 돌려주므로 **메모리가 요소 수에 비례하지 않습니다.** 거대한 파일의 행 처리나 무한 수열을 다룰 수 있습니다.

`yield` 만 쓰면 만들어집니다. 다만 한 번만 순회할 수 있어서 두 번 쓰려면 리스트로 만들거나 생성 함수를 다시 호출해야 합니다.

### Q9. イテレータとイテラブルの違いは？
(이터레이터와 이터러블의 차이)

**🇯🇵 回答**

イテラブルは `__iter__` を持ち「イテレータを作れる」ものです。イテレータは `__next__` を持ち「次を返せる」もので、状態を持ちます。

リストはイテラブルですがイテレータではありません。`for` は内部で `iter()` を呼んでイテレータを取り出しています。ここを分けて理解していると、ジェネレータを二度回せない理由も自然に説明できます。

**🇰🇷 답변**

이터러블은 `__iter__` 를 가진 "이터레이터를 만들 수 있는" 것입니다. 이터레이터는 `__next__` 를 가진 "다음을 돌려줄 수 있는" 것이고 상태를 가집니다.

리스트는 이터러블이지만 이터레이터는 아닙니다. `for` 는 내부에서 `iter()` 를 불러 이터레이터를 꺼냅니다. 이 구분을 알고 있으면 제너레이터를 두 번 못 도는 이유도 자연스럽게 설명됩니다.

### Q10. クロージャとは何ですか？ループ変数を捕まえるときの注意は？
(클로저와 루프 변수 캡처 주의점)

**🇯🇵 回答**

外側のスコープの変数を覚えたまま持ち歩く関数のことです。

注意点は、捕まえるのは**値ではなく変数そのもの**だということです。ループの中で関数を作って後で呼ぶと、全部が最後の値を見ます。防ぐにはデフォルト引数で束縛するか、`functools.partial` を使います。

**🇰🇷 답변**

바깥 스코프의 변수를 기억한 채 들고 다니는 함수입니다.

주의할 점은 잡는 것이 **값이 아니라 변수 자체**라는 것입니다. 루프 안에서 함수를 만들어 나중에 호출하면 전부 마지막 값을 봅니다. 막으려면 기본 인자로 묶거나 `functools.partial` 을 씁니다.

### Q11. デコレータは何をするものですか？
(데코레이터란)

**🇯🇵 回答**

関数を受け取って関数を返す仕組みで、元の処理を書き換えずに前後の処理を足せます。ロギング、計測、リトライ、キャッシュなどに使います。

書くときは `functools.wraps` を必ず付けます。付けないと関数名やドキュメント文字列が失われて、デバッグやドキュメント生成で困ります。

**🇰🇷 답변**

함수를 받아 함수를 돌려주는 구조로, 원래 처리를 고치지 않고 앞뒤 처리를 덧붙일 수 있습니다. 로깅·측정·재시도·캐시 등에 씁니다.

작성할 때는 `functools.wraps` 를 반드시 붙입니다. 안 붙이면 함수 이름과 독스트링이 사라져서 디버깅이나 문서 생성에서 곤란해집니다.

### Q12. `*args` と `**kwargs` は何ですか？
(*args 와 **kwargs)

**🇯🇵 回答**

`*args` は位置引数をタプルで、`**kwargs` はキーワード引数を辞書でまとめて受け取ります。

デコレータやラッパーのように「引数をそのまま通す」場面で使います。逆に普通の API で多用すると、シグネチャから何を渡すべきか読めなくなるので、公開する関数では明示的な引数を優先します。

**🇰🇷 답변**

`*args` 는 위치 인자를 튜플로, `**kwargs` 는 키워드 인자를 딕셔너리로 묶어 받습니다.

데코레이터나 래퍼처럼 "인자를 그대로 통과시키는" 자리에 씁니다. 반대로 일반 API 에서 남발하면 시그니처만 봐서는 무엇을 넘겨야 할지 알 수 없으므로, 공개 함수에서는 명시적인 인자를 우선합니다.

### Q13. 変数のスコープはどう解決されますか？
(변수 스코프 해석 순서)

**🇯🇵 回答**

LEGB の順です。ローカル、外側の関数、グローバル、組み込みの順に探します。

関数の中でグローバル変数に代入したい場合は `global`、外側の関数の変数に代入したい場合は `nonlocal` が要ります。ただし、どちらも使うということは設計を見直す合図でもあります。

**🇰🇷 답변**

LEGB 순서입니다. 지역 → 감싸는 함수 → 전역 → 빌트인 순으로 찾습니다.

함수 안에서 전역 변수에 대입하려면 `global`, 바깥 함수의 변수에 대입하려면 `nonlocal` 이 필요합니다. 다만 둘 다 쓴다는 것은 설계를 다시 볼 신호이기도 합니다.

### Q14. GIL とは何で、何が制限されますか？
(GIL 이란)

**🇯🇵 回答**

CPython のインタプリタが同時に一つのスレッドしか Python バイトコードを実行させない仕組みです。参照カウントの安全性を単純に保つためにあります。

制限されるのは **CPU バウンドの並列化**です。I/O 待ちの間は GIL が解放されるので、ネットワークやファイル待ちが多い処理はスレッドでも効果があります。CPU を使い切りたいなら `multiprocessing` を使います。

**🇰🇷 답변**

CPython 인터프리터가 동시에 한 스레드만 파이썬 바이트코드를 실행하게 하는 장치입니다. 참조 카운팅의 안전성을 단순하게 지키려고 있습니다.

제한되는 것은 **CPU 바운드의 병렬화**입니다. I/O 대기 중에는 GIL 이 풀리므로 네트워크나 파일 대기가 많은 처리는 스레드로도 효과가 있습니다. CPU 를 다 쓰고 싶으면 `multiprocessing` 을 씁니다.

### Q15. スレッド・プロセス・asyncio はどう使い分けますか？
(스레드·프로세스·asyncio 사용 구분)

**🇯🇵 回答**

I/O バウンドで接続数が多いなら asyncio、I/O バウンドだが既存のブロッキングライブラリを使うならスレッド、CPU バウンドならプロセスです。

判断の起点は「待っているのか、計算しているのか」です。まず測って、待ち時間が支配的ならスレッドや asyncio、CPU が張り付いているならプロセスに分けます。

**🇰🇷 답변**

I/O 바운드이고 연결 수가 많으면 asyncio, I/O 바운드지만 기존 블로킹 라이브러리를 쓴다면 스레드, CPU 바운드면 프로세스입니다.

판단의 출발점은 "기다리고 있는가, 계산하고 있는가" 입니다. 먼저 재 보고 대기 시간이 지배적이면 스레드나 asyncio, CPU 가 붙어 있으면 프로세스로 나눕니다.

### Q16. `async`/`await` はどう動きますか？
(async/await 의 동작)

**🇯🇵 回答**

コルーチンを定義し、`await` の地点で制御をイベントループに返します。ループは待ち状態のタスクを置いておいて、別の準備できたタスクを進めます。

一番の注意点は、**コルーチンの中でブロッキング処理を呼ぶとループ全体が止まる**ことです。同期的なライブラリを使うなら `run_in_executor` でスレッドに逃がします。

**🇰🇷 답변**

코루틴을 정의하고 `await` 지점에서 제어를 이벤트 루프로 돌려줍니다. 루프는 대기 중인 태스크를 두고 준비된 다른 태스크를 진행시킵니다.

가장 큰 주의점은 **코루틴 안에서 블로킹 처리를 부르면 루프 전체가 멈춘다**는 것입니다. 동기 라이브러리를 써야 하면 `run_in_executor` 로 스레드에 넘깁니다.

### Q17. 例外処理の `else` と `finally` は何が違いますか？
(예외 처리의 else 와 finally)

**🇯🇵 回答**

`else` は例外が起きなかったときだけ実行され、`finally` は起きても起きなくても必ず実行されます。

`try` の中身は例外が出うる最小限にして、成功したときの続きは `else` に置くと、意図しない例外を握りつぶしません。後片付けは `finally` かコンテキストマネージャに任せます。

**🇰🇷 답변**

`else` 는 예외가 나지 않았을 때만 실행되고, `finally` 는 나든 안 나든 반드시 실행됩니다.

`try` 안은 예외가 날 수 있는 최소한으로 좁히고 성공했을 때의 후속 처리는 `else` 에 두면, 의도치 않은 예외를 삼키지 않습니다. 뒷정리는 `finally` 나 컨텍스트 매니저에 맡깁니다.

### Q18. コンテキストマネージャは何のためにありますか？
(컨텍스트 매니저의 목적)

**🇯🇵 回答**

「入るときと出るときの処理」を対にして、例外が出ても必ず後始末をするためです。ファイル、ロック、DB のトランザクションが典型です。

自作するときは `__enter__`/`__exit__` を実装するか、`contextlib.contextmanager` を使います。`with` を使えば `finally` を書き忘れる余地がなくなります。

**🇰🇷 답변**

"들어갈 때와 나올 때의 처리"를 짝지어, 예외가 나도 반드시 뒷정리를 하기 위해서입니다. 파일·락·DB 트랜잭션이 전형입니다.

직접 만들 때는 `__enter__`/`__exit__` 를 구현하거나 `contextlib.contextmanager` 를 씁니다. `with` 를 쓰면 `finally` 를 빠뜨릴 여지가 없어집니다.

### Q19. `__init__` と `__new__` の違いは？
(__init__ 과 __new__ 의 차이)

**🇯🇵 回答**

`__new__` はインスタンスを生成するもので、`__init__` は生成済みのインスタンスを初期化するものです。

普段は `__init__` だけで足ります。`__new__` を触るのは、不変型を継承するときやシングルトンのようにインスタンス生成そのものを制御したいときに限ります。

**🇰🇷 답변**

`__new__` 는 인스턴스를 생성하는 것이고, `__init__` 은 생성된 인스턴스를 초기화하는 것입니다.

평소에는 `__init__` 만으로 충분합니다. `__new__` 를 건드리는 건 불변 타입을 상속할 때나 싱글턴처럼 인스턴스 생성 자체를 제어하고 싶을 때로 한정합니다.

---

### Q20. 多重継承のメソッド解決順序(MRO)はどう決まりますか？
(다중 상속의 MRO)

**🇯🇵 回答**

C3 線形化というアルゴリズムで決まり、`ClassName.__mro__` で確認できます。深さ優先ではなく、継承の一貫した順序を保つ形です。

だからこそ `super()` は「親クラス」ではなく「MRO の次」を呼びます。協調的多重継承では、各クラスが `super()` を呼び続けることが前提になります。

**🇰🇷 답변**

C3 선형화라는 알고리즘으로 정해지고 `ClassName.__mro__` 로 확인할 수 있습니다. 깊이 우선이 아니라 상속의 일관된 순서를 유지하는 형태입니다.

그래서 `super()` 는 "부모 클래스"가 아니라 "MRO 상의 다음"을 호출합니다. 협조적 다중 상속에서는 각 클래스가 `super()` 를 계속 호출하는 것이 전제입니다.

### Q21. `@property` は何のために使いますか？
(@property 의 용도)

**🇯🇵 回答**

属性アクセスの形を保ったまま、裏で計算や検証を挟むためです。最初は素の属性で公開しておいて、後から `@property` に変えても呼び出し側は変わりません。

逆に、重い処理や副作用のあるものを property にするのは避けます。見た目が属性なので、呼ぶ側が「安い」と誤解するからです。

**🇰🇷 답변**

속성 접근 형태를 유지한 채 뒤에서 계산이나 검증을 끼우기 위해서입니다. 처음에는 평범한 속성으로 공개해 두고 나중에 `@property` 로 바꿔도 호출하는 쪽은 그대로입니다.

반대로 무거운 처리나 부수효과가 있는 것을 property 로 만드는 건 피합니다. 겉보기가 속성이라 부르는 쪽이 "싸다"고 오해하기 때문입니다.

---

### Q22. `dataclass`・`NamedTuple`・辞書はどう使い分けますか？
(dataclass·NamedTuple·dict 사용 구분)

**🇯🇵 回答**

構造が決まっているなら `dataclass`、不変で軽い値の組なら `NamedTuple`、キーが動的なら辞書です。

辞書を「型のように」使うのが一番ありがちな失敗です。キーの打ち間違いが実行時まで分からず、補完も効きません。`dataclass` にすると型チェックとエディタの支援が効きます。

**🇰🇷 답변**

구조가 정해져 있으면 `dataclass`, 불변이고 가벼운 값 묶음이면 `NamedTuple`, 키가 동적이면 딕셔너리입니다.

딕셔너리를 "타입처럼" 쓰는 것이 가장 흔한 실패입니다. 키 오타가 실행 시점까지 드러나지 않고 자동완성도 안 됩니다. `dataclass` 로 만들면 타입 검사와 에디터 지원을 받습니다.

### Q23. `__slots__` は何のためにありますか？
(__slots__ 의 목적)

**🇯🇵 回答**

インスタンスごとの `__dict__` をなくして、属性を固定し、メモリを減らすためです。同じオブジェクトを大量に持つときに効きます。

副作用として、宣言していない属性を後から生やせなくなります。それを「制約」ではなく「意図」として使える場面に限定します。

**🇰🇷 답변**

인스턴스마다의 `__dict__` 를 없애 속성을 고정하고 메모리를 줄이기 위해서입니다. 같은 객체를 대량으로 가질 때 효과가 있습니다.

부수효과로 선언하지 않은 속성을 나중에 붙일 수 없게 됩니다. 그것을 "제약"이 아니라 "의도"로 쓸 수 있는 자리에만 한정합니다.

---

### Q24. ダックタイピングと ABC・Protocol の関係は？
(덕 타이핑과 ABC·Protocol)

**🇯🇵 回答**

ダックタイピングは「その振る舞いができれば良い」という考え方です。ABC は継承を要求して実装を強制する仕組み、Protocol は**継承なしで構造だけで型を合わせる**仕組みです。

実務では、既存のクラスに手を入れられない場合や外部ライブラリを扱う場合に Protocol が便利です。静的チェックはできて、実行時の結合は増えません。

**🇰🇷 답변**

덕 타이핑은 "그 행동을 할 수 있으면 된다"는 사고방식입니다. ABC 는 상속을 요구해 구현을 강제하는 장치이고, Protocol 은 **상속 없이 구조만으로 타입을 맞추는** 장치입니다.

실무에서는 기존 클래스를 고칠 수 없거나 외부 라이브러리를 다룰 때 Protocol 이 편합니다. 정적 검사는 되면서 런타임 결합은 늘지 않습니다.

---

### Q25. 型ヒントは実行時に効きますか？
(타입 힌트는 런타임에 효과가 있나)

**🇯🇵 回答**

いいえ、実行時には基本的に無視されます。効かせるには mypy などの静的チェッカーを CI で回す必要があります。

それでも価値があります。エディタの補完と、リファクタリング時の安全性、そして何より**関数の契約がコードに書かれる**ことです。実行時の検証が必要なら Pydantic のようなライブラリを別途使います。

**🇰🇷 답변**

아니요, 런타임에는 기본적으로 무시됩니다. 효과를 보려면 mypy 같은 정적 검사기를 CI 에서 돌려야 합니다.

그래도 가치가 있습니다. 에디터 자동완성, 리팩터링 시 안전성, 그리고 무엇보다 **함수의 계약이 코드에 적힌다**는 점입니다. 런타임 검증이 필요하면 Pydantic 같은 라이브러리를 따로 씁니다.
