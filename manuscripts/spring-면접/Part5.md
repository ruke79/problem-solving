### Q116. Actuator では何を公開しますか？
(Actuator 로 무엇을 공개하나)

**🇯🇵 回答**

必要なものだけを明示的に公開します。既定では `health` と `info` だけが有効で、それ以外は自分で開ける必要があります。

注意すべきは `env`、`heapdump`、`beans` などです。設定値や内部構造が見えるので、**外部に露出させると情報漏洩になります**。管理用ポートを分けるか、認証を掛けるのが前提です。

**🇰🇷 답변**

필요한 것만 명시적으로 공개합니다. 기본으로는 `health` 와 `info` 만 켜져 있고, 그 외는 직접 열어야 합니다.

주의할 것은 `env`, `heapdump`, `beans` 등입니다. 설정값이나 내부 구조가 보이므로 **외부에 노출하면 정보 유출이 됩니다.** 관리용 포트를 나누거나 인증을 거는 것이 전제입니다.

### Q117. liveness と readiness の違いは？
(liveness 와 readiness 의 차이)

**🇯🇵 回答**

liveness は「プロセスが生きているか」で、失敗すると再起動されます。readiness は「トラフィックを受けられるか」で、失敗するとロードバランサから外されるだけです。

区別が重要なのは、**readiness に外部依存を含めてよいが liveness には含めてはいけない**からです。DBが一時的に落ちたときに liveness を失敗させると、全Podが再起動を繰り返して復旧をさらに遅らせます。

**🇰🇷 답변**

liveness 는 "프로세스가 살아 있는가"로, 실패하면 재시작됩니다. readiness 는 "트래픽을 받을 수 있는가"로, 실패하면 로드밸런서에서 빠질 뿐입니다.

구별이 중요한 이유는 **readiness 에는 외부 의존을 포함해도 되지만 liveness 에는 포함하면 안 되기** 때문입니다. DB 가 일시적으로 죽었을 때 liveness 를 실패시키면 모든 Pod 가 재시작을 반복해 복구를 더 늦춥니다.

### Q118. graceful shutdown はなぜ必要ですか？
(graceful shutdown 은 왜 필요한가)

**🇯🇵 回答**

処理中のリクエストを完了させてから終了するためです。いきなりプロセスを落とすと、処理中のリクエストがエラーになります。

`server.shutdown=graceful` を有効にし、猶予時間を設定します。加えてKubernetesでは、ロードバランサから外れる前にプロセスが終わらないよう、`preStop` で数秒待つ必要があります。**ルーティング除外の伝播には時間差がある**からです。

**🇰🇷 답변**

처리 중인 요청을 완료시킨 뒤 종료하기 위해서입니다. 갑자기 프로세스를 죽이면 처리 중인 요청이 에러가 됩니다.

`server.shutdown=graceful` 을 켜고 유예 시간을 설정합니다. 여기에 Kubernetes 에서는 로드밸런서에서 빠지기 전에 프로세스가 끝나지 않도록 `preStop` 으로 몇 초 기다려야 합니다. **라우팅 제외의 전파에는 시간차가 있기** 때문입니다.

### Q119. 監視すべき指標は何ですか？
(모니터링해야 할 지표)

**🇯🇵 回答**

まずリクエストレート、エラー率、レイテンシです。レイテンシは平均ではなく p95・p99 を見ます。平均は外れ値を隠すからです。

加えてリソース側として、スレッドプールの使用率、コネクションプールの active と pending、GCの頻度と時間を見ます。**利用者が体感するものから逆算して選ぶ**のが原則で、測りやすい指標を安易に選ぶとSLOがずれます。

**🇰🇷 답변**

먼저 요청률, 에러율, 지연입니다. 지연은 평균이 아니라 p95·p99 를 봅니다. 평균은 이상치를 감추기 때문입니다.

여기에 리소스 쪽으로 스레드풀 사용률, 커넥션 풀의 active 와 pending, GC 빈도와 시간을 봅니다. **이용자가 체감하는 것에서 역산해 고르는 것**이 원칙이고, 재기 쉬운 지표를 안이하게 고르면 SLO 가 어긋납니다.

### Q120. 分散トレーシングは何を解決しますか？
(분산 트레이싱은 무엇을 해결하나)

**🇯🇵 回答**

複数サービスをまたいだ一つのリクエストを、繋がった形で追えるようにします。マイクロサービスでは、どのサービスのどこで時間がかかったかがログだけでは分かりません。

トレースIDを伝播させ、ログにも同じIDを出すのが要点です。**非同期処理やスレッドプールをまたぐとコンテキストが切れる**ので、そこは明示的に引き継ぐ必要があります。切れていることに気づかず「トレースが途中で終わる」のはよくある落とし穴です。

**🇰🇷 답변**

여러 서비스를 넘나드는 하나의 요청을 이어진 형태로 추적할 수 있게 합니다. 마이크로서비스에서는 어느 서비스의 어디서 시간이 걸렸는지가 로그만으로는 알 수 없습니다.

트레이스 ID 를 전파하고 로그에도 같은 ID 를 남기는 것이 요점입니다. **비동기 처리나 스레드풀을 넘으면 컨텍스트가 끊기므로** 거기는 명시적으로 인계해야 합니다. 끊긴 걸 모르고 "트레이스가 도중에 끝난다"는 흔한 함정입니다.

### Q121. サンプリングを入れると何に注意しますか？
(샘플링을 넣으면 무엇을 주의하나)

**🇯🇵 回答**

コストは下がりますが、**稀に起きるエラーがサンプリングから漏れる**ことです。まさに調べたい事象だけが記録されていない、という事態が起きます。

だからエラーや遅いリクエストは必ず残す、という条件付きサンプリングにします。全体は低い比率で、異常なものは100%という形です。

**🇰🇷 답변**

비용은 내려가지만 **드물게 나는 에러가 샘플링에서 누락된다**는 것입니다. 정작 조사하고 싶은 사건만 기록되지 않는 사태가 생깁니다.

그래서 에러나 느린 요청은 반드시 남기는 조건부 샘플링으로 합니다. 전체는 낮은 비율로, 이상한 것은 100% 로 하는 형태입니다.

### Q122. 構造化ログはなぜ必要ですか？
(구조화 로그는 왜 필요한가)

**🇯🇵 回答**

検索と集計ができるようにするためです。テキストのままだと、grep はできても「特定ユーザーの、特定期間の、エラーだけ」を集計するのが困難です。

JSONで出力し、トレースID、ユーザーID、リクエストIDのようなキーを固定します。**個人情報や認証情報を出さない**ことも同時に設計します。ログは長期に保存されるので、一度出してしまうと回収が難しいからです。

**🇰🇷 답변**

검색과 집계를 가능하게 하기 위해서입니다. 텍스트 그대로면 grep 은 되어도 "특정 사용자의, 특정 기간의, 에러만"을 집계하기가 어렵습니다.

JSON 으로 출력하고 트레이스 ID, 사용자 ID, 요청 ID 같은 키를 고정합니다. **개인정보나 인증 정보를 남기지 않는 것**도 함께 설계합니다. 로그는 장기간 보존되므로 한 번 남기면 회수가 어렵기 때문입니다.

### Q123. ログレベルはどう使い分けますか？
(로그 레벨은 어떻게 구분해 쓰나)

**🇯🇵 回答**

ERROR は人が対応すべきこと、WARN は今は動いているが注視すべきこと、INFO は業務上の節目、DEBUG は開発時の詳細です。

一番よくないのは、対応不要なものを ERROR で出すことです。**アラートが鳴りすぎると誰も見なくなり、本当の障害を見逃します**。だから ERROR は「これが出たら起こされてもよい」という基準で選んでいます。

**🇰🇷 답변**

ERROR 는 사람이 대응해야 할 것, WARN 은 지금은 동작하지만 주시할 것, INFO 는 업무상의 분기점, DEBUG 는 개발 시의 상세입니다.

가장 나쁜 것은 대응이 필요 없는 것을 ERROR 로 내는 것입니다. **알림이 너무 울리면 아무도 보지 않게 되고, 진짜 장애를 놓칩니다.** 그래서 ERROR 는 "이게 나면 깨워도 좋다"는 기준으로 고릅니다.

### Q124. 本番で設定値を変更したいときはどうしますか？
(프로덕션에서 설정값을 바꾸고 싶을 때)

**🇯🇵 回答**

再起動できるなら環境変数を変えて入れ替えるのが単純で確実です。ログレベルだけなら Actuator の `loggers` エンドポイントで実行時に変えられます。

より本格的には Spring Cloud Config や外部の設定ストアを使い、`@RefreshScope` で反映します。ただし**動的に変わる設定は、変わった瞬間の挙動をテストしにくい**ので、必要な範囲に留めるようにしています。

**🇰🇷 답변**

재시작할 수 있으면 환경변수를 바꿔 교체하는 것이 단순하고 확실합니다. 로그 레벨만이면 Actuator 의 `loggers` 엔드포인트로 실행 중에 바꿀 수 있습니다.

더 본격적으로는 Spring Cloud Config 나 외부 설정 저장소를 쓰고 `@RefreshScope` 로 반영합니다. 다만 **동적으로 바뀌는 설정은 바뀌는 순간의 동작을 테스트하기 어려우므로** 필요한 범위로 제한합니다.

### Q125. `@SpringBootTest` はいつ使いますか？
(@SpringBootTest 는 언제 쓰나)

**🇯🇵 回答**

コンテキスト全体を起動するので、配線が正しいことや、複数層をまたぐ振る舞いを確認したいときに使います。

ただし遅いので、全部これで書くとテスト時間が現実的でなくなります。**単体で足りるものは単体で、統合が必要なところだけ統合で**、という切り分けが基本です。コンテキストはキャッシュされるので、設定を無闇に変えると再作成が増えて遅くなります。

**🇰🇷 답변**

컨텍스트 전체를 띄우므로, 배선이 올바른지나 여러 계층을 넘나드는 동작을 확인하고 싶을 때 씁니다.

다만 느리므로 전부 이걸로 쓰면 테스트 시간이 현실적이지 않게 됩니다. **단위로 충분한 것은 단위로, 통합이 필요한 곳만 통합으로** 나누는 것이 기본입니다. 컨텍스트는 캐시되므로 설정을 함부로 바꾸면 재생성이 늘어 느려집니다.

### Q126. スライステストにはどんなものがありますか？
(슬라이스 테스트의 종류)

**🇯🇵 回答**

`@WebMvcTest` はコントローラ層だけ、`@DataJpaTest` はJPA関連だけ、`@JsonTest` はシリアライズだけを読み込みます。

必要なBeanしか作らないので圧倒的に速いです。`@WebMvcTest` ならサービス層は `@MockBean` で差し替えます。**テストしたい層を明確にする効果もある**ので、単に速いだけでなく設計上も良い習慣だと考えています。

**🇰🇷 답변**

`@WebMvcTest` 는 컨트롤러 계층만, `@DataJpaTest` 는 JPA 관련만, `@JsonTest` 는 직렬화만 읽어들입니다.

필요한 빈만 만들므로 압도적으로 빠릅니다. `@WebMvcTest` 면 서비스 계층은 `@MockBean` 으로 바꿔 끼웁니다. **테스트하려는 계층을 명확히 하는 효과도 있으므로** 단지 빠른 것뿐 아니라 설계상으로도 좋은 습관이라고 생각합니다.

### Q127. インメモリDBでテストすることの問題は？
(인메모리 DB 로 테스트하는 것의 문제)

**🇯🇵 回答**

本番と方言が違うので、**通るはずのないSQLが通り、通るべきSQLが落ちます**。データ型、関数、ロック挙動、分離レベルの実装が全て異なります。

特にトランザクションの挙動やデッドロックはインメモリでは再現しません。Testcontainers で本番と同じDBを立てられる今は、そちらを使うべきだと考えています。起動は遅くなりますが、**テストが緑なのに本番で壊れる**よりはるかに安いコストです。

**🇰🇷 답변**

프로덕션과 방언이 달라서 **통과할 리 없는 SQL 이 통과하고, 통과해야 할 SQL 이 실패합니다.** 데이터 타입, 함수, 락 동작, 격리 수준 구현이 전부 다릅니다.

특히 트랜잭션 동작이나 데드락은 인메모리에서 재현되지 않습니다. Testcontainers 로 프로덕션과 같은 DB 를 띄울 수 있는 지금은 그쪽을 써야 한다고 생각합니다. 기동은 느려지지만, **테스트는 녹색인데 프로덕션에서 깨지는** 것보다 훨씬 싼 비용입니다.

### Q128. MockMvc と `@SpringBootTest(webEnvironment=RANDOM_PORT)` の違いは？
(MockMvc 와 RANDOM_PORT 의 차이)

**🇯🇵 回答**

MockMvc はサーバーを起動せず、DispatcherServlet の内部を直接呼びます。速いですが、実際のHTTP通信は経由しません。

`RANDOM_PORT` は実際にサーバーを立てて `TestRestTemplate` などで叩きます。フィルタやシリアライズを含めた**本物の経路**を確認できますが遅いです。基本はMockMvcで、通信そのものが検証対象のときだけ後者を使います。

**🇰🇷 답변**

MockMvc 는 서버를 띄우지 않고 DispatcherServlet 내부를 직접 호출합니다. 빠르지만 실제 HTTP 통신은 거치지 않습니다.

`RANDOM_PORT` 는 실제로 서버를 띄워 `TestRestTemplate` 등으로 호출합니다. 필터와 직렬화를 포함한 **진짜 경로**를 확인할 수 있지만 느립니다. 기본은 MockMvc 로 하고, 통신 자체가 검증 대상일 때만 후자를 씁니다.

### Q129. 外部APIに依存するテストはどう書きますか？
(외부 API 에 의존하는 테스트는 어떻게 쓰나)

**🇯🇵 回答**

WireMock のようなスタブサーバーを立てて、HTTPレベルで検証します。単純なモックだと、シリアライズやタイムアウトの挙動まで検証できないからです。

重要なのは、**モックが実物とずれる**リスクです。相手のAPIが変わってもテストは緑のままです。だから契約テストを入れるか、少なくとも仕様変更の通知を受け取れる状態にしておく必要があります。

**🇰🇷 답변**

WireMock 같은 스텁 서버를 띄워 HTTP 레벨에서 검증합니다. 단순한 목이면 직렬화나 타임아웃 동작까지는 검증할 수 없기 때문입니다.

중요한 것은 **목이 실물과 어긋나는** 리스크입니다. 상대 API 가 바뀌어도 테스트는 녹색인 채입니다. 그래서 계약 테스트를 넣거나, 최소한 사양 변경 통지를 받을 수 있는 상태로 해 둬야 합니다.

### Q130. `@MockBean` を使うときの注意点は？
(@MockBean 을 쓸 때의 주의점)

**🇯🇵 回答**

コンテキストのキャッシュが効かなくなることです。`@MockBean` の組み合わせごとに別のコンテキストが作られるので、多用するとテスト全体が遅くなります。

もう一つは、モックしすぎると**自分が書いた期待どおりに動くことを確認するだけ**になる点です。境界にだけ使い、内部のロジックは実物で検証するようにしています。

**🇰🇷 답변**

컨텍스트 캐시가 안 듣게 된다는 것입니다. `@MockBean` 조합마다 다른 컨텍스트가 만들어지므로, 많이 쓰면 테스트 전체가 느려집니다.

또 하나는 목을 너무 많이 쓰면 **자기가 쓴 기대대로 동작하는 것을 확인할 뿐**이 된다는 점입니다. 경계에만 쓰고 내부 로직은 실물로 검증하도록 합니다.

### Q131. テストデータはどう管理しますか？
(테스트 데이터는 어떻게 관리하나)

**🇯🇵 回答**

テストごとに必要なデータをそのテスト内で作るのが基本です。共通のフィクスチャに全部入れると、どのデータに依存しているかが読めなくなり、変更したときに無関係なテストが落ちます。

また**テスト間で状態を共有しない**ようにします。実行順序に依存するテストは、単独では通るのに全体では落ちる、という最も厄介な形になります。

**🇰🇷 답변**

테스트마다 필요한 데이터를 그 테스트 안에서 만드는 것이 기본입니다. 공통 픽스처에 전부 넣으면 어느 데이터에 의존하는지 읽을 수 없게 되고, 바꿨을 때 무관한 테스트가 깨집니다.

또 **테스트 간에 상태를 공유하지 않도록** 합니다. 실행 순서에 의존하는 테스트는 단독으로는 통과하는데 전체에서는 실패하는, 가장 까다로운 형태가 됩니다.

---

### Q132. Spring Security の認証と認可の流れを説明してください。
(Spring Security 의 인증과 인가 흐름)

**🇯🇵 回答**

フィルタチェーンで処理されます。認証フィルタが資格情報を取り出し、`AuthenticationManager` が検証し、成功すれば `Authentication` を `SecurityContext` に格納します。

その後、認可フィルタが必要な権限を持っているかを判定します。**認証と認可は別の段階**なので、401 と 403 を正しく使い分けられます。`SecurityContext` は `ThreadLocal` に入るので、別スレッドには引き継がれません。

**🇰🇷 답변**

필터 체인에서 처리됩니다. 인증 필터가 자격 정보를 꺼내고, `AuthenticationManager` 가 검증하고, 성공하면 `Authentication` 을 `SecurityContext` 에 저장합니다.

그 후 인가 필터가 필요한 권한을 갖고 있는지 판정합니다. **인증과 인가는 다른 단계**이므로 401 과 403 을 올바르게 구분해 쓸 수 있습니다. `SecurityContext` 는 `ThreadLocal` 에 들어가므로 다른 스레드로는 인계되지 않습니다.

### Q133. セッション認証とトークン認証はどう使い分けますか？
(세션 인증과 토큰 인증의 사용 구분)

**🇯🇵 回答**

サーバー側で状態を持てるならセッション、スケールアウトやモバイルを含むならトークンです。

ただしセッションでもRedisに外出しすれば水平スケールできます。トークンは**サーバー側で即座に無効化できない**という弱点があるので、ログアウトや権限剥奪を即時に反映したい要件があるならセッションの方が素直です。要件で選ぶべきで、新しいから良いというものではありません。

**🇰🇷 답변**

서버 쪽에서 상태를 가질 수 있으면 세션, 스케일 아웃이나 모바일을 포함하면 토큰입니다.

다만 세션도 Redis 로 빼면 수평 확장이 됩니다. 토큰은 **서버 쪽에서 즉시 무효화할 수 없다**는 약점이 있으므로, 로그아웃이나 권한 회수를 즉시 반영해야 하는 요건이라면 세션이 맞습니다. 요건으로 골라야 하고, 새롭다고 좋은 것은 아닙니다.

### Q134. JWTを使うときに注意することは？
(JWT 를 쓸 때 주의할 점)

**🇯🇵 回答**

三つあります。有効期限を短くすること、機密情報を入れないこと、そして署名アルゴリズムを固定することです。ペイロードはBase64なので誰でも読めます。

無効化できない問題には、アクセストークンを短命にしてリフレッシュトークンで更新する構成で対処します。リフレッシュトークンは**サーバー側で管理して、使ったら回転させます**。再利用が検出されたら盗まれたとみなして全部無効化します。

**🇰🇷 답변**

세 가지입니다. 유효 기간을 짧게 할 것, 기밀 정보를 넣지 않을 것, 그리고 서명 알고리즘을 고정할 것입니다. 페이로드는 Base64 라 누구나 읽을 수 있습니다.

무효화할 수 없는 문제는 액세스 토큰을 단명으로 하고 리프레시 토큰으로 갱신하는 구성으로 대처합니다. 리프레시 토큰은 **서버 쪽에서 관리하고 쓰면 회전시킵니다.** 재사용이 감지되면 탈취된 것으로 보고 전부 무효화합니다.

### Q135. パスワードはどう保存しますか？
(비밀번호는 어떻게 저장하나)

**🇯🇵 回答**

ソルト付きの、計算コストが高いハッシュを使います。bcrypt、scrypt、Argon2 のいずれかです。`BCryptPasswordEncoder` ならソルトは自動で含まれるので、同じパスワードでもハッシュは毎回変わります。

SHA-256 のような高速なハッシュは使いません。**速いことが攻撃者にとって有利**だからです。work factor はハードウェアの性能に合わせて定期的に見直します。

**🇰🇷 답변**

솔트가 붙은, 계산 비용이 큰 해시를 씁니다. bcrypt, scrypt, Argon2 중 하나입니다. `BCryptPasswordEncoder` 면 솔트가 자동으로 포함되므로 같은 비밀번호라도 해시는 매번 달라집니다.

SHA-256 같은 빠른 해시는 쓰지 않습니다. **빠른 것이 공격자에게 유리하기** 때문입니다. work factor 는 하드웨어 성능에 맞춰 정기적으로 재검토합니다.

### Q136. CSRF はどんな攻撃で、どう防ぎますか？
(CSRF 는 어떤 공격이고 어떻게 막나)

**🇯🇵 回答**

利用者のブラウザに保存された認証情報を使って、意図しないリクエストを送らせる攻撃です。ブラウザがクッキーを自動で付けることを悪用します。

防御はトークンです。サーバーが発行した値をリクエストに含めさせ、一致しなければ拒否します。攻撃者はその値を知り得ません。加えてクッキーに `SameSite` を設定します。**トークンを使わない認証、つまり Authorization ヘッダーだけなら CSRF は成立しない**ので、その場合は無効化してよいです。

**🇰🇷 답변**

이용자의 브라우저에 저장된 인증 정보를 이용해 의도하지 않은 요청을 보내게 하는 공격입니다. 브라우저가 쿠키를 자동으로 붙이는 것을 악용합니다.

방어는 토큰입니다. 서버가 발행한 값을 요청에 포함시키고, 일치하지 않으면 거부합니다. 공격자는 그 값을 알 수 없습니다. 여기에 쿠키에 `SameSite` 를 설정합니다. **쿠키를 쓰지 않는 인증, 즉 Authorization 헤더만 쓰면 CSRF 가 성립하지 않으므로** 그 경우는 꺼도 됩니다.

### Q137. XSS はどう防ぎますか？
(XSS 는 어떻게 막나)

**🇯🇵 回答**

出力時のエスケープが基本です。テンプレートエンジンの自動エスケープを有効にしておけば、タグは文字として表示され実行されません。

危険なのは、意図的にエスケープを外す機能です。Thymeleaf の `th:utext` のような箇所が攻撃の通り道になります。加えて多層防御として、Content-Security-Policy と、クッキーに `HttpOnly` を設定します。**入力時の除去だけに頼らない**のが要点です。

**🇰🇷 답변**

출력 시 이스케이프가 기본입니다. 템플릿 엔진의 자동 이스케이프를 켜 두면 태그는 문자로 표시되고 실행되지 않습니다.

위험한 것은 의도적으로 이스케이프를 끄는 기능입니다. Thymeleaf 의 `th:utext` 같은 곳이 공격의 통로가 됩니다. 여기에 다층 방어로 Content-Security-Policy 와 쿠키의 `HttpOnly` 를 설정합니다. **입력 시 제거에만 의존하지 않는 것**이 요점입니다.

### Q138. 認可のロジックはどこに書きますか？
(인가 로직은 어디에 쓰나)

**🇯🇵 回答**

URLレベルの粗い制御はセキュリティ設定に、リソース単位の細かい判定はサービス層に書きます。`@PreAuthorize` を使えばメソッド単位で宣言できます。

重要なのは、**「自分のデータかどうか」の判定を忘れない**ことです。ログイン済みであることだけを確認して、他人のIDを指定すれば他人のデータが見える、という脆弱性は非常に多いです。

**🇰🇷 답변**

URL 레벨의 거친 제어는 보안 설정에, 리소스 단위의 세밀한 판정은 서비스 계층에 씁니다. `@PreAuthorize` 를 쓰면 메서드 단위로 선언할 수 있습니다.

중요한 것은 **"자기 데이터인가"의 판정을 잊지 않는 것**입니다. 로그인했다는 것만 확인하고, 남의 ID 를 지정하면 남의 데이터가 보이는 취약점은 매우 흔합니다.

### Q139. 機密情報はどう管理しますか？
(기밀 정보는 어떻게 관리하나)

**🇯🇵 回答**

リポジトリに入れないことが大前提です。環境変数か、Vault や Parameter Store のような秘密管理サービスから注入します。

加えて、**誤ってコミットされたときに検知する仕組み**を入れます。CIでシークレットスキャンを回し、履歴に入ってしまった場合は削除だけでなく必ずローテーションします。一度公開された値は、消しても漏れたものとして扱います。

**🇰🇷 답변**

리포지토리에 넣지 않는 것이 대전제입니다. 환경변수나 Vault·Parameter Store 같은 비밀 관리 서비스에서 주입합니다.

여기에 **실수로 커밋됐을 때 감지하는 장치**를 넣습니다. CI 에서 시크릿 스캔을 돌리고, 이력에 들어간 경우는 삭제뿐 아니라 반드시 회전시킵니다. 한 번 공개된 값은 지워도 유출된 것으로 취급합니다.

### Q140. 依存ライブラリの脆弱性にどう対応しますか？
(의존 라이브러리 취약점에 어떻게 대응하나)

**🇯🇵 回答**

CIに依存スキャンを組み込み、定期的に実行します。Dependabot のような自動更新も入れて、小さな更新を継続的に取り込む形にします。

重要なのは、**溜めないこと**です。一年放置してからまとめて上げると、破壊的変更が重なって移行できなくなります。日常的に小さく上げていれば、緊急のセキュリティ更新も慌てずに適用できます。

**🇰🇷 답변**

CI 에 의존성 스캔을 넣고 정기적으로 실행합니다. Dependabot 같은 자동 갱신도 넣어 작은 갱신을 지속적으로 받아들이는 형태로 합니다.

중요한 것은 **쌓아두지 않는 것**입니다. 1년 방치했다가 한꺼번에 올리면 파괴적 변경이 겹쳐 올릴 수 없게 됩니다. 일상적으로 조금씩 올려 두면 긴급 보안 업데이트도 당황하지 않고 적용할 수 있습니다.

### Q141. 本番で急に遅くなったとき、どう調べますか？
(프로덕션이 갑자기 느려졌을 때 어떻게 조사하나)

**🇯🇵 回答**

まず範囲を切り分けます。全体が遅いのか特定エンドポイントだけか、いつからか、直前に何かデプロイや設定変更があったか。

次にレイヤーを下ります。アプリのメトリクスでスレッドプールとコネクションプールの状態を見て、詰まっている層を特定します。GC時間が伸びていればメモリ側、DBの待ちが増えていればクエリ側です。**推測で手を入れず、計測から始める**のが原則です。

**🇰🇷 답변**

먼저 범위를 가릅니다. 전체가 느린지 특정 엔드포인트만인지, 언제부터인지, 직전에 배포나 설정 변경이 있었는지.

다음으로 계층을 내려갑니다. 앱 메트릭에서 스레드풀과 커넥션 풀 상태를 보고 막혀 있는 계층을 특정합니다. GC 시간이 늘었으면 메모리 쪽, DB 대기가 늘었으면 쿼리 쪽입니다. **추측으로 손대지 말고 측정에서 시작하는 것**이 원칙입니다.

### Q142. 一部のAPIの障害が全体に波及しないようにするには？
(일부 API 의 장애가 전체로 번지지 않게 하려면)

**🇯🇵 回答**

バルクヘッド、つまりリソースの分離です。全エンドポイントが同じスレッドプールを共有していると、一つの重い処理が全スレッドを占有し、無関係な軽い処理まで巻き込んで止まります。

重要度や特性で別々のプールを割り当てれば、影響範囲がそのプール内に閉じます。加えてサーキットブレーカーとタイムアウトを組み合わせて、**遅い依存に引きずられない**ようにします。

**🇰🇷 답변**

벌크헤드, 즉 리소스 분리입니다. 모든 엔드포인트가 같은 스레드풀을 공유하면 하나의 무거운 처리가 전 스레드를 점유해 무관한 가벼운 처리까지 말려들어 멈춥니다.

중요도나 특성으로 별도 풀을 할당하면 영향 범위가 그 풀 안에 닫힙니다. 여기에 서킷브레이커와 타임아웃을 조합해 **느린 의존에 끌려가지 않게** 합니다.

### Q143. デプロイ戦略はどう選びますか？
(배포 전략은 어떻게 고르나)

**🇯🇵 回答**

ローリングが基本です。段階的に入れ替えるのでリソース効率が良く、Kubernetesの標準です。

即座に切り戻したい、あるいはDBの互換性が心配ならブルーグリーン。新機能のリスクを小さく試したいならカナリアで、少量のトラフィックを流してエラー率とレイテンシを監視します。**どれを選んでも、DBの変更が前方互換であることが前提**になります。

**🇰🇷 답변**

롤링이 기본입니다. 단계적으로 교체하므로 리소스 효율이 좋고 Kubernetes 의 표준입니다.

즉시 되돌리고 싶거나 DB 호환성이 걱정되면 블루그린. 새 기능의 리스크를 작게 시험하고 싶으면 카나리로, 소량의 트래픽을 흘려 에러율과 지연을 모니터링합니다. **어느 것을 고르든 DB 변경이 하위 호환인 것이 전제**가 됩니다.

### Q144. 設定ミスを本番に出さないためにどうしますか？
(설정 실수를 프로덕션에 내보내지 않으려면)

**🇯🇵 回答**

起動時に落とすようにします。`@ConfigurationProperties` と `@Validated` を組み合わせれば、必須項目の欠落や不正な値を起動時点で検出できます。

さらに、環境ごとの差分をレビュー対象にします。設定はコードと同じくGitで管理し、**変更が差分として見える状態**にしておくのが重要です。手で本番だけ変えた設定は、必ずいつか誰かが上書きします。

**🇰🇷 답변**

기동 시에 실패하게 만듭니다. `@ConfigurationProperties` 와 `@Validated` 를 조합하면 필수 항목 누락이나 부정한 값을 기동 시점에 검출할 수 있습니다.

나아가 환경별 차이를 리뷰 대상으로 삼습니다. 설정은 코드와 마찬가지로 Git 으로 관리하고 **변경이 차이로 보이는 상태**로 두는 것이 중요합니다. 손으로 프로덕션만 바꾼 설정은 반드시 언젠가 누군가가 덮어씁니다.

### Q145. Spring Boot のバージョンアップはどう進めますか？
(Spring Boot 버전 업은 어떻게 진행하나)

**🇯🇵 回答**

まずリリースノートと移行ガイドで、削除された機能と非推奨を洗い出します。特に削除は動かなくなるので最優先です。Spring Boot 3 では Java 17 必須と `javax` から `jakarta` への移行が大きな山でした。

進め方は、テストが十分にあることを確認してから一段階ずつ上げます。**マイナーを飛ばさずに順に上げる**方が、問題の切り分けが圧倒的に楽です。そして必ず、負荷試験まで含めて検証してから本番に出します。

**🇰🇷 답변**

먼저 릴리스 노트와 마이그레이션 가이드로 삭제된 기능과 비권장을 뽑아냅니다. 특히 삭제는 동작하지 않게 되므로 최우선입니다. Spring Boot 3 에서는 Java 17 필수와 `javax` 에서 `jakarta` 로의 전환이 큰 고비였습니다.

진행 방식은, 테스트가 충분한지 확인한 뒤 한 단계씩 올립니다. **마이너를 건너뛰지 않고 순서대로 올리는** 편이 문제의 원인을 짚기가 압도적으로 쉽습니다. 그리고 반드시 부하 시험까지 포함해 검증한 뒤 프로덕션에 내보냅니다.
