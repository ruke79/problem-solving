### Q56. リクエストが来てからレスポンスを返すまでの流れを説明してください。
(요청이 와서 응답을 반환하기까지의 흐름)

**🇯🇵 回答**

まず `DispatcherServlet` が受け取り、`HandlerMapping` でどのコントローラが担当するかを決めます。次に `HandlerAdapter` が実際に呼び出し、その前後で `HandlerInterceptor` が動きます。

戻り値が `@ResponseBody` なら `HttpMessageConverter` がJSONに変換し、ビュー名なら `ViewResolver` がビューを解決します。例外が出た場合は `HandlerExceptionResolver` が処理します。**入口が一つに集約されている**のがこの設計の要点です。

**🇰🇷 답변**

먼저 `DispatcherServlet` 이 받고, `HandlerMapping` 으로 어느 컨트롤러가 담당할지 정합니다. 다음으로 `HandlerAdapter` 가 실제로 호출하고, 그 앞뒤에서 `HandlerInterceptor` 가 동작합니다.

반환값이 `@ResponseBody` 면 `HttpMessageConverter` 가 JSON 으로 변환하고, 뷰 이름이면 `ViewResolver` 가 뷰를 해결합니다. 예외가 나면 `HandlerExceptionResolver` 가 처리합니다. **입구가 하나로 모여 있는 것**이 이 설계의 요점입니다.

### Q57. `@Controller` と `@RestController` の違いは？
(@Controller 와 @RestController 의 차이)

**🇯🇵 回答**

`@RestController` は `@Controller` と `@ResponseBody` を合わせたものです。全メソッドの戻り値が、ビュー名ではなくレスポンスボディとして扱われます。

だからAPIサーバーなら `@RestController`、サーバーサイドレンダリングをするなら `@Controller` を使います。混在させると、文字列を返したときにビュー名として解決されて404になる、という混乱が起きます。

**🇰🇷 답변**

`@RestController` 는 `@Controller` 와 `@ResponseBody` 를 합친 것입니다. 모든 메서드의 반환값이 뷰 이름이 아니라 응답 바디로 다뤄집니다.

그래서 API 서버면 `@RestController`, 서버 사이드 렌더링을 하면 `@Controller` 를 씁니다. 섞으면 문자열을 반환했을 때 뷰 이름으로 해석되어 404 가 나는 혼란이 생깁니다.

### Q58. `@RequestParam`・`@PathVariable`・`@RequestBody` の使い分けは？
(@RequestParam·@PathVariable·@RequestBody 의 사용 구분)

**🇯🇵 回答**

`@PathVariable` はリソースの識別子、つまりURIの一部です。`@RequestParam` はクエリ文字列で、絞り込みやページングなどの条件に使います。`@RequestBody` はJSONなどの本文です。

REST の考え方に沿えば、**何を指すかはパス、どう絞るかはクエリ、何を送るかはボディ**という整理になります。GETにボディを付ける設計は避けます。

**🇰🇷 답변**

`@PathVariable` 은 리소스의 식별자, 즉 URI 의 일부입니다. `@RequestParam` 은 쿼리 문자열로 필터링이나 페이징 조건에 씁니다. `@RequestBody` 는 JSON 등의 본문입니다.

REST 사고방식에 따르면 **무엇을 가리키는가는 경로, 어떻게 좁히는가는 쿼리, 무엇을 보내는가는 바디**라는 정리가 됩니다. GET 에 바디를 붙이는 설계는 피합니다.

### Q59. `HttpMessageConverter` は何をしますか？
(HttpMessageConverter 는 무엇을 하나)

**🇯🇵 回答**

リクエストボディをJavaオブジェクトに、戻り値をレスポンスボディに変換します。どのコンバータを使うかは `Content-Type` と `Accept` ヘッダーで決まります。

JSONなら通常 Jackson が使われます。だから日付のフォーマットやスネークケースの変換といった話は、コントローラではなく `ObjectMapper` の設定側で一括して決めるのが筋です。

**🇰🇷 답변**

요청 바디를 자바 객체로, 반환값을 응답 바디로 변환합니다. 어느 컨버터를 쓸지는 `Content-Type` 과 `Accept` 헤더로 정해집니다.

JSON 이면 보통 Jackson 이 쓰입니다. 그래서 날짜 포맷이나 스네이크 케이스 변환 같은 이야기는 컨트롤러가 아니라 `ObjectMapper` 설정 쪽에서 일괄로 정하는 것이 맞습니다.

### Q60. 入力値のバリデーションはどう行いますか？
(입력값 검증은 어떻게 하나)

**🇯🇵 回答**

DTOに `@NotNull` や `@Size` などの制約を付け、コントローラの引数に `@Valid` を付けます。違反すると `MethodArgumentNotValidException` が投げられます。

重要なのは、**この例外を `@RestControllerAdvice` で捕まえて統一した形式で返す**ことです。既定のエラーレスポンスはクライアントが扱いにくいので、どのフィールドがなぜ弾かれたかを構造化して返します。

**🇰🇷 답변**

DTO 에 `@NotNull` 이나 `@Size` 같은 제약을 붙이고, 컨트롤러 인자에 `@Valid` 를 붙입니다. 위반하면 `MethodArgumentNotValidException` 이 던져집니다.

중요한 것은 **이 예외를 `@RestControllerAdvice` 에서 잡아 통일된 형식으로 반환하는 것**입니다. 기본 에러 응답은 클라이언트가 다루기 어려우므로, 어느 필드가 왜 걸렸는지를 구조화해서 반환합니다.

### Q61. `@Valid` と `@Validated` の違いは？
(@Valid 와 @Validated 의 차이)

**🇯🇵 回答**

`@Valid` は標準の Bean Validation、`@Validated` は Spring が拡張したものです。違いはグループ指定ができるかどうかと、適用できる場所です。

`@Validated` はクラスに付けるとメソッドの引数にも検証を掛けられます。登録と更新で必須項目が違う場合はグループを使いたいので `@Validated`、それ以外は `@Valid` で十分です。

**🇰🇷 답변**

`@Valid` 는 표준 Bean Validation, `@Validated` 는 Spring 이 확장한 것입니다. 차이는 그룹 지정이 가능한지와 적용할 수 있는 위치입니다.

`@Validated` 는 클래스에 붙이면 메서드 인자에도 검증을 걸 수 있습니다. 등록과 수정에서 필수 항목이 다르면 그룹을 쓰고 싶으므로 `@Validated`, 그 외에는 `@Valid` 로 충분합니다.

### Q62. 例外処理はどう設計しますか？
(예외 처리는 어떻게 설계하나)

**🇯🇵 回答**

`@RestControllerAdvice` に集約します。コントローラごとに `try-catch` を書くと、レスポンス形式がばらついてクライアントが困ります。

設計の要点は二つです。**業務例外とシステム例外を分ける**こと、そして**内部情報を外に出さない**ことです。スタックトレースやSQLをそのまま返すと攻撃の手がかりになるので、外にはエラーコードとメッセージだけ返し、詳細はログに残します。

**🇰🇷 답변**

`@RestControllerAdvice` 에 모읍니다. 컨트롤러마다 `try-catch` 를 쓰면 응답 형식이 제각각이 되어 클라이언트가 곤란해집니다.

설계의 요점은 두 가지입니다. **업무 예외와 시스템 예외를 나누는 것**, 그리고 **내부 정보를 밖으로 내보내지 않는 것**입니다. 스택 트레이스나 SQL 을 그대로 반환하면 공격의 단서가 되므로, 밖에는 에러 코드와 메시지만 반환하고 상세는 로그에 남깁니다.

### Q63. エラーレスポンスはどんな形にしますか？
(에러 응답은 어떤 형태로 하나)

**🇯🇵 回答**

HTTPステータスで大分類を示し、ボディに機械可読なエラーコードと人向けのメッセージを入れます。バリデーションエラーならフィールドごとの詳細も付けます。

標準化したいなら RFC 7807 の Problem Details が使えます。Spring Boot 3 では `ProblemDetail` として組み込まれているので、**独自形式を作る前にこちらを検討**するようにしています。

**🇰🇷 답변**

HTTP 상태로 대분류를 나타내고, 바디에 기계가 읽을 에러 코드와 사람이 읽을 메시지를 넣습니다. 검증 에러면 필드별 상세도 붙입니다.

표준화하고 싶으면 RFC 7807 의 Problem Details 를 쓸 수 있습니다. Spring Boot 3 에서는 `ProblemDetail` 로 내장되어 있으므로 **독자 형식을 만들기 전에 이쪽을 검토**하도록 합니다.

### Q64. HTTPステータスコードはどう使い分けますか？
(HTTP 상태 코드는 어떻게 구분해 쓰나)

**🇯🇵 回答**

400番台はクライアント側の問題、500番台はサーバー側の問題です。認証されていないなら401、認証済みだが権限がないなら403、リソースがなければ404、バリデーション違反なら400を使います。

避けるべきなのは、エラーを200で返してボディのフラグで示す設計です。**リトライも監視もキャッシュも全部機能しなくなります**。ステータスコードはプロトコルの一部として正しく使います。

**🇰🇷 답변**

400 번대는 클라이언트 쪽 문제, 500 번대는 서버 쪽 문제입니다. 인증되지 않았으면 401, 인증됐지만 권한이 없으면 403, 리소스가 없으면 404, 검증 위반이면 400 을 씁니다.

피해야 할 것은 에러를 200 으로 반환하고 바디의 플래그로 나타내는 설계입니다. **재시도도 모니터링도 캐시도 전부 기능하지 않게 됩니다.** 상태 코드는 프로토콜의 일부로서 올바르게 씁니다.

### Q65. 冪等性のあるHTTPメソッドはどれですか？なぜ重要ですか？
(멱등성이 있는 HTTP 메서드는 무엇이고 왜 중요한가)

**🇯🇵 回答**

GET、PUT、DELETE、HEAD が冪等です。何度実行しても結果が同じになります。POSTは冪等ではありません。

重要なのは、冪等ならクライアントやゲートウェイが**安心してリトライできる**からです。ネットワークが切れたとき、成功したかどうか分からなくても再送できます。POSTで重複が致命的なケースでは、`Idempotency-Key` ヘッダーを使って重複実行を防ぎます。

**🇰🇷 답변**

GET, PUT, DELETE, HEAD 가 멱등입니다. 몇 번 실행해도 결과가 같아집니다. POST 는 멱등이 아닙니다.

중요한 것은 멱등이면 클라이언트나 게이트웨이가 **안심하고 재시도할 수 있기** 때문입니다. 네트워크가 끊겼을 때 성공했는지 몰라도 재전송할 수 있습니다. POST 에서 중복이 치명적인 경우는 `Idempotency-Key` 헤더로 중복 실행을 막습니다.

### Q66. Filter・Interceptor・AOP はどう使い分けますか？
(필터·인터셉터·AOP 의 사용 구분)

**🇯🇵 回答**

FilterはサーブレットコンテナのレベルでDispatcherServletの外側、InterceptorはSpring MVCの内部でハンドラの前後、AOPはBeanのメソッド単位です。

だから、リクエスト全体に効かせたいエンコーディングやセキュリティはFilter、ハンドラの情報が必要な認可やロギングはInterceptor、業務メソッドに紐づく処理はAOPを使います。**どのレイヤーの情報が必要かで決まります**。

**🇰🇷 답변**

Filter 는 서블릿 컨테이너 레벨로 DispatcherServlet 바깥쪽, Interceptor 는 Spring MVC 내부에서 핸들러 앞뒤, AOP 는 빈의 메서드 단위입니다.

그래서 요청 전체에 걸고 싶은 인코딩이나 보안은 Filter, 핸들러 정보가 필요한 인가나 로깅은 Interceptor, 업무 메서드에 묶인 처리는 AOP 를 씁니다. **어느 레이어의 정보가 필요한가로 정해집니다.**

### Q67. CORS とは何で、プリフライトはいつ発生しますか？
(CORS 란 무엇이고 프리플라이트는 언제 발생하나)

**🇯🇵 回答**

ブラウザの同一オリジンポリシーを、サーバー側が明示的に緩めるための仕組みです。ヘッダーで「このオリジンからは許可する」と宣言します。

プリフライトは、単純リクエストの条件を外れたときに発生します。`PUT` や `DELETE`、`Content-Type: application/json`、カスタムヘッダーがある場合です。本番では `allowedOrigins` にワイルドカードを使わず、必要なオリジンだけを列挙します。

**🇰🇷 답변**

브라우저의 동일 출처 정책을 서버 쪽에서 명시적으로 완화하기 위한 장치입니다. 헤더로 "이 출처에서는 허용한다"고 선언합니다.

프리플라이트는 단순 요청 조건을 벗어났을 때 발생합니다. `PUT` 이나 `DELETE`, `Content-Type: application/json`, 커스텀 헤더가 있는 경우입니다. 프로덕션에서는 `allowedOrigins` 에 와일드카드를 쓰지 않고 필요한 출처만 열거합니다.

### Q68. APIのバージョニングはどうしますか？
(API 버저닝은 어떻게 하나)

**🇯🇵 回答**

URIに含める方法が一番わかりやすく、実務でもよく使われます。`/v1/orders` のような形です。ヘッダーで指定する方法はURIがきれいですが、動作確認やキャッシュの扱いが面倒になります。

より重要なのは、**そもそもバージョンを上げなくて済む変更にすること**です。フィールドの追加は後方互換なので既存クライアントを壊しません。削除や型変更だけがバージョンを分ける理由になります。

**🇰🇷 답변**

URI 에 포함하는 방법이 가장 알기 쉽고 실무에서도 자주 쓰입니다. `/v1/orders` 같은 형태입니다. 헤더로 지정하는 방법은 URI 가 깔끔하지만 동작 확인이나 캐시 처리가 번거로워집니다.

더 중요한 것은 **애초에 버전을 올리지 않아도 되는 변경으로 만드는 것**입니다. 필드 추가는 하위 호환이라 기존 클라이언트를 깨지 않습니다. 삭제나 타입 변경만이 버전을 나누는 이유가 됩니다.

### Q69. ページングはどう設計しますか？
(페이징은 어떻게 설계하나)

**🇯🇵 回答**

小規模ならオフセット方式で十分です。`Pageable` を受け取れば Spring Data が処理してくれます。

ただしオフセットは深いページで急激に遅くなります。DBが先頭から読み飛ばす必要があるからです。件数が多い、あるいは無限スクロールなら、直前の最後のキーを渡すカーソル方式にします。**総件数のカウントも重いので、必要ないなら `Slice` を使います**。

**🇰🇷 답변**

소규모면 오프셋 방식으로 충분합니다. `Pageable` 을 받으면 Spring Data 가 처리해 줍니다.

다만 오프셋은 깊은 페이지에서 급격히 느려집니다. DB 가 앞에서부터 읽어 건너뛰어야 하기 때문입니다. 건수가 많거나 무한 스크롤이면 직전 마지막 키를 넘기는 커서 방식으로 합니다. **총 건수 카운트도 무거우므로 필요 없으면 `Slice` 를 씁니다.**

### Q70. DTOとエンティティを分ける理由は？
(DTO 와 엔티티를 나누는 이유)

**🇯🇵 回答**

三つあります。エンティティをそのまま返すと内部構造が外に漏れること、遅延ロードの関連を触って予期しないクエリやエラーが出ること、そしてAPIの都合でエンティティを変えたくなることです。

特に二つ目は実務でよく起きます。JSON変換の途中で遅延ロードに触れて `LazyInitializationException` が出る、あるいは無限に関連を辿ってしまう、という形です。**境界でDTOに詰め替える**のが安全です。

**🇰🇷 답변**

세 가지입니다. 엔티티를 그대로 반환하면 내부 구조가 밖으로 새는 것, 지연 로딩 연관을 건드려 예상치 못한 쿼리나 에러가 나는 것, 그리고 API 사정으로 엔티티를 바꾸고 싶어지는 것입니다.

특히 두 번째는 실무에서 자주 일어납니다. JSON 변환 도중에 지연 로딩을 건드려 `LazyInitializationException` 이 나거나, 무한히 연관을 따라가는 형태입니다. **경계에서 DTO 로 옮겨 담는 것**이 안전합니다.

### Q71. `RestTemplate` と `WebClient` はどちらを使いますか？
(RestTemplate 과 WebClient 중 무엇을 쓰나)

**🇯🇵 回答**

新規なら `WebClient` です。`RestTemplate` はメンテナンスモードで、新機能は入りません。`WebClient` は同期でも使えるので、WebFluxを導入しなくても採用できます。

Spring Framework 6 からは `RestClient` という同期専用の選択肢も加わりました。**どれを使うにしても、タイムアウトを必ず設定する**ことが一番重要です。既定では無制限のことがあり、相手が応答しないとスレッドが返ってきません。

**🇰🇷 답변**

신규면 `WebClient` 입니다. `RestTemplate` 은 유지보수 모드로 새 기능이 들어오지 않습니다. `WebClient` 는 동기로도 쓸 수 있으므로 WebFlux 를 도입하지 않아도 채택할 수 있습니다.

Spring Framework 6 부터는 `RestClient` 라는 동기 전용 선택지도 생겼습니다. **어느 것을 쓰든 타임아웃을 반드시 설정하는 것**이 가장 중요합니다. 기본이 무제한인 경우가 있어 상대가 응답하지 않으면 스레드가 돌아오지 않습니다.

---

### Q72. 外部API呼び出しの障害にどう備えますか？
(외부 API 호출의 장애에 어떻게 대비하나)

**🇯🇵 回答**

まずタイムアウトを接続と読み取りの両方に設定します。次にリトライですが、冪等な操作にだけ、指数バックオフとジッターを入れて行います。

その上でサーキットブレーカーを入れます。相手が落ちているのにリトライを続けると、こちらのスレッドを食い潰して**自分まで倒れます**。一定の失敗率で回路を開き、フォールバックを返す設計にします。

**🇰🇷 답변**

먼저 타임아웃을 접속과 읽기 양쪽에 설정합니다. 다음으로 재시도인데, 멱등한 조작에만 지수 백오프와 지터를 넣어 합니다.

그 위에 서킷브레이커를 넣습니다. 상대가 죽었는데 재시도를 계속하면 이쪽 스레드를 다 먹어 **자기까지 쓰러집니다.** 일정 실패율에서 회로를 열고 폴백을 반환하는 설계로 합니다.

---

### Q73. リトライとサーキットブレーカーを組み合わせるときの注意点は？
(재시도와 서킷브레이커를 조합할 때의 주의점)

**🇯🇵 回答**

順序で挙動が変わります。リトライを外側に置くと、1回の呼び出しで複数の失敗がカウントされるので回路が早く開きます。サーキットブレーカーを外側に置くと、リトライ全体が1回として数えられます。

どちらが正しいかは要件次第ですが、**最小試行回数を満たせずに回路が開かない**という事態は避けたいので、設定値と順序をセットで決めるようにしています。

**🇰🇷 답변**

순서로 동작이 달라집니다. 재시도를 바깥에 두면 한 번의 호출에서 여러 실패가 집계되어 회로가 빨리 열립니다. 서킷브레이커를 바깥에 두면 재시도 전체가 1회로 세어집니다.

어느 쪽이 옳은지는 요건에 달렸지만, **최소 시행 횟수를 못 채워 회로가 안 열리는** 사태는 피하고 싶으므로 설정값과 순서를 세트로 정하도록 합니다.

### Q74. レート制限はどう実装しますか？
(레이트 리밋은 어떻게 구현하나)

**🇯🇵 回答**

複数インスタンスがある前提なら、カウンタはRedisのような中央に置きます。**インメモリだとインスタンス数の分だけ制限が緩みます**。

アルゴリズムはトークンバケットを基本にします。固定ウィンドウ方式は境界で二倍のリクエストを通してしまうからです。またRedisが落ちると全APIが止まるので、失敗時は通すのか止めるのかを先に決めておきます。

**🇰🇷 답변**

여러 인스턴스가 있는 전제라면 카운터는 Redis 같은 중앙에 둡니다. **인메모리면 인스턴스 수만큼 제한이 샙니다.**

알고리즘은 토큰 버킷을 기본으로 합니다. 고정 윈도우 방식은 경계에서 두 배의 요청을 통과시키기 때문입니다. 또 Redis 가 죽으면 모든 API 가 멈추므로, 실패 시 통과시킬지 막을지를 먼저 정해 둡니다.

---

### Q75. Spring MVC のスレッドモデルを説明してください。
(Spring MVC 의 스레드 모델)

**🇯🇵 回答**

リクエストごとにスレッドプールからスレッドを一つ割り当て、レスポンスを返すまでそのスレッドが担当します。実装が直感的でデバッグしやすい反面、**同時処理数がスレッド数で頭打ち**になります。

問題になるのはDB待ちや外部API待ちです。その間スレッドは何もせずブロックされたままなので、待ち時間が長いほど効率が落ちます。

**🇰🇷 답변**

요청마다 스레드풀에서 스레드를 하나 할당하고, 응답을 반환할 때까지 그 스레드가 담당합니다. 구현이 직관적이고 디버깅하기 쉬운 반면 **동시 처리 수가 스레드 수에서 막힙니다.**

문제가 되는 것은 DB 대기나 외부 API 대기입니다. 그동안 스레드는 아무것도 하지 않고 블록된 채이므로, 대기 시간이 길수록 효율이 떨어집니다.

---

### Q76. Tomcat のスレッドプール設定はどう決めますか？
(Tomcat 스레드풀 설정은 어떻게 정하나)

**🇯🇵 回答**

`server.tomcat.threads.max` が同時処理数の上限です。既定は200ですが、これが適切かはアプリの待ち時間次第です。

重要なのは、**下流の上限と揃える**ことです。スレッドを400にしてもDBコネクションプールが20なら、380個は待つだけです。むしろ待ち行列が伸びて応答が悪化します。負荷試験で、スレッド数を増やしてスループットが伸びなくなる点を探します。

**🇰🇷 답변**

`server.tomcat.threads.max` 가 동시 처리 수의 상한입니다. 기본은 200 인데, 이게 적절한지는 앱의 대기 시간에 달렸습니다.

중요한 것은 **뒷단의 상한과 맞추는 것**입니다. 스레드를 400 으로 해도 DB 커넥션 풀이 20 이면 380 개는 기다리기만 합니다. 오히려 대기열이 길어져 응답이 나빠집니다. 부하 시험에서 스레드 수를 늘려도 처리량이 안 느는 지점을 찾습니다.

---

### Q77. WebFlux は MVC と何が違い、いつ選びますか？
(WebFlux 는 MVC 와 무엇이 다르고 언제 고르나)

**🇯🇵 回答**

WebFluxは少数のイベントループスレッドでノンブロッキングに処理します。だから待ち時間が長い処理を大量に捌く場合に、少ないスレッドで高い同時実行数を出せます。

ただし**全経路がノンブロッキングでないと意味がありません**。途中にブロッキングのJDBCが一つでもあると、イベントループを塞いで全体が止まります。学習コストとデバッグの難しさも上がるので、既存のブロッキング資産があるなら仮想スレッドの方が現実的な選択です。

**🇰🇷 답변**

WebFlux 는 소수의 이벤트 루프 스레드로 논블로킹 처리합니다. 그래서 대기 시간이 긴 처리를 대량으로 처리할 때 적은 스레드로 높은 동시성을 냅니다.

다만 **전 경로가 논블로킹이 아니면 의미가 없습니다.** 도중에 블로킹 JDBC 가 하나라도 있으면 이벤트 루프를 막아 전체가 멈춥니다. 학습 비용과 디버깅의 어려움도 올라가므로, 기존 블로킹 자산이 있다면 가상 스레드가 현실적인 선택입니다.

---

### Q78. Spring Boot で仮想スレッドを使うとどうなりますか？
(Spring Boot 에서 가상 스레드를 쓰면 어떻게 되나)

**🇯🇵 回答**

`spring.threads.virtual.enabled=true` を入れると、リクエストごとに仮想スレッドが割り当てられます。**コードを書き換えずに**、ブロッキングのまま同時実行数を大きく伸ばせます。

注意点は二つです。CPUバウンドな処理には効果がないこと、そして `synchronized` の中でブロックするとピニングが起きることです。またスレッド数が上限として機能しなくなるので、**下流の保護は別途必要**になります。

**🇰🇷 답변**

`spring.threads.virtual.enabled=true` 를 넣으면 요청마다 가상 스레드가 할당됩니다. **코드를 바꾸지 않고** 블로킹인 채로 동시 실행 수를 크게 늘릴 수 있습니다.

주의점은 두 가지입니다. CPU 바운드 처리에는 효과가 없다는 것, 그리고 `synchronized` 안에서 블록하면 피닝이 일어난다는 것입니다. 또 스레드 수가 상한으로 기능하지 않게 되므로 **뒷단 보호는 별도로 필요**해집니다.

---

### Q79. 非同期処理はどう実装しますか？
(비동기 처리는 어떻게 구현하나)

**🇯🇵 回答**

`@Async` を付けて、`@EnableAsync` を有効にします。ただし**既定のExecutorをそのまま使わない**ようにしています。設定次第では無制限にスレッドが増えるので、専用の `ThreadPoolTaskExecutor` を定義してキュー容量と拒否ポリシーを明示します。

もう一つ、`@Async` メソッドの戻り値を `void` にすると例外が消えます。結果や失敗を知りたいなら `CompletableFuture` を返します。

**🇰🇷 답변**

`@Async` 를 붙이고 `@EnableAsync` 를 켭니다. 다만 **기본 Executor 를 그대로 쓰지 않도록** 합니다. 설정에 따라서는 스레드가 무제한으로 늘어나므로, 전용 `ThreadPoolTaskExecutor` 를 정의해 큐 용량과 거부 정책을 명시합니다.

또 하나, `@Async` 메서드의 반환값을 `void` 로 하면 예외가 사라집니다. 결과나 실패를 알고 싶으면 `CompletableFuture` 를 반환합니다.

### Q80. リクエストごとの情報をどうやって下位層まで運びますか？
(요청별 정보를 어떻게 하위 계층까지 나르나)

**🇯🇵 回答**

引数で渡すのが最も明示的ですが、ログのトレースIDのように全層で必要なものは `MDC` や `ThreadLocal` を使います。

注意点は、**非同期や別スレッドに移ると引き継がれない**ことです。`@Async` やスレッドプールに渡す場合は、明示的にコピーする仕組みが要ります。加えて、スレッドが使い回されるので処理の最後に必ずクリアします。残っていると次のリクエストに漏れます。

**🇰🇷 답변**

인자로 넘기는 것이 가장 명시적이지만, 로그의 트레이스 ID 처럼 전 계층에서 필요한 것은 `MDC` 나 `ThreadLocal` 을 씁니다.

주의점은 **비동기나 다른 스레드로 옮기면 인계되지 않는다**는 것입니다. `@Async` 나 스레드풀에 넘길 때는 명시적으로 복사하는 장치가 필요합니다. 게다가 스레드가 재사용되므로 처리 마지막에 반드시 지웁니다. 남아 있으면 다음 요청으로 샙니다.

### Q81. ファイルアップロードで注意することは？
(파일 업로드에서 주의할 점)

**🇯🇵 回答**

まずサイズ上限を設定します。`spring.servlet.multipart.max-file-size` を指定しないと、大きなファイルでメモリやディスクを圧迫されます。

次に、ファイル名をそのまま使わないことです。パス区切り文字が入っていると意図しない場所に書き込まれます。**拡張子ではなく実際の中身で種別を確認**し、保存先はWebから直接配信されない場所にします。

**🇰🇷 답변**

먼저 크기 상한을 설정합니다. `spring.servlet.multipart.max-file-size` 를 지정하지 않으면 큰 파일이 메모리와 디스크를 압박합니다.

다음으로 파일 이름을 그대로 쓰지 않는 것입니다. 경로 구분자가 들어 있으면 의도하지 않은 곳에 써집니다. **확장자가 아니라 실제 내용으로 종류를 확인**하고, 저장 위치는 웹에서 직접 배포되지 않는 곳으로 합니다.

### Q82. 大きなレスポンスを返すときはどうしますか？
(큰 응답을 반환할 때)

**🇯🇵 回答**

一度に全部メモリに載せない形にします。`StreamingResponseBody` や `ResponseEntity<Resource>` を使えば、少しずつ書き出せます。

加えて、そもそも返す量を減らせないかを考えます。ページングを入れる、必要なフィールドだけ返す、圧縮を有効にする。**リモートのクライアントほど、バイト数が応答時間を支配します**。

**🇰🇷 답변**

한 번에 전부 메모리에 올리지 않는 형태로 합니다. `StreamingResponseBody` 나 `ResponseEntity<Resource>` 를 쓰면 조금씩 써 나갈 수 있습니다.

여기에 애초에 반환량을 줄일 수 없는지 생각합니다. 페이징을 넣고, 필요한 필드만 반환하고, 압축을 켭니다. **원격 클라이언트일수록 바이트 수가 응답 시간을 지배합니다.**

### Q83. Server-Sent Events と WebSocket の使い分けは？
(SSE 와 WebSocket 의 사용 구분)

**🇯🇵 回答**

サーバーからクライアントへの一方向でよいならSSEです。HTTPの上に構築されているので、プロキシやファイアウォールを通しやすく、実装も単純です。自動再接続も標準で備わっています。

双方向のやり取りが必要ならWebSocketです。チャットのような用途ですね。LLMの応答をトークンごとに流すような場面は一方向なので、SSEで十分なことが多いです。

**🇰🇷 답변**

서버에서 클라이언트로의 단방향이면 SSE 입니다. HTTP 위에 구축되어 있어 프록시나 방화벽을 통과하기 쉽고 구현도 단순합니다. 자동 재접속도 표준으로 갖춰져 있습니다.

양방향 주고받기가 필요하면 WebSocket 입니다. 채팅 같은 용도지요. LLM 응답을 토큰 단위로 흘리는 상황은 단방향이므로 SSE 로 충분한 경우가 많습니다.

### Q84. スケールアウトしたときにWebSocketで困ることは？
(스케일 아웃했을 때 WebSocket 에서 곤란한 점)

**🇯🇵 回答**

接続が特定のインスタンスに固定されるので、**別のインスタンスに繋がっている相手にメッセージを届けられません**。

対策はバックプレーンです。Redis の Pub/Sub などを挟んで、どのインスタンスが受け取っても全体に配信されるようにします。ただし Pub/Sub はメッセージを永続化しないので、取りこぼしが許されない場合は本体をDBに保存し、Pub/Subは通知だけに使います。

**🇰🇷 답변**

접속이 특정 인스턴스에 고정되므로 **다른 인스턴스에 붙어 있는 상대에게 메시지를 전달할 수 없습니다.**

대책은 백플레인입니다. Redis 의 Pub/Sub 등을 끼워 어느 인스턴스가 받아도 전체에 전파되도록 합니다. 다만 Pub/Sub 은 메시지를 영속화하지 않으므로, 유실이 허용되지 않으면 본체는 DB 에 저장하고 Pub/Sub 은 통지에만 씁니다.

---

### Q85. ステートレスであることがなぜ重要ですか？
(스테이트리스가 왜 중요한가)

**🇯🇵 回答**

どのインスタンスが受けても同じ結果になるので、水平スケールが自由にできるからです。インスタンスを増やしても減らしても、ユーザーへの影響がありません。

逆に、インメモリのセッションやカウンタを持つと**インスタンスごとに状態がずれます**。レート制限が緩む、ログイン状態が飛ぶ、といった形で表面化します。状態は Redis やDBのような共有ストアに出すのが原則です。

**🇰🇷 답변**

어느 인스턴스가 받아도 같은 결과가 되므로 수평 확장이 자유롭기 때문입니다. 인스턴스를 늘리든 줄이든 사용자에게 영향이 없습니다.

반대로 인메모리 세션이나 카운터를 가지면 **인스턴스마다 상태가 어긋납니다.** 레이트 리밋이 새거나 로그인 상태가 날아가는 형태로 드러납니다. 상태는 Redis 나 DB 같은 공유 저장소로 빼는 것이 원칙입니다.
