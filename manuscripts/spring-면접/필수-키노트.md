# Spring Boot 면접 — 필수 문항 지정과 키노트

> **시간이 부족할 때 이 파일만 보면 된다.** 145문항을 세 등급으로 나누고,
> S급에는 **일본어 한 문장**을 붙였다. 그 문장만 외워도 답이 성립한다.
>
> 등급 기준은 **출제 빈도 × 변별력**이다. Spring 면접은 Java 보다 **함정 질문의 비중이 크다** —
> 프록시를 안 거치면 안 걸린다는 계열이 특히 그렇다.
>
> **`▶레슨 3-2` 표기는 `spring-tutorial/` 의 실행 레슨 번호다** (인프라 없이 돈다 —
> `./gradlew :spring-tutorial:test`). §5 의 `SPRING-*` 케이스는 실물 DB 검증,
> `▶레슨` 은 그중 컨테이너·프록시·경계만 떼어 바로 돌려 보는 판이다.

## 1. S급 — 반드시 나온다 (18문항)

### ① DI · 빈

**Q3. 의존성 주입 세 방식 중 무엇을 쓰나** ★가장 자주 ▶레슨 1-1
> コンストラクタ注入です。理由は三つで、フィールドを `final` にできること、必須の依存がシグネチャに現れること、テストで `new` するだけで組み立てられることです。

**Q7. 싱글턴 빈에 프로토타입 빈을 주입하면** ★함정 ▶레슨 2-3·2-4
> 期待どおりには動きません。注入は singleton の生成時に一度だけなので、**以後ずっと同じインスタンスが使われます**。毎回必要なら `ObjectProvider` を使います。

**Q4. 순환 참조는 왜 일어나고 어떻게 고치나** ▶레슨 1-2
> A が B を、B が A を必要とする状態です。Spring Boot 2.6 から既定で禁止されました。回避設定は対症療法で、**本質的には責務の分割が間違っている**ので、共通部分を第三のクラスに切り出します。

**Q14. 자동 구성은 어떻게 동작하나** ★가장 자주
> `@EnableAutoConfiguration` が設定クラスの一覧を読み込み、各クラスに付いた `@ConditionalOnClass` や `@ConditionalOnMissingBean` で**条件に合うものだけが有効になります**。だからクラスパスに依存を足すだけで設定が入るように見えます。

### ② AOP · 트랜잭션 (이 랩이 실행으로 확인한 영역)

**Q35. 같은 클래스 안에서 부르면 `@Transactional` 이 안 걸리는 이유** ★가장 자주 ▶레슨 3-2·4-6
> 自己呼び出しがプロキシを通らないからです。プロキシが挟まるのは外部から呼ばれたときだけで、内部の `this.method()` は素のオブジェクトの呼び出しになります。対処は呼び出し側を別のBeanに分けることです。

**Q42. `@Transactional` 은 어떤 예외에서 롤백하나** ★함정 ▶레슨 4-2·4-3
> 既定では `RuntimeException` と `Error` だけです。**チェック例外ではロールバックせず、そのままコミットされます**。戻したいなら `rollbackFor` を明示するか、最初からランタイム例外に包みます。

**Q34. JDK 동적 프록시와 CGLIB 의 차이** ▶레슨 3-4·3-5
> JDK動的プロキシはインターフェースが必須、CGLIBは対象クラスを継承します。Spring Boot は既定でCGLIBなので、**`final` クラスやメソッドにはプロキシを掛けられません**。

**Q38. `REQUIRED` 와 `REQUIRES_NEW` 의 차이** ▶레슨 4-5
> `REQUIRED` は既存に参加するので、内側でロールバックすると外側も巻き込まれます。`REQUIRES_NEW` は別のコネクションで新しく始めるので、外側がロールバックしても内側のデータは残ります。

**Q47. `@Transactional` 이 안 걸리는 경우 다섯** ▶레슨 3-3·3-5·4-6
> 自己呼び出し、`private` メソッド、`final`、Beanでないクラス、別スレッドです。共通しているのは**プロキシを経由しない**という点です。

**Q45. 트랜잭션 안에서 외부 API 를 호출해도 되나** ★실무 ▶레슨 4-8
> 避けるべきです。相手が遅いとその間ずっとDBコネクションを握り続け、プールが枯渇してアプリ全体が止まります。DBのコミット後にイベントで呼び出す形にします。

---

### ③ Web · MVC

**Q56. 요청부터 응답까지의 흐름** ★가장 자주
> `DispatcherServlet` が受け取り、`HandlerMapping` で担当を決め、`HandlerAdapter` が呼び出し、その前後で `Interceptor` が動きます。戻り値は `HttpMessageConverter` か `ViewResolver` が処理し、例外は `HandlerExceptionResolver` が扱います。

**Q66. 필터 · 인터셉터 · AOP 의 구분** ★가장 자주 ▶레슨 5-7
> Filterはサーブレットコンテナのレベル、InterceptorはSpring MVCの内部、AOPはBeanのメソッド単位です。**どのレイヤーの情報が必要かで決まります**。

**Q64. HTTP 상태 코드를 올바르게 쓰는 이유** ▶레슨 5-5·5-6
> エラーを200で返してボディのフラグで示すと、**リトライも監視もキャッシュも全部機能しなくなります**。ステータスコードはプロトコルの一部として正しく使います。

**Q76. Tomcat 스레드풀 크기** ★실무
> 重要なのは**下流の上限と揃える**ことです。スレッドを400にしてもDBコネクションプールが20なら、380個は待つだけで、むしろ待ち行列が伸びて応答が悪化します。

---

### ④ 데이터 접근

**Q89. N+1 문제란** ★가장 자주
> 一覧のクエリが1回、各要素の関連を取るクエリがN回発行される状態です。遅延ロードでループ中に関連へアクセスした瞬間に個別クエリが走ります。**本番のデータ量で初めて顕在化する**のが厄介です。

**Q92. fetch join 과 페이징을 함께 쓰면** ★변별력 최고
> コレクションの fetch join にページングを掛けると、**Hibernateは limit 句を付けずに全件を取得し、メモリ上でページングします**。警告は出ますが例外にならないので、データが増えたときにOOMになります。

**Q94. OSIV 를 끄는 이유** ★실무
> 有効だと**ビューのレンダリングが終わるまでDBコネクションを保持し続ける**からです。トラフィックが増えるとプールが枯渇します。無効にすると `LazyInitializationException` が出ますが、それは問題が可視化されただけです。

**Q108. 커넥션 풀 고갈의 원인 판별** ★변별력 최고
> スロークエリなら**必ず返却されるので使用時間の分布に現れ**、p99が伸びます。リークなら**そもそも返却されず分布に現れない**のに active だけ増え続けます。`leakDetectionThreshold` を設定すれば借りた時点のスタックトレースが出ます。

## 4. 면접 30분 전 최종 점검 — 이것만은

**"프록시를 안 거치면 안 걸린다"** 하나로 묶이는 것이 Spring 함정의 절반입니다.

| 안 걸리는 경우 | 왜 |
|---|---|
| 자기 호출 `this.method()` | 프록시를 안 거침 (Q35 ▶3-2·4-6) |
| `private` 메서드 | CGLIB 이 오버라이드 못 함 (Q36) |
| `final` 클래스·메서드 | 상속 불가 (Q34 ▶3-5) |
| 빈이 아닌 클래스 | 프록시가 안 만들어짐 (Q47 ▶3-1) |
| 다른 스레드 | `ThreadLocal` 이 안 넘어감 (Q37·Q48 ▶7-6) |

**여섯 개의 "아니오"**

| 질문의 유혹 | 정답 |
|---|---|
| 체크 예외도 롤백되나? | **아니오** — 기본은 런타임만 (Q42 ▶4-2) |
| 트랜잭션 안에서 외부 API 불러도 되나? | **아니오** — 커넥션 점유 (Q45 ▶4-8) |
| fetch join 에 페이징 붙여도 되나? | **아니오** — `limit` 없이 전건 로드 (Q92) |
| OSIV 켜 두면 편하지 않나? | **아니오** — 렌더링 끝까지 커넥션 보유 (Q94) |
| `connectionTimeout` 을 늘리면 안전한가? | **아니오** — 스레드가 더 오래 막힘 (Q107) |
| liveness 에 DB 체크를 넣어도 되나? | **아니오** — 전 Pod 재시작 유발 (Q117) |

## 5. 이 세트의 강점을 활용하세요

**S급·A급의 상당수는 이 저장소가 실제로 실행해 확인한 것입니다.**

| 문항 | 근거 케이스 |
|---|---|
| Q35 자기 호출 | `SPRING-01` |
| Q34 프록시 종류 | `SPRING-02` |
| Q38 `REQUIRES_NEW` | `SPRING-03` |
| Q42 롤백 규칙 | `SPRING-04` |
| Q7 싱글턴+프로토타입 | `SPRING-05` |
| Q89 N+1 | `JPA-01` |
| Q92 fetch join + 페이징 | `JPA-06` |
| Q94 OSIV | `JPA-03` |
| Q106~Q108 커넥션 풀 | `DB-02`·`DB-06` |
| Q136·Q137 CSRF·XSS | `SEC-01`·`SEC-02` |

**여기에 `spring-tutorial/` 52건이 더해졌다.** 본문의 `▶레슨 n-m` 이 그 번호다 —
인프라 없이 돌므로 면접 전날에도 확인할 수 있고, 대응표 전체는
`spring-tutorial/README.md` §3 에 있다. 특히 §4 첫 표의 "프록시를 안 거치면
안 걸린다"는 레슨 3-2(AOP) → 4-6(@Transactional) → 7-2(@Cacheable) 로
**같은 함정을 세 번 실행해 볼 수 있다.**

**"직접 재 봤습니다"라고 말할 수 있는 문항이 여기 있습니다.** 다만
자동 구성 내부(Q14~16), 가상 스레드(Q78), 배포 전략(Q143) 등은 **검증하지 않았으니**
그쪽은 "일반적으로 알려진 바로는" 으로 말하는 편이 안전합니다(`README.md` 참고).
