### Q86. 永続性コンテキストとは何ですか？
(영속성 컨텍스트란)

**🇯🇵 回答**

エンティティを管理する一次キャッシュです。トランザクションの間、同じIDのエンティティは同一インスタンスとして扱われます。

これがあることで、同じデータを二度読んでもSQLは一度で済み、変更を追跡して自動でUPDATEを出せます。逆に言えば、**トランザクションが終わると管理から外れる**ので、その後の遅延ロードは失敗します。

**🇰🇷 답변**

엔티티를 관리하는 1차 캐시입니다. 트랜잭션 동안 같은 ID 의 엔티티는 동일 인스턴스로 다뤄집니다.

이게 있어서 같은 데이터를 두 번 읽어도 SQL 은 한 번으로 끝나고, 변경을 추적해 자동으로 UPDATE 를 낼 수 있습니다. 뒤집어 말하면 **트랜잭션이 끝나면 관리에서 벗어나므로** 그 뒤의 지연 로딩은 실패합니다.

### Q87. ダーティチェックはどう動きますか？
(더티 체킹은 어떻게 동작하나)

**🇯🇵 回答**

エンティティを読み込んだ時点のスナップショットを持っておき、フラッシュのタイミングで現在の値と比較して、差があればUPDATE文を生成します。

だから `save()` を呼ばなくても更新されます。これは便利ですが、**意図しない変更も反映される**ということでもあります。読み取り目的のメソッドには `readOnly = true` を付けて、スナップショット自体を持たないようにします。

**🇰🇷 답변**

엔티티를 읽어들인 시점의 스냅샷을 갖고 있다가, 플러시 시점에 현재 값과 비교해 차이가 있으면 UPDATE 문을 생성합니다.

그래서 `save()` 를 부르지 않아도 갱신됩니다. 편리하지만 **의도하지 않은 변경도 반영된다**는 뜻이기도 합니다. 읽기 목적 메서드에는 `readOnly = true` 를 붙여 스냅샷 자체를 갖지 않게 합니다.

### Q88. フラッシュはいつ起きますか？
(플러시는 언제 일어나나)

**🇯🇵 回答**

トランザクションのコミット時、JPQLなどのクエリ実行の直前、そして明示的に `flush()` を呼んだときです。

二つ目が重要で、**まだDBに書かれていない変更があると、クエリの結果が正しくなくなる**ためJPAが先に書き出します。だから「保存していないのにSELECTの結果に反映されている」という挙動が起きます。ここを知らないと、SQLログの順序が理解できません。

**🇰🇷 답변**

트랜잭션 커밋 시, JPQL 같은 쿼리 실행 직전, 그리고 명시적으로 `flush()` 를 불렀을 때입니다.

두 번째가 중요한데, **아직 DB 에 쓰이지 않은 변경이 있으면 쿼리 결과가 부정확해지므로** JPA 가 먼저 써 냅니다. 그래서 "저장하지 않았는데 SELECT 결과에 반영되어 있는" 동작이 일어납니다. 여기를 모르면 SQL 로그의 순서를 이해할 수 없습니다.

### Q89. N+1問題とは何ですか？
(N+1 문제란)

**🇯🇵 回答**

一覧を取るクエリが1回、その各要素の関連を取るクエリがN回発行される状態です。100件取ると101回SQLが飛びます。

原因は遅延ロードで、ループの中で関連にアクセスした瞬間に個別クエリが走ります。件数が少ない開発環境では気づかず、**本番のデータ量で初めて顕在化する**のが厄介なところです。

**🇰🇷 답변**

목록을 가져오는 쿼리 1회, 그 각 요소의 연관을 가져오는 쿼리가 N 회 발행되는 상태입니다. 100건을 가져오면 101회 SQL 이 날아갑니다.

원인은 지연 로딩으로, 루프 안에서 연관에 접근하는 순간 개별 쿼리가 돕니다. 건수가 적은 개발 환경에서는 눈치채지 못하고 **프로덕션 데이터 양에서 처음 드러나는** 것이 까다로운 점입니다.

### Q90. N+1をどう解決しますか？
(N+1 을 어떻게 해결하나)

**🇯🇵 回答**

基本は fetch join です。JPQLで `join fetch` を書けば1回のSQLでまとめて取れます。

件数が多い、あるいは複数の関連を同時に取りたい場合は `@BatchSize` かグローバルの `default_batch_fetch_size` を使います。これはN回をIN句でまとめるので、101回が2回程度になります。**必ずSQLログを見て、実際に減ったことを確認します**。

**🇰🇷 답변**

기본은 fetch join 입니다. JPQL 에서 `join fetch` 를 쓰면 1회 SQL 로 한꺼번에 가져옵니다.

건수가 많거나 여러 연관을 동시에 가져오고 싶으면 `@BatchSize` 나 전역 `default_batch_fetch_size` 를 씁니다. 이건 N 회를 IN 절로 묶으므로 101회가 2회 정도가 됩니다. **반드시 SQL 로그를 보고 실제로 줄었는지 확인합니다.**

### Q91. `@ManyToOne` の fetch を EAGER にするのはなぜ危険ですか？
(@ManyToOne 의 fetch 를 EAGER 로 하면 왜 위험한가)

**🇯🇵 回答**

必要のない場面でも常にJOINや追加クエリが走るからです。さらに、EAGERの関連が連鎖すると、一件取るだけで大量のテーブルを引くことになります。

しかもJPQLで取得する場合、EAGERは**まず本体を取ってから関連を個別に取る**という形になり、かえってN+1を生みます。だから原則は全てLAZYにして、必要な場所で fetch join する方針にしています。

**🇰🇷 답변**

필요 없는 상황에서도 항상 JOIN 이나 추가 쿼리가 돌기 때문입니다. 게다가 EAGER 연관이 연쇄되면 한 건을 가져오는 데 대량의 테이블을 끌어옵니다.

게다가 JPQL 로 조회하는 경우, EAGER 는 **먼저 본체를 가져온 뒤 연관을 개별로 가져오는** 형태가 되어 오히려 N+1 을 만듭니다. 그래서 원칙은 전부 LAZY 로 하고, 필요한 곳에서 fetch join 하는 방침으로 합니다.

### Q92. fetch join とページングを一緒に使うとどうなりますか？
(fetch join 과 페이징을 함께 쓰면 어떻게 되나)

**🇯🇵 回答**

コレクションの fetch join にページングを掛けると、**Hibernate は limit 句を付けずに全件を取得し、メモリ上でページングします**。

警告ログ(HHH90003004)は出ますが例外にはならないので、動いてしまい、データが増えたときにOOMになります。対処は、ページングは本体だけに掛けて、関連は `@BatchSize` で取る形にすることです。ToOne 側の fetch join なら行数が増えないので併用できます。

**🇰🇷 답변**

컬렉션 fetch join 에 페이징을 걸면 **Hibernate 는 limit 절을 붙이지 않고 전체를 가져와 메모리에서 페이징합니다.**

경고 로그(HHH90003004)는 나오지만 예외는 아니라서 동작해 버리고, 데이터가 늘었을 때 OOM 이 납니다. 대처는 페이징은 본체에만 걸고 연관은 `@BatchSize` 로 가져오는 형태로 하는 것입니다. ToOne 쪽 fetch join 은 행 수가 늘지 않으므로 병용할 수 있습니다.

### Q93. `LazyInitializationException` はなぜ起きますか？
(LazyInitializationException 은 왜 나나)

**🇯🇵 回答**

永続性コンテキストが閉じた後に遅延ロードの関連へアクセスしたからです。トランザクションが終わるとプロキシを初期化できません。

対処は三つあります。トランザクションの中で必要な関連を先に取っておく、DTOに詰め替えて返す、あるいは `open-in-view` を有効にする。ただし三つ目は次の質問の理由で推奨しません。

**🇰🇷 답변**

영속성 컨텍스트가 닫힌 뒤에 지연 로딩 연관에 접근했기 때문입니다. 트랜잭션이 끝나면 프록시를 초기화할 수 없습니다.

대처는 세 가지입니다. 트랜잭션 안에서 필요한 연관을 미리 가져오거나, DTO 로 옮겨 담아 반환하거나, `open-in-view` 를 켜는 것입니다. 다만 세 번째는 다음 질문의 이유로 권장하지 않습니다.

### Q94. OSIV(Open Session In View)を無効にする理由は？
(OSIV 를 끄는 이유)

**🇯🇵 回答**

有効だと、ビューのレンダリングが終わるまでDBコネクションを保持し続けるからです。レンダリングや外部呼び出しが遅いと、その間ずっとコネクションを占有します。

トラフィックが増えるとプールが枯渇し、アプリ全体が止まります。Spring Boot は起動時に警告を出します。**無効にすると `LazyInitializationException` が出るようになりますが、それは問題が可視化されただけ**で、境界を正しく設計する契機になります。

**🇰🇷 답변**

켜져 있으면 뷰 렌더링이 끝날 때까지 DB 커넥션을 계속 쥐고 있기 때문입니다. 렌더링이나 외부 호출이 느리면 그동안 계속 커넥션을 점유합니다.

트래픽이 늘면 풀이 고갈되어 앱 전체가 멈춥니다. Spring Boot 는 기동 시 경고를 냅니다. **끄면 `LazyInitializationException` 이 나게 되지만, 그건 문제가 드러난 것일 뿐**이고 경계를 제대로 설계하는 계기가 됩니다.

### Q95. Spring Data JPA のメソッド名クエリはどこまで使いますか？
(Spring Data JPA 의 메서드명 쿼리는 어디까지 쓰나)

**🇯🇵 回答**

条件が二つか三つまでです。それ以上になるとメソッド名が異常に長くなり、読めなくなります。

複雑になったら `@Query` でJPQLを書くか、QueryDSLのような型安全なビルダーを使います。**メソッド名は仕様書ではない**ので、長さが読みやすさを損なう時点で切り替えます。

**🇰🇷 답변**

조건이 두세 개까지입니다. 그 이상이 되면 메서드 이름이 비정상적으로 길어져 읽을 수 없게 됩니다.

복잡해지면 `@Query` 로 JPQL 을 쓰거나 QueryDSL 같은 타입 안전한 빌더를 씁니다. **메서드 이름은 명세서가 아니므로**, 길이가 가독성을 해치는 시점에 바꿉니다.

### Q96. `save()` は常にINSERTを発行しますか？
(save() 는 항상 INSERT 를 발행하나)

**🇯🇵 回答**

いいえ。内部で新規かどうかを判定し、既存なら `merge` になります。判定は既定でIDが `null` かどうかです。

だからIDを自分で採番するエンティティでは、**新規なのに `merge` 扱いになって余計なSELECTが走ります**。件数が多いと無視できません。その場合は `Persistable` を実装して判定を上書きするか、`EntityManager.persist` を直接使います。

**🇰🇷 답변**

아니요. 내부에서 신규인지 판정하고, 기존이면 `merge` 가 됩니다. 판정은 기본적으로 ID 가 `null` 인지 여부입니다.

그래서 ID 를 직접 채번하는 엔티티에서는 **신규인데 `merge` 로 취급되어 불필요한 SELECT 가 돕니다.** 건수가 많으면 무시할 수 없습니다. 그 경우는 `Persistable` 을 구현해 판정을 덮어쓰거나 `EntityManager.persist` 를 직접 씁니다.

### Q97. 大量データの挿入はどうしますか？
(대량 데이터 삽입은 어떻게 하나)

**🇯🇵 回答**

JDBCのバッチを有効にします。`hibernate.jdbc.batch_size` を設定し、一定件数ごとに `flush` と `clear` を入れます。`clear` しないと永続性コンテキストが膨らんでOOMになります。

ただしIDが `IDENTITY` 戦略だとバッチが効きません。**INSERTしないとIDが決まらないので、まとめられない**からです。大量投入があるならシーケンスかテーブル採番を選びます。

**🇰🇷 답변**

JDBC 배치를 켭니다. `hibernate.jdbc.batch_size` 를 설정하고 일정 건수마다 `flush` 와 `clear` 를 넣습니다. `clear` 하지 않으면 영속성 컨텍스트가 부풀어 OOM 이 납니다.

다만 ID 가 `IDENTITY` 전략이면 배치가 안 먹습니다. **INSERT 하지 않으면 ID 가 정해지지 않아 묶을 수 없기** 때문입니다. 대량 투입이 있다면 시퀀스나 테이블 채번을 고릅니다.

### Q98. 一括更新・削除で気をつけることは？
(벌크 연산에서 주의할 점)

**🇯🇵 回答**

`@Modifying` を付けたJPQLの一括更新は、**永続性コンテキストを通さずに直接DBを更新します**。だからコンテキストに残っている古いエンティティと食い違います。

対策は `clearAutomatically = true` を指定して、実行後にコンテキストをクリアすることです。またダーティチェックも `@PreUpdate` も走らないので、監査項目が更新されない点にも注意します。

**🇰🇷 답변**

`@Modifying` 을 붙인 JPQL 벌크 갱신은 **영속성 컨텍스트를 거치지 않고 DB 를 직접 갱신합니다.** 그래서 컨텍스트에 남아 있는 낡은 엔티티와 어긋납니다.

대책은 `clearAutomatically = true` 를 지정해 실행 후 컨텍스트를 비우는 것입니다. 또 더티 체킹도 `@PreUpdate` 도 돌지 않으므로 감사 항목이 갱신되지 않는 점도 주의합니다.

### Q99. 楽観ロックと悲観ロックはどう使い分けますか？
(낙관 락과 비관 락의 사용 구분)

**🇯🇵 回答**

競合の頻度で決めます。滅多にぶつからないなら楽観ロック、`@Version` を付けて、更新時にバージョンが変わっていれば例外にします。ロックを取らないので同時実行性が高いです。

在庫の減算のように必ず競合する箇所は悲観ロックです。`PESSIMISTIC_WRITE` で行ロックを取ります。ただし待ちが発生するので、**タイムアウトを必ず設定**します。

**🇰🇷 답변**

경합 빈도로 정합니다. 좀처럼 부딪히지 않으면 낙관 락으로, `@Version` 을 붙여 갱신 시 버전이 바뀌었으면 예외로 만듭니다. 락을 잡지 않으므로 동시성이 높습니다.

재고 차감처럼 반드시 경합하는 곳은 비관 락입니다. `PESSIMISTIC_WRITE` 로 행 락을 잡습니다. 다만 대기가 발생하므로 **타임아웃을 반드시 설정**합니다.

### Q100. 楽観ロックで例外が出たらどうしますか？
(낙관 락에서 예외가 나면 어떻게 하나)

**🇯🇵 回答**

業務によって分かれます。単純な再取得と再試行で済むなら、リトライを掛けます。ただし無限には試さず、回数上限を決めます。

ユーザーの入力が絡む場合は、勝手にやり直すと**別の人の変更を上書きする**ことになります。その場合は「他の人が更新しました」と伝えて、利用者に判断させるのが正しい設計だと考えています。

**🇰🇷 답변**

업무에 따라 갈립니다. 단순 재조회와 재시도로 끝나면 재시도를 겁니다. 다만 무한히 시도하지 않고 횟수 상한을 정합니다.

사용자 입력이 얽힌 경우는 마음대로 다시 하면 **다른 사람의 변경을 덮어쓰게** 됩니다. 그 경우는 "다른 사람이 갱신했습니다"라고 알리고 이용자에게 판단하게 하는 것이 옳은 설계라고 생각합니다.

### Q101. デッドロックが起きたときどう対応しますか？
(데드락이 났을 때 어떻게 대응하나)

**🇯🇵 回答**

まず本当にデッドロックかを切り分けます。SQLState が `40P01` ならデッドロック、ロック待ちのタイムアウトとは別物です。ここを混同すると対策を間違えます。

デッドロックなら、原因はほぼ**ロック取得順序の不一致**です。複数行を更新する処理でIDの昇順に揃えるだけで消えることが多いです。合わせてトランザクションを短くし、範囲を狭めます。

**🇰🇷 답변**

먼저 정말 데드락인지 가립니다. SQLState 가 `40P01` 이면 데드락이고, 락 대기 타임아웃과는 다른 것입니다. 여기를 혼동하면 대책을 틀립니다.

데드락이라면 원인은 거의 **락 획득 순서의 불일치**입니다. 여러 행을 갱신하는 처리에서 ID 오름차순으로 맞추기만 해도 사라지는 경우가 많습니다. 함께 트랜잭션을 짧게 하고 범위를 좁힙니다.

### Q102. JPAの一次キャッシュと二次キャッシュの違いは？
(JPA 의 1차 캐시와 2차 캐시의 차이)

**🇯🇵 回答**

一次キャッシュは永続性コンテキスト単位、つまりトランザクションの間だけです。二次キャッシュはアプリケーション全体で共有され、トランザクションをまたいで生きます。

二次キャッシュで重要なのは、**エンティティをIDで持つ仕組みであってクエリ結果は持たない**ことです。だから全件がキャッシュにあってもJPQLは毎回SQLを発行します。クエリ結果まで載せたいならクエリキャッシュを別に有効にする必要があります。

**🇰🇷 답변**

1차 캐시는 영속성 컨텍스트 단위, 즉 트랜잭션 동안만입니다. 2차 캐시는 애플리케이션 전체에서 공유되며 트랜잭션을 넘어 살아 있습니다.

2차 캐시에서 중요한 것은 **엔티티를 ID 로 갖는 구조이지 쿼리 결과를 갖지 않는다**는 것입니다. 그래서 모든 엔티티가 캐시에 있어도 JPQL 은 매번 SQL 을 발행합니다. 쿼리 결과까지 담으려면 쿼리 캐시를 따로 켜야 합니다.

---

### Q103. 二次キャッシュを使うときの注意点は？
(2차 캐시를 쓸 때의 주의점)

**🇯🇵 回答**

更新が多いデータには向きません。無効化のコストがかかり、整合性のリスクも増えます。参照がほとんどで、変更が稀なマスタ系に限定します。

複数インスタンスがある場合はさらに注意が要ります。インスタンスごとにキャッシュを持つと、**片方だけ古い値を返す**状態になります。分散キャッシュにするか、TTLを短くして許容するかを決めます。

**🇰🇷 답변**

갱신이 많은 데이터에는 맞지 않습니다. 무효화 비용이 들고 정합성 리스크도 늘어납니다. 조회가 대부분이고 변경이 드문 마스터 계열에 한정합니다.

여러 인스턴스가 있으면 더 주의가 필요합니다. 인스턴스마다 캐시를 가지면 **한쪽만 낡은 값을 반환하는** 상태가 됩니다. 분산 캐시로 하거나 TTL 을 짧게 해서 허용할지 정합니다.

### Q104. `@Cacheable` を使うときに気をつけることは？
(@Cacheable 을 쓸 때 신경 쓸 것)

**🇯🇵 回答**

キーの設計と、TTLと上限の設定です。上限がないキャッシュは実質メモリリークで、いずれOOMになります。

もう一つは自己呼び出しです。`@Transactional` と同じくプロキシ方式なので、**同じクラス内から呼ぶとキャッシュが効きません**。また `sync = true` を付けてもインスタンスごとなので、N台なら最大N回オリジンを呼びます。

**🇰🇷 답변**

키 설계와 TTL·상한 설정입니다. 상한이 없는 캐시는 사실상 메모리 누수이고 언젠가 OOM 이 납니다.

또 하나는 자기 호출입니다. `@Transactional` 과 마찬가지로 프록시 방식이라 **같은 클래스 안에서 부르면 캐시가 안 걸립니다.** 또 `sync = true` 를 붙여도 인스턴스마다이므로, N 대면 최대 N 회 원본을 호출합니다.

### Q105. キャッシュスタンピードとは何で、どう防ぎますか？
(캐시 스탬피드란 무엇이고 어떻게 막나)

**🇯🇵 回答**

人気のキーのTTLが切れた瞬間、そこへの大量のアクセスが一斉にキャッシュミスとなり、まとめてDBに押し寄せる現象です。一瞬でDBが落ちることがあります。

対策は三つです。分散ロックで最初の一つだけがDBを引く、論理TTLで期限前に非同期で更新する、あるいはTTLにジッターを入れて失効時刻を散らす。**重要度に応じて使い分ける**のが現実的です。

**🇰🇷 답변**

인기 있는 키의 TTL 이 끊긴 순간, 그쪽으로의 대량 접근이 일제히 캐시 미스가 되어 한꺼번에 DB 로 몰리는 현상입니다. 순간적으로 DB 가 죽을 수 있습니다.

대책은 세 가지입니다. 분산 락으로 처음 하나만 DB 를 조회하거나, 논리 TTL 로 만료 전에 비동기 갱신하거나, TTL 에 지터를 넣어 만료 시각을 흩뜨리는 것입니다. **중요도에 따라 구분해 쓰는 것**이 현실적입니다.

### Q106. HikariCP のプールサイズはどう決めますか？
(HikariCP 의 풀 크기는 어떻게 정하나)

**🇯🇵 回答**

大きくすればよいものではありません。DBは接続ごとにリソースを使うので、増やしすぎるとDB側が先に苦しくなります。

決め方は、まずDBの `max_connections` とインスタンス数から逆算して上限を出し、その範囲で負荷試験をします。**1インスタンスあたりのプールサイズ × 最大インスタンス数がDBの上限を超えない**ようにするのが必須条件です。

**🇰🇷 답변**

크게 하면 좋은 것이 아닙니다. DB 는 접속마다 리소스를 쓰므로, 너무 늘리면 DB 쪽이 먼저 힘들어집니다.

정하는 방법은, 먼저 DB 의 `max_connections` 와 인스턴스 수에서 역산해 상한을 내고 그 범위에서 부하 시험을 합니다. **1인스턴스당 풀 크기 × 최대 인스턴스 수가 DB 상한을 넘지 않게** 하는 것이 필수 조건입니다.

### Q107. `connectionTimeout` を長くするのは適切ですか？
(connectionTimeout 을 길게 하는 것이 적절한가)

**🇯🇵 回答**

適切ではありません。これは「プールからコネクションを取得できるまで待つ時間」なので、長くすると**枯渇時にリクエストスレッドが長時間ブロックされます**。

その間にきたリクエストがスレッドを食い潰し、DBの一時的な遅延がアプリ全体の停止に発展します。むしろ短くして速く失敗させ、リトライやサーキットブレーカーで制御できる状態にする方が安全です。

**🇰🇷 답변**

적절하지 않습니다. 이건 "풀에서 커넥션을 얻을 때까지 기다리는 시간"이므로, 길게 하면 **고갈 시 요청 스레드가 장시간 블록됩니다.**

그동안 들어온 요청이 스레드를 다 먹어, DB 의 일시적 지연이 앱 전체의 정지로 발전합니다. 오히려 짧게 해서 빨리 실패시키고, 재시도나 서킷브레이커로 제어할 수 있는 상태로 만드는 편이 안전합니다.

### Q108. コネクションプールが枯渇したとき、原因をどう切り分けますか？
(커넥션 풀이 고갈됐을 때 원인을 어떻게 가리나)

**🇯🇵 回答**

リークかスロークエリかを、使用時間のメトリクスで機械的に分けます。

スロークエリなら、コネクションは必ず返却されるので使用時間の分布に現れ、p99が伸びます。リークなら**そもそも返却されないので分布に現れず**、active だけが階段状に増え続けます。後者なら `leakDetectionThreshold` を設定すると、借りた時点のスタックトレースが警告ログに出るので原因箇所を直接特定できます。

**🇰🇷 답변**

누수인지 슬로우 쿼리인지를 사용 시간 메트릭으로 기계적으로 나눕니다.

슬로우 쿼리면 커넥션은 반드시 반납되므로 사용 시간 분포에 나타나고 p99 가 늘어납니다. 누수면 **애초에 반납되지 않아 분포에 나타나지 않고**, active 만 계단식으로 계속 늘어납니다. 후자면 `leakDetectionThreshold` 를 설정하면 빌린 시점의 스택 트레이스가 경고 로그에 나오므로 원인 지점을 직접 특정할 수 있습니다.

### Q109. `maxLifetime` は何のために設定しますか？
(maxLifetime 은 무엇을 위해 설정하나)

**🇯🇵 回答**

DB側やネットワーク機器が先にコネクションを切ってしまう問題を防ぐためです。プールが「まだ生きている」と思って掴み続けると、次にそれを借りたリクエストが原因の分かりにくい通信エラーで落ちます。

だから `maxLifetime` はDBの `wait_timeout` より短く設定します。**アプリ側から先に、能動的に捨てる**という発想が重要です。しかもこのエラーは特定のリクエストだけ再現性なく起きるので、調査コストが非常に高くなります。

**🇰🇷 답변**

DB 쪽이나 네트워크 장비가 먼저 커넥션을 끊어 버리는 문제를 막기 위해서입니다. 풀이 "아직 살아 있다"고 여겨 계속 쥐고 있으면, 다음에 그걸 빌린 요청이 원인을 알기 어려운 통신 에러로 죽습니다.

그래서 `maxLifetime` 은 DB 의 `wait_timeout` 보다 짧게 설정합니다. **앱 쪽에서 먼저 능동적으로 버린다**는 발상이 중요합니다. 게다가 이 에러는 특정 요청만 재현성 없이 발생하므로 조사 비용이 매우 큽니다.

### Q110. JPAとMyBatisはどう使い分けますか？
(JPA 와 MyBatis 의 사용 구분)

**🇯🇵 回答**

ドメインが中心で、エンティティの状態変化を扱う業務ならJPAが向きます。ボイラープレートが減り、変更追跡も自動です。

一方、複雑な集計や統計のようにSQLそのものが主役なら、MyBatisやJdbcTemplateの方が素直です。JPAで無理に書くと読めなくなります。**同じプロジェクトで併用しても問題ない**ので、用途で選ぶのが現実的だと考えています。

**🇰🇷 답변**

도메인이 중심이고 엔티티의 상태 변화를 다루는 업무면 JPA 가 맞습니다. 보일러플레이트가 줄고 변경 추적도 자동입니다.

반면 복잡한 집계나 통계처럼 SQL 자체가 주역이면 MyBatis 나 JdbcTemplate 쪽이 자연스럽습니다. JPA 로 무리하게 쓰면 읽을 수 없게 됩니다. **같은 프로젝트에서 병용해도 문제없으므로** 용도로 고르는 것이 현실적이라고 생각합니다.

### Q111. QueryDSL を使う利点は？
(QueryDSL 을 쓰는 이점)

**🇯🇵 回答**

型安全であることと、動的クエリが書きやすいことです。文字列のJPQLだとタイプミスが実行時まで分かりませんが、QueryDSLはコンパイルで落ちます。

特に検索条件がユーザー入力で変わる画面では、`BooleanBuilder` や `BooleanExpression` で条件を組み立てられるのが大きいです。文字列連結で `where` を組む実装は、必ずどこかで壊れます。

**🇰🇷 답변**

타입 안전하다는 것과 동적 쿼리를 쓰기 쉽다는 것입니다. 문자열 JPQL 은 오타가 실행 시점까지 드러나지 않지만, QueryDSL 은 컴파일에서 걸립니다.

특히 검색 조건이 사용자 입력으로 바뀌는 화면에서는 `BooleanBuilder` 나 `BooleanExpression` 으로 조건을 조립할 수 있는 것이 큽니다. 문자열 연결로 `where` 를 짜는 구현은 반드시 어딘가에서 깨집니다.

### Q112. SQLインジェクションはどう防ぎますか？
(SQL 인젝션은 어떻게 막나)

**🇯🇵 回答**

パラメータをバインドすることです。プレースホルダを使えば値は必ずデータとして扱われ、SQL構文として解釈されません。

ただしバインドできない箇所があります。`ORDER BY` の列名やテーブル名は動的にバインドできないので、そこは**ホワイトリストで許可した値以外を弾きます**。多層防御としては、アプリが使うDBユーザーの権限を必要最小限にしておくことも重要です。

**🇰🇷 답변**

파라미터를 바인딩하는 것입니다. 플레이스홀더를 쓰면 값은 반드시 데이터로 다뤄지고 SQL 구문으로 해석되지 않습니다.

다만 바인딩할 수 없는 곳이 있습니다. `ORDER BY` 의 컬럼명이나 테이블명은 동적으로 바인딩할 수 없으므로, 거기는 **화이트리스트로 허용한 값 외에는 걸러냅니다.** 다층 방어로는 앱이 쓰는 DB 사용자 권한을 필요 최소한으로 해 두는 것도 중요합니다.

### Q113. DBスキーマの変更はどう管理しますか？
(DB 스키마 변경은 어떻게 관리하나)

**🇯🇵 回答**

Flyway か Liquibase でバージョン管理します。`ddl-auto` を本番で使うのは論外で、`validate` にしておいて差分があれば起動を止めるのが安全です。

マイグレーションは**前方互換になるよう分割**します。カラムを消す場合、まず使わなくする、次のリリースで実際に削除する、という二段階にすれば、ロールバックしても動きます。

**🇰🇷 답변**

Flyway 나 Liquibase 로 버전 관리합니다. `ddl-auto` 를 프로덕션에서 쓰는 것은 논외이고, `validate` 로 두어 차이가 있으면 기동을 멈추는 것이 안전합니다.

마이그레이션은 **하위 호환이 되도록 분할**합니다. 컬럼을 지울 때는 먼저 쓰지 않게 하고 다음 릴리스에서 실제로 삭제하는 2단계로 하면, 롤백해도 동작합니다.

### Q114. 無停止でカラムを削除するにはどうしますか？
(무중단으로 컬럼을 삭제하려면)

**🇯🇵 回答**

Expand and Contract で進めます。まず新しい構造を追加して両方書き込む、次にアプリを新しい方だけ読むように切り替える、最後に古いカラムを削除します。

各段階で**新旧どちらのバージョンのアプリも動く**状態を保つのが要点です。そうしないとローリングデプロイの途中で壊れます。削除は必ず最後、かつ全インスタンスの入れ替えが完了してから行います。

**🇰🇷 답변**

Expand and Contract 로 진행합니다. 먼저 새 구조를 추가해 양쪽에 쓰고, 다음으로 앱을 새 쪽만 읽도록 전환하고, 마지막에 옛 컬럼을 삭제합니다.

각 단계에서 **신·구 어느 버전의 앱도 동작하는** 상태를 유지하는 것이 요점입니다. 그러지 않으면 롤링 배포 도중에 깨집니다. 삭제는 반드시 마지막에, 그리고 전 인스턴스 교체가 끝난 뒤에 합니다.

### Q115. 読み取り専用レプリカをどう使いますか？
(읽기 전용 레플리카는 어떻게 쓰나)

**🇯🇵 回答**

`@Transactional(readOnly = true)` を目印にして、`AbstractRoutingDataSource` で接続先を振り分けるのが定番です。

注意点はレプリケーション遅延です。書き込んだ直後に読むと、**まだ反映されていない古い値が返る**ことがあります。自分の書き込みを自分で読む場面ではプライマリを見るようにするか、そもそもその経路はレプリカに向けない設計にします。

**🇰🇷 답변**

`@Transactional(readOnly = true)` 를 표식으로 삼아 `AbstractRoutingDataSource` 로 접속 대상을 나누는 것이 정석입니다.

주의점은 복제 지연입니다. 쓴 직후에 읽으면 **아직 반영되지 않은 낡은 값이 돌아올** 수 있습니다. 자기 쓰기를 자기가 읽는 상황에서는 프라이머리를 보게 하거나, 애초에 그 경로는 레플리카로 보내지 않는 설계로 합니다.
