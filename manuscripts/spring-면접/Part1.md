### Q1. DIコンテナは何を解決しますか？
(DI 컨테이너는 무엇을 해결하나)

**🇯🇵 回答**

オブジェクトの生成と依存関係の解決を、使う側のコードから切り離すことです。`new` を自分で書かなくなるので、実装を差し替えても呼び出し側を変えずに済みます。

効果が一番はっきり出るのはテストです。依存を外から入れられるので、DBや外部APIを本物ではなくテスト用の実装に置き換えられます。

**🇰🇷 답변**

객체의 생성과 의존 관계 해결을 쓰는 쪽 코드에서 분리하는 것입니다. `new` 를 직접 쓰지 않게 되므로 구현을 바꿔 끼워도 호출하는 쪽을 고치지 않아도 됩니다.

효과가 가장 뚜렷하게 나오는 것은 테스트입니다. 의존을 밖에서 넣을 수 있어 DB 나 외부 API 를 진짜가 아닌 테스트용 구현으로 바꿀 수 있습니다.

### Q2. IoC と DI の関係を説明してください。
(IoC 와 DI 의 관계)

**🇯🇵 回答**

IoC は「制御の反転」という広い概念で、生成や実行の主導権をフレームワーク側に渡すことです。DI はそれを実現する具体的な手段の一つです。

つまり DI は IoC の一種で、両者は同義ではありません。Template Method のように継承で制御を反転させる形も IoC に含まれます。

**🇰🇷 답변**

IoC 는 "제어의 역전"이라는 넓은 개념으로, 생성이나 실행의 주도권을 프레임워크 쪽에 넘기는 것입니다. DI 는 그것을 실현하는 구체적 수단 중 하나입니다.

즉 DI 는 IoC 의 한 종류이고, 둘은 동의어가 아닙니다. Template Method 처럼 상속으로 제어를 역전시키는 형태도 IoC 에 포함됩니다.

### Q3. 依存性注入は三つの方式のうちどれを使いますか？
(의존성 주입 세 방식 중 무엇을 쓰나)

**🇯🇵 回答**

コンストラクタ注入を使います。理由は三つです。フィールドを `final` にできるので不変になること、必須の依存がコンストラクタのシグネチャに現れること、そしてテストで `new` するだけで組み立てられることです。

フィールド注入は簡潔ですが、リフレクションがないとインスタンス化できず、依存が増えても気づきにくいという欠点があります。**依存が多すぎてコンストラクタが長くなったら、それは責務が多すぎるという信号**として受け取ります。

**🇰🇷 답변**

생성자 주입을 씁니다. 이유는 세 가지입니다. 필드를 `final` 로 만들 수 있어 불변이 된다는 것, 필수 의존이 생성자 시그니처에 드러난다는 것, 그리고 테스트에서 `new` 만으로 조립할 수 있다는 것입니다.

필드 주입은 간결하지만 리플렉션 없이는 인스턴스화할 수 없고, 의존이 늘어도 알아채기 어렵다는 단점이 있습니다. **의존이 너무 많아 생성자가 길어지면, 그건 책임이 너무 많다는 신호**로 받아들입니다.

### Q4. 循環参照はなぜ起きて、どう直しますか？
(순환 참조는 왜 일어나고 어떻게 고치나)

**🇯🇵 回答**

A が B を、B が A を必要とする状態です。コンストラクタ注入だとどちらも先に作れないので、起動時にエラーになります。

Spring Boot 2.6 からはデフォルトで禁止されました。回避設定を入れることもできますが、それは対症療法です。**本質的には責務の分割が間違っている**ので、共通部分を第三のクラスに切り出すか、イベントで疎結合にするのが正しい直し方だと考えています。

**🇰🇷 답변**

A 가 B 를, B 가 A 를 필요로 하는 상태입니다. 생성자 주입이면 어느 쪽도 먼저 만들 수 없어 기동 시 에러가 납니다.

Spring Boot 2.6 부터는 기본으로 금지됐습니다. 우회 설정을 넣을 수도 있지만 그건 대증요법입니다. **본질적으로는 책임 분할이 잘못된 것**이므로, 공통 부분을 제3의 클래스로 떼어내거나 이벤트로 느슨하게 만드는 것이 올바른 수정이라고 봅니다.

### Q5. 同じ型のBeanが複数あるとき、どう指定しますか？
(같은 타입의 빈이 여러 개일 때 어떻게 지정하나)

**🇯🇵 回答**

`@Qualifier` で名前を指定するか、`@Primary` で既定を決めます。使い分けは、ほとんどの場合に使う実装があるなら `@Primary`、呼び出し側ごとに選びたいなら `@Qualifier` です。

もう一つ、`List<Strategy>` の形で受け取ると**同じ型のBeanが全部注入されます**。ストラテジーパターンを組むときはこれが便利で、実装を足すだけで拡張できます。

**🇰🇷 답변**

`@Qualifier` 로 이름을 지정하거나 `@Primary` 로 기본을 정합니다. 구분은, 대부분의 경우에 쓰는 구현이 있으면 `@Primary`, 호출하는 쪽마다 고르고 싶으면 `@Qualifier` 입니다.

또 하나, `List<Strategy>` 형태로 받으면 **같은 타입의 빈이 전부 주입됩니다.** 전략 패턴을 짤 때 이게 편리해서, 구현을 추가하기만 하면 확장됩니다.

### Q6. Beanのスコープにはどんなものがありますか？
(빈 스코프의 종류)

**🇯🇵 回答**

既定は singleton で、コンテナごとに一つです。prototype は取得のたびに新しく作られます。Web環境では request、session、application も使えます。

実務ではほぼ singleton です。だからこそ**Beanに状態を持たせないことが前提**になります。インスタンス変数にリクエストごとの値を入れると、別のリクエストと混ざります。

**🇰🇷 답변**

기본은 singleton 으로 컨테이너마다 하나입니다. prototype 은 가져올 때마다 새로 만들어집니다. 웹 환경에서는 request, session, application 도 쓸 수 있습니다.

실무에서는 거의 singleton 입니다. 그래서 **빈에 상태를 두지 않는 것이 전제**가 됩니다. 인스턴스 변수에 요청마다 다른 값을 넣으면 다른 요청과 섞입니다.

### Q7. singletonのBeanにprototypeのBeanを注入するとどうなりますか？
(싱글턴 빈에 프로토타입 빈을 주입하면 어떻게 되나)

**🇯🇵 回答**

期待どおりには動きません。注入は singleton の生成時に一度だけ起きるので、**以後ずっと同じインスタンスが使われます**。毎回新しくはなりません。

毎回必要なら `ObjectProvider` を注入して `getObject()` を呼ぶか、`@Lookup` を使います。この挙動は勘違いされやすいので、実際に確認しておくと説明しやすいです。

**🇰🇷 답변**

기대대로 동작하지 않습니다. 주입은 싱글턴 생성 시 한 번만 일어나므로 **이후 계속 같은 인스턴스가 쓰입니다.** 매번 새로 만들어지지 않습니다.

매번 필요하면 `ObjectProvider` 를 주입해 `getObject()` 를 부르거나 `@Lookup` 을 씁니다. 이 동작은 오해하기 쉬우므로 실제로 확인해 두면 설명하기 쉽습니다.

### Q8. Beanのライフサイクルを説明してください。
(빈 생명주기)

**🇯🇵 回答**

インスタンス生成、依存性の注入、`Aware` 系のコールバック、`BeanPostProcessor` の前処理、`@PostConstruct` と初期化メソッド、後処理、そして利用、最後に破棄時の `@PreDestroy` という流れです。

実務で使うのは `@PostConstruct` と `@PreDestroy` くらいですが、AOPのプロキシが被さるのが `BeanPostProcessor` の後処理の段階だと知っていると、プロキシ関連の挙動が理解しやすくなります。

**🇰🇷 답변**

인스턴스 생성, 의존성 주입, `Aware` 계열 콜백, `BeanPostProcessor` 의 전처리, `@PostConstruct` 와 초기화 메서드, 후처리, 그리고 사용, 마지막으로 소멸 시 `@PreDestroy` 순서입니다.

실무에서 쓰는 것은 `@PostConstruct` 와 `@PreDestroy` 정도지만, AOP 프록시가 씌워지는 것이 `BeanPostProcessor` 의 후처리 단계라는 것을 알면 프록시 관련 동작을 이해하기 쉬워집니다.

### Q9. `@Component` と `@Bean` はどう使い分けますか？
(@Component 와 @Bean 의 사용 구분)

**🇯🇵 回答**

自分が書いたクラスなら `@Component`、外部ライブラリのクラスを登録するなら `@Bean` です。ライブラリのソースにアノテーションを足せないからです。

また `@Bean` はメソッドなので、生成のロジックを書けます。条件によってインスタンスを変えたい場合や、細かい設定が必要な場合も `@Bean` を使います。

**🇰🇷 답변**

직접 쓴 클래스면 `@Component`, 외부 라이브러리의 클래스를 등록하면 `@Bean` 입니다. 라이브러리 소스에 어노테이션을 추가할 수 없기 때문입니다.

또 `@Bean` 은 메서드라서 생성 로직을 쓸 수 있습니다. 조건에 따라 인스턴스를 바꾸고 싶거나 세부 설정이 필요한 경우도 `@Bean` 을 씁니다.

### Q10. `@Configuration` クラス内で `@Bean` メソッドを直接呼ぶとどうなりますか？
(@Configuration 안에서 @Bean 메서드를 직접 부르면 어떻게 되나)

**🇯🇵 回答**

シングルトンが保たれます。`@Configuration` クラスは CGLIB でプロキシ化されていて、メソッド呼び出しを横取りし、既にコンテナにあればそれを返すからです。

これを無効にするのが `proxyBeanMethods = false` で、その場合は普通のメソッド呼び出しになるので**毎回新しいインスタンスが作られます**。起動が少し速くなる代わりに、Bean 間の参照に注意が必要になります。

**🇰🇷 답변**

싱글턴이 유지됩니다. `@Configuration` 클래스는 CGLIB 로 프록시화되어 있어서 메서드 호출을 가로채고, 이미 컨테이너에 있으면 그것을 반환하기 때문입니다.

이걸 끄는 것이 `proxyBeanMethods = false` 이고, 그 경우는 평범한 메서드 호출이 되므로 **매번 새 인스턴스가 만들어집니다.** 기동이 조금 빨라지는 대신 빈 간 참조에 주의해야 합니다.

### Q11. コンポーネントスキャンの範囲はどう決まりますか？
(컴포넌트 스캔 범위는 어떻게 정해지나)

**🇯🇵 回答**

`@SpringBootApplication` が付いたクラスのパッケージと、その配下が対象になります。だからメインクラスはルートパッケージに置くのが原則です。

上位や別ツリーのパッケージにあるクラスは自動では登録されません。ライブラリとして切り出したモジュールを取り込むときは、`@ComponentScan` を明示するか、自動構成の仕組みに乗せる必要があります。

**🇰🇷 답변**

`@SpringBootApplication` 이 붙은 클래스의 패키지와 그 하위가 대상이 됩니다. 그래서 메인 클래스는 루트 패키지에 두는 것이 원칙입니다.

상위나 다른 트리의 패키지에 있는 클래스는 자동으로 등록되지 않습니다. 라이브러리로 떼어낸 모듈을 가져올 때는 `@ComponentScan` 을 명시하거나 자동 구성 구조에 얹어야 합니다.

### Q12. `ApplicationContext` と `BeanFactory` の違いは？
(ApplicationContext 와 BeanFactory 의 차이)

**🇯🇵 回答**

`BeanFactory` はDIの最小機能だけを持ちます。`ApplicationContext` はそれを継承し、国際化、イベント発行、リソース読み込み、AOPとの統合などを加えたものです。

もう一つ大きな違いは初期化のタイミングで、`ApplicationContext` は起動時に singleton を先に作ります。だから**設定ミスがあれば起動時点で落ちる**ので、実行中に初めて気づく事態を避けられます。

**🇰🇷 답변**

`BeanFactory` 는 DI 의 최소 기능만 갖습니다. `ApplicationContext` 는 그것을 상속하고 국제화, 이벤트 발행, 리소스 로딩, AOP 통합 등을 더한 것입니다.

또 하나 큰 차이는 초기화 시점으로, `ApplicationContext` 는 기동 시에 싱글턴을 미리 만듭니다. 그래서 **설정 실수가 있으면 기동 시점에 실패하므로**, 실행 중에 처음 알게 되는 사태를 피할 수 있습니다.

### Q13. 遅延初期化(lazy initialization)は使うべきですか？
(지연 초기화는 써야 하나)

**🇯🇵 回答**

全体に効かせるのは避けています。起動は速くなりますが、設定ミスが起動時に見つからず、最初のリクエストで初めて落ちるからです。

起動時間が本当に問題で、かつ滅多に使わない重いBeanがある場合に、そのBeanだけ `@Lazy` にします。**全体設定ではなく個別指定**にするのが原則だと考えています。

**🇰🇷 답변**

전체에 적용하는 것은 피하고 있습니다. 기동은 빨라지지만 설정 실수가 기동 시에 발견되지 않고 첫 요청에서야 실패하기 때문입니다.

기동 시간이 정말 문제이고 좀처럼 쓰지 않는 무거운 빈이 있는 경우에, 그 빈만 `@Lazy` 로 합니다. **전체 설정이 아니라 개별 지정**으로 하는 것이 원칙이라고 봅니다.

### Q14. Spring Boot の自動構成(auto-configuration)はどう動きますか？
(Spring Boot 자동 구성은 어떻게 동작하나)

**🇯🇵 回答**

`@EnableAutoConfiguration` が、依存ライブラリに含まれる設定クラスの一覧を読み込みます。今は `META-INF/spring/...AutoConfiguration.imports` というファイルです。

読み込んだ各設定クラスには `@ConditionalOnClass` や `@ConditionalOnMissingBean` が付いていて、**条件に合うものだけが有効になります**。だからクラスパスに依存を足すだけで設定が入るように見えます。

**🇰🇷 답변**

`@EnableAutoConfiguration` 이 의존 라이브러리에 포함된 설정 클래스 목록을 읽어들입니다. 지금은 `META-INF/spring/...AutoConfiguration.imports` 라는 파일입니다.

읽어들인 각 설정 클래스에는 `@ConditionalOnClass` 나 `@ConditionalOnMissingBean` 이 붙어 있어 **조건에 맞는 것만 활성화됩니다.** 그래서 클래스패스에 의존을 추가하기만 하면 설정이 들어오는 것처럼 보입니다.

### Q15. 自動構成の内容を上書きしたいときはどうしますか？
(자동 구성 내용을 덮어쓰고 싶을 때)

**🇯🇵 回答**

同じ型のBeanを自分で定義するだけです。多くの自動構成は `@ConditionalOnMissingBean` が付いているので、**自分のBeanがあればそちらが優先されます**。

それでも効かない場合は `@SpringBootApplication(exclude = ...)` で特定の自動構成を外します。何が効いているかを調べるには、`--debug` で起動して条件評価レポートを見るのが確実です。

**🇰🇷 답변**

같은 타입의 빈을 직접 정의하기만 하면 됩니다. 대부분의 자동 구성에는 `@ConditionalOnMissingBean` 이 붙어 있어 **자기 빈이 있으면 그쪽이 우선됩니다.**

그래도 안 되면 `@SpringBootApplication(exclude = ...)` 로 특정 자동 구성을 제외합니다. 무엇이 적용됐는지 조사하려면 `--debug` 로 기동해 조건 평가 리포트를 보는 것이 확실합니다.

### Q16. `@ConditionalOn...` にはどんな種類がありますか？
(@ConditionalOn... 의 종류)

**🇯🇵 回答**

`@ConditionalOnClass` はクラスパスにその型があるとき、`@ConditionalOnMissingBean` は同じ型のBeanがまだないとき、`@ConditionalOnProperty` は設定値が一致するとき、`@ConditionalOnWebApplication` はWeb環境のときです。

自作のスターターを作る際にもこれらを使います。特に `@ConditionalOnMissingBean` は、利用者が上書きできる余地を残すための定番です。

**🇰🇷 답변**

`@ConditionalOnClass` 는 클래스패스에 그 타입이 있을 때, `@ConditionalOnMissingBean` 은 같은 타입 빈이 아직 없을 때, `@ConditionalOnProperty` 는 설정값이 일치할 때, `@ConditionalOnWebApplication` 은 웹 환경일 때입니다.

직접 스타터를 만들 때도 이것들을 씁니다. 특히 `@ConditionalOnMissingBean` 은 이용자가 덮어쓸 여지를 남기기 위한 정석입니다.

### Q17. スターター(starter)とは何ですか？
(스타터란)

**🇯🇵 回答**

関連する依存関係をまとめた、依存の束です。`spring-boot-starter-web` を入れれば、Spring MVC、Tomcat、Jackson などが揃った状態になります。

バージョンの整合性は親のBOMが管理するので、個別にバージョンを書かなくて済みます。**依存の組み合わせで悩む時間を消す**のがスターターの本質だと理解しています。

**🇰🇷 답변**

관련된 의존 관계를 묶은 의존 꾸러미입니다. `spring-boot-starter-web` 을 넣으면 Spring MVC, Tomcat, Jackson 등이 갖춰진 상태가 됩니다.

버전 정합성은 부모 BOM 이 관리하므로 개별로 버전을 쓰지 않아도 됩니다. **의존 조합으로 고민하는 시간을 없애는 것**이 스타터의 본질이라고 이해하고 있습니다.

---

### Q18. 設定値の外部化はどう行いますか？
(설정값 외부화는 어떻게 하나)

**🇯🇵 回答**

`application.yml` を基本にして、環境ごとの差分はプロファイルで分けます。優先順位があり、コマンドライン引数、環境変数、プロファイル別ファイル、既定ファイルの順で上書きされます。

重要なのは、**認証情報をファイルに書かない**ことです。それらは環境変数か、Vault や Parameter Store のような秘密管理の仕組みから注入します。

**🇰🇷 답변**

`application.yml` 을 기본으로 하고 환경별 차이는 프로파일로 나눕니다. 우선순위가 있어 커맨드라인 인자, 환경변수, 프로파일별 파일, 기본 파일 순으로 덮어씁니다.

중요한 것은 **인증 정보를 파일에 쓰지 않는 것**입니다. 그것들은 환경변수나 Vault·Parameter Store 같은 비밀 관리 구조에서 주입합니다.

---

### Q19. `@Value` と `@ConfigurationProperties` の使い分けは？
(@Value 와 @ConfigurationProperties 의 사용 구분)

**🇯🇵 回答**

値が一つか二つなら `@Value`、関連する設定のまとまりなら `@ConfigurationProperties` です。

後者は型安全で、`@Validated` を付ければ起動時に検証できます。設定ミスをアプリ起動の時点で落とせるのが大きな利点です。IDE の補完も効くので、設定項目が増えるほど有利になります。

**🇰🇷 답변**

값이 한두 개면 `@Value`, 관련된 설정의 묶음이면 `@ConfigurationProperties` 입니다.

후자는 타입 안전하고 `@Validated` 를 붙이면 기동 시에 검증할 수 있습니다. 설정 실수를 앱 기동 시점에 실패시킬 수 있는 것이 큰 이점입니다. IDE 자동완성도 되므로 설정 항목이 늘수록 유리해집니다.

---

### Q20. プロファイルはどう使いますか？注意点は？
(프로파일은 어떻게 쓰나, 주의점은)

**🇯🇵 回答**

`application-dev.yml` のように環境別のファイルを用意し、`spring.profiles.active` で選びます。Bean 側も `@Profile` で切り替えられます。

注意点は、**プロファイルで分岐しすぎると本番だけ動かない構成**が生まれることです。差分は接続先やログレベル程度に留め、ロジックそのものをプロファイルで変えるのは避けるようにしています。

**🇰🇷 답변**

`application-dev.yml` 처럼 환경별 파일을 두고 `spring.profiles.active` 로 고릅니다. 빈 쪽도 `@Profile` 로 전환할 수 있습니다.

주의점은 **프로파일로 너무 많이 분기하면 프로덕션에서만 동작하지 않는 구성**이 생긴다는 것입니다. 차이는 접속 대상이나 로그 레벨 정도로 그치고, 로직 자체를 프로파일로 바꾸는 것은 피하도록 합니다.

---

### Q21. `application.yml` と `application.properties` はどちらを使いますか？
(application.yml 과 properties 중 무엇을 쓰나)

**🇯🇵 回答**

階層が深い設定が多いので yml を使うことが多いです。ただし yml はインデントに厳しく、リストの書き方でミスが起きやすいという弱点があります。

どちらでも機能は同じなので、チームで統一することの方が重要だと考えています。両方あると優先順位で混乱するので、混在は避けます。

**🇰🇷 답변**

계층이 깊은 설정이 많아 yml 을 쓰는 경우가 많습니다. 다만 yml 은 들여쓰기에 엄격하고 리스트 작성에서 실수가 나기 쉽다는 약점이 있습니다.

어느 쪽이든 기능은 같으므로 팀에서 통일하는 것이 더 중요하다고 생각합니다. 둘 다 있으면 우선순위로 혼란스러워지므로 혼재는 피합니다.

---

### Q22. `CommandLineRunner` と `ApplicationRunner` はいつ使いますか？
(CommandLineRunner 와 ApplicationRunner 는 언제 쓰나)

**🇯🇵 回答**

起動完了後に一度だけ処理を走らせたいときです。初期データの投入や、起動時のヘルスチェックなどに使います。二つの違いは引数の受け取り方だけで、`ApplicationRunner` の方が解析済みで扱いやすいです。

注意点は、ここで例外を投げるとアプリケーションが起動失敗になることです。任意の処理なら握って続行するか、そもそもここに置かない判断も必要です。

**🇰🇷 답변**

기동 완료 후에 한 번만 처리를 돌리고 싶을 때입니다. 초기 데이터 투입이나 기동 시 헬스체크 등에 씁니다. 둘의 차이는 인자를 받는 방식뿐이고, `ApplicationRunner` 쪽이 파싱되어 있어 다루기 쉽습니다.

주의점은 여기서 예외를 던지면 애플리케이션이 기동 실패가 된다는 것입니다. 선택적인 처리라면 잡고 계속하거나, 애초에 여기 두지 않는 판단도 필요합니다.

---

### Q23. `ApplicationEvent` はどんなときに使いますか？
(ApplicationEvent 는 언제 쓰나)

**🇯🇵 回答**

呼び出し元が結果を必要としない通知に使います。注文が確定したときにメール送信や統計更新を行う、といった副次的な処理です。直接呼び出すより結合が緩みます。

ただし既定では同期で、しかも同じトランザクションの中で走ります。**イベントを非同期にするとトランザクションが伝播しない**ので、その前提で設計する必要があります。トランザクションのコミット後に処理したいなら `@TransactionalEventListener` を使います。

**🇰🇷 답변**

호출하는 쪽이 결과를 필요로 하지 않는 통지에 씁니다. 주문이 확정됐을 때 메일 발송이나 통계 갱신을 하는 부수적 처리입니다. 직접 호출보다 결합이 느슨해집니다.

다만 기본은 동기이고 같은 트랜잭션 안에서 돕니다. **이벤트를 비동기로 하면 트랜잭션이 전파되지 않으므로** 그 전제로 설계해야 합니다. 트랜잭션 커밋 후에 처리하고 싶으면 `@TransactionalEventListener` 를 씁니다.

---

### Q24. Spring Boot はなぜ設定が少なくて済むのですか？
(Spring Boot 는 왜 설정이 적어도 되나)

**🇯🇵 回答**

規約による設定という考え方です。よくある構成をデフォルトとして持っておき、違う場合だけ書けばよいようにしています。

これを支えているのが自動構成と、依存を束ねるスターター、そして組み込みサーバーです。従来はXMLやJava Configで自分で書いていた部分を、**条件付きの既定値として提供する**ことで減らしています。

**🇰🇷 답변**

관례에 의한 설정이라는 사고방식입니다. 흔한 구성을 기본값으로 갖고 있고, 다른 경우에만 쓰면 되도록 합니다.

이걸 떠받치는 것이 자동 구성과 의존을 묶는 스타터, 그리고 내장 서버입니다. 종래에는 XML 이나 Java Config 로 직접 쓰던 부분을 **조건부 기본값으로 제공**해 줄인 것입니다.

---

### Q25. 組み込みサーバーの利点と注意点は？
(내장 서버의 이점과 주의점)

**🇯🇵 回答**

アプリと同じ成果物にサーバーが入るので、環境ごとにサーバーを用意して設定を合わせる手間がなくなります。JARを実行するだけで動くのでコンテナとの相性も良いです。

注意点は、サーバーのチューニングもアプリの設定として管理する必要があることです。スレッドプールの上限や接続タイムアウトはデフォルトのままだと本番負荷に合わないことが多いので、必ず見直します。

**🇰🇷 답변**

앱과 같은 산출물에 서버가 들어가므로, 환경마다 서버를 준비하고 설정을 맞추는 수고가 없어집니다. JAR 을 실행하기만 하면 되므로 컨테이너와의 상성도 좋습니다.

주의점은 서버 튜닝도 앱 설정으로 관리해야 한다는 것입니다. 스레드풀 상한이나 접속 타임아웃은 기본값 그대로면 프로덕션 부하에 맞지 않는 경우가 많으므로 반드시 재검토합니다.

---

### Q26. Fat JAR の中身はどうなっていますか？
(Fat JAR 의 내부 구조)

**🇯🇵 回答**

自分のクラスは `BOOT-INF/classes`、依存ライブラリは `BOOT-INF/lib` に**JARのまま**入っています。展開して混ぜないので、同名リソースの衝突が起きません。

起動時は Spring Boot 独自のローダーがこれを読み込みます。ただしコンテナに載せる場合は、レイヤーを分けてビルドした方がキャッシュが効きます。依存は変わりにくく、自分のコードは毎回変わるからです。

**🇰🇷 답변**

자기 클래스는 `BOOT-INF/classes`, 의존 라이브러리는 `BOOT-INF/lib` 에 **JAR 그대로** 들어 있습니다. 풀어서 섞지 않으므로 같은 이름 리소스의 충돌이 나지 않습니다.

기동 시에는 Spring Boot 고유의 로더가 이걸 읽어들입니다. 다만 컨테이너에 올릴 때는 레이어를 나눠 빌드하는 편이 캐시가 잘 듣습니다. 의존은 잘 안 바뀌고 자기 코드는 매번 바뀌기 때문입니다.

---

### Q27. Bean の登録が期待どおりか、どう確認しますか？
(빈 등록이 기대대로인지 어떻게 확인하나)

**🇯🇵 回答**

`--debug` を付けて起動すると条件評価レポートが出ます。どの自動構成が有効になり、どれがなぜ無効だったかまで理由が書かれています。

実行中なら Actuator の `beans` エンドポイントで一覧を取れます。「入れたはずのライブラリが効いていない」という状況では、まずここを見るのが一番速いです。

**🇰🇷 답변**

`--debug` 를 붙여 기동하면 조건 평가 리포트가 나옵니다. 어느 자동 구성이 활성화됐고 어느 것이 왜 비활성이었는지까지 이유가 적혀 있습니다.

실행 중이면 Actuator 의 `beans` 엔드포인트로 목록을 얻을 수 있습니다. "넣었을 텐데 라이브러리가 안 먹는다"는 상황에서는 먼저 여기를 보는 것이 가장 빠릅니다.

### Q28. Bean名が衝突するとどうなりますか？
(빈 이름이 충돌하면 어떻게 되나)

**🇯🇵 回答**

既定では起動時にエラーになります。以前は後から定義された方で上書きされる設定がありましたが、事故のもとなので Spring Boot 2.1 から既定で禁止されました。

複数のモジュールを取り込むときに起きやすいので、共通ライブラリ側のBean名はパッケージを含めた具体的な名前にして、衝突しにくくしておきます。

**🇰🇷 답변**

기본적으로는 기동 시 에러가 납니다. 예전에는 나중에 정의된 쪽으로 덮어쓰는 설정이 있었지만, 사고의 원인이라 Spring Boot 2.1 부터 기본으로 금지됐습니다.

여러 모듈을 가져올 때 일어나기 쉬우므로, 공통 라이브러리 쪽 빈 이름은 패키지를 포함한 구체적인 이름으로 해서 충돌하기 어렵게 해 둡니다.

### Q29. `@SpringBootApplication` は何を束ねていますか？
(@SpringBootApplication 은 무엇을 묶은 것인가)

**🇯🇵 回答**

`@SpringBootConfiguration`、`@EnableAutoConfiguration`、`@ComponentScan` の三つです。設定クラスであること、自動構成を有効にすること、配下をスキャンすることを一つにまとめたものです。

だからスキャン範囲を変えたい、自動構成の一部を外したい、といった場合は、この三つを個別に書くこともできます。

**🇰🇷 답변**

`@SpringBootConfiguration`, `@EnableAutoConfiguration`, `@ComponentScan` 세 가지입니다. 설정 클래스라는 것, 자동 구성을 켜는 것, 하위를 스캔하는 것을 하나로 묶은 것입니다.

그래서 스캔 범위를 바꾸고 싶거나 자동 구성의 일부를 빼고 싶으면, 이 셋을 개별로 쓸 수도 있습니다.

---

### Q30. 起動時間を短縮したい場合、何を検討しますか？
(기동 시간을 줄이고 싶으면 무엇을 검토하나)

**🇯🇵 回答**

まず計測です。`--debug` の条件評価レポートと `spring-boot-actuator` の `startup` エンドポイントで、どの段階に時間がかかっているかを特定します。推測で外すと必要な機能まで落とします。

その上で、使っていない自動構成を除外する、コンポーネントスキャンの範囲を絞る、重いBeanだけを `@Lazy` にする、といった手を打ちます。極端に短縮したいなら GraalVM のネイティブイメージという選択肢もありますが、制約が大きいので用途を選びます。

**🇰🇷 답변**

먼저 측정입니다. `--debug` 의 조건 평가 리포트와 `spring-boot-actuator` 의 `startup` 엔드포인트로 어느 단계에 시간이 걸리는지 특정합니다. 추측으로 빼면 필요한 기능까지 죽입니다.

그 위에서 쓰지 않는 자동 구성을 제외하고, 컴포넌트 스캔 범위를 좁히고, 무거운 빈만 `@Lazy` 로 하는 수를 씁니다. 극단적으로 줄이고 싶으면 GraalVM 네이티브 이미지라는 선택지도 있지만, 제약이 커서 용도를 가립니다.
