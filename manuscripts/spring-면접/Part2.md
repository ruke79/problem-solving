### Q31. AOP は何を解決しますか？
(AOP 는 무엇을 해결하나)

**🇯🇵 回答**

ログ、トランザクション、認可のように、複数の場所に同じ形で現れる関心事を一箇所にまとめることです。横断的関心事と呼ばれます。

これがないと、全メソッドの先頭と末尾に同じコードを書くことになり、本来のビジネスロジックが埋もれます。AOPはそれを外に出して、対象を宣言で指定できるようにします。

**🇰🇷 답변**

로그, 트랜잭션, 인가처럼 여러 곳에 같은 형태로 나타나는 관심사를 한 곳에 모으는 것입니다. 횡단 관심사라고 부릅니다.

이게 없으면 모든 메서드의 앞뒤에 같은 코드를 쓰게 되어 본래의 비즈니스 로직이 묻힙니다. AOP 는 그것을 밖으로 빼고 대상을 선언으로 지정할 수 있게 합니다.

### Q32. AOP の主な用語を説明してください。
(AOP 의 주요 용어)

**🇯🇵 回答**

Aspect が横断的関心事のまとまり、Advice が実際に実行される処理、Pointcut がどこに適用するかの条件、Join Point が適用できる箇所です。

Spring AOP の Join Point は**メソッド実行だけ**です。AspectJ のようにフィールドアクセスやコンストラクタは対象になりません。この制約が次の質問に繋がります。

**🇰🇷 답변**

Aspect 가 횡단 관심사의 묶음, Advice 가 실제로 실행되는 처리, Pointcut 이 어디에 적용할지의 조건, Join Point 가 적용 가능한 지점입니다.

Spring AOP 의 Join Point 는 **메서드 실행뿐**입니다. AspectJ 처럼 필드 접근이나 생성자는 대상이 되지 않습니다. 이 제약이 다음 질문으로 이어집니다.

### Q33. Spring AOP はどうやって実現されていますか？
(Spring AOP 는 어떻게 구현되어 있나)

**🇯🇵 回答**

実行時にプロキシオブジェクトを作り、それをBeanとして登録します。呼び出し側はプロキシを掴むので、間に処理を挟めます。

だからバイトコードを書き換える AspectJ とは仕組みが違います。プロキシ方式である以上、**プロキシを経由しない呼び出しには効きません**。これが Spring AOP の制約の根っこです。

**🇰🇷 답변**

실행 시점에 프록시 객체를 만들어 그것을 빈으로 등록합니다. 호출하는 쪽은 프록시를 잡으므로 사이에 처리를 끼울 수 있습니다.

그래서 바이트코드를 고쳐 쓰는 AspectJ 와는 구조가 다릅니다. 프록시 방식인 이상 **프록시를 거치지 않는 호출에는 적용되지 않습니다.** 이것이 Spring AOP 제약의 뿌리입니다.

### Q34. JDK動的プロキシとCGLIBプロキシの違いは？
(JDK 동적 프록시와 CGLIB 프록시의 차이)

**🇯🇵 回答**

JDK動的プロキシはインターフェースを実装したクラスを生成するので、**インターフェースが必須**です。CGLIBは対象クラスを継承したサブクラスを作るので、インターフェースがなくても使えます。

Spring Boot は既定でCGLIBを使います。CGLIBは継承なので、`final` クラスや `final` メソッドにはプロキシを掛けられません。うっかり `final` を付けてAOPが効かなくなることがあります。

**🇰🇷 답변**

JDK 동적 프록시는 인터페이스를 구현한 클래스를 생성하므로 **인터페이스가 필수**입니다. CGLIB 은 대상 클래스를 상속한 서브클래스를 만들므로 인터페이스가 없어도 쓸 수 있습니다.

Spring Boot 는 기본으로 CGLIB 을 씁니다. CGLIB 은 상속이라 `final` 클래스나 `final` 메서드에는 프록시를 걸 수 없습니다. 무심코 `final` 을 붙여 AOP 가 안 먹는 경우가 있습니다.

### Q35. 同じクラス内のメソッドを呼ぶと `@Transactional` が効かないのはなぜですか？
(같은 클래스 안의 메서드를 부르면 @Transactional 이 안 걸리는 이유)

**🇯🇵 回答**

自己呼び出しがプロキシを通らないからです。プロキシが挟まるのは外部から呼ばれたときだけで、内部の `this.method()` は素のオブジェクトの呼び出しになります。

対処は三つあります。呼び出し側を別のBeanに分ける、自分自身をプロキシとして注入する、あるいは AspectJ を使う。**設計として一番きれいなのは最初の方法**だと考えています。

**🇰🇷 답변**

자기 호출이 프록시를 거치지 않기 때문입니다. 프록시가 끼는 것은 외부에서 호출됐을 때뿐이고, 내부의 `this.method()` 는 원본 객체의 호출이 됩니다.

대처는 세 가지입니다. 호출하는 쪽을 다른 빈으로 나누거나, 자기 자신을 프록시로 주입하거나, AspectJ 를 쓰는 것입니다. **설계로서 가장 깔끔한 것은 첫 번째**라고 생각합니다.

### Q36. `private` メソッドに `@Transactional` を付けるとどうなりますか？
(private 메서드에 @Transactional 을 붙이면)

**🇯🇵 回答**

効きません。CGLIBは継承でプロキシを作るので、`private` メソッドはオーバーライドできず、間に処理を挟めないからです。

しかもエラーにならず**黙って無視される**のが厄介です。トランザクションがあるつもりで書いたコードが、実際にはコミット済みで動いてしまいます。`public` にするか、別Beanに切り出します。

**🇰🇷 답변**

안 걸립니다. CGLIB 은 상속으로 프록시를 만들므로 `private` 메서드는 오버라이드할 수 없어 사이에 처리를 끼울 수 없기 때문입니다.

게다가 에러가 나지 않고 **조용히 무시되는** 것이 까다롭습니다. 트랜잭션이 있는 줄 알고 쓴 코드가 실제로는 커밋된 채로 동작합니다. `public` 으로 하거나 다른 빈으로 떼어냅니다.

### Q37. `@Transactional` はどう動作しますか？
(@Transactional 은 어떻게 동작하나)

**🇯🇵 回答**

プロキシがメソッドの前後に処理を挟みます。入る前にトランザクションを開始してコネクションを確保し、正常終了ならコミット、対象の例外が出ればロールバックします。

このコネクションは `ThreadLocal` で管理されます。だから**同じスレッドの中でだけ**トランザクションが繋がります。`@Async` や別スレッドに渡すと繋がらないのはこのためです。

**🇰🇷 답변**

프록시가 메서드 앞뒤에 처리를 끼웁니다. 들어가기 전에 트랜잭션을 시작해 커넥션을 확보하고, 정상 종료면 커밋, 대상 예외가 나면 롤백합니다.

이 커넥션은 `ThreadLocal` 로 관리됩니다. 그래서 **같은 스레드 안에서만** 트랜잭션이 이어집니다. `@Async` 나 다른 스레드로 넘기면 이어지지 않는 것이 이 때문입니다.

### Q38. トランザクション伝播の `REQUIRED` と `REQUIRES_NEW` の違いは？
(전파 속성 REQUIRED 와 REQUIRES_NEW 의 차이)

**🇯🇵 回答**

`REQUIRED` は既定で、既にトランザクションがあれば参加します。だから内側でロールバックすると**外側も巻き込まれます**。

`REQUIRES_NEW` は既存のものを一時停止して新しいトランザクションを始めます。別のコネクションを使うので、内側をコミットしてから外側がロールバックしても、内側のデータは残ります。監査ログのように「本処理が失敗しても記録は残したい」場合に使います。

**🇰🇷 답변**

`REQUIRED` 는 기본값으로, 이미 트랜잭션이 있으면 참여합니다. 그래서 안쪽에서 롤백하면 **바깥쪽도 함께 말려듭니다.**

`REQUIRES_NEW` 는 기존 것을 일시 중단하고 새 트랜잭션을 시작합니다. 다른 커넥션을 쓰므로 안쪽을 커밋한 뒤 바깥쪽이 롤백해도 안쪽 데이터는 남습니다. 감사 로그처럼 "본 처리가 실패해도 기록은 남기고 싶은" 경우에 씁니다.

### Q39. `REQUIRES_NEW` を使うときの注意点は？
(REQUIRES_NEW 사용 시 주의점)

**🇯🇵 回答**

コネクションを二本使うことです。外側が保持したまま内側が新しく取るので、プールサイズが足りないと**自分で自分を待つデッドロック**になります。

もう一つは、内側と外側が同じ行を触ると互いにロック待ちになる点です。使うなら、対象データが重ならないことを確認します。

**🇰🇷 답변**

커넥션을 두 개 쓴다는 것입니다. 바깥쪽이 쥔 채로 안쪽이 새로 잡으므로, 풀 크기가 부족하면 **자기가 자기를 기다리는 데드락**이 됩니다.

또 하나는 안쪽과 바깥쪽이 같은 행을 건드리면 서로 락 대기가 된다는 점입니다. 쓴다면 대상 데이터가 겹치지 않는지 확인합니다.

### Q40. 他の伝播オプションにはどんなものがありますか？
(다른 전파 옵션의 종류)

**🇯🇵 回答**

`SUPPORTS` はあれば参加、なければ非トランザクションで実行。`MANDATORY` はなければ例外。`NOT_SUPPORTED` は一時停止して非トランザクションで実行。`NEVER` はあれば例外。`NESTED` はセーブポイントを使った入れ子です。

実務で使うのはほぼ `REQUIRED` と `REQUIRES_NEW` です。`MANDATORY` は「必ず呼び出し元にトランザクションがあること」を強制したいときに、意図の表明として有効です。

**🇰🇷 답변**

`SUPPORTS` 는 있으면 참여하고 없으면 비트랜잭션으로 실행. `MANDATORY` 는 없으면 예외. `NOT_SUPPORTED` 는 일시 중단하고 비트랜잭션으로 실행. `NEVER` 는 있으면 예외. `NESTED` 는 세이브포인트를 쓴 중첩입니다.

실무에서 쓰는 것은 거의 `REQUIRED` 와 `REQUIRES_NEW` 입니다. `MANDATORY` 는 "반드시 호출한 쪽에 트랜잭션이 있어야 한다"를 강제하고 싶을 때 의도 표명으로 유효합니다.

### Q41. トランザクション分離レベルの違いは？
(트랜잭션 격리 수준의 차이)

**🇯🇵 回答**

`READ UNCOMMITTED` はダーティリードが起きます。`READ COMMITTED` はそれを防ぎますが、同じ行を二度読むと値が変わりうる。`REPEATABLE READ` は再読み込みの一貫性を保ち、`SERIALIZABLE` は完全に直列化します。

実務では既定を使うのが基本です。PostgreSQL と Oracle は `READ COMMITTED`、MySQL は `REPEATABLE READ` が既定なので、**DBを移行すると挙動が変わりうる**ことは意識しておく必要があります。

**🇰🇷 답변**

`READ UNCOMMITTED` 는 더티 리드가 납니다. `READ COMMITTED` 는 그걸 막지만 같은 행을 두 번 읽으면 값이 바뀔 수 있습니다. `REPEATABLE READ` 는 재읽기의 일관성을 지키고, `SERIALIZABLE` 은 완전히 직렬화합니다.

실무에서는 기본값을 쓰는 것이 기본입니다. PostgreSQL 과 Oracle 은 `READ COMMITTED`, MySQL 은 `REPEATABLE READ` 가 기본이라 **DB 를 옮기면 동작이 달라질 수 있다**는 것은 염두에 둬야 합니다.

### Q42. `@Transactional` はどんな例外でロールバックしますか？
(@Transactional 은 어떤 예외에서 롤백하나)

**🇯🇵 回答**

既定では `RuntimeException` と `Error` だけです。**チェック例外ではロールバックせず、そのままコミットされます**。

これは事故になりやすい挙動です。`IOException` を投げたのにデータが残っている、という状況が起きます。チェック例外でも戻したいなら `rollbackFor` を明示します。私は最初からランタイム例外に包む方針にしています。

**🇰🇷 답변**

기본은 `RuntimeException` 과 `Error` 뿐입니다. **체크 예외에서는 롤백하지 않고 그대로 커밋됩니다.**

이건 사고가 나기 쉬운 동작입니다. `IOException` 을 던졌는데 데이터가 남아 있는 상황이 생깁니다. 체크 예외에서도 되돌리고 싶으면 `rollbackFor` 를 명시합니다. 저는 처음부터 런타임 예외로 감싸는 방침으로 합니다.

### Q43. 例外を `catch` したらロールバックはどうなりますか？
(예외를 catch 하면 롤백은 어떻게 되나)

**🇯🇵 回答**

トランザクションのメソッドの中で握りつぶすと、プロキシまで例外が届かないので**コミットされます**。

ただし内側が `REQUIRED` で参加していて、そこで例外が出た場合は事情が違います。内側が rollback-only の印を付けるので、外側が握りつぶしてコミットしようとしても `UnexpectedRollbackException` になります。「握りつぶせば大丈夫」ではないという点が要注意です。

**🇰🇷 답변**

트랜잭션 메서드 안에서 삼키면 예외가 프록시까지 도달하지 않으므로 **커밋됩니다.**

다만 안쪽이 `REQUIRED` 로 참여했고 거기서 예외가 난 경우는 사정이 다릅니다. 안쪽이 rollback-only 표시를 하므로, 바깥쪽이 삼키고 커밋하려 해도 `UnexpectedRollbackException` 이 납니다. "삼키면 괜찮다"가 아니라는 점을 조심해야 합니다.

### Q44. `readOnly = true` は何をしますか？
(readOnly = true 는 무엇을 하나)

**🇯🇵 回答**

JPAでは、フラッシュモードを `MANUAL` にしてダーティチェック用のスナップショットを持たなくなるので、メモリと処理が軽くなります。

またDBやドライバによっては読み取り専用として扱われ、レプリカへのルーティングにも使えます。**書き込みを防ぐ保証ではない**ので、安全装置として過信はしません。参照系のメソッドには基本的に付けています。

**🇰🇷 답변**

JPA 에서는 플러시 모드를 `MANUAL` 로 하고 더티 체킹용 스냅샷을 갖지 않게 되므로 메모리와 처리가 가벼워집니다.

또 DB 나 드라이버에 따라서는 읽기 전용으로 다뤄져 레플리카 라우팅에도 쓸 수 있습니다. **쓰기를 막는 보장은 아니므로** 안전장치로 과신하지는 않습니다. 조회 계열 메서드에는 기본적으로 붙이고 있습니다.

### Q45. トランザクションの中で外部API呼び出しをしてもよいですか？
(트랜잭션 안에서 외부 API 를 호출해도 되나)

**🇯🇵 回答**

避けるべきです。相手が遅いとその間ずっとDBコネクションを握り続けることになり、プールが枯渇してアプリ全体が止まります。

しかもDBのトランザクションと外部呼び出しは一緒にロールバックできません。設計としては、**DBのコミット後にイベントで呼び出す**か、Outbox パターンで確実に送る形にします。

**🇰🇷 답변**

피해야 합니다. 상대가 느리면 그동안 계속 DB 커넥션을 쥐고 있게 되어, 풀이 고갈되고 앱 전체가 멈춥니다.

게다가 DB 트랜잭션과 외부 호출은 함께 롤백할 수 없습니다. 설계로는 **DB 커밋 후에 이벤트로 호출**하거나 Outbox 패턴으로 확실히 보내는 형태로 합니다.

### Q46. トランザクションの範囲はどう決めますか？
(트랜잭션 범위는 어떻게 정하나)

**🇯🇵 回答**

原則はサービス層です。複数のリポジトリ操作を一つの業務単位としてまとめる場所だからです。コントローラに付けると、ビューのレンダリング中までトランザクションが続きます。

範囲は**必要な最小限**にします。長く保持するほどロックが長く残り、同時実行性が落ちるからです。ただし細かく切りすぎると整合性が保てないので、業務的にひとまとまりの単位に合わせます。

**🇰🇷 답변**

원칙은 서비스 계층입니다. 여러 리포지토리 조작을 하나의 업무 단위로 묶는 자리이기 때문입니다. 컨트롤러에 붙이면 뷰 렌더링 중까지 트랜잭션이 이어집니다.

범위는 **필요 최소한**으로 합니다. 오래 쥘수록 락이 오래 남아 동시성이 떨어지기 때문입니다. 다만 너무 잘게 자르면 정합성을 지킬 수 없으므로 업무적으로 한 덩어리인 단위에 맞춥니다.

---

### Q47. `@Transactional` が効かないケースを挙げてください。
(@Transactional 이 안 걸리는 경우)

**🇯🇵 回答**

代表的なのは五つです。自己呼び出し、`private` メソッド、`final` メソッドやクラス、Beanとして登録されていないクラス、そして別スレッドでの実行です。

共通しているのは**プロキシを経由しない**という点です。効いていないことに気づきにくいので、疑わしいときは `TransactionSynchronizationManager.isActualTransactionActive()` でログに出して確認します。

**🇰🇷 답변**

대표적인 것이 다섯 가지입니다. 자기 호출, `private` 메서드, `final` 메서드나 클래스, 빈으로 등록되지 않은 클래스, 그리고 다른 스레드에서의 실행입니다.

공통점은 **프록시를 거치지 않는다**는 점입니다. 안 걸린다는 걸 알아채기 어려우므로, 의심스러울 때는 `TransactionSynchronizationManager.isActualTransactionActive()` 로 로그에 찍어 확인합니다.

---

### Q48. `@Async` を付けたメソッドはトランザクションを引き継ぎますか？
(@Async 메서드는 트랜잭션을 이어받나)

**🇯🇵 回答**

引き継ぎません。トランザクションは `ThreadLocal` に紐づいているので、別スレッドに移った時点で切れます。`SecurityContext` や `MDC` も同様です。

だから非同期側で必要なら、そちらで改めて `@Transactional` を付けます。呼び出し元のトランザクションがコミットされる前に非同期処理が走ると、**まだ見えないデータを読む**ことにもなるので、順序にも注意が必要です。

**🇰🇷 답변**

이어받지 않습니다. 트랜잭션은 `ThreadLocal` 에 묶여 있어 다른 스레드로 옮긴 시점에 끊깁니다. `SecurityContext` 나 `MDC` 도 마찬가지입니다.

그래서 비동기 쪽에서 필요하면 거기서 다시 `@Transactional` 을 붙입니다. 호출한 쪽의 트랜잭션이 커밋되기 전에 비동기 처리가 돌면 **아직 보이지 않는 데이터를 읽게** 되므로 순서에도 주의가 필요합니다.

---

### Q49. コミット後に処理を実行したいときはどうしますか？
(커밋 후에 처리를 실행하고 싶을 때)

**🇯🇵 回答**

`@TransactionalEventListener` を `AFTER_COMMIT` で使います。イベントを発行しておいて、コミットが成功したときだけリスナーが動きます。

これでメール送信やキャッシュ無効化のような「確定してから行いたい処理」を安全に書けます。ロールバックされた場合は実行されないので、**存在しない注文の通知を送る**といった事故を防げます。

**🇰🇷 답변**

`@TransactionalEventListener` 를 `AFTER_COMMIT` 으로 씁니다. 이벤트를 발행해 두고, 커밋이 성공했을 때만 리스너가 동작합니다.

이걸로 메일 발송이나 캐시 무효화처럼 "확정된 뒤에 하고 싶은 처리"를 안전하게 쓸 수 있습니다. 롤백된 경우는 실행되지 않으므로 **존재하지 않는 주문의 알림을 보내는** 사고를 막을 수 있습니다.

---

### Q50. 宣言的トランザクションとプログラム的トランザクションの使い分けは？
(선언적 트랜잭션과 프로그래밍적 트랜잭션의 사용 구분)

**🇯🇵 回答**

基本は宣言的、つまり `@Transactional` です。読みやすく、ビジネスロジックと混ざりません。

`TransactionTemplate` を使うのは、範囲をメソッドより細かくしたい場合です。長い処理の一部だけをトランザクションにしたい、あるいはループの中で単位ごとにコミットしたい、といった場面ではこちらの方が素直に書けます。

**🇰🇷 답변**

기본은 선언적, 즉 `@Transactional` 입니다. 읽기 쉽고 비즈니스 로직과 섞이지 않습니다.

`TransactionTemplate` 을 쓰는 것은 범위를 메서드보다 잘게 하고 싶은 경우입니다. 긴 처리의 일부만 트랜잭션으로 하고 싶거나, 루프 안에서 단위마다 커밋하고 싶은 상황에서는 이쪽이 더 깔끔하게 써집니다.

---

### Q51. テストに `@Transactional` を付けると何が起きますか？
(테스트에 @Transactional 을 붙이면 무슨 일이 일어나나)

**🇯🇵 回答**

テスト終了時に自動でロールバックされ、DBが汚れません。これは便利ですが、落とし穴もあります。

一つは、テストとプロダクションコードが同じトランザクションになるので、**本番では別トランザクションになる問題を見逃す**ことです。もう一つは、コミットされないので `AFTER_COMMIT` のリスナーが動かないことです。そこを検証したいテストでは付けません。

**🇰🇷 답변**

테스트 종료 시 자동으로 롤백되어 DB 가 더러워지지 않습니다. 편리하지만 함정도 있습니다.

하나는 테스트와 프로덕션 코드가 같은 트랜잭션이 되므로 **실제로는 별개 트랜잭션이 되는 문제를 놓친다**는 것입니다. 또 하나는 커밋되지 않으므로 `AFTER_COMMIT` 리스너가 동작하지 않는다는 것입니다. 그걸 검증하려는 테스트에는 붙이지 않습니다.

---

### Q52. 複数のAdviceが同じメソッドに適用される順序は？
(여러 Advice 가 같은 메서드에 적용되는 순서)

**🇯🇵 回答**

`@Order` か `Ordered` で決めます。値が小さいほど外側になります。指定しないと順序は保証されません。

実務で意識するのは、トランザクションと自作Aspectの前後関係です。**トランザクションの内側で動かしたいのか外側なのか**で挙動が変わります。例えばリトライを掛けるAspectは、トランザクションの外側でないと同じ壊れたトランザクションを再試行することになります。

**🇰🇷 답변**

`@Order` 나 `Ordered` 로 정합니다. 값이 작을수록 바깥쪽이 됩니다. 지정하지 않으면 순서는 보장되지 않습니다.

실무에서 신경 쓰는 것은 트랜잭션과 직접 만든 Aspect 의 앞뒤 관계입니다. **트랜잭션 안쪽에서 돌릴지 바깥쪽에서 돌릴지**로 동작이 달라집니다. 예를 들어 재시도를 거는 Aspect 는 트랜잭션 바깥쪽이 아니면 같은 깨진 트랜잭션을 재시도하게 됩니다.

---

### Q53. `@Around` と他のAdviceの違いは？
(@Around 와 다른 Advice 의 차이)

**🇯🇵 回答**

`@Around` だけが実行そのものを制御できます。`proceed()` を呼ばなければ対象メソッドは実行されませんし、戻り値も差し替えられます。

その分責任が重く、`proceed()` の呼び忘れや戻り値の返し忘れが致命的なバグになります。だから前処理だけなら `@Before`、後処理だけなら `@AfterReturning` のように、**必要最小限のAdviceを選ぶ**ようにしています。

**🇰🇷 답변**

`@Around` 만이 실행 자체를 제어할 수 있습니다. `proceed()` 를 부르지 않으면 대상 메서드는 실행되지 않고, 반환값도 바꿔 끼울 수 있습니다.

그만큼 책임이 무겁고 `proceed()` 호출 누락이나 반환값 누락이 치명적 버그가 됩니다. 그래서 전처리만이면 `@Before`, 후처리만이면 `@AfterReturning` 처럼 **필요 최소한의 Advice 를 고르도록** 합니다.

---

### Q54. `@Repository` が付いていると何が変わりますか？
(@Repository 가 붙으면 무엇이 달라지나)

**🇯🇵 回答**

コンポーネントスキャンの対象になることに加え、例外の変換が有効になります。JDBCやJPAの固有例外が、Springの `DataAccessException` 階層に翻訳されます。

これによって、上位層がDB製品固有の例外に依存しなくなります。MySQLからPostgreSQLに変えても、`DuplicateKeyException` を捕まえるコードはそのまま動きます。

**🇰🇷 답변**

컴포넌트 스캔 대상이 되는 것에 더해, 예외 변환이 활성화됩니다. JDBC 나 JPA 의 고유 예외가 Spring 의 `DataAccessException` 계층으로 번역됩니다.

이로써 상위 계층이 DB 제품 고유 예외에 의존하지 않게 됩니다. MySQL 에서 PostgreSQL 로 바꿔도 `DuplicateKeyException` 을 잡는 코드는 그대로 동작합니다.

---

### Q55. AOP を自作するときに気をつけていることは？
(AOP 를 직접 만들 때 신경 쓰는 것)

**🇯🇵 回答**

Pointcut を広く取りすぎないことです。全メソッドに掛けると、意図しない箇所まで巻き込まれ、性能にも効きます。パッケージやアノテーションで限定します。

もう一つは、**Aspectの中で例外を握りつぶさない**ことです。横断的な処理が本来の例外を消してしまうと、原因調査が非常に難しくなります。ログを出したら必ず再スローします。

**🇰🇷 답변**

Pointcut 을 너무 넓게 잡지 않는 것입니다. 모든 메서드에 걸면 의도하지 않은 곳까지 말려들고 성능에도 영향이 옵니다. 패키지나 어노테이션으로 한정합니다.

또 하나는 **Aspect 안에서 예외를 삼키지 않는 것**입니다. 횡단 처리가 본래의 예외를 지워 버리면 원인 조사가 매우 어려워집니다. 로그를 남겼으면 반드시 다시 던집니다.
