### Q1. Kubernetes は何を解決するものですか？
(쿠버네티스가 해결하는 것)

**🇯🇵 回答**

コンテナを「どこで何個動かすか」を宣言的に管理する仕組みです。望ましい状態を書いておくと、コントローラが現在の状態をそこに近づけ続けます。

だから、ノードが落ちても別のノードで立て直しますし、デプロイも段階的に置き換えられます。**手順ではなく状態を書く**ところが、それまでの運用と一番違う点です。

**🇰🇷 답변**

컨테이너를 "어디서 몇 개 돌릴지"를 선언적으로 관리하는 장치입니다. 원하는 상태를 적어 두면 컨트롤러가 현재 상태를 거기에 계속 맞춥니다.

그래서 노드가 죽어도 다른 노드에서 다시 세우고, 배포도 단계적으로 교체합니다. **절차가 아니라 상태를 적는다**는 점이 이전 운영과 가장 다른 점입니다.

### Q2. コントロールプレーンとデータプレーンの役割は？
(컨트롤 플레인과 데이터 플레인의 역할)

**🇯🇵 回答**

コントロールプレーンは API サーバ、etcd、スケジューラ、コントローラマネージャです。状態を保持し、どこに置くかを決めます。

データプレーンは各ノードの kubelet と kube-proxy、コンテナランタイムで、実際にコンテナを動かします。**API サーバが唯一の入口**で、すべての操作はそこを通ります。etcd が壊れるとクラスタの状態そのものを失うので、バックアップの対象です。

**🇰🇷 답변**

컨트롤 플레인은 API 서버, etcd, 스케줄러, 컨트롤러 매니저입니다. 상태를 보관하고 어디에 둘지를 정합니다.

데이터 플레인은 각 노드의 kubelet 과 kube-proxy, 컨테이너 런타임으로 실제로 컨테이너를 돌립니다. **API 서버가 유일한 입구**이고 모든 조작은 거기를 지납니다. etcd 가 깨지면 클러스터 상태 자체를 잃으므로 백업 대상입니다.

### Q3. Pod とは何ですか？なぜコンテナ単位ではないのですか？
(Pod 이란, 왜 컨테이너 단위가 아닌가)

**🇯🇵 回答**

Pod は同じネットワークとストレージを共有する、一つ以上のコンテナのまとまりです。スケジューリングの最小単位でもあります。

こうなっているのは、ログ収集やプロキシのように**本体と生死を共にする補助プロセス**を同居させたいからです。逆に言えば、独立してスケールさせたいものは別の Pod にします。

**🇰🇷 답변**

Pod 은 같은 네트워크와 스토리지를 공유하는 하나 이상의 컨테이너 묶음입니다. 스케줄링의 최소 단위이기도 합니다.

이렇게 된 것은 로그 수집이나 프록시처럼 **본체와 생사를 같이하는 보조 프로세스**를 함께 두고 싶기 때문입니다. 반대로 독립적으로 확장하고 싶은 것은 다른 Pod 으로 나눕니다.

### Q4. Deployment・ReplicaSet・Pod の関係は？
(Deployment·ReplicaSet·Pod 의 관계)

**🇯🇵 回答**

Deployment が ReplicaSet を作り、ReplicaSet が Pod の数を保ちます。三層になっているのは、**更新のときに新旧の ReplicaSet を並行させる**ためです。

だからロールバックは、前の ReplicaSet に戻すだけで済みます。Pod を直接作ると、消えたときに誰も作り直してくれないので、実務ではまず Deployment を使います。

**🇰🇷 답변**

Deployment 가 ReplicaSet 을 만들고 ReplicaSet 이 Pod 수를 유지합니다. 3층인 것은 **갱신할 때 신·구 ReplicaSet 을 병행시키기** 위해서입니다.

그래서 롤백은 이전 ReplicaSet 으로 되돌리기만 하면 됩니다. Pod 을 직접 만들면 사라졌을 때 아무도 다시 만들어 주지 않으므로 실무에서는 먼저 Deployment 를 씁니다.

### Q5. StatefulSet は Deployment と何が違いますか？
(StatefulSet 과 Deployment 의 차이)

**🇯🇵 回答**

Pod に安定した名前と、それぞれ専用のボリュームが付きます。起動と停止の順序も保証されます。

DB やブローカーのように、**個体の識別が意味を持つもの**に使います。逆にステートレスなアプリに使うと、更新が遅くなるだけで利点がありません。ボリュームは Pod を消しても残るので、後片付けは別に必要です。

**🇰🇷 답변**

Pod 에 안정적인 이름과 각자 전용 볼륨이 붙습니다. 기동과 정지 순서도 보장됩니다.

DB 나 브로커처럼 **개체의 식별이 의미를 갖는 것**에 씁니다. 반대로 스테이트리스한 앱에 쓰면 갱신만 느려지고 이점이 없습니다. 볼륨은 Pod 을 지워도 남으므로 뒷정리는 따로 필요합니다.

---

### Q6. DaemonSet はどんなときに使いますか？
(DaemonSet 사용 시점)

**🇯🇵 回答**

すべてのノードに一つずつ置きたいときです。ログ収集エージェント、監視エージェント、ネットワークプラグインが典型です。

ノードが増えれば自動で配られ、減れば消えます。ノードのリソースを常に消費するので、**軽く保つこと**と、リソース制限を必ず付けることが運用上の要点です。

**🇰🇷 답변**

모든 노드에 하나씩 두고 싶을 때입니다. 로그 수집 에이전트, 모니터링 에이전트, 네트워크 플러그인이 전형입니다.

노드가 늘면 자동으로 배포되고 줄면 사라집니다. 노드의 리소스를 항상 소비하므로 **가볍게 유지하는 것**과 리소스 제한을 반드시 붙이는 것이 운영상의 요점입니다.

### Q7. Service は何をしていますか？
(Service 의 역할)

**🇯🇵 回答**

複数の Pod に対する**安定した宛先**を提供します。Pod は入れ替わるたびに IP が変わるので、直接指定できません。

セレクタでラベルの合う Pod を集め、そこへ振り分けます。実体としては、各ノードの kube-proxy が転送ルールを入れています。名前解決はクラスタ内 DNS が担当します。

**🇰🇷 답변**

여러 Pod 에 대한 **안정적인 목적지**를 제공합니다. Pod 은 교체될 때마다 IP 가 바뀌므로 직접 지정할 수 없습니다.

셀렉터로 라벨이 맞는 Pod 을 모아 그쪽으로 분배합니다. 실체로는 각 노드의 kube-proxy 가 전달 규칙을 넣습니다. 이름 해석은 클러스터 내 DNS 가 담당합니다.

---

### Q8. Service のタイプはどう使い分けますか？
(Service 타입 구분)

**🇯🇵 回答**

ClusterIP はクラスタ内部からのみ、NodePort は各ノードのポートを開ける、LoadBalancer はクラウドのロードバランサを作ります。

外部公開は基本的に Ingress か Gateway 経由にします。サービスごとに LoadBalancer を作ると、その数だけ課金され管理も増えるからです。ヘッドレスにすると個々の Pod の IP を返すので、StatefulSet と組み合わせます。

**🇰🇷 답변**

ClusterIP 는 클러스터 내부에서만, NodePort 는 각 노드의 포트를 열고, LoadBalancer 는 클라우드의 로드밸런서를 만듭니다.

외부 공개는 기본적으로 Ingress 나 Gateway 를 거칩니다. 서비스마다 LoadBalancer 를 만들면 그 수만큼 과금되고 관리도 늘기 때문입니다. 헤드리스로 하면 개별 Pod 의 IP 를 돌려주므로 StatefulSet 과 조합합니다.

### Q9. Ingress は何をしますか？
(Ingress 의 역할)

**🇯🇵 回答**

HTTP のレベルで、ホスト名やパスに応じて後ろのサービスへ振り分けます。TLS の終端もここで行うことが多いです。

Ingress 自体は仕様で、実際に働くのはコントローラです。だから使える機能はコントローラ依存で、注釈で細かい設定をすることになります。それを整理するために Gateway API が出てきた、という流れも押さえておきます。

**🇰🇷 답변**

HTTP 수준에서 호스트명이나 경로에 따라 뒤의 서비스로 분배합니다. TLS 종료도 여기서 하는 경우가 많습니다.

Ingress 자체는 사양이고 실제로 일하는 것은 컨트롤러입니다. 그래서 쓸 수 있는 기능이 컨트롤러에 의존하고 어노테이션으로 세부 설정을 하게 됩니다. 그것을 정리하려고 Gateway API 가 나왔다는 흐름도 알아 둡니다.

---

### Q10. リクエストが Pod に届くまでの流れを説明してください。
(요청이 Pod 에 닿기까지)

**🇯🇵 回答**

外部のロードバランサから Ingress コントローラの Pod に入り、そこでホストとパスを見て Service に渡します。Service の宛先は kube-proxy のルールで実際の Pod に転送されます。

クラスタ内部同士なら、DNS でサービス名を引いて ClusterIP に出し、同じく転送されます。**この経路のどこで切れているか**を切り分けるのが、繋がらないときの調査手順になります。

**🇰🇷 답변**

외부 로드밸런서에서 Ingress 컨트롤러 Pod 으로 들어가고, 거기서 호스트와 경로를 보고 Service 로 넘깁니다. Service 의 목적지는 kube-proxy 규칙으로 실제 Pod 에 전달됩니다.

클러스터 내부끼리라면 DNS 로 서비스 이름을 조회해 ClusterIP 로 보내고 마찬가지로 전달됩니다. **이 경로 중 어디서 끊겼는지**를 가려내는 것이 안 될 때의 조사 절차가 됩니다.

### Q11. liveness と readiness の違いは？
(liveness 와 readiness 의 차이)

**🇯🇵 回答**

liveness は「死んでいるなら再起動する」、readiness は「準備できていないならトラフィックを送らない」です。役割が全く違います。

よくある事故は、liveness に重い依存チェックを入れることです。DB が一瞬遅いだけで**再起動ループ**になります。依存の確認は readiness に置き、liveness は自分自身が生きているかだけを見ます。

**🇰🇷 답변**

liveness 는 "죽었으면 재시작", readiness 는 "준비 안 됐으면 트래픽을 보내지 않기"입니다. 역할이 전혀 다릅니다.

흔한 사고는 liveness 에 무거운 의존성 검사를 넣는 것입니다. DB 가 잠깐 느린 것만으로 **재시작 루프**가 됩니다. 의존성 확인은 readiness 에 두고, liveness 는 자기 자신이 살아 있는지만 봅니다.

### Q12. startupProbe は何のためにありますか？
(startupProbe 의 목적)

**🇯🇵 回答**

起動に時間がかかるアプリのためです。これがないと、起動途中に liveness が失敗して再起動を繰り返します。

JVM のようにウォームアップが要るものでは特に効きます。startupProbe が成功するまで他のプローブは動かないので、**起動の猶予と稼働中の判定を分けて設定できます**。

**🇰🇷 답변**

기동에 시간이 걸리는 앱을 위해서입니다. 이게 없으면 기동 도중에 liveness 가 실패해 재시작을 반복합니다.

JVM 처럼 워밍업이 필요한 것에서 특히 효과가 있습니다. startupProbe 가 성공할 때까지 다른 프로브는 동작하지 않으므로 **기동 유예와 가동 중 판정을 나눠 설정할 수 있습니다.**

### Q13. requests と limits はどう違いますか？
(requests 와 limits 의 차이)

**🇯🇵 回答**

requests はスケジューリングで確保する量、limits は超えてはいけない上限です。

CPU の limit を超えるとスロットルされ、メモリの limit を超えると **OOMKilled** されます。ここが CPU とメモリで挙動が違う一番大事な点です。requests を書かないとスケジューラが判断できず、ノードが過負荷になります。

**🇰🇷 답변**

requests 는 스케줄링에서 확보하는 양, limits 는 넘어서는 안 되는 상한입니다.

CPU 의 limit 을 넘으면 스로틀되고, 메모리의 limit 을 넘으면 **OOMKilled** 됩니다. 여기가 CPU 와 메모리에서 동작이 다른 가장 중요한 점입니다. requests 를 안 쓰면 스케줄러가 판단할 수 없어 노드가 과부하가 됩니다.

---

### Q14. limits と JVM の関係で気をつけることは？
(limits 와 JVM 의 관계)

**🇯🇵 回答**

JVM はコンテナの制限を見て自分を構成します。**CPU が 1 だとエルゴノミクスがシリアル GC を選び**、メモリ制限の一定割合をヒープにします。

なので limits を決めることが実質的に JVM のチューニングになります。もう一つ、ヒープの外にもメタスペースやスレッドスタック、ネイティブが要るので、**コンテナの制限はヒープより十分大きく**しないと OOMKilled になります。

**🇰🇷 답변**

JVM 은 컨테이너의 제한을 보고 스스로를 구성합니다. **CPU 가 1 이면 에르고노믹스가 Serial GC 를 고르고**, 메모리 제한의 일정 비율을 힙으로 잡습니다.

그래서 limits 를 정하는 것이 사실상 JVM 튜닝이 됩니다. 또 하나, 힙 밖에도 메타스페이스와 스레드 스택, 네이티브가 필요하므로 **컨테이너 제한은 힙보다 충분히 크게** 잡지 않으면 OOMKilled 가 납니다.

### Q15. Pod の QoS クラスとは何ですか？
(Pod 의 QoS 클래스)

**🇯🇵 回答**

requests と limits の書き方で決まります。両方同じなら Guaranteed、requests だけなら Burstable、どちらもなければ BestEffort です。

ノードのメモリが逼迫したとき、**BestEffort から順に退去させられます**。重要なワークロードは Guaranteed にしておくと、巻き添えで落ちにくくなります。これを知らずに何も書かないと、一番先に落ちる側になります。

**🇰🇷 답변**

requests 와 limits 를 어떻게 쓰느냐로 정해집니다. 둘이 같으면 Guaranteed, requests 만 있으면 Burstable, 둘 다 없으면 BestEffort 입니다.

노드의 메모리가 부족해지면 **BestEffort 부터 순서대로 쫓겨납니다.** 중요한 워크로드는 Guaranteed 로 두면 휘말려 죽는 일이 줄어듭니다. 이걸 모르고 아무것도 안 쓰면 가장 먼저 죽는 쪽이 됩니다.

---

### Q16. スケジューリングはどう制御しますか？
(스케줄링 제어)

**🇯🇵 回答**

ノードセレクタやアフィニティで「どこに置きたいか」、taint と toleration で「誰を受け入れるか」を制御します。

よく使うのは反アフィニティです。同じサービスの複製を**別のノードや別のゾーンに散らす**ことで、一台落ちても全滅しないようにします。GPU ノードのような特別なノードには taint を付けて、必要な Pod だけを通します。

**🇰🇷 답변**

노드 셀렉터나 어피니티로 "어디에 두고 싶은가", taint 와 toleration 으로 "누구를 받아들일까"를 제어합니다.

자주 쓰는 것은 안티 어피니티입니다. 같은 서비스의 복제본을 **다른 노드나 다른 존에 흩어** 한 대가 죽어도 전멸하지 않게 합니다. GPU 노드 같은 특별한 노드에는 taint 를 붙여 필요한 Pod 만 통과시킵니다.

---

### Q17. ConfigMap と Secret はどう使い分けますか？
(ConfigMap 과 Secret 구분)

**🇯🇵 回答**

設定値は ConfigMap、機密情報は Secret です。ただし Secret は既定では base64 で保存されているだけで、**暗号化ではありません**。

なので etcd の保存時暗号化を有効にし、RBAC で読める人を絞ります。より厳格にするなら外部の秘密管理サービスから注入します。どちらも環境変数かボリュームで渡しますが、**環境変数はプロセス一覧やログに漏れやすい**点に注意します。

**🇰🇷 답변**

설정값은 ConfigMap, 기밀정보는 Secret 입니다. 다만 Secret 은 기본적으로 base64 로 저장될 뿐 **암호화가 아닙니다.**

그래서 etcd 저장 시 암호화를 켜고 RBAC 로 읽을 수 있는 사람을 좁힙니다. 더 엄격히 하려면 외부 비밀 관리 서비스에서 주입합니다. 둘 다 환경변수나 볼륨으로 넘기는데 **환경변수는 프로세스 목록이나 로그로 새기 쉬운** 점에 주의합니다.

### Q18. 設定を変えたとき Pod に反映させるには？
(설정 변경을 Pod 에 반영)

**🇯🇵 回答**

環境変数として渡している場合は再起動が要ります。ボリュームでマウントしていれば、しばらくしてファイルは更新されますが、**アプリが読み直さなければ意味がありません**。

実務では、設定のハッシュを Pod のアノテーションに入れておいて、変わったら自動でローリング更新が走るようにします。何が反映されて何が反映されないかを、あいまいにしないのが要点です。

**🇰🇷 답변**

환경변수로 넘긴 경우는 재시작이 필요합니다. 볼륨으로 마운트했다면 얼마 뒤 파일은 갱신되지만 **앱이 다시 읽지 않으면 의미가 없습니다.**

실무에서는 설정의 해시를 Pod 어노테이션에 넣어 두고, 바뀌면 자동으로 롤링 업데이트가 돌게 합니다. 무엇이 반영되고 무엇이 반영되지 않는지를 모호하게 두지 않는 것이 요점입니다.

### Q19. ローリングアップデートはどう動きますか？
(롤링 업데이트의 동작)

**🇯🇵 回答**

新しい ReplicaSet を少しずつ増やし、古い方を減らします。`maxSurge` と `maxUnavailable` で、増やす余裕と落としてよい数を決めます。

readiness が通るまで新しい Pod にはトラフィックが来ないので、**readiness を正しく作っていることが前提**です。ここが雑だと、起動途中の Pod にリクエストが流れてエラーになります。

**🇰🇷 답변**

새 ReplicaSet 을 조금씩 늘리고 옛것을 줄입니다. `maxSurge` 와 `maxUnavailable` 로 늘릴 여유와 내려도 되는 수를 정합니다.

readiness 가 통과할 때까지 새 Pod 에는 트래픽이 오지 않으므로 **readiness 를 제대로 만든 것이 전제**입니다. 여기가 엉성하면 기동 중인 Pod 으로 요청이 흘러 에러가 납니다.

### Q20. デプロイ戦略はどう選びますか？
(배포 전략 선택)

**🇯🇵 回答**

標準はローリングです。停止なしで置き換えられ、追加のリソースも少なくて済みます。

リスクの高い変更ではカナリアにして、一部のトラフィックだけを新バージョンに流し、指標を見て進めます。DB スキーマの変更が絡むなら、新旧が同時に動ける形にしてから段階を分けます。**戦略の前に、戻せるようにしておくこと**が先です。

**🇰🇷 답변**

기본은 롤링입니다. 무중단으로 교체되고 추가 리소스도 적게 듭니다.

위험이 큰 변경은 카나리로 해서 일부 트래픽만 새 버전으로 흘리고 지표를 보며 진행합니다. DB 스키마 변경이 얽히면 신·구가 동시에 돌 수 있는 형태로 만든 뒤 단계를 나눕니다. **전략 이전에 되돌릴 수 있게 해 두는 것**이 먼저입니다.

### Q21. Pod を安全に終了させるにはどうしますか？
(Pod 의 안전한 종료)

**🇯🇵 回答**

終了が始まると、Service の宛先から外す処理と SIGTERM の送信が**並行して**起きます。つまり、外れる前に落ちると接続中のリクエストが失敗します。

なので、SIGTERM を受けたら少し待ってから新規受付を止め、処理中を終わらせます。`preStop` で数秒待つのが定番です。`terminationGracePeriodSeconds` も、処理が終わる時間より長くしておきます。

**🇰🇷 답변**

종료가 시작되면 Service 목적지에서 빼는 처리와 SIGTERM 전송이 **병행해서** 일어납니다. 즉 빠지기 전에 죽으면 처리 중인 요청이 실패합니다.

그래서 SIGTERM 을 받으면 잠시 기다렸다가 신규 수신을 멈추고 처리 중인 것을 끝냅니다. `preStop` 으로 몇 초 기다리는 것이 정석입니다. `terminationGracePeriodSeconds` 도 처리가 끝나는 시간보다 길게 잡습니다.

### Q22. HPA はどう動きますか？
(HPA 의 동작)

**🇯🇵 回答**

指標を見て Pod の数を増減します。CPU 使用率が定番ですが、カスタム指標も使えます。

注意点は二つです。一つは、**requests を書いていないと CPU 使用率が計算できない**こと。もう一つは、増やしても効かない場合があることです。ボトルネックが DB や外部 API なら、Pod を増やしても相手が詰まるだけです。増減の揺れを防ぐ設定も入れます。

**🇰🇷 답변**

지표를 보고 Pod 수를 늘리고 줄입니다. CPU 사용률이 기본이지만 커스텀 지표도 쓸 수 있습니다.

주의점은 둘입니다. 하나는 **requests 를 안 쓰면 CPU 사용률을 계산할 수 없다**는 것, 또 하나는 늘려도 효과가 없는 경우가 있다는 것입니다. 병목이 DB 나 외부 API 라면 Pod 을 늘려도 상대가 막힐 뿐입니다. 증감의 진동을 막는 설정도 넣습니다.

### Q23. Job と CronJob はどう使いますか？
(Job 과 CronJob 사용)

**🇯🇵 回答**

一度きりの処理が Job、定期実行が CronJob です。失敗時の再試行回数や、並列度を指定できます。

注意するのは重複実行です。前回が終わっていないときにどうするかを `concurrencyPolicy` で決めます。それでも二重に走る可能性はあるので、**処理自体を冪等に作る**のが前提です。終わった Job が残り続けないよう、履歴の保持数も設定します。

**🇰🇷 답변**

한 번만 실행하는 처리가 Job, 정기 실행이 CronJob 입니다. 실패 시 재시도 횟수나 병렬도를 지정할 수 있습니다.

주의할 것은 중복 실행입니다. 이전 실행이 안 끝났을 때 어떻게 할지를 `concurrencyPolicy` 로 정합니다. 그래도 두 번 돌 가능성이 있으므로 **처리 자체를 멱등하게 만드는 것**이 전제입니다. 끝난 Job 이 계속 남지 않도록 이력 보존 수도 설정합니다.

### Q24. 永続ボリュームはどう扱いますか？
(퍼시스턴트 볼륨 취급)

**🇯🇵 回答**

PVC で「こういうストレージが欲しい」と要求し、StorageClass に従って実体が用意されます。

気をつけるのはアクセスモードです。多くのブロックストレージは**一つのノードからしか書けません**。複数 Pod で共有したいならファイルストレージが要ります。それと、削除ポリシー次第では PVC を消した瞬間にデータが消えます。

**🇰🇷 답변**

PVC 로 "이런 스토리지가 필요하다"고 요구하면 StorageClass 에 따라 실체가 준비됩니다.

주의할 것은 접근 모드입니다. 많은 블록 스토리지는 **한 노드에서만 쓸 수 있습니다.** 여러 Pod 에서 공유하려면 파일 스토리지가 필요합니다. 그리고 삭제 정책에 따라서는 PVC 를 지우는 순간 데이터가 사라집니다.

### Q25. namespace は何のために分けますか？
(네임스페이스를 나누는 이유)

**🇯🇵 回答**

名前の衝突を避け、権限とリソース割り当ての単位を作るためです。RBAC の範囲、ResourceQuota、NetworkPolicy をここに紐づけます。

ただし**強い分離ではありません**。同じノードの上で動くので、本当に分離が要るならクラスタを分けるか、ノードを分ける判断が要ります。環境ごと(開発と本番)を namespace で分けるのは、この理由で勧めません。

**🇰🇷 답변**

이름 충돌을 피하고 권한과 리소스 할당의 단위를 만들기 위해서입니다. RBAC 범위, ResourceQuota, NetworkPolicy 를 여기에 묶습니다.

다만 **강한 격리는 아닙니다.** 같은 노드 위에서 돌기 때문에 정말 격리가 필요하면 클러스터를 나누거나 노드를 나누는 판단이 필요합니다. 환경별(개발과 운영)을 네임스페이스로 나누는 것은 이 이유로 권하지 않습니다.
