### Q26. Pod が起動しないとき、どう調べますか？
(Pod 이 기동하지 않을 때)

**🇯🇵 回答**

まず状態を見ます。`Pending` ならスケジュールできていない、`ImagePullBackOff` ならイメージが取れない、`CrashLoopBackOff` なら起動して落ちている。**状態ごとに原因の場所が違います**。

`describe` のイベントに理由が出ていることが多いです。`Pending` ならリソース不足か taint、`CrashLoop` ならアプリのログを見ます。前のコンテナのログは `--previous` で取れます。

**🇰🇷 답변**

먼저 상태를 봅니다. `Pending` 이면 스케줄되지 못한 것, `ImagePullBackOff` 면 이미지를 못 받는 것, `CrashLoopBackOff` 면 떴다가 죽는 것. **상태마다 원인의 위치가 다릅니다.**

`describe` 의 이벤트에 이유가 나와 있는 경우가 많습니다. `Pending` 이면 리소스 부족이나 taint, `CrashLoop` 이면 앱 로그를 봅니다. 이전 컨테이너의 로그는 `--previous` 로 볼 수 있습니다.

### Q27. OOMKilled が出たらどうしますか？
(OOMKilled 가 나오면)

**🇯🇵 回答**

まず、本当に足りないのか、リークなのかを分けます。使用量が右肩上がりならリークです。単に足りないなら limit を上げます。

JVM なら、ヒープの外を忘れていないかを確認します。ヒープを limit と同じにすると、メタスペースやスレッドスタックの分で必ず超えます。**limit はヒープより十分大きく**取ります。

**🇰🇷 답변**

먼저 정말 부족한 건지 누수인지를 나눕니다. 사용량이 우상향이면 누수입니다. 단순히 부족하면 limit 을 올립니다.

JVM 이라면 힙 밖을 잊지 않았는지 확인합니다. 힙을 limit 과 같게 잡으면 메타스페이스와 스레드 스택 몫에서 반드시 초과합니다. **limit 은 힙보다 충분히 크게** 잡습니다.

### Q28. サービスに繋がらないとき、どこから見ますか？
(서비스에 연결되지 않을 때)

**🇯🇵 回答**

経路を順にたどります。まず Service のセレクタに合う Pod がいるか、`Endpoints` が空でないかを見ます。**空なら、ラベルが合っていないか readiness が通っていません**。

次にポート番号、それから DNS で名前が引けるか、最後に NetworkPolicy で塞がれていないかを見ます。Pod に入って直接叩ければ、アプリ側かネットワーク側かの切り分けができます。

**🇰🇷 답변**

경로를 순서대로 따라갑니다. 먼저 Service 셀렉터에 맞는 Pod 이 있는지, `Endpoints` 가 비어 있지 않은지를 봅니다. **비어 있으면 라벨이 안 맞거나 readiness 가 통과하지 못한 것입니다.**

다음으로 포트 번호, 그다음 DNS 로 이름이 조회되는지, 마지막으로 NetworkPolicy 로 막혀 있지 않은지를 봅니다. Pod 안에 들어가 직접 때려 보면 앱 쪽인지 네트워크 쪽인지 가릴 수 있습니다.

### Q29. NetworkPolicy はどう使いますか？
(NetworkPolicy 사용)

**🇯🇵 回答**

既定ではすべての Pod が互いに通信できます。NetworkPolicy を当てると、**そのラベルの Pod は許可したものだけ**を受け付けるようになります。

最小権限を作るなら、まず全拒否を入れてから必要な経路を開けます。注意点は、**CNI が対応していないと何も起きない**ことです。ポリシーを書いたのに効いていない、という事故が起きるので、必ず実際に塞がっているかを確認します。

**🇰🇷 답변**

기본적으로는 모든 Pod 이 서로 통신할 수 있습니다. NetworkPolicy 를 적용하면 **그 라벨의 Pod 은 허용한 것만** 받아들이게 됩니다.

최소 권한을 만들려면 먼저 전면 거부를 넣고 필요한 경로를 엽니다. 주의점은 **CNI 가 대응하지 않으면 아무 일도 일어나지 않는다**는 것입니다. 정책을 썼는데 안 듣는 사고가 나므로 반드시 실제로 막혔는지 확인합니다.

### Q30. RBAC はどう設計しますか？
(RBAC 설계)

**🇯🇵 回答**

Role で「何にどの操作を許すか」を決め、RoleBinding で誰に与えるかを決めます。namespace を越えるなら ClusterRole です。

原則は最小権限です。人には読み取り中心、書き込みは CI のサービスアカウントに寄せます。**`cluster-admin` を配らない**こと、そして Pod に付けるサービスアカウントの権限を絞ることが実務の要点です。既定のサービスアカウントに何でもできる権限が付いていないかを確認します。

**🇰🇷 답변**

Role 로 "무엇에 어떤 조작을 허용할지"를 정하고 RoleBinding 으로 누구에게 줄지를 정합니다. 네임스페이스를 넘으면 ClusterRole 입니다.

원칙은 최소 권한입니다. 사람에게는 읽기 중심, 쓰기는 CI 의 서비스 어카운트로 모읍니다. **`cluster-admin` 을 뿌리지 않는 것**, 그리고 Pod 에 붙이는 서비스 어카운트 권한을 좁히는 것이 실무의 요점입니다. 기본 서비스 어카운트에 뭐든 할 수 있는 권한이 붙어 있지 않은지 확인합니다.

### Q31. コンテナのセキュリティで気をつけることは？
(컨테이너 보안 주의점)

**🇯🇵 回答**

root で動かさないこと、ファイルシステムを読み取り専用にすること、不要な権限を落とすことです。`privileged` は原則使いません。

イメージ側も同じくらい大事です。**必要最小限のベースイメージ**にして、脆弱性スキャンを CI に入れます。小さくすると攻撃面が減り、転送も速くなります。代わりにデバッグ用のツールが入っていないので、調査は一時的なデバッグコンテナで行います。

**🇰🇷 답변**

root 로 돌리지 않기, 파일시스템을 읽기 전용으로 하기, 불필요한 권한 떨구기입니다. `privileged` 는 원칙적으로 쓰지 않습니다.

이미지 쪽도 그만큼 중요합니다. **필요 최소한의 베이스 이미지**로 하고 취약점 스캔을 CI 에 넣습니다. 작게 하면 공격 표면이 줄고 전송도 빨라집니다. 대신 디버그 도구가 없으므로 조사는 임시 디버그 컨테이너로 합니다.

### Q32. イメージのタグ運用はどうしますか？
(이미지 태그 운영)

**🇯🇵 回答**

`latest` は使いません。どのコードが動いているか分からなくなり、再現も切り戻しもできなくなります。

コミットハッシュやバージョンでタグを付け、可能ならダイジェストで固定します。`imagePullPolicy` も合わせて考えます。**同じタグで中身を差し替える運用**は、ノードごとに違うイメージが動く事故につながります。

**🇰🇷 답변**

`latest` 는 쓰지 않습니다. 어떤 코드가 돌고 있는지 알 수 없게 되고 재현도 롤백도 못 합니다.

커밋 해시나 버전으로 태그를 붙이고 가능하면 다이제스트로 고정합니다. `imagePullPolicy` 도 함께 생각합니다. **같은 태그로 내용을 바꿔치기하는 운영**은 노드마다 다른 이미지가 도는 사고로 이어집니다.

### Q33. ノードが落ちたら何が起きますか？
(노드가 죽으면)

**🇯🇵 回答**

しばらくして NotReady と判定され、その上の Pod が退去対象になり、他のノードで作り直されます。ただし**すぐではありません**。判定の猶予があるので、その間は一部のリクエストが失敗しえます。

だから複製を複数のノードに散らしておくことが前提です。StatefulSet はボリュームの都合で移動が難しいことがあるので、そこは別に考えます。

**🇰🇷 답변**

얼마 뒤 NotReady 로 판정되고 그 위의 Pod 이 축출 대상이 되어 다른 노드에서 다시 만들어집니다. 다만 **즉시는 아닙니다.** 판정 유예가 있어 그동안은 일부 요청이 실패할 수 있습니다.

그래서 복제본을 여러 노드에 흩어 두는 것이 전제입니다. StatefulSet 은 볼륨 사정으로 이동이 어려울 수 있어 그쪽은 따로 생각합니다.

### Q34. ノードの入れ替えはどうしますか？
(노드 교체)

**🇯🇵 回答**

`cordon` で新規スケジュールを止め、`drain` で Pod を退去させてから外します。

このとき PodDisruptionBudget を設定しておくと、**同時に落とせる数を制限**できます。設定していないと、複製が一斉に退去して一時的にサービスが止まることがあります。計画的な作業ほど、この設定の有無が効きます。

**🇰🇷 답변**

`cordon` 으로 신규 스케줄을 막고 `drain` 으로 Pod 을 축출한 뒤 뺍니다.

이때 PodDisruptionBudget 을 설정해 두면 **동시에 내릴 수 있는 수를 제한**할 수 있습니다. 설정하지 않으면 복제본이 한꺼번에 축출되어 일시적으로 서비스가 멈추기도 합니다. 계획된 작업일수록 이 설정의 유무가 크게 작용합니다.

### Q35. リソースが逼迫すると Pod はどうなりますか？
(리소스가 부족해지면)

**🇯🇵 回答**

メモリが逼迫すると kubelet が退去を始めます。順番は QoS クラス次第で、BestEffort が先、Guaranteed が最後です。

CPU は退去ではなくスロットルです。だから「遅いけれど死なない」という形で出ます。**症状の出方が違う**ので、遅延の調査では CPU スロットルの指標を必ず見ます。ノードの空きが常に少ないなら、requests の設計を見直します。

**🇰🇷 답변**

메모리가 부족해지면 kubelet 이 축출을 시작합니다. 순서는 QoS 클래스에 따라 BestEffort 가 먼저, Guaranteed 가 마지막입니다.

CPU 는 축출이 아니라 스로틀입니다. 그래서 "느리지만 죽지는 않는" 형태로 나타납니다. **증상이 나타나는 방식이 다르므로** 지연 조사에서는 CPU 스로틀 지표를 반드시 봅니다. 노드의 여유가 늘 적다면 requests 설계를 다시 봅니다.

### Q36. ログはどう集めますか？
(로그 수집)

**🇯🇵 回答**

コンテナは標準出力に出し、ノード上のエージェントが集めて外へ送ります。ファイルに書くとローテーションや収集を自分で面倒見ることになります。

Pod は消えるとログも消えるので、**外部に集約されていることが前提**です。構造化して出し、リクエスト ID を入れておくと、サービスをまたいで追えます。個人情報を出さないことも合わせて確認します。

**🇰🇷 답변**

컨테이너는 표준 출력으로 내고 노드 위의 에이전트가 모아 밖으로 보냅니다. 파일에 쓰면 로테이션과 수집을 직접 챙기게 됩니다.

Pod 은 사라지면 로그도 사라지므로 **외부에 집약돼 있는 것이 전제**입니다. 구조화해서 내보내고 요청 ID 를 넣어 두면 서비스를 넘어 추적할 수 있습니다. 개인정보를 내보내지 않는 것도 함께 확인합니다.

### Q37. 監視では何を見ますか？
(모니터링 지표)

**🇯🇵 回答**

アプリの側はリクエスト数・エラー率・レイテンシ、基盤の側はノードとPodのリソース、再起動回数、Pending の数です。

**再起動回数はとくに効きます。**静かに増えているときは、liveness の設定かメモリ不足を疑います。レイテンシは平均ではなくパーセンタイルで見ます。アラートは症状ではなく、原因に近いところに付けます。

**🇰🇷 답변**

앱 쪽은 요청 수·에러율·지연, 기반 쪽은 노드와 Pod 의 리소스, 재시작 횟수, Pending 수입니다.

**재시작 횟수는 특히 유용합니다.** 조용히 늘고 있을 때는 liveness 설정이나 메모리 부족을 의심합니다. 지연은 평균이 아니라 백분위수로 봅니다. 알림은 증상보다 원인에 가까운 곳에 겁니다.

### Q38. マニフェストはどう管理しますか？
(매니페스트 관리)

**🇯🇵 回答**

Git に置いて、環境ごとの差分は Kustomize や Helm の値で表現します。手で `kubectl edit` した変更は、次のデプロイで消えるうえに記録が残りません。

GitOps にすると、**クラスタの状態が Git と一致していること**をツールが保証します。差分が出たら検知できるのが利点です。誰が何を変えたかが履歴に残るので、監査にも効きます。

**🇰🇷 답변**

Git 에 두고 환경별 차이는 Kustomize 나 Helm 의 값으로 표현합니다. 손으로 `kubectl edit` 한 변경은 다음 배포에서 사라지고 기록도 남지 않습니다.

GitOps 로 하면 **클러스터 상태가 Git 과 일치하는 것**을 도구가 보장합니다. 차이가 생기면 감지할 수 있는 것이 장점입니다. 누가 무엇을 바꿨는지가 이력에 남아 감사에도 도움이 됩니다.

### Q39. Helm と Kustomize はどう使い分けますか？
(Helm 과 Kustomize 구분)

**🇯🇵 回答**

Helm はテンプレートと値でパッケージとして配る仕組み、Kustomize はベースに対する差分を重ねる仕組みです。

外部に配布するもの、あるいは複雑な条件分岐が要るものは Helm。自分たちのアプリを環境ごとに少し変えるだけなら Kustomize の方が読みやすいです。**テンプレートが複雑になりすぎると、YAML が読めなくなる**ので、そこを分岐点にしています。

**🇰🇷 답변**

Helm 은 템플릿과 값으로 패키지처럼 배포하는 장치, Kustomize 는 베이스에 대한 차분을 겹치는 장치입니다.

외부에 배포하는 것이나 복잡한 조건 분기가 필요한 것은 Helm. 우리 앱을 환경별로 조금 바꾸는 정도면 Kustomize 가 읽기 쉽습니다. **템플릿이 너무 복잡해지면 YAML 을 읽을 수 없게 되므로** 거기를 분기점으로 삼습니다.

### Q40. Operator / CRD は何のためにありますか？
(Operator·CRD 의 목적)

**🇯🇵 回答**

Kubernetes の API を自分たちのリソースで拡張し、運用の手順をコントローラとして自動化する仕組みです。

DB のバックアップやフェイルオーバーのように、**手順が決まっている運用**を宣言的にできます。ただし自作するとそれ自体を保守することになるので、既存の Operator で足りないかを先に検討します。

**🇰🇷 답변**

쿠버네티스 API 를 우리 리소스로 확장하고 운영 절차를 컨트롤러로 자동화하는 장치입니다.

DB 의 백업이나 페일오버처럼 **절차가 정해진 운영**을 선언적으로 만들 수 있습니다. 다만 직접 만들면 그것 자체를 유지보수하게 되므로, 기존 Operator 로 충분하지 않은지 먼저 검토합니다.

### Q41. サービスメッシュは入れるべきですか？
(서비스 메시 도입 여부)

**🇯🇵 回答**

mTLS、リトライ、サーキットブレーカー、詳細な可視化をアプリのコードを変えずに得られます。サービス数が多いほど効きます。

一方で、**サイドカーの分だけリソースと遅延が増え**、障害の切り分けが一段複雑になります。数個のサービスなら、ライブラリで足りることが多いです。導入するなら、何が欲しくて入れるのかを先に決めます。

**🇰🇷 답변**

mTLS, 재시도, 서킷 브레이커, 상세한 가시화를 앱 코드를 고치지 않고 얻을 수 있습니다. 서비스 수가 많을수록 효과가 큽니다.

한편 **사이드카만큼 리소스와 지연이 늘고** 장애 분리가 한 단계 복잡해집니다. 서비스가 몇 개면 라이브러리로 충분한 경우가 많습니다. 도입한다면 무엇을 얻으려고 넣는지를 먼저 정합니다.

### Q42. サイドカーはどんなときに使いますか？
(사이드카 사용 시점)

**🇯🇵 回答**

本体と生死を共にする補助が要るときです。プロキシ、ログ転送、証明書の更新などです。

注意点は起動と終了の順序でした。**本体より先に落ちると、終了処理が通信できません**。この問題のためにネイティブなサイドカー(初期化コンテナとして常駐させる形)が入ったので、新しいクラスタではそちらを使います。

**🇰🇷 답변**

본체와 생사를 같이하는 보조가 필요할 때입니다. 프록시, 로그 전송, 인증서 갱신 등입니다.

주의점은 기동과 종료 순서였습니다. **본체보다 먼저 죽으면 종료 처리가 통신하지 못합니다.** 이 문제 때문에 네이티브 사이드카(초기화 컨테이너로 상주시키는 형태)가 들어왔으므로 새 클러스터에서는 그쪽을 씁니다.

### Q43. init コンテナは何に使いますか？
(init 컨테이너의 용도)

**🇯🇵 回答**

本体の前に必ず終わらせたい準備に使います。設定の取得、マイグレーションの待機、依存サービスの疎通確認などです。

本体と分けることで、権限やツールを準備段階だけに閉じ込められます。ただし、ここで長く待つと起動が遅くなるので、**待つ理由が本当にあるか**を確認します。DB マイグレーションを全 Pod で走らせると競合するので、Job に分ける方が安全です。

**🇰🇷 답변**

본체 전에 반드시 끝내야 하는 준비에 씁니다. 설정 취득, 마이그레이션 대기, 의존 서비스 소통 확인 등입니다.

본체와 나누면 권한이나 도구를 준비 단계에만 가둘 수 있습니다. 다만 여기서 오래 기다리면 기동이 느려지므로 **기다릴 이유가 정말 있는지** 확인합니다. DB 마이그레이션을 전 Pod 에서 돌리면 경합하므로 Job 으로 나누는 편이 안전합니다.

### Q44. マルチテナントのクラスタで気をつけることは？
(멀티테넌트 클러스터 주의점)

**🇯🇵 回答**

namespace は名前と権限の分離であって、**強い隔離ではありません**。同じノードの上で動くので、ノイジーネイバーの影響を受けます。

なので ResourceQuota と LimitRange で使える量を制限し、NetworkPolicy で通信を絞ります。本当に強い分離が要るなら、ノードプールを分けるかクラスタ自体を分けます。どこまでの分離が必要かを、要件として先に決めます。

**🇰🇷 답변**

네임스페이스는 이름과 권한의 분리이지 **강한 격리가 아닙니다.** 같은 노드 위에서 돌기 때문에 시끄러운 이웃의 영향을 받습니다.

그래서 ResourceQuota 와 LimitRange 로 쓸 수 있는 양을 제한하고 NetworkPolicy 로 통신을 좁힙니다. 정말 강한 격리가 필요하면 노드 풀을 나누거나 클러스터 자체를 나눕니다. 어디까지의 격리가 필요한지를 요건으로 먼저 정합니다.

### Q45. クラスタのアップグレードはどう進めますか？
(클러스터 업그레이드)

**🇯🇵 回答**

コントロールプレーンを先に、ノードを後に上げます。バージョンの差は決められた範囲内に収めます。

事前に確認するのは、**削除された API バージョン**です。マニフェストが古い API を使っていると、上げた瞬間に適用できなくなります。検出するツールがあるので CI に入れます。ノードは一台ずつ drain して入れ替え、PDB で同時停止を制限します。

**🇰🇷 답변**

컨트롤 플레인을 먼저, 노드를 나중에 올립니다. 버전 차이는 정해진 범위 안으로 유지합니다.

사전에 확인할 것은 **제거된 API 버전**입니다. 매니페스트가 옛 API 를 쓰고 있으면 올리는 순간 적용이 안 됩니다. 검출하는 도구가 있으니 CI 에 넣습니다. 노드는 한 대씩 drain 해 교체하고 PDB 로 동시 정지를 제한합니다.

### Q46. コスト最適化はどう進めますか？
(비용 최적화)

**🇯🇵 回答**

まず実際の使用量と requests のずれを見ます。**過大な requests は、使っていない分のノードを買っている**のと同じです。

そのうえで、オートスケールでノードを需要に追随させ、中断されてよいワークロードはスポットに寄せます。ただし可用性を削って安くするのは判断が要るので、**どのワークロードなら落ちてよいか**を先に決めます。

**🇰🇷 답변**

먼저 실제 사용량과 requests 의 차이를 봅니다. **과도한 requests 는 쓰지 않는 만큼의 노드를 사는 것**과 같습니다.

그다음 오토스케일로 노드를 수요에 맞추고, 중단돼도 되는 워크로드는 스팟으로 옮깁니다. 다만 가용성을 깎아 싸게 만드는 것은 판단이 필요하므로 **어느 워크로드가 죽어도 되는지**를 먼저 정합니다.

### Q47. デプロイしたのに反映されないとき、何を疑いますか？
(배포했는데 반영되지 않을 때)

**🇯🇵 回答**

まず新しい Pod が実際に立っているかを見ます。ロールアウトが途中で止まっているなら、readiness が通っていないか、リソースが足りずに Pending です。

次にイメージです。**同じタグを使い回していると、ノードがキャッシュを使って古いものを動かします**。それから、設定を環境変数で渡していて再起動していないケース。この三つでたいてい説明がつきます。

**🇰🇷 답변**

먼저 새 Pod 이 실제로 떠 있는지 봅니다. 롤아웃이 중간에 멈춰 있다면 readiness 가 통과하지 못했거나 리소스가 부족해 Pending 입니다.

다음으로 이미지입니다. **같은 태그를 돌려쓰면 노드가 캐시를 써서 옛것을 돌립니다.** 그리고 설정을 환경변수로 넘겼는데 재시작하지 않은 경우. 이 셋으로 대개 설명이 됩니다.

### Q48. 一部のリクエストだけ遅い、というときはどう調べますか？
(일부 요청만 느릴 때)

**🇯🇵 回答**

まず特定の Pod に偏っているかを見ます。偏っているなら、その Pod のノードが混んでいるか、CPU スロットルが起きている可能性があります。

偏っていないなら、下流の依存かデータ側です。分散トレーシングがあれば、どの区間で時間を使っているかが一発で分かります。**平均ではなくパーセンタイルで見る**ことと、Pod 単位で分けて見ることが要点です。

**🇰🇷 답변**

먼저 특정 Pod 에 몰려 있는지를 봅니다. 몰려 있다면 그 Pod 의 노드가 혼잡하거나 CPU 스로틀이 일어나고 있을 가능성이 있습니다.

몰려 있지 않다면 하류 의존이나 데이터 쪽입니다. 분산 트레이싱이 있으면 어느 구간에서 시간을 쓰는지 한 번에 보입니다. **평균이 아니라 백분위수로 보는 것**과 Pod 단위로 나눠 보는 것이 요점입니다.

### Q49. Kubernetes を入れるべきでないのはどんなときですか？
(쿠버네티스를 넣지 말아야 할 때)

**🇯🇵 回答**

サービスが少なく、運用する人が限られているときです。**クラスタ自体の運用コスト**が、得られる利点を上回ります。

小規模ならマネージドのコンテナ実行環境や PaaS で十分なことが多いです。入れるなら、複数サービスのスケール、自己修復、宣言的な運用のどれが必要なのかを言えるようにします。「みんな使っているから」で入れると、YAML の保守だけが残ります。

**🇰🇷 답변**

서비스가 적고 운영할 사람이 한정적일 때입니다. **클러스터 자체의 운영 비용**이 얻는 이점을 넘어섭니다.

소규모라면 매니지드 컨테이너 실행 환경이나 PaaS 로 충분한 경우가 많습니다. 도입한다면 다중 서비스의 확장, 자기 치유, 선언적 운영 중 무엇이 필요한지를 말할 수 있어야 합니다. "다들 쓰니까"로 넣으면 YAML 유지보수만 남습니다.

### Q50. 障害が起きたとき、まず何をしますか？
(장애 시 첫 대응)

**🇯🇵 回答**

影響範囲の確認と、直近の変更の確認です。**多くの障害は直前のデプロイか設定変更**に紐づいているので、まずそこを疑い、必要なら戻します。

原因究明より復旧が先です。戻したうえで、`describe` のイベント、Pod の状態、リソース、ログの順に見ます。そして、その場の対処と再発防止を分けて記録します。後から読み返せる記録があるかどうかで、次の障害の速さが変わります。

**🇰🇷 답변**

영향 범위 확인과 최근 변경 확인입니다. **많은 장애는 직전의 배포나 설정 변경**에 연결되므로 먼저 거기를 의심하고 필요하면 되돌립니다.

원인 규명보다 복구가 먼저입니다. 되돌린 뒤에 `describe` 의 이벤트, Pod 상태, 리소스, 로그 순으로 봅니다. 그리고 그 자리의 대처와 재발 방지를 나눠 기록합니다. 나중에 되짚을 기록이 있는지에 따라 다음 장애의 속도가 달라집니다.
