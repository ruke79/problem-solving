# Kubernetes 면접 — 필수 문항 지정과 키노트

> **시간이 부족할 때 이 파일만 보면 된다.** 50문항을 세 등급으로 나누고,
> S급에는 **일본어 한 문장**을 붙였다. 그 문장만 외워도 답이 성립한다.
>
> ⚠️ **이 저장소는 Kubernetes 를 검증하지 못했다**(`docs/02` §1-3). 그래서 쿠버네티스 자체의
> 동작에는 실행 근거가 없다. 다만 **JVM 과 컨테이너의 관계**는 확인한 것이 있어
> `CN-04A` 처럼 표시했다 — 면접에서는 **그 둘을 나눠 말하는 것**이 가장 강한 답변이 된다.

## 1. S급 — 반드시 나온다 (10문항)

### ① 프로브와 리소스 — 가장 자주, 그리고 가장 자주 틀린다

**Q11. liveness 와 readiness 의 차이** ★가장 자주 · 함정
> liveness は「死んでいるなら再起動する」、readiness は「準備できていないならトラフィックを送らない」で、役割が全く違います。**liveness に重い依存チェックを入れると、DB が一瞬遅いだけで再起動ループになります**。

**Q13. requests 와 limits 의 차이** ★가장 자주
> requests はスケジューリングで確保する量、limits は超えてはいけない上限です。**CPU の limit を超えるとスロットルされ、メモリの limit を超えると OOMKilled されます** — ここが CPU とメモリで挙動が違う一番大事な点です。

**Q14. limits 와 JVM 의 관계** ★자바 면접에서 특히 · 변별력 최고 ✅`CN-04A`·`CN-04B`
> JVM はコンテナの制限を見て自分を構成するので、**CPU が 1 だとエルゴノミクスがシリアル GC を選びます**。またヒープの外にもメタスペースやスレッドスタックが要るので、コンテナの制限はヒープより十分大きくしないと OOMKilled になります。

**Q27. OOMKilled 가 나오면** ★실무 ✅`JVM-07`
> まず本当に足りないのか、リークなのかを分けます。使用量が右肩上がりならリークです。JVM なら**ヒープの外を忘れていないか**を確認します。ヒープを limit と同じにすると必ず超えます。

---

### ② 트래픽이 흐르는 길

**Q7. Service 는 무엇을 하나** ★가장 자주
> 複数の Pod に対する**安定した宛先**を提供します。Pod は入れ替わるたびに IP が変わるので直接指定できません。セレクタでラベルの合う Pod を集め、各ノードの kube-proxy が転送します。

**Q28. 서비스에 연결이 안 될 때 어디부터 보나** ★실무 · 변별력
> 経路を順にたどります。まず Service のセレクタに合う Pod がいるか、**`Endpoints` が空でないか**を見ます。空ならラベルが合っていないか readiness が通っていません。次にポート、DNS、NetworkPolicy の順です。

---

### ③ 배포와 종료

**Q19. 롤링 업데이트는 어떻게 동작하나** ★가장 자주
> 新しい ReplicaSet を少しずつ増やし、古い方を減らします。**readiness が通るまで新しい Pod にはトラフィックが来ない**ので、readiness を正しく作っていることが前提です。

**Q21. Pod 을 안전하게 종료시키려면** ★실무 함정
> 終了が始まると、Service の宛先から外す処理と SIGTERM の送信が**並行して**起きます。つまり外れる前に落ちると処理中のリクエストが失敗するので、`preStop` で数秒待ってから終了処理に入ります。

---

### ④ 장애 대응 — 반드시 물어본다

**Q26. Pod 이 안 뜰 때 어떻게 조사하나** ★가장 자주
> まず状態を見ます。`Pending` ならスケジュールできていない、`ImagePullBackOff` ならイメージが取れない、`CrashLoopBackOff` なら起動して落ちている。**状態ごとに原因の場所が違います**。

**Q50. 장애가 났을 때 먼저 무엇을 하나** ★시니어면 반드시
> 影響範囲の確認と、**直近の変更の確認**です。多くの障害は直前のデプロイか設定変更に紐づいているので、まずそこを疑い、必要なら戻します。原因究明より復旧が先です。

## 2. A급 — 자주 나온다 (15문항)

| Q | 한 줄 | 근거 |
|---|---|---|
| Q1 | **절차가 아니라 상태를 쓴다** — 컨트롤러가 계속 맞춰 준다 | |
| Q2 | API 서버가 유일한 입구, etcd 가 상태의 전부 → 백업 대상 | |
| Q3 | Pod = 네트워크·스토리지를 공유하는 묶음, 스케줄링의 최소 단위 | |
| Q4 | Deployment → ReplicaSet → Pod. 3층인 건 **신·구 병행**을 위해서 | |
| Q5 | StatefulSet 은 안정된 이름과 전용 볼륨 — 개체 식별이 의미 있을 때만 | |
| Q8 | 외부 공개는 서비스마다 LB 말고 **Ingress 경유** | |
| Q9 | Ingress 는 사양이고 실제 기능은 **컨트롤러 의존** | |
| Q10 | LB → Ingress → Service → Pod. 이 경로 중 어디서 끊겼는지를 가른다 | |
| Q12 | startupProbe 는 **기동 유예와 가동 판정을 분리**한다(JVM 워밍업) | ✅`PERF-04` |
| Q16 | 안티 어피니티로 복제본을 다른 노드·존에 흩는다 | |
| Q17 | Secret 은 **암호화가 아니라 base64** — etcd 암호화와 RBAC 이 필요 | |
| Q20 | 전략 이전에 **되돌릴 수 있게** 해 두는 것이 먼저 | |
| Q22 | HPA 는 requests 가 없으면 CPU 사용률을 못 구한다 | ✅`CN-09A` |
| Q24 | 블록 스토리지는 대개 **한 노드에서만 쓸 수 있다** | |
| Q25 | 네임스페이스는 이름·권한의 분리이지 **강한 격리가 아니다** | |

## 3. B급 — 나오면 가산점 (준비된 사람이 적다)

| Q | 왜 차별점인가 | 근거 |
|---|---|---|
| **Q15 QoS 클래스** | 메모리가 부족하면 **BestEffort 부터 쫓겨난다** | |
| **Q35 축출과 스로틀** | 메모리는 축출, CPU 는 스로틀 — **증상이 다르다** | |
| **Q34 PodDisruptionBudget** | `drain` 때 동시에 내려가는 수를 제한한다 | |
| **Q29 NetworkPolicy** | **CNI 가 대응 안 하면 아무 일도 안 일어난다** | |
| **Q42 사이드카 종료 순서** | 본체보다 먼저 죽으면 종료 처리가 통신을 못 한다 | |
| **Q45 제거된 API 버전** | 업그레이드 전에 매니페스트를 검사한다 | |
| **Q46 과도한 requests** | **쓰지 않는 만큼의 노드를 사는 것**과 같다 | |
| **Q49 안 넣어야 할 때** | "클러스터 운영 비용이 이점을 넘는다"고 말할 수 있으면 신뢰가 올라간다 | |

## 4. 면접 30분 전 최종 점검 — 이것만은

**여섯 개의 "아니오"** 를 기억하면 함정 질문은 대부분 막힙니다.

| 질문의 유혹 | 정답 |
|---|---|
| liveness 에 DB 확인을 넣어도 되나? | **아니오** — 재시작 루프가 된다 (Q11) |
| 메모리 limit 을 힙과 같게 잡아도 되나? | **아니오** — 힙 밖에서 넘친다 (Q14 ✅`JVM-07`) |
| CPU limit 을 넘으면 Pod 이 죽나? | **아니오** — CPU 는 스로틀, 죽는 건 메모리 (Q13·Q35) |
| 이미지 태그를 `latest` 로 써도 되나? | **아니오** — 무엇이 도는지 알 수 없다 (Q32) |
| 네임스페이스로 나누면 격리되나? | **아니오** — 같은 노드 위에서 돈다 (Q25·Q44) |
| Pod 이 삭제되면 곧바로 트래픽이 끊기나? | **아니오** — 엔드포인트 제거와 SIGTERM 이 **병행**된다 (Q21) |

**그리고 하나의 "예"** — *CPU 1개 컨테이너의 JVM 은 SerialGC 로 뜹니다.* (Q14 ✅`CN-04A`)

## 5. 답변할 때의 태도 — 이 세트는 특히 중요합니다

**쿠버네티스 자체의 동작은 이 저장소에서 검증하지 못했습니다.** 그러니 말하는 방식을 나눠야 합니다.

- ✅ 좋은 예 — "컨테이너에 CPU 1개를 주면 JVM 이 SerialGC 를 고르는 것은 **직접 재 봤고**,
  쿠버네티스의 축출 순서는 **문서 기준으로는** BestEffort 부터입니다."
- ❌ 나쁜 예 — 둘을 섞어서 전부 경험한 것처럼 말하기. 되물으면 바로 드러납니다.

**그리고 이 세트에는 수치를 쓰지 않았습니다.** 재지 않은 숫자를 인용하지 않기 위해서입니다.
모르면 "재 본 적은 없지만, 저라면 `describe` 의 이벤트부터 보겠습니다" 가 훨씬 좋은 인상을 줍니다.
