### Q31. `List`・`Set`・`Map` の違いを説明してください。
(List·Set·Map 의 차이)

**🇯🇵 回答**

`List` は順序があり重複を許すコレクション、`Set` は重複を許さないコレクション、`Map` はキーと値の組を保持するものです。

`Map` は厳密には `Collection` インターフェースを継承していません。キーの集合、値の集合、エントリの集合として取り出せるという形で関わっています。

**🇰🇷 답변**

`List` 는 순서가 있고 중복을 허용하는 컬렉션, `Set` 은 중복을 허용하지 않는 컬렉션, `Map` 은 키와 값의 쌍을 보유하는 것입니다.

`Map` 은 엄밀히는 `Collection` 인터페이스를 상속하지 않습니다. 키 집합·값 집합·엔트리 집합으로 꺼낼 수 있다는 형태로 관계를 맺고 있습니다.

### Q32. `ArrayList` と `LinkedList` はどう使い分けますか？
(ArrayList 와 LinkedList 의 사용 구분)

**🇯🇵 回答**

`ArrayList` は内部が配列なのでインデックスアクセスが O(1)、途中への挿入削除は要素の移動が必要です。`LinkedList` は逆で、ノードの繋ぎ替えだけなら O(1) ですが、位置を探すのに O(n) かかります。

ただし実務ではほぼ `ArrayList` を選びます。`LinkedList` は理論上有利でも、ノードごとにオブジェクトが増えてキャッシュ効率が悪く、実測では負けることが多いからです。

**🇰🇷 답변**

`ArrayList` 는 내부가 배열이라 인덱스 접근이 O(1), 중간 삽입·삭제는 요소 이동이 필요합니다. `LinkedList` 는 반대로 노드 연결만 바꾸면 O(1) 이지만 위치를 찾는 데 O(n) 이 걸립니다.

다만 실무에서는 거의 `ArrayList` 를 고릅니다. `LinkedList` 는 이론상 유리해도 노드마다 객체가 늘어 캐시 효율이 나쁘고, 실측에서는 지는 경우가 많기 때문입니다.

### Q33. `ArrayList` の容量はどう増えますか？初期容量を指定する意味は？
(ArrayList 의 용량은 어떻게 늘어나나, 초기 용량 지정의 의미)

**🇯🇵 回答**

満杯になると約1.5倍の新しい配列を作り、既存要素をコピーします。つまり拡張のたびに配列のコピーが走ります。

入る件数が事前に分かっているなら初期容量を指定します。数万件を入れると分かっているのにデフォルトの10から始めると、コピーが何度も繰り返されます。`HashMap` も同じ考え方です。

**🇰🇷 답변**

가득 차면 약 1.5배 크기의 새 배열을 만들어 기존 요소를 복사합니다. 즉 확장할 때마다 배열 복사가 일어납니다.

들어갈 건수를 미리 안다면 초기 용량을 지정합니다. 수만 건이 들어갈 걸 알면서 기본값 10에서 시작하면 복사가 여러 번 반복됩니다. `HashMap` 도 같은 사고방식입니다.

### Q34. `HashSet` はどうやって重複を判定しますか？
(HashSet 은 어떻게 중복을 판정하나)

**🇯🇵 回答**

内部は `HashMap` で、要素をキーとして保持しています。判定は `hashCode()` でバケットを絞り、その中で `equals()` を比較する二段構えです。

だから `equals` と `hashCode` を正しく実装していないオブジェクトを入れると、同じ内容なのに重複して入ってしまいます。Part 1 の Q2 とそのまま繋がる話です。

**🇰🇷 답변**

내부는 `HashMap` 이고 요소를 키로 보유합니다. 판정은 `hashCode()` 로 버킷을 좁히고, 그 안에서 `equals()` 를 비교하는 2단 구조입니다.

그래서 `equals` 와 `hashCode` 를 제대로 구현하지 않은 객체를 넣으면 같은 내용인데도 중복해서 들어갑니다. Part 1 의 Q2 와 그대로 이어지는 이야기입니다.

### Q35. `HashMap` の内部構造と `put` の流れを説明してください。
(HashMap 의 내부 구조와 put 의 흐름)

**🇯🇵 回答**

内部はバケットの配列です。`put` ではまずキーの `hashCode()` を取り、上位ビットを混ぜる補助ハッシュをかけてから、配列長との `AND` でインデックスを決めます。

そのバケットが空なら新しいノードを置き、既に何かあれば `equals()` で同じキーを探し、あれば値を上書き、なければ末尾に追加します。要素数が閾値を超えるとリサイズします。

**🇰🇷 답변**

내부는 버킷의 배열입니다. `put` 에서는 먼저 키의 `hashCode()` 를 얻고, 상위 비트를 섞는 보조 해시를 적용한 뒤 배열 길이와의 `AND` 로 인덱스를 정합니다.

그 버킷이 비어 있으면 새 노드를 놓고, 이미 뭔가 있으면 `equals()` 로 같은 키를 찾아 있으면 값을 덮어쓰고 없으면 끝에 추가합니다. 요소 수가 임계값을 넘으면 리사이즈합니다.

### Q36. ハッシュ衝突が起きるとどうなりますか？
(해시 충돌이 나면 어떻게 되나)

**🇯🇵 回答**

同じバケットに連結リストとして繋がります。衝突が多いとこのリストが長くなり、検索が O(n) に近づきます。

Java 8 からは、一つのバケットのノードが8個を超え、かつ配列長が64以上ならレッドブラックツリーに変換されます。これで最悪ケースが O(log n) に抑えられます。悪意あるキーで衝突を意図的に起こす攻撃への対策でもあります。

**🇰🇷 답변**

같은 버킷에 연결 리스트로 이어집니다. 충돌이 많으면 이 리스트가 길어져 검색이 O(n) 에 가까워집니다.

Java 8 부터는 한 버킷의 노드가 8개를 넘고 배열 길이가 64 이상이면 레드블랙 트리로 변환됩니다. 이걸로 최악 케이스가 O(log n) 으로 억제됩니다. 악의적인 키로 충돌을 의도적으로 일으키는 공격에 대한 대책이기도 합니다.

### Q37. `HashMap` のリサイズはいつ、どのように起きますか？
(HashMap 의 리사이즈는 언제 어떻게 일어나나)

**🇯🇵 回答**

要素数が「容量 × 負荷係数」を超えたときです。負荷係数のデフォルトは0.75なので、容量16なら13件目で発生します。

リサイズでは配列を2倍にして全要素を再配置します。これがコストなので、件数が読めるなら初期容量を指定します。`new HashMap<>(expected / 0.75 + 1)` のように見積もるのが定石です。

**🇰🇷 답변**

요소 수가 "용량 × 부하율"을 넘었을 때입니다. 부하율 기본값이 0.75 이므로 용량 16이면 13번째에 발생합니다.

리사이즈에서는 배열을 2배로 늘리고 전 요소를 재배치합니다. 이게 비용이므로 건수를 예측할 수 있으면 초기 용량을 지정합니다. `new HashMap<>(expected / 0.75 + 1)` 처럼 잡는 것이 정석입니다.

### Q38. `HashMap` のキーに可変オブジェクトを使うとどうなりますか？
(HashMap 의 키로 가변 객체를 쓰면 어떻게 되나)

**🇯🇵 回答**

`put` した後にキーのフィールドを変更すると、`hashCode` が変わってしまい、そのエントリを二度と取り出せなくなります。

バケットの位置は `put` 時のハッシュで決まっているのに、`get` では新しいハッシュで探しにいくからです。だからキーには不変オブジェクトを使うのが原則です。`String` がキーとして好まれる理由の一つでもあります。

**🇰🇷 답변**

`put` 한 뒤에 키의 필드를 변경하면 `hashCode` 가 바뀌어 그 엔트리를 두 번 다시 꺼낼 수 없게 됩니다.

버킷 위치는 `put` 시점의 해시로 정해졌는데 `get` 에서는 새 해시로 찾아가기 때문입니다. 그래서 키에는 불변 객체를 쓰는 것이 원칙입니다. `String` 이 키로 선호되는 이유 중 하나이기도 합니다.

### Q39. `HashMap` と `Hashtable` と `ConcurrentHashMap` の違いは？
(HashMap·Hashtable·ConcurrentHashMap 의 차이)

**🇯🇵 回答**

`HashMap` は同期化されておらず、`null` のキーと値を許します。`Hashtable` は全メソッドが `synchronized` で、`null` を許しません。今は使いません。

`ConcurrentHashMap` は現実的な選択肢で、テーブル全体ではなくバケット単位でロックするため、`Hashtable` よりはるかにスケールします。読み取りは基本的にロックなしです。

**🇰🇷 답변**

`HashMap` 은 동기화되어 있지 않고 `null` 키와 값을 허용합니다. `Hashtable` 은 모든 메서드가 `synchronized` 이고 `null` 을 허용하지 않습니다. 지금은 쓰지 않습니다.

`ConcurrentHashMap` 이 현실적인 선택지로, 테이블 전체가 아니라 버킷 단위로 락을 걸기 때문에 `Hashtable` 보다 훨씬 잘 확장됩니다. 읽기는 기본적으로 락이 없습니다.

### Q40. `ConcurrentHashMap` を使っていれば `get` してから `put` する処理も安全ですか？
(ConcurrentHashMap 을 쓰면 get 후 put 하는 처리도 안전한가)

**🇯🇵 回答**

いいえ、安全ではありません。個々のメソッドはアトミックですが、`get` して判断して `put` するという**組み合わせはアトミックではありません**。その間に他のスレッドが割り込めます。

カウンタの更新などはこれで壊れます。`compute`、`merge`、`putIfAbsent` のような複合操作用のメソッドを使う必要があります。

**🇰🇷 답변**

아니요, 안전하지 않습니다. 개별 메서드는 원자적이지만, `get` 해서 판단하고 `put` 하는 **조합은 원자적이지 않습니다.** 그 사이에 다른 스레드가 끼어들 수 있습니다.

카운터 갱신 같은 것이 이걸로 깨집니다. `compute`, `merge`, `putIfAbsent` 같은 복합 연산용 메서드를 써야 합니다.

### Q41. `LinkedHashMap` はどんなときに使いますか？
(LinkedHashMap 은 언제 쓰나)

**🇯🇵 回答**

挿入順、あるいはアクセス順を保ちたいときです。内部で双方向リンクを持っているので、イテレーションの順序が保証されます。

実務で効くのは LRU キャッシュです。アクセス順モードにして `removeEldestEntry` をオーバーライドすると、数行で上限付きの LRU が作れます。

**🇰🇷 답변**

삽입 순서, 혹은 접근 순서를 유지하고 싶을 때입니다. 내부에 양방향 링크를 갖고 있어 순회 순서가 보장됩니다.

실무에서 효과가 큰 것은 LRU 캐시입니다. 접근 순서 모드로 하고 `removeEldestEntry` 를 오버라이드하면 몇 줄로 상한이 있는 LRU 를 만들 수 있습니다.

### Q42. `TreeMap` の特徴と使いどころは？
(TreeMap 의 특징과 쓰임새)

**🇯🇵 回答**

レッドブラックツリーで実装されていて、キーが常にソートされた状態で保持されます。取得や挿入は O(log n) なので `HashMap` より遅いです。

使うのは順序が意味を持つときです。範囲検索が必要な場合、`headMap`・`tailMap`・`subMap` や `floorKey`・`ceilingKey` が使えるのが `HashMap` にない強みです。

**🇰🇷 답변**

레드블랙 트리로 구현되어 있어 키가 항상 정렬된 상태로 유지됩니다. 조회나 삽입이 O(log n) 이라 `HashMap` 보다 느립니다.

쓰는 것은 순서가 의미를 가질 때입니다. 범위 검색이 필요한 경우 `headMap`·`tailMap`·`subMap` 이나 `floorKey`·`ceilingKey` 를 쓸 수 있는 것이 `HashMap` 에 없는 강점입니다.

### Q43. `Comparable` と `Comparator` の違いは？
(Comparable 과 Comparator 의 차이)

**🇯🇵 回答**

`Comparable` はクラス自身が持つ「自然順序」で、`compareTo` を実装します。`Comparator` は外部から与える比較ルールで、一つのクラスに対して複数定義できます。

だから、そのクラス本来の順序が一つに決まるなら `Comparable`、画面や用途ごとに並び順を変えたいなら `Comparator` を使います。後者は `Comparator.comparing(...).thenComparing(...)` で組み立てられます。

**🇰🇷 답변**

`Comparable` 은 클래스 자신이 갖는 "자연 순서"로 `compareTo` 를 구현합니다. `Comparator` 는 외부에서 주는 비교 규칙으로, 한 클래스에 대해 여러 개 정의할 수 있습니다.

그래서 그 클래스 본래의 순서가 하나로 정해지면 `Comparable`, 화면이나 용도마다 정렬을 바꾸고 싶으면 `Comparator` 를 씁니다. 후자는 `Comparator.comparing(...).thenComparing(...)` 으로 조립할 수 있습니다.

### Q44. `compareTo` と `equals` の整合性はなぜ重要ですか？
(compareTo 와 equals 의 정합성이 왜 중요한가)

**🇯🇵 回答**

`TreeSet` や `TreeMap` は `equals` ではなく `compareTo` の結果で同一性を判断するからです。

`compareTo` が0を返すのに `equals` が `false` を返す実装だと、`TreeSet` では重複扱いで弾かれるのに `HashSet` では両方入る、という食い違いが起きます。`Set` の契約に反する状態です。だから両者は一致させるのが原則です。

**🇰🇷 답변**

`TreeSet` 이나 `TreeMap` 은 `equals` 가 아니라 `compareTo` 의 결과로 동일성을 판단하기 때문입니다.

`compareTo` 가 0을 반환하는데 `equals` 가 `false` 를 반환하는 구현이면, `TreeSet` 에서는 중복으로 걸러지는데 `HashSet` 에서는 둘 다 들어가는 어긋남이 생깁니다. `Set` 의 계약에 어긋나는 상태입니다. 그래서 둘은 일치시키는 것이 원칙입니다.

### Q45. `ConcurrentModificationException` はなぜ起きますか？
(ConcurrentModificationException 은 왜 나나)

**🇯🇵 回答**

イテレーション中にコレクションを直接変更したからです。イテレータが持っている変更回数と、コレクション側の変更回数がずれると投げられます。

これは fail-fast といって、壊れた状態で処理を続けるより早く落とす設計です。ループ中に削除したいなら `iterator.remove()` を使うか、`removeIf` を使います。名前に反して、単一スレッドでも起きます。

**🇰🇷 답변**

순회 중에 컬렉션을 직접 변경했기 때문입니다. 이터레이터가 가진 변경 횟수와 컬렉션 쪽 변경 횟수가 어긋나면 던져집니다.

이건 fail-fast 라고 해서, 깨진 상태로 처리를 계속하는 것보다 빨리 실패시키는 설계입니다. 루프 중에 삭제하려면 `iterator.remove()` 를 쓰거나 `removeIf` 를 씁니다. 이름과 달리 단일 스레드에서도 발생합니다.

### Q46. `Arrays.asList()` で作ったリストに `add` するとどうなりますか？
(Arrays.asList() 로 만든 리스트에 add 하면 어떻게 되나)

**🇯🇵 回答**

`UnsupportedOperationException` が出ます。返ってくるのは元の配列をラップした固定長のビューで、`ArrayList` ではないからです。

要素の置き換えはできますが、サイズは変えられません。可変にしたいなら `new ArrayList<>(Arrays.asList(...))` と包み直します。`List.of()` はさらに厳しく、置き換えもできない完全な不変リストです。

**🇰🇷 답변**

`UnsupportedOperationException` 이 납니다. 돌아오는 것은 원래 배열을 감싼 고정 길이 뷰이고 `ArrayList` 가 아니기 때문입니다.

요소 교체는 되지만 크기는 바꿀 수 없습니다. 가변으로 만들려면 `new ArrayList<>(Arrays.asList(...))` 로 다시 감쌉니다. `List.of()` 는 더 엄격해서 교체도 안 되는 완전한 불변 리스트입니다.

### Q47. `List.of()` と `Collections.unmodifiableList()` の違いは？
(List.of() 와 Collections.unmodifiableList() 의 차이)

**🇯🇵 回答**

`List.of()` は要素をコピーして本当に不変なリストを作ります。`Collections.unmodifiableList()` は元のリストへの読み取り専用ビューを返すだけです。

だから後者は、**元のリストを書き換えるとビュー側も変わります**。防御的に不変を保証したいときは `List.of()` か `List.copyOf()` を使うべきです。`List.of()` は `null` 要素を許さない点も違います。

**🇰🇷 답변**

`List.of()` 는 요소를 복사해 진짜 불변 리스트를 만듭니다. `Collections.unmodifiableList()` 는 원래 리스트에 대한 읽기 전용 뷰를 반환할 뿐입니다.

그래서 후자는 **원래 리스트를 바꾸면 뷰 쪽도 바뀝니다.** 방어적으로 불변을 보장하고 싶으면 `List.of()` 나 `List.copyOf()` 를 써야 합니다. `List.of()` 는 `null` 요소를 허용하지 않는 점도 다릅니다.

### Q48. `Iterator` と `ListIterator` の違いは？
(Iterator 와 ListIterator 의 차이)

**🇯🇵 回答**

`Iterator` は前方向のみで `remove` だけができます。`ListIterator` は `List` 専用で、双方向に動け、`add` と `set` もできます。

実務では、ループ中に要素を置き換えたい場合に `ListIterator` を使います。ただし多くの場合はストリームか `replaceAll` の方が読みやすいので、そちらを先に検討します。

**🇰🇷 답변**

`Iterator` 는 앞 방향으로만 가고 `remove` 만 할 수 있습니다. `ListIterator` 는 `List` 전용으로 양방향으로 움직일 수 있고 `add` 와 `set` 도 됩니다.

실무에서는 루프 중에 요소를 교체하고 싶을 때 `ListIterator` 를 씁니다. 다만 대부분은 스트림이나 `replaceAll` 이 읽기 쉬우므로 그쪽을 먼저 검토합니다.

### Q49. `Queue`・`Deque`・`Stack` の使い分けは？
(Queue·Deque·Stack 의 사용 구분)

**🇯🇵 回答**

FIFO なら `Queue`、両端から出し入れするなら `Deque` です。`Stack` クラスは `Vector` を継承していて全メソッドが同期化されているため、今は使いません。

LIFO が必要なら `ArrayDeque` を使います。スタックとしてもキューとしても速く、これが現在の標準的な選択です。

**🇰🇷 답변**

FIFO 면 `Queue`, 양쪽 끝에서 넣고 빼면 `Deque` 입니다. `Stack` 클래스는 `Vector` 를 상속해 모든 메서드가 동기화되어 있어 지금은 쓰지 않습니다.

LIFO 가 필요하면 `ArrayDeque` 를 씁니다. 스택으로도 큐로도 빠르고, 이것이 현재의 표준적인 선택입니다.

---

### Q50. `BlockingQueue` はどんな場面で使いますか？
(BlockingQueue 는 어떤 상황에서 쓰나)

**🇯🇵 回答**

生産者と消費者を分離するときです。キューが空なら取り出し側が、満杯なら投入側が自動的に待つので、待ち合わせのコードを自分で書かなくて済みます。

容量に上限を付けられるのが重要です。無制限だと、消費が追いつかないときにキューが膨らみ続けて `OutOfMemoryError` になります。スレッドプールのタスクキューもこれです。

**🇰🇷 답변**

생산자와 소비자를 분리할 때입니다. 큐가 비면 꺼내는 쪽이, 가득 차면 넣는 쪽이 자동으로 대기하므로 대기 코드를 직접 쓰지 않아도 됩니다.

용량에 상한을 둘 수 있는 것이 중요합니다. 무제한이면 소비가 못 따라갈 때 큐가 계속 부풀어 `OutOfMemoryError` 가 납니다. 스레드풀의 작업 큐도 이것입니다.

### Q51. `Collections.synchronizedList()` を使えばスレッドセーフですか？
(Collections.synchronizedList() 를 쓰면 스레드 세이프한가)

**🇯🇵 回答**

個々のメソッドはスレッドセーフになりますが、**イテレーションは別です**。ループの間は自分で `synchronized` ブロックを書く必要があります。

さらに、全メソッドが同じロックを取るのでスケールしません。読み取りが多いなら `CopyOnWriteArrayList`、マップなら `ConcurrentHashMap` のように、並行用に設計されたコレクションを選ぶ方が現実的です。

**🇰🇷 답변**

개별 메서드는 스레드 세이프해지지만 **순회는 별개입니다.** 루프 동안은 직접 `synchronized` 블록을 써야 합니다.

게다가 모든 메서드가 같은 락을 잡으므로 확장되지 않습니다. 읽기가 많으면 `CopyOnWriteArrayList`, 맵이면 `ConcurrentHashMap` 처럼 병행용으로 설계된 컬렉션을 고르는 편이 현실적입니다.

### Q52. `CopyOnWriteArrayList` はどんなときに適していますか？
(CopyOnWriteArrayList 는 언제 적합한가)

**🇯🇵 回答**

読み取りが圧倒的に多く、書き込みが稀な場合です。書き込みのたびに配列全体をコピーするので、書き込みが多いと非常に重くなります。

代表的な用途はリスナーの登録リストです。登録は起動時にほぼ終わり、その後はイベントごとに読むだけ、という形が理想的です。読み取りはロックなしで済みます。

**🇰🇷 답변**

읽기가 압도적으로 많고 쓰기가 드문 경우입니다. 쓸 때마다 배열 전체를 복사하므로 쓰기가 많으면 매우 무거워집니다.

대표적인 용도는 리스너 등록 리스트입니다. 등록은 기동 시에 거의 끝나고 이후에는 이벤트마다 읽기만 하는 형태가 이상적입니다. 읽기는 락 없이 됩니다.

### Q53. `Set` から重複を除くとき、順序を保ちたい場合はどうしますか？
(Set 으로 중복을 제거할 때 순서를 유지하려면)

**🇯🇵 回答**

`LinkedHashSet` を使います。`HashSet` は順序を保証せず、`TreeSet` はソート順になってしまうので、元の登場順を保ちたいならこれが唯一の選択肢です。

ストリームなら `Collectors.toCollection(LinkedHashSet::new)` を指定します。`distinct()` も出現順を保つので、単純な重複排除ならそちらの方が簡潔です。

**🇰🇷 답변**

`LinkedHashSet` 을 씁니다. `HashSet` 은 순서를 보장하지 않고 `TreeSet` 은 정렬 순서가 되어 버리므로, 원래 등장 순서를 유지하려면 이것이 유일한 선택지입니다.

스트림이면 `Collectors.toCollection(LinkedHashSet::new)` 를 지정합니다. `distinct()` 도 출현 순서를 유지하므로 단순 중복 제거라면 그쪽이 간결합니다.

### Q54. `Map` を走査するとき `keySet` と `entrySet` のどちらを使いますか？
(Map 순회에서 keySet 과 entrySet 중 무엇을 쓰나)

**🇯🇵 回答**

値も必要なら必ず `entrySet` です。`keySet` で回して中で `get` を呼ぶと、要素数の分だけ余計な検索が走ります。

`entrySet` ならキーと値を一度に取れるのでその無駄がありません。キーだけしか使わない場合に限って `keySet` を使います。

**🇰🇷 답변**

값도 필요하면 반드시 `entrySet` 입니다. `keySet` 으로 돌면서 안에서 `get` 을 부르면 요소 수만큼 불필요한 검색이 일어납니다.

`entrySet` 이면 키와 값을 한 번에 얻을 수 있어 그 낭비가 없습니다. 키만 쓰는 경우에 한해 `keySet` 을 씁니다.

### Q55. コレクションに `null` を入れることの是非は？
(컬렉션에 null 을 넣는 것의 시비)

**🇯🇵 回答**

避けるべきだと考えています。`null` が入ると、取り出したすべての箇所で `null` チェックが必要になり、意味も曖昧になります。「値がない」のか「未設定」なのか区別できません。

実際、`List.of()` や `ConcurrentHashMap` は `null` を許しません。値がないことを表したいなら空のコレクションか `Optional` を使い、`null` は入れない方針にしています。

**🇰🇷 답변**

피해야 한다고 생각합니다. `null` 이 들어가면 꺼내는 모든 지점에서 `null` 체크가 필요해지고 의미도 모호해집니다. "값이 없다"인지 "미설정"인지 구별할 수 없습니다.

실제로 `List.of()` 나 `ConcurrentHashMap` 은 `null` 을 허용하지 않습니다. 값이 없음을 나타내고 싶으면 빈 컬렉션이나 `Optional` 을 쓰고, `null` 은 넣지 않는 방침으로 하고 있습니다.
