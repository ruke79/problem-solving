### Q86. JVMのランタイムデータ領域を説明してください。
(JVM 런타임 데이터 영역)

**🇯🇵 回答**

大きく五つです。全スレッドで共有するのがヒープとメソッド領域、スレッドごとに持つのがJVMスタック、PCレジスタ、ネイティブメソッドスタックです。

オブジェクトはヒープに置かれ、GCの対象になります。ローカル変数と参照はスタックに積まれ、メソッドが終われば自動で消えます。この二つの区別が分かっていると、メモリ問題の切り分けが速くなります。

**🇰🇷 답변**

크게 다섯 개입니다. 모든 스레드가 공유하는 것이 힙과 메서드 영역, 스레드마다 갖는 것이 JVM 스택, PC 레지스터, 네이티브 메서드 스택입니다.

객체는 힙에 놓이고 GC 대상이 됩니다. 지역 변수와 참조는 스택에 쌓이고 메서드가 끝나면 자동으로 사라집니다. 이 둘의 구별을 알고 있으면 메모리 문제의 切り分け가 빨라집니다.

### Q87. クラスローダーの委譲モデルとは何ですか？
(클래스로더의 위임 모델이란)

**🇯🇵 回答**

クラスをロードする要求が来たら、まず親のローダーに委譲し、親が見つけられなかったときだけ自分がロードする仕組みです。ブートストラップ、プラットフォーム、アプリケーションの順に上から探します。

目的は安全性です。自作の `java.lang.String` を置いても、先に本物が見つかるので置き換えられません。逆に、この仕組みを理解していないと同じクラスが別ローダーで二重にロードされ、`ClassCastException` の原因になります。

**🇰🇷 답변**

클래스를 로드하라는 요청이 오면 먼저 부모 로더에 위임하고, 부모가 못 찾았을 때만 자신이 로드하는 구조입니다. 부트스트랩, 플랫폼, 애플리케이션 순으로 위에서부터 찾습니다.

목적은 안전성입니다. 직접 만든 `java.lang.String` 을 놓아도 진짜가 먼저 발견되므로 대체되지 않습니다. 반대로 이 구조를 이해하지 못하면 같은 클래스가 다른 로더로 이중 로드되어 `ClassCastException` 의 원인이 됩니다.

### Q88. GCはどうやって「不要なオブジェクト」を判断しますか？
(GC 는 어떻게 "불필요한 객체"를 판단하나)

**🇯🇵 回答**

参照カウントではなく、到達可能性で判断します。GCルートから参照を辿っていって、到達できなかったオブジェクトを回収対象とします。

GCルートになるのは、スタック上のローカル変数、静的フィールド、JNIの参照などです。参照カウント方式ではないので、**循環参照だけで回収されないということはありません**。

**🇰🇷 답변**

참조 카운트가 아니라 도달 가능성으로 판단합니다. GC 루트에서 참조를 따라가서 도달하지 못한 객체를 회수 대상으로 삼습니다.

GC 루트가 되는 것은 스택 위의 지역 변수, 정적 필드, JNI 참조 등입니다. 참조 카운트 방식이 아니므로 **순환 참조만으로 회수되지 않는 일은 없습니다.**

### Q89. なぜヒープを世代(Young/Old)に分けるのですか？
(왜 힙을 세대로 나누나)

**🇯🇵 回答**

「ほとんどのオブジェクトはすぐ死ぬ」という経験則があるからです。弱世代仮説と呼ばれます。

新しい領域だけを頻繁に、狭く回収すれば、生き残っている少数だけをコピーすればよいので非常に速く済みます。全体を毎回スキャンするより圧倒的に効率的です。長生きしたものだけをOld領域に移し、そちらはたまにしか回収しません。

**🇰🇷 답변**

"대부분의 객체는 금방 죽는다"는 경험칙이 있기 때문입니다. 약한 세대 가설이라고 합니다.

새 영역만 자주, 좁게 회수하면 살아남은 소수만 복사하면 되므로 매우 빠릅니다. 전체를 매번 스캔하는 것보다 압도적으로 효율적입니다. 오래 산 것만 Old 영역으로 옮기고, 그쪽은 가끔만 회수합니다.

### Q90. Minor GC と Full GC の違いは？
(Minor GC 와 Full GC 의 차이)

**🇯🇵 回答**

Minor GC は Young 領域だけを対象にし、生存オブジェクトが少ないので短時間で終わります。Full GC は Old 領域まで含めた全体が対象で、停止時間がずっと長くなります。

だから運用で見るべきなのは**Full GCの頻度と時間**です。Minor GCが頻繁なのは正常ですが、Full GCが数秒単位で繰り返されているなら、メモリリークかヒープ不足を疑います。

**🇰🇷 답변**

Minor GC 는 Young 영역만 대상으로 하고 생존 객체가 적어 짧게 끝납니다. Full GC 는 Old 영역까지 포함한 전체가 대상이라 정지 시간이 훨씬 깁니다.

그래서 운영에서 봐야 하는 것은 **Full GC 의 빈도와 시간**입니다. Minor GC 가 잦은 것은 정상이지만, Full GC 가 수 초 단위로 반복되고 있다면 메모리 누수나 힙 부족을 의심합니다.

### Q91. Stop-The-World とは何ですか？
(Stop-The-World 란)

**🇯🇵 回答**

GCの実行中にアプリケーションのスレッドを全て止めることです。参照関係が動いている最中に回収すると整合性が取れないので、安全な地点で揃えて止めます。

現代のGCはこの時間を短くする方向に進化していますが、**ゼロにはできません**。だからレイテンシが重要なシステムでは、停止時間の合計ではなく最大値を見る必要があります。

**🇰🇷 답변**

GC 실행 중에 애플리케이션 스레드를 전부 멈추는 것입니다. 참조 관계가 움직이는 도중에 회수하면 정합성이 맞지 않으므로, 안전한 지점에서 맞춰 멈춥니다.

현대의 GC 는 이 시간을 줄이는 방향으로 진화했지만 **0으로는 만들 수 없습니다.** 그래서 지연이 중요한 시스템에서는 정지 시간의 합계가 아니라 최댓값을 봐야 합니다.

### Q92. G1GC の特徴は何ですか？
(G1GC 의 특징)

**🇯🇵 回答**

ヒープを固定サイズのリージョンに分割し、世代をリージョンの集合として扱います。そしてゴミの多いリージョンから優先的に回収します。Garbage First という名前の由来です。

最大の利点は、`MaxGCPauseMillis` で停止時間の目標を指定できることです。ただし目標はあくまでヒントで、守れないこともあります。Java 9 以降のデフォルトです。

**🇰🇷 답변**

힙을 고정 크기 리전으로 분할하고, 세대를 리전의 집합으로 다룹니다. 그리고 쓰레기가 많은 리전부터 우선 회수합니다. Garbage First 라는 이름의 유래입니다.

가장 큰 이점은 `MaxGCPauseMillis` 로 정지 시간 목표를 지정할 수 있다는 것입니다. 다만 목표는 어디까지나 힌트라 지키지 못하는 경우도 있습니다. Java 9 이후의 기본값입니다.

### Q93. G1GC で humongous object が問題になるのはなぜですか？
(G1GC 에서 거대 객체가 문제가 되는 이유)

**🇯🇵 回答**

リージョンサイズの半分を超えるオブジェクトは humongous object として扱われ、通常の割り当て経路を通らずに Old 領域へ直接置かれます。

そのため、大きな配列を頻繁に作るとOld領域が急速に埋まり、Full GCを誘発します。対策はリージョンサイズを大きくするか、そもそも巨大なオブジェクトを作らない設計に変えることです。

**🇰🇷 답변**

리전 크기의 절반을 넘는 객체는 거대 객체로 다뤄져, 통상의 할당 경로를 거치지 않고 Old 영역에 직접 놓입니다.

그래서 큰 배열을 자주 만들면 Old 영역이 급속히 차서 Full GC 를 유발합니다. 대책은 리전 크기를 키우거나, 애초에 거대한 객체를 만들지 않는 설계로 바꾸는 것입니다.

### Q94. GCアルゴリズムはどう選びますか？
(GC 알고리즘은 어떻게 고르나)

**🇯🇵 回答**

まず変えないのが基本です。デフォルトのG1で問題が出ていないなら触りません。

その上で、スループット最優先でバッチのように多少の停止を許せるならParallel、停止時間を極限まで短くしたく、大きなヒープを使うならZGCやShenandoahを検討します。ただし**必ず変更前後を計測して比較**します。書籍の推奨をそのまま当てはめるのは危険です。

**🇰🇷 답변**

먼저 바꾸지 않는 것이 기본입니다. 기본값인 G1 로 문제가 없다면 건드리지 않습니다.

그 위에서, 처리량 최우선이고 배치처럼 다소의 정지를 허용할 수 있으면 Parallel, 정지 시간을 극한까지 줄이고 싶고 큰 힙을 쓴다면 ZGC 나 Shenandoah 를 검토합니다. 다만 **반드시 변경 전후를 측정해 비교합니다.** 책의 권장을 그대로 적용하는 것은 위험합니다.

### Q95. GCログでは何を見ますか？
(GC 로그에서 무엇을 보나)

**🇯🇵 回答**

三つ見ます。Full GCの頻度と停止時間、GCの後にヒープ使用量が下がっているか、そして経過時間に対するGC時間の割合です。

特に重要なのが二つ目です。**Full GCの後も使用量が下がらず、右肩上がりに増えていくならメモリリーク**です。GCログは本番でも常時有効にしておくべきで、オーバーヘッドはほとんどありません。

**🇰🇷 답변**

세 가지를 봅니다. Full GC 의 빈도와 정지 시간, GC 후에 힙 사용량이 내려가는지, 그리고 경과 시간 대비 GC 시간의 비율입니다.

특히 중요한 것이 두 번째입니다. **Full GC 후에도 사용량이 내려가지 않고 우상향으로 늘어난다면 메모리 누수**입니다. GC 로그는 프로덕션에서도 상시 켜 두어야 하고, 오버헤드는 거의 없습니다.

### Q96. Javaにメモリリークはありますか？あるならどんな形ですか？
(Java 에 메모리 누수가 있나, 있다면 어떤 형태인가)

**🇯🇵 回答**

あります。GCがあるので「解放し忘れ」は起きませんが、**不要になったのに参照が残っている**状態は起きます。GCから見ると使用中なので回収されません。

代表的なのは、`static` なコレクションに追加し続ける、リスナーの登録解除漏れ、`ThreadLocal` の `remove` 忘れ、キャッシュに上限を設けていない、の四つです。どれも「捨てるコードを書き忘れた」形をしています。

**🇰🇷 답변**

있습니다. GC 가 있으니 "해제 누락"은 없지만, **불필요해졌는데 참조가 남아 있는** 상태는 생깁니다. GC 입장에서는 사용 중이라 회수되지 않습니다.

대표적인 것은 `static` 컬렉션에 계속 추가, 리스너 등록 해제 누락, `ThreadLocal` 의 `remove` 누락, 캐시에 상한을 두지 않음, 이 네 가지입니다. 전부 "버리는 코드를 안 썼다"는 형태입니다.

### Q97. メモリリークをどう調査しますか？
(메모리 누수를 어떻게 조사하나)

**🇯🇵 回答**

まずGCログで、Full GCの後もヒープが減らないことを確認します。ここでリークかどうかが分かります。

次にヒープヒストグラムを時間を空けて二回取り、増え続けているクラスを特定します。`jcmd GC.class_histogram` で取れます。当たりが付いたらヒープダンプを取得し、MATなどで支配木を見て「何が参照を保持しているか」を辿ります。**増えているものではなく、それを掴んでいるものを探す**のがコツです。

**🇰🇷 답변**

먼저 GC 로그에서 Full GC 후에도 힙이 줄지 않는 것을 확인합니다. 여기서 누수인지 아닌지 알 수 있습니다.

다음으로 힙 히스토그램을 시간 간격을 두고 두 번 떠서 계속 늘어나는 클래스를 특정합니다. `jcmd GC.class_histogram` 으로 뜰 수 있습니다. 짐작이 서면 힙 덤프를 떠서 MAT 등으로 지배 트리를 보고 "무엇이 참조를 붙들고 있는지"를 추적합니다. **늘어나는 것이 아니라 그것을 쥐고 있는 것을 찾는 것**이 요령입니다.

### Q98. `OutOfMemoryError` にはどんな種類がありますか？
(OutOfMemoryError 의 종류)

**🇯🇵 回答**

メッセージで原因が全く違います。`Java heap space` はヒープ不足かリーク、`Metaspace` はクラスの作りすぎ、`unable to create new native thread` はスレッドの作りすぎ、`GC overhead limit exceeded` はGCばかりで前に進めない状態です。

だから最初に見るのはメッセージです。ヒープを増やせば直ると決めつけると、スレッド起因の場合はむしろ悪化します。

**🇰🇷 답변**

메시지로 원인이 전혀 달라집니다. `Java heap space` 는 힙 부족이나 누수, `Metaspace` 는 클래스를 너무 많이 만든 것, `unable to create new native thread` 는 스레드를 너무 많이 만든 것, `GC overhead limit exceeded` 는 GC 만 하느라 진행이 안 되는 상태입니다.

그래서 가장 먼저 보는 것은 메시지입니다. 힙을 늘리면 낫는다고 단정하면, 스레드가 원인인 경우는 오히려 악화됩니다.

### Q99. 本番で `OutOfMemoryError` に備える設定は？
(프로덕션에서 OOM 에 대비하는 설정)

**🇯🇵 回答**

`-XX:+HeapDumpOnOutOfMemoryError` と `-XX:HeapDumpPath` を必ず入れます。落ちた瞬間のダンプが残っていないと、後から再現するのは非常に難しいからです。

加えてGCログの出力とローテーションも設定します。障害が起きてから調べる準備を始めるのでは遅い、というのが実務で一番効く教訓だと考えています。

**🇰🇷 답변**

`-XX:+HeapDumpOnOutOfMemoryError` 와 `-XX:HeapDumpPath` 를 반드시 넣습니다. 죽는 순간의 덤프가 남아 있지 않으면 나중에 재현하기가 매우 어렵기 때문입니다.

여기에 GC 로그 출력과 로테이션도 설정합니다. 장애가 난 뒤에 조사할 준비를 시작하면 늦다는 것이, 실무에서 가장 효과가 큰 교훈이라고 생각합니다.

### Q100. Metaspace は PermGen と何が違いますか？
(Metaspace 는 PermGen 과 무엇이 다른가)

**🇯🇵 回答**

置き場所が違います。PermGenはヒープ内でしたが、MetaspaceはネイティブメモリにあるのでヒープのGC対象外です。

デフォルトで上限がなく、OSのメモリまで使えるので `PermGen space` エラーは出にくくなりました。ただし裏を返すと、**暴走したときにOSのメモリを食い尽くします**。だから `MaxMetaspaceSize` は「増やす」のではなく「上限を決める」ために設定します。

**🇰🇷 답변**

놓이는 곳이 다릅니다. PermGen 은 힙 안이었지만 Metaspace 는 네이티브 메모리에 있어 힙 GC 대상 밖입니다.

기본적으로 상한이 없고 OS 메모리까지 쓸 수 있어 `PermGen space` 에러는 잘 나지 않게 됐습니다. 다만 뒤집어 말하면 **폭주하면 OS 메모리를 다 먹습니다.** 그래서 `MaxMetaspaceSize` 는 "늘리기" 위해서가 아니라 "상한을 정하기" 위해 설정합니다.

### Q101. Strong・Soft・Weak・Phantom の参照はどう違いますか？
(Strong·Soft·Weak·Phantom 참조의 차이)

**🇯🇵 回答**

Strongは通常の参照で、あれば絶対に回収されません。Softはメモリが不足したときに回収されるのでキャッシュ向きです。Weakは次のGCで回収されるので、`WeakHashMap` のようにキーが消えたら一緒に消したい用途に使います。

Phantomは値を取り出せず、回収されたことを知るためだけに使います。実務で自分で書くのは稀ですが、ライブラリの後始末処理で使われています。

**🇰🇷 답변**

Strong 은 통상의 참조로, 있으면 절대 회수되지 않습니다. Soft 는 메모리가 부족할 때 회수되므로 캐시에 적합합니다. Weak 은 다음 GC 에서 회수되므로 `WeakHashMap` 처럼 키가 사라지면 함께 지우고 싶은 용도에 씁니다.

Phantom 은 값을 꺼낼 수 없고, 회수됐다는 것을 알기 위해서만 씁니다. 실무에서 직접 쓰는 일은 드물지만 라이브러리의 뒷정리 처리에 쓰이고 있습니다.

---

### Q102. `finalize()` を使ってはいけない理由は？
(finalize 를 쓰면 안 되는 이유)

**🇯🇵 回答**

呼ばれる保証も、呼ばれるタイミングの保証もないからです。オブジェクトの回収が一世代遅れるので性能も落ちます。Java 9 で非推奨になり、削除される方向です。

リソースの解放は `try-with-resources` と `AutoCloseable` で明示的に行います。どうしても後始末が必要なら `Cleaner` を使いますが、それも保険であって主たる手段にはしません。

**🇰🇷 답변**

호출된다는 보장도, 호출 시점의 보장도 없기 때문입니다. 객체 회수가 한 세대 늦어져 성능도 떨어집니다. Java 9 에서 비권장이 됐고 제거되는 방향입니다.

리소스 해제는 `try-with-resources` 와 `AutoCloseable` 로 명시적으로 합니다. 굳이 뒷정리가 필요하면 `Cleaner` 를 쓰지만, 그것도 보험이지 주된 수단으로 삼지는 않습니다.

---

### Q103. `System.gc()` を呼ぶべきですか？
(System.gc() 를 불러야 하나)

**🇯🇵 回答**

呼ぶべきではありません。あくまで要求であって強制ではなく、しかも呼ばれた場合はFull GCになるので、長い停止を自分で招くことになります。

「メモリが心配だから念のため」という理由で入っているコードを見ることがありますが、効果がないどころか有害です。取り除く対象だと考えています。

**🇰🇷 답변**

부르면 안 됩니다. 어디까지나 요청이지 강제가 아니고, 게다가 실제로 실행되면 Full GC 가 되므로 긴 정지를 스스로 불러오게 됩니다.

"메모리가 걱정되니 혹시 몰라서"라는 이유로 들어 있는 코드를 볼 때가 있는데, 효과가 없기는커녕 해롭습니다. 제거 대상이라고 생각합니다.

---

### Q104. JITコンパイラは何をしますか？
(JIT 컴파일러는 무엇을 하나)

**🇯🇵 回答**

最初はインタプリタで実行し、実行回数が閾値を超えたメソッドやループをネイティブコードにコンパイルします。よく通る箇所だけを最適化する仕組みです。

だから同じコードでも**ウォームアップ後は桁違いに速くなります**。ベンチマークでウォームアップが必須なのはこれが理由です。インライン化やエスケープ解析といった最適化も、実行時の情報があるからこそできます。

**🇰🇷 답변**

처음에는 인터프리터로 실행하고, 실행 횟수가 임계값을 넘은 메서드나 루프를 네이티브 코드로 컴파일합니다. 자주 지나는 곳만 최적화하는 구조입니다.

그래서 같은 코드라도 **워밍업 후에는 자릿수 단위로 빨라집니다.** 벤치마크에 워밍업이 필수인 이유가 이것입니다. 인라이닝이나 이스케이프 분석 같은 최적화도 실행 시점의 정보가 있기에 가능합니다.

---

### Q105. エスケープ解析とは何ですか？
(이스케이프 분석이란)

**🇯🇵 回答**

そのオブジェクトがメソッドの外に漏れないと判定できれば、ヒープに置かずスタックに置いたり、そもそも生成自体を消したりする最適化です。ロックも削除できます。

つまり「小さいオブジェクトを作ると必ず遅い」とは限りません。**まず素直に書いて、計測してから最適化する**という順序が正しいことの根拠にもなります。

**🇰🇷 답변**

그 객체가 메서드 밖으로 새지 않는다고 판정되면, 힙에 놓지 않고 스택에 놓거나 아예 생성 자체를 없애는 최적화입니다. 락도 제거할 수 있습니다.

즉 "작은 객체를 만들면 반드시 느리다"고 할 수는 없습니다. **먼저 솔직하게 쓰고, 측정한 뒤에 최적화한다**는 순서가 옳다는 근거도 됩니다.

---

### Q106. マイクロベンチマークで注意すべきことは？
(마이크로벤치마크에서 주의할 점)

**🇯🇵 回答**

三つあります。ウォームアップをしないとインタプリタを測ることになる、結果を使わないと最適化で処理ごと消される(デッドコード削除)、そして計測の解像度が足りないと差が0として出てしまうことです。

だからミリ秒で切って比較するのは危険です。マイクロ秒以上の解像度を使い、最低限の差を要求します。本格的に測るならJMHを使うのが前提だと考えています。

**🇰🇷 답변**

세 가지입니다. 워밍업을 안 하면 인터프리터를 재게 된다, 결과를 쓰지 않으면 최적화로 처리째 사라진다(죽은 코드 제거), 그리고 측정 해상도가 부족하면 차이가 0으로 나온다는 것입니다.

그래서 밀리초로 잘라 비교하는 것은 위험합니다. 마이크로초 이상의 해상도를 쓰고 최소한의 여유를 요구합니다. 본격적으로 재려면 JMH 를 쓰는 것이 전제라고 생각합니다.

---

### Q107. 平均レイテンシではなくパーセンタイルを見る理由は？
(평균 지연이 아니라 퍼센타일을 보는 이유)

**🇯🇵 回答**

平均は外れ値を隠すからです。90%のリクエストが10msでも、残りの10%が3秒なら、平均は300ms程度に見えてしまい、実際にひどい体験をしている利用者が見えません。

だからp95やp99を見ます。特にGCの停止時間はまさにこの裾に出るので、平均だけを見ているとGCチューニングの必要性に気づけません。

**🇰🇷 답변**

평균은 이상치를 감추기 때문입니다. 90% 의 요청이 10ms 여도 나머지 10% 가 3초라면 평균은 300ms 정도로 보여, 실제로 나쁜 경험을 하는 이용자가 안 보입니다.

그래서 p95 나 p99 를 봅니다. 특히 GC 정지 시간은 바로 이 꼬리에 나타나므로, 평균만 보고 있으면 GC 튜닝의 필요성을 알아채지 못합니다.

---

### Q108. CPU使用率が高いとき、どう原因を特定しますか？
(CPU 사용률이 높을 때 어떻게 원인을 특정하나)

**🇯🇵 回答**

まずOSレベルで `top` を見ますが、重要なのは `top -H` で**スレッド単位まで下りる**ことです。プロセス単位では犯人が見えません。

CPUを食っているスレッドIDを16進数に変換し、`jstack` で取ったスレッドダンプの `nid` と突き合わせると、どのメソッドで回っているかが分かります。GCスレッドだった場合は、CPU問題ではなくメモリ問題です。

**🇰🇷 답변**

먼저 OS 레벨에서 `top` 을 보는데, 중요한 것은 `top -H` 로 **스레드 단위까지 내려가는 것**입니다. 프로세스 단위로는 범인이 안 보입니다.

CPU 를 먹고 있는 스레드 ID 를 16진수로 변환해 `jstack` 으로 뜬 스레드 덤프의 `nid` 와 대조하면 어느 메서드에서 돌고 있는지 알 수 있습니다. GC 스레드였다면 CPU 문제가 아니라 메모리 문제입니다.

---

### Q109. サンプリング型と計測型のプロファイラの違いは？
(샘플링형과 계측형 프로파일러의 차이)

**🇯🇵 回答**

サンプリング型は一定間隔でスタックを覗くだけなのでオーバーヘッドが小さく、本番でも使えます。計測型は全メソッドに計測コードを差し込むので正確ですが、遅くなり、しかも**インライン化を妨げて実際とは違う姿を見せる**ことがあります。

だからまずサンプリングで当たりを付け、必要な範囲だけ計測型で詳しく見る、という順序にしています。

**🇰🇷 답변**

샘플링형은 일정 간격으로 스택을 들여다볼 뿐이라 오버헤드가 작아 프로덕션에서도 쓸 수 있습니다. 계측형은 모든 메서드에 계측 코드를 삽입하므로 정확하지만 느려지고, 게다가 **인라이닝을 방해해 실제와 다른 모습을 보여줄** 수 있습니다.

그래서 먼저 샘플링으로 짐작을 잡고, 필요한 범위만 계측형으로 자세히 보는 순서로 하고 있습니다.

---

### Q110. Java Flight Recorder は何に使いますか？
(JFR 은 무엇에 쓰나)

**🇯🇵 回答**

本番環境での継続的な記録に使います。オーバーヘッドが数%程度と小さいので、常時有効にしておいて、問題が起きた区間を後から取り出せます。

GC、割り当て、ロック競合、I/O、例外までまとめて記録されるのが強みです。JDK 11 以降はオープンソースになっていて、追加ライセンスなしで使えます。

**🇰🇷 답변**

프로덕션 환경에서의 지속적인 기록에 씁니다. 오버헤드가 수 % 정도로 작아 상시 켜 두고 문제가 난 구간을 나중에 꺼낼 수 있습니다.

GC, 할당, 락 경합, I/O, 예외까지 한꺼번에 기록되는 것이 강점입니다. JDK 11 이후는 오픈소스가 되어 추가 라이선스 없이 쓸 수 있습니다.

---

### Q111. ヒープサイズはどう決めますか？
(힙 크기는 어떻게 정하나)

**🇯🇵 回答**

`-Xms` と `-Xmx` を同じ値にするのが基本です。動的な拡張のたびにGCが走るのを避けられます。

大きさは、Full GC後の使用量、つまりライブデータ量を基準にして、その2倍から3倍を目安にします。**大きくすればよいというものではなく**、大きすぎると一回のFull GCが長くなります。コンテナでは物理メモリの上限も考慮する必要があります。

**🇰🇷 답변**

`-Xms` 와 `-Xmx` 를 같은 값으로 하는 것이 기본입니다. 동적 확장 때마다 GC 가 도는 것을 피할 수 있습니다.

크기는 Full GC 후의 사용량, 즉 라이브 데이터 양을 기준으로 그 2~3배를 잡습니다. **크게 하면 좋은 것이 아니고**, 너무 크면 한 번의 Full GC 가 길어집니다. 컨테이너에서는 물리 메모리 상한도 고려해야 합니다.

---

### Q112. コンテナ内でJVMのメモリ設定はどうしますか？
(컨테이너 안에서 JVM 메모리 설정은 어떻게 하나)

**🇯🇵 回答**

古いJDKはホストのメモリを見てしまい、コンテナの上限を超えるヒープを取ってOOM Killerに殺されることがありました。JDK 10 以降はcgroupを認識するので、基本的にはそのままで動きます。

その上で `-XX:MaxRAMPercentage` で割合指定するのが実務的です。固定値だとコンテナのサイズを変えるたびに直す必要があるからです。**ヒープ以外にもメタスペースやスレッドスタックがある**ので、100%は指定しません。

**🇰🇷 답변**

옛 JDK 는 호스트 메모리를 보고 컨테이너 상한을 넘는 힙을 잡아 OOM Killer 에 죽는 일이 있었습니다. JDK 10 이후는 cgroup 을 인식하므로 기본적으로는 그대로 동작합니다.

그 위에서 `-XX:MaxRAMPercentage` 로 비율 지정하는 것이 실무적입니다. 고정값이면 컨테이너 크기를 바꿀 때마다 고쳐야 하기 때문입니다. **힙 외에도 메타스페이스와 스레드 스택이 있으므로** 100% 는 지정하지 않습니다.

### Q113. 圧縮oopと32GBの境界について説明してください。
(압축 oop 와 32GB 경계)

**🇯🇵 回答**

64ビットJVMでは、ヒープが32GB未満なら参照を32ビットに圧縮して保持できます。メモリ使用量が減り、キャッシュ効率も上がります。

問題は境界です。ヒープを33GBにすると圧縮oopが無効になり、**31GBに設定したときより実質的に使える容量が減る**という逆転が起きます。だから32GB前後の設定は避けます。

**🇰🇷 답변**

64비트 JVM 에서는 힙이 32GB 미만이면 참조를 32비트로 압축해 보유할 수 있습니다. 메모리 사용량이 줄고 캐시 효율도 올라갑니다.

문제는 경계입니다. 힙을 33GB 로 하면 압축 oop 이 무효가 되어 **31GB 로 설정했을 때보다 실질적으로 쓸 수 있는 용량이 줄어드는** 역전이 일어납니다. 그래서 32GB 전후의 설정은 피합니다.

### Q114. TLAB とは何ですか？
(TLAB 이란)

**🇯🇵 回答**

Thread Local Allocation Buffer で、スレッドごとにEden領域の一部を切り出して専有する仕組みです。

これがないと、オブジェクトを割り当てるたびにスレッド間で同期が必要になります。TLABがあれば自分の領域にポインタを進めるだけで済むので、割り当てが非常に速くなります。**Javaのオブジェクト生成が意外と安いのはこれが理由**です。

**🇰🇷 답변**

Thread Local Allocation Buffer 로, 스레드마다 Eden 영역의 일부를 떼어 전유하는 구조입니다.

이게 없으면 객체를 할당할 때마다 스레드 간 동기화가 필요합니다. TLAB 이 있으면 자기 영역에 포인터를 진행시키기만 하면 되므로 할당이 매우 빨라집니다. **Java 의 객체 생성이 의외로 싼 것은 이 때문입니다.**

---

### Q115. 例外を投げるコストが高いと言われるのはなぜですか？
(예외를 던지는 비용이 크다고 하는 이유)

**🇯🇵 回答**

例外そのものより、生成時にスタックトレースを収集する処理が重いからです。しかもそのコストは**スタックの深さに比例**します。

だから深いフレームワークの中で例外を大量に投げると、目に見えて遅くなります。JVM自身も、頻出するシステム例外はスタックなしで再利用するほどです。対策はスタック収集を止めることではなく、例外を制御フローに使わないようにコードを直すことです。

**🇰🇷 답변**

예외 자체보다 생성 시 스택 트레이스를 수집하는 처리가 무겁기 때문입니다. 게다가 그 비용은 **스택 깊이에 비례**합니다.

그래서 깊은 프레임워크 안에서 예외를 대량으로 던지면 눈에 띄게 느려집니다. JVM 자신도 자주 나는 시스템 예외는 스택 없이 재사용할 정도입니다. 대책은 스택 수집을 끄는 것이 아니라, 예외를 제어 흐름에 쓰지 않도록 코드를 고치는 것입니다.

- **"늘리면 된다"를 부정하는 질문 3개** — 힙 크기(Q111), Metaspace(Q100), 압축 oop(Q113).
