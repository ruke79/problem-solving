### Q1. `==` と `equals()` の違いを説明してください。
(== 와 equals() 의 차이)

**🇯🇵 回答**

`==` は参照そのものの比較で、同じインスタンスを指しているかを見ます。`equals()` は値の比較で、クラスが定義した「等しさ」の基準に従います。

プリミティブ型には `==` を使いますが、オブジェクトの中身を比べたいときは必ず `equals()` を使います。`String` を `==` で比べて動いてしまうことがあるのは、文字列リテラルがプールで共有されているからで、たまたま一致しているだけです。

**🇰🇷 답변**

`==` 는 참조 자체의 비교로, 같은 인스턴스를 가리키는지를 봅니다. `equals()` 는 값 비교이고, 클래스가 정의한 "같음"의 기준을 따릅니다.

기본형에는 `==` 를 쓰지만, 객체의 내용을 비교하려면 반드시 `equals()` 를 씁니다. `String` 을 `==` 로 비교했는데 동작하는 경우가 있는 것은 문자열 리터럴이 풀에서 공유되기 때문이고, 우연히 일치한 것뿐입니다.

### Q2. `equals()` をオーバーライドするとき `hashCode()` も一緒に実装する理由は？
(equals 를 오버라이드할 때 hashCode 도 함께 구현하는 이유)

**🇯🇵 回答**

「等しいオブジェクトは同じハッシュコードを返す」という契約があるからです。これを破ると `HashMap` や `HashSet` が壊れます。

具体的には、`equals` 上は等しいのにハッシュコードが違うと、別のバケットに入ってしまい、`put` した値を `get` で取り出せなくなります。IDE の自動生成か `Objects.hash()` を使うのが安全です。

**🇰🇷 답변**

"같은 객체는 같은 해시코드를 반환한다"는 계약이 있기 때문입니다. 이걸 어기면 `HashMap` 이나 `HashSet` 이 깨집니다.

구체적으로는 `equals` 상으로는 같은데 해시코드가 다르면 다른 버킷에 들어가서, `put` 한 값을 `get` 으로 꺼내지 못하게 됩니다. IDE 자동 생성이나 `Objects.hash()` 를 쓰는 것이 안전합니다.

### Q3. `String` が不変(immutable)である理由は何ですか？
(String 이 불변인 이유)

**🇯🇵 回答**

理由は主に三つです。第一に文字列プールで安全に共有できること、第二にハッシュコードをキャッシュできるので `HashMap` のキーとして速いこと、第三にスレッドセーフになることです。

セキュリティ面もあります。ファイルパスや接続情報を渡した後で書き換えられると、検証を通した後に別の値になってしまうからです。

**🇰🇷 답변**

이유는 크게 세 가지입니다. 첫째 문자열 풀에서 안전하게 공유할 수 있다는 것, 둘째 해시코드를 캐시할 수 있어 `HashMap` 의 키로 빠르다는 것, 셋째 스레드 세이프해진다는 것입니다.

보안 측면도 있습니다. 파일 경로나 접속 정보를 넘긴 뒤에 바뀌면, 검증을 통과한 후에 다른 값이 되어 버리기 때문입니다.

### Q4. `String`・`StringBuilder`・`StringBuffer` の使い分けは？
(String·StringBuilder·StringBuffer 사용 구분)

**🇯🇵 回答**

`String` は不変なので、連結のたびに新しいインスタンスができます。ループの中で `+` を使うと、その回数だけゴミが生まれます。

繰り返し組み立てるときは `StringBuilder` を使います。`StringBuffer` は同期化されている分だけ遅いので、複数スレッドで同じインスタンスを共有する場合に限ります。実務ではほぼ `StringBuilder` です。

**🇰🇷 답변**

`String` 은 불변이라 연결할 때마다 새 인스턴스가 생깁니다. 루프 안에서 `+` 를 쓰면 그 횟수만큼 쓰레기가 생깁니다.

반복해서 조립할 때는 `StringBuilder` 를 씁니다. `StringBuffer` 는 동기화된 만큼 느리므로, 여러 스레드가 같은 인스턴스를 공유하는 경우에만 씁니다. 실무에서는 거의 `StringBuilder` 입니다.

### Q5. 一行の文字列連結も `StringBuilder` に書き換えるべきですか？
(한 줄짜리 문자열 연결도 StringBuilder 로 바꿔야 하나)

**🇯🇵 回答**

いいえ、必要ありません。一つの文の中の `+` はコンパイラが `StringBuilder` に変換してくれるので、手で書き換えても速くなりません。むしろ読みにくくなります。

問題になるのはループをまたぐ場合です。この場合はコンパイラが最適化できず、繰り返しのたびに新しい `StringBuilder` が作られます。**ループの外で一つ作る**のが正解です。

**🇰🇷 답변**

아니요, 필요 없습니다. 한 문장 안의 `+` 는 컴파일러가 `StringBuilder` 로 변환해 주므로 손으로 바꿔도 빨라지지 않습니다. 오히려 읽기 어려워집니다.

문제가 되는 것은 루프를 걸칠 때입니다. 이 경우는 컴파일러가 최적화하지 못해 반복마다 새 `StringBuilder` 가 만들어집니다. **루프 밖에서 하나 만드는 것**이 정답입니다.

### Q6. プリミティブ型と参照型の違いは？
(기본형과 참조형의 차이)

**🇯🇵 回答**

プリミティブ型は値そのものを保持し、スタックに置かれます。`int` や `boolean` などの八種類です。参照型はヒープ上のオブジェクトを指すアドレスを保持します。

違いが効くのは、`null` を持てるかどうか、ジェネリクスに使えるかどうか、そしてメモリ効率です。`int` の配列と `Integer` のリストではフットプリントが大きく変わります。

**🇰🇷 답변**

기본형은 값 자체를 보유하고 스택에 놓입니다. `int` 나 `boolean` 등 여덟 종류입니다. 참조형은 힙 위의 객체를 가리키는 주소를 보유합니다.

차이가 드러나는 것은 `null` 을 가질 수 있는지, 제네릭에 쓸 수 있는지, 그리고 메모리 효율입니다. `int` 배열과 `Integer` 리스트는 풋프린트가 크게 달라집니다.

### Q7. オートボクシングで注意すべき点は？
(오토박싱에서 주의할 점)

**🇯🇵 回答**

二つあります。一つは性能で、ループの中でボクシングが起きると、その回数だけ `Integer` オブジェクトが生成されます。合計を求めるだけの処理が何倍も遅くなることがあります。

もう一つは `null` です。`Integer` を `int` に代入する際に `null` だと `NullPointerException` が出ます。原因が見えにくい箇所なので、`Optional` やデフォルト値で防ぎます。

**🇰🇷 답변**

두 가지입니다. 하나는 성능으로, 루프 안에서 박싱이 일어나면 그 횟수만큼 `Integer` 객체가 생성됩니다. 합계를 구하는 정도의 처리가 몇 배씩 느려지기도 합니다.

또 하나는 `null` 입니다. `Integer` 를 `int` 에 대입할 때 `null` 이면 `NullPointerException` 이 납니다. 원인이 잘 안 보이는 지점이라 `Optional` 이나 기본값으로 막습니다.

### Q8. `Integer` を `==` で比較すると値によって結果が変わるのはなぜですか？
(Integer 를 == 로 비교하면 값에 따라 결과가 달라지는 이유)

**🇯🇵 回答**

`Integer` のキャッシュがあるからです。`-128` から `127` までは同じインスタンスが再利用されるので `==` でも `true` になりますが、それを超えると別インスタンスになり `false` になります。

つまり `127` では動いて `128` で壊れる、という典型的なバグです。ラッパー型の比較には必ず `equals()` を使います。

**🇰🇷 답변**

`Integer` 캐시가 있기 때문입니다. `-128` 부터 `127` 까지는 같은 인스턴스가 재사용되므로 `==` 로도 `true` 가 되지만, 그 범위를 넘으면 다른 인스턴스가 되어 `false` 가 됩니다.

즉 `127` 에서는 동작하고 `128` 에서 깨지는 전형적인 버그입니다. 래퍼 타입 비교에는 반드시 `equals()` 를 씁니다.

### Q9. `final` はどこに付けられ、それぞれ何を意味しますか？
(final 은 어디에 붙일 수 있고 각각 무슨 의미인가)

**🇯🇵 回答**

変数・メソッド・クラスの三つに付けられます。変数なら再代入禁止、メソッドならオーバーライド禁止、クラスなら継承禁止です。

注意点は、変数の `final` は**参照の固定であって中身の不変ではない**ことです。`final List` でも `add` はできます。不変にしたいなら `List.of()` などを併せて使います。

**🇰🇷 답변**

변수·메서드·클래스 세 곳에 붙일 수 있습니다. 변수면 재대입 금지, 메서드면 오버라이드 금지, 클래스면 상속 금지입니다.

주의할 점은 변수의 `final` 이 **참조의 고정이지 내용의 불변이 아니라는 것**입니다. `final List` 라도 `add` 는 됩니다. 불변으로 만들려면 `List.of()` 같은 것을 함께 씁니다.

### Q10. `static` メンバーの特徴と注意点は？
(static 멤버의 특징과 주의점)

**🇯🇵 回答**

インスタンスではなくクラスに属し、クラスロード時に一度だけ初期化されます。全インスタンスで共有されます。

注意点は二つで、一つはスレッドセーフでないこと、もう一つは**参照が残り続けるのでGCされないこと**です。`static` なコレクションに追加だけして削除しない実装は、典型的なメモリリークになります。

**🇰🇷 답변**

인스턴스가 아니라 클래스에 속하고, 클래스 로드 시 한 번만 초기화됩니다. 모든 인스턴스에서 공유됩니다.

주의점은 두 가지로, 하나는 스레드 세이프하지 않다는 것, 또 하나는 **참조가 계속 남아 GC 되지 않는다는 것**입니다. `static` 컬렉션에 추가만 하고 삭제하지 않는 구현은 전형적인 메모리 누수가 됩니다.

### Q11. オーバーロードとオーバーライドの違いは？
(오버로딩과 오버라이딩의 차이)

**🇯🇵 回答**

オーバーロードは同じクラス内で名前が同じで引数が違うメソッドを複数定義することで、**コンパイル時**にどれを呼ぶかが決まります。

オーバーライドは親クラスのメソッドを子クラスで再定義することで、**実行時**に実際の型を見て決まります。ポリモーフィズムが効くのはこちらです。戻り値の型だけを変えてもオーバーロードにはなりません。

**🇰🇷 답변**

오버로딩은 같은 클래스 안에서 이름이 같고 인자가 다른 메서드를 여러 개 정의하는 것으로, **컴파일 시점**에 어느 것을 호출할지 결정됩니다.

오버라이딩은 부모 클래스의 메서드를 자식에서 재정의하는 것으로, **실행 시점**에 실제 타입을 보고 결정됩니다. 다형성이 작동하는 것은 이쪽입니다. 반환 타입만 바꿔서는 오버로딩이 되지 않습니다.

### Q12. 抽象クラスとインターフェースはどう使い分けますか？
(추상 클래스와 인터페이스의 사용 구분)

**🇯🇵 回答**

「である(is-a)」の関係で状態を共有したいなら抽象クラス、「できる(can-do)」という能力を定義したいならインターフェースを使います。

実務での判断基準は多重継承の必要性です。インターフェースは複数実装できますが、クラスは一つしか継承できません。迷ったらインターフェースを選び、共通実装が本当に必要になってから抽象クラスを検討します。

**🇰🇷 답변**

"이다(is-a)" 관계이고 상태를 공유하고 싶으면 추상 클래스, "할 수 있다(can-do)"는 능력을 정의하고 싶으면 인터페이스를 씁니다.

실무의 판단 기준은 다중 상속의 필요성입니다. 인터페이스는 여러 개 구현할 수 있지만 클래스는 하나만 상속할 수 있습니다. 망설여지면 인터페이스를 고르고, 공통 구현이 정말 필요해진 뒤에 추상 클래스를 검토합니다.

### Q13. インターフェースの `default` メソッドは何のために導入されましたか？
(인터페이스의 default 메서드는 무엇을 위해 도입됐나)

**🇯🇵 回答**

既存の実装クラスを壊さずにインターフェースへメソッドを追加するためです。`Collection` に `stream()` を足せたのはこの仕組みのおかげです。

ただし複数のインターフェースから同じシグネチャの `default` を継承すると衝突するので、その場合は実装クラス側でオーバーライドして明示する必要があります。

**🇰🇷 답변**

기존 구현 클래스를 깨지 않고 인터페이스에 메서드를 추가하기 위해서입니다. `Collection` 에 `stream()` 을 넣을 수 있었던 것이 이 구조 덕분입니다.

다만 여러 인터페이스에서 같은 시그니처의 `default` 를 상속하면 충돌하므로, 그 경우는 구현 클래스 쪽에서 오버라이드해 명시해야 합니다.

### Q14. アクセス修飾子の四種類を説明してください。
(접근 제어자 네 가지)

**🇯🇵 回答**

`public` はどこからでも、`protected` は同じパッケージと継承先から、修飾子なし(package-private)は同じパッケージから、`private` は同じクラス内からのみアクセスできます。

原則は**必要最小限**です。まず `private` で作り、外に出す必要が出てから広げます。フィールドを安易に `public` にすると不変条件を守れなくなります。

**🇰🇷 답변**

`public` 은 어디서나, `protected` 는 같은 패키지와 상속받은 곳에서, 제어자 없음(package-private)은 같은 패키지에서, `private` 은 같은 클래스 안에서만 접근할 수 있습니다.

원칙은 **필요 최소한**입니다. 먼저 `private` 으로 만들고, 밖으로 열 필요가 생기면 넓힙니다. 필드를 쉽게 `public` 으로 두면 불변 조건을 지킬 수 없게 됩니다.

### Q15. Java は値渡しですか、参照渡しですか？
(Java 는 값 전달인가 참조 전달인가)

**🇯🇵 回答**

Java は常に**値渡し**です。オブジェクトの場合は「参照という値」がコピーされて渡されます。

だからメソッド内で引数に別のオブジェクトを再代入しても呼び出し元には反映されませんが、渡されたオブジェクトの中身を変更した場合は反映されます。この二つを区別できるかがこの質問の要点だと理解しています。

**🇰🇷 답변**

Java 는 항상 **값 전달**입니다. 객체의 경우는 "참조라는 값"이 복사되어 전달됩니다.

그래서 메서드 안에서 인자에 다른 객체를 재대입해도 호출한 쪽에는 반영되지 않지만, 전달받은 객체의 내용을 변경한 경우는 반영됩니다. 이 둘을 구분할 수 있는지가 이 질문의 핵심이라고 생각합니다.

### Q16. 不変(immutable)クラスはどう作りますか？
(불변 클래스를 만드는 방법)

**🇯🇵 回答**

クラスを `final` にし、フィールドを `private final` にし、setter を作らず、コンストラクタで全て初期化します。

見落としやすいのが**可変オブジェクトの防御的コピー**です。`List` や `Date` をそのまま受け取って保持すると、外から書き換えられます。受け取るときと返すときの両方でコピーする必要があります。`record` を使うとこの多くが自動になりますが、防御的コピーだけは自分で書きます。

**🇰🇷 답변**

클래스를 `final` 로 하고, 필드를 `private final` 로 하고, setter 를 만들지 않고, 생성자에서 전부 초기화합니다.

놓치기 쉬운 것이 **가변 객체의 방어적 복사**입니다. `List` 나 `Date` 를 그대로 받아 보유하면 밖에서 바꿀 수 있습니다. 받을 때와 반환할 때 양쪽에서 복사해야 합니다. `record` 를 쓰면 대부분이 자동이 되지만, 방어적 복사만은 직접 써야 합니다.

### Q17. `Object` クラスの主なメソッドを挙げてください。
(Object 클래스의 주요 메서드)

**🇯🇵 回答**

`equals()`、`hashCode()`、`toString()`、`getClass()`、`clone()`、`wait()`/`notify()`/`notifyAll()` です。

実務で必ず意識するのは最初の三つで、特に `toString()` はログの読みやすさに直結します。`clone()` は浅いコピーで扱いが難しいので、コピーコンストラクタか静的ファクトリを使う方が安全だと考えています。

**🇰🇷 답변**

`equals()`, `hashCode()`, `toString()`, `getClass()`, `clone()`, `wait()`/`notify()`/`notifyAll()` 입니다.

실무에서 늘 신경 쓰는 것은 앞의 세 개이고, 특히 `toString()` 은 로그의 가독성에 직결됩니다. `clone()` 은 얕은 복사라 다루기 까다로우므로, 복사 생성자나 정적 팩토리를 쓰는 편이 안전하다고 생각합니다.

### Q18. チェック例外と非チェック例外の違いと使い分けは？
(체크 예외와 언체크 예외의 차이와 사용 구분)

**🇯🇵 回答**

チェック例外はコンパイラが処理を強制するもので、`Exception` を継承します。非チェック例外は `RuntimeException` 系で、強制されません。

使い分けの基準は**呼び出し側が回復できるか**です。ファイルがない、通信に失敗したなど、呼び出し側が代替手段を取れるならチェック例外。引数が不正、状態がおかしいなどプログラムのバグならランタイム例外にします。

**🇰🇷 답변**

체크 예외는 컴파일러가 처리를 강제하는 것으로 `Exception` 을 상속합니다. 언체크 예외는 `RuntimeException` 계열로 강제되지 않습니다.

구분 기준은 **호출하는 쪽이 회복할 수 있는가**입니다. 파일이 없다, 통신에 실패했다처럼 호출한 쪽이 대안을 취할 수 있으면 체크 예외. 인자가 잘못됐다, 상태가 이상하다처럼 프로그램의 버그면 런타임 예외로 합니다.

---

### Q19. `try-with-resources` は何を解決しますか？
(try-with-resources 는 무엇을 해결하나)

**🇯🇵 回答**

リソースの解放漏れと、`finally` 内で例外が起きたときに元の例外が消える問題を解決します。

`AutoCloseable` を実装していれば自動で `close()` が呼ばれ、しかも**逆順で**閉じられます。`finally` で発生した例外は抑制例外として元の例外にぶら下がるので、本来の原因を見失いません。DB のコネクションやストリームは基本的にこれを使います。

**🇰🇷 답변**

리소스 해제 누락과, `finally` 안에서 예외가 나면 원래 예외가 사라지는 문제를 해결합니다.

`AutoCloseable` 을 구현했다면 자동으로 `close()` 가 호출되고, 게다가 **역순으로** 닫힙니다. `finally` 에서 발생한 예외는 억제 예외로 원래 예외에 매달리므로 본래 원인을 놓치지 않습니다. DB 커넥션이나 스트림은 기본적으로 이걸 씁니다.

---

### Q20. `finally` の中で `return` するとどうなりますか？
(finally 안에서 return 하면 어떻게 되나)

**🇯🇵 回答**

`try` 側の `return` や例外を**上書きしてしまいます**。例外が投げられていても `finally` の `return` で握りつぶされ、原因が完全に消えます。

だから `finally` の中では `return` も `throw` も書かない、というのが原則です。静的解析ツールも警告を出します。

**🇰🇷 답변**

`try` 쪽의 `return` 이나 예외를 **덮어씁니다.** 예외가 던져졌더라도 `finally` 의 `return` 으로 삼켜져 원인이 완전히 사라집니다.

그래서 `finally` 안에서는 `return` 도 `throw` 도 쓰지 않는 것이 원칙입니다. 정적 분석 도구도 경고를 냅니다.

### Q21. ジェネリクスを使う利点は何ですか？
(제네릭을 쓰는 이점)

**🇯🇵 回答**

型安全性をコンパイル時に確保できることと、キャストが不要になることです。

ジェネリクスがなかった頃は `List` から取り出すたびにキャストが必要で、間違った型を入れても実行時まで気づけませんでした。ジェネリクスはその誤りをコンパイルエラーに変えます。エラーを早い段階に移動させる仕組みだと理解しています。

**🇰🇷 답변**

타입 안전성을 컴파일 시점에 확보할 수 있다는 것과, 캐스트가 불필요해진다는 것입니다.

제네릭이 없던 시절에는 `List` 에서 꺼낼 때마다 캐스트가 필요했고, 잘못된 타입을 넣어도 실행 시점까지 알 수 없었습니다. 제네릭은 그 오류를 컴파일 에러로 바꿉니다. 오류를 이른 단계로 옮기는 장치라고 생각합니다.

---

### Q22. 型消去(type erasure)とは何で、どんな制約が生まれますか？
(타입 소거란 무엇이고 어떤 제약이 생기나)

**🇯🇵 回答**

コンパイル後にジェネリクスの型情報が消え、`Object` などに置き換えられる仕組みです。ジェネリクス導入前のコードとの互換性を保つためです。

そのため実行時に型を知ることができず、`new T[]` はできない、`instanceof List<String>` は書けない、`List<String>` と `List<Integer>` のオーバーロードは定義できない、といった制約が生まれます。

**🇰🇷 답변**

컴파일 후에 제네릭 타입 정보가 사라지고 `Object` 등으로 대체되는 구조입니다. 제네릭 도입 전 코드와의 호환성을 지키기 위해서입니다.

그래서 실행 시점에 타입을 알 수 없고, `new T[]` 는 못 하고, `instanceof List<String>` 은 못 쓰고, `List<String>` 과 `List<Integer>` 의 오버로딩은 정의할 수 없다는 제약이 생깁니다.

---

### Q23. `? extends` と `? super` はどう使い分けますか？
(? extends 와 ? super 의 사용 구분)

**🇯🇵 回答**

PECS、つまり Producer は `extends`、Consumer は `super` という原則で覚えています。

読み取り専用、つまりそのコレクションから値を取り出すだけなら `? extends T`。書き込み、つまり値を入れるなら `? super T` です。`Collections.copy(dest, src)` の宣言がそのままこの形になっています。

**🇰🇷 답변**

PECS, 즉 Producer 는 `extends`, Consumer 는 `super` 라는 원칙으로 기억하고 있습니다.

읽기 전용, 즉 그 컬렉션에서 값을 꺼내기만 한다면 `? extends T`. 쓰기, 즉 값을 넣는다면 `? super T` 입니다. `Collections.copy(dest, src)` 의 선언이 그대로 이 형태로 되어 있습니다.

---

### Q24. `enum` を使う利点は？
(enum 을 쓰는 이점)

**🇯🇵 回答**

取りうる値をコンパイル時に固定できることが最大の利点です。文字列や `int` の定数だと、想定外の値が入ってもコンパイルは通ってしまいます。

さらに Java の `enum` はクラスなので、フィールドやメソッドを持てます。区分値ごとに振る舞いを変えたい場合、`switch` を書く代わりに `enum` の抽象メソッドで表現すると分岐が消えます。シングルトンの実装にも使われます。

**🇰🇷 답변**

가질 수 있는 값을 컴파일 시점에 고정할 수 있다는 것이 가장 큰 이점입니다. 문자열이나 `int` 상수면 예상 밖의 값이 들어와도 컴파일은 통과해 버립니다.

게다가 Java 의 `enum` 은 클래스라서 필드와 메서드를 가질 수 있습니다. 구분값마다 동작을 바꾸고 싶을 때 `switch` 를 쓰는 대신 `enum` 의 추상 메서드로 표현하면 분기가 사라집니다. 싱글턴 구현에도 쓰입니다.

---

### Q25. `record` は何を解決しますか？普通のクラスとの違いは？
(record 는 무엇을 해결하나, 일반 클래스와의 차이)

**🇯🇵 回答**

データを運ぶだけのクラスのボイラープレートを消します。コンストラクタ、`equals`、`hashCode`、`toString`、アクセサが自動生成されます。

制約もあります。暗黙的に `final` で継承できず、フィールドも全て `final` です。だから DTO や値オブジェクトには向きますが、JPA のエンティティのように可変性やデフォルトコンストラクタが要るものには使えません。

**🇰🇷 답변**

데이터를 나르기만 하는 클래스의 보일러플레이트를 없앱니다. 생성자, `equals`, `hashCode`, `toString`, 접근자가 자동 생성됩니다.

제약도 있습니다. 암묵적으로 `final` 이라 상속할 수 없고 필드도 전부 `final` 입니다. 그래서 DTO 나 값 객체에는 적합하지만, JPA 엔티티처럼 가변성이나 기본 생성자가 필요한 것에는 쓸 수 없습니다.

---

### Q26. `var` はどんなときに使い、どんなときに避けますか？
(var 는 언제 쓰고 언제 피하나)

**🇯🇵 回答**

右辺を見れば型が明らかなときに使います。`var list = new ArrayList<String>()` のような場合は冗長さが減って読みやすくなります。

避けるのは型が推測しにくいときです。メソッドの戻り値をそのまま受ける場合、`var result = service.process()` では何が返ってくるか分かりません。**読み手が型を知る手がかりが行内にあるか**を基準にしています。

**🇰🇷 답변**

우변을 보면 타입이 명확할 때 씁니다. `var list = new ArrayList<String>()` 같은 경우는 장황함이 줄어 읽기 쉬워집니다.

피하는 것은 타입을 추측하기 어려울 때입니다. 메서드 반환값을 그대로 받는 경우, `var result = service.process()` 로는 무엇이 오는지 알 수 없습니다. **읽는 사람이 타입을 알 단서가 그 줄 안에 있는가**를 기준으로 삼고 있습니다.

### Q27. クラスの初期化はどんな順番で行われますか？
(클래스 초기화는 어떤 순서로 일어나나)

**🇯🇵 回答**

まず親クラスが先です。静的フィールドと `static` 初期化ブロックがクラスロード時に一度だけ、次にインスタンス生成のたびにインスタンスフィールドと初期化ブロック、最後にコンストラクタの本体が走ります。

実務で問題になるのは、コンストラクタから**オーバーライド可能なメソッドを呼ぶ**ケースです。子クラスのフィールドがまだ初期化されていない状態で子のメソッドが動くので、`null` を踏みます。

**🇰🇷 답변**

먼저 부모 클래스가 우선입니다. 정적 필드와 `static` 초기화 블록이 클래스 로드 시 한 번만, 다음으로 인스턴스 생성마다 인스턴스 필드와 초기화 블록, 마지막으로 생성자 본문이 실행됩니다.

실무에서 문제가 되는 것은 생성자에서 **오버라이드 가능한 메서드를 호출하는** 경우입니다. 자식 클래스의 필드가 아직 초기화되지 않은 상태에서 자식 메서드가 동작하므로 `null` 을 밟습니다.

### Q28. `instanceof` のパターンマッチングは何が便利ですか？
(instanceof 패턴 매칭의 편리한 점)

**🇯🇵 回答**

型チェックとキャストと変数宣言が一行にまとまります。`if (o instanceof String s)` と書けば、その中で `s` をそのまま使えます。

以前は「チェックしてキャストして代入する」を三行書く必要があり、キャスト先を書き間違える余地がありました。それがなくなります。`switch` のパターンマッチングと組み合わせると、型による分岐がかなり読みやすくなります。

**🇰🇷 답변**

타입 체크와 캐스트와 변수 선언이 한 줄로 합쳐집니다. `if (o instanceof String s)` 라고 쓰면 그 안에서 `s` 를 그대로 쓸 수 있습니다.

이전에는 "체크하고 캐스트하고 대입한다"를 세 줄 써야 했고, 캐스트 대상을 잘못 쓸 여지가 있었습니다. 그게 없어집니다. `switch` 패턴 매칭과 조합하면 타입에 의한 분기가 상당히 읽기 쉬워집니다.

### Q29. 可変長引数(varargs)を使うときの注意点は？
(가변 인자 사용 시 주의점)

**🇯🇵 回答**

内部的には配列が作られるので、呼び出しのたびに配列が生成されます。ホットパスで多用すると無駄が出ます。

もう一つはオーバーロードとの相性で、どのメソッドが選ばれるか分かりにくくなります。またジェネリクスと組み合わせると型安全でない警告が出ます。引数の数が本当に不定のときだけ使うようにしています。

**🇰🇷 답변**

내부적으로는 배열이 만들어지므로 호출할 때마다 배열이 생성됩니다. 핫 패스에서 많이 쓰면 낭비가 생깁니다.

또 하나는 오버로딩과의 상성으로, 어느 메서드가 선택되는지 알기 어려워집니다. 제네릭과 조합하면 타입 안전하지 않다는 경고도 나옵니다. 인자 개수가 정말 불특정할 때만 쓰도록 하고 있습니다.

### Q30. 内部クラスと `static` ネストクラスの違いは？
(내부 클래스와 static 중첩 클래스의 차이)

**🇯🇵 回答**

内部クラスは外部クラスのインスタンスへの参照を暗黙に持ちますが、`static` ネストクラスは持ちません。

この違いがメモリリークにつながります。内部クラスのインスタンスが長生きすると、外部クラスまで一緒に生き続けてしまいます。外部の状態を使わないなら `static` を付けるのが原則です。

**🇰🇷 답변**

내부 클래스는 외부 클래스 인스턴스에 대한 참조를 암묵적으로 갖지만, `static` 중첩 클래스는 갖지 않습니다.

이 차이가 메모리 누수로 이어집니다. 내부 클래스의 인스턴스가 오래 살면 외부 클래스까지 함께 살아남습니다. 외부의 상태를 쓰지 않는다면 `static` 을 붙이는 것이 원칙입니다.
