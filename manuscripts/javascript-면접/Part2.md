### Q26. ブラウザのレンダリングはどう進みますか？
(브라우저 렌더링 과정)

**🇯🇵 回答**

HTML をパースして DOM、CSS から CSSOM を作り、合わせてレンダーツリーを作ります。そこからレイアウトで位置と大きさを決め、ペイントして合成します。

性能で効くのは、レイアウトを何度も起こさないことです。スタイルの読み書きを交互にすると強制同期レイアウトが起きます。`transform` と `opacity` だけを変えるアニメーションはレイアウトを飛ばせるので滑らかです。

**🇰🇷 답변**

HTML 을 파싱해 DOM 을, CSS 로 CSSOM 을 만들고 합쳐서 렌더 트리를 만듭니다. 거기서 레이아웃으로 위치와 크기를 정하고 페인트한 뒤 합성합니다.

성능에서 중요한 것은 레이아웃을 여러 번 일으키지 않는 것입니다. 스타일 읽기와 쓰기를 번갈아 하면 강제 동기 레이아웃이 발생합니다. `transform` 과 `opacity` 만 바꾸는 애니메이션은 레이아웃을 건너뛸 수 있어 부드럽습니다.

### Q27. Core Web Vitals は何を見ていますか？
(Core Web Vitals 가 보는 것)

**🇯🇵 回答**

LCP は主要なコンテンツが表示されるまで、CLS はレイアウトのずれ、INP は操作への応答性です。

見方の要点は、**実ユーザーのデータで見ることと、平均ではなく 75 パーセンタイルで見ること**です。開発機の速い回線で測ると問題が見えません。改善は画像の最適化、重要リソースの先読み、長いタスクの分割から入ります。

**🇰🇷 답변**

LCP 는 주요 콘텐츠가 표시될 때까지, CLS 는 레이아웃 이동, INP 는 조작에 대한 응답성입니다.

보는 요령은 **실사용자 데이터로 보는 것과 평균이 아니라 75 백분위수로 보는 것**입니다. 개발 장비의 빠른 회선에서 재면 문제가 안 보입니다. 개선은 이미지 최적화, 중요 리소스 선로딩, 긴 태스크 분할부터 들어갑니다.

### Q28. バンドルサイズはどう小さくしますか？
(번들 크기 줄이기)

**🇯🇵 回答**

まず何が大きいのかを可視化します。想像で削るとほとんど効きません。

そのうえでコード分割で初回に要らないものを遅延読み込みし、ESM とサイドエフェクトの宣言でツリーシェイキングを効かせます。日付やアイコンのような**巨大なライブラリを丸ごと入れていないか**を確認するのが定番です。

**🇰🇷 답변**

먼저 무엇이 큰지를 시각화합니다. 짐작으로 깎으면 거의 효과가 없습니다.

그다음 코드 분할로 첫 화면에 필요 없는 것을 지연 로딩하고, ESM 과 사이드이펙트 선언으로 트리 셰이킹이 되게 합니다. 날짜나 아이콘 같은 **거대한 라이브러리를 통째로 넣고 있지 않은지** 확인하는 것이 정석입니다.

### Q29. HTTP キャッシュはどう設計しますか？
(HTTP 캐시 설계)

**🇯🇵 回答**

内容が変わらない静的アセットはファイル名にハッシュを付けて、長い `max-age` と `immutable` を付けます。HTML は都度検証させます。

`ETag` と `If-None-Match` で 304 を返せば転送量が減ります。設計の要点は「**更新をどう届けるか**」で、ハッシュ付きファイル名にしておけば古いキャッシュを踏む事故が起きません。

**🇰🇷 답변**

내용이 바뀌지 않는 정적 자산은 파일명에 해시를 붙이고 긴 `max-age` 와 `immutable` 을 줍니다. HTML 은 매번 검증하게 합니다.

`ETag` 와 `If-None-Match` 로 304 를 주면 전송량이 줄어듭니다. 설계의 요점은 "**갱신을 어떻게 전달할 것인가**" 이고, 해시 붙은 파일명으로 두면 옛 캐시를 밟는 사고가 없습니다.

### Q30. CORS はブラウザ側から見るとどういう仕組みですか？
(CORS 를 브라우저 관점에서)

**🇯🇵 回答**

別オリジンへのリクエストに対し、**サーバが許可を返さない限りブラウザがレスポンスを読ませない**仕組みです。リクエスト自体は飛んでいることもあります。

単純リクエストでなければ、先に `OPTIONS` のプリフライトが飛びます。認証情報を送るなら `credentials` の設定とサーバ側の `Allow-Credentials` が両方要り、そのときワイルドカードのオリジンは使えません。

**🇰🇷 답변**

다른 오리진으로의 요청에 대해 **서버가 허가를 주지 않는 한 브라우저가 응답을 읽지 못하게** 하는 장치입니다. 요청 자체는 나가 있는 경우도 있습니다.

단순 요청이 아니면 먼저 `OPTIONS` 프리플라이트가 나갑니다. 인증 정보를 보내려면 `credentials` 설정과 서버 쪽 `Allow-Credentials` 가 둘 다 필요하고, 그때는 와일드카드 오리진을 쓸 수 없습니다.

### Q31. CSRF はどう防ぎますか？
(CSRF 방어)

**🇯🇵 回答**

Cookie による自動送信を悪用する攻撃なので、`SameSite` 属性で他サイトからの送信を止めるのが第一です。加えて CSRF トークンを検証します。

トークンを `Authorization` ヘッダで送る方式なら、自動送信されないので CSRF の主な経路は塞がります。代わりに XSS の影響が大きくなるので、どちらを選んでもリスクの形が変わるだけだと理解しておきます。

**🇰🇷 답변**

쿠키의 자동 전송을 악용하는 공격이므로 `SameSite` 속성으로 타 사이트에서의 전송을 막는 것이 첫째입니다. 여기에 CSRF 토큰을 검증합니다.

토큰을 `Authorization` 헤더로 보내는 방식이면 자동 전송되지 않아 CSRF 의 주 경로는 막힙니다. 대신 XSS 의 영향이 커지므로, 어느 쪽을 골라도 위험의 형태가 바뀔 뿐이라고 이해해 둡니다.

### Q32. Node.js のイベントループはブラウザと何が違いますか？
(Node 의 이벤트 루프와 브라우저의 차이)

**🇯🇵 回答**

基本の考え方は同じですが、Node は libuv のフェーズに分かれています。タイマー、保留中のコールバック、poll、check、close の順に回ります。

`setImmediate` は check フェーズ、`process.nextTick` はフェーズの合間に最優先で走ります。`nextTick` を再帰的に積むと他が動けなくなるので、実務ではまず使いません。

**🇰🇷 답변**

기본 사고방식은 같지만 Node 는 libuv 의 페이즈로 나뉩니다. 타이머, 보류 콜백, poll, check, close 순으로 돕니다.

`setImmediate` 는 check 페이즈, `process.nextTick` 은 페이즈 사이에서 최우선으로 실행됩니다. `nextTick` 을 재귀적으로 쌓으면 다른 것이 못 돌게 되므로 실무에서는 거의 쓰지 않습니다.

### Q33. Node で CPU を使う処理はどう扱いますか？
(Node 에서 CPU 작업 처리)

**🇯🇵 回答**

イベントループを止めるので、そのまま書いてはいけません。一つの重い同期処理が全リクエストの応答を止めます。

対策は `worker_threads` に逃がすか、別プロセス・別サービスに切り出すことです。CPU コアを使い切るための `cluster` は、**並行性ではなく多重化**の手段だと区別して説明します。

**🇰🇷 답변**

이벤트 루프를 멈추므로 그대로 쓰면 안 됩니다. 무거운 동기 처리 하나가 모든 요청의 응답을 멈춥니다.

대책은 `worker_threads` 로 넘기거나 별도 프로세스·서비스로 떼어내는 것입니다. CPU 코어를 다 쓰기 위한 `cluster` 는 **동시성이 아니라 다중화** 수단이라고 구분해 설명합니다.

### Q34. ストリームとバックプレッシャーについて説明してください。
(스트림과 배압)

**🇯🇵 回答**

大きなデータを一度にメモリへ載せず、少しずつ流す仕組みです。読み込み側が速すぎると書き込み側が追いつかないので、`pipe` は内部で流量を調整します。

自分で `data` イベントを扱うときは、`write` の戻り値が `false` なら `drain` を待ちます。これを無視するとメモリが膨らみます。実務では `pipeline` を使ってエラー処理と後始末を任せます。

**🇰🇷 답변**

큰 데이터를 한 번에 메모리에 올리지 않고 조금씩 흘리는 구조입니다. 읽는 쪽이 너무 빠르면 쓰는 쪽이 못 따라가므로 `pipe` 가 내부에서 유량을 조절합니다.

직접 `data` 이벤트를 다룰 때는 `write` 의 반환값이 `false` 면 `drain` 을 기다립니다. 이걸 무시하면 메모리가 부풉니다. 실무에서는 `pipeline` 을 써서 에러 처리와 뒷정리를 맡깁니다.

### Q35. 外部 API を呼ぶときに必ずすることは？
(외부 API 호출 시 반드시 하는 것)

**🇯🇵 回答**

タイムアウトの設定です。`fetch` は既定でタイムアウトしないので、`AbortSignal.timeout` などで必ず切ります。

その上でリトライは冪等な操作に限り、指数バックオフとジッターを入れます。連続失敗にはサーキットブレーカーで早く諦めます。相手が遅いだけで自分のイベントループやコネクションが枯れるのを防ぐのが目的です。

**🇰🇷 답변**

타임아웃 설정입니다. `fetch` 는 기본적으로 타임아웃되지 않으므로 `AbortSignal.timeout` 등으로 반드시 끊습니다.

그 위에 재시도는 멱등한 조작에만 하고 지수 백오프와 지터를 넣습니다. 연속 실패에는 서킷 브레이커로 빨리 포기합니다. 상대가 느릴 뿐인데 내 이벤트 루프나 커넥션이 마르는 것을 막는 게 목적입니다.

### Q36. エラーハンドリングで気をつけていることは？
(에러 처리에서 주의하는 것)

**🇯🇵 回答**

握りつぶさないことです。`catch` して何もしないと、原因が分からないまま壊れた状態で動き続けます。

Node では `unhandledRejection` と `uncaughtException` を監視し、ログを残してから安全に終了します。エラーには文脈を足して再送出し、`cause` を使って元の原因を保ちます。ユーザーには内部情報を出しません。

**🇰🇷 답변**

삼키지 않는 것입니다. `catch` 해 놓고 아무것도 안 하면 원인을 모른 채 깨진 상태로 계속 돕니다.

Node 에서는 `unhandledRejection` 과 `uncaughtException` 을 감시해 로그를 남기고 안전하게 종료합니다. 에러에는 문맥을 더해 다시 던지고 `cause` 로 원래 원인을 보존합니다. 사용자에게 내부 정보는 내보내지 않습니다.

### Q37. 依存関係の管理で気をつけることは？
(의존성 관리 주의점)

**🇯🇵 回答**

ロックファイルをコミットして、CI では `npm ci` のように**ロック通りに入れる**コマンドを使います。そうしないとビルドごとに違うものが入ります。

それから依存の数そのものを警戒します。小さなユーティリティのために大きな依存木を持つと、脆弱性対応の負担が増えます。監査を CI に入れて、更新は定期的に小さく回します。

**🇰🇷 답변**

락 파일을 커밋하고 CI 에서는 `npm ci` 처럼 **락 그대로 설치하는** 명령을 씁니다. 그러지 않으면 빌드마다 다른 것이 들어옵니다.

그리고 의존성 개수 자체를 경계합니다. 작은 유틸리티 때문에 큰 의존 트리를 가지면 취약점 대응 부담이 늘어납니다. 감사를 CI 에 넣고 업데이트는 정기적으로 작게 돌립니다.

### Q38. プロトタイプ汚染とは何ですか？
(프로토타입 오염)

**🇯🇵 回答**

外部入力のキーに `__proto__` や `constructor` が混ざり、`Object.prototype` を書き換えてしまう攻撃です。アプリ全体の挙動が変わります。

深いマージやクエリのパースで起きやすいので、キーを検証するか `Object.create(null)` の辞書を使います。ライブラリを使う場合は、この対策が入っているバージョンかを確認します。

**🇰🇷 답변**

외부 입력의 키에 `__proto__` 나 `constructor` 가 섞여 `Object.prototype` 을 덮어쓰는 공격입니다. 앱 전체 동작이 바뀝니다.

깊은 병합이나 쿼리 파싱에서 일어나기 쉬우므로 키를 검증하거나 `Object.create(null)` 사전을 씁니다. 라이브러리를 쓴다면 이 대책이 들어간 버전인지 확인합니다.

### Q39. テストはどう書いていますか？
(테스트 작성 방식)

**🇯🇵 回答**

純粋な関数はそのまま単体テストにします。DOM が絡むところは、実装の内部ではなく**ユーザーから見える振る舞い**を対象にします。

外部 API はモックしますが、モックしすぎると結合の壊れに気づけません。重要な経路は実際にリクエストが飛ぶ形か、契約テストで守ります。テストは仕様書として読めることを意識します。

**🇰🇷 답변**

순수 함수는 그대로 단위 테스트로 만듭니다. DOM 이 얽힌 곳은 구현 내부가 아니라 **사용자에게 보이는 동작**을 대상으로 합니다.

외부 API 는 목으로 만들되 너무 많이 만들면 결합이 깨진 것을 못 알아챕니다. 중요한 경로는 실제 요청이 나가는 형태나 계약 테스트로 지킵니다. 테스트는 명세서로 읽히도록 의식합니다.

### Q40. SPA と SSR はどう選びますか？
(SPA 와 SSR 선택)

**🇯🇵 回答**

初回表示と SEO が重要なら SSR、ログイン後の操作中心なら SPA で十分なことが多いです。

判断材料は要件です。ニュースや商品ページのように検索から入ってくるものは SSR、管理画面のように認証の内側で回すものは SPA。実際にはページ単位で混在させるのが現実的です。

**🇰🇷 답변**

첫 화면 표시와 SEO 가 중요하면 SSR, 로그인 이후 조작 중심이면 SPA 로 충분한 경우가 많습니다.

판단 재료는 요구사항입니다. 뉴스나 상품 페이지처럼 검색으로 들어오는 것은 SSR, 관리 화면처럼 인증 안쪽에서 도는 것은 SPA. 실제로는 페이지 단위로 섞는 것이 현실적입니다.

### Q41. 認証情報をフロントでどう扱いますか？
(프런트에서 인증 정보 취급)

**🇯🇵 回答**

`HttpOnly` の Cookie に置くのが基本です。JavaScript から読めないので XSS で直接盗まれません。

トークンをメモリに持つ方式もありますが、リロードで消えるので更新の仕組みが要ります。いずれにせよ、**アクセストークンは短命にしてリフレッシュで回す**のが前提です。ログアウトで確実に無効化できる経路も用意します。

**🇰🇷 답변**

`HttpOnly` 쿠키에 두는 것이 기본입니다. 자바스크립트에서 읽을 수 없어 XSS 로 직접 탈취되지 않습니다.

토큰을 메모리에 갖는 방식도 있지만 새로고침에 사라져 갱신 장치가 필요합니다. 어느 쪽이든 **액세스 토큰은 짧게 두고 리프레시로 돌리는 것**이 전제입니다. 로그아웃으로 확실히 무효화하는 경로도 마련합니다.

### Q42. 大量の DOM 更新はどう最適化しますか？
(대량 DOM 갱신 최적화)

**🇯🇵 回答**

一件ずつ触らず、まとめて反映します。`DocumentFragment` に組んでから一度だけ挿入するか、フレームワークならまとめて再描画させます。

読み書きの順序も重要です。位置やサイズを読む処理と書く処理を交互にすると、そのたびにレイアウトが強制されます。読み取りをまとめてから書き込みます。長いリストは仮想スクロールで見える分だけ描きます。

**🇰🇷 답변**

하나씩 건드리지 않고 모아서 반영합니다. `DocumentFragment` 에 조립한 뒤 한 번만 삽입하거나, 프레임워크라면 모아서 다시 그리게 합니다.

읽기와 쓰기의 순서도 중요합니다. 위치나 크기를 읽는 처리와 쓰는 처리를 번갈아 하면 그때마다 레이아웃이 강제됩니다. 읽기를 모은 뒤 쓰기를 합니다. 긴 목록은 가상 스크롤로 보이는 만큼만 그립니다.

---

### Q43. Web Worker はいつ使いますか？
(Web Worker 사용 시점)

**🇯🇵 回答**

メインスレッドを塞ぐ計算があるときです。暗号処理、大きな JSON の解析、画像処理などを別スレッドに逃がすと、操作の応答性が保てます。

DOM は触れないので、やり取りはメッセージです。データのコピーコストがあるので、`Transferable` や `SharedArrayBuffer` を使うか、そもそも渡す量を減らす設計にします。

**🇰🇷 답변**

메인 스레드를 막는 계산이 있을 때입니다. 암호 처리, 큰 JSON 파싱, 이미지 처리 등을 별 스레드로 넘기면 조작 응답성을 지킬 수 있습니다.

DOM 은 만질 수 없으므로 주고받기는 메시지입니다. 데이터 복사 비용이 있으니 `Transferable` 이나 `SharedArrayBuffer` 를 쓰거나, 애초에 넘기는 양을 줄이는 설계로 갑니다.

---

### Q44. 日時とタイムゾーンはどう扱いますか？
(날짜·시간대 취급)

**🇯🇵 回答**

保存と通信は UTC の ISO 8601 文字列で統一し、表示のときだけローカルに変換します。

`Date` は扱いづらく、月が 0 始まりだったりパースが環境依存だったりします。実務ではライブラリを使うか、標準の `Intl` と `Temporal` を使います。サーバのタイムゾーンに依存する計算を書かないことが一番大事です。

**🇰🇷 답변**

저장과 통신은 UTC 의 ISO 8601 문자열로 통일하고 표시할 때만 로컬로 변환합니다.

`Date` 는 다루기 까다로워 월이 0 부터 시작하거나 파싱이 환경 의존적입니다. 실무에서는 라이브러리를 쓰거나 표준 `Intl` 과 `Temporal` 을 씁니다. 서버 시간대에 의존하는 계산을 쓰지 않는 것이 가장 중요합니다.

---

### Q45. 文字列の扱いで気をつけることは？
(문자열 처리 주의점)

**🇯🇵 回答**

`length` は UTF-16 のコード単位の数なので、絵文字や一部の漢字は 2 と数えられます。文字数を数えるなら `Intl.Segmenter` やスプレッドで分けます。

比較の前には `normalize()` を掛けます。見た目が同じでも合成の仕方が違うと一致しません。入力の受け口で正規化しておくと、後段の比較や重複判定が安定します。

**🇰🇷 답변**

`length` 는 UTF-16 코드 단위 수라서 이모지나 일부 한자는 2 로 셉니다. 글자 수를 세려면 `Intl.Segmenter` 나 스프레드로 나눕니다.

비교 전에는 `normalize()` 를 겁니다. 겉보기가 같아도 결합 방식이 다르면 일치하지 않습니다. 입력 수신부에서 정규화해 두면 이후의 비교나 중복 판정이 안정됩니다.

---

### Q46. ログとモニタリングはどうしていますか？
(로그와 모니터링)

**🇯🇵 回答**

フロントはエラー収集ツールに送り、ソースマップを紐づけて元のコードで読めるようにします。ユーザーの操作の文脈も一緒に残します。

サーバ側は構造化ログにして、リクエスト ID でフロントからバックエンドまで追えるようにします。個人情報やトークンをログに入れないことは必ず確認します。

**🇰🇷 답변**

프런트는 에러 수집 도구로 보내고 소스맵을 연결해 원래 코드로 읽히게 합니다. 사용자 조작의 문맥도 함께 남깁니다.

서버 쪽은 구조화 로그로 만들어 요청 ID 로 프런트부터 백엔드까지 추적되게 합니다. 개인정보나 토큰을 로그에 넣지 않는 것은 반드시 확인합니다.

---

### Q47. 本番でだけ再現するバグはどう調べますか？
(운영에서만 재현되는 버그 조사)

**🇯🇵 回答**

まず再現条件を絞ります。特定のブラウザか、特定の回線速度か、特定のデータか。エラー収集ツールの端末情報とユーザー操作の履歴が手がかりになります。

ソースマップを本番に紐づけておくこと、機能フラグで段階的に出すこと、そして**ログに十分な文脈があること**が、後から調べられるかを決めます。

**🇰🇷 답변**

먼저 재현 조건을 좁힙니다. 특정 브라우저인지, 특정 회선 속도인지, 특정 데이터인지. 에러 수집 도구의 단말 정보와 사용자 조작 이력이 단서가 됩니다.

소스맵을 운영에 연결해 두는 것, 기능 플래그로 단계적으로 내보내는 것, 그리고 **로그에 충분한 문맥이 있는 것**이 나중에 조사할 수 있는지를 결정합니다.

### Q48. パフォーマンスの改善はどこから手を付けますか？
(성능 개선 착수 순서)

**🇯🇵 回答**

測ってから決めます。実ユーザーのデータでどの指標が悪いのかを見て、そこに効く施策だけをやります。

順番としては、まず送るものを減らす、次に送る回数を減らす、最後に描画を軽くする、という順で効きやすいです。**改善したら同じ指標で再測定する**ところまでを一組にしています。

**🇰🇷 답변**

재고 나서 정합니다. 실사용자 데이터로 어느 지표가 나쁜지를 보고 거기에 듣는 조치만 합니다.

순서로는 먼저 보내는 것을 줄이고, 다음에 보내는 횟수를 줄이고, 마지막에 그리기를 가볍게 하는 순으로 효과가 잘 납니다. **개선했으면 같은 지표로 다시 측정하는 것**까지를 한 묶음으로 합니다.

---

### Q49. ランタイムやフレームワークの選定はどう考えますか？
(런타임·프레임워크 선정)

**🇯🇵 回答**

新しさより、チームが運用できるかと情報の多さを重視します。エコシステムと長期サポートがあるかを見ます。

Deno や Bun のような選択肢も出ていますが、既存の資産と採用のしやすさを考えると、まだ Node が既定です。導入するなら小さい範囲で試し、**戻せる形**にしてから広げます。

**🇰🇷 답변**

새로움보다 팀이 운용할 수 있는지와 정보의 많음을 중시합니다. 생태계와 장기 지원이 있는지를 봅니다.

Deno 나 Bun 같은 선택지도 나왔지만 기존 자산과 채용 용이성을 생각하면 아직 Node 가 기본입니다. 도입한다면 작은 범위에서 시험하고 **되돌릴 수 있는 형태**로 만든 뒤 넓힙니다.

---

### Q50. 新しい仕様やバージョンにどう追随していますか？
(새 사양·버전 추종)

**🇯🇵 回答**

まず対応状況を確認します。書けることと、対象ブラウザで動くことは別だからです。ブラウザの対応表と、Node なら LTS のスケジュールを見ます。

チームには「使ってよい範囲」を lint の設定として書き下します。口頭の合意よりも機械で強制する方が確実です。大きな更新は CI に新バージョンのジョブを並行で足して、通ってから切り替えます。

**🇰🇷 답변**

먼저 지원 상황을 확인합니다. 쓸 수 있다는 것과 대상 브라우저에서 도는 것은 다르기 때문입니다. 브라우저 지원표와 Node 라면 LTS 일정을 봅니다.

팀에는 "써도 되는 범위"를 lint 설정으로 적어 둡니다. 구두 합의보다 기계로 강제하는 편이 확실합니다. 큰 업데이트는 CI 에 새 버전 잡을 병행으로 추가해 통과한 뒤 전환합니다.
