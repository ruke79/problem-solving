### Q1. `var`・`let`・`const` の違いは？
(var·let·const 의 차이)

**🇯🇵 回答**

`var` は関数スコープで巻き上げられ、宣言前でも `undefined` として参照できてしまいます。`let` と `const` はブロックスコープで、宣言前の参照は TDZ でエラーになります。

`const` は再代入を禁止するだけで、中身の変更は防ぎません。基本は `const`、再代入が要るときだけ `let`、`var` は使いません。

**🇰🇷 답변**

`var` 는 함수 스코프이고 호이스팅되어 선언 전에도 `undefined` 로 참조됩니다. `let` 과 `const` 는 블록 스코프이고 선언 전 참조는 TDZ 로 에러가 납니다.

`const` 는 재대입을 막을 뿐 내용 변경은 막지 않습니다. 기본은 `const`, 재대입이 필요할 때만 `let`, `var` 는 쓰지 않습니다.

### Q2. `==` と `===` はどう違いますか？
(== 와 === 의 차이)

**🇯🇵 回答**

`==` は型変換をしてから比較し、`===` は型も含めて比較します。`0 == "0"` が真になるような挙動が事故のもとです。

原則 `===` を使います。例外は `== null` で、これは `null` と `undefined` の両方を一度に判定できる慣用句として使うことがあります。

**🇰🇷 답변**

`==` 는 형 변환을 한 뒤 비교하고 `===` 는 타입까지 포함해 비교합니다. `0 == "0"` 이 참이 되는 동작이 사고의 원인입니다.

원칙은 `===` 입니다. 예외는 `== null` 로, `null` 과 `undefined` 를 한 번에 판정하는 관용구로 쓰기도 합니다.

### Q3. クロージャとは何ですか？
(클로저란)

**🇯🇵 回答**

関数が定義されたときのスコープを覚えたまま持ち歩く仕組みです。外側の変数を、関数が生きている限り参照できます。

カウンタやプライベート変数、モジュールパターンに使います。注意点は、DOM や大きなオブジェクトを掴んだままにすると解放されず、メモリリークになることです。

**🇰🇷 답변**

함수가 정의될 때의 스코프를 기억한 채 들고 다니는 구조입니다. 바깥 변수를 함수가 살아 있는 한 참조할 수 있습니다.

카운터나 프라이빗 변수, 모듈 패턴에 씁니다. 주의점은 DOM 이나 큰 객체를 잡은 채로 두면 해제되지 않아 메모리 누수가 된다는 것입니다.

### Q4. `this` は何で決まりますか？
(this 는 무엇으로 정해지나)

**🇯🇵 回答**

呼び出し方で決まります。メソッド呼び出しならレシーバ、単独呼び出しなら `undefined`(strict)、`new` ならその新しいインスタンス、`call`/`apply`/`bind` なら指定したものです。

アロー関数だけが例外で、**自分の `this` を持たず定義時の外側を使います**。だからコールバックではアロー関数が安全で、逆にメソッドやプロトタイプの定義には向きません。

**🇰🇷 답변**

호출 방식으로 정해집니다. 메서드 호출이면 리시버, 단독 호출이면 `undefined`(strict), `new` 면 새 인스턴스, `call`/`apply`/`bind` 면 지정한 것입니다.

화살표 함수만 예외로 **자기 `this` 를 갖지 않고 정의 시점의 바깥을 씁니다.** 그래서 콜백에는 화살표 함수가 안전하고, 반대로 메서드나 프로토타입 정의에는 맞지 않습니다.

### Q5. プロトタイプチェーンとは何ですか？
(프로토타입 체인)

**🇯🇵 回答**

オブジェクトはプロトタイプへの参照を持ち、プロパティが見つからなければそこをたどって探します。この連鎖がプロトタイプチェーンです。

`class` 構文はこの仕組みの糖衣です。継承もプロトタイプのつなぎ替えで実現されているので、`class` を使っていても中身はプロトタイプだと理解しておくと、`instanceof` の挙動などが説明できます。

**🇰🇷 답변**

객체는 프로토타입에 대한 참조를 갖고, 프로퍼티를 못 찾으면 그쪽을 따라가며 찾습니다. 이 연쇄가 프로토타입 체인입니다.

`class` 문법은 이 구조의 문법 설탕입니다. 상속도 프로토타입 연결로 구현되므로, `class` 를 쓰더라도 속은 프로토타입이라고 이해해 두면 `instanceof` 의 동작 같은 것을 설명할 수 있습니다.

### Q6. イベントループはどう動きますか？
(이벤트 루프의 동작)

**🇯🇵 回答**

コールスタックが空になると、まずマイクロタスクキューを**空になるまで**処理し、その後マクロタスクを一つ取ります。

Promise のコールバックはマイクロタスク、`setTimeout` はマクロタスクです。だから `setTimeout(fn, 0)` より Promise の方が先に走ります。マイクロタスクの中で再帰的にマイクロタスクを積むと、レンダリングが止まる点も要注意です。

**🇰🇷 답변**

콜 스택이 비면 먼저 마이크로태스크 큐를 **빌 때까지** 처리하고, 그다음 매크로태스크를 하나 꺼냅니다.

Promise 콜백은 마이크로태스크, `setTimeout` 은 매크로태스크입니다. 그래서 `setTimeout(fn, 0)` 보다 Promise 가 먼저 돕니다. 마이크로태스크 안에서 재귀적으로 마이크로태스크를 쌓으면 렌더링이 멈추는 점도 주의해야 합니다.

### Q7. Promise の状態と `then` の連鎖について説明してください。
(Promise 의 상태와 then 체인)

**🇯🇵 回答**

pending から fulfilled か rejected へ一度だけ遷移します。`then` は新しい Promise を返すので連鎖でき、途中で返した値が次に渡ります。

`then` の中で Promise を返すと、それが解決されてから次に進みます。ここを忘れて `return` を書かないと、待たずに先へ進んでしまうというのがよくあるバグです。

**🇰🇷 답변**

pending 에서 fulfilled 나 rejected 로 한 번만 전이합니다. `then` 은 새 Promise 를 반환하므로 체이닝이 되고, 중간에 반환한 값이 다음으로 넘어갑니다.

`then` 안에서 Promise 를 반환하면 그것이 해결된 뒤 다음으로 갑니다. 이걸 잊고 `return` 을 안 쓰면 기다리지 않고 진행해 버리는 것이 흔한 버그입니다.

### Q8. `Promise.all` と `allSettled` はどう使い分けますか？
(Promise.all 과 allSettled 사용 구분)

**🇯🇵 回答**

`all` はどれか一つでも失敗した時点で全体が reject になります。`allSettled` は全部の結果を成功・失敗込みで返します。

「全部そろわないと意味がない」処理は `all`、「取れたものだけで画面を作る」処理は `allSettled` です。`race` は最初の一つ、`any` は最初の成功を取ります。

**🇰🇷 답변**

`all` 은 하나라도 실패하는 시점에 전체가 reject 됩니다. `allSettled` 는 전부의 결과를 성공·실패 포함해 돌려줍니다.

"전부 갖춰지지 않으면 의미가 없는" 처리는 `all`, "받은 것만으로 화면을 만드는" 처리는 `allSettled` 입니다. `race` 는 가장 먼저 끝난 하나, `any` 는 첫 성공을 취합니다.

### Q9. `async`/`await` のエラー処理はどう書きますか？
(async/await 의 에러 처리)

**🇯🇵 回答**

`try`/`catch` で囲みます。`await` した Promise が reject するとその場で例外になるので、同期コードと同じ形で書けます。

注意点は、`await` を付け忘れた Promise は catch されないことです。それが未処理の rejection になります。Node なら `unhandledRejection` を監視して、握りつぶさないようにします。

**🇰🇷 답변**

`try`/`catch` 로 감쌉니다. `await` 한 Promise 가 reject 되면 그 자리에서 예외가 되므로 동기 코드와 같은 형태로 쓸 수 있습니다.

주의점은 `await` 를 빠뜨린 Promise 는 catch 되지 않는다는 것입니다. 그것이 미처리 rejection 이 됩니다. Node 라면 `unhandledRejection` 을 감시해 삼키지 않도록 합니다.

### Q10. 複数の非同期処理を並行に走らせるときの注意は？
(여러 비동기 처리를 병행할 때의 주의)

**🇯🇵 回答**

`for` の中で `await` すると直列になります。並行にしたいなら Promise を先に作って `Promise.all` に渡します。

ただし無制限に並行にすると、相手のサーバや自分のコネクション上限を壊します。件数が多いときは同時実行数を制限する仕組みを入れます。速さより**相手に迷惑をかけないこと**を優先します。

**🇰🇷 답변**

`for` 안에서 `await` 하면 직렬이 됩니다. 병행으로 하려면 Promise 를 먼저 만들어 `Promise.all` 에 넘깁니다.

다만 무제한으로 병행하면 상대 서버나 자기 연결 상한을 깨뜨립니다. 건수가 많을 때는 동시 실행 수를 제한하는 장치를 넣습니다. 속도보다 **상대에게 폐를 끼치지 않는 것**을 우선합니다.

### Q11. 浅いコピーと深いコピーはどうしますか？
(얕은 복사와 깊은 복사)

**🇯🇵 回答**

スプレッド構文や `Object.assign` は一段目だけの浅いコピーです。ネストした中身は同じ参照を共有します。

深いコピーは `structuredClone` が標準で使えるようになりました。`JSON.parse(JSON.stringify(...))` は手軽ですが、`undefined` や `Date`、循環参照で壊れるので、知った上で使い分けます。

**🇰🇷 답변**

스프레드 구문이나 `Object.assign` 은 한 겹만의 얕은 복사입니다. 중첩된 내용은 같은 참조를 공유합니다.

깊은 복사는 `structuredClone` 을 표준으로 쓸 수 있게 됐습니다. `JSON.parse(JSON.stringify(...))` 는 간편하지만 `undefined` 나 `Date`, 순환 참조에서 깨지므로 알고 나서 구분해 씁니다.

### Q12. `null` と `undefined` はどう使い分けますか？
(null 과 undefined 구분)

**🇯🇵 回答**

`undefined` は「まだ値がない」、`null` は「意図的に空である」を表します。未初期化の変数や存在しないプロパティは `undefined` です。

判定には optional chaining と nullish 合体演算子を使います。`??` は `0` や空文字を残せるので、`||` を使って `0` が消えるバグを避けられます。

**🇰🇷 답변**

`undefined` 는 "아직 값이 없다", `null` 은 "의도적으로 비었다"를 나타냅니다. 초기화되지 않은 변수나 없는 프로퍼티는 `undefined` 입니다.

판정에는 옵셔널 체이닝과 nullish 병합 연산자를 씁니다. `??` 는 `0` 이나 빈 문자열을 살려 주므로, `||` 를 써서 `0` 이 사라지는 버그를 피할 수 있습니다.

### Q13. 配列の `map`・`filter`・`reduce` はどう使い分けますか？
(map·filter·reduce 사용 구분)

**🇯🇵 回答**

変換なら `map`、絞り込みなら `filter`、一つの値にまとめるなら `reduce` です。いずれも元の配列を変更しません。

`reduce` は何でも書けてしまうので、読みにくくなるなら普通のループにします。あと `forEach` は途中で抜けられないので、早期 return が要るなら `for...of` を使います。

**🇰🇷 답변**

변환이면 `map`, 걸러내기면 `filter`, 하나의 값으로 모으면 `reduce` 입니다. 셋 다 원본 배열을 바꾸지 않습니다.

`reduce` 는 무엇이든 쓸 수 있어서 읽기 어려워지면 평범한 루프로 바꿉니다. 그리고 `forEach` 는 중간에 빠져나올 수 없으므로 조기 반환이 필요하면 `for...of` 를 씁니다.

### Q14. 配列を破壊するメソッドとそうでないメソッドの区別は？
(배열을 변형하는 메서드와 아닌 것)

**🇯🇵 回答**

`push`・`splice`・`sort`・`reverse` は元の配列を変更します。`map`・`filter`・`slice`・`concat` は新しい配列を返します。

`sort` は特に注意が必要で、その場で並べ替える上に**既定は文字列比較**です。数値を並べるなら比較関数を渡します。最近は `toSorted` のような非破壊版も使えます。

**🇰🇷 답변**

`push`·`splice`·`sort`·`reverse` 는 원본 배열을 바꿉니다. `map`·`filter`·`slice`·`concat` 은 새 배열을 돌려줍니다.

`sort` 는 특히 주의해야 하는데, 제자리에서 정렬하는 데다 **기본이 문자열 비교**입니다. 숫자를 정렬하려면 비교 함수를 넘깁니다. 요즘은 `toSorted` 같은 비파괴 버전도 쓸 수 있습니다.

### Q15. `Map` とオブジェクトはどう使い分けますか？
(Map 과 객체의 구분)

**🇯🇵 回答**

キーが文字列やシンボル以外になるなら `Map`、動的に増減するなら `Map`、構造が決まっているレコードならオブジェクトです。

`Map` はキーの順序が保証され、サイズが `size` で取れ、プロトタイプ由来のキーと衝突しません。オブジェクトを辞書として使うと `__proto__` のようなキーで事故が起きます。

**🇰🇷 답변**

키가 문자열이나 심볼 이외가 되면 `Map`, 동적으로 늘고 줄면 `Map`, 구조가 정해진 레코드면 객체입니다.

`Map` 은 키 순서가 보장되고 `size` 로 크기를 얻을 수 있으며 프로토타입 유래 키와 충돌하지 않습니다. 객체를 사전처럼 쓰면 `__proto__` 같은 키에서 사고가 납니다.

### Q16. CommonJS と ES Modules の違いは？
(CommonJS 와 ES Modules 의 차이)

**🇯🇵 回答**

CommonJS は同期的に読み込み、実行時に解決します。ESM は静的に解析されるので、ツリーシェイキングやトップレベル `await` が使えます。

混在させると解決順やデフォルトエクスポートの扱いで問題が出ます。新規は ESM に寄せて、必要なら動的 `import()` で橋渡しします。

**🇰🇷 답변**

CommonJS 는 동기적으로 읽고 실행 시점에 해석합니다. ESM 은 정적으로 분석되므로 트리 셰이킹과 톱레벨 `await` 를 쓸 수 있습니다.

섞으면 해석 순서나 기본 내보내기 처리에서 문제가 납니다. 신규는 ESM 으로 맞추고, 필요하면 동적 `import()` 로 다리를 놓습니다.

### Q17. ジェネレータとイテレータは何に使いますか？
(제너레이터와 이터레이터의 용도)

**🇯🇵 回答**

`Symbol.iterator` を実装すれば `for...of` で回せます。ジェネレータは `function*` と `yield` でイテレータを簡単に作る仕組みです。

大量データを少しずつ流す、無限列を扱う、非同期の順次処理を書く、といった場面で使います。実務では `for await...of` と非同期イテレータでストリームを扱うことが多いです。

**🇰🇷 답변**

`Symbol.iterator` 를 구현하면 `for...of` 로 돌 수 있습니다. 제너레이터는 `function*` 과 `yield` 로 이터레이터를 쉽게 만드는 장치입니다.

대량 데이터를 조금씩 흘리거나, 무한 수열을 다루거나, 비동기 순차 처리를 쓸 때 씁니다. 실무에서는 `for await...of` 와 비동기 이터레이터로 스트림을 다루는 경우가 많습니다.

### Q18. デバウンスとスロットルの違いは？
(디바운스와 스로틀의 차이)

**🇯🇵 回答**

デバウンスは「最後の呼び出しから一定時間おいて一度だけ」、スロットルは「一定間隔で最大一回」です。

検索窓の入力補完はデバウンス、スクロールやリサイズの追従はスロットルが向きます。どちらもタイマーを持つので、コンポーネントの破棄時にクリアしないとリークします。

**🇰🇷 답변**

디바운스는 "마지막 호출로부터 일정 시간 뒤 한 번만", 스로틀은 "일정 간격으로 최대 한 번"입니다.

검색창 입력 자동완성은 디바운스, 스크롤·리사이즈 추종은 스로틀이 맞습니다. 둘 다 타이머를 가지므로 컴포넌트 파기 시 정리하지 않으면 누수가 됩니다.

### Q19. JavaScript でメモリリークはどんなときに起きますか？
(자바스크립트의 메모리 누수)

**🇯🇵 回答**

一番多いのはイベントリスナーやタイマーの解除漏れです。DOM を消してもリスナーが参照を持っていると回収されません。

他には、グローバルなキャッシュに入れっぱなし、クロージャが大きなオブジェクトを掴んだまま、`setInterval` の止め忘れです。調査は DevTools のヒープスナップショットを二点取って差分を見ます。

**🇰🇷 답변**

가장 많은 것은 이벤트 리스너와 타이머의 해제 누락입니다. DOM 을 지워도 리스너가 참조를 갖고 있으면 회수되지 않습니다.

그 밖에는 전역 캐시에 계속 담아 두기, 클로저가 큰 객체를 잡은 채로 두기, `setInterval` 정지 누락입니다. 조사는 DevTools 힙 스냅샷을 두 지점에서 떠 차분을 봅니다.

### Q20. 数値の精度で気をつけることは？
(숫자 정밀도 주의점)

**🇯🇵 回答**

`0.1 + 0.2` が `0.3` にならないのは IEEE 754 の二進浮動小数点だからです。金額の計算には使いません。

対策は、最小単位の整数で持つか、`BigInt` や十進の専用ライブラリを使うことです。それから、サーバが返す 64 ビット整数の ID を数値で受けると精度が落ちるので、文字列で受け取ります。

**🇰🇷 답변**

`0.1 + 0.2` 가 `0.3` 이 되지 않는 것은 IEEE 754 이진 부동소수점이기 때문입니다. 금액 계산에는 쓰지 않습니다.

대책은 최소 단위 정수로 갖거나 `BigInt`·십진 전용 라이브러리를 쓰는 것입니다. 그리고 서버가 주는 64비트 정수 ID 를 숫자로 받으면 정밀도가 깨지므로 문자열로 받습니다.

### Q21. TypeScript を使う理由は何ですか？
(타입스크립트를 쓰는 이유)

**🇯🇵 回答**

実行しないと分からなかったエラーを、書いている最中に見つけられることです。リファクタリングの安全性と、補完によるドキュメント効果も大きいです。

コンパイル後は型が消えるので、**実行時の検証は別に必要**です。外部から来る JSON は型注釈を付けただけでは保証されないので、境界でスキーマ検証をします。

**🇰🇷 답변**

실행해야 알 수 있던 에러를 쓰는 도중에 찾을 수 있다는 점입니다. 리팩터링 안전성과 자동완성에 따른 문서 효과도 큽니다.

컴파일 후에는 타입이 사라지므로 **런타임 검증은 따로 필요합니다.** 외부에서 오는 JSON 은 타입 주석만으로 보장되지 않으니 경계에서 스키마 검증을 합니다.

### Q22. `any` と `unknown` はどう違いますか？
(any 와 unknown 의 차이)

**🇯🇵 回答**

`any` は型チェックを無効にするので、そこから先の安全性が全部消えます。`unknown` は「何か分からない値」で、使う前に絞り込みを強制します。

外部入力の受け口は `unknown` にして、型ガードや検証ライブラリで確定させます。`any` を使うのは移行期の一時的な逃げ道に限り、`eslint` で検出できるようにしておきます。

**🇰🇷 답변**

`any` 는 타입 검사를 무효로 만들어 그 뒤의 안전성이 전부 사라집니다. `unknown` 은 "무엇인지 모르는 값"이라 쓰기 전에 좁히기를 강제합니다.

외부 입력의 수신부는 `unknown` 으로 두고 타입 가드나 검증 라이브러리로 확정합니다. `any` 는 이행기의 일시적 도피로만 쓰고 `eslint` 로 검출되게 해 둡니다.

### Q23. イベントのバブリングと委譲について説明してください。
(이벤트 버블링과 위임)

**🇯🇵 回答**

イベントは対象から祖先へ伝わります。これを利用して親に一つだけリスナーを付け、`event.target` で判定するのがイベント委譲です。

行が動的に増える表やリストで効きます。リスナーの数が要素数に比例しないので、メモリと登録コストが下がり、後から追加された要素にも自動で効きます。

**🇰🇷 답변**

이벤트는 대상에서 조상으로 전파됩니다. 이를 이용해 부모에 리스너를 하나만 달고 `event.target` 으로 판정하는 것이 이벤트 위임입니다.

행이 동적으로 늘어나는 표나 목록에서 효과적입니다. 리스너 수가 요소 수에 비례하지 않아 메모리와 등록 비용이 줄고, 나중에 추가된 요소에도 자동으로 동작합니다.

### Q24. `localStorage`・`sessionStorage`・Cookie の使い分けは？
(localStorage·sessionStorage·쿠키 구분)

**🇯🇵 回答**

`localStorage` は永続、`sessionStorage` はタブを閉じるまで、Cookie はサーバに自動で送られます。

**認証トークンを `localStorage` に置くと XSS で盗まれます。**セッションの識別子は `HttpOnly`・`Secure`・`SameSite` を付けた Cookie に置くのが基本です。ストレージには機密でない表示設定などを入れます。

**🇰🇷 답변**

`localStorage` 는 영속, `sessionStorage` 는 탭을 닫을 때까지, 쿠키는 서버로 자동 전송됩니다.

**인증 토큰을 `localStorage` 에 두면 XSS 로 탈취됩니다.** 세션 식별자는 `HttpOnly`·`Secure`·`SameSite` 를 붙인 쿠키에 두는 것이 기본입니다. 스토리지에는 기밀이 아닌 표시 설정 같은 것을 넣습니다.

### Q25. XSS はどう防ぎますか？
(XSS 방어)

**🇯🇵 回答**

出力時のエスケープが基本です。フレームワークは既定でエスケープするので、それを外す API を安易に使わないことです。`innerHTML` に外部入力を入れないのも同じ理由です。

多層で守ります。サニタイズが必要なら実績のあるライブラリを使い、CSP を設定してインラインスクリプトの実行自体を制限します。Cookie は `HttpOnly` にして、盗まれても使えないようにします。

**🇰🇷 답변**

출력 시 이스케이프가 기본입니다. 프레임워크는 기본적으로 이스케이프하므로 그것을 푸는 API 를 함부로 쓰지 않는 것입니다. `innerHTML` 에 외부 입력을 넣지 않는 것도 같은 이유입니다.

여러 겹으로 막습니다. 새니타이즈가 필요하면 검증된 라이브러리를 쓰고, CSP 를 설정해 인라인 스크립트 실행 자체를 제한합니다. 쿠키는 `HttpOnly` 로 두어 탈취돼도 쓸 수 없게 합니다.
