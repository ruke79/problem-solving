SPRING Q3빈출
依存性注入は三つの方式のうちどれを使いますか？
의존성 주입 세 방식 중 무엇을 쓰나
SPRING Q3빈출
コンストラクタ注入です。理由は三つで、フィールドを final にできること、必須の依存がシグネチャに現れること、テストで new するだけで組み立てられることです。
SPRING Q7함정
singletonのBeanにprototypeのBeanを注入するとどうなりますか？
싱글턴 빈에 프로토타입 빈을 주입하면 어떻게 되나
SPRING Q7함정
期待どおりには動きません。注入は singleton の生成時に一度だけなので、以後ずっと同じインスタンスが使われます。毎回必要なら ObjectProvider を使います。
SPRING Q4
循環参照はなぜ起きて、どう直しますか？
순환 참조는 왜 일어나고 어떻게 고치나
SPRING Q4
A が B を、B が A を必要とする状態です。Spring Boot 2.6 から既定で禁止されました。回避設定は対症療法で、本質的には責務の分割が間違っているので、共通部分を第三のクラスに切り出します。
SPRING Q14빈출
Spring Boot の自動構成(auto-configuration)はどう動きますか？
Spring Boot 자동 구성은 어떻게 동작하나
SPRING Q14빈출
@EnableAutoConfiguration が設定クラスの一覧を読み込み、各クラスに付いた @ConditionalOnClass や @ConditionalOnMissingBean で条件に合うものだけが有効になります。だからクラスパスに依存を足すだけで設定が入るように見えます。
SPRING Q35빈출
同じクラス内のメソッドを呼ぶと @Transactional が効かないのはなぜですか？
같은 클래스 안의 메서드를 부르면 @Transactional 이 안 걸리는 이유
SPRING Q35빈출
自己呼び出しがプロキシを通らないからです。プロキシが挟まるのは外部から呼ばれたときだけで、内部の this.method() は素のオブジェクトの呼び出しになります。対処は呼び出し側を別のBeanに分けることです。
SPRING Q42함정
@Transactional はどんな例外でロールバックしますか？
@Transactional 은 어떤 예외에서 롤백하나
SPRING Q42함정
既定では RuntimeException と Error だけです。チェック例外ではロールバックせず、そのままコミットされます。戻したいなら rollbackFor を明示するか、最初からランタイム例外に包みます。
SPRING Q34
JDK動的プロキシとCGLIBプロキシの違いは？
JDK 동적 프록시와 CGLIB 프록시의 차이
SPRING Q34
JDK動的プロキシはインターフェースが必須、CGLIBは対象クラスを継承します。Spring Boot は既定でCGLIBなので、final クラスやメソッドにはプロキシを掛けられません。
SPRING Q38
トランザクション伝播の REQUIRED と REQUIRES_NEW の違いは？
전파 속성 REQUIRED 와 REQUIRES_NEW 의 차이
SPRING Q38
REQUIRED は既存に参加するので、内側でロールバックすると外側も巻き込まれます。REQUIRES_NEW は別のコネクションで新しく始めるので、外側がロールバックしても内側のデータは残ります。
SPRING Q47
@Transactional が効かないケースを挙げてください。
@Transactional 이 안 걸리는 경우
SPRING Q47
自己呼び出し、private メソッド、final、Beanでないクラス、別スレッドです。共通しているのはプロキシを経由しないという点です。
SPRING Q45실무
トランザクションの中で外部API呼び出しをしてもよいですか？
트랜잭션 안에서 외부 API 를 호출해도 되나
SPRING Q45실무
避けるべきです。相手が遅いとその間ずっとDBコネクションを握り続け、プールが枯渇してアプリ全体が止まります。DBのコミット後にイベントで呼び出す形にします。
SPRING Q56빈출
リクエストが来てからレスポンスを返すまでの流れを説明してください。
요청이 와서 응답을 반환하기까지의 흐름
SPRING Q56빈출
DispatcherServlet が受け取り、HandlerMapping で担当を決め、HandlerAdapter が呼び出し、その前後で Interceptor が動きます。戻り値は HttpMessageConverter か ViewResolver が処理し、例外は HandlerExceptionResolver が扱います。
SPRING Q66빈출
Filter・Interceptor・AOP はどう使い分けますか？
필터·인터셉터·AOP 의 사용 구분
SPRING Q66빈출
Filterはサーブレットコンテナのレベル、InterceptorはSpring MVCの内部、AOPはBeanのメソッド単位です。どのレイヤーの情報が必要かで決まります。
SPRING Q64
HTTPステータスコードはどう使い分けますか？
HTTP 상태 코드는 어떻게 구분해 쓰나
SPRING Q64
エラーを200で返してボディのフラグで示すと、リトライも監視もキャッシュも全部機能しなくなります。ステータスコードはプロトコルの一部として正しく使います。
SPRING Q76실무
Tomcat のスレッドプール設定はどう決めますか？
Tomcat 스레드풀 설정은 어떻게 정하나
SPRING Q76실무
重要なのは下流の上限と揃えることです。スレッドを400にしてもDBコネクションプールが20なら、380個は待つだけで、むしろ待ち行列が伸びて応答が悪化します。
SPRING Q89빈출
N+1問題とは何ですか？
N+1 문제란
SPRING Q89빈출
一覧のクエリが1回、各要素の関連を取るクエリがN回発行される状態です。遅延ロードでループ中に関連へアクセスした瞬間に個別クエリが走ります。本番のデータ量で初めて顕在化するのが厄介です。
SPRING Q92변별력
fetch join とページングを一緒に使うとどうなりますか？
fetch join 과 페이징을 함께 쓰면 어떻게 되나
SPRING Q92변별력
コレクションの fetch join にページングを掛けると、Hibernateは limit 句を付けずに全件を取得し、メモリ上でページングします。警告は出ますが例外にならないので、データが増えたときにOOMになります。
SPRING Q94실무
OSIV(Open Session In View)を無効にする理由は？
OSIV 를 끄는 이유
SPRING Q94실무
有効だとビューのレンダリングが終わるまでDBコネクションを保持し続けるからです。トラフィックが増えるとプールが枯渇します。無効にすると LazyInitializationException が出ますが、それは問題が可視化されただけです。
SPRING Q108변별력
コネクションプールが枯渇したとき、原因をどう切り分けますか？
커넥션 풀이 고갈됐을 때 원인을 어떻게 가리나
SPRING Q108변별력
スロークエリなら必ず返却されるので使用時間の分布に現れ、p99が伸びます。リークならそもそも返却されず分布に現れないのに active だけ増え続けます。leakDetectionThreshold を設定すれば借りた時点のスタックトレースが出ます。
