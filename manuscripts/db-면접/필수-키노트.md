# DB 면접 — 필수 문항 지정과 키노트

> **시간이 부족할 때 이 파일만 보면 된다.** 50문항을 세 등급으로 나누고,
> S급에는 **일본어 한 문장**을 붙였다. 그 문장만 외워도 답이 성립한다.
>
> **이 세트는 다섯 주제 세트 중 실행 근거가 가장 두껍다.** S급 10문항 중 **8개에 케이스가 붙는다.**
> `DB-14` 처럼 표시된 것은 실물 PostgreSQL 16 위에서 돌려 확인한 것이다 —
> `./gradlew test -Dverify.only=DB-14` 로 직접 돌려 볼 수 있다.
> **외운 문장과 실행해 본 문장은, 되물었을 때 답할 수 있는 범위가 다르다.**

## 1. S급 — 반드시 나온다 (10문항)

### ① 인덱스 — 가장 자주 나오는 영역

**Q5. 복합 인덱스의 컬럼 순서가 중요한 이유** ★가장 자주 ✅`DB-14`
> 先頭の列から順にしか使えないからです。`(A, B)` のインデックスは A の条件では効きますが、**B だけの条件では効きません**。等値条件でよく使う列を先に、範囲条件の列を後ろに置きます。

**Q4. 인덱스가 있는데 안 쓰이는 경우** ★함정 ✅`DB-03`
> 大きく三つです。条件が列を加工しているとき、中間一致のとき、そして**選択率が悪くて全件読んだ方が速いと判断されたとき**です。最後は正常な動作なので、実行計画で理由を確認します。

**Q7. 실행 계획에서 무엇을 보나** ✅`DB-03`
> まずアクセス方法、次に結合の方法と順序、そして**見積もりの行数と実際の行数の差**を見ます。差が大きければ統計が古いか、条件の書き方が推定を狂わせています。

---

### ② 트랜잭션과 락

**Q11. 격리 수준의 차이를 현상으로** ★가장 자주 ✅`DB-01`
> READ COMMITTED では同じ行を二度読むと値が変わりうる、いわゆる反復不能読み取りが起きます。REPEATABLE READ ではスナップショットが保たれるので変わりません。SERIALIZABLE は競合時に失敗するので**リトライの実装が前提**です。

**Q15. 데드락은 왜 일어나고 어떻게 막나** ★가장 자주 ✅`DB-07`
> 複数のトランザクションが**違う順序で**ロックを取り合うと起きます。一番実効性がある対策はアクセス順序をそろえることで、ゼロにはできないので**再試行を前提に設計**します。

**Q12. MVCC 란** ★변별력
> 行の複数バージョンを持ち、読み取りは自分のスナップショットに合うバージョンを見る仕組みで、**読み取りが書き込みをブロックしません**。代わりに古いバージョンが溜まるので、長時間開きっぱなしのトランザクションはテーブルを膨らませます。

---

### ③ 커넥션 풀 — 실무에서 가장 많이 터진다

**Q17. 커넥션 풀 사이즈는 어떻게 정하나** ★실무 · 가장 자주 ✅`DB-02`
> 大きくすれば速いわけではありません。DB 側は CPU とディスクで並列度が決まるので、それを超えて渡しても**待ち行列が DB の中に移るだけ**です。アプリのインスタンス数 × プールサイズが DB の最大接続数を超えないことも必ず確認します。

**Q18. 풀 고갈의 원인을 어떻게 가르나** ★변별력 최고 ✅`DB-06`
> 三つに分けます。リーク、占有が長い、単純な容量不足です。見分け方は**負荷を止めた後**で、負荷が終わってもアクティブが減らないならリーク、負荷中だけ張り付くなら占有時間か容量の問題です。

---

### ④ 안전과 설계

**Q19. SQL 인젝션은 어떻게 막나** ★보안 ✅`DB-04`·`DB-19`
> パラメータバインディングです。値としてドライバに渡すので構文として解釈されません。注意点は**バインドできない場所がある**ことで、テーブル名や並び替えの列名はホワイトリストで対応付けます。

**Q35. 같은 처리가 두 번 실행돼도 괜찮게 만들려면** ★실무 ✅`DB-12`
> 冪等にします。リクエストごとの一意なキーを受け取り、**そのキーにユニーク制約を張って**二回目を弾きます。アプリで確認してから実行する方式は、同時に来ると両方が通ってしまいます。

## 4. 면접 30분 전 최종 점검 — 이것만은

**여섯 개의 "아니오"** 를 기억하면 함정 질문은 대부분 막힙니다.

| 질문의 유혹 | 정답 |
|---|---|
| `(A, B)` 인덱스가 `B` 조건에도 쓰이나? | **아니오** — 선행 컬럼부터만 (Q5 ✅`DB-14`) |
| 인덱스를 안 타면 항상 문제인가? | **아니오** — 선택도가 나쁘면 전건 스캔이 정답 (Q4 ✅`DB-03`) |
| 커넥션 풀은 크게 잡으면 빨라지나? | **아니오** — 대기열이 DB 안으로 옮겨갈 뿐 (Q17 ✅`DB-02`) |
| 프리페어드 스테이트먼트면 인젝션은 끝인가? | **아니오** — 정렬 컬럼은 바인딩 못 한다 (Q19 ✅`DB-19`) |
| 앱에서 "이미 처리했나" 확인하면 중복이 막히나? | **아니오** — 동시에 오면 둘 다 통과 (Q35 ✅`DB-12`) |
| 분산 락만 걸면 안전한가? | **아니오** — 펜싱 토큰이 필요 (Q36 ✅`DB-16`) |

**그리고 하나의 "예"** — *데드락은 0 으로 만들 수 없으니 재시도를 전제로 설계합니다.* (Q15 ✅`DB-07`)

## 5. 이 세트의 강점을 활용하세요

**S급 10문항 중 8개, B급 8문항 중 8개 전부에 실행 근거가 있습니다.** 이것은 다른 지원자와
가장 크게 갈리는 지점입니다. 다만 **말하는 방식이 중요합니다.**

- ✅ 좋은 예 — "락 순서를 엇갈리게 해서 재현해 봤는데, 락 타임아웃이 아니라 **데드락(40P01)** 으로 잡혔습니다."
- ❌ 나쁜 예 — "데드락은 40P01 로 잡힙니다." (외운 것처럼 들리고, 되물으면 막힙니다)

**제품을 특정해 물으면 전제를 밝히세요.** 이 저장소의 케이스는 전부 **PostgreSQL 16 기준**입니다.
MySQL InnoDB 의 갭 락이나 클러스터 인덱스는 재현하지 않았으므로,
"PostgreSQL 에서는 이렇게 확인했고, MySQL 은 문서 기준으로는" 이라고 나눠 말하는 편이 안전합니다.
