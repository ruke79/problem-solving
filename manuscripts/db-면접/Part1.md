### Q1. 正規化と非正規化はどう判断しますか？
(정규화와 비정규화의 판단)

**🇯🇵 回答**

まず正規化します。重複がないので更新の異常が起きず、整合性を DB に任せられるからです。

非正規化は、実際に測って**結合が明確なボトルネックになったとき**の最後の手段です。入れるなら、更新経路を一本にして不整合の入口を減らします。最初から非正規化するのは、たいてい早すぎる最適化です。

**🇰🇷 답변**

먼저 정규화합니다. 중복이 없어 갱신 이상이 생기지 않고 정합성을 DB 에 맡길 수 있기 때문입니다.

비정규화는 실제로 재 보고 **조인이 명확한 병목이 됐을 때**의 마지막 수단입니다. 넣는다면 갱신 경로를 하나로 만들어 불일치의 입구를 줄입니다. 처음부터 비정규화하는 것은 대개 이른 최적화입니다.

### Q2. 主キーはどう選びますか？
(기본키 선택 기준)

**🇯🇵 回答**

不変で、意味を持たない値が良いです。業務上の値を主キーにすると、仕様変更で変わったときに参照している全部が壊れます。

自動採番は挿入が末尾に集中して効率的ですが、外部に露出すると件数が推測できます。分散環境で採番したいなら UUID ですが、**v4 はランダムで挿入位置が散る**ので、時刻順の v7 のようなものを選びます。

**🇰🇷 답변**

불변이고 의미를 갖지 않는 값이 좋습니다. 업무상 값을 기본키로 하면 사양 변경으로 값이 바뀔 때 참조하는 전부가 깨집니다.

자동 채번은 삽입이 끝에 몰려 효율적이지만 외부에 노출되면 건수가 추측됩니다. 분산 환경에서 채번하려면 UUID 지만, **v4 는 무작위라 삽입 위치가 흩어지므로** 시각 순서인 v7 같은 것을 고릅니다.

### Q3. インデックスはどういう構造ですか？
(인덱스의 구조)

**🇯🇵 回答**

多くは B+木です。値がソートされて葉に並び、根から辿るので探索が対数時間になります。範囲検索と並び替えにも効きます。

代わりに書き込みが遅くなります。INSERT・UPDATE・DELETE のたびにインデックスも更新されるからです。だから「とりあえず全部の列に付ける」のは逆効果です。

**🇰🇷 답변**

대부분 B+트리입니다. 값이 정렬되어 잎에 나열되고 루트부터 따라가므로 탐색이 로그 시간이 됩니다. 범위 검색과 정렬에도 효과가 있습니다.

대신 쓰기가 느려집니다. INSERT·UPDATE·DELETE 마다 인덱스도 갱신되기 때문입니다. 그래서 "일단 모든 컬럼에 붙이는" 것은 역효과입니다.

### Q4. インデックスがあるのに使われないのはどんなときですか？
(인덱스가 있는데 안 쓰이는 경우)

**🇯🇵 回答**

大きく三つです。条件が列を加工しているとき、前方一致でない中間一致のとき、そして**選択率が悪くて全件読んだ方が速いと判断されたとき**です。

最後のケースは正常な動作です。テーブルの大半が該当するなら、インデックスを辿って行を拾うより順に読む方が速い。だから「使われない=おかしい」と決めつけず、実行計画で理由を見ます。

**🇰🇷 답변**

크게 셋입니다. 조건이 컬럼을 가공할 때, 전방 일치가 아닌 중간 일치일 때, 그리고 **선택도가 나빠 전건을 읽는 편이 빠르다고 판단됐을 때**입니다.

마지막은 정상 동작입니다. 테이블 대부분이 해당한다면 인덱스를 타고 행을 집는 것보다 순서대로 읽는 편이 빠릅니다. 그래서 "안 탄다 = 이상하다"로 단정하지 않고 실행 계획에서 이유를 봅니다.

### Q5. 複合インデックスの列の順序はなぜ重要ですか？
(복합 인덱스의 컬럼 순서)

**🇯🇵 回答**

先頭の列から順にしか使えないからです。`(A, B)` のインデックスは A の条件、または A と B の条件では効きますが、**B だけの条件では効きません**。

なので、等値条件でよく使う列を先に、範囲条件の列を後ろに置きます。並び替えの列まで含めると、ソートも省けます。

**🇰🇷 답변**

선행 컬럼부터 순서대로만 쓸 수 있기 때문입니다. `(A, B)` 인덱스는 A 조건, 또는 A 와 B 조건에서는 효과가 있지만 **B 만의 조건에서는 효과가 없습니다.**

그래서 등치 조건으로 자주 쓰는 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둡니다. 정렬 컬럼까지 포함하면 정렬도 생략됩니다.

### Q6. カバリングインデックスとは何ですか？
(커버링 인덱스)

**🇯🇵 回答**

必要な列がすべてインデックスに含まれていて、**テーブル本体を読まずに済む**状態です。ランダムアクセスが消えるので大きく速くなります。

PostgreSQL なら `INCLUDE` で列を足せます。ただし列を増やすとインデックスが太って書き込みとキャッシュ効率が悪くなるので、効果の大きいクエリに絞って使います。

**🇰🇷 답변**

필요한 컬럼이 전부 인덱스에 들어 있어 **테이블 본체를 읽지 않아도 되는** 상태입니다. 랜덤 액세스가 사라져 크게 빨라집니다.

PostgreSQL 이라면 `INCLUDE` 로 컬럼을 덧붙일 수 있습니다. 다만 컬럼을 늘리면 인덱스가 커져 쓰기와 캐시 효율이 나빠지므로 효과가 큰 쿼리에만 한정해 씁니다.

### Q7. 実行計画では何を見ますか？
(실행 계획에서 보는 것)

**🇯🇵 回答**

まずアクセス方法です。全件走査か、インデックス走査か。次に結合の方法と順序、そして**見積もりの行数と実際の行数の差**を見ます。

差が大きければ統計が古いか、条件の書き方が推定を狂わせています。`EXPLAIN` だけだと見積もりしか出ないので、実測が要るときは `EXPLAIN ANALYZE` を使います。

**🇰🇷 답변**

먼저 접근 방법입니다. 전건 스캔인지 인덱스 스캔인지. 다음으로 조인 방법과 순서, 그리고 **추정 행 수와 실제 행 수의 차이**를 봅니다.

차이가 크면 통계가 낡았거나 조건 작성 방식이 추정을 어긋나게 한 것입니다. `EXPLAIN` 만으로는 추정치만 나오므로 실측이 필요하면 `EXPLAIN ANALYZE` 를 씁니다.

### Q8. 結合のアルゴリズムにはどんなものがありますか？
(조인 알고리즘의 종류)

**🇯🇵 回答**

ネステッドループ、ハッシュ結合、マージ結合です。片方が小さくて索引があるならネステッドループ、大きい同士ならハッシュ、両方ソート済みならマージが選ばれます。

選ぶのはオプティマイザなので、こちらは統計を新しく保ち、必要なインデックスを用意します。遅いときは「なぜこの方法を選んだか」を行数の見積もりから逆算します。

**🇰🇷 답변**

네스티드 루프, 해시 조인, 머지 조인입니다. 한쪽이 작고 인덱스가 있으면 네스티드 루프, 큰 것끼리면 해시, 양쪽이 정렬돼 있으면 머지가 선택됩니다.

고르는 것은 옵티마이저이므로 우리는 통계를 최신으로 유지하고 필요한 인덱스를 갖춥니다. 느릴 때는 "왜 이 방법을 골랐는가"를 행 수 추정에서 역산합니다.

### Q9. 統計情報はなぜ重要ですか？
(통계 정보의 중요성)

**🇯🇵 回答**

オプティマイザは統計から行数を見積もって計画を決めます。統計が古いと、実際は百万行なのに数行だと思い込んで、まずい計画を選びます。

大量に投入した直後や、データ分布が大きく変わったときは統計を更新します。自動でも走りますが、バッチの後などタイミングが読めるところでは明示的に走らせます。

**🇰🇷 답변**

옵티마이저는 통계로 행 수를 추정해 계획을 정합니다. 통계가 낡으면 실제로는 백만 행인데 몇 행이라고 믿고 나쁜 계획을 고릅니다.

대량 적재 직후나 데이터 분포가 크게 바뀌었을 때는 통계를 갱신합니다. 자동으로도 돌지만 배치 후처럼 시점을 알 수 있는 곳에서는 명시적으로 돌립니다.

### Q10. ACID について説明してください。
(ACID 설명)

**🇯🇵 回答**

原子性は全部やるか何もしないか、一貫性は制約を保つこと、独立性は同時実行しても直列に見えること、永続性はコミットしたら残ることです。

実務で一番議論になるのは独立性です。完全な直列化は重いので、多くの DB は緩めた分離レベルを既定にしていて、そこで何が起きうるかを知っている必要があります。

**🇰🇷 답변**

원자성은 전부 하거나 아무것도 하지 않는 것, 일관성은 제약을 지키는 것, 독립성은 동시에 실행해도 직렬로 보이는 것, 지속성은 커밋하면 남는 것입니다.

실무에서 가장 논의가 되는 것은 독립성입니다. 완전한 직렬화는 무거워서 많은 DB 가 완화된 격리 수준을 기본으로 두고, 거기서 무엇이 일어날 수 있는지를 알고 있어야 합니다.

### Q11. 分離レベルの違いを現象で説明してください。
(격리 수준을 현상으로 설명)

**🇯🇵 回答**

READ COMMITTED では、同じ行を二度読むと値が変わりうる、いわゆる反復不能読み取りが起きます。REPEATABLE READ ではスナップショットが保たれるので変わりません。

SERIALIZABLE は書き込みの偏りまで防ぎますが、競合時にトランザクションが失敗するので**リトライの実装が前提**になります。既定は PostgreSQL も MySQL InnoDB も違うので、必ず確認します。

**🇰🇷 답변**

READ COMMITTED 에서는 같은 행을 두 번 읽으면 값이 달라질 수 있는, 이른바 반복 불가능 읽기가 생깁니다. REPEATABLE READ 에서는 스냅샷이 유지되어 바뀌지 않습니다.

SERIALIZABLE 은 쓰기 편향까지 막지만 경합 시 트랜잭션이 실패하므로 **재시도 구현이 전제**입니다. 기본값은 PostgreSQL 과 MySQL InnoDB 가 다르니 반드시 확인합니다.

### Q12. MVCC とは何ですか？
(MVCC 란)

**🇯🇵 回答**

行の複数バージョンを持ち、読み取りは自分のスナップショットに合うバージョンを見る仕組みです。**読み取りが書き込みをブロックしない**のが最大の利点です。

代わりに古いバージョンが溜まります。PostgreSQL では VACUUM が回収し、長時間開きっぱなしのトランザクションがあると回収できずテーブルが膨らみます。長いトランザクションを避けるべき理由の一つです。

**🇰🇷 답변**

행의 여러 버전을 두고, 읽기는 자기 스냅샷에 맞는 버전을 보는 구조입니다. **읽기가 쓰기를 막지 않는 것**이 가장 큰 장점입니다.

대신 옛 버전이 쌓입니다. PostgreSQL 에서는 VACUUM 이 회수하는데, 오래 열려 있는 트랜잭션이 있으면 회수하지 못해 테이블이 부풉니다. 긴 트랜잭션을 피해야 하는 이유 중 하나입니다.

### Q13. スナップショット分離でも防げない異常はありますか？
(스냅샷 격리로도 못 막는 이상)

**🇯🇵 回答**

書き込みスキューです。二つのトランザクションが別々の行を見て、それぞれ条件を満たしていると判断して書き込むと、合わせると不変条件が壊れます。

「当直は最低一人」のような制約が典型です。防ぐには SERIALIZABLE にするか、対象行を明示的にロックするか、DB の制約として表現します。**アプリの条件分岐だけでは守れません。**

**🇰🇷 답변**

쓰기 스큐입니다. 두 트랜잭션이 각각 다른 행을 보고 저마다 조건을 만족한다고 판단해 쓰면, 합쳐 놓고 보면 불변식이 깨집니다.

"당직은 최소 한 명" 같은 제약이 전형입니다. 막으려면 SERIALIZABLE 로 하거나 대상 행을 명시적으로 잠그거나 DB 제약으로 표현합니다. **애플리케이션의 조건 분기만으로는 지킬 수 없습니다.**

### Q14. ロックにはどんな種類がありますか？
(락의 종류)

**🇯🇵 回答**

粒度で言うと行ロック、テーブルロック。種類で言うと共有ロックと排他ロックです。MySQL InnoDB にはギャップロックがあり、範囲に対する挿入も止めます。

大事なのは、**ロックを持っている時間を短くすること**です。トランザクションの中で外部 API を呼ぶような設計は、そこでロックを抱えたまま待つことになります。

**🇰🇷 답변**

단위로는 행 락과 테이블 락, 종류로는 공유 락과 배타 락입니다. MySQL InnoDB 에는 갭 락이 있어 범위에 대한 삽입도 막습니다.

중요한 것은 **락을 쥐고 있는 시간을 짧게 하는 것**입니다. 트랜잭션 안에서 외부 API 를 부르는 설계는 그동안 락을 안은 채 기다리게 됩니다.

### Q15. デッドロックはなぜ起きて、どう対処しますか？
(데드락의 원인과 대처)

**🇯🇵 回答**

複数のトランザクションが違う順序でロックを取り合うと起きます。DB は検出して片方を失敗させます。

対策は、**アクセス順序をそろえること**、トランザクションを短くすること、そして失敗したら再試行できるようにしておくことです。ゼロにはできないので、再試行を前提に設計するのが現実的です。ログでどの文が絡んだかを見て順序を直します。

**🇰🇷 답변**

여러 트랜잭션이 서로 다른 순서로 락을 잡으면 발생합니다. DB 가 탐지해 한쪽을 실패시킵니다.

대책은 **접근 순서를 통일하는 것**, 트랜잭션을 짧게 하는 것, 그리고 실패하면 재시도할 수 있게 해 두는 것입니다. 0 으로는 만들 수 없으므로 재시도를 전제로 설계하는 것이 현실적입니다. 로그에서 어떤 문장이 얽혔는지 보고 순서를 고칩니다.

### Q16. 楽観ロックと悲観ロックはどう使い分けますか？
(낙관 락과 비관 락의 구분)

**🇯🇵 回答**

競合が少ないなら楽観ロックです。バージョン列を持って、更新時に一致するかを見ます。競合したら例外にして、再読み込みからやり直します。

競合が多く、失敗のコストが高いなら悲観ロックで先に押さえます。`SELECT ... FOR UPDATE` です。ただし待ちが発生するので、**タイムアウトを設定**しないと詰まります。

**🇰🇷 답변**

경합이 적으면 낙관 락입니다. 버전 컬럼을 두고 갱신 시 일치하는지를 봅니다. 충돌하면 예외로 만들고 다시 읽는 데서 재시도합니다.

경합이 많고 실패 비용이 크면 비관 락으로 먼저 잡습니다. `SELECT ... FOR UPDATE` 입니다. 다만 대기가 생기므로 **타임아웃을 설정**하지 않으면 막힙니다.

### Q17. コネクションプールのサイズはどう決めますか？
(커넥션 풀 사이즈 결정)

**🇯🇵 回答**

大きくすれば速いわけではありません。DB 側は CPU とディスクの本数で並列度が決まるので、それを超えて渡しても待ち行列が DB の中に移るだけです。

出発点は「コア数の数倍」程度の小さい値で、待ち時間とスループットを見て調整します。**アプリのインスタンス数 × プールサイズが DB の最大接続数を超えない**ことも必ず確認します。

**🇰🇷 답변**

크게 잡는다고 빨라지지 않습니다. DB 쪽은 CPU 와 디스크 수로 병렬도가 정해지므로, 그보다 많이 넘겨도 대기열이 DB 안으로 옮겨갈 뿐입니다.

출발점은 "코어 수의 몇 배" 정도의 작은 값이고, 대기 시간과 처리량을 보며 조정합니다. **앱 인스턴스 수 × 풀 사이즈가 DB 의 최대 접속 수를 넘지 않는 것**도 반드시 확인합니다.

### Q18. コネクションプールが枯渇したとき、原因をどう切り分けますか？
(커넥션 풀 고갈의 원인 분리)

**🇯🇵 回答**

三つに分けます。返却漏れによるリーク、一件あたりの占有が長い、単純に容量不足です。

見分け方は、負荷を止めた後です。**負荷が終わってもアクティブが減らないならリーク**、負荷中だけ張り付くなら占有時間か容量の問題です。占有時間はクエリの遅さか、トランザクション内の外部呼び出しを疑います。

**🇰🇷 답변**

셋으로 나눕니다. 반납 누락에 의한 누수, 건당 점유가 긴 경우, 단순 용량 부족입니다.

가려내는 방법은 부하를 멈춘 뒤입니다. **부하가 끝나도 active 가 줄지 않으면 누수**, 부하 중에만 붙어 있으면 점유 시간이나 용량 문제입니다. 점유 시간은 쿼리가 느린지, 트랜잭션 안의 외부 호출이 있는지를 의심합니다.

### Q19. SQL インジェクションはどう防ぎますか？
(SQL 인젝션 방어)

**🇯🇵 回答**

パラメータバインディングです。値としてドライバに渡すので、中身に何が入っていても構文として解釈されません。文字列を組み立ててエスケープする方法は、抜けが必ず出ます。

注意点は、**バインドできない場所がある**ことです。テーブル名や並び替えの列名は値ではないので、ホワイトリストで対応付けます。ここを文字列結合したままにして事故になる例が多いです。

**🇰🇷 답변**

파라미터 바인딩입니다. 값으로 드라이버에 넘기므로 안에 무엇이 들어 있어도 구문으로 해석되지 않습니다. 문자열을 조립해 이스케이프하는 방법은 반드시 빠지는 곳이 생깁니다.

주의할 점은 **바인딩할 수 없는 자리가 있다**는 것입니다. 테이블명이나 정렬 컬럼명은 값이 아니므로 화이트리스트로 대응시킵니다. 여기를 문자열 결합인 채로 두어 사고가 나는 예가 많습니다.

### Q20. ページングはどう設計しますか？
(페이징 설계)

**🇯🇵 回答**

`OFFSET` は後ろのページほど遅くなります。読み飛ばす分も読むからです。さらに、途中で行が増減すると重複や抜けが起きます。

無限スクロールのような UI なら、**前回の最後のキーを条件にするキーセット方式**にします。`WHERE (created_at, id) < (?, ?) ORDER BY ... LIMIT n` の形です。任意のページ番号に飛ぶ必要があるときだけ `OFFSET` を使います。

**🇰🇷 답변**

`OFFSET` 은 뒤쪽 페이지일수록 느려집니다. 건너뛸 만큼도 읽기 때문입니다. 게다가 중간에 행이 늘거나 줄면 중복과 누락이 생깁니다.

무한 스크롤 같은 UI 라면 **직전 마지막 키를 조건으로 하는 키셋 방식**으로 합니다. `WHERE (created_at, id) < (?, ?) ORDER BY ... LIMIT n` 형태입니다. 임의 페이지 번호로 점프해야 할 때만 `OFFSET` 을 씁니다.

### Q21. 件数の取得が重いときはどうしますか？
(건수 조회가 무거울 때)

**🇯🇵 回答**

正確な全件数は、条件次第で全部数える必要があるので重いです。まず**本当に正確な数が要るのか**を確認します。

多くの画面は「次のページがあるか」で足ります。それなら一件多く取って判定します。概数でよければ統計から見積もる方法もあります。どうしても必要なら、カウンタ表を別に持って更新する設計にします。

**🇰🇷 답변**

정확한 전체 건수는 조건에 따라 전부 세야 해서 무겁습니다. 먼저 **정말 정확한 수가 필요한지**를 확인합니다.

많은 화면은 "다음 페이지가 있는가"로 충분합니다. 그렇다면 한 건 더 가져와 판정합니다. 어림수로 괜찮다면 통계에서 추정하는 방법도 있습니다. 꼭 필요하면 카운터 테이블을 따로 두고 갱신하는 설계로 갑니다.

### Q22. 大量のデータを挿入するときはどうしますか？
(대량 삽입)

**🇯🇵 回答**

一件ずつのラウンドトリップをやめて、まとめて送ります。バッチにすると往復が減り、桁で速くなることがあります。

さらに大きいときは、DB のバルクロード機能を使います。加えて、インデックスや制約を投入中だけ外して後で付け直す、トランザクションを適度に分ける、といった手も使います。**途中で失敗したときの再開点**も設計に入れておきます。

**🇰🇷 답변**

한 건씩의 왕복을 그만두고 묶어서 보냅니다. 배치로 만들면 왕복이 줄어 자릿수로 빨라지기도 합니다.

더 클 때는 DB 의 벌크 로드 기능을 씁니다. 여기에 인덱스나 제약을 적재 중에만 떼었다가 나중에 다시 붙이거나, 트랜잭션을 적당히 나누는 방법도 씁니다. **중간에 실패했을 때의 재개 지점**도 설계에 넣어 둡니다.

### Q23. 一括更新・削除で気をつけることは？
(일괄 갱신·삭제 주의점)

**🇯🇵 回答**

一度に大量を更新すると、ロックが広がり、レプリケーションが遅れ、ログが膨らみます。分割して少しずつ回すのが基本です。

削除は特に注意で、大量に消すと MVCC の古いバージョンが残ってテーブルが膨らみます。可能なら論理削除やパーティション単位の切り離しにします。ORM を使っている場合は、**一括更新が永続化コンテキストを迂回する**点も忘れないようにします。

**🇰🇷 답변**

한 번에 대량을 갱신하면 락이 넓어지고 복제가 밀리며 로그가 부풉니다. 나눠서 조금씩 도는 것이 기본입니다.

삭제는 특히 주의해야 하는데, 대량으로 지우면 MVCC 의 옛 버전이 남아 테이블이 부풉니다. 가능하면 논리 삭제나 파티션 단위 분리로 합니다. ORM 을 쓴다면 **일괄 갱신이 영속성 컨텍스트를 우회한다**는 점도 잊지 않습니다.

### Q24. 遅いクエリはどう見つけますか？
(느린 쿼리 찾기)

**🇯🇵 回答**

スロークエリログと、PostgreSQL なら `pg_stat_statements` を見ます。**一回が遅いもの**と、**一回は速いが回数が多くて合計で重いもの**を分けて見るのが要点です。

後者は見落とされがちですが、N+1 のような形で総時間の大半を占めていることがあります。合計時間の降順で並べると、直す価値のある順に出てきます。

**🇰🇷 답변**

슬로 쿼리 로그와, PostgreSQL 이라면 `pg_stat_statements` 를 봅니다. **한 번이 느린 것**과 **한 번은 빠르지만 횟수가 많아 합계로 무거운 것**을 나눠 보는 것이 요점입니다.

후자는 놓치기 쉬운데 N+1 같은 형태로 총 시간의 대부분을 차지하기도 합니다. 총 시간 내림차순으로 정렬하면 고칠 가치가 있는 순서로 나옵니다.

### Q25. アプリ側の N+1 はどう見つけて直しますか？
(앱 쪽 N+1 발견과 수정)

**🇯🇵 回答**

まず**クエリの実行回数を数えます**。時間ではなく回数で見ると、一覧の件数に比例して増えているのがすぐ分かります。

直し方は、結合してまとめて取るか、まとめて取る別クエリにするかです。ページングが絡むと結合ができない場合があるので、そのときは ID をまとめて `IN` で引く方式にします。直したら**もう一度回数を数えて**減ったことを確認します。

**🇰🇷 답변**

먼저 **쿼리 실행 횟수를 셉니다.** 시간이 아니라 횟수로 보면 목록 건수에 비례해 늘어나는 것이 바로 보입니다.

고치는 방법은 조인해 한 번에 가져오거나, 묶어서 가져오는 별도 쿼리로 만드는 것입니다. 페이징이 얽히면 조인이 안 되는 경우가 있어, 그때는 ID 를 모아 `IN` 으로 당기는 방식으로 합니다. 고친 뒤에는 **다시 횟수를 세어** 줄었는지 확인합니다.
