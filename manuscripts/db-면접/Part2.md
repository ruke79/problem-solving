### Q26. パーティショニングは何のために使いますか？
(파티셔닝의 목적)

**🇯🇵 回答**

大きな表を分割して、条件に合うパーティションだけを読ませるためです。日付で切るのが典型で、古いデータの削除もパーティションごと外すだけになります。

効果が出るのは**パーティションキーが条件に入っているとき**だけです。入っていないクエリは全パーティションを読むので、むしろ遅くなります。キーの選び方がすべてです。

**🇰🇷 답변**

큰 테이블을 나눠 조건에 맞는 파티션만 읽게 하기 위해서입니다. 날짜로 자르는 것이 전형이고, 오래된 데이터 삭제도 파티션째 떼어내면 됩니다.

효과가 나는 것은 **파티션 키가 조건에 들어 있을 때**뿐입니다. 안 들어간 쿼리는 전 파티션을 읽으므로 오히려 느려집니다. 키를 어떻게 고르느냐가 전부입니다.

### Q27. シャーディングとパーティショニングは何が違いますか？
(샤딩과 파티셔닝의 차이)

**🇯🇵 回答**

パーティショニングは一つの DB の中で分ける話、シャーディングは複数のサーバに分ける話です。

シャーディングは書き込みまでスケールできますが、**シャードをまたぐ結合とトランザクションができなくなります**。運用も一段難しくなるので、レプリカやパーティションで足りないかを先に検討します。入れるならシャードキーを慎重に選びます。後から変えるのが最も高くつくからです。

**🇰🇷 답변**

파티셔닝은 하나의 DB 안에서 나누는 이야기, 샤딩은 여러 서버로 나누는 이야기입니다.

샤딩은 쓰기까지 확장되지만 **샤드를 넘는 조인과 트랜잭션이 불가능해집니다.** 운영도 한 단계 어려워지므로 레플리카나 파티션으로 충분하지 않은지 먼저 검토합니다. 도입한다면 샤드 키를 신중히 고릅니다. 나중에 바꾸는 것이 가장 비싸기 때문입니다.

### Q28. リードレプリカを使うときの注意点は？
(읽기 레플리카 사용 시 주의점)

**🇯🇵 回答**

レプリケーション遅延です。書いた直後に読むと、まだ反映されていないことがあります。

なので「自分が書いたものを読む」経路はプライマリに向けます。一覧や集計のように少し古くても構わない読み取りをレプリカに回します。遅延は監視して、閾値を超えたら読み先をプライマリに戻す仕組みを入れておくと安全です。

**🇰🇷 답변**

복제 지연입니다. 쓴 직후에 읽으면 아직 반영되지 않았을 수 있습니다.

그래서 "자기가 쓴 것을 읽는" 경로는 프라이머리로 보냅니다. 목록이나 집계처럼 조금 낡아도 되는 읽기를 레플리카로 돌립니다. 지연은 모니터링하고, 임계를 넘으면 읽기 대상을 프라이머리로 되돌리는 장치를 넣어 두면 안전합니다.

### Q29. 無停止でスキーマを変更するにはどうしますか？
(무중단 스키마 변경)

**🇯🇵 回答**

一度に変えないことです。**追加 → 両方に書く → 移行 → 読み先を切り替える → 古いものを消す**、という段階に分けます。各段階で新旧のコードが同時に動けることが条件です。

危ないのは列の削除や型変更です。特に既存行を書き換える変更はテーブル全体を作り直すので、大きな表では長時間ロックになります。定数の既定値を付けた列追加のように、メタデータだけで済む操作かどうかを事前に確認します。

**🇰🇷 답변**

한 번에 바꾸지 않는 것입니다. **추가 → 양쪽에 쓰기 → 이행 → 읽는 곳 전환 → 옛것 삭제** 단계로 나눕니다. 각 단계에서 신·구 코드가 동시에 돌 수 있는 것이 조건입니다.

위험한 것은 컬럼 삭제와 타입 변경입니다. 특히 기존 행을 다시 쓰는 변경은 테이블 전체를 재작성하므로 큰 표에서는 오랜 락이 됩니다. 상수 기본값을 붙인 컬럼 추가처럼 메타데이터만으로 끝나는 조작인지 미리 확인합니다.

### Q30. スキーマ変更はどう管理していますか？
(스키마 변경 관리)

**🇯🇵 回答**

マイグレーションツールでバージョン管理し、コードと同じリポジトリに入れます。適用済みの履歴が DB に残るので、どの環境がどこまで進んでいるかが分かります。

原則は**前進のみ**です。切り戻しは逆マイグレーションではなく、打ち消す新しいマイグレーションを足します。ORM の自動更新機能は本番では使いません。何が実行されるか分からないからです。

**🇰🇷 답변**

마이그레이션 도구로 버전 관리하고 코드와 같은 저장소에 넣습니다. 적용 이력이 DB 에 남으므로 어느 환경이 어디까지 갔는지 알 수 있습니다.

원칙은 **전진뿐**입니다. 되돌리기는 역마이그레이션이 아니라 상쇄하는 새 마이그레이션을 추가합니다. ORM 의 자동 갱신 기능은 운영에서 쓰지 않습니다. 무엇이 실행될지 알 수 없기 때문입니다.

### Q31. バックアップと復旧はどう設計しますか？
(백업과 복구 설계)

**🇯🇵 回答**

RPO と RTO から決めます。どこまでのデータ欠損を許容するか、どれだけで復旧するか。それによってフルバックアップの頻度と、ログを使った時点復旧が要るかが決まります。

一番大事なのは**復旧を実際に試すこと**です。取れているつもりで戻せないケースが多いので、定期的にリストア訓練をします。バックアップは別の場所に置きます。

**🇰🇷 답변**

RPO 와 RTO 에서 정합니다. 데이터 손실을 어디까지 허용할지, 얼마 만에 복구할지. 그에 따라 풀 백업 주기와 로그를 이용한 시점 복구가 필요한지가 정해집니다.

가장 중요한 것은 **복구를 실제로 해 보는 것**입니다. 받아 놓은 줄 알았는데 되돌리지 못하는 경우가 많으므로 정기적으로 복원 훈련을 합니다. 백업은 다른 장소에 둡니다.

### Q32. DB の監視では何を見ますか？
(DB 모니터링 지표)

**🇯🇵 回答**

接続数と待ち、遅いクエリ、レプリケーション遅延、ディスク使用量とキャッシュヒット率です。PostgreSQL なら加えて長時間トランザクションと VACUUM の状況を見ます。

見方の要点は、平均ではなく**分布と傾向**です。平均レイテンシが同じでも、p99 が悪化していれば一部のユーザーは確実に困っています。閾値のアラートは、症状ではなく原因に近いものに付けます。

**🇰🇷 답변**

접속 수와 대기, 느린 쿼리, 복제 지연, 디스크 사용량과 캐시 히트율입니다. PostgreSQL 이라면 여기에 장시간 트랜잭션과 VACUUM 상황을 봅니다.

보는 요령은 평균이 아니라 **분포와 추세**입니다. 평균 지연이 같아도 p99 가 나빠졌다면 일부 사용자는 확실히 곤란을 겪고 있습니다. 임계 알림은 증상보다 원인에 가까운 것에 겁니다.

### Q33. キャッシュはどこに、どう入れますか？
(캐시 도입 위치와 방식)

**🇯🇵 回答**

まず読み取りが多く、少し古くても許される場所に入れます。方式はキャッシュアサイドが基本で、外れたら DB を読んで書き戻します。

難しいのは無効化です。更新経路を一本にして、そこで消すか書き換えるようにします。TTL は「最悪どれだけ古くて良いか」から決めます。**キャッシュを入れる前に、そもそもクエリを速くできないかを確認**します。

**🇰🇷 답변**

먼저 읽기가 많고 조금 낡아도 되는 곳에 넣습니다. 방식은 캐시 어사이드가 기본이고, 미스면 DB 를 읽어 다시 채웁니다.

어려운 것은 무효화입니다. 갱신 경로를 하나로 만들고 거기서 지우거나 덮어씁니다. TTL 은 "최악의 경우 얼마나 낡아도 되는가"에서 정합니다. **캐시를 넣기 전에 애초에 쿼리를 빠르게 할 수 없는지 확인**합니다.

### Q34. キャッシュスタンピードとは何ですか？
(캐시 스탬피드)

**🇯🇵 回答**

人気のキーが期限切れになった瞬間に、待っていたリクエストが一斉に DB へ流れる現象です。ちょうど負荷が高いときに起きるので被害が大きくなります。

対策は、再計算を一つにまとめること、期限にばらつきを持たせること、期限切れ前に非同期で更新することです。実装としては、ロックを取って一つだけが読みに行き、他は待つ形にします。

**🇰🇷 답변**

인기 있는 키가 만료되는 순간 기다리던 요청이 한꺼번에 DB 로 몰리는 현상입니다. 마침 부하가 높을 때 일어나 피해가 커집니다.

대책은 재계산을 하나로 묶는 것, 만료 시각에 편차를 주는 것, 만료 전에 비동기로 갱신하는 것입니다. 구현으로는 락을 잡아 하나만 읽으러 가고 나머지는 기다리는 형태로 만듭니다.

### Q35. 同じ処理が二回実行されても大丈夫にするにはどうしますか？
(같은 처리가 두 번 실행돼도 괜찮게 만들기)

**🇯🇵 回答**

冪等にします。決済のように副作用があるものは、リクエストごとの一意なキーを受け取り、**そのキーにユニーク制約を張って**二回目を弾きます。

アプリで「すでに処理済みか」を確認してから実行する方式は、同時に来ると両方が通ります。判定と実行の間に隙間があるからです。最終的な保証は DB の制約に置きます。

**🇰🇷 답변**

멱등하게 만듭니다. 결제처럼 부수효과가 있는 것은 요청마다 고유한 키를 받아 **그 키에 유니크 제약을 걸어** 두 번째를 막습니다.

애플리케이션에서 "이미 처리했는지" 확인한 뒤 실행하는 방식은 동시에 오면 둘 다 통과합니다. 판정과 실행 사이에 틈이 있기 때문입니다. 최종 보증은 DB 제약에 둡니다.

### Q36. 分散ロックはロックだけで十分ですか？
(분산 락은 락만으로 충분한가)

**🇯🇵 回答**

不十分です。ロックの有効期限が切れた後に、前の持ち主が遅れて処理を続けると、後から取った人の結果を上書きしてしまいます。

なのでフェンシングトークンを使います。ロックのたびに単調増加する番号を発行し、書き込み側が**古い番号の書き込みを拒否**します。ロックはあくまで効率のためで、正しさは書き込み側で担保する、という整理です。

**🇰🇷 답변**

불충분합니다. 락의 유효 기간이 끝난 뒤 이전 소유자가 뒤늦게 처리를 이어가면, 나중에 잡은 쪽의 결과를 덮어씁니다.

그래서 펜싱 토큰을 씁니다. 락을 잡을 때마다 단조 증가하는 번호를 발급하고, 쓰는 쪽이 **오래된 번호의 쓰기를 거절**합니다. 락은 어디까지나 효율을 위한 것이고 정확성은 쓰는 쪽에서 담보한다는 정리입니다.

### Q37. DB 更新とメッセージ送信を確実に一致させるには？
(DB 갱신과 메시지 발행의 일치)

**🇯🇵 回答**

二つを一つのトランザクションにはできないので、Outbox パターンを使います。業務データと一緒に**同じトランザクションで送信予定を専用テーブルに書き**、別のプロセスがそれを読んで送ります。

こうすると「DB は更新されたのにメッセージが飛ばない」も「メッセージは飛んだのに DB が戻った」も起きません。送信側は重複しうるので、受信側は冪等に作ります。

**🇰🇷 답변**

둘을 하나의 트랜잭션으로 묶을 수 없으므로 Outbox 패턴을 씁니다. 업무 데이터와 함께 **같은 트랜잭션에서 발행 예정을 전용 테이블에 쓰고**, 별도 프로세스가 그것을 읽어 보냅니다.

이렇게 하면 "DB 는 갱신됐는데 메시지가 안 나가는" 것도, "메시지는 나갔는데 DB 가 롤백된" 것도 생기지 않습니다. 보내는 쪽은 중복될 수 있으므로 받는 쪽을 멱등하게 만듭니다.

### Q38. CDC を使うときの注意点は？
(CDC 사용 시 주의점)

**🇯🇵 回答**

DB の変更ログを読んで流す方式なので、アプリを変えずに変更を配れます。ただしスキーマ変更がそのまま下流に伝わるので、結合が強くなります。

もう一つは削除の扱いです。既定の設定では**削除イベントに主キーしか載らない**ことがあり、他の列が要る下流は困ります。必要なら設定を変えるか、論理削除にします。順序保証と再実行時の重複も前提に置きます。

**🇰🇷 답변**

DB 의 변경 로그를 읽어 흘리는 방식이라 애플리케이션을 고치지 않고 변경을 배포할 수 있습니다. 다만 스키마 변경이 그대로 하류에 전달되어 결합이 강해집니다.

또 하나는 삭제 처리입니다. 기본 설정에서는 **삭제 이벤트에 기본키만 실리는** 경우가 있어 다른 컬럼이 필요한 하류가 곤란해집니다. 필요하면 설정을 바꾸거나 논리 삭제로 합니다. 순서 보장과 재실행 시 중복도 전제로 둡니다.

### Q39. イベントソーシングと CQRS はどんなときに使いますか？
(이벤트 소싱과 CQRS 사용 시점)

**🇯🇵 回答**

監査や履歴が本質的に重要な領域、あるいは読み取りと書き込みの要件が大きく違うときです。

代償が大きい点は正直に言います。イベントのスキーマ進化、再生の時間、結果整合性への対応が必要です。全体に入れるのではなく、必要な境界だけに限定します。再生が重くなったらスナップショットで途中から復元します。

**🇰🇷 답변**

감사나 이력이 본질적으로 중요한 영역, 또는 읽기와 쓰기의 요구가 크게 다를 때입니다.

대가가 큰 점은 솔직히 말합니다. 이벤트 스키마 진화, 재생 시간, 결과적 일관성 대응이 필요합니다. 전체에 넣지 않고 필요한 경계에만 한정합니다. 재생이 무거워지면 스냅샷으로 중간부터 복원합니다.

### Q40. RDB と NoSQL はどう選びますか？
(RDB 와 NoSQL 선택)

**🇯🇵 回答**

既定は RDB です。トランザクションと制約、そして後から要件が変わっても問い合わせられる柔軟さがあるからです。

NoSQL を選ぶのは、アクセスパターンが明確で、その形に最適化した読み書きが要るときです。キーバリューでの高速な参照、ドキュメントでのスキーマ柔軟性、時系列の大量書き込みなどです。「スケールするから」だけを理由に選ぶと、後で結合が要ることに気づいて苦労します。

**🇰🇷 답변**

기본은 RDB 입니다. 트랜잭션과 제약, 그리고 나중에 요구가 바뀌어도 질의할 수 있는 유연함이 있기 때문입니다.

NoSQL 을 고르는 것은 접근 패턴이 명확하고 그 형태에 최적화된 읽기·쓰기가 필요할 때입니다. 키-값의 빠른 조회, 도큐먼트의 스키마 유연성, 시계열의 대량 쓰기 등입니다. "확장되니까"만을 이유로 고르면 나중에 조인이 필요하다는 걸 깨닫고 고생합니다.

### Q41. Redis はどんな用途に使いますか？
(Redis 의 용도)

**🇯🇵 回答**

キャッシュ、セッション、レート制限のカウンタ、簡単なキューです。データ構造が豊富なので、ソート済み集合でランキング、TTL 付きキーで期限管理ができます。

注意点は、**永続化の設定次第でデータが消えうる**ことと、単一スレッドなので重いコマンドが全体を止めることです。`KEYS` のような全走査は本番で使いません。

**🇰🇷 답변**

캐시, 세션, 레이트 리밋 카운터, 간단한 큐입니다. 자료구조가 풍부해서 정렬 집합으로 랭킹, TTL 키로 기한 관리를 할 수 있습니다.

주의점은 **영속화 설정에 따라 데이터가 사라질 수 있다**는 것과, 단일 스레드라 무거운 명령이 전체를 멈춘다는 것입니다. `KEYS` 같은 전 스캔은 운영에서 쓰지 않습니다.

### Q42. 全文検索はどうしますか？
(전문 검색)

**🇯🇵 回答**

RDB でも前方一致ならインデックスが効きますが、**中間一致は基本的に効かず全件走査になります**。日本語のように単語区切りがない言語では形態素解析も要ります。

小規模なら DB の全文検索機能で足ります。関連度順、ファセット、表記ゆれの吸収が要るなら検索エンジンを別に立てます。その場合は同期の遅れと二重管理のコストを受け入れる判断になります。

**🇰🇷 답변**

RDB 에서도 전방 일치면 인덱스가 듣지만 **중간 일치는 기본적으로 안 듣고 전건 스캔이 됩니다.** 일본어처럼 띄어쓰기가 없는 언어는 형태소 분석도 필요합니다.

소규모면 DB 의 전문 검색 기능으로 충분합니다. 관련도 순, 패싯, 표기 흔들림 흡수가 필요하면 검색 엔진을 따로 세웁니다. 그 경우 동기화 지연과 이중 관리 비용을 받아들이는 판단이 됩니다.

### Q43. OLTP と OLAP はどう分けますか？
(OLTP 와 OLAP 의 분리)

**🇯🇵 回答**

OLTP は短いトランザクションを大量に、OLAP は大きな範囲を集計します。求めるものが逆なので、同じ DB で両方やると分析クエリが業務を止めます。

分けるのが基本です。レプリカに分析を回すか、集計用のデータストアに転送します。列指向のストアは集計に向いていて、同じ集計が桁で速くなることがあります。

**🇰🇷 답변**

OLTP 는 짧은 트랜잭션을 대량으로, OLAP 은 큰 범위를 집계합니다. 요구가 반대라서 같은 DB 에서 둘 다 하면 분석 쿼리가 업무를 멈춥니다.

나누는 것이 기본입니다. 레플리카로 분석을 돌리거나 집계용 데이터 스토어로 전송합니다. 컬럼 지향 스토어는 집계에 맞아 같은 집계가 자릿수로 빨라지기도 합니다.

### Q44. 履歴を持つマスタはどう設計しますか？
(이력을 갖는 마스터 설계)

**🇯🇵 回答**

上書きしてしまうと、過去の集計が現在の値で再計算されてしまいます。価格を変えた途端に去年の売上が変わる、というのが典型的な事故です。

なので、変更のたびに新しい行を作り、有効期間を持たせます。集計は取引時点の値を参照します。すべての属性で履歴が要るわけではないので、**どの属性が履歴を必要とするか**を業務要件から決めます。

**🇰🇷 답변**

덮어써 버리면 과거 집계가 현재 값으로 다시 계산됩니다. 가격을 바꾼 순간 작년 매출이 바뀌는 것이 전형적인 사고입니다.

그래서 변경할 때마다 새 행을 만들고 유효 기간을 갖게 합니다. 집계는 거래 시점의 값을 참조합니다. 모든 속성에 이력이 필요한 것은 아니므로 **어느 속성이 이력을 필요로 하는지**를 업무 요건에서 정합니다.

### Q45. マルチテナントのデータはどう分離しますか？
(멀티테넌시 데이터 분리)

**🇯🇵 回答**

方式は三つ、DB を分ける、スキーマを分ける、同じ表にテナント ID を持つ、です。数が多いなら最後が現実的です。

その場合の危険は、**条件を書き忘れると他のテナントが見えること**です。アプリの規律だけに頼らず、行レベルセキュリティのように DB 側で強制する仕組みを入れます。条件を書き忘れても自分のテナントの行しか見えない、という状態を作ります。

**🇰🇷 답변**

방식은 셋입니다. DB 를 나누기, 스키마를 나누기, 같은 테이블에 테넌트 ID 를 두기. 수가 많으면 마지막이 현실적입니다.

그 경우의 위험은 **조건을 빠뜨리면 다른 테넌트가 보이는 것**입니다. 애플리케이션의 규율에만 기대지 않고 행 수준 보안처럼 DB 쪽에서 강제하는 장치를 넣습니다. 조건을 빠뜨려도 자기 테넌트 행만 보이는 상태를 만듭니다.

### Q46. 個人情報はどう扱いますか？
(개인정보 취급)

**🇯🇵 回答**

保存時の暗号化とアクセス制御が基本です。加えて、そもそも**持たない・早く消す**という判断をします。要件がないのに保持期間を長く取らないことです。

開発環境にはマスクしたデータを配ります。ログに出さないことも徹底します。削除要求に応えられるよう、どこに複製があるか（バックアップ、分析基盤、キャッシュ）を把握しておく必要があります。

**🇰🇷 답변**

저장 시 암호화와 접근 제어가 기본입니다. 여기에 애초에 **갖지 않고 빨리 지운다**는 판단을 합니다. 요건이 없는데 보존 기간을 길게 잡지 않는 것입니다.

개발 환경에는 마스킹한 데이터를 내립니다. 로그에 남기지 않는 것도 철저히 합니다. 삭제 요청에 응할 수 있도록 어디에 복제본이 있는지(백업·분석 기반·캐시)를 파악해 두어야 합니다.

### Q47. バッチが途中で失敗したらどうしますか？
(배치가 도중에 실패하면)

**🇯🇵 回答**

最初からやり直さないで済むように、チェックポイントを持ちます。どこまで処理したかを記録しておけば、失敗した塊から再開できます。

そのためには、各塊の処理が冪等であることが前提です。加えて、失敗した件だけを退避して後で調べられるようにします。全体を止めるか、失敗を飛ばして進むかは、業務要件から決めます。

**🇰🇷 답변**

처음부터 다시 하지 않아도 되도록 체크포인트를 둡니다. 어디까지 처리했는지 기록해 두면 실패한 덩어리부터 재개할 수 있습니다.

그러려면 각 덩어리의 처리가 멱등해야 합니다. 여기에 실패한 건만 따로 빼 두어 나중에 조사할 수 있게 합니다. 전체를 멈출지, 실패를 건너뛰고 진행할지는 업무 요건에서 정합니다.

### Q48. 複数のサーバに同じバッチが配られているとき、二重実行をどう防ぎますか？
(여러 서버의 배치 중복 실행 방지)

**🇯🇵 回答**

排他制御を入れます。DB の行ロックや専用のロックテーブル、あるいは Redis のロックで、**一つのノードだけが実行権を取る**形にします。

ロックを取れなかったノードは何もせずに終わります。ロックには有効期限を付けて、ノードが落ちたときに永久に握られたままにならないようにします。期限切れ後の遅れた処理に備えて、処理自体も冪等にしておきます。

**🇰🇷 답변**

배타 제어를 넣습니다. DB 의 행 락이나 전용 락 테이블, 또는 Redis 락으로 **한 노드만 실행권을 잡는** 형태로 만듭니다.

락을 못 잡은 노드는 아무것도 하지 않고 끝냅니다. 락에는 유효 기간을 붙여 노드가 죽었을 때 영원히 잡힌 채로 남지 않게 합니다. 기한 만료 후 뒤늦은 처리에 대비해 처리 자체도 멱등하게 해 둡니다.

### Q49. サーバーレスから DB に繋ぐときの落とし穴は？
(서버리스에서 DB 연결의 함정)

**🇯🇵 回答**

同時実行数がそのまま接続数になることです。関数が急に千個立ち上がると、千の接続を張りに行って**DB 側の上限で拒否されます**。アプリのエラーではなくサーバに断られる形で出ます。

対策は、接続を仲介するプロキシを挟むか、同時実行数に上限を設けることです。関数の外で接続を作って再利用する書き方も効きますが、根本的には上限の設計が要ります。

**🇰🇷 답변**

동시 실행 수가 그대로 접속 수가 되는 것입니다. 함수가 갑자기 천 개 떠오르면 천 개의 접속을 만들러 가서 **DB 쪽 상한에서 거절됩니다.** 애플리케이션 에러가 아니라 서버가 거절하는 형태로 나옵니다.

대책은 접속을 중개하는 프록시를 끼우거나 동시 실행 수에 상한을 두는 것입니다. 함수 밖에서 접속을 만들어 재사용하는 작성법도 효과가 있지만 근본적으로는 상한 설계가 필요합니다.

### Q50. 本番で急に DB が遅くなったら、どう調べますか？
(운영 DB 가 갑자기 느려졌을 때)

**🇯🇵 回答**

まず切り分けます。全部が遅いのか、特定のクエリだけか。前者ならリソースかロック、後者なら実行計画の変化を疑います。

見る順番は、実行中のクエリと待ち事象、接続数、そしてロックの依存関係です。長時間のトランザクションが一つあるだけで全体が詰まることがあります。直近のデプロイやデータ量の変化と突き合わせると、原因にたどり着きやすいです。**その場の対処と、後からの再発防止を分けて話す**ようにしています。

**🇰🇷 답변**

먼저 나눕니다. 전부 느린지, 특정 쿼리만 느린지. 전자면 리소스나 락, 후자면 실행 계획의 변화를 의심합니다.

보는 순서는 실행 중인 쿼리와 대기 이벤트, 접속 수, 그리고 락 의존 관계입니다. 장시간 트랜잭션 하나만으로 전체가 막히기도 합니다. 최근 배포나 데이터량 변화와 대조하면 원인에 닿기 쉽습니다. **그 자리의 대처와 이후의 재발 방지를 나눠서 말하도록** 하고 있습니다.
