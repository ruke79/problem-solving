## Q31. モノリスからMSAへ移行する際の最大の課題

**🇯🇵 回答**

技術的な最大の課題は、データ整合性です。モノリスなら一つのトランザクションでロールバックできたものが、サービスごとにDBが分かれた瞬間に不可能になります。対応としてはSagaパターンで補償トランザクションを設計しますが、ここで見落とされがちなのがDB更新とイベント発行の原子性です。DBにコミットした直後にプロセスが落ちてイベントが飛ばない、という状態が起きるため、Outboxパターンでイベントを同じトランザクションでDBに書き、別プロセスがそれをKafkaに送る構成にします。ただ、実際に移行を難しくしているのは技術ではなくサービス境界の切り方だと考えています。境界を間違えると、一つの機能追加で三つのサービスを同時にデプロイする必要が出てきます。これは分散モノリスと呼ばれる最悪の状態で、モノリスの結合度とMSAの運用コストを両方背負うことになります。だからDDDの境界づけられたコンテキストで慎重に切り、迷ったら大きめに切って後から分割する方針を採ります。加えて、運用の準備が先に必要です。分散トレーシングとログ集約がない状態でサービスを分けると、障害時にどこで失敗したのか誰にも分からなくなります。私はMSA化の前に可観測性を整えることを必ず条件にします。

**🇰🇷 답변**

기술적인 최대 과제는 데이터 정합성입니다. 모놀리스라면 하나의 트랜잭션으로 롤백할 수 있던 것이, 서비스 별로 DB가 나뉘는 순간 불가능해집니다. 대응으로 Saga 패턴으로 보상 트랜잭션을 설계하지만, 여기서 놓치 기 쉬운 것이 DB 갱신과 이벤트 발행의 원자성입니다. DB에 커밋한 직후 프로세스가 죽어 이벤트가 안 날아가 는 상태가 발생하므로, Outbox 패턴으로 이벤트를 같은 트랜잭션에서 DB에 쓰고 별도 프로세스가 그것을 Kafka로 보내는 구성으로 갑니다. 다만 실제로 전환을 어렵게 만드는 건 기술이 아니라 서비스 경계를 나누는 방식이라고 생각합니다. 경계를 잘 못 잡으면 기능 하나 추가에 세 개 서비스를 동시에 배포해야 하는 상황이 생깁니다. 이건 분산 모놀리스라 불리 는 최악의 상태로, 모놀리스의 결합도와 MSA의 운영 비용을 둘 다 짊어지게 됩니다. 그래서 DDD의 바운디드 컨텍스트로 신중히 나누고, 애매하면 크게 잘랐다가 나중에 분할하는 방침을 취합니다. 여기에 운영 준비가 먼저 필요합니다. 분산 트레이싱과 로그 집약이 없는 상태로 서비스를 나누면, 장애 시 어 디서 실패했는지 아무도 모르게 됩니다. 저는 MSA화 전에 관측 가능성을 갖추는 것을 반드시 조건으로 겁니 다.

## Q32. サービス間通信 REST vs gRPC の使い分け

**🇯🇵 回答**

外部公開やフロントエンドとの通信はREST、内部のサービス間はgRPCという使い分けを基本にします。RESTを外部に使う理由は、ブラウザからそのまま叩けること、HTTPキャッシュが効くこと、そしてデバッグやドキュメント化のエコシステムが圧倒的に豊富なことです。外部の開発者に使ってもらうAPIでバイナリプロトコルを強いるのは、導入障壁が高すぎます。内部にgRPCを使う理由は三つあります。Protocol Buffersによるバイナリシリアライズでペイロードが小さいこと、HTTP/2の多重化で接続を使い回せること、そしてスキーマからコードが自動生成されるため、フィールド追加時の破壊的変更をビルド時に検出できることです。実運用ではこの三つ目が一番効きます。ただし注意点があります。gRPCはHTTP/2の長寿命接続を使うため、L4ロードバランサーだと最初に繋がったPodに固定され続けて負荷が偏ります。L7対応のプロキシかクライアント側ロードバランシングが必要です。そしてもう一つ、同期RPCを使うかどうか自体を先に検討します。gRPCもRESTも同期呼び出しである限り、呼び先が落ちれば呼び元も影響を受けます。在庫更新後の通知やポイント付与のように即時性が不要なものは、Kafkaを介したイベント連携にして、そもそも同期の依存を作らない方が可用性は上がります。

**🇰🇷 답변**

외부 공개나 프론트엔드와의 통신은 REST, 내부 서비스 간은 gRPC라는 구분을 기본으로 합니다. REST를 외부에 쓰는 이유는 브라우저에서 바로 호출 가능하다는 점, HTTP 캐시가 듣는다는 점, 그리고 디버 깅과 문서화 생태계가 압도적으로 풍부하다는 점입니다. 외부 개발자가 쓸 API에 바이너리 프로토콜을 강요하 는 건 진입 장벽이 너무 높습니다. 내부에 gRPC를 쓰는 이유는 세 가지입니다. Protocol Buffers의 바이너리 직렬화로 페이로드가 작다는 점, HTTP/2 다중화로 접속을 재사용한다는 점, 그리고 스키마에서 코드가 자동 생성되므로 필드 추가 시 파괴적 변경을 빌드 타임에 검출할 수 있다는 점입니다. 실운영에서는 이 세 번째가 가장 효과적입니다. 단, 주의점이 있습니다. gRPC는 HTTP/2 장수명 접속을 쓰기 때문에 L4 로드밸런서면 처음 연결된 Pod에 계속 고정되어 부하가 치우칩니다. L7 대응 프록시나 클라이언트 사이드 로드밸런싱이 필요합니다. 그리고 하나 더, 동기 RPC를 쓸지 여부 자체를 먼저 검토합니다. gRPC든 REST든 동기 호출인 이상 호출 대 상이 죽으면 호출자도 영향을 받습니다. 재고 갱신 후의 알림이나 포인트 적립처럼 즉시성이 불필요한 것은 Kafka를 통한 이벤트 연계로 해서 애초에 동기 의존을 만들지 않는 편이 가용성이 올라갑니다.

## Q33. 分散トレーシングとは

**🇯🇵 回答**

一つのユーザーリクエストが複数サービスを横断するとき、その全経路を一本の線として追跡する仕組みです。具体的には、入り口でリクエストにTrace IDを付与し、各サービスでの処理をSpanという単位で記録します。SpanにはIDと親SpanのID、開始・終了時刻が入るので、集めるとリクエスト全体の木構造とそれぞれの所要時間が復元できます。IDを次のサービスに引き継ぐ伝播が肝で、ここは自前実装せずW3C Trace Contextの標準ヘッダーに従い、OpenTelemetryのライブラリに任せます。ベンダーロックインを避けられるのも理由です。導入して一番効くのは、「APIが遅い」という報告に対して、どのサービスのどの処理が何ミリ秒かかっているかを推測ではなく事実として出せる点です。私はここでログにもTrace IDを必ず含めるようにしています。トレースで遅い箇所を特定し、同じIDでログを引くとその時の詳細が分かるという流れを作れます。運用上の論点はサンプリングです。全リクエストを保存するとコストが現実的でないので通常は数%に絞りますが、それだとエラーのトレースが取れないことがあります。可能ならエラーや遅延したリクエストを優先して残すテールベースサンプリングを検討します。もう一点、非同期区間でトレースが途切れるのはコンテキストがThreadLocalに乗っているためで、これは例外を出さずに静かに起きるため、ダッシュボードでトレースが途中で切れているのを見て初めて気づくことが多いです。

**🇰🇷 답변**

하나의 사용자 요청이 여러 서비스를 횡단할 때, 그 전 경로를 한 줄기 선으로 추적하는 장치입니다. 구체적으로는 입구에서 요청에 Trace ID를 부여하고, 각 서비스에서의 처리를 Span이라는 단위로 기록합니 다. Span에는 ID와 부모 Span의 ID, 시작·종료 시각이 들어가므로, 모으면 요청 전체의 트리 구조와 각각의 소요 시간이 복원됩니다. ID를 다음 서비스로 넘기는 전파가 핵심이며, 이 부분은 직접 구현하지 않고 W3C Trace Context 표준 헤더를 따라 OpenTelemetry 라이브러리에 맡깁니다. 벤더 락인을 피할 수 있는 것 도 이유입니다. 도입해서 가장 효과적인 것은, “API가 느리다”는 보고에 대해 어느 서비스의 어느 처리가 몇 ms 걸리는지를 추측이 아니라 사실로 낼 수 있다는 점입니다. 저는 여기서 로그에도 Trace ID를 반드시 포함시킵니다. 트레 이스로 느린 지점을 특정하고 같은 ID로 로그를 뽑으면 그때의 상세를 알 수 있는 흐름을 만들 수 있습니다. 운영상의 논점은 샘플링입니다. 전체 요청을 저장하면 비용이 비현실적이라 보통 수 %로 좁히지만, 그러면 에 러의 트레이스를 못 잡는 경우가 있습니다. 가능하면 에러나 지연된 요청을 우선 남기는 테일 기반 샘플링을 검토합니다. 한 가지 더, 비동기 구간에서 트레이스가 끊기는 건 Context 가 ThreadLocal 에 실려 있기 때문이고, 이건 예외 없이 조용히 일어나기 때문에 대시보드에서 트레이스가 중간에 잘려 보일 때에야 알아채는 경우가 많습니다.

## Q34. サーキットブレーカーパターンの目的と動作原理

**🇯🇵 回答**

目的は障害の連鎖を止めることです。呼び先が落ちているのに呼び続けると、呼び元のスレッドがタイムアウト待ちで埋まり、無関係な機能まで巻き込んで停止します。これを防ぐために、失敗が続いたら呼び出しそのものを遮断します。動作は三状態で説明できます。通常はCLOSEDで素通しし、直近の呼び出しのうち失敗率が閾値を超えるとOPENになります。このとき「最低試行回数」も条件に入れるのが重要で、これがないと最初の1回が失敗しただけで遮断されてしまいます。OPENの間は呼び出さずに即座に失敗を返し、一定時間後にHALF-OPENへ移り、数件だけ試して回復していればCLOSEDに戻ります。設計上の要点は、遮断したときに何を返すかです。ただエラーにするのではなく、キャッシュした古い値を返す、機能を縮退させて表示だけ消す、といったフォールバックを業務側と決めておきます。もう一つ強調したいのは、サーキットブレーカーは単独では機能しないという点です。前提として全ての外部呼び出しに適切なタイムアウトが設定されていること、そしてリトライは指数バックオフとジッターを入れることが必要です。タイムアウトなしのリトライは、落ちかけた相手にトドメを刺すだけになります。具体的な数値で言うと、私は通常 minimumNumberOfCalls を5、失敗率の閾値を50%、OPEN状態の待機時間を30秒、HALF-OPENでの試行呼び出しを3件から始めます。数値を挙げること自体が「実際に設定した」という根拠になります。

**🇰🇷 답변**

목적은 장애의 연쇄를 멈추는 것입니다. 호출 대상이 죽었는데 계속 호출하면, 호출자의 스레드가 타임아웃 대 기로 채워져 무관한 기능까지 휘말려 정지합니다. 이를 막기 위해 실패가 이어지면 호출 자체를 차단합니다. 동작은 3상태로 설명할 수 있습니다. 평소에는 CLOSED로 통과시키고, 최근 호출 중 실패율이 임계치를 넘으 면 OPEN이 됩니다. 이때 “최소 시행 횟수”도 조건에 넣는 것이 중요한데, 이게 없으면 첫 1회 실패만으로 차 단되어 버립니다. OPEN 동안은 호출하지 않고 즉시 실패를 반환하고, 일정 시간 후 HALF-OPEN으로 옮겨 몇 건만 시도해 회복되었으면 CLOSED로 돌아갑니다. 설계상의 요점은 차단했을 때 무엇을 반환하는가입니다. 그냥 에러로 하지 않고, 캐시한 오래된 값을 반환한다, 기능을 축소해 표시만 없앤다 같은 폴백을 업무 쪽과 정해둡니다. 또 하나 강조하고 싶은 것은 서킷 브레이커는 단독으로는 기능하지 않는다는 점입니다. 전제로 모든 외부 호출 에 적절한 타임아웃이 설정되어 있을 것, 그리고 재시도는 지수 백오프와 지터를 넣을 것이 필요합니다. 타임아웃 없는 재시도는 죽어가는 상대에게 확인사살을 하는 셈입니다. 실제 수치로 말씀드리면, 저는 보통 minimumNumberOfCalls 를 5, 실패율 임계치를 50%, OPEN 상태 대기 시간을 30초, HALF-OPEN 에서의 시험 호출을 3건으로 시작합니다. 숫자를 대는 것 자체가 '실제로 설정해 봤다'는 근거가 됩니다.

## Q35. ゼロトラストセキュリティとmTLS

**🇯🇵 回答**

ゼロトラストは、社内ネットワークの内側だから安全という前提を捨てる考え方です。従来は境界防御、つまりファイアウォールの内側を信頼していましたが、一箇所侵入されると横移動で全体が抜かれます。そこで「どのネットワークにいるか」ではなく「誰であるか」で毎回検証する方針に切り替えます。その実装の中核がmTLSです。通常のTLSはクライアントがサーバーの証明書を検証する片方向ですが、mTLSはサーバーもクライアントの証明書を検証します。これによりサービス同士が互いの身元を暗号的に証明でき、証明書を持たないプロセスは通信そのものができません。通信内容も暗号化されるので、内部ネットワークの盗聴にも耐えます。実運用で難しいのは証明書のライフサイクル管理です。数十のサービスに証明書を配り、短い有効期限で自動ローテーションするのを自前で作るのは現実的ではありません。だからIstioのようなサービスメッシュを使い、サイドカーに証明書の発行と更新を任せる構成が一般的です。一点補足すると、mTLSは認証であって認可ではありません。「誰か」は証明できますが「何をしてよいか」は別です。サービスAはサービスBの読み取りAPIだけ呼べる、といったポリシーを別途定義する必要があります。ここを混同すると、証明書さえあれば何でも呼べる状態になります。

**🇰🇷 답변**

제로 트러스트는 사내 네트워크 내부니까 안전하다는 전제를 버리는 사고방식입니다. 종래에는 경계 방어, 즉 방화벽 안쪽을 신뢰했지만 한 곳이 뚫리면 횡이동으로 전체가 털립니다. 그래서 “어느 네트워크에 있는가”가 아니라 “누구인가”로 매번 검증하는 방침으로 전환합니다. 그 구현의 핵심이 mTLS입니다. 일반 TLS는 클라이언트가 서버 인증서를 검증하는 단방향이지만, mTLS는 서버도 클라이언트 인증서를 검증합니다. 이로써 서비스끼리 서로의 신원을 암호학적으로 증명할 수 있고, 인 증서를 갖지 않은 프로세스는 통신 자체가 불가능합니다. 통신 내용도 암호화되므로 내부 네트워크 도청에도 견딥니다. 실운영에서 어려운 것은 인증서 라이프사이클 관리입니다. 수십 개 서비스에 인증서를 배포하고 짧은 유효기간 으로 자동 로테이션하는 것을 직접 만드는 건 비현실적입니다. 그래서 Istio 같은 서비스 메시를 써서 사이드카 에 인증서 발급과 갱신을 맡기는 구성이 일반적입니다. 한 가지 보충하면, mTLS는 인증이지 인가가 아닙니다. “누구인가”는 증명하지만 “무엇을 해도 되는가”는 별 개입니다. 서비스 A는 서비스 B의 읽기 API만 호출 가능하다는 식의 정책을 별도로 정의해야 합니다. 여기를 혼동하면 인증서만 있으면 뭐든 호출 가능한 상태가 됩니다.

## Q36. APIゲートウェイの役割

**🇯🇵 回答**

クライアントからの単一の入り口として、全リクエストを受けて適切なサービスにルーティングする層です。ここに集約するのは横断的関心事です。認証トークンの検証、レート制限、TLS終端、共通のログとメトリクス出力、CORS設定など、全サービスが必要とするが本質的なビジネスロジックではないものをまとめます。メリットは、各サービスがこれらを実装しなくてよくなることで、認証ロジックが十数のサービスに散らばって仕様がずれる、という事故を防げます。同時に、注意すべき点が二つあります。一つ目は、ゲートウェイが単一障害点になることです。冗長化と、ゲートウェイ自体の性能余裕を必ず確保します。二つ目、そしてより重要なのが、ゲートウェイにビジネスロジックを入れないことです。ここに条件分岐やデータ変換を書き始めると、全サービスがゲートウェイのデプロイに依存するようになり、結局分散モノリスに戻ります。ゲートウェイに入れてよいのは「全サービスに共通で、ドメイン知識を必要としない処理」だけ、という線引きを最初に決めます。なお、クライアントごとにレスポンスを最適化したい場合は、ゲートウェイとは別にBFF層を置きます。ゲートウェイに詰め込まないための分離です。

**🇰🇷 답변**

클라이언트로부터의 단일 진입점으로서 모든 요청을 받아 적절한 서비스로 라우팅하는 계층입니다. 여기에 집약하는 것은 횡단 관심사입니다. 인증 토큰 검증, 레이트 리밋, TLS 종단, 공통 로그와 메트릭 출력, CORS 설정 등 모든 서비스가 필요로 하지만 본질적인 비즈니스 로직은 아닌 것들을 모읍니다. 장점은 각 서비 스가 이것들을 구현하지 않아도 된다는 점으로, 인증 로직이 십수 개 서비스에 흩어져 스펙이 어긋나는 사고를 막을 수 있습니다. 동시에 주의할 점이 두 가지 있습니다. 첫째, 게이트웨이가 단일 장애점이 된다는 것. 이중화와 게이트웨이 자 체의 성능 여유를 반드시 확보합니다. 둘째, 그리고 더 중요한 것이 게이트웨이에 비즈니스 로직을 넣지 않는 것 입니다. 여기에 조건 분기나 데이터 변환을 쓰기 시작하면 모든 서비스가 게이트웨이 배포에 의존하게 되어, 결 국 분산 모놀리스로 되돌아갑니다. 게이트웨이에 넣어도 되는 건 “모든 서비스에 공통이고 도메인 지식이 필요 없는 처리”뿐이라는 선을 처음에 정합니다. 덧붙여, 클라이언트별로 응답을 최적화하고 싶다면 게이트웨이와 별도로 BFF 계층을 둡니다. 게이트웨이에 몰 아넣지 않기 위한 분리입니다.

## Q37. 分散システムにおける結果整合性

**🇯🇵 回答**

更新が全ノードに即座に反映されるわけではないが、時間が経てば最終的に全ノードが同じ状態に収束する、という一貫性モデルです。なぜこれを選ぶかというと、CAP定理の帰結です。ネットワーク分断は必ず起きるという前提に立つと、強一貫性を保つには分断中に応答を止めるしかありません。可用性を優先するなら一時的な不整合を許容するという選択になります。実際、Kafkaを介したサービス間連携は本質的にこのモデルになります。設計する上で重要なのは、どこまでの遅延なら業務が成立するかを事前に決めることです。商品ページの在庫表示が数秒古いのは許容できても、決済の残高が古いのは許容できません。だから全システムを一律に結果整合性にするのではなく、ドメインごとに判断します。実装上は三点を必ず入れます。第一に冪等性で、リトライで同じイベントが二度届いても結果が変わらないようにします。第二にイベントの順序と重複への対処で、バージョン番号やタイムスタンプで古い更新を弾きます。第三にユーザー体験の考慮です。自分が投稿した直後に一覧に出てこないと壊れて見えるので、自分の更新だけはプライマリから読む、といった工夫を入れます。技術的に正しくても、ユーザーに不整合が見えたら失敗です。

**🇰🇷 답변**

갱신이 모든 노드에 즉시 반영되지는 않지만, 시간이 지나면 최종적으로 모든 노드가 같은 상태로 수렴한다는 일관성 모델입니다. 왜 이것을 선택하느냐면 CAP 정리의 귀결입니다. 네트워크 분단은 반드시 일어난다는 전제에 서면, 강일관성 을 지키려면 분단 중 응답을 멈추는 수밖에 없습니다. 가용성을 우선한다면 일시적 불일치를 허용한다는 선택 이 됩니다. 실제로 Kafka를 통한 서비스 간 연계는 본질적으로 이 모델이 됩니다. 설계할 때 중요한 것은 어느 정도의 지연까지면 업무가 성립하는지를 사전에 정하는 것입니다. 상품 페이지의 재고 표시가 수 초 오래된 건 허용해도, 결제 잔고가 오래된 건 허용할 수 없습니다. 그래서 전 시스템을 일률적 으로 결과적 일관성으로 하지 않고 도메인별로 판단합니다. 구현상으로는 세 가지를 반드시 넣습니다. 첫째 멱등성으로, 재시도로 같은 이벤트가 두 번 도착해도 결과가 변 하지 않게 합니다. 둘째 이벤트 순서와 중복 대처로, 버전 번호나 타임스탬프로 오래된 갱신을 걸러냅니다. 셋 째 사용자 경험 고려입니다. 자기가 올린 직후에 목록에 안 나오면 고장난 것처럼 보이므로, 자신의 갱신만은 프라이머리에서 읽는 식의 장치를 넣습니다. 기술적으로 옳아도 사용자에게 불일치가 보이면 실패입니다.

## Q38. Dockerコンテナと仮想マシンの違い

**🇯🇵 回答**

最大の違いは、OSカーネルを共有するかどうかです。VMはハイパーバイザーの上にゲストOSを丸ごと起動するので、カーネルを含めた完全な隔離が得られます。その代わりメモリを数GB単位で消費し、起動に数十秒かかります。一方コンテナはホストOSのカーネルを共有し、namespacesでプロセスやネットワークの見え方を分離し、cgroupsでCPUやメモリの使用量を制限しているだけです。実体は隔離されたプロセスなので、起動は一秒未満、メモリも数十MBから動きます。この差が実務にもたらす価値は、密度とスピードです。同じサーバーに何倍もの数を詰め込めますし、イメージがレイヤー構造でキャッシュされるためCI/CDが速い。そして「開発環境では動いたのに」という問題が、依存関係ごとイメージに固めることで解消されます。一方でトレードオフも明確です。カーネルを共有するということは、隔離の壁がVMより薄いということです。カーネルの脆弱性を突かれるとコンテナの外に出られる可能性がありますし、ホストと異なるカーネルを必要とするOSは動きません。だからマルチテナントで信頼できないコードを動かす場合は、VMかgVisorのようなサンドボックスを検討します。用途で使い分けるべきもので、コンテナが常にVMの上位互換というわけではありません。

**🇰🇷 답변**

가장 큰 차이는 OS 커널을 공유하는지 여부입니다. VM은 하이퍼바이저 위에 게스트 OS를 통째로 기동하므로 커널을 포함한 완전한 격리를 얻습니다. 대신 메모 리를 수 GB 단위로 소비하고 기동에 수십 초가 걸립니다. 반면 컨테이너는 호스트 OS의 커널을 공유하고, namespaces로 프로세스와 네트워크의 가시 범위를 분리하고, cgroups로 CPU와 메모리 사용량을 제한 할 뿐입니다. 실체는 격리된 프로세스이므로 기동은 1초 미만, 메모리도 수십 MB부터 돌아갑니다. 이 차이가 실무에 가져오는 가치는 밀도와 속도입니다. 같은 서버에 몇 배의 수를 담을 수 있고, 이미지가 레이 어 구조로 캐시되므로 CI/CD가 빠릅니다. 그리고 “개발 환경에서는 됐는데”라는 문제가 의존 관계째로 이미 지에 굳힘으로써 해소됩니다. 한편 트레이드오프도 명확합니다. 커널을 공유한다는 것은 격리의 벽이 VM보다 얇다는 것입니다. 커널 취약점 을 찔리면 컨테이너 밖으로 나갈 가능성이 있고, 호스트와 다른 커널을 필요로 하는 OS는 돌아가지 않습니다. 그래서 멀티테넌트로 신뢰할 수 없는 코드를 돌릴 경우에는 VM이나 gVisor 같은 샌드박스를 검토합니다. 용 도로 나눠 써야 하는 것이지, 컨테이너가 항상 VM의 상위 호환은 아닙니다.

## Q39. Kubernetesを導入する最大のメリット

**🇯🇵 回答**

最大のメリットは、あるべき状態を宣言すれば、そこに収束させ続けてくれることだと考えています。具体的には三つの形で現れます。第一に自己修復で、Podが落ちてもノードが死んでも、定義したレプリカ数になるよう自動で再作成されます。夜間にプロセスが落ちて朝まで気づかない、ということがなくなります。第二にオートスケールで、負荷に応じてHPAがPod数を増減させます。第三にローリングアップデートとロールバックが標準機能として使えることです。そしてもう一つ、地味ですが実務で効くのがサービスディスカバリです。Podは死んで再作成されるたびIPが変わりますが、Service経由で名前解決するので、呼ぶ側は相手のIPを意識しなくてよくなります。ただし正直に申し上げると、Kubernetesは無料ではありません。運用の複雑さが確実に増えます。特に効果を出すために必須なのが、リソースのrequests/limits設定と、liveness・readinessプローブの適切な実装です。ここを雑にすると、起動途中のPodにトラフィックが流れたり、逆にヘルスチェックが厳しすぎて再起動ループに入ったりします。チーム規模が小さくサービス数も少ない段階なら、マネージドのコンテナサービスの方が合理的なことも多いと考えています。

**🇰🇷 답변**

가장 큰 장점은 있어야 할 상태를 선언하면 거기로 계속 수렴시켜 준다는 점이라고 생각합니다. 구체적으로는 세 가지 형태로 나타납니다. 첫째 자가 치유로, Pod가 죽어도 노드가 죽어도 정의한 레플리카 수 가 되도록 자동으로 재생성됩니다. 야간에 프로세스가 죽어 아침까지 모르는 일이 없어집니다. 둘째 오토스케 일로, 부하에 따라 HPA가 Pod 수를 증감시킵니다. 셋째 롤링 업데이트와 롤백을 표준 기능으로 쓸 수 있다는 점입니다. 그리고 하나 더, 수수하지만 실무에서 효과적인 것이 서비스 디스커버리입니다. Pod는 죽고 재생성될 때마다 IP가 바뀌지만 Service를 통해 이름 해결하므로, 호출하는 쪽은 상대의 IP를 의식하지 않아도 됩니다. 다만 솔직히 말씀드리면 Kubernetes는 공짜가 아닙니다. 운영의 복잡도가 확실히 늘어납니다. 특히 효과를 내기 위해 필수인 것이 리소스 requests/limits 설정과 liveness·readiness 프로브의 적절한 구현입니다. 여기를 대충 하면 기동 중인 Pod로 트래픽이 흐르거나, 반대로 헬스체크가 너무 엄격해 재시작 루프에 빠집니 다. 팀 규모가 작고 서비스 수도 적은 단계라면 매니지드 컨테이너 서비스가 합리적인 경우도 많다고 생각합니 다.

## Q40. Blue-Greenデプロイとカナリアリリースの違い

**🇯🇵 回答**

Blue-Greenは、新バージョンの環境を丸ごと立ち上げ、動作確認後にトラフィックを一気に100%切り替える方式です。最大の利点は切り戻しが数秒で済むことで、問題が起きたらロードバランサーの向き先を戻すだけです。欠点は環境を二面持つのでインフラコストが倍かかること、そして切り替えた瞬間に全ユーザーが新バージョンに乗るため、検知が遅れると影響が全体に及ぶことです。カナリアは、新バージョンに1%、5%、10%と段階的にトラフィックを流し、その間エラー率とレイテンシを監視して問題なければ比率を上げていく方式です。影響範囲を限定できるのが最大の価値で、本番でしか出ない問題を少数のユーザーで検知できます。欠点は、判定の自動化と十分なメトリクスがないと機能しないこと、そして2バージョンが同時に動く期間が長くなることです。実務で本当に難しいのは、どちらの方式でもDBスキーマの変更です。ロールバックしてもDBは戻せないので、カラム追加と削除を同一リリースでやらない、いわゆる拡張・縮小方式を徹底します。新旧どちらのコードでも動くスキーマを一度経由してから、後続リリースで古いカラムを消します。使い分けとしては、影響が読みにくい大きな変更やパフォーマンス特性が変わる変更はカナリア、影響が限定的で早く出したいものはBlue-Greenを選びます。両者を併用し、機能単位の出し分けはフィーチャーフラグで別管理するのが今の主流だと考えています。

**🇰🇷 답변**

Blue-Green은 새 버전 환경을 통째로 띄워 동작 확인 후 트래픽을 한 번에 100% 전환하는 방식입니다. 최 대 이점은 롤백이 수 초면 끝난다는 것으로, 문제가 생기면 로드밸런서의 방향만 되돌리면 됩니다. 단점은 환경 을 두 벌 유지하므로 인프라 비용이 배로 든다는 점, 그리고 전환하는 순간 모든 사용자가 새 버전으로 옮겨가므 로 탐지가 늦으면 영향이 전체에 미친다는 점입니다. 카나리는 새 버전에 1%, 5%, 10%로 단계적으로 트래픽을 흘리며 그동안 에러율과 레이턴시를 모니터링해 문제없으면 비율을 올려가는 방식입니다. 영향 범위를 한정할 수 있는 것이 최대 가치로, 프로덕션에서만 나오 는 문제를 소수 사용자로 탐지할 수 있습니다. 단점은 판정 자동화와 충분한 메트릭이 없으면 기능하지 않는다 는 점, 그리고 두 버전이 동시에 도는 기간이 길어진다는 점입니다. 실무에서 진짜 어려운 것은 어느 방식이든 DB 스키마 변경입니다. 롤백해도 DB는 되돌릴 수 없으므로, 컬럼 추가와 삭제를 같은 릴리스에서 하지 않는, 이른바 확장·축소 방식을 철저히 지킵니다. 신·구 어느 코드에서도 돌아가는 스키마를 한 번 경유한 뒤, 후속 릴리스에서 옛 컬럼을 지웁니다. 사용 구분으로는, 영향을 읽기 어려운 큰 변경이나 성능 특성이 바뀌는 변경은 카나리, 영향이 한정적이고 빨리 내고 싶은 것은 Blue-Green을 고릅니다. 양쪽을 병용하고 기능 단위의 노출 제어는 피처 플래그로 별도 관리 하는 것이 현재 주류라고 생각합니다.

## Q41. KafkaとRabbitMQの違い

**🇯🇵 回答**

根本的な違いは、Kafkaが「ログ」でRabbitMQが「キュー」である点です。RabbitMQはメッセージブローカーで、コンシューマーがACKを返した時点でメッセージはキューから消えます。一件ずつの配送保証と、Exchangeによる柔軟なルーティング、優先度や遅延配送といった機能が強みです。タスク分配やRPC的な用途に向いています。Kafkaは分散コミットログで、メッセージはディスクに追記され、消費されても保持期間が来るまで消えません。コンシューマーは自分がどこまで読んだかというオフセットを持つだけです。この構造から二つの強みが出ます。一つは過去に遡っての再処理で、バグを直したあとオフセットを戻して同じデータを流し直せます。もう一つは、同じデータを複数の用途で独立に読めることで、リアルタイム処理と分析基盤への転送が互いに干渉しません。順次書き込みなのでスループットも桁違いです。使い分けとしては、イベントストリーミング、大量ログ、複数の下流で同じデータを使う、再処理が必要、という場合はKafka。細かいルーティング、優先度、遅延メッセージ、少量でも低レイテンシなタスクキュー、という場合はRabbitMQを選びます。一点付け加えると、Kafkaは順序保証がパーティション単位である点に注意が必要です。同じキーは同じパーティションに行くので、注文IDをキーにすればその注文内の順序は保証されますが、全体の順序は保証されません。ここを誤解すると本番で順序逆転の事故になります。

**🇰🇷 답변**

근본적인 차이는 Kafka가 "로그"이고 RabbitMQ가 "큐"라는 점입니다. RabbitMQ는 메시지 브로커로, 컨슈머가 ACK를 반환한 시점에 메시지가 큐에서 사라집니다. 건별 배송 보 증과 Exchange를 통한 유연한 라우팅, 우선순위나 지연 배송 같은 기능이 강점입니다. 태스크 분배나 RPC 적 용도에 적합합니다. Kafka는 분산 커밋 로그로, 메시지는 디스크에 추가되고 소비되어도 보존 기간이 올 때까지 사라지지 않습니 다. 컨슈머는 자기가 어디까지 읽었는지의 오프셋을 가질 뿐입니다. 이 구조에서 두 가지 강점이 나옵니다. 하 나는 과거로 거슬러 올라간 재처리로, 버그를 고친 뒤 오프셋을 되돌려 같은 데이터를 다시 흘릴 수 있습니다. 다른 하나는 같은 데이터를 여러 용도로 독립적으로 읽을 수 있어, 실시간 처리와 분석 기반으로의 전송이 서로 간섭하지 않는 점입니다. 순차 쓰기이므로 스루풋도 자릿수가 다릅니다. 사용 구분으로는, 이벤트 스트리밍, 대량 로그, 여러 하류에서 같은 데이터를 사용, 재처리 필요라면 Kafka. 세 밀한 라우팅, 우선순위, 지연 메시지, 소량이어도 저지연 태스크 큐라면 RabbitMQ를 고릅니다. 한 가지 덧붙이면, Kafka는 순서 보증이 파티션 단위라는 점에 주의가 필요합니다. 같은 키는 같은 파티션으로 가므로 주문 ID를 키로 하면 그 주문 내의 순서는 보증되지만, 전체 순서는 보증되지 않습니다. 여기를 오해하 면 프로덕션에서 순서 역전 사고가 됩니다.

## Q42. トラフィック急増時にKafkaでシステムを守る

**🇯🇵 回答**

考え方は負荷平準化です。瞬間的なピークをそのままDBに流すのではなく、Kafkaに一度受け止めて、コンシューマーが処理できる速度でだけ引き取ります。書き込みは順次追記なので、Kafka自体は非常に高いスループットに耐えます。APIの設計もこれに合わせます。リクエストを受けたら最低限の検証だけしてKafkaにpublishし、即座に202 Acceptedと受付IDを返します。ユーザーには別のエンドポイントかWebSocketで完了を通知します。同期でDBまで書き切ろうとするから詰まるので、同期パスを最短にするのが本質です。コンシューマー側では、DBへの書き込みをバッチにまとめてラウンドトリップを減らし、リトライで重複が来る前提で冪等キーによる重複排除を入れます。ただし、正直に言うとキューは万能ではありません。キューは負荷を遅らせるだけで、消してはくれない。到着レートが処理能力を継続的に超えていれば、ラグは無限に伸びてデータは古くなり続けます。だから前段でレート制限を入れて過剰な流入自体を止めること、そしてスケール限界を事前に把握しておくことが必要です。特にコンシューマーはパーティション数より増やせないので、パーティション数は将来の並列度を見越して設計時に決めておきます。ここは後から増やしにくいポイントです。

**🇰🇷 답변**

사고방식은 부하 평준화입니다. 순간적인 피크를 그대로 DB로 흘리지 않고 Kafka에 한 번 받아둔 뒤, 컨슈머 가 처리할 수 있는 속도로만 가져갑니다. 쓰기가 순차 추가이므로 Kafka 자체는 매우 높은 스루풋을 견딥니다. API 설계도 여기에 맞춥니다. 요청을 받으면 최소한의 검증만 하고 Kafka에 publish한 뒤 즉시 202 Accepted와 접수 ID를 반환합니다. 사용자에게는 별도 엔드포인트나 WebSocket으로 완료를 통지합니 다. 동기로 DB까지 다 쓰려고 하니까 막히는 것이므로, 동기 경로를 최단으로 하는 것이 본질입니다. 컨슈머 쪽에서는 DB 쓰기를 배치로 묶어 라운드트립을 줄이고, 재시도로 중복이 온다는 전제로 멱등 키에 의한 중복 제거를 넣습니다. 다만 솔직히 말해 큐는 만능이 아닙니다. 큐는 부하를 미룰 뿐 없애주지 않습니다. 도착 레이트가 처리 능력을 지속적으로 넘으면 랙은 무한히 늘어나고 데이터는 계속 오래됩니다. 그래서 앞단에 레이트 리밋을 넣어 과도 한 유입 자체를 막는 것, 그리고 스케일 한계를 사전에 파악해 두는 것이 필요합니다. 특히 컨슈머는 파티션 수 보다 늘릴 수 없으므로, 파티션 수는 미래의 병렬도를 내다보고 설계 시점에 정해둡니다. 이건 나중에 늘리기 어려운 지점입니다.

## Q43. Kafkaコンシューマーの再処理戦略

**🇯🇵 回答**

前提として、同じパーティション内でリトライを繰り返すのは避けます。Kafkaはオフセット順に処理するため、一件が詰まるとその後ろが全て止まる、ヘッドオブラインブロッキングが発生するからです。一件の不正データで数万件が止まります。そこでノンブロッキングリトライを採ります。失敗したメッセージは元のトピックでは処理済みとしてコミットし、リトライ専用トピックに移します。リトライトピックは遅延の段階を分けて用意し、5秒後、1分後、10分後のように間隔を広げながら再試行させます。ここでも失敗したらDLQに退避させます。Spring Kafkaなら @RetryableTopic でこの構成を宣言的に組めます。ただしトレードオフを明示すべきで、リトライトピックに移した時点でそのメッセージの順序は崩れます。順序が業務要件に含まれる場合、例えば同一口座の入出金のようなケースでは、この方式は使えません。その場合は該当キーの処理を一時停止させるか、そもそも順序に依存しない設計に変えるかを検討します。エラーの分類も重要です。相手のタイムアウトのような一時的エラーはリトライで回復しますが、必須項目が欠けたデータは何度やっても失敗するので、即座にDLQへ送る方が無駄がありません。最後にDLQは、入れて終わりでは意味がありません。件数をメトリクス化してアラートし、再投入する運用手段まで用意して初めて完成だと考えています。

**🇰🇷 답변**

전제로, 같은 파티션 안에서 재시도를 반복하는 것은 피합니다. Kafka는 오프셋 순으로 처리하므로 한 건이 막 히면 그 뒤가 전부 멈추는 헤드 오브 라인 블로킹이 발생하기 때문입니다. 한 건의 불량 데이터로 수만 건이 멈 춥니다. 그래서 논블로킹 재시도를 취합니다. 실패한 메시지는 원래 토픽에서는 처리 완료로 커밋하고 재시도 전용 토 픽으로 옮깁니다. 재시도 토픽은 지연 단계를 나눠 준비해, 5초 후·1분 후·10분 후처럼 간격을 넓히며 재시도시 킵니다. 여기서도 실패하면 DLQ로 대피시킵니다. Spring Kafka라면 @RetryableTopic 으로 이 구성을 선언적으로 짤 수 있습니다. 다만 트레이드오프를 명시해야 하는데, 재시도 토픽으로 옮긴 시점에 그 메시지의 순서는 깨집니다. 순서가 업 무 요건에 포함된 경우, 예를 들어 동일 계좌의 입출금 같은 케이스에서는 이 방식을 쓸 수 없습니다. 그 경우에 는 해당 키의 처리를 일시 정지시키거나, 애초에 순서에 의존하지 않는 설계로 바꿀지를 검토합니다. 에러 분류도 중요합니다. 상대의 타임아웃 같은 일시적 에러는 재시도로 회복되지만, 필수 항목이 빠진 데이터 는 몇 번을 해도 실패하므로 즉시 DLQ로 보내는 편이 낭비가 없습니다. 마지막으로 DLQ는 넣고 끝이면 의미가 없습니다. 건수를 메트릭화해 알림을 걸고 재투입하는 운영 수단까지 준비해야 비로소 완성이라고 생각합니다.

## Q44. コネクションリークの検出と調査 【Q18の深掘り版】

> ⚠️ Q18と同一の設問。ここでは「リークなのか、長時間占有なのか、そもそもプール不足なの か」の判別プロセスに軸を置いた別バージョンです。

**🇯🇵 回答**

まず、症状が似た三つを切り分けるところから始めます。プールが枯渇しているという現象は同じでも、原因が「返却されていない(リーク)」「返却は遅いが返ってはいる(長時間占有)」「単純にプールが小さい(容量不足)」の三つに分かれ、対処が全く違うためです。判別にはメトリクスの形を見ます。負荷が下がっても hikaricp.connections.active が減らず階段状に増え続けるならリーク。負荷に連動して増減するがピークで pending が発生するなら占有か容量不足。占有か容量不足かは、平均の貸出時間を見れば分かります。数百ミリ秒なら容量不足、数秒以上なら何かを待っています。リークだと判断したら leakDetectionThreshold を設定します。これは指定時間を超えて返却されないコネクションについて、借りた時点のスタックトレースを警告ログに出力するもので、犯人のメソッドが直接特定できます。それでも分からなければスレッドダンプを取り、どのスレッドがどこで止まっているかを確認します。原因として実際に多いのは、DataSource から直接取得して try-with-resources を使っていない箇所、@Transactional の内側で外部API呼び出しをしていて相手の遅延をそのまま持ち込んでいるケース、そしてOSIVが有効でビュー描画までセッションを保持しているケースです。二番目は厳密にはリークではありませんが、症状も対処も同じで、トランザクション境界からI/O待ちを外に出すのが解決策になります。

**🇰🇷 답변**

먼저, 증상이 비슷한 세 가지를 구분하는 것부터 시작합니다. 풀이 고갈된다는 현상은 같아도 원인이 “반환되지 않음(누수)”, “반환은 느리지만 돌아옴(장시간 점유)”, “단순히 풀이 작음(용량 부족)“의 세 가지로 갈리고, 대 처가 완전히 다르기 때문입니다. 판별에는 메트릭의 형태를 봅니다. 부하가 내려가도 hikaricp.connections.active 가 줄지 않고 계단식 으로 계속 늘면 누수. 부하에 연동해 증감하지만 피크에서 pending 이 발생하면 점유거나 용량 부족. 점유인 지 용량 부족인지는 평균 대출 시간을 보면 알 수 있습니다. 수백 ms면 용량 부족, 수 초 이상이면 무언가를 기 다리고 있는 것입니다. 누수로 판단되면 leakDetectionThreshold 를 설정합니다. 이는 지정 시간을 넘겨 반환되지 않은 커넥션에 대해 빌린 시점의 스택 트레이스를 경고 로그로 출력하는 것으로, 범인 메서드를 직접 특정할 수 있습니다. 그래 도 모르겠으면 스레드 덤프를 떠서 어느 스레드가 어디서 멈춰 있는지 확인합니다. 원인으로 실제로 많은 것은, DataSource 에서 직접 얻으면서 try-with-resources를 쓰지 않은 부분, @Transactional 안쪽에서 외부 API를 호출해 상대의 지연을 그대로 끌어들이는 케이스, 그리고 OSIV가 켜져 있어 뷰 렌더링까지 세션을 유지하는 케이스입니다. 두 번째는 엄밀히는 누수가 아니지만 증상도 대처도 같으며, 트랜잭션 경계에서 I/O 대기를 밖으로 빼는 것이 해결책이 됩니다.

## Q45. オートスケーリングのトリガー条件設計

**🇯🇵 回答**

CPU使用率だけをトリガーにするのは、多くのアプリケーションで不適切だと考えています。Webアプリの大半はI/O待ちが主なので、DBの応答が遅くてリクエストが詰まっていてもCPUは低いままです。CPUが上がった頃には既に手遅れです。だからアプリの特性に合わせたカスタムメトリクスを使います。API層ならリクエストレートかp95レイテンシ、あるいはスレッドプールの使用率。Kafkaコンシューマーならコンシューマーラグが最も適切で、ラグが一定件数を超えたらPodを増やす、というのが最も素直な指標です。KEDAを使えばこうした外部メトリクスでのスケールが素直に組めます。設計上、必ず考慮する点が三つあります。第一にスケールアウトには時間がかかること。イメージのpull、JVMの起動とウォームアップまで含めると数十秒から数分かかるので、閾値は限界の手前、例えば使用率70%程度で先に発火させます。第二にフラッピング防止で、スケールインには長めの安定化ウィンドウを設定します。増減を繰り返すと接続断が頻発します。第三に、下流の限界を必ず確認すること。Podを10倍にしてもDBの最大接続数は変わらないので、無邪気にスケールするとDB側を落とします。1Podあたりのプールサイズ×最大Pod数がDBの上限を超えないよう逆算しておきます。最後に、急激なスパイクは事後のスケールでは間に合わないので、イベントが分かっている場合はスケジュールベースで事前にスケールさせます。

**🇰🇷 답변**

CPU 사용률만 트리거로 삼는 것은 많은 애플리케이션에서 부적절하다고 생각합니다. 웹 앱의 대부분은 I/O 대기가 주이므로, DB 응답이 느려 요청이 밀려도 CPU는 낮게 유지됩니다. CPU가 올라갔을 때는 이미 늦습 니다. 그래서 앱 특성에 맞춘 커스텀 메트릭을 씁니다. API 계층이면 요청 레이트나 p95 레이턴시, 혹은 스레드 풀 사용률. Kafka 컨슈머라면 컨슈머 랙이 가장 적절하며, 랙이 일정 건수를 넘으면 Pod를 늘리는 것이 가장 자 연스러운 지표입니다. KEDA를 쓰면 이런 외부 메트릭 기반 스케일을 무리 없이 구성할 수 있습니다. 설계상 반드시 고려하는 점이 세 가지 있습니다. 첫째, 스케일 아웃에는 시간이 걸린다는 것. 이미지 pull, JVM 기동과 워밍업까지 포함하면 수십 초~수 분 걸리므로, 임계치는 한계 앞에서, 예를 들어 사용률 70% 정 도에서 먼저 발화시킵니다. 둘째 플래핑 방지로, 스케일 인에는 긴 안정화 윈도를 설정합니다. 증감을 반복하면 접속 단절이 빈발합니다. 셋째, 하류의 한계를 반드시 확인할 것. Pod를 10배로 해도 DB 최대 접속 수는 변하 지 않으므로, 순진하게 스케일하면 DB 쪽을 죽입니다. 1Pod당 풀 사이즈 × 최대 Pod 수가 DB 상한을 넘지 않도록 역산해 둡니다. 마지막으로, 급격한 스파이크는 사후 스케일로는 늦으므로 이벤트를 아는 경우에는 스케줄 기반으로 사전에 스 케일시킵니다. Part 3 (Q31~45) の要点 / 요점 この15問を貫く評価軸は「分散させたことで新しく生まれる問題を語れるか」です。MSA・ K8s・Kafkaは、いずれも問題を解決すると同時に新しい問題を作ります。整合性、順序、障害の連 鎖、運用の複雑さ。メリットだけを述べる候補者と、その代償を言える候補者の差がそのまま評価差 になります。 이 15문항을 관통하는 평가 축은 “분산시킴으로써 새로 생기는 문제를 말할 수 있는가“입니다. MSA·K8s·Kafka는 모두 문제를 해결하는 동시에 새로운 문제를 만듭니다. 정합성, 순서, 장애 연쇄, 운영 복 잡도. 장점만 말하는 지원자와 그 대가를 말할 수 있는 지원자의 차이가 그대로 평가 차이가 됩니다.
