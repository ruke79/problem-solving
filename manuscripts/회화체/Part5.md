# Part 8. 시스템 설계 (System Design)

### Q61. 大規模チケット予約システムのDBダウン防止
(대규모 티켓 예약 시스템의 DB 다운 방지)

**🇯🇵 回答**

このタイプの設計で最初に決めるべきは、「どこまでを同期で処理して、どこからを非同期に逃がすか」という境界線です。

まず入り口に待機列を置きます。開始時刻ちょうどに殺到するアクセスを、RedisのSorted Setやトークンベースの仕組みで受け止めて、順番に応じてトークンを発行します。ここでのポイントは、待機列自体が新たなボトルネックにならないことです。Redisへの書き込みだけで完結させて、この時点ではDBに触れさせません。

座席選択と決済は、もう一段守りが必要です。同一座席への同時アクセスは、DBの行ロックだけに頼らずRedisで先に排他制御します。座席IDをキーにSETNXで数秒だけ仮押さえして、決済が成立したらDBに確定を書く。仮押さえが切れれば他の人に解放される、という設計ですね。DBの行ロックは競合したときに長く待たされる可能性がありますが、Redisの操作はミリ秒で終わるので、ユーザー体験の面でも有利です。

決済の確定処理はKafkaを介して非同期にします。フロントには「受付済み」を即座に返して、実際の確定はコンシューマーがDBの許容量に合わせて処理します。これでDBへの書き込みレートは、常に一定の上限以下に保たれます。

そして忘れてはいけないのが、在庫という有限リソースの整合性です。売り切れ超過が最も避けたい事故なので、座席数の減算はDBのトランザクションで行って、Redis側の仮押さえと最終的な一貫性を持たせるための照合バッチも用意します。

**🇰🇷 답변**

이런 유형의 설계에서 제일 먼저 정해야 할 건, "어디까지를 동기로 처리하고 어디부터를 비동기로 뺄 것인가"라는 경계선입니다.

먼저 입구에 대기열을 둡니다. 시작 시각 정각에 몰리는 접속을 Redis의 Sorted Set이나 토큰 기반 장치로 받아서, 순서에 따라 토큰을 발행합니다. 여기서 포인트는 대기열 자체가 새로운 병목이 되지 않는 겁니다. Redis 쓰기만으로 완결시키고, 이 시점에서는 DB를 안 건드리게 합니다.

좌석 선택이랑 결제는 한 단계 더 방어가 필요합니다. 같은 좌석에 대한 동시 접근은 DB 행 락에만 의존하지 않고 Redis로 먼저 배타 제어합니다. 좌석 ID를 키로 SETNX로 몇 초만 가예약하고, 결제가 성립하면 DB에 확정을 씁니다. 가예약이 만료되면 다른 사람한테 풀리는 설계고요. DB 행 락은 경합했을 때 오래 기다릴 가능성이 있는데, Redis 조작은 밀리초로 끝나니까 사용자 경험 면에서도 유리합니다.

결제 확정 처리는 Kafka를 통해 비동기로 합니다. 프론트에는 "접수 완료"를 즉시 반환하고, 실제 확정은 컨슈머가 DB의 허용량에 맞춰서 처리합니다. 이러면 DB로의 쓰기 레이트가 항상 일정 상한 이하로 유지됩니다.

그리고 잊으면 안 되는 게 재고라는 유한 자원의 정합성입니다. 초과 판매가 제일 피하고 싶은 사고니까, 좌석 수 감산은 DB 트랜잭션으로 하고, Redis 쪽 가예약이랑 최종적 일관성을 맞추기 위한 대조 배치도 준비합니다.

### Q62. 分散環境でのAPI Rate Limit実装
(분산 환경에서의 API Rate Limit 구현)

**🇯🇵 回答**

複数のゲートウェイインスタンスが状態を共有する必要があるので、Redisを中央のカウンターとして使います。

アルゴリズムはトークンバケットを基本にします。固定ウィンドウ方式は、ウィンドウの境界をまたいだ瞬間に制限の2倍のリクエストが通ってしまうという弱点があるので避けます。実際に測ると、制限が秒間10件でも、境界を跨ぐ200ミリ秒の区間で20件が通過します。ウィンドウが切り替わる瞬間に、前のウィンドウの残余と新しいウィンドウの許容量が重なるからですね。トークンバケットなら一定レートでトークンが補充されて、バーストも一定量までは許容できるので、実際のトラフィックパターンに近い制御ができます。

実装で最も注意すべきは、「残トークンの確認」と「消費」の間で競合状態が起きることです。複数のリクエストが同時にRedisへ問い合わせると、両方が「まだ枠がある」と判定してしまって、制限を超えて通してしまいます。これを防ぐには、確認と消費を単一の操作にする必要があって、Luaスクリプトでアトミックに実行します。RedisはシングルスレッドでLuaスクリプトを実行するので、スクリプト内の処理は他のコマンドに割り込まれません。

キー設計も重要で、ユーザー単位、APIエンドポイント単位、あるいはその組み合わせで、細かく制限をかけられるようにします。

もう一つ実務的な論点は、Redis自体の可用性です。Rate LimitのためにRedisを噛ませたことで、Redisが落ちると全APIが機能しなくなる。これは本末転倒ですよね。Redis障害時はフェイルオープン、つまり制限をかけずに全通過にするか、フェイルクローズにするかを、業務の性質で事前に決めておきます。決済APIのような濫用リスクが高いものはフェイルクローズ寄り、それ以外は可用性を優先してフェイルオープンにすることが多いです。

**🇰🇷 답변**

여러 게이트웨이 인스턴스가 상태를 공유해야 하니까, Redis를 중앙 카운터로 씁니다.

알고리즘은 토큰 버킷을 기본으로 합니다. 고정 윈도 방식은 윈도 경계를 넘는 순간 제한의 2배 요청이 통과해 버리는 약점이 있어서 피합니다. 실제로 재 보면, 제한이 초당 10건이어도 경계를 낀 200밀리초 구간에 20건이 통과합니다. 창이 넘어가는 순간에 이전 창의 잔여분이랑 새 창의 허용치가 겹치기 때문이죠. 토큰 버킷이면 일정 레이트로 토큰이 채워지고 버스트도 일정량까지 허용되니까, 실제 트래픽 패턴에 가까운 제어가 가능합니다.

구현에서 제일 주의해야 할 건, "잔여 토큰 확인"이랑 "소비" 사이에 경쟁 상태가 생긴다는 겁니다. 여러 요청이 동시에 Redis에 물어보면 둘 다 "아직 여유가 있다"고 판정해 버려서, 제한을 넘겨 통과시킵니다. 이걸 막으려면 확인이랑 소비를 단일 조작으로 만들어야 하고, Lua 스크립트로 원자적으로 실행합니다. Redis는 싱글 스레드로 Lua 스크립트를 실행하니까, 스크립트 안의 처리는 다른 명령에 안 끼어들립니다.

키 설계도 중요해서, 사용자 단위, API 엔드포인트 단위, 아니면 그 조합으로 세밀하게 제한을 걸 수 있게 합니다.

또 하나 실무적인 논점은 Redis 자체의 가용성입니다. Rate Limit 하려고 Redis를 끼웠는데 Redis가 죽으면 전체 API가 기능을 못 한다. 이건 본말전도잖아요. Redis 장애 시 페일 오픈, 그러니까 제한 없이 전부 통과시킬지, 페일 클로즈로 할지를 업무 성격으로 미리 정해 둡니다. 결제 API처럼 악용 리스크가 높은 건 페일 클로즈 쪽, 그 외에는 가용성을 우선해서 페일 오픈으로 하는 경우가 많습니다.

### Q63. SPOF（単一障害点）の特定と排除
(SPOF 특정과 배제)

**🇯🇵 回答**

SPOFを見つけるアプローチは、リクエストが入り口から応答を返すまでの経路を一本ずつたどって、「この箱が一つ落ちたら何が止まるか」を各層で問うことです。

代表的な層ごとに見ていきます。まずロードバランサー自体が単一ノードなら冗長化します。クラウドならマネージドLBが前提として冗長化されていることが多いですが、オンプレやセルフホストの場合は明示的にActive-Standbyや複数台構成にする必要があります。

次にアプリケーション層はステートレスにしてAuto Scalingグループに乗せて、複数AZに分散配置します。ステートを持たせるとインスタンス障害時にセッションが消えるので、セッションはRedisなど外部ストアに出します。

DB層が最も難しいです。Primary-Replica構成にしてもPrimaryそのものは単一障害点として残ります。ここへの対処は、フェイルオーバーの自動化と、フェイルオーバーにかかる時間をSLAとして許容できるかの判断ですね。マネージドサービスなら自動、自前ならPatroniのようなツールを使います。Multi-AZ配置で物理的な障害には強くなりますが、フェイルオーバー中の数十秒は書き込みが止まる、という制約は残ります。

実は見落とされやすいSPOFが二つあります。一つはDNSで、TTLを長く設定していると、フェイルオーバー後も古いIPを引き続ける端末が出ます。もう一つは外部依存です。たとえば決済代行会社や認証プロバイダですね。ここが落ちると、どれだけ自社を冗長化しても止まります。外部依存に対してはサーキットブレーカーとフォールバックを用意して、キャッシュされた結果を返すとか縮退運転するとか、完全な代替は無理でも影響範囲を局所化します。

**🇰🇷 답변**

SPOF를 찾는 접근은, 요청이 입구부터 응답을 반환할 때까지의 경로를 한 줄씩 따라가면서 "이 상자가 하나 죽으면 뭐가 멈추는가"를 각 층에서 묻는 겁니다.

대표적인 층별로 보겠습니다. 먼저 로드밸런서 자체가 단일 노드면 이중화합니다. 클라우드면 매니지드 LB가 전제로 이중화돼 있는 경우가 많지만, 온프레미스나 셀프 호스트면 명시적으로 Active-Standby나 다중 구성으로 해야 합니다.

다음으로 애플리케이션 계층은 스테이트리스로 만들어서 오토 스케일링 그룹에 올리고, 여러 AZ에 분산 배치합니다. 상태를 갖게 하면 인스턴스 장애 시 세션이 사라지니까, 세션은 Redis 같은 외부 스토어로 뺍니다.

DB 계층이 제일 어렵습니다. Primary-Replica 구성으로 해도 Primary 자체는 단일 장애점으로 남거든요. 여기에 대한 대처는 페일오버 자동화랑, 페일오버에 걸리는 시간을 SLA로 허용할 수 있는지의 판단입니다. 매니지드 서비스면 자동이고, 자체 구축이면 Patroni 같은 도구를 씁니다. Multi-AZ 배치로 물리적 장애에는 강해지지만, 페일오버 중 수십 초는 쓰기가 멈춘다는 제약은 남습니다.

사실 놓치기 쉬운 SPOF가 두 가지 있습니다. 하나는 DNS로, TTL을 길게 설정해 두면 페일오버 후에도 옛 IP를 계속 참조하는 단말이 나옵니다. 다른 하나는 외부 의존입니다. 예를 들어 결제 대행사나 인증 프로바이더요. 여기가 죽으면 자사를 아무리 이중화해도 멈춥니다. 외부 의존에 대해서는 서킷 브레이커랑 폴백을 준비해서, 캐시된 결과를 반환한다든가 축소 운영한다든가, 완전한 대체는 무리여도 영향 범위를 국소화합니다.

### Q64. URL短縮サービスの設計
(URL 단축 서비스 설계)

**🇯🇵 回答**

要件を最初に確認したいのは、「短縮URLは推測されて困るか、つまりランダム性が必要か」という点です。企業の秘密キャンペーンURLなどは、連番だと推測されるリスクがありますから。今回は一般的なユースケースとして進めます。

ID採番は、DBのAuto Incrementで一意な数値IDを発行して、それをBase62、つまり0-9、a-z、A-Zにエンコードして短縮コードにします。7桁のBase62で約3.5兆通り、62の7乗ですね、これをカバーできるので当面の規模には十分です。6桁でも568億通りあるので、サービス規模によっては6桁から始める判断もあります。ハッシュ化して衝突を確認するより、採番の一意性をDBに保証させるほうが、実装がシンプルで確実です。分散環境で採番サーバーがボトルネックにならないよう、IDの範囲を各アプリインスタンスに事前配布するTicket Serverの仕組みも選択肢に入れます。

読み書きの比率は、読み取りが圧倒的に多いサービスなので、ここに設計の重心を置きます。短縮コードをキーにしたRedisキャッシュを必須にして、リダイレクトのほとんどをDBに触れずに返せるようにします。DBスキーマは short_code を主キーにして、original_url、created_at、expires_at、click_count 程度ですね。クリック数のような頻繁に更新される値は、書き込み競合を避けるため同期的にインクリメントせず、Kafka経由で非同期集計にします。

リダイレクトのHTTPステータスも設計判断です。301、つまり恒久的リダイレクトにすると、ブラウザがキャッシュしてしまって以後サーバーに来なくなるので、クリック数が計測できません。分析が必要なら302を使う、というのは意外と見落とされがちな点です。

**🇰🇷 답변**

요건을 먼저 확인하고 싶은 건, "단축 URL이 추측되면 곤란한가, 그러니까 랜덤성이 필요한가"라는 점입니다. 기업의 비밀 캠페인 URL 같은 건 연번이면 추측될 리스크가 있으니까요. 이번에는 일반적인 유스케이스로 진행하겠습니다.

ID 채번은 DB의 Auto Increment로 유일한 숫자 ID를 발급하고, 그걸 Base62, 그러니까 0-9, a-z, A-Z로 인코딩해서 단축 코드로 만듭니다. 7자리 Base62로 약 3.5조 가지, 62의 7제곱이죠, 이걸 커버할 수 있으니까 당분간 규모에는 충분합니다. 6자리로도 568억이라, 서비스 규모에 따라서는 6자리로 시작하는 판단도 있고요. 해시화해서 충돌을 확인하는 것보다, 채번의 유일성을 DB에 보증시키는 쪽이 구현이 단순하고 확실합니다. 분산 환경에서 채번 서버가 병목이 안 되도록, ID 범위를 각 앱 인스턴스에 미리 배포하는 Ticket Server 방식도 선택지에 넣습니다.

읽기쓰기 비율은 읽기가 압도적으로 많은 서비스라서, 여기에 설계의 무게중심을 둡니다. 단축 코드를 키로 한 Redis 캐시를 필수로 하고, 리다이렉트 대부분을 DB를 안 건드리고 반환할 수 있게 합니다. DB 스키마는 short_code를 기본키로 하고, original_url, created_at, expires_at, click_count 정도입니다. 클릭 수처럼 자주 갱신되는 값은 쓰기 경합을 피하려고 동기적으로 증가시키지 않고, Kafka를 통해 비동기 집계합니다.

리다이렉트의 HTTP 상태 코드도 설계 판단입니다. 301, 그러니까 영구 리다이렉트로 하면 브라우저가 캐시해 버려서 이후로 서버에 안 오니까 클릭 수를 계측할 수 없습니다. 분석이 필요하면 302를 쓴다, 이건 의외로 놓치기 쉬운 부분입니다.

### Q65. レプリケーションとシャーディングの使い分け
(레플리케이션과 샤딩의 구분)

**🇯🇵 回答**

まず適用する順番があります。読み取りが多いなら先にレプリケーションを試して、それでも足りない、あるいは書き込みそのものが限界を超えているときに、初めてシャーディングを検討します。シャーディングは最後の手段、という位置づけを崩しません。

レプリケーションはデータの複製を複数持つだけなので、導入が容易です。アプリ側の変更もほぼ、読み取り先の向き先を変えるだけで済みます。ただしレプリカ遅延という代償があって、書き込み直後にレプリカを読むと古いデータが返る可能性があります。決済直後の残高確認のように整合性が必要な処理は、意図的にPrimaryを読みに行く実装が必要です。

シャーディングはデータ自体を複数のDBに水平分割するので、書き込み容量そのものを増やせます。ただ代償が非常に大きいです。「どのシャードにデータがあるか」を判断するシャーディングキーの設計が最重要で、これを誤ると特定シャードにデータとアクセスが偏るホットスポットが発生します。さらに、異なるシャードをまたぐJOINができなくなって、トランザクションも単一シャード内でしか完結しません。ユーザーIDでシャーディングした場合、複数ユーザーにまたがる集計処理は、アプリ側で各シャードに問い合わせて結果をマージする必要があります。

実務での判断基準は、「シャーディングを避けるための代替手段を使い切ったか」です。インデックス最適化、パーティショニング、キャッシュ、リードレプリカの追加。これらをすべて試して、なお単一DBの書き込み限界に達しているなら、シャーディングに進みます。逆に、この判断を急ぎすぎると、複雑さに見合う効果が出ないままアプリケーション全体が重くなってしまいます。

**🇰🇷 답변**

먼저 적용하는 순서가 있습니다. 읽기가 많으면 레플리케이션을 먼저 시도하고, 그래도 부족하거나 쓰기 자체가 한계를 넘었을 때 비로소 샤딩을 검토합니다. 샤딩은 최후의 수단이라는 위치를 안 무너뜨립니다.

레플리케이션은 데이터 복제본을 여러 개 갖는 것뿐이라 도입이 쉽습니다. 앱 쪽 변경도 거의 읽기 대상 방향만 바꾸면 됩니다. 다만 레플리카 지연이라는 대가가 있어서, 쓰기 직후에 레플리카를 읽으면 오래된 데이터가 반환될 가능성이 있습니다. 결제 직후 잔고 확인처럼 정합성이 필요한 처리는 의도적으로 Primary를 읽으러 가는 구현이 필요합니다.

샤딩은 데이터 자체를 여러 DB에 수평 분할하니까 쓰기 용량 자체를 늘릴 수 있습니다. 그런데 대가가 아주 큽니다. "어느 샤드에 데이터가 있는가"를 판단하는 샤딩 키 설계가 제일 중요한데, 이걸 잘못하면 특정 샤드에 데이터랑 접근이 몰리는 핫스팟이 생깁니다. 게다가 다른 샤드를 넘나드는 JOIN이 안 되고, 트랜잭션도 단일 샤드 안에서만 완결됩니다. 사용자 ID로 샤딩한 경우, 여러 사용자에 걸친 집계 처리는 앱 쪽에서 각 샤드에 물어보고 결과를 병합해야 합니다.

실무에서의 판단 기준은 "샤딩을 피하기 위한 대체 수단을 다 써 봤는가"입니다. 인덱스 최적화, 파티셔닝, 캐시, 리드 레플리카 추가. 이것들을 전부 시도했는데도 단일 DB의 쓰기 한계에 도달했다면 샤딩으로 갑니다. 반대로 이 판단을 너무 서두르면, 복잡함에 걸맞은 효과가 안 나온 채 애플리케이션 전체가 무거워져 버립니다.

# Part 9. 트러블슈팅 및 성능 프로파일링

### Q66. OOM発生時の原因特定手順
(OOM 발생 시 원인 특정 절차)

**🇯🇵 回答**

まず前提として、障害が起きてから慌てて調べるんじゃなくて、事前にダンプが自動で残る設定にしておくこと。これが出発点です。`-XX:+HeapDumpOnOutOfMemoryError` と `-XX:HeapDumpPath` をJVM起動オプションに入れておけば、OOMの瞬間の状態がファイルとして残ります。これがないと再現待ちになって、調査が長期化します。

ダンプが取れたら、MATのようなツールで開いて、Dominator Tree、支配木から見ます。これは「どのオブジェクトが、どれだけの子オブジェクトのメモリ解放を妨げているか」を示すビューです。単純にサイズの大きいオブジェクトを探すより、根本原因の候補に速くたどり着けます。ここで巨大なコレクション、HashMapやListが残っていれば、それがリークの主犯である可能性が高いです。

原因として実際に多いパターンは三つあります。一つ目はstaticなコレクションへの追加のみで削除がない実装。二つ目はリスナーやコールバックの登録解除漏れで、オブジェクトが不要になっても参照が残り続けてGCの対象にならないケース。三つ目はキャッシュに上限や有効期限を設定し忘れていて、無限に肥大化するケースです。

区別すべきなのは、真のメモリリークなのか、それとも単に一時的な負荷でヒープサイズが足りないだけなのか、という点です。後者ならヒープサイズの調整や処理のバッチ化で解決しますが、前者は増やしても遅れて同じ症状が再発します。ダンプを取ったタイミングを変えて複数回比較して、特定のオブジェクトの数が時間とともに増え続けているかを確認すると、この二つを切り分けられます。

**🇰🇷 답변**

먼저 전제로, 장애가 나고 나서 허둥지둥 조사하는 게 아니라 미리 덤프가 자동으로 남는 설정을 해 두는 것. 이게 출발점입니다. `-XX:+HeapDumpOnOutOfMemoryError`랑 `-XX:HeapDumpPath`를 JVM 기동 옵션에 넣어 두면, OOM 순간의 상태가 파일로 남습니다. 이게 없으면 재현 대기가 돼서 조사가 길어집니다.

덤프를 뜨면 MAT 같은 도구로 열어서 Dominator Tree, 지배 트리부터 봅니다. 이건 "어느 객체가 얼마나 많은 자식 객체의 메모리 해제를 막고 있는지"를 보여주는 뷰입니다. 단순히 크기가 큰 객체를 찾는 것보다 근본 원인 후보에 빨리 도달할 수 있습니다. 여기서 거대한 컬렉션, HashMap이나 List가 남아 있으면 그게 누수의 주범일 가능성이 높습니다.

원인으로 실제로 많은 패턴은 세 가지입니다. 첫째는 static 컬렉션에 추가만 하고 삭제가 없는 구현. 둘째는 리스너나 콜백의 등록 해제 누락으로, 객체가 필요 없어져도 참조가 계속 남아서 GC 대상이 안 되는 케이스. 셋째는 캐시에 상한이나 유효기간 설정을 깜빡해서 무한히 비대해지는 케이스입니다.

구분해야 하는 건, 진짜 메모리 누수인지 아니면 단순히 일시적인 부하로 힙 사이즈가 부족한 것뿐인지, 이 점입니다. 후자면 힙 사이즈 조정이나 처리 배치화로 해결되지만, 전자는 늘려도 늦게 같은 증상이 재발합니다. 덤프를 뜨는 타이밍을 바꿔서 여러 번 비교하고, 특정 객체의 수가 시간이 지나면서 계속 늘고 있는지 확인하면 이 둘을 구분할 수 있습니다.

### Q67. CPU使用率100%張り付き時の調査
(CPU 사용률 100% 고착 시의 조사)

**🇯🇵 回答**

まずOSレベルで `top` を実行して、どのプロセスがCPUを食っているかを確認します。ここで重要なのは、プロセス単位じゃなくて `top -H` でスレッド単位まで見ることです。犯人は一つのアプリケーション内の特定のスレッドであることがほとんどなので、そのスレッドIDを控えます。

次にJavaなら、そのスレッドIDを16進数に変換して、`jstack` で取得したスレッドダンプの中から同じIDのスレッドを探します。ここでスタックトレースを見れば、そのスレッドが具体的にどのメソッドで動き続けているかが分かります。

原因として実際に多いのは三つです。一つ目は、正規表現の破滅的バックトラッキングです。ユーザー入力を含む文字列に対して曖昧なパターンを当てると、入力長に対して指数的に処理時間が増えて、CPUを使い切ったまま返ってこなくなります。二つ目はロジックの不備による無限ループやビジーウェイトで、これはスタックトレースを見れば同じ場所で回り続けていることがすぐ分かります。三つ目はGCです。Full GCが頻発している場合は、スレッドダンプじゃなくてGCログを見るべきですね。この場合、犯人のスレッドはアプリケーションコードじゃなくてGCスレッド自体になります。

区別する簡単な方法は、複数回、数秒間隔でスレッドダンプを取ることです。同じスタックトレースの位置に何度も現れるスレッドがあれば、それが無限ループかホットループの強い証拠になります。一方、毎回違う場所にいるなら、単に処理量が多いだけで異常ではない可能性があります。

付け加えると、実際に測ってみると、教科書に出てくる `^(a+)+$` のような例は最新のJVMでは瞬時に終わります。爆発するのは `(.*a){20}b` のように、繰り返すグループの中が `.*` で開いている形です。条件は「中身が単一文字クラスで決定的か」であって、「中に量指定子が入っているかどうか」ではないんですね。

**🇰🇷 답변**

먼저 OS 레벨에서 `top`을 실행해서 어느 프로세스가 CPU를 먹는지 확인합니다. 여기서 중요한 건 프로세스 단위가 아니라 `top -H`로 스레드 단위까지 보는 겁니다. 범인은 하나의 애플리케이션 안의 특정 스레드인 경우가 대부분이니까, 그 스레드 ID를 적어 둡니다.

다음으로 Java라면 그 스레드 ID를 16진수로 변환해서, `jstack`으로 뜬 스레드 덤프 안에서 같은 ID의 스레드를 찾습니다. 여기서 스택 트레이스를 보면 그 스레드가 구체적으로 어느 메서드에서 계속 돌고 있는지 알 수 있습니다.

원인으로 실제로 많은 건 세 가지입니다. 첫째, 정규 표현식의 파국적 백트래킹입니다. 사용자 입력이 들어간 문자열에 애매한 패턴을 대면, 입력 길이에 대해 지수적으로 처리 시간이 늘어서 CPU를 다 써 버린 채 안 돌아옵니다. 둘째, 로직 결함에 의한 무한 루프나 바쁜 대기인데, 이건 스택 트레이스를 보면 같은 곳에서 계속 도는 걸 바로 알 수 있습니다. 셋째는 GC입니다. Full GC가 빈발하는 경우는 스레드 덤프가 아니라 GC 로그를 봐야 합니다. 이 경우 범인 스레드는 애플리케이션 코드가 아니라 GC 스레드 자체가 됩니다.

구분하는 간단한 방법은 여러 번, 수 초 간격으로 스레드 덤프를 뜨는 겁니다. 같은 스택 트레이스 위치에 몇 번이고 나타나는 스레드가 있으면, 그게 무한 루프나 핫 루프의 강한 증거가 됩니다. 반대로 매번 다른 곳에 있으면 단순히 처리량이 많을 뿐 이상이 아닐 가능성이 있습니다.

덧붙이면, 실제로 재 보면 교과서에 나오는 `^(a+)+$` 같은 예시는 최신 JVM에서 순식간에 끝납니다. 폭발하는 건 `(.*a){20}b`처럼 반복되는 그룹 안이 `.*`로 열려 있는 형태입니다. 조건은 "안에 수량자가 있는가"가 아니라 "몸통이 단일 문자 클래스라 결정적인가"거든요.

### Q68. コネクションプール枯渇：接続リークとスロークエリの切り分け 【Q18・Q44の第三変奏】
(커넥션 풀 고갈: 접속 누수와 슬로 쿼리의 구분 — Q18·Q44의 세 번째 변주)

> ⚠️ Q18·Q44와 같은 주제의 3회째 출제입니다. 여기서는 질문이 지정하는 "어느 메트릭으로 구분하는가"에 핀포인트로 답합니다.

**🇯🇵 回答**

両者はプールが枯渇するという結果は同じですが、`hikaricp.connections.usage` の分布を見れば機械的に切り分けられます。これはコネクションが「借りられてから返却されるまでの時間」を計測するメトリクスです。

スロークエリが原因の場合、この使用時間はDBの応答時間に比例して伸びますが、必ず返却されて分布に現れます。ヒストグラムでp99が数秒に伸びていれば、DB側のスロークエリログと突き合わせて、同時刻に実行されていた重いクエリを特定します。負荷や特定のクエリパターンと相関して悪化するのも特徴ですね。

リークが原因の場合、そのコネクションはそもそも返却されないので、usageの計測自体に現れません。activeは増え続けるのに、usageのヒストグラムには対応する記録が見えない、という矛盾した状態になります。ここで `leakDetectionThreshold` を設定していれば、閾値を超えて返却されないコネクションについて、借りた時点のスタックトレースが警告ログに出るので、原因のメソッドを直接特定できます。

判別の実務手順としては、まず active と pending の推移を見て枯渇の傾向を掴みます。階段状なのか、負荷連動なのか。次に usage のヒストグラムで、p95・p99が異常に長い借用が存在するかを確認します。存在すればスロークエリ側、存在しないのにactiveだけ増え続けるならリーク側、という判定です。

両方が絡むケースもあります。スロークエリで一時的にプールが逼迫している間に、たまたま別の箇所でリークしているコネクションが可視化されずに隠れている、ということもあるので、両方のログを常に突き合わせる習慣にしています。

**🇰🇷 답변**

둘 다 풀이 고갈된다는 결과는 같은데요, `hikaricp.connections.usage`의 분포를 보면 기계적으로 구분할 수 있습니다. 이건 커넥션이 "빌려진 뒤 반환될 때까지의 시간"을 계측하는 메트릭입니다.

슬로 쿼리가 원인인 경우, 이 사용 시간은 DB 응답 시간에 비례해서 늘어나지만 반드시 반환되어 분포에 나타납니다. 히스토그램에서 p99가 수 초로 늘어나 있으면, DB 쪽 슬로 쿼리 로그랑 대조해서 같은 시각에 돌던 무거운 쿼리를 특정합니다. 부하나 특정 쿼리 패턴이랑 상관해서 나빠지는 것도 특징이고요.

누수가 원인인 경우, 그 커넥션은 애초에 반환이 안 되니까 usage 계측 자체에 안 나타납니다. active는 계속 늘어나는데 usage 히스토그램에는 대응하는 기록이 안 보이는, 모순된 상태가 됩니다. 여기서 `leakDetectionThreshold`를 설정해 뒀다면, 임계치를 넘겨 반환 안 된 커넥션에 대해 빌린 시점의 스택 트레이스가 경고 로그로 나오니까, 원인 메서드를 직접 특정할 수 있습니다.

판별의 실무 절차로는, 먼저 active랑 pending의 추이를 보고 고갈의 경향을 파악합니다. 계단식인지, 부하 연동인지. 다음으로 usage 히스토그램에서 p95·p99가 비정상적으로 긴 대여가 있는지 확인합니다. 있으면 슬로 쿼리 쪽, 없는데 active만 계속 늘면 누수 쪽, 이런 판정입니다.

둘 다 얽힌 케이스도 있습니다. 슬로 쿼리로 일시적으로 풀이 압박받는 동안, 우연히 다른 곳에서 누수 중인 커넥션이 가려져서 안 보이는 경우도 있어서, 양쪽 로그를 항상 같이 보는 습관을 들이고 있습니다.

### Q69. キャッシュのThundering Herd問題
(캐시의 Thundering Herd 문제)

**🇯🇵 回答**

人気のキーのTTLが切れた瞬間、そのキーへの大量の同時アクセスが全て同時にキャッシュミスになって、一斉にDBへ問い合わせる現象です。DBが本来さばける負荷を、一瞬だけ数百倍のリクエストが押し寄せるので、瞬間的にDBが落ちることがあります。

対策の第一は分散ロックです。最初にキャッシュミスを引いたリクエストだけがDBへの問い合わせ権を得て、他のリクエストはロック解放を短時間待つか、ロック中は古い値をそのまま返します。Redisなら `SET key value NX PX 5000` のようなアトミックな命令でロックを表現して、Redlockのような分散ロック実装を使います。ただしロック自体が新たなボトルネックにならないよう、ロック保持時間は極力短くします。

第二の対策が、論理TTLによる先行更新です。実際のキャッシュ有効期限は長めに設定しつつ、値に「論理的な期限」を別途持たせておきます。期限が近づいた最初のリクエストがバックグラウンドで非同期に値を再生成する間、他のリクエストには古い値を返し続けます。ユーザーからは遅延が見えませんし、DBへの問い合わせも1回に抑えられます。

より単純な対策としては、TTLにジッター、つまりランダムなばらつきを入れることです。多数のキーが同じタイミングで失効するのを避けるだけでも、被害はかなり分散されます。

どの対策を選ぶかは重要度で判断します。アクセス頻度が極端に高い少数のキー、いわゆるホットキーには分散ロックや論理TTLのような重い対策を。それ以外の大多数のキーにはジッターだけで十分。そういう形で濃淡をつけるのが現実的です。全キーに同じ重装備の対策を入れると、実装と運用のコストに見合いません。

**🇰🇷 답변**

인기 있는 키의 TTL이 만료되는 순간, 그 키에 대한 대량의 동시 접근이 전부 동시에 캐시 미스가 돼서 일제히 DB로 문의하는 현상입니다. DB가 원래 감당할 수 있는 부하를 순간적으로 수백 배의 요청이 덮치니까, 순식간에 DB가 죽는 경우가 있습니다.

대책의 첫째는 분산 락입니다. 처음 캐시 미스를 뽑은 요청만 DB 문의 권한을 얻고, 다른 요청들은 락 해제를 짧게 기다리거나 락이 걸린 동안은 오래된 값을 그대로 반환합니다. Redis라면 `SET key value NX PX 5000` 같은 원자적 명령으로 락을 표현하고, Redlock 같은 분산 락 구현을 씁니다. 다만 락 자체가 새로운 병목이 안 되도록 락 보유 시간은 최대한 짧게 합니다.

둘째 대책이 논리 TTL에 의한 선행 갱신입니다. 실제 캐시 유효기간은 길게 설정하면서, 값에 "논리적 기한"을 따로 갖게 해 둡니다. 기한이 다가온 첫 요청이 백그라운드에서 비동기로 값을 재생성하는 동안, 다른 요청들한테는 오래된 값을 계속 반환합니다. 사용자한테는 지연이 안 보이고, DB 문의도 1회로 억제됩니다.

더 단순한 대책으로는 TTL에 지터, 그러니까 랜덤한 편차를 넣는 겁니다. 많은 키가 같은 타이밍에 만료되는 걸 피하는 것만으로도 피해가 꽤 분산됩니다.

어느 대책을 고를지는 중요도로 판단합니다. 접근 빈도가 극단적으로 높은 소수의 키, 이른바 핫 키에는 분산 락이나 논리 TTL 같은 무거운 대책을. 그 외 대다수 키에는 지터만으로 충분하고요. 이런 식으로 강약을 조절하는 게 현실적입니다. 전체 키에 같은 중장비 대책을 넣으면 구현이랑 운영 비용에 안 맞습니다.

### Q70. Spring Bootのgraceful shutdown設定
(Spring Boot의 graceful shutdown 설정)

**🇯🇵 回答**

`server.shutdown=graceful` を設定して、あわせて `spring.lifecycle.timeout-per-shutdown-phase` で猶予時間を決めます。

これが必要な理由は、デプロイやスケールインの瞬間に処理中のリクエストが強制終了されると、ユーザーにエラーが返るだけじゃなくて、決済のような処理が中途半端な状態でDBに残るリスクがあるからです。

Kubernetesの場合、Podを終了する際にまずSIGTERMを送って、一定時間、デフォルトは30秒ですね、それを過ぎてもプロセスが生きていればSIGKILLで強制終了します。gracefulを有効にすると、SIGTERMを受け取った時点で新規リクエストの受付を止めて、既存の処理中リクエストが完了するまで待ってから終了するようになります。

ただし、この設定だけでは不十分です。Kubernetesのservice側がPodの終了を検知してルーティングから除外するまでには、若干のタイムラグがあるんですよ。その間に新しいリクエストが送られてくる可能性があります。これを防ぐには、preStopフックで数秒スリープを入れて、ルーティング除外がserviceに伝播する時間を稼いでから実際のシャットダウンシーケンスに入る、という組み合わせが必要です。preStopがないと、正常に終了処理をしているつもりでも一部のリクエストが取りこぼされます。

猶予時間の設定も重要な判断です。Kubernetesの `terminationGracePeriodSeconds` は、Spring Bootの猶予時間より長く設定しなければ意味がありません。Spring側を40秒待つ設定にしておきながら、Kubernetesをデフォルトの30秒のままにすると、40秒を待たずに30秒でSIGKILLが飛んでしまって、gracefulの意味がなくなります。この二つの時間設定は必ずセットで確認します。

**🇰🇷 답변**

`server.shutdown=graceful`을 설정하고, 같이 `spring.lifecycle.timeout-per-shutdown-phase`로 유예 시간을 정합니다.

이게 필요한 이유는, 배포나 스케일 인 순간에 처리 중인 요청이 강제 종료되면 사용자한테 에러가 반환될 뿐 아니라, 결제 같은 처리가 어중간한 상태로 DB에 남을 리스크가 있기 때문입니다.

Kubernetes의 경우 Pod를 종료할 때 먼저 SIGTERM을 보내고, 일정 시간, 기본값은 30초죠, 그게 지나도 프로세스가 살아 있으면 SIGKILL로 강제 종료합니다. graceful을 켜면 SIGTERM을 받은 시점에 신규 요청 접수를 멈추고, 기존에 처리 중인 요청이 완료될 때까지 기다렸다가 종료하게 됩니다.

다만 이 설정만으로는 부족합니다. Kubernetes의 service 쪽이 Pod의 종료를 감지해서 라우팅에서 빼기까지는 약간의 시차가 있거든요. 그 사이에 새 요청이 올 가능성이 있습니다. 이걸 막으려면 preStop 훅에서 몇 초 슬립을 넣어서, 라우팅 제외가 service에 전파되는 시간을 벌고 나서 실제 셧다운 시퀀스에 들어가는 조합이 필요합니다. preStop이 없으면 정상적으로 종료 처리를 한다고 생각해도 일부 요청이 누락됩니다.

유예 시간 설정도 중요한 판단입니다. Kubernetes의 `terminationGracePeriodSeconds`는 Spring Boot의 유예 시간보다 길게 설정하지 않으면 의미가 없습니다. Spring 쪽을 40초 대기로 잡아 놓고 Kubernetes는 기본값 30초 그대로 두면, 40초를 기다려 주기는커녕 30초에 SIGKILL이 날아와서 graceful의 의미가 사라집니다. 이 두 시간 설정은 반드시 세트로 확인합니다.

# Part 10. DevOps 및 Observability

### Q71. Observabilityの3本柱
(Observability의 3요소)

**🇯🇵 回答**

メトリクス、ログ、トレースの三つですね。ただ大事なのは、それぞれが答えられる問いが違うという点です。

メトリクスは「何が起きているか」を時系列の数値で示します。CPU使用率、リクエスト数、エラー率。集計済みなので低コストで長期間保持できて、異常の検知とアラートに向いています。ただし集計されている分、個々のリクエストで何が起きたかは分かりません。

ログは「何が起きたか」の詳細を、テキストの記録として残します。特定のリクエストで例外が出た理由や、変数の値まで追えます。情報量は多い代わりに、量が膨大でコストがかかりますし、検索性を担保するにはインデックス設計が必要です。

トレースは「どこで時間がかかったか」を、リクエストが複数サービスをまたぐ経路として示します。分散システムで、ボトルネックがどのサービスのどの処理にあるかを特定するのは、トレースにしかできません。

この三つを別々のツールでバラバラに見ていると、障害調査が遅くなります。メトリクスでエラー率の上昇を検知して、トレースでその時間帯の遅いリクエストを見つけて、そのTrace IDでログを引いて詳細な原因を見る。この一本の流れが繋がって、初めて価値が出ます。

だから私は導入時、三つを別々に整えるんじゃなくて、Trace IDをログの構造化フィールドに必ず含めるところから始めます。これがないと、三本柱があっても線として繋がりません。

**🇰🇷 답변**

메트릭, 로그, 트레이스 세 가지입니다. 다만 중요한 건 각각이 답할 수 있는 질문이 다르다는 점이에요.

메트릭은 "무슨 일이 일어나고 있는가"를 시계열 수치로 보여줍니다. CPU 사용률, 요청 수, 에러율. 집계된 거라서 저비용으로 오래 보관할 수 있고, 이상 탐지랑 알림에 적합합니다. 다만 집계된 만큼 개별 요청에서 무슨 일이 있었는지는 알 수 없습니다.

로그는 "무슨 일이 있었는가"의 상세를 텍스트 기록으로 남깁니다. 특정 요청에서 예외가 난 이유나 변수 값까지 추적할 수 있습니다. 정보량이 많은 대신 양이 방대해서 비용이 들고, 검색성을 담보하려면 인덱스 설계가 필요합니다.

트레이스는 "어디서 시간이 걸렸는가"를, 요청이 여러 서비스를 걸치는 경로로 보여줍니다. 분산 시스템에서 병목이 어느 서비스의 어느 처리에 있는지를 특정하는 건 트레이스만이 할 수 있습니다.

이 세 가지를 각각 별도 도구로 따로따로 보면 장애 조사가 늦어집니다. 메트릭으로 에러율 상승을 감지하고, 트레이스로 그 시간대의 느린 요청을 찾고, 그 Trace ID로 로그를 뽑아서 상세 원인을 본다. 이 하나의 흐름이 이어져야 비로소 가치가 생깁니다.

그래서 저는 도입할 때 세 가지를 따로 갖추는 게 아니라, Trace ID를 로그의 구조화 필드에 반드시 포함시키는 것부터 시작합니다. 이게 없으면 3요소가 있어도 선으로 안 이어집니다.

### Q72. CI/CDで本番デプロイリスクを最小化する工夫
(CI/CD로 프로덕션 배포 리스크를 최소화하는 방법)

**🇯🇵 回答**

多層で防御する考え方です。

デプロイ前の層では、単体テストと結合テストをパイプラインに必須化して、テストが通らなければマージもデプロイもできない仕組みにします。加えて静的解析とセキュリティスキャンも自動化して、人のレビューを設計判断に集中させます。

デプロイの層では、カナリアリリースで新バージョンに1〜5%だけトラフィックを流して、エラー率やレイテンシのメトリクスを監視します。ここで重要なのは、判定を人間の目視じゃなくて自動化することです。500エラー率が閾値を超えたら自動でロールバックする仕組みがないと、深夜のデプロイで異常に気づくのが遅れますから。

そしてもう一段、見落とされがちなのが、デプロイとリリースを分離するという考え方です。フィーチャーフラグを使えば、コードは全ユーザーに配布した状態のまま、機能の有効化だけを対象ユーザーの一部に絞れます。これによって、コードのデプロイに起因する問題、起動失敗などですね、それと機能自体の問題を切り分けて検証できます。問題が起きても、再デプロイせずフラグを切るだけで即座に元に戻せるのも利点です。

最後に、DBマイグレーションだけは通常のカナリアと別扱いにしています。ロールバックが効かないので、拡張・縮小方式で段階的に進めて、アプリのロールバックが必要になっても、常に前のバージョンと現在のスキーマの両方に対応できる状態を維持します。

**🇰🇷 답변**

다층으로 방어하는 사고방식입니다.

배포 전 계층에서는 단위 테스트랑 통합 테스트를 파이프라인에 필수화해서, 테스트가 통과 안 하면 머지도 배포도 못 하는 구조로 합니다. 여기에 정적 분석이랑 보안 스캔도 자동화해서, 사람의 리뷰를 설계 판단에 집중시킵니다.

배포 계층에서는 카나리 릴리스로 새 버전에 1~5%만 트래픽을 흘려서, 에러율이랑 레이턴시 메트릭을 모니터링합니다. 여기서 중요한 건 판정을 사람의 육안이 아니라 자동화하는 겁니다. 500 에러율이 임계치를 넘으면 자동으로 롤백하는 장치가 없으면, 심야 배포에서 이상을 알아채는 게 늦어지니까요.

그리고 한 단계 더, 놓치기 쉬운 게 배포랑 릴리스를 분리한다는 사고방식입니다. 피처 플래그를 쓰면 코드는 전체 사용자한테 배포한 상태 그대로, 기능 활성화만 대상 사용자 일부로 좁힐 수 있습니다. 이러면 코드 배포에 기인한 문제, 기동 실패 같은 거요, 그것과 기능 자체의 문제를 나눠서 검증할 수 있습니다. 문제가 생겨도 재배포 없이 플래그만 끄면 즉시 원래대로 돌릴 수 있는 것도 이점이고요.

마지막으로 DB 마이그레이션만은 일반 카나리랑 따로 다룹니다. 롤백이 안 먹히니까, 확장·축소 방식으로 단계적으로 진행하고, 앱 롤백이 필요해져도 항상 이전 버전이랑 현재 스키마 양쪽에 대응할 수 있는 상태를 유지합니다.

### Q73. DBマイグレーションの無停止手順
(DB 마이그레이션 무중단 절차)

**🇯🇵 回答**

原則はExpand/Contractです。新旧どちらのコードでも動作するスキーマの状態を一度経由してから、古いものを消す。この順番を守ります。

具体的な五段階を、ロールバック可能性の視点で説明します。

第一段階で新しいカラムを追加します。この時点では、既存の読み書きには一切影響しません。

第二段階でアプリケーションが新旧両方に書き込む、デュアルライトに切り替えます。ここが最も事故の起きやすい段階です。新カラムへの書き込みに失敗して例外を投げると、既存の処理まで壊れてしまうので、新カラムへの書き込みは失敗しても本処理に影響しないよう、防御的に実装します。

第三段階で既存データを新カラムへバックフィルします。大量データの場合は本番の負荷が高い時間を避けて、小さいバッチに分けて流します。

第四段階で、アプリケーションを新カラムだけ読む設定に切り替えます。この切り替え作業こそが、実質的な「デプロイ」に相当する最も緊張する瞬間です。ここで問題が起きても、コードはまだ旧カラムを読めるので、設定を戻すだけで即座に切り戻せます。

十分な期間、問題がないことを確認してから、最後の第五段階で旧カラムを削除します。

この手順の本質は、各段階が独立してロールバック可能であることです。一足飛びに新スキーマへ移行しようとすると、途中で問題が起きたときに戻す手段がなくなります。段階を割ることで、常に「今の一歩前」に戻れる状態を保ちます。そして旧カラムの削除だけは最も慎重に行って、本当に誰も参照していないことをログとメトリクスで確認してから実行します。

**🇰🇷 답변**

원칙은 Expand/Contract입니다. 신·구 어느 코드로도 동작하는 스키마 상태를 한 번 거친 다음에 옛것을 지운다. 이 순서를 지킵니다.

구체적인 5단계를 롤백 가능성의 관점에서 설명하겠습니다.

1단계에서 새 컬럼을 추가합니다. 이 시점에서는 기존 읽기쓰기에 전혀 영향이 없습니다.

2단계에서 애플리케이션이 신·구 양쪽에 쓰는 듀얼 라이트로 전환합니다. 여기가 제일 사고 나기 쉬운 단계입니다. 새 컬럼 쓰기에 실패해서 예외를 던지면 기존 처리까지 망가져 버리니까, 새 컬럼 쓰기는 실패해도 본 처리에 영향 없도록 방어적으로 구현합니다.

3단계에서 기존 데이터를 새 컬럼으로 백필합니다. 대량 데이터면 프로덕션 부하가 높은 시간을 피해서 작은 배치로 나눠서 흘립니다.

4단계에서 애플리케이션을 새 컬럼만 읽는 설정으로 전환합니다. 이 전환 작업이야말로 실질적인 "배포"에 해당하는, 제일 긴장되는 순간입니다. 여기서 문제가 생겨도 코드는 아직 옛 컬럼을 읽을 수 있으니까, 설정만 되돌리면 즉시 되돌릴 수 있습니다.

충분한 기간 문제가 없다는 걸 확인한 다음, 마지막 5단계에서 옛 컬럼을 삭제합니다.

이 절차의 본질은 각 단계가 독립적으로 롤백 가능하다는 겁니다. 한 번에 새 스키마로 넘어가려고 하면, 도중에 문제가 생겼을 때 되돌릴 수단이 없어집니다. 단계를 나눠서 항상 "지금의 한 걸음 전"으로 돌아갈 수 있는 상태를 유지합니다. 그리고 옛 컬럼 삭제만은 가장 신중하게 해서, 정말로 아무도 참조하지 않는다는 걸 로그랑 메트릭으로 확인한 다음에 실행합니다.

### Q74. Liveness / Readiness Probeの違い
(Liveness / Readiness Probe의 차이)

**🇯🇵 回答**

Livenessは「プロセスが生きているか」を確認します。失敗するとKubernetesはコンテナを再起動させます。デッドロックに陥って応答しなくなったプロセスを外から検知して回復させる、最後の砦ですね。

Readinessは「トラフィックを受ける準備ができているか」を確認します。失敗してもコンテナは再起動されず、サービスのルーティング対象から一時的に外れるだけです。起動直後でDBコネクションプールの初期化中とか、依存する外部サービスへの疎通確認が済んでいない間はここを失敗させて、準備ができた瞬間にトラフィックを受け始めます。

この二つを混同すると、実運用でよくある事故が起きます。典型的なのが、Readinessで見るべき「DB接続が一時的に不安定」という条件を、Livenessに入れてしまうケースです。DBが数秒詰まっただけで、正常なアプリケーションプロセスまで次々に再起動されてしまって、再起動の負荷がさらにDBを圧迫する。こういうスパイラルに陥ります。Livenessはプロセス自体の生存、つまり「自分だけで判断できる」項目に限定して、外部依存の状態はReadiness側に置くのが安全な設計です。

もう一点重要なのがStartup Probeです。起動に時間がかかるアプリケーションでは、起動完了前にLivenessが早すぎるタイミングで失敗と判定して、起動中のコンテナを再起動し続けるループに陥ることがあります。Startup Probeで起動完了を別に確認させて、それが通るまではLiveness・Readinessの判定を待たせることで、この問題を避けます。

**🇰🇷 답변**

Liveness는 "프로세스가 살아 있는가"를 확인합니다. 실패하면 Kubernetes가 컨테이너를 재시작시킵니다. 데드락에 빠져서 응답을 안 하게 된 프로세스를 밖에서 감지해 회복시키는, 최후의 보루입니다.

Readiness는 "트래픽을 받을 준비가 됐는가"를 확인합니다. 실패해도 컨테이너는 재시작되지 않고, 서비스 라우팅 대상에서 일시적으로 빠질 뿐입니다. 기동 직후에 DB 커넥션 풀 초기화 중이라든가, 의존하는 외부 서비스와의 소통 확인이 안 끝난 동안은 여기를 실패시키고, 준비가 되는 순간부터 트래픽을 받기 시작합니다.

이 둘을 혼동하면 실운영에서 흔한 사고가 납니다. 전형적인 게, Readiness로 봐야 할 "DB 접속이 일시적으로 불안정"이라는 조건을 Liveness에 넣어 버리는 케이스입니다. DB가 몇 초 막혔을 뿐인데 정상적인 애플리케이션 프로세스까지 줄줄이 재시작돼 버리고, 재시작 부하가 DB를 더 압박한다. 이런 악순환에 빠집니다. Liveness는 프로세스 자체의 생존, 그러니까 "스스로 판단할 수 있는" 항목으로 한정하고, 외부 의존 상태는 Readiness 쪽에 두는 게 안전한 설계입니다.

한 가지 더 중요한 게 Startup Probe입니다. 기동에 시간이 걸리는 애플리케이션에서는, 기동 완료 전에 Liveness가 너무 이른 타이밍에 실패로 판정해서 기동 중인 컨테이너를 계속 재시작시키는 루프에 빠지는 경우가 있습니다. Startup Probe로 기동 완료를 따로 확인시키고, 그게 통과할 때까지는 Liveness·Readiness 판정을 미루게 해서 이 문제를 피합니다.

### Q75. IaC導入のメリットと注意点
(IaC 도입의 장점과 주의점)

**🇯🇵 回答**

メリットは、インフラの構成をコードとして再現可能にできることです。手順書に書かれた手動作業って、実行する人によって微妙な差が出たり、実行し忘れる項目が出たりするんですよね。コード化すればレビューを通せますし、Gitの履歴として「いつ誰が何を変えたか」が残ります。同じ構成のステージング環境を一瞬で複製できるのも大きな利点です。

注意点は運用面に集中します。

最も重要なのがStateファイルの扱いです。TerraformのStateには、実在するリソースの詳細な情報、時にはパスワードのような機密情報まで平文で含まれることがあります。これをGitにコミットしてしまう事故は実際によく起きるので、S3のようなリモートバックエンドに置いて、暗号化を有効にして、アクセス権限を絞ります。

次に、複数人が同時にapplyするとState不整合や意図しない上書きが起きるので、DynamoDBのようなロック機構を必ず設定します。ロックがないと、二人が同時にリソースを変更し始めて、片方の変更が消える事故が起きます。

そしてコードレビューだけでは不十分な点として、適用前に必ず plan の差分を確認する運用を徹底します。意図しないリソースの削除が計画に含まれていないか、レビュアーが目視で確認してからapplyする。このステップを飛ばさないことが重要です。特に本番環境では、破壊的変更を含むplanを実行する前に、承認フローを挟むパイプライン設計にしています。

**🇰🇷 답변**

장점은 인프라 구성을 코드로 재현 가능하게 만들 수 있다는 겁니다. 절차서에 적힌 수동 작업은 실행하는 사람에 따라 미묘한 차이가 나거나, 실행을 깜빡하는 항목이 나오거든요. 코드화하면 리뷰를 거칠 수 있고, Git 이력으로 "언제 누가 뭘 바꿨는지"가 남습니다. 같은 구성의 스테이징 환경을 순식간에 복제할 수 있는 것도 큰 이점이고요.

주의점은 운영 면에 집중됩니다.

가장 중요한 게 State 파일의 취급입니다. Terraform의 State에는 실재하는 리소스의 상세 정보, 때로는 비밀번호 같은 기밀 정보까지 평문으로 들어가는 경우가 있습니다. 이걸 Git에 커밋해 버리는 사고는 실제로 자주 일어나니까, S3 같은 원격 백엔드에 두고 암호화를 켜고 접근 권한을 좁힙니다.

다음으로, 여러 명이 동시에 apply하면 State 불일치나 의도치 않은 덮어쓰기가 생기니까, DynamoDB 같은 락 메커니즘을 반드시 설정합니다. 락이 없으면 두 명이 동시에 리소스를 변경하기 시작해서 한쪽의 변경이 사라지는 사고가 납니다.

그리고 코드 리뷰만으로는 부족한 점으로, 적용 전에 반드시 plan의 차분을 확인하는 운영을 철저히 합니다. 의도치 않은 리소스 삭제가 계획에 들어 있지 않은지, 리뷰어가 육안으로 확인한 다음에 apply한다. 이 스텝을 안 건너뛰는 게 중요합니다. 특히 프로덕션 환경에서는 파괴적 변경이 포함된 plan을 실행하기 전에 승인 플로를 끼우는 파이프라인 설계로 합니다.
