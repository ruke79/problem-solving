# Part 8. 시스템 설계 (System Design)

### Q61. 大規模チケット予約システムのDBダウン防止
(대규모 티켓 예약 시스템의 DB 다운 방지)

**🇯🇵 回答**

最初に決めるべきは、「どこまでを同期で処理して、どこからを非同期に逃がすか」という境界線です。

まず入り口に待機列を置きます。開始時刻に殺到するアクセスをRedisのSorted Setで受け止めて、順番にトークンを発行します。ポイントは、待機列自体が新たなボトルネックにならないことです。Redisへの書き込みだけで完結させて、この時点ではDBに触れさせません。

座席選択はもう一段守りが必要です。同一座席への同時アクセスは、DBの行ロックだけに頼らずRedisで先に排他制御します。座席IDをキーにSETNXで数秒だけ仮押さえして、決済が成立したらDBに確定を書く。Redisの操作はミリ秒で終わるので、ユーザー体験の面でも有利です。

そして忘れてはいけないのが在庫の整合性です。売り切れ超過が最も避けたい事故なので、座席数の減算はDBのトランザクションで行って、照合バッチも用意します。

**🇰🇷 답변**

제일 먼저 정해야 할 건 "어디까지를 동기로 처리하고 어디부터를 비동기로 뺄 것인가"라는 경계선입니다.

먼저 입구에 대기열을 둡니다. 시작 시각에 몰리는 접속을 Redis의 Sorted Set으로 받아서 순서대로 토큰을 발행합니다. 포인트는 대기열 자체가 새로운 병목이 되지 않는 겁니다. Redis 쓰기만으로 완결시키고, 이 시점에서는 DB를 안 건드리게 합니다.

좌석 선택은 한 단계 더 방어가 필요합니다. 같은 좌석에 대한 동시 접근은 DB 행 락에만 의존하지 않고 Redis로 먼저 배타 제어합니다. 좌석 ID를 키로 SETNX로 몇 초만 가예약하고, 결제가 성립하면 DB에 확정을 씁니다. Redis 조작은 밀리초로 끝나니까 사용자 경험 면에서도 유리합니다.

그리고 잊으면 안 되는 게 재고의 정합성입니다. 초과 판매가 제일 피하고 싶은 사고니까, 좌석 수 감산은 DB 트랜잭션으로 하고 대조 배치도 준비합니다.

### Q62. 分散環境でのAPI Rate Limit実装
(분산 환경에서의 API Rate Limit 구현)

**🇯🇵 回答**

複数のゲートウェイインスタンスが状態を共有する必要があるので、Redisを中央のカウンターとして使います。

アルゴリズムはトークンバケットを基本にします。固定ウィンドウ方式は、境界をまたいだ瞬間に制限の2倍が通ってしまうという弱点があるので避けます。前のウィンドウの残余と新しいウィンドウの許容量が重なるからですね。

実装で最も注意すべきは、「残トークンの確認」と「消費」の間で競合状態が起きることです。同時に問い合わせると両方が「まだ枠がある」と判定して、制限を超えて通してしまいます。これを防ぐには確認と消費を単一の操作にする必要があって、Luaスクリプトでアトミックに実行します。

もう一つ実務的な論点は、Redis自体の可用性です。Rate LimitのためにRedisを噛ませたことで、落ちると全APIが機能しなくなる。これは本末転倒ですよね。フェイルオープンかフェイルクローズかを、業務の性質で事前に決めておきます。

**🇰🇷 답변**

여러 게이트웨이 인스턴스가 상태를 공유해야 하니까, Redis를 중앙 카운터로 씁니다.

알고리즘은 토큰 버킷을 기본으로 합니다. 고정 윈도 방식은 경계를 넘는 순간 제한의 2배가 통과해 버리는 약점이 있어서 피합니다. 이전 창의 잔여분과 새 창의 허용치가 겹치기 때문이죠.

구현에서 제일 주의해야 할 건, "잔여 토큰 확인"과 "소비" 사이에 경쟁 상태가 생긴다는 겁니다. 동시에 물어보면 둘 다 "아직 여유가 있다"고 판정해서 제한을 넘겨 통과시킵니다. 이걸 막으려면 확인과 소비를 단일 조작으로 만들어야 하고, Lua 스크립트로 원자적으로 실행합니다.

또 하나 실무적인 논점은 Redis 자체의 가용성입니다. Rate Limit 하려고 Redis를 끼웠는데 죽으면 전체 API가 기능을 못 한다. 이건 본말전도잖아요. 페일 오픈으로 갈지 페일 클로즈로 갈지를 업무 성격으로 미리 정해 둡니다.

### Q63. SPOF（単一障害点）の特定と排除
(SPOF 특정과 배제)

**🇯🇵 回答**

SPOFを見つけるアプローチは、リクエストが入り口から応答を返すまでの経路をたどって、「この箱が一つ落ちたら何が止まるか」を各層で問うことです。

ロードバランサーが単一ノードなら冗長化します。アプリケーション層はステートレスにして複数AZに分散配置し、セッションはRedisなど外部ストアに出します。

DB層が最も難しいです。Primary-Replica構成にしてもPrimaryは単一障害点として残ります。対処はフェイルオーバーの自動化と、その所要時間をSLAとして許容できるかの判断ですね。

実は見落とされやすいSPOFが二つあります。一つはDNSで、TTLを長くしているとフェイルオーバー後も古いIPを引き続ける端末が出ます。もう一つは外部依存です。決済代行や認証プロバイダが落ちると、どれだけ自社を冗長化しても止まります。ここにはサーキットブレーカーとフォールバックを用意して、影響範囲を局所化します。

**🇰🇷 답변**

SPOF를 찾는 접근은, 요청이 입구부터 응답을 반환할 때까지의 경로를 따라가면서 "이 상자가 하나 죽으면 뭐가 멈추는가"를 각 층에서 묻는 겁니다.

로드밸런서가 단일 노드면 이중화합니다. 애플리케이션 계층은 스테이트리스로 만들어 여러 AZ에 분산 배치하고, 세션은 Redis 같은 외부 스토어로 뺍니다.

DB 계층이 제일 어렵습니다. Primary-Replica 구성으로 해도 Primary는 단일 장애점으로 남습니다. 대처는 페일오버 자동화와, 그 소요 시간을 SLA로 허용할 수 있는지의 판단입니다.

사실 놓치기 쉬운 SPOF가 두 가지 있습니다. 하나는 DNS로, TTL을 길게 두면 페일오버 후에도 옛 IP를 계속 참조하는 단말이 나옵니다. 다른 하나는 외부 의존입니다. 결제 대행이나 인증 프로바이더가 죽으면 자사를 아무리 이중화해도 멈춥니다. 여기에는 서킷 브레이커와 폴백을 준비해서 영향 범위를 국소화합니다.

### Q64. URL短縮サービスの設計
(URL 단축 서비스 설계)

**🇯🇵 回答**

最初に確認したいのは、「短縮URLは推測されて困るか」という点です。連番だと推測されるリスクがありますから。今回は一般的なユースケースとして進めます。

ID採番は、DBのAuto Incrementで一意な数値IDを発行して、Base62にエンコードします。7桁で約3.5兆通りをカバーできます。ハッシュ化して衝突を確認するより、採番の一意性をDBに保証させるほうが実装がシンプルで確実です。

読み取りが圧倒的に多いサービスなので、ここに設計の重心を置きます。短縮コードをキーにしたRedisキャッシュを必須にして、リダイレクトのほとんどをDBに触れずに返します。クリック数のような頻繁に更新される値は、書き込み競合を避けるため非同期集計にします。

リダイレクトのHTTPステータスも設計判断です。301だとブラウザがキャッシュして以後サーバーに来ないので、クリック数が計測できません。分析が必要なら302を使う、というのは意外と見落とされがちです。

**🇰🇷 답변**

먼저 확인하고 싶은 건 "단축 URL이 추측되면 곤란한가"라는 점입니다. 연번이면 추측될 리스크가 있으니까요. 이번에는 일반적인 유스케이스로 진행하겠습니다.

ID 채번은 DB의 Auto Increment로 유일한 숫자 ID를 발급해서 Base62로 인코딩합니다. 7자리로 약 3.5조 가지를 커버할 수 있습니다. 해시화해서 충돌을 확인하는 것보다, 채번의 유일성을 DB에 보증시키는 쪽이 구현이 단순하고 확실합니다.

읽기가 압도적으로 많은 서비스라서 여기에 설계의 무게중심을 둡니다. 단축 코드를 키로 한 Redis 캐시를 필수로 하고, 리다이렉트 대부분을 DB를 안 건드리고 반환합니다. 클릭 수처럼 자주 갱신되는 값은 쓰기 경합을 피하려고 비동기 집계합니다.

리다이렉트의 HTTP 상태 코드도 설계 판단입니다. 301이면 브라우저가 캐시해서 이후로 서버에 안 오니까 클릭 수를 계측할 수 없습니다. 분석이 필요하면 302를 쓴다, 이건 의외로 놓치기 쉽습니다.

### Q65. レプリケーションとシャーディングの使い分け
(레플리케이션과 샤딩의 구분)

**🇯🇵 回答**

まず適用する順番があります。読み取りが多いなら先にレプリケーションを試して、それでも足りない、あるいは書き込みが限界を超えているときに初めてシャーディングを検討します。シャーディングは最後の手段という位置づけを崩しません。

レプリケーションは導入が容易で、アプリ側も読み取り先を変えるだけです。ただしレプリカ遅延という代償があって、書き込み直後に読むと古いデータが返ります。決済直後の残高確認のような処理は、意図的にPrimaryを読む実装が必要です。

シャーディングは書き込み容量そのものを増やせますが、代償が大きいです。シャーディングキーの設計を誤ると特定シャードにアクセスが偏るホットスポットが発生します。さらにシャードをまたぐJOINができなくなり、トランザクションも単一シャード内でしか完結しません。

判断基準は「シャーディングを避けるための代替手段を使い切ったか」です。急ぎすぎると、複雑さに見合う効果が出ないまま全体が重くなります。

**🇰🇷 답변**

먼저 적용하는 순서가 있습니다. 읽기가 많으면 레플리케이션을 먼저 시도하고, 그래도 부족하거나 쓰기가 한계를 넘었을 때 비로소 샤딩을 검토합니다. 샤딩은 최후의 수단이라는 위치를 안 무너뜨립니다.

레플리케이션은 도입이 쉽고 앱 쪽도 읽기 대상만 바꾸면 됩니다. 다만 레플리카 지연이라는 대가가 있어서, 쓰기 직후에 읽으면 오래된 데이터가 반환됩니다. 결제 직후 잔고 확인 같은 처리는 의도적으로 Primary를 읽는 구현이 필요합니다.

샤딩은 쓰기 용량 자체를 늘릴 수 있지만 대가가 큽니다. 샤딩 키 설계를 잘못하면 특정 샤드에 접근이 몰리는 핫스팟이 생깁니다. 게다가 샤드를 넘나드는 JOIN이 안 되고, 트랜잭션도 단일 샤드 안에서만 완결됩니다.

판단 기준은 "샤딩을 피하기 위한 대체 수단을 다 써 봤는가"입니다. 너무 서두르면 복잡함에 걸맞은 효과가 안 나온 채 전체가 무거워집니다.

### Q66. OOM発生時の原因特定手順
(OOM 발생 시 원인 특정 절차)

**🇯🇵 回答**

まず前提として、障害が起きてから慌てて調べるのではなく、事前にダンプが自動で残る設定にしておくこと。`-XX:+HeapDumpOnOutOfMemoryError` を入れておけば、OOMの瞬間の状態がファイルとして残ります。これがないと再現待ちになって調査が長期化します。

ダンプが取れたら、MATで開いてDominator Treeから見ます。「どのオブジェクトが、どれだけの子オブジェクトの解放を妨げているか」を示すビューなので、単純にサイズの大きいものを探すより根本原因に速くたどり着けます。

原因として多いのは三つです。staticなコレクションへの追加のみで削除がない実装。リスナーの登録解除漏れ。そしてキャッシュに上限や有効期限を設定し忘れているケースです。

区別すべきは、真のリークなのか一時的な負荷でヒープが足りないだけなのかです。ダンプを複数回取って、特定のオブジェクトの数が時間とともに増え続けているかを確認すると切り分けられます。

**🇰🇷 답변**

먼저 전제로, 장애가 나고 나서 허둥지둥 조사하는 게 아니라 미리 덤프가 자동으로 남는 설정을 해 두는 것. `-XX:+HeapDumpOnOutOfMemoryError`를 넣어 두면 OOM 순간의 상태가 파일로 남습니다. 이게 없으면 재현 대기가 돼서 조사가 길어집니다.

덤프를 뜨면 MAT로 열어서 Dominator Tree부터 봅니다. "어느 객체가 얼마나 많은 자식 객체의 해제를 막고 있는지"를 보여주는 뷰라서, 단순히 크기가 큰 걸 찾는 것보다 근본 원인에 빨리 도달합니다.

원인으로 많은 건 세 가지입니다. static 컬렉션에 추가만 하고 삭제가 없는 구현. 리스너의 등록 해제 누락. 그리고 캐시에 상한이나 유효기간 설정을 깜빡한 케이스입니다.

구분해야 하는 건 진짜 누수인지, 일시적인 부하로 힙이 부족한 것뿐인지입니다. 덤프를 여러 번 떠서 특정 객체의 수가 시간이 지나면서 계속 늘고 있는지 확인하면 구분됩니다.

### Q67. CPU使用率100%張り付き時の調査
(CPU 사용률 100% 고착 시의 조사)

**🇯🇵 回答**

まずOSレベルで `top` を実行します。重要なのは、プロセス単位ではなく `top -H` でスレッド単位まで見ることです。犯人は特定のスレッドであることがほとんどなので、そのスレッドIDを控えます。

次にJavaなら、そのIDを16進数に変換して、`jstack` のスレッドダンプから同じスレッドを探します。スタックトレースを見れば、どのメソッドで動き続けているかが分かります。

原因として多いのは三つです。正規表現の破滅的バックトラッキング。ロジックの不備による無限ループ。そしてGCです。Full GCが頻発している場合は、スレッドダンプではなくGCログを見るべきですね。

区別する簡単な方法は、数秒間隔で複数回スレッドダンプを取ることです。同じ位置に何度も現れるスレッドがあれば、無限ループの強い証拠になります。

付け加えると、実際に測ると `^(a+)+$` のような教科書の例は最新のJVMでは瞬時に終わります。爆発するのは `(.*a){20}b` のように繰り返すグループの中が `.*` で開いている形です。

**🇰🇷 답변**

먼저 OS 레벨에서 `top`을 실행합니다. 중요한 건 프로세스 단위가 아니라 `top -H`로 스레드 단위까지 보는 겁니다. 범인은 특정 스레드인 경우가 대부분이니까 그 스레드 ID를 적어 둡니다.

다음으로 Java라면 그 ID를 16진수로 변환해서 `jstack` 스레드 덤프에서 같은 스레드를 찾습니다. 스택 트레이스를 보면 어느 메서드에서 계속 돌고 있는지 알 수 있습니다.

원인으로 많은 건 세 가지입니다. 정규 표현식의 파국적 백트래킹. 로직 결함에 의한 무한 루프. 그리고 GC입니다. Full GC가 빈발하는 경우는 스레드 덤프가 아니라 GC 로그를 봐야 합니다.

구분하는 간단한 방법은 수 초 간격으로 여러 번 스레드 덤프를 뜨는 겁니다. 같은 위치에 몇 번이고 나타나는 스레드가 있으면 무한 루프의 강한 증거가 됩니다.

덧붙이면, 실제로 재 보면 `^(a+)+$` 같은 교과서 예시는 최신 JVM에서 순식간에 끝납니다. 폭발하는 건 `(.*a){20}b`처럼 반복되는 그룹 안이 `.*`로 열려 있는 형태입니다.

### Q68. コネクションプール枯渇：接続リークとスロークエリの切り分け 【Q18・Q44の第三変奏】
(커넥션 풀 고갈: 접속 누수와 슬로 쿼리의 구분 — Q18·Q44의 세 번째 변주)

> ⚠️ Q18·Q44와 같은 주제의 3회째 출제입니다. 여기서는 질문이 지정하는 "어느 메트릭으로 구분하는가"에 핀포인트로 답합니다.

**🇯🇵 回答**

両者はプールが枯渇するという結果は同じですが、`hikaricp.connections.usage` の分布を見れば機械的に切り分けられます。これはコネクションが「借りられてから返却されるまでの時間」を計測するメトリクスです。

スロークエリが原因の場合、この使用時間はDBの応答時間に比例して伸びますが、必ず返却されて分布に現れます。ヒストグラムでp99が数秒に伸びていれば、DB側のスロークエリログと突き合わせます。

リークが原因の場合、そのコネクションはそもそも返却されないので、usageの計測自体に現れません。activeは増え続けるのに、usageには対応する記録が見えないという矛盾した状態になります。ここで `leakDetectionThreshold` を設定していれば、借りた時点のスタックトレースが出るので原因を直接特定できます。

判別の手順は、まずactiveとpendingの推移で傾向を掴み、次にusageのヒストグラムに異常に長い借用が存在するかを確認する、という順です。

**🇰🇷 답변**

둘 다 풀이 고갈된다는 결과는 같은데요, `hikaricp.connections.usage`의 분포를 보면 기계적으로 구분할 수 있습니다. 이건 커넥션이 "빌려진 뒤 반환될 때까지의 시간"을 계측하는 메트릭입니다.

슬로 쿼리가 원인인 경우, 이 사용 시간은 DB 응답 시간에 비례해서 늘어나지만 반드시 반환되어 분포에 나타납니다. 히스토그램에서 p99가 수 초로 늘어나 있으면 DB 쪽 슬로 쿼리 로그와 대조합니다.

누수가 원인인 경우, 그 커넥션은 애초에 반환이 안 되니까 usage 계측 자체에 안 나타납니다. active는 계속 늘어나는데 usage에는 대응하는 기록이 안 보이는 모순된 상태가 됩니다. 여기서 `leakDetectionThreshold`를 설정해 뒀다면 빌린 시점의 스택 트레이스가 나오니까 원인을 직접 특정할 수 있습니다.

판별 절차는, 먼저 active와 pending의 추이로 경향을 파악하고, 다음으로 usage 히스토그램에 비정상적으로 긴 대여가 있는지 확인하는 순서입니다.

### Q69. キャッシュのThundering Herd問題
(캐시의 Thundering Herd 문제)

**🇯🇵 回答**

人気のキーのTTLが切れた瞬間、そのキーへの大量の同時アクセスが全てキャッシュミスになって、一斉にDBへ問い合わせる現象です。一瞬だけ数百倍のリクエストが押し寄せるので、瞬間的にDBが落ちることがあります。

第一の対策は分散ロックです。最初にキャッシュミスを引いたリクエストだけがDBへの問い合わせ権を得て、他は古い値を返します。ただしロック自体がボトルネックにならないよう、保持時間は極力短くします。

第二が論理TTLによる先行更新です。実際の有効期限は長めにして、値に論理的な期限を別途持たせます。期限が近づいた最初のリクエストが非同期に再生成する間、他には古い値を返し続けます。

より単純な対策は、TTLにジッターを入れることです。どれを選ぶかは重要度で判断します。ホットキーには重い対策を、それ以外はジッターだけで十分。全キーに同じ重装備を入れると、コストに見合いません。

**🇰🇷 답변**

인기 있는 키의 TTL이 만료되는 순간, 그 키에 대한 대량의 동시 접근이 전부 캐시 미스가 돼서 일제히 DB로 문의하는 현상입니다. 순간적으로 수백 배의 요청이 덮치니까 순식간에 DB가 죽는 경우가 있습니다.

첫 번째 대책은 분산 락입니다. 처음 캐시 미스를 뽑은 요청만 DB 문의 권한을 얻고, 나머지는 오래된 값을 반환합니다. 다만 락 자체가 병목이 안 되도록 보유 시간은 최대한 짧게 합니다.

둘째가 논리 TTL에 의한 선행 갱신입니다. 실제 유효기간은 길게 하고, 값에 논리적 기한을 따로 갖게 합니다. 기한이 다가온 첫 요청이 비동기로 재생성하는 동안, 나머지에는 오래된 값을 계속 반환합니다.

더 단순한 대책은 TTL에 지터를 넣는 겁니다. 어느 걸 고를지는 중요도로 판단합니다. 핫 키에는 무거운 대책을, 그 외에는 지터만으로 충분합니다. 전체 키에 같은 중장비를 넣으면 비용에 안 맞습니다.

### Q70. Spring Bootのgraceful shutdown設定
(Spring Boot의 graceful shutdown 설정)

**🇯🇵 回答**

`server.shutdown=graceful` を設定して、`spring.lifecycle.timeout-per-shutdown-phase` で猶予時間を決めます。

必要な理由は、デプロイの瞬間に処理中のリクエストが強制終了されると、エラーが返るだけでなく決済のような処理が中途半端な状態でDBに残るリスクがあるからです。gracefulを有効にすると、SIGTERMを受けた時点で新規受付を止めて、処理中が完了するまで待ってから終了します。

ただしこの設定だけでは不十分です。Kubernetesのservice側がPodの終了を検知してルーティングから除外するまでにタイムラグがあるんですよ。その間に新しいリクエストが来ます。preStopフックで数秒スリープを入れて、除外が伝播する時間を稼いでからシャットダウンに入る組み合わせが必要です。

猶予時間の設定も重要です。`terminationGracePeriodSeconds` をSpring側より長くしないと、待たずにSIGKILLが飛んでgracefulの意味がなくなります。この二つは必ずセットで確認します。

**🇰🇷 답변**

`server.shutdown=graceful`을 설정하고 `spring.lifecycle.timeout-per-shutdown-phase`로 유예 시간을 정합니다.

필요한 이유는, 배포 순간에 처리 중인 요청이 강제 종료되면 에러가 반환될 뿐 아니라 결제 같은 처리가 어중간한 상태로 DB에 남을 리스크가 있기 때문입니다. graceful을 켜면 SIGTERM을 받은 시점에 신규 접수를 멈추고, 처리 중인 게 완료될 때까지 기다렸다가 종료합니다.

다만 이 설정만으로는 부족합니다. Kubernetes의 service 쪽이 Pod 종료를 감지해서 라우팅에서 빼기까지 시차가 있거든요. 그 사이에 새 요청이 옵니다. preStop 훅에서 몇 초 슬립을 넣어서 제외가 전파되는 시간을 벌고 나서 셧다운에 들어가는 조합이 필요합니다.

유예 시간 설정도 중요합니다. `terminationGracePeriodSeconds`를 Spring 쪽보다 길게 하지 않으면, 기다려 주지 않고 SIGKILL이 날아와서 graceful의 의미가 사라집니다. 이 둘은 반드시 세트로 확인합니다.

# Part 10. DevOps 및 Observability

### Q71. Observabilityの3本柱
(Observability의 3요소)

**🇯🇵 回答**

メトリクス、ログ、トレースの三つですね。大事なのは、それぞれが答えられる問いが違うという点です。

メトリクスは「何が起きているか」を時系列の数値で示します。集計済みなので低コストで長期保持でき、検知とアラートに向いています。ただし個々のリクエストで何が起きたかは分かりません。

ログは「何が起きたか」の詳細をテキストで残します。情報量は多い代わりに、量が膨大でコストがかかります。

トレースは「どこで時間がかかったか」を、複数サービスをまたぐ経路として示します。分散システムでボトルネックを特定するのは、トレースにしかできません。

この三つを別々に見ていると調査が遅くなります。メトリクスで異常を検知し、トレースで遅いリクエストを見つけ、そのTrace IDでログを引く。この流れが繋がって初めて価値が出ます。だから導入時は、Trace IDをログの構造化フィールドに含めるところから始めます。

**🇰🇷 답변**

메트릭, 로그, 트레이스 세 가지입니다. 중요한 건 각각이 답할 수 있는 질문이 다르다는 점이에요.

메트릭은 "무슨 일이 일어나고 있는가"를 시계열 수치로 보여줍니다. 집계된 거라서 저비용으로 오래 보관할 수 있고 탐지와 알림에 적합합니다. 다만 개별 요청에서 무슨 일이 있었는지는 알 수 없습니다.

로그는 "무슨 일이 있었는가"의 상세를 텍스트로 남깁니다. 정보량이 많은 대신 양이 방대해서 비용이 듭니다.

트레이스는 "어디서 시간이 걸렸는가"를 여러 서비스를 걸치는 경로로 보여줍니다. 분산 시스템에서 병목을 특정하는 건 트레이스만이 할 수 있습니다.

이 세 가지를 따로따로 보면 조사가 늦어집니다. 메트릭으로 이상을 감지하고, 트레이스로 느린 요청을 찾고, 그 Trace ID로 로그를 뽑는다. 이 흐름이 이어져야 비로소 가치가 생깁니다. 그래서 도입할 때는 Trace ID를 로그의 구조화 필드에 넣는 것부터 시작합니다.

### Q72. CI/CDで本番デプロイリスクを最小化する工夫
(CI/CD로 프로덕션 배포 리스크를 최소화하는 방법)

**🇯🇵 回答**

多層で防御する考え方です。

デプロイ前の層では、テストをパイプラインに必須化して、通らなければマージもデプロイもできない仕組みにします。静的解析とセキュリティスキャンも自動化して、人のレビューを設計判断に集中させます。

デプロイの層ではカナリアリリースで1〜5%だけ流して、エラー率とレイテンシを監視します。重要なのは、判定を人間の目視ではなく自動化することです。閾値を超えたら自動でロールバックする仕組みがないと、深夜のデプロイで気づくのが遅れますから。

もう一段、見落とされがちなのがデプロイとリリースの分離です。フィーチャーフラグを使えば、コードは全ユーザーに配布したまま機能の有効化だけを絞れます。問題が起きても再デプロイせずフラグを切るだけで戻せます。

DBマイグレーションだけは別扱いです。ロールバックが効かないので拡張・縮小方式で段階的に進めます。

**🇰🇷 답변**

다층으로 방어하는 사고방식입니다.

배포 전 계층에서는 테스트를 파이프라인에 필수화해서, 통과 안 하면 머지도 배포도 못 하는 구조로 합니다. 정적 분석과 보안 스캔도 자동화해서 사람의 리뷰를 설계 판단에 집중시킵니다.

배포 계층에서는 카나리 릴리스로 1~5%만 흘려서 에러율과 레이턴시를 모니터링합니다. 중요한 건 판정을 사람의 육안이 아니라 자동화하는 겁니다. 임계치를 넘으면 자동으로 롤백하는 장치가 없으면 심야 배포에서 알아채는 게 늦어지니까요.

한 단계 더, 놓치기 쉬운 게 배포와 릴리스의 분리입니다. 피처 플래그를 쓰면 코드는 전체 사용자에게 배포한 채로 기능 활성화만 좁힐 수 있습니다. 문제가 생겨도 재배포 없이 플래그만 끄면 되돌릴 수 있고요.

DB 마이그레이션만은 따로 다룹니다. 롤백이 안 먹히니까 확장·축소 방식으로 단계적으로 진행합니다.

### Q73. DBマイグレーションの無停止手順
(DB 마이그레이션 무중단 절차)

**🇯🇵 回答**

原則はExpand/Contractです。新旧どちらのコードでも動作するスキーマの状態を一度経由してから、古いものを消す。この順番を守ります。

第一段階で新しいカラムを追加します。既存の読み書きには影響しません。第二段階で新旧両方に書き込むデュアルライトに切り替えます。ここが最も事故の起きやすい段階で、新カラムへの書き込み失敗が既存処理を壊さないよう防御的に実装します。第三段階で既存データをバックフィルします。第四段階で読み取りを新カラムに切り替えます。ここで問題が起きても、設定を戻すだけで即座に切り戻せます。十分な期間を置いてから、第五段階で旧カラムを削除します。

この手順の本質は、各段階が独立してロールバック可能であることです。一足飛びに移行しようとすると、途中で問題が起きたときに戻す手段がなくなります。旧カラムの削除だけは、本当に誰も参照していないことをログで確認してから実行します。

**🇰🇷 답변**

원칙은 Expand/Contract입니다. 신·구 어느 코드로도 동작하는 스키마 상태를 한 번 거친 다음에 옛것을 지운다. 이 순서를 지킵니다.

1단계에서 새 컬럼을 추가합니다. 기존 읽기쓰기에는 영향이 없습니다. 2단계에서 신·구 양쪽에 쓰는 듀얼 라이트로 전환합니다. 여기가 제일 사고 나기 쉬운 단계라, 새 컬럼 쓰기 실패가 기존 처리를 망가뜨리지 않도록 방어적으로 구현합니다. 3단계에서 기존 데이터를 백필합니다. 4단계에서 읽기를 새 컬럼으로 전환합니다. 여기서 문제가 생겨도 설정만 되돌리면 즉시 되돌릴 수 있습니다. 충분한 기간을 둔 다음, 5단계에서 옛 컬럼을 삭제합니다.

이 절차의 본질은 각 단계가 독립적으로 롤백 가능하다는 겁니다. 한 번에 넘어가려고 하면 도중에 문제가 생겼을 때 되돌릴 수단이 없어집니다. 옛 컬럼 삭제만은 정말로 아무도 참조하지 않는다는 걸 로그로 확인한 다음에 실행합니다.

### Q74. Liveness / Readiness Probeの違い
(Liveness / Readiness Probe의 차이)

**🇯🇵 回答**

Livenessは「プロセスが生きているか」を確認します。失敗するとコンテナが再起動されます。デッドロックで応答しなくなったプロセスを外から回復させる、最後の砦ですね。

Readinessは「トラフィックを受ける準備ができているか」を確認します。失敗しても再起動されず、ルーティング対象から一時的に外れるだけです。起動直後で初期化中の間はここを失敗させます。

この二つを混同すると、実運用でよくある事故が起きます。典型的なのが、「DB接続が一時的に不安定」という条件をLivenessに入れてしまうケースです。DBが数秒詰まっただけで正常なプロセスまで次々に再起動され、その負荷がさらにDBを圧迫する。Livenessは自分だけで判断できる項目に限定して、外部依存はReadiness側に置くのが安全です。

もう一点、起動に時間がかかるアプリではStartup Probeを使います。起動完了前にLivenessが失敗と判定して再起動ループに陥るのを避けられます。

**🇰🇷 답변**

Liveness는 "프로세스가 살아 있는가"를 확인합니다. 실패하면 컨테이너가 재시작됩니다. 데드락으로 응답을 안 하게 된 프로세스를 밖에서 회복시키는 최후의 보루입니다.

Readiness는 "트래픽을 받을 준비가 됐는가"를 확인합니다. 실패해도 재시작되지 않고 라우팅 대상에서 일시적으로 빠질 뿐입니다. 기동 직후 초기화 중인 동안은 여기를 실패시킵니다.

이 둘을 혼동하면 실운영에서 흔한 사고가 납니다. 전형적인 게 "DB 접속이 일시적으로 불안정"이라는 조건을 Liveness에 넣어 버리는 케이스입니다. DB가 몇 초 막혔을 뿐인데 정상적인 프로세스까지 줄줄이 재시작되고, 그 부하가 DB를 더 압박합니다. Liveness는 스스로 판단할 수 있는 항목으로 한정하고, 외부 의존은 Readiness 쪽에 두는 게 안전합니다.

한 가지 더, 기동에 시간이 걸리는 앱에서는 Startup Probe를 씁니다. 기동 완료 전에 Liveness가 실패로 판정해서 재시작 루프에 빠지는 걸 피할 수 있습니다.

### Q75. IaC導入のメリットと注意点
(IaC 도입의 장점과 주의점)

**🇯🇵 回答**

メリットは、インフラの構成をコードとして再現可能にできることです。手順書の手動作業は実行する人によって差が出ますが、コード化すればレビューを通せますし、Gitの履歴として誰が何を変えたかが残ります。同じ構成の環境を一瞬で複製できるのも大きいです。

注意点は運用面に集中します。最も重要なのがStateファイルの扱いです。TerraformのStateには機密情報が平文で含まれることがあります。Gitにコミットする事故は実際によく起きるので、リモートバックエンドに置いて暗号化とアクセス制限をかけます。

次に、複数人が同時にapplyするとState不整合が起きるので、ロック機構を必ず設定します。

そしてコードレビューだけでは不十分で、適用前に必ず plan の差分を確認する運用を徹底します。意図しない削除が計画に含まれていないかを目視で確認してからapplyする。本番では承認フローを挟むパイプライン設計にしています。

**🇰🇷 답변**

장점은 인프라 구성을 코드로 재현 가능하게 만들 수 있다는 겁니다. 절차서의 수동 작업은 실행하는 사람에 따라 차이가 나지만, 코드화하면 리뷰를 거칠 수 있고 Git 이력으로 누가 뭘 바꿨는지가 남습니다. 같은 구성의 환경을 순식간에 복제할 수 있는 것도 크고요.

주의점은 운영 면에 집중됩니다. 가장 중요한 게 State 파일의 취급입니다. Terraform의 State에는 기밀 정보가 평문으로 들어가는 경우가 있습니다. Git에 커밋하는 사고는 실제로 자주 일어나니까, 원격 백엔드에 두고 암호화와 접근 제한을 겁니다.

다음으로, 여러 명이 동시에 apply하면 State 불일치가 생기니까 락 메커니즘을 반드시 설정합니다.

그리고 코드 리뷰만으로는 부족해서, 적용 전에 반드시 plan의 차분을 확인하는 운영을 철저히 합니다. 의도치 않은 삭제가 계획에 들어 있지 않은지 육안으로 확인한 다음에 apply한다. 프로덕션에서는 승인 플로를 끼우는 파이프라인 설계로 합니다.
