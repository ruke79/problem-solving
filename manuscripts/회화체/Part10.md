# Part 28. 시스템 아키텍처 엣지 케이스

### Q152. トランザクショナル・アウトボックスパターン
(트랜잭셔널 아웃박스 패턴)

**🇯🇵 回答**

DBの更新とKafkaへのメッセージ送信を、完全に同期させるためのパターンです。業務データと一緒にOutboxテーブルへイベントを同じトランザクションで保存しておいて、別の非同期リレーワーカーがそのテーブルを読んでKafkaに送る。これでメッセージが確実に送られることを保証します。

このパターンが解決する問題を正確に言うと、「二重書き込み問題」、Dual Write Problemです。

DBにコミットした直後、Kafkaへの送信前にプロセスが落ちるとどうなるか。業務データは保存されたのに、イベントが飛ばない状態になります。逆にKafkaへ先に送ってDBのコミットが失敗すると、実際には起きていない事象のイベントが流れます。

この二つの操作は別々のシステムなので、普通のトランザクションでは同時に保証できません。Outboxは「一つのDBトランザクションの中に閉じ込める」ことでこれを解決します。

リレーワーカーの実装方式は二つあります。一つはOutboxテーブルをポーリングする方式。実装は簡単ですけど、DBに定期的な負荷がかかります。もう一つがQ51でお話ししたCDC、Debeziumですね。これでOutboxテーブルのbinlogを読む方式で、DBへの追加負荷がほぼゼロという利点があります。私は規模が大きいなら後者を選びます。

そして重要な前提が一つ。このパターンが保証するのはAt-Least-Once、最低一回であって、Exactly-Onceではありません。リレーワーカーが送信した後、オフセット更新の前に落ちれば、同じイベントが再送されます。だからQ100でお話しした通り、コンシューマー側の冪等な処理が必ずセットで必要になります。

**🇰🇷 답변**

DB 갱신이랑 Kafka 메시지 전송을 완전히 동기화하기 위한 패턴입니다. 업무 데이터랑 같이 Outbox 테이블에 이벤트를 같은 트랜잭션으로 저장해두고, 별도의 비동기 릴레이 워커가 그 테이블을 읽어서 Kafka로 보냅니다. 이걸로 메시지가 확실히 간다는 걸 보장합니다.

이 패턴이 푸는 문제를 정확히 말하면 "이중 쓰기 문제", Dual Write Problem입니다.

DB에 커밋한 직후, Kafka로 보내기 전에 프로세스가 죽으면 어떻게 될까요. 업무 데이터는 저장됐는데 이벤트가 안 날아간 상태가 됩니다. 반대로 Kafka에 먼저 보내고 DB 커밋이 실패하면, 실제로는 안 일어난 사건의 이벤트가 흘러갑니다.

이 두 조작은 서로 다른 시스템입니다. 그래서 보통 트랜잭션으로는 동시에 보장 못 합니다. Outbox는 "하나의 DB 트랜잭션 안에 가둔다"는 방식으로 이걸 해결합니다.

릴레이 워커 구현 방식은 두 가지입니다. 하나는 Outbox 테이블을 폴링하는 방식. 구현은 쉬운데 DB에 주기적으로 부하가 걸립니다. 다른 하나가 Q51에서 말씀드린 CDC, Debezium이요. 이걸로 Outbox 테이블의 binlog를 읽는 방식인데, DB에 추가 부하가 거의 없다는 장점이 있습니다. 저는 규모가 크면 후자를 고릅니다.

그리고 중요한 전제 하나. 이 패턴이 보장하는 건 At-Least-Once, 최소 한 번이지 Exactly-Once가 아닙니다. 릴레이 워커가 보낸 다음에 오프셋 갱신 전에 죽으면 같은 이벤트가 다시 갑니다. 그래서 Q100에서 말씀드린 대로, 컨슈머 쪽의 멱등한 처리가 반드시 세트로 필요합니다.

### Q153. BFFパターンを導入する最大の理由
(BFF 패턴을 도입하는 가장 큰 이유)

**🇯🇵 回答**

Web、iOS、Androidみたいに、クライアントごとに最適なAPIを作るためです。バックエンドの複雑なマイクロサービス群を隠して、各クライアントが必要とするデータの集約や変換をBFFでやる。これでフロントエンド側の過剰な通信を防げます。

でも、もう一つ、組織的にはもっと重要な理由があります。BFFはフロントエンドチームが所有する層だ、という点です。

BFFがない構成だと、モバイル画面に新しいフィールドを一つ追加したいだけでも、バックエンドチームにAPI変更を依頼して、その優先順位を待つ必要があります。BFFがあれば、フロントエンドチームが自分たちのBFFを自分たちのペースで変えられる。だからチーム間の依存関係とリードタイムが劇的に短くなります。これはQ88でお話ししたチーム間コミュニケーションコストの削減と同じ効果を、アーキテクチャで実現している例ですね。

一方で代償も明確です。クライアントの数だけBFFが増えるので、共通ロジックの重複という新しい問題が生まれます。認証やロギングみたいな共通処理は、各BFFに散らばらせずにQ36でお話ししたAPIゲートウェイ層に集約する。この役割分担をはっきりさせておく必要があります。

それとBFFが増えるとデプロイと監視の対象も増えます。だからクライアントが1種類しかない段階でBFFを入れるのは、典型的な過剰設計です。クライアントの多様化が実際に起きてから入れる。これがQ94のYAGNIに沿った判断だと考えています。

**🇰🇷 답변**

Web, iOS, Android처럼 클라이언트마다 최적인 API를 만들기 위해서입니다. 백엔드의 복잡한 마이크로서비스들을 감추고, 각 클라이언트가 필요한 데이터 집계나 변환을 BFF에서 합니다. 이러면 프론트엔드 쪽의 과한 통신을 막을 수 있습니다.

그런데 하나 더, 조직적으로는 더 중요한 이유가 있습니다. BFF는 프론트엔드 팀이 소유하는 계층이라는 점입니다.

BFF가 없는 구성이면, 모바일 화면에 새 필드 하나 추가하고 싶어도 백엔드 팀한테 API 변경을 부탁하고 그 우선순위를 기다려야 합니다. BFF가 있으면 프론트엔드 팀이 자기들 BFF를 자기들 속도로 바꿀 수 있습니다. 그래서 팀 간 의존 관계랑 리드타임이 확 짧아집니다. 이건 Q88에서 말씀드린 팀 간 커뮤니케이션 비용 절감이랑 같은 효과를 아키텍처로 실현한 예입니다.

한편 대가도 명확합니다. 클라이언트 수만큼 BFF가 늘어나니까 공통 로직 중복이라는 새 문제가 생깁니다. 인증이나 로깅 같은 공통 처리는 각 BFF에 흩어놓지 말고 Q36에서 말씀드린 API 게이트웨이 계층에 모읍니다. 이 역할 분담을 확실히 해둬야 합니다.

그리고 BFF가 늘면 배포랑 모니터링 대상도 늡니다. 그래서 클라이언트가 한 종류밖에 없는 단계에서 BFF를 넣는 건 전형적인 과잉 설계입니다. 클라이언트가 실제로 다양해지고 나서 넣는다. 이게 Q94의 YAGNI에 맞는 판단이라고 생각합니다.

### Q154. WebSocketサーバーのスケールアウトの課題と解決策
(WebSocket 서버 스케일 아웃의 과제와 해결책)

**🇯🇵 回答**

WebSocketはステートフルな接続を維持します。だから単一サーバーに依存するとスケールアウトできません。解決策として、RedisのPub/Sub機能やKafkaみたいなメッセージブローカーをバックエンドに挟んで、複数サーバー間でイベントをブロードキャストするアーキテクチャを設計します。

具体的な問題を説明します。ユーザーAがサーバー1に、ユーザーBがサーバー2に接続しているとします。AがBにメッセージを送ろうとしても、サーバー1はBの接続を持っていないので、直接届けられません。

そこでサーバー1がRedis Pub/Subにメッセージをpublishします。全サーバーがそれをsubscribeして、自分が接続を持っているユーザー宛のメッセージだけを配信する。こういう構成にします。

実装上、さらに考えるべき点が三つあります。

第一にロードバランサーの設定。WebSocketはHTTPからのプロトコルアップグレードを伴うので、LBがこれを正しく通す設定が必要です。Upgradeヘッダーの転送と、十分に長いアイドルタイムアウトですね。

第二に接続の復旧。サーバーの再起動やスケールインで接続が切れたとき、クライアント側で指数バックオフを入れた自動再接続を実装しないと、全クライアントが同時に再接続を試みてサーバーが即死します。

第三にRedis Pub/Subの配送保証。Pub/Subはメッセージを永続化しません。だから一瞬でも切断されていたサーバーは、その間のメッセージを取りこぼします。チャットの履歴みたいに取りこぼしが許されない場合は、Pub/Subだけに頼らない設計にします。メッセージ本体はDBに保存して、Pub/Subは「新着があった」という通知だけに使う。こういう形ですね。

**🇰🇷 답변**

WebSocket은 스테이트풀한 연결을 유지합니다. 그래서 단일 서버에 의존하면 스케일 아웃이 안 됩니다. 해결책으로 Redis의 Pub/Sub 기능이나 Kafka 같은 메시지 브로커를 백엔드에 끼워서, 여러 서버 간에 이벤트를 브로드캐스트하는 아키텍처를 설계합니다.

구체적인 문제를 설명드리겠습니다. 사용자 A가 서버 1에, 사용자 B가 서버 2에 접속해 있다고 해봅시다. A가 B한테 메시지를 보내려고 해도, 서버 1은 B의 연결을 안 가지고 있어서 직접 전달을 못 합니다.

그래서 서버 1이 Redis Pub/Sub에 메시지를 publish합니다. 모든 서버가 그걸 subscribe해서, 자기가 연결을 가지고 있는 사용자 앞으로 온 메시지만 배송합니다. 이런 구성으로 합니다.

구현할 때 더 생각해야 할 점이 세 개 있습니다.

첫째는 로드밸런서 설정. WebSocket은 HTTP에서 프로토콜 업그레이드를 하니까, LB가 이걸 제대로 통과시키는 설정이 필요합니다. Upgrade 헤더 전달이랑 충분히 긴 아이들 타임아웃이요.

둘째는 연결 복구. 서버 재시작이나 스케일 인으로 연결이 끊겼을 때, 클라이언트 쪽에서 지수 백오프를 넣은 자동 재접속을 구현 안 하면, 모든 클라이언트가 동시에 재접속을 시도해서 서버가 즉사합니다.

셋째는 Redis Pub/Sub의 배송 보장. Pub/Sub은 메시지를 영속화하지 않습니다. 그래서 잠깐이라도 끊겼던 서버는 그동안의 메시지를 놓칩니다. 채팅 이력처럼 놓치면 안 되는 경우는 Pub/Sub에만 기대지 않는 설계로 갑니다. 메시지 본체는 DB에 저장하고, Pub/Sub은 "새 글이 있다"는 알림에만 씁니다. 이런 형태로요.

### Q155. ヘキサゴナルアーキテクチャの核心的目的【Q138の再出題】
(헥사고날 아키텍처의 핵심 목적 【Q138 재출제】)

> ⚠️ Q138(벤더 락인)에서 헥사고날을 "락인 경감의 수단"으로 설명했습니다. 여기서는 아키텍처 자체의 목적(테스트 용이성 포함)을 묻고 있습니다.

**🇯🇵 回答**

ビジネスロジックを、DBや外部API、UIといった外部の詳細技術から完全に独立させることです。これによって、DBをOracleからMySQLに変えても、中心となるドメインロジックのコードは一切修正しなくて済む。高い保守性を実現します。

Q138ではこれをベンダーロックイン軽減の文脈でお話ししました。でも実は、日常的な開発において一番大きな恩恵はテスト容易性です。

ドメイン層が外部技術に依存していないということは、DBもWebサーバーも起動せずに、純粋なJavaのオブジェクトとしてビジネスロジックの単体テストが書けるということです。テストの実行が数ミリ秒で終わるので、開発中に何度でも気軽に回せます。

逆に、ドメインロジックがJPAのEntityやSpringのアノテーションに強く依存していたらどうなるか。テストのたびにコンテキストの起動が必要になって、テスト全体が数分かかるようになります。そうなると結果として、誰もテストを回さなくなります。

依存の向きも重要な原則です。依存は必ず「外側から内側、ドメインへ」の一方向でなければなりません。

ドメイン層はインターフェース、ポートだけを定義して、それを実装するアダプター、JPA実装やREST実装は外側に置きます。実行時にはDIコンテナがアダプターを注入するので、ドメイン層はアダプターの存在すら知りません。

これはQ92でお話ししたDIの本質的な価値でもあります。DIは単にテストを楽にする道具じゃなくて、依存の向きを制御するアーキテクチャ上の仕組みなんだ、という理解。これがこの二つの質問を繋ぐ視点だと考えています。

**🇰🇷 답변**

비즈니스 로직을 DB나 외부 API, UI 같은 외부의 상세 기술에서 완전히 독립시키는 겁니다. 이러면 DB를 오라클에서 MySQL로 바꿔도, 중심이 되는 도메인 로직 코드는 하나도 안 고쳐도 됩니다. 높은 유지보수성을 실현합니다.

Q138에서는 이걸 벤더 락인 경감이라는 맥락으로 말씀드렸습니다. 그런데 사실 일상적인 개발에서 제일 큰 혜택은 테스트 용이성입니다.

도메인 계층이 외부 기술에 의존 안 한다는 건, DB도 웹 서버도 안 띄우고 순수한 Java 객체로 비즈니스 로직 단위 테스트를 쓸 수 있다는 뜻입니다. 테스트 실행이 몇 밀리초면 끝나니까 개발하면서 몇 번이든 가볍게 돌릴 수 있습니다.

반대로 도메인 로직이 JPA의 Entity나 Spring 애노테이션에 강하게 붙어 있으면 어떻게 될까요. 테스트할 때마다 컨텍스트를 띄워야 해서 테스트 전체가 몇 분씩 걸립니다. 그러면 결과적으로 아무도 테스트를 안 돌립니다.

의존의 방향도 중요한 원칙입니다. 의존은 반드시 "바깥에서 안쪽, 도메인으로" 가는 단방향이어야 합니다.

도메인 계층은 인터페이스, 그러니까 포트만 정의하고, 그걸 구현하는 어댑터, JPA 구현이나 REST 구현은 바깥에 둡니다. 실행할 때는 DI 컨테이너가 어댑터를 주입하니까, 도메인 계층은 어댑터가 있다는 것조차 모릅니다.

이건 Q92에서 말씀드린 DI의 본질적인 가치이기도 합니다. DI는 그냥 테스트를 편하게 해주는 도구가 아니라, 의존의 방향을 제어하는 아키텍처 장치다. 이 이해가 이 두 질문을 잇는 시점이라고 생각합니다.

# Part 29. 고급 데이터베이스 및 파이프라인 심화

### Q156. Kafkaのホットパーティション解決【Q123の再出題・具体的解決策編】
(Kafka 핫 파티션 해결 【Q123 재출제 · 구체적 해결책편】)

> ⚠️ Q123에서는 "순서 보장을 위한 파티션 키 설계"의 부작용으로 핫 파티션을 다뤘습니다. 여기서는 그 해결책 자체를 묻고 있습니다.

**🇯🇵 回答**

パーティションキーの設計が原因です。例えば顧客IDでキーを切ると、特定の大口顧客のトラフィックが集中します。これを防ぐには、IDにランダムなソルトを付けてキーを分散させるか、順序保証が要らない場合はラウンドロビン方式でメッセージを均等に散らします。

ここで必ずセットで言うべきなのが、ソルトを付けると順序保証が失われるという代償です。

Q123でお話しした通り、Kafkaの順序保証は同じパーティション内でだけ有効です。だから同じ顧客IDのメッセージが複数パーティションに散らばった瞬間、その顧客の中での処理順序は保証されなくなります。つまりこの問題は「順序保証」と「負荷分散」のどちらを取るかというトレードオフそのものです。どちらか一方を無条件に選べる問題じゃありません。

実務での現実的な解決策としては、まずキーの粒度を見直すアプローチを検討します。

「顧客ID」でホットスポットが起きるなら、業務上、順序保証が本当に必要な単位は何なのか。例えば「顧客ID + 注文ID」みたいに、もっと細かい粒度でも要件を満たせないかを確認します。粒度を細かくできれば、順序保証を保ったまま自然に分散されます。

それでも大口顧客一人の負荷が単一パーティションの処理能力を超えるなら、「その顧客だけ特別扱いする」という選択肢もあります。ホットな少数のキーを専用のトピック、あるいは専用パーティション群に隔離して、そこだけ別の処理リソースを割り当てる。Q144でお話ししたバルクヘッドパターンの応用ですね。

**🇰🇷 답변**

파티션 키 설계가 원인입니다. 예를 들어 고객 ID로 키를 잡으면 특정 대형 고객의 트래픽이 몰립니다. 이걸 막으려면 ID에 랜덤한 솔트를 붙여서 키를 분산시키거나, 순서 보장이 필요 없으면 라운드 로빈으로 메시지를 고르게 뿌립니다.

여기서 반드시 세트로 말해야 하는 게, 솔트를 붙이면 순서 보장이 사라진다는 대가입니다.

Q123에서 말씀드린 대로 Kafka의 순서 보장은 같은 파티션 안에서만 유효합니다. 그래서 같은 고객 ID 메시지가 여러 파티션에 흩어지는 순간, 그 고객 안에서의 처리 순서는 보장이 안 됩니다. 그러니까 이 문제는 "순서 보장"이랑 "부하 분산" 중에 뭘 고르느냐 하는 트레이드오프 그 자체입니다. 어느 한쪽을 무조건 고를 수 있는 문제가 아닙니다.

실무에서 현실적인 해결책으로는, 일단 키의 단위를 다시 보는 접근부터 검토합니다.

"고객 ID"에서 핫스팟이 생긴다면, 업무상 순서 보장이 정말로 필요한 단위가 뭔지를 봅니다. 예를 들어 "고객 ID + 주문 ID"처럼 더 잘게 쪼갠 단위로도 요건을 채울 수 있는지 확인합니다. 단위를 잘게 만들 수 있으면 순서 보장을 유지한 채로 자연스럽게 분산됩니다.

그래도 대형 고객 한 명의 부하가 단일 파티션 처리 능력을 넘으면, "그 고객만 특별 취급한다"는 선택지도 있습니다. 핫한 소수의 키를 전용 토픽, 아니면 전용 파티션 그룹으로 격리하고 거기만 별도 처리 리소스를 붙입니다. Q144에서 말씀드린 벌크헤드 패턴의 응용이죠.

### Q157. レプリケーション遅延でユーザーが自分の更新を読めない問題
(레플리케이션 지연으로 사용자가 자기 갱신을 못 읽는 문제)

**🇯🇵 回答**

書き込み直後にRead Replicaを参照してしまうのが原因です。解決策として、書き込みを行ったユーザーのセッションに一定時間フラグを立てて、そのユーザーの次の読み取りリクエストだけは強制的にPrimaryへ向ける。こういうルーティング制御をします。

この問題は「Read Your Own Writes」、自分の書き込みを読める、という一貫性モデルの名前で知られています。Q37でお話しした結果整合性の実務的な副作用そのものですね。

技術的には正しく動いていても、ユーザーから見ると「投稿したのに一覧に出てこない」という完全なバグに見えます。だからUX上は必ず対処が必要です。

セッションフラグ方式には注意点があります。フラグの有効時間を何秒にするか。これは実際のレプリカ遅延の実測値から決める必要があります。短すぎると効果がないし、長すぎるとPrimaryへの読み取り負荷が増えて、レプリカを分けた意味が薄れます。私は遅延のp99を計測して、それより少し長い時間を設定します。

もっと精密な代替手段もあります。書き込み時に取得したトランザクションの位置情報、MySQLならGTID、PostgreSQLならLSNですね。これをクライアント側に持たせて、読み取り時にレプリカがその位置まで追いついているかを確認する。追いついていればレプリカから、まだならPrimaryから読む。この判定ができるので、時間ベースの推測より正確です。実装コストは上がりますけど、Primaryへの不要な負荷を最小化できます。

あと、対象を絞ることも重要です。全ての読み取りをこの仕組みの対象にする必要はありません。「自分が今書き込んだデータを直後に読む」画面、投稿完了画面やマイページなどだけに限定すれば、Primaryへの負荷増加を抑えられます。

**🇰🇷 답변**

쓰기 직후에 Read Replica를 보게 되는 게 원인입니다. 해결책으로, 쓰기를 한 사용자의 세션에 일정 시간 플래그를 세워두고, 그 사용자의 다음 읽기 요청만 강제로 Primary로 보냅니다. 이렇게 라우팅을 제어합니다.

이 문제는 "Read Your Own Writes", 자기 쓰기를 읽을 수 있다는 일관성 모델 이름으로 알려져 있습니다. Q37에서 말씀드린 결과적 일관성의 실무적인 부작용 그 자체입니다.

기술적으로는 제대로 돌고 있어도, 사용자 눈에는 "글을 올렸는데 목록에 안 나온다"는 완전한 버그로 보입니다. 그래서 UX상 반드시 대처해야 합니다.

세션 플래그 방식에는 주의점이 있습니다. 플래그 유효 시간을 몇 초로 할 거냐. 이건 실제 레플리카 지연의 실측치에서 정해야 합니다. 너무 짧으면 효과가 없고, 너무 길면 Primary로 가는 읽기 부하가 늘어서 레플리카를 나눈 의미가 옅어집니다. 저는 지연의 p99를 재보고, 그보다 조금 긴 시간으로 잡습니다.

더 정밀한 대안도 있습니다. 쓸 때 받은 트랜잭션 위치 정보, MySQL이면 GTID, PostgreSQL이면 LSN이요. 이걸 클라이언트한테 들려주고, 읽을 때 레플리카가 그 위치까지 따라왔는지 확인합니다. 따라왔으면 레플리카에서, 아직이면 Primary에서 읽습니다. 이 판정이 되니까 시간 기반 추측보다 정확합니다. 구현 비용은 올라가지만, Primary로 가는 불필요한 부하를 최소화할 수 있습니다.

그리고 대상을 좁히는 것도 중요합니다. 모든 읽기를 이 장치의 대상으로 할 필요는 없습니다. "자기가 방금 쓴 데이터를 바로 읽는" 화면, 작성 완료 화면이나 마이페이지 같은 데만 한정하면 Primary 부하 증가를 억제할 수 있습니다.

### Q158. RDBMSテキスト検索の限界とElasticsearch導入基準
(RDBMS 텍스트 검색의 한계와 Elasticsearch 도입 기준)

**🇯🇵 回答**

RDBMSのLIKE検索はインデックスが効かず全件スキャンになります。だから大規模データでは致命的です。形態素解析、同義語対応、あるいはミリ秒単位のフルテキスト検索要件が出てきた段階で、DBからデータを同期させたElasticsearchを検索専用の基盤として入れます。

技術的な原理を補足すると、`LIKE 'keyword%'`、前方一致ですね。これはB+Treeインデックスが効きます。でも `LIKE '%keyword%'`、中間一致は効きません。

Q5でお話しした通り、B+Treeは値の先頭から順に並んでいます。だから先頭が不定な検索では木を辿れなくて、全件を舐めるしかない。これが根本原因です。

導入判断の基準としては、まずRDBMS内で解決できないかを検討します。

MySQLやPostgreSQLにも全文検索インデックス、FULLTEXTやGINがあります。データ量が数十万件くらいで、日本語の形態素解析要件がそれほど厳しくなければ、これで十分なことも多いです。

Elasticsearchの導入は、「検索専用の別システムを運用する」というコストを背負う判断です。クラスタの監視、DBとの同期パイプライン、Q51のCDCですね、この維持。それに同期遅延や不整合への対処。こういう運用負担が新たに発生します。

だから私の判断基準は明確です。「検索がプロダクトの主要な価値提供の一部になっているか」。

ECサイトの商品検索みたいに、検索体験そのものが売上に直結するならElasticsearchの価値は十分にあります。でも管理画面での稀な絞り込み検索くらいなら、RDBMSの全文検索インデックスで済ませる方が全体コストは低くなります。これもQ94のYAGNIに沿った、必要になってから入れるという判断ですね。

**🇰🇷 답변**

RDBMS의 LIKE 검색은 인덱스를 못 타고 풀 스캔이 됩니다. 그래서 대규모 데이터에서는 치명적입니다. 형태소 분석, 동의어 처리, 아니면 밀리초 단위 풀 텍스트 검색 요건이 나온 시점에, DB에서 데이터를 동기화시킨 Elasticsearch를 검색 전용 기반으로 넣습니다.

기술적 원리를 보충하면요. `LIKE 'keyword%'`, 전방 일치요. 이건 B+Tree 인덱스가 먹습니다. 그런데 `LIKE '%keyword%'`, 중간 일치는 안 먹습니다.

Q5에서 말씀드린 대로 B+Tree는 값의 앞부분부터 순서대로 늘어서 있습니다. 그래서 앞부분이 뭔지 모르는 검색에서는 트리를 못 타고 전건을 다 훑을 수밖에 없습니다. 이게 근본 원인입니다.

도입 판단 기준으로는, 일단 RDBMS 안에서 해결이 안 되는지부터 봅니다.

MySQL이나 PostgreSQL에도 전문 검색 인덱스, FULLTEXT나 GIN이 있습니다. 데이터량이 수십만 건 정도이고 일본어 형태소 분석 요건이 그렇게 빡세지 않으면, 이걸로 충분한 경우도 많습니다.

Elasticsearch 도입은 "검색 전용 별도 시스템을 운영한다"는 비용을 지는 판단입니다. 클러스터 모니터링, DB랑의 동기화 파이프라인, Q51의 CDC요, 이거 유지. 거기에 동기 지연이나 불일치 대처까지. 이런 운영 부담이 새로 생깁니다.

그래서 제 판단 기준은 명확합니다. "검색이 프로덕트의 주요 가치 제공의 일부인가".

이커머스 상품 검색처럼 검색 경험 자체가 매출에 직결되면 Elasticsearch의 가치는 충분합니다. 그런데 관리 화면에서 가끔 하는 필터링 검색 정도면, RDBMS 전문 검색 인덱스로 끝내는 게 전체 비용은 낮습니다. 이것도 Q94의 YAGNI에 맞는, 필요해지면 넣는다는 판단입니다.

### Q159. 公共機関でのOracleチューニング経験が現代インフラにどう活きるか
(공공기관에서의 오라클 튜닝 경험이 현대 인프라에 어떻게 살아나는가)

**🇯🇵 回答**

特定の製品の知識ではなくて、「データがディスクのどこにあって、どうI/Oが発生するか」という物理的な構造への深い理解。これが私の武器です。この「インデックスと実行計画の原理」は、NoSQLのパーティションキー設計にも、データパイプラインのボトルネック特定にも、完全に共通する普遍的なエンジニアリング力です。

具体的に対応関係を挙げます。

まずOracleでの実行計画の読み方は、そのままPostgreSQLやMySQLのEXPLAIN ANALYZEの読み方に転用できます。Q46ですね。統計情報が古いと実行計画が狂う、という現象はDB製品を問わず共通です。

次に、インデックスの物理構造の理解は、NoSQLのパーティションキー設計に直結します。Q106でお話しした、UUIDがB-Treeでページ分割を起こすという知識。それとQ156でお話ししたKafkaのホットパーティション問題。この二つは「キーの分布がデータの物理配置を決めて、それが性能を左右する」という、全く同じ原理の違う現れ方です。DynamoDBのパーティションキー設計でホットパーティションを避ける議論も、構造的にはOracleでのインデックス設計の議論と同型です。

そして三つ目に、「まず計測してから直す」という規律そのものです。Q53でお話ししたスロークエリのチューニングプロセス、累計時間で優先順位をつけて、実行計画で仮説を立てて、本番相当データで検証する。これはDBに限らずアプリケーションのプロファイリングにも、データパイプラインのボトルネック特定にもそのまま使えます。

製品知識は陳腐化します。でもこの「物理構造への理解」と「計測に基づく規律」は陳腐化しない。これが私が長年のDB経験から得た、一番価値ある資産だと考えています。

**🇰🇷 답변**

특정 제품 지식이 아니라 "데이터가 디스크 어디에 있고, I/O가 어떻게 발생하는가"라는 물리적 구조에 대한 깊은 이해. 이게 제 무기입니다. 이 "인덱스랑 실행 계획의 원리"는 NoSQL 파티션 키 설계에도, 데이터 파이프라인 병목 찾기에도 완전히 통하는 보편적인 엔지니어링 역량입니다.

구체적으로 대응 관계를 들어보겠습니다.

먼저 오라클에서 실행 계획 읽는 법은 그대로 PostgreSQL이나 MySQL의 EXPLAIN ANALYZE 읽는 법으로 옮겨갑니다. Q46이요. 통계 정보가 오래되면 실행 계획이 어긋난다는 현상은 DB 제품 상관없이 공통입니다.

다음으로 인덱스의 물리 구조 이해는 NoSQL 파티션 키 설계로 바로 연결됩니다. Q106에서 말씀드린, UUID가 B-Tree에서 페이지 분할을 일으킨다는 지식. 그리고 Q156에서 말씀드린 Kafka 핫 파티션 문제. 이 둘은 "키의 분포가 데이터의 물리 배치를 정하고, 그게 성능을 좌우한다"는 똑같은 원리가 다르게 나타난 겁니다. DynamoDB 파티션 키 설계에서 핫 파티션을 피하는 이야기도 구조적으로는 오라클 인덱스 설계 이야기랑 같은 형태입니다.

그리고 세 번째로, "먼저 재고 나서 고친다"는 규율 그 자체입니다. Q53에서 말씀드린 슬로우 쿼리 튜닝 프로세스요. 누적 시간으로 우선순위 매기고, 실행 계획으로 가설 세우고, 프로덕션 수준 데이터로 검증한다. 이건 DB만이 아니라 애플리케이션 프로파일링에도, 데이터 파이프라인 병목 찾기에도 그대로 씁니다.

제품 지식은 낡습니다. 그런데 이 "물리 구조에 대한 이해"랑 "계측에 기반한 규율"은 안 낡습니다. 이게 제가 오랜 DB 경험에서 얻은 제일 값진 자산이라고 생각합니다.

# Part 30. AI 프로덕션 환경 및 LLM 실무

### Q160. RAGシステムの回答品質をどう評価・監視するか
(RAG 시스템의 답변 품질을 어떻게 평가·모니터링할 것인가)

**🇯🇵 回答**

人間による定性評価には限界があります。だからRAGASのようなフレームワークを使って、検索された文脈の関連性と、回答の忠実性を自動でスコアリングするCI/CDパイプラインを作ります。

この評価を設計する上で一番重要なのが、評価軸を「検索」と「生成」に分けることです。

回答が悪かったとき、原因が「そもそも正しい文書を検索できていない」のか、「文書は正しいのにLLMがそれを無視して答えた」のか。これで打つべき手が全く違うからです。前者ならQ54でお話ししたハイブリッド検索やリランキングの改善。後者ならプロンプトの改善が必要になります。

RAGASのContext Relevance、検索の質ですね。それとFaithfulness、生成が文脈に忠実かどうか。この指標の分離は、まさにこの切り分けを可能にするためのものです。

そして前提として、Q54でもお話しした通り、Golden Datasetを用意することが全ての出発点です。想定質問と、期待される回答・正解文書のペアですね。これがないと自動評価そのものが成立しません。

本番運用での監視については、オフライン評価だけでは足りません。実際のユーザーからのフィードバックを集めます。良い/悪いのボタン、回答後の再質問率、人間のオペレーターへのエスカレーション率。こういうものですね。それをオフラインのスコアと突き合わせることが重要です。

オフライン評価のスコアが高いのに実際のユーザー満足度が低い。この場合、それはGolden Datasetが実際のユーザーの質問傾向を反映していないというシグナルです。だからデータセット自体を更新する必要があります。評価パイプラインもまた、継続的に見直すべき対象だと考えています。

**🇰🇷 답변**

사람이 하는 정성 평가에는 한계가 있습니다. 그래서 RAGAS 같은 프레임워크를 써서, 검색된 문맥의 연관성이랑 답변의 충실성을 자동으로 점수 매기는 CI/CD 파이프라인을 만듭니다.

이 평가를 설계할 때 제일 중요한 게, 평가 축을 "검색"이랑 "생성"으로 나누는 겁니다.

답변이 나빴을 때, 원인이 "애초에 맞는 문서를 못 찾았다"인지 "문서는 맞는데 LLM이 그걸 무시하고 답했다"인지. 이거에 따라 손 쓸 방법이 완전히 다르거든요. 앞엣것이면 Q54에서 말씀드린 하이브리드 검색이나 리랭킹 개선. 뒤엣것이면 프롬프트 개선이 필요합니다.

RAGAS의 Context Relevance, 검색의 질이요. 그리고 Faithfulness, 생성이 문맥에 충실한가. 이 지표를 나눠놓은 건 바로 이 구분을 가능하게 하려는 겁니다.

그리고 전제로, Q54에서도 말씀드린 대로 Golden Dataset을 준비하는 게 모든 것의 출발점입니다. 예상 질문이랑, 기대되는 답변·정답 문서의 쌍이요. 이게 없으면 자동 평가 자체가 성립을 안 합니다.

프로덕션 운영에서의 모니터링은 오프라인 평가만으로는 부족합니다. 실제 사용자 피드백을 모읍니다. 좋아요/싫어요 버튼, 답변 후 재질문율, 사람 오퍼레이터로의 에스컬레이션율. 이런 것들이요. 그걸 오프라인 점수랑 맞춰보는 게 중요합니다.

오프라인 평가 점수는 높은데 실제 사용자 만족도가 낮다. 이 경우는 Golden Dataset이 실제 사용자의 질문 경향을 못 담고 있다는 신호입니다. 그래서 데이터셋 자체를 갱신해야 합니다. 평가 파이프라인도 계속 다시 봐야 할 대상이라고 생각합니다.

### Q161. LLMに社内RDBの構造化データを問い合わせる設計
(LLM에 사내 RDB의 정형 데이터를 질의하는 설계)

**🇯🇵 回答**

テキスト化してベクトルDBに入れるんじゃなくて、Text-to-SQL技術か、LLMのFunction Calling機能を使います。ユーザーの自然言語の質問をLLMに解析させて、バックエンドで安全に実行できるSQLや内部API呼び出しに変換する。その結果をまたLLMに解釈させて回答させます。

この設計判断には明確な理由があります。構造化データをベクトル化すると、集計や比較みたいな正確性が求められる質問に、全く答えられなくなるからです。

「今月の売上合計は?」という質問に対して、ベクトル検索は「意味的に似た文章」を返すことしかできません。正確な数値の集計はできない。RDBに対してSQLを実行すれば、100%正確な数値が返ります。得意分野が違うので、データの性質に応じて手法を使い分ける、という判断です。

ただし、LLMが生成したSQLをそのまま実行するのは極めて危険です。ここはQ79、プロンプトインジェクションでお話しした「LLMの出力を信頼しない」という原則が、最も強く適用される場面です。

具体的な防御として、私は三層で守ります。

第一に、SQLを直接生成させるんじゃなくて、Function Callingで「許可された関数」を呼ばせる方式を優先します。「月次売上を取得する(年, 月)」という関数だけを公開すれば、任意のSQLは実行され得ません。

第二に、どうしてもText-to-SQLが必要な場合は、読み取り専用かつ対象テーブルが制限されたDBユーザーで実行します。DELETE/UPDATE/DROPが構造的に不可能な状態にする。

第三に、Q126でお話ししたRLSや、WHERE句への強制的なユーザーID付与。これでそのユーザーが本来アクセスできる範囲のデータしか返らないようにします。

**🇰🇷 답변**

텍스트로 만들어서 벡터 DB에 넣는 게 아니라, Text-to-SQL 기술이나 LLM의 Function Calling 기능을 씁니다. 사용자의 자연어 질문을 LLM한테 해석시켜서, 백엔드에서 안전하게 실행할 수 있는 SQL이나 내부 API 호출로 바꿉니다. 그 결과를 다시 LLM한테 해석시켜서 답하게 합니다.

이 설계 판단에는 명확한 이유가 있습니다. 정형 데이터를 벡터화하면, 집계나 비교처럼 정확성이 필요한 질문에 전혀 답을 못 하게 되기 때문입니다.

"이번 달 매출 합계는?"이라는 질문에 벡터 검색은 "의미적으로 비슷한 문장"을 돌려줄 수밖에 없습니다. 정확한 수치 집계는 못 합니다. RDB에 SQL을 실행하면 100% 정확한 숫자가 나옵니다. 잘하는 분야가 다르니까, 데이터 성질에 맞춰서 방법을 나눠 쓴다는 판단입니다.

다만 LLM이 만든 SQL을 그대로 실행하는 건 굉장히 위험합니다. 여기는 Q79, 프롬프트 인젝션에서 말씀드린 "LLM의 출력을 믿지 않는다"는 원칙이 제일 강하게 적용되는 국면입니다.

구체적인 방어로 저는 3층으로 지킵니다.

첫째, SQL을 직접 만들게 하지 않고 Function Calling으로 "허가된 함수"를 부르게 하는 방식을 우선합니다. "월간 매출을 가져온다(년, 월)"라는 함수만 열어두면 임의의 SQL은 실행될 수가 없습니다.

둘째, 꼭 Text-to-SQL이 필요하면 읽기 전용이고 대상 테이블이 제한된 DB 계정으로 실행합니다. DELETE/UPDATE/DROP이 구조적으로 불가능한 상태로 만듭니다.

셋째, Q126에서 말씀드린 RLS나 WHERE 절에 사용자 ID를 강제로 붙이는 것. 이걸로 그 사용자가 원래 접근할 수 있는 범위의 데이터만 나오게 합니다.

### Q162. プロンプトのバージョン管理とリリース戦略
(프롬프트의 버전 관리와 릴리스 전략)

**🇯🇵 回答**

プロンプトもコードの一部として扱います。Gitでバージョン管理して、変更するときは必ず事前に用意したGolden Datasetに対して自動テストを回します。本番への適用は、ランタイムで動的に切り替えられるように、外部のプロンプト管理システムからロードする設計にします。

ここで一見矛盾して見える二つの要求があります。「Gitでバージョン管理する」ことと、「ランタイムで動的に切り替える」ことです。

これはQ72でお話しした「デプロイとリリースの分離」、フィーチャーフラグですね。これと全く同じ構造で解決します。プロンプトの内容自体はGitで管理してレビューと履歴を担保しつつ、本番でどのバージョンを使うかはアプリケーションの再デプロイなしに切り替えられるようにする。これで、プロンプトの変更で問題が起きた場合、コードのロールバックを待たずに即座に前のバージョンへ戻せます。

自動テストの中身も重要です。プロンプトの評価は決定論的じゃないので、普通のユニットテストみたいな完全一致の判定ができません。

だからGolden Datasetに対する評価スコア、Q160のRAGASのような指標ですね。これが変更前と比べて閾値以上に劣化していないかを判定する。こういう形にします。「合格/不合格」じゃなくて「劣化していないか」を見るのが、プロンプトのテストの特徴です。

そして、プロンプトの変更もカナリアリリースの対象にします。Q40のカナリアと同じく、新しいプロンプトをまず数%のトラフィックに適用して、ユーザーのフィードバック指標、Q160でお話しした再質問率などを監視してから全面展開します。

プロンプトの一文字の変更が出力を大きく変えることがあります。だからコードと同等か、それ以上に慎重な展開が必要だと考えています。

**🇰🇷 답변**

프롬프트도 코드의 일부로 다룹니다. Git으로 버전 관리하고, 바꿀 때는 반드시 미리 준비한 Golden Dataset에 대고 자동 테스트를 돌립니다. 프로덕션 적용은 런타임에 동적으로 바꿀 수 있게, 외부 프롬프트 관리 시스템에서 로드하는 설계로 합니다.

여기서 언뜻 모순돼 보이는 두 가지 요구가 있습니다. "Git으로 버전 관리한다"랑 "런타임에 동적으로 바꾼다"입니다.

이건 Q72에서 말씀드린 "배포랑 릴리스의 분리", 피처 플래그요. 이거랑 완전히 같은 구조로 해결합니다. 프롬프트 내용 자체는 Git으로 관리해서 리뷰랑 이력을 남기고, 프로덕션에서 어느 버전을 쓸지는 애플리케이션 재배포 없이 바꿀 수 있게 합니다. 이러면 프롬프트 변경으로 문제가 났을 때 코드 롤백을 기다릴 필요 없이 바로 이전 버전으로 돌아갈 수 있습니다.

자동 테스트의 내용도 중요합니다. 프롬프트 평가는 결정론적이지 않아서, 보통 유닛 테스트처럼 완전 일치로 판정할 수가 없습니다.

그래서 Golden Dataset에 대한 평가 점수, Q160의 RAGAS 같은 지표요. 이게 변경 전보다 임계치 이상으로 나빠지지 않았는지를 판정합니다. 이런 형태로 갑니다. "합격/불합격"이 아니라 "나빠지지 않았는가"를 보는 게 프롬프트 테스트의 특징입니다.

그리고 프롬프트 변경도 카나리 릴리스 대상으로 합니다. Q40의 카나리랑 마찬가지로, 새 프롬프트를 일단 몇 % 트래픽에만 적용하고 사용자 피드백 지표, Q160에서 말씀드린 재질문율 같은 걸 보고 나서 전면 전개합니다.

프롬프트 한 글자 바꾼 게 출력을 크게 바꾸는 경우가 있습니다. 그래서 코드랑 똑같이, 아니면 그 이상으로 신중하게 펼쳐야 한다고 생각합니다.

### Q163. 通常のベクトルRAGとGraphRAGの違い
(일반 벡터 RAG와 GraphRAG의 차이)

**🇯🇵 回答**

ベクトルRAGは意味が似ている文章を検索するのに向いていますが、文書間の複雑な関係性を捉えるのが苦手です。GraphRAGはエンティティの関係性をグラフDBとして構築して参照するので、より推論的で正確な回答をLLMに生成させることができます。

具体的に、ベクトルRAGが苦手な質問の型を挙げると分かりやすいと思います。

「A社と取引のある企業のうち、B技術を使っている会社は?」みたいな、複数のホップ、関係の連鎖を辿る必要がある質問です。ベクトル検索は「意味的に近い文書」を上位k件返すだけなので、複数の文書にまたがった関係を組み合わせて推論することができません。GraphRAGはエンティティ間の関係をグラフとして持っているので、こういうマルチホップの探索ができます。

それと、全体を俯瞰する要約型の質問もベクトルRAGは苦手です。「この文書群全体の主要なテーマは何か」みたいな質問ですね。上位k件しか見ないので、全体像を把握できないからです。GraphRAGはグラフのコミュニティ構造を分析することで、こういう大局的な質問にも答えられます。

一方で、GraphRAGのコストは無視できません。文書からエンティティと関係を抽出してグラフを構築する前処理に、大量のLLM呼び出しが必要です。初期構築コストがベクトルRAGとは桁違いになります。文書が更新されるたびに、グラフの再構築や部分更新も必要になります。

だから判断基準は明確です。「質問の型がマルチホップや全体俯瞰を必要とするか」。

「この規定では何日休めますか」みたいな、単一文書内で完結する質問が大半なら、ベクトルRAGで十分でGraphRAGはオーバースペックです。両者は排他じゃないので、ベースはベクトルRAGで作って、関係性の推論が必要な特定の用途にだけGraphRAGを組み合わせる。このハイブリッドも現実的な選択肢だと考えています。

**🇰🇷 답변**

벡터 RAG는 의미가 비슷한 문장을 찾는 데는 잘 맞는데, 문서 사이의 복잡한 관계를 잡아내는 건 약합니다. GraphRAG는 엔티티의 관계를 그래프 DB로 만들어서 참조하니까, LLM이 더 추론적이고 정확한 답을 만들 수 있습니다.

구체적으로 벡터 RAG가 약한 질문 유형을 들면 이해가 쉬울 것 같습니다.

"A사랑 거래하는 기업 중에 B기술 쓰는 회사는?" 같은, 여러 홉, 그러니까 관계의 연쇄를 따라가야 하는 질문입니다. 벡터 검색은 "의미적으로 가까운 문서"를 상위 k건 돌려줄 뿐이라서, 여러 문서에 걸친 관계를 조합해서 추론할 수가 없습니다. GraphRAG는 엔티티 사이의 관계를 그래프로 들고 있으니까 이런 멀티홉 탐색이 됩니다.

그리고 전체를 조망하는 요약형 질문도 벡터 RAG는 약합니다. "이 문서 전체의 주요 테마가 뭐냐" 같은 질문이요. 상위 k건만 보니까 전체 그림을 못 잡거든요. GraphRAG는 그래프의 커뮤니티 구조를 분석해서 이런 큰 그림 질문에도 답할 수 있습니다.

한편 GraphRAG의 비용은 무시 못 합니다. 문서에서 엔티티랑 관계를 뽑아서 그래프를 만드는 전처리에 LLM 호출이 엄청 많이 필요합니다. 초기 구축 비용이 벡터 RAG랑은 자릿수가 다릅니다. 문서가 갱신될 때마다 그래프 재구축이나 부분 갱신도 필요해집니다.

그래서 판단 기준은 명확합니다. "질문 유형이 멀티홉이나 전체 조망을 필요로 하는가".

"이 규정에서는 며칠 쉴 수 있나요" 같은, 문서 하나 안에서 끝나는 질문이 대부분이면 벡터 RAG로 충분하고 GraphRAG는 오버스펙입니다. 둘은 배타적이지 않으니까, 베이스는 벡터 RAG로 만들고 관계 추론이 필요한 특정 용도에만 GraphRAG를 붙이는 하이브리드도 현실적인 선택지라고 생각합니다.

### Q164. LLM回答をSSEでストリーミングする利点【Q56の再出題・実装編】
(LLM 답변을 SSE로 스트리밍하는 이점 【Q56 재출제 · 구현편】)

> ⚠️ Q56(AI 추론 레이턴시 대책)에서 SSE를 대책 중 하나로 들었습니다. 여기서는 왜 SSE인가, WebFlux로 어떻게 구현하는가 하는 기술 선정 측면을 묻고 있습니다.

**🇯🇵 回答**

LLMは文章生成に数秒から数十秒かかります。同期通信だとユーザーが離脱してしまいます。SSEを使って、生成されたトークンから順にフロントエンドへ流す。これで体感のレスポンス時間を劇的に短縮できて、UXが向上します。

ここで、なぜWebSocket、Q154ですね、じゃなくてSSEを選ぶのか。この技術選定の理由をお話ししたいと思います。

LLMのストリーミングは、サーバーからクライアントへの一方向の通信です。双方向通信は必要ありません。SSEはHTTPの上に構築されているので、既存のインフラ、ロードバランサーや認証やプロキシをそのまま使えます。切断時の自動再接続も、ブラウザのEventSource APIが標準で提供してくれます。

WebSocketは双方向が必要な場合には優れています。でもこの用途では、不必要な複雑さを持ち込むことになる。要件に対して最小限の技術を選ぶ、という判断です。

WebFluxを使う理由も明確です。従来のブロッキングモデル、Q12でお話ししたTomcatのスレッドプールですね。これだと数十秒かかるLLMの応答を待つ間、そのスレッドが占有され続けます。同時接続が増えるとスレッドプールが枯渇して、Q13でお話ししたのと同じスレッド枯渇の状態に陥ります。WebFluxのイベントループモデルなら、待機中にスレッドを解放できるので、少数のスレッドで大量の同時ストリーミング接続を扱えます。

なお、Q12でも触れた通り、Java 21の仮想スレッドを使えば、WebFluxみたいなリアクティブな書き方をしなくても同じようなスループットが得られる。この選択肢も現在はあります。既存コードがブロッキングスタイルで書かれているなら、こちらの方が移行コストが低いという判断もあり得ると考えています。

**🇰🇷 답변**

LLM은 문장 생성에 몇 초에서 몇십 초가 걸립니다. 동기 통신이면 사용자가 나가버립니다. SSE를 써서 생성된 토큰부터 순서대로 프론트엔드로 흘려보냅니다. 이러면 체감 응답 시간이 확 줄어들고 UX가 좋아집니다.

여기서 왜 WebSocket, Q154요, 그게 아니라 SSE를 고르는가. 이 기술 선정 이유를 말씀드리고 싶습니다.

LLM 스트리밍은 서버에서 클라이언트로 가는 단방향 통신입니다. 양방향 통신은 필요 없습니다. SSE는 HTTP 위에 만들어져 있어서 기존 인프라, 로드밸런서나 인증이나 프록시를 그대로 씁니다. 끊겼을 때 자동 재접속도 브라우저의 EventSource API가 표준으로 해줍니다.

WebSocket은 양방향이 필요할 때는 훌륭합니다. 그런데 이 용도에서는 필요 없는 복잡함을 끌고 들어오게 됩니다. 요건에 맞는 최소한의 기술을 고른다는 판단입니다.

WebFlux를 쓰는 이유도 명확합니다. 기존의 블로킹 모델, Q12에서 말씀드린 Tomcat 스레드 풀이요. 이러면 몇십 초 걸리는 LLM 응답을 기다리는 동안 그 스레드가 계속 잡혀 있습니다. 동시 접속이 늘면 스레드 풀이 말라서 Q13에서 말씀드린 것과 같은 스레드 고갈 상태가 됩니다. WebFlux의 이벤트 루프 모델이면 기다리는 동안 스레드를 놓을 수 있으니까, 적은 스레드로 많은 동시 스트리밍 접속을 다룰 수 있습니다.

덧붙이면, Q12에서도 언급한 대로 Java 21의 가상 스레드를 쓰면 WebFlux 같은 리액티브 작성법 없이도 비슷한 처리량을 낼 수 있습니다. 이 선택지도 지금은 있습니다. 기존 코드가 블로킹 스타일로 쓰여 있으면 이쪽이 이행 비용이 낮다는 판단도 가능하다고 생각합니다.

### Q165. 公共機関から民間Web企業への適応
(공공기관에서 민간 웹 기업으로의 적응)

**🇯🇵 回答**

公共機関での期間は、決して技術の停滞ではありませんでした。無停止・無欠損を保証する、堅牢なアーキテクチャの鍛錬の期間でした。この絶対にシステムを落とさないインフラ設計のノウハウは、トラフィックが激しいWeb企業でこそ輝くと確信しています。アジャイルな開発サイクルにも、これまでのサービス立ち上げなどで培った経験で、すぐに適応できます。

この質問の裏にある面接官の本当の懸念は何か。「スピード感の違いに戸惑わないか」「変化を受け入れられるか」だと理解しています。だから公共機関での経験を弁明するんじゃなくて、その経験が民間で具体的にどう活きるかを翻訳して示す。これが答えの核心です。

具体的には二つの資産があります。

一つ目は「落ちないシステム」への設計感覚です。Q144でお話ししたDesign for Failureの発想は、可用性が絶対条件の環境で長く働くことで、身体に染み込んだものです。急成長するWebサービスほど、成長のどこかの段階で必ず安定性の問題に直面します。だからこの感覚は移行先でも価値を持つと考えています。

二つ目が、大量データを扱う際の物理的な感覚です。Q159でお話しした通り、これは製品や環境を問わず通用する普遍的な力です。

同時に、正直に認めるべきこともあります。リリース頻度やA/Bテストみたいに、速く小さく試す文化。ここにはキャッチアップが必要な部分があるという自覚は持っています。

ただ、これは学習可能な領域です。Q150でお話しした通り、私は新しい環境への適応を短期間でやってきた実績があります。適応が必要な部分を隠さず認めた上で、それが学習可能であることと、逆に自分が持ち込める資産を明確に示す。この構成が、この質問への一番誠実な答え方だと考えています。

**🇰🇷 답변**

공공기관에서 보낸 기간은 절대로 기술의 정체가 아니었습니다. 무중단·무손실을 보장하는 견고한 아키텍처를 단련한 기간이었습니다. 이 절대로 시스템을 안 죽이는 인프라 설계 노하우는, 트래픽이 거센 웹 기업에서 오히려 더 빛날 거라고 확신합니다. 애자일한 개발 사이클에도 지금까지 서비스 런칭 같은 데서 쌓은 경험으로 금방 적응할 수 있습니다.

이 질문 뒤에 있는 면접관의 진짜 걱정이 뭘까요. "속도감 차이에 당황하지 않을까", "변화를 받아들일 수 있을까"라고 이해합니다. 그래서 공공기관 경험을 변명하는 게 아니라, 그 경험이 민간에서 구체적으로 어떻게 살아나는지를 번역해서 보여드립니다. 이게 답변의 핵심입니다.

구체적으로는 두 가지 자산이 있습니다.

첫째는 "안 죽는 시스템"에 대한 설계 감각입니다. Q144에서 말씀드린 Design for Failure의 발상은, 가용성이 절대 조건인 환경에서 오래 일하면서 몸에 밴 겁니다. 급성장하는 웹 서비스일수록 성장의 어느 단계에서는 반드시 안정성 문제에 부딪힙니다. 그래서 이 감각은 옮겨간 곳에서도 가치가 있다고 생각합니다.

둘째가 대량 데이터를 다룰 때의 물리적인 감각입니다. Q159에서 말씀드린 대로, 이건 제품이나 환경 상관없이 통하는 보편적인 힘입니다.

동시에 솔직히 인정해야 할 것도 있습니다. 릴리스 빈도나 A/B 테스트처럼 빠르고 작게 시도하는 문화. 여기는 캐치업이 필요한 부분이 있다는 자각을 갖고 있습니다.

다만 이건 학습 가능한 영역입니다. Q150에서 말씀드린 대로 저는 새 환경에 단기간에 적응해온 실적이 있습니다. 적응이 필요한 부분을 숨기지 않고 인정한 다음에, 그게 학습 가능하다는 것과 반대로 제가 가져올 수 있는 자산을 명확히 보여드린다. 이 구성이 이 질문에 대한 제일 성실한 답변 방식이라고 생각합니다.

### Q166. 外国人として日本のエンジニアチームとコミュニケーションを取る戦略
(외국인으로서 일본 엔지니어 팀과 커뮤니케이션하는 전략)

**🇯🇵 回答**

技術という世界共通の言語を最大限に活用します。抽象的な日本語での議論が難航したら、UML、シーケンス図、あるいは簡潔な擬似コードをホワイトボードに書いて視覚的に共有します。論理的で丁寧なドキュメンテーション能力で、言語の壁を越えた信頼を築きます。

これに加えて、私が特に意識しているのが「認識のズレを早期に確認する習慣」です。

日本語での議論では、私が理解したつもりの内容と、相手の意図が微妙にずれている可能性が常にあります。だから重要な決定事項については必ず、「私の理解では〜ということですが、認識は合っていますでしょうか」と、自分の言葉で言い直して確認します。

これは言語の問題を超えて、Q88でお話ししたチーム間の認識合わせの手法としても有効です。日本人同士でも起きる曖昧さの解消に役立ちます。

もう一つ、非同期のコミュニケーションを積極的に活用するという戦略もあります。

会議の場での即座の反応が求められる場面より、Slackやドキュメントでの文章によるやり取りの方が、私は正確に意図を伝えられます。議論の前に自分の考えを文書としてまとめて共有しておけば、会議では認識合わせだけで済みます。そうすれば言語のハンデが議論の質に影響しにくくなる。これはQ88でお話しした「同期コミュニケーションは意思決定のためだけに使う」という原則とも一致します。

そして、日本語能力の向上は継続的に努力すべき自分の責任だと考えています。言語の壁を技術力でカバーするという発想に留まらず、業務で必要な水準の日本語を身につけることも、チームへの敬意の一つの形だと捉えています。

**🇰🇷 답변**

기술이라는 세계 공통의 언어를 최대한 활용합니다. 추상적인 일본어 논의가 막히면, UML이나 시퀀스 다이어그램, 아니면 간결한 의사 코드를 화이트보드에 그려서 시각적으로 공유합니다. 논리적이고 꼼꼼한 문서화 능력으로 언어의 벽을 넘는 신뢰를 쌓겠습니다.

여기에 더해서 제가 특히 신경 쓰는 게 "인식 차이를 일찍 확인하는 습관"입니다.

일본어로 하는 논의에서는, 제가 이해했다고 생각한 내용이랑 상대의 의도가 미묘하게 어긋날 가능성이 항상 있습니다. 그래서 중요한 결정 사항은 반드시 "제 이해로는 ~라는 건데, 인식이 맞습니까"라고 제 말로 다시 말해서 확인합니다.

이건 언어 문제를 넘어서, Q88에서 말씀드린 팀 간 인식 맞추기 기법으로도 유효합니다. 일본인끼리도 생기는 애매함을 푸는 데 도움이 됩니다.

하나 더, 비동기 커뮤니케이션을 적극적으로 쓴다는 전략도 있습니다.

회의 자리에서 즉각 반응해야 하는 상황보다, Slack이나 문서로 글을 주고받는 쪽이 제가 의도를 정확히 전달할 수 있습니다. 논의하기 전에 제 생각을 문서로 정리해서 공유해두면, 회의에서는 인식 맞추기만 하면 됩니다. 그러면 언어 핸디캡이 논의의 질에 영향을 덜 미치게 됩니다. 이건 Q88에서 말씀드린 "동기 커뮤니케이션은 의사결정에만 쓴다"는 원칙이랑도 맞습니다.

그리고 일본어 능력 향상은 계속 노력해야 할 제 책임이라고 생각합니다. 언어의 벽을 기술력으로 메운다는 발상에만 머물지 않고, 업무에 필요한 수준의 일본어를 익히는 것도 팀에 대한 경의의 한 형태라고 봅니다.

### Q167. 非現実的なスケジュールを要求された場合
(비현실적인 일정을 요구받은 경우)

**🇯🇵 回答**

「できません」と即答するんじゃなくて、要件を優先順位で分割します。「期日通りに出すには、機能AとBのコア機能だけをローンチして、機能Cはフェーズ2に回すプランであれば可能です」というふうに、選択権を経営陣に提示するアプローチを取ります。

これはQ23・Q118でお話しした「選択肢とコストの形で返す」という原則の、一番厳しい場面での適用です。

ここで一点強調したいのが、削るのは「機能」であって「品質」ではない、という線引きです。

スケジュールを守るためにテストを省略する、セキュリティ対応を後回しにする。こういう品質の妥協を提案するのは、短期的には期日を守れても、中長期でもっと大きな代償を払うことになります。Q117でお話しした通り、妥協するのは可逆的な部分だけ。不可逆な部分、スキーマ、APIの契約、セキュリティは守り抜きます。

もう一つ重要なのが、見積もりの根拠を示すことです。「無理です」じゃなくて、「この機能はこれだけ工数がかかって、これらの依存関係があるので、この期日では物理的にこの範囲までです」と、判断の材料を提示する。数字と根拠があれば、経営側も感情じゃなくて事実として受け止められます。

そして、リスクを明示的に共有して記録に残すことも忘れません。

仮に経営判断として「それでも全機能を期日通りに」と決まった場合。Q134でお話ししたDisagree and Commitの姿勢で全力を尽くします。でもその際に「この条件では品質面でこういうリスクがある」という懸念を、ADRやメールとして記録しておきます。

これは責任逃れのためじゃありません。実際にリスクが表に出たときに素早く対処するため、そして次回の見積もりの精度を上げるための材料にするためです。

**🇰🇷 답변**

"안 됩니다"라고 바로 답하는 게 아니라, 요건을 우선순위로 쪼갭니다. "기일 안에 내려면 기능 A랑 B의 핵심만 런칭하고, 기능 C는 페이즈 2로 미루는 플랜이면 가능합니다"라는 식으로, 선택권을 경영진한테 드리는 접근을 취합니다.

이건 Q23·Q118에서 말씀드린 "선택지랑 비용의 형태로 돌려준다"는 원칙을, 제일 혹독한 상황에 적용한 겁니다.

여기서 하나 강조하고 싶은 게, 깎는 건 "기능"이지 "품질"이 아니라는 선 긋기입니다.

일정을 지키려고 테스트를 생략한다, 보안 대응을 뒤로 미룬다. 이런 품질 타협을 제안하는 건, 단기적으로는 기일을 지켜도 중장기적으로 훨씬 큰 대가를 치르게 됩니다. Q117에서 말씀드린 대로 타협하는 건 되돌릴 수 있는 부분만. 못 되돌리는 부분, 스키마, API 계약, 보안은 끝까지 지킵니다.

또 하나 중요한 게 견적의 근거를 보여주는 겁니다. "무리입니다"가 아니라 "이 기능은 이만큼 공수가 들고 이런 의존 관계가 있어서, 이 기일로는 물리적으로 여기까지입니다"라고 판단 재료를 드립니다. 숫자랑 근거가 있으면 경영 쪽도 감정이 아니라 사실로 받아들일 수 있습니다.

그리고 리스크를 명시적으로 공유하고 기록에 남기는 것도 잊지 않습니다.

만약 경영 판단으로 "그래도 전 기능을 기일 안에"라고 정해지면. Q134에서 말씀드린 Disagree and Commit의 자세로 최선을 다합니다. 그런데 그때 "이 조건에서는 품질 면에서 이런 리스크가 있다"는 우려를 ADR이나 메일로 기록해둡니다.

이건 책임을 피하려는 게 아닙니다. 실제로 리스크가 터졌을 때 빨리 대처하려고, 그리고 다음 견적의 정확도를 높이는 재료로 쓰려고입니다.

### Q168. コードレビューでのスタイル論争の解決【Q21・Q22の再出題】
(코드 리뷰에서의 스타일 논쟁 해결 【Q21·Q22 재출제】)

> ⚠️ Q21(팀 개발에서 신경 쓰는 것)에서 이미 "기계적인 건 사람이 리뷰하지 않는다"고 말했습니다. 여기서는 논쟁이 실제로 벌어진 상황에서의 해결을 묻고 있습니다.

**🇯🇵 回答**

人間がレビューでスタイルを指摘するのは時間の無駄です。LintツールをCIパイプラインに強制導入して、機械的なフォーマットチェックは自動化します。チームのレビュー時間は、アーキテクチャやセキュリティの議論みたいな、より高次元な活動にだけ集中させます。

ここで重要なのは、論争を「どちらが正しいか」で決着させないことです。

タブとスペース、あるいは特定の命名規則。どちらが優れているかには客観的な正解がありません。だから議論を続けても収束しません。Q9でお話しした「事実で決着する問題か、好みの問題か」の切り分けで言えば、これは典型的な好みの問題です。

だから私が取るアプローチは、「決め方を決める」ことです。

具体的には、言語やフレームワークのコミュニティで最も広く使われている標準スタイルを、そのまま採用することを提案します。JavaならGoogle Java Style、Prettierのデフォルトなどですね。

「我々のチームの好み」じゃなくて「外部の既成事実」を基準にする。そうすれば、誰の意見が通ったかという感情的な問題を避けられます。そして一度決めたらLinterとFormatterで機械的に強制して、以後この議論に時間を使わないことをチームで合意します。

Q9でお話しした「可逆的な決定は速く決めて進む」という原則が、ここに直接適用されます。スタイル規約は完全に可逆的な決定です。だから完璧な合意を目指して時間を溶かすより、標準に従って早く決めて、本質的な議論に時間を回す。その方がチーム全体の利益になります。

**🇰🇷 답변**

사람이 리뷰에서 스타일을 지적하는 건 시간 낭비입니다. Lint 도구를 CI 파이프라인에 강제로 넣어서 기계적인 포맷 체크는 자동화합니다. 팀의 리뷰 시간은 아키텍처나 보안 논의 같은, 더 높은 차원의 활동에만 쏟게 합니다.

여기서 중요한 건 논쟁을 "어느 쪽이 옳은가"로 끝내지 않는 겁니다.

탭이냐 스페이스냐, 아니면 특정 명명 규칙. 어느 쪽이 더 낫냐에는 객관적인 정답이 없습니다. 그래서 논의를 계속해도 수렴이 안 됩니다. Q9에서 말씀드린 "사실로 결론 나는 문제냐, 취향의 문제냐"로 나눠보면 이건 전형적인 취향의 문제입니다.

그래서 제가 쓰는 접근은 "정하는 방법을 정한다"입니다.

구체적으로는 언어나 프레임워크 커뮤니티에서 제일 널리 쓰이는 표준 스타일을 그대로 채택하자고 제안합니다. Java면 Google Java Style, Prettier의 기본값 같은 거요.

"우리 팀의 취향"이 아니라 "바깥의 기성 사실"을 기준으로 삼습니다. 그러면 누구 의견이 관철됐느냐 하는 감정적인 문제를 피할 수 있습니다. 그리고 한번 정하면 Linter랑 Formatter로 기계적으로 강제하고, 앞으로 이 논의에는 시간 안 쓰기로 팀에서 합의합니다.

Q9에서 말씀드린 "되돌릴 수 있는 결정은 빨리 정하고 나아간다"는 원칙이 여기 바로 적용됩니다. 스타일 규약은 완전히 되돌릴 수 있는 결정입니다. 그러니까 완벽한 합의를 노리며 시간을 녹이는 것보다, 표준을 따라서 빨리 정하고 본질적인 논의에 시간을 돌리는 게 팀 전체한테 이득입니다.

### Q169. バーンアウトを防ぐタスク管理【Q21・Q86の再出題】
(번아웃을 막는 태스크 관리 【Q21·Q86 재출제】)

> ⚠️ Q21·Q86에서 "속인화 해소"를 다뤘습니다. 여기서는 속인화가 번아웃으로 바로 이어진다는 인과가 초점입니다.

**🇯🇵 回答**

バス係数を上げないことです。特定のシニアにだけ難易度の高いタスクやオンコールを集中させない。ペアプログラミングなどを通じて若手にも知識を分散させて、属人化を防いで、全員が休める体制を作ります。

属人化がバーンアウトを生む構造を、具体的に言います。

「その人しか対応できない」状態は、その人が休暇中でも深夜でも呼ばれることを意味します。障害が起きるたびに同じ人が呼ばれて、その人は常に緊張状態に置かれる。そして皮肉なことに、忙しすぎて知識を共有する時間が取れないので、属人化がさらに深刻になる。この悪循環に陥ります。

だからこれは「その人の頑張り」の問題じゃありません。Q85・Q86でお話ししたのと同じく、構造の問題として扱う必要があります。

具体的な対策として三つ実施しています。

第一にオンコールのローテーション。対応可能な人を意図的に増やして、当番制にします。これを可能にするには、Q71でお話しした可観測性の整備と、ランブック、手順書の充実が前提になります。

第二に、難易度の高いタスクを意図的に若手とペアで進めること。短期的には速度が落ちますけど、中期的には対応可能な人が増えます。

第三に、深夜対応が発生した場合は翌日の勤務を調整するという運用ルールです。

そして、シニア自身が休む姿を見せることも重要だと考えています。リーダーが休まないチームでは、メンバーも休みづらくなります。Q90でお話しした心理的安全性と同じく、これも自分の行動で示すべきことだと捉えています。

**🇰🇷 답변**

버스 팩터를 안 올리는 겁니다. 특정 시니어한테만 난이도 높은 태스크나 온콜을 몰아주지 않습니다. 페어 프로그래밍 같은 걸로 주니어한테도 지식을 나눠서, 속인화를 막고 다 같이 쉴 수 있는 체제를 만듭니다.

속인화가 번아웃을 만드는 구조를 구체적으로 말씀드리겠습니다.

"그 사람만 대응할 수 있는" 상태는, 그 사람이 휴가 중이든 새벽이든 불려간다는 뜻입니다. 장애가 날 때마다 같은 사람이 불려가고, 그 사람은 늘 긴장 상태에 놓입니다. 그리고 아이러니하게도, 너무 바빠서 지식을 나눌 시간을 못 냅니다. 그래서 속인화가 더 심해집니다. 이 악순환에 빠집니다.

그러니까 이건 "그 사람의 노력" 문제가 아닙니다. Q85·Q86에서 말씀드린 것과 마찬가지로 구조의 문제로 다뤄야 합니다.

구체적인 대책으로 세 가지를 하고 있습니다.

첫째는 온콜 로테이션. 대응할 수 있는 사람을 일부러 늘려서 당번제로 만듭니다. 이게 가능하려면 Q71에서 말씀드린 관측 가능성 정비랑 런북, 그러니까 절차서가 잘 갖춰져 있어야 합니다.

둘째는 난이도 높은 태스크를 일부러 주니어랑 페어로 진행하는 것. 단기적으로는 속도가 떨어지지만 중기적으로는 대응 가능한 사람이 늘어납니다.

셋째는 새벽 대응이 생기면 다음 날 근무를 조정하는 운영 룰입니다.

그리고 시니어 본인이 쉬는 모습을 보여주는 것도 중요하다고 생각합니다. 리더가 안 쉬는 팀에서는 멤버도 쉬기가 어려워집니다. Q90에서 말씀드린 심리적 안전성이랑 마찬가지로, 이것도 제 행동으로 보여줘야 할 일이라고 봅니다.
