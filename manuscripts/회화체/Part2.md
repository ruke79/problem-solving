# 1. 백엔드 프레임워크 및 보안 심층 검증

### Q16. HikariCPの maxLifetime を設定する際、データベース側の設定とどう連動させるべきですか？
(maxLifetime을 DB 측 설정과 어떻게 연동해야 하는가)

**🇯🇵 回答**

原則は一つです。`maxLifetime` は、DB側やインフラ側が強制的にコネクションを切る時間より必ず短くします。MySQLなら `wait_timeout` ですね。あと間にNLBやファイアウォールがあるなら、そのアイドルタイムアウトも一緒に見ます。

なぜかというと、DBが先に切ったコネクションを、プールが「まだ生きている」と思って掴み続けてしまうからです。そうすると、次にそれを借りたリクエストが、原因の分かりにくい通信エラーで落ちます。しかもこのエラー、特定のリクエストだけ、再現性もなく出るんですよ。調査コストが本当に高いです。だからアプリ側から先に、能動的に捨てるという発想が大事になります。

具体的な数字で言うと、`wait_timeout` より数十秒から数分短く取ります。たとえばDB側が10分なら、`maxLifetime` は8〜9分くらいですね。HikariCPは内部でmaxLifetimeに数%のばらつきを持たせてくれるので、全コネクションが同時に破棄されるのは自動で避けてくれます。そこは任せて大丈夫です。

注意点が一つあります。DBがマネージドサービスの場合、プロキシ層やロードバランサーが独自にアイドルタイムアウトを持っていることがあります。DBの設定だけ見て安心せずに、経路上で一番短いタイムアウトを基準にするのが安全です。

**🇰🇷 답변**

원칙은 하나입니다. `maxLifetime`은 DB 쪽이나 인프라 쪽이 강제로 커넥션을 끊는 시간보다 반드시 짧게 잡습니다. MySQL이면 `wait_timeout`이고요. 그리고 중간에 NLB나 방화벽이 있으면 그 아이들 타임아웃도 같이 봅니다.

왜냐면 DB가 먼저 끊은 커넥션을 풀이 "아직 살아 있다"고 생각하고 계속 잡고 있게 되거든요. 그러면 다음에 그걸 빌린 요청이 원인 파악이 어려운 통신 에러로 죽습니다. 게다가 이 에러가 특정 요청에서만, 재현성도 없이 나옵니다. 조사 비용이 정말 큽니다. 그래서 앱 쪽에서 먼저 능동적으로 버린다는 발상이 중요해집니다.

구체적인 숫자로 말씀드리면, `wait_timeout`보다 수십 초에서 수 분 정도 짧게 잡습니다. 예를 들어 DB 쪽이 10분이면 `maxLifetime`은 8~9분 정도요. HikariCP가 내부적으로 maxLifetime에 몇 % 편차를 줘서 모든 커넥션이 동시에 폐기되는 건 알아서 피해 줍니다. 그 부분은 맡겨도 됩니다.

주의할 점이 하나 있습니다. DB가 매니지드 서비스인 경우, 프록시 계층이나 로드밸런서가 자기만의 아이들 타임아웃을 갖고 있는 경우가 있습니다. DB 설정만 보고 안심하지 말고, 경로상에서 제일 짧은 타임아웃을 기준으로 삼는 게 안전합니다.

### Q17. ファイアウォール経由でTCPセッションが切断される環境において、コネクションプールを安定させる設定は？
(방화벽 경유로 TCP 세션이 끊기는 환경에서 커넥션 풀 안정화 설정)

**🇯🇵 回答**

このケースで効くのは `keepaliveTime` です。デフォルトが0、つまり無効になっているので、明示的に有効化する必要があります。

有効にすると何が起きるか。HikariCPがアイドル状態のコネクションに対して、定期的に軽い検証クエリを投げてくれます。すると経路上のファイアウォールやNATから見て「使われている接続」として扱われるので、アイドルタイムアウトによる無言の切断を防げます。値は30秒から60秒、つまり30000〜60000msあたりですね。あと設定上、`keepaliveTime` は `maxLifetime` より小さくないと意味がないので、そこは必ずセットで確認します。

ただ、これは対症療法でもあるんですよね。根本的には、ファイアウォールのアイドルタイムアウトより短い `maxLifetime` を設定して、そもそも長時間アイドルなコネクションを持たない構成にするのが本筋です。私は両方入れる派で、`maxLifetime` で寿命を管理して、`keepaliveTime` で経路の死活を維持する、という形にしています。

加えて、切断されたコネクションを掴んでしまった場合の保険として、`connectionTestQuery` ではなくJDBC4の `isValid()` による検証に任せて、`validationTimeout` も短く設定しておきます。

**🇰🇷 답변**

이 케이스에서 효과적인 건 `keepaliveTime`입니다. 기본값이 0, 그러니까 비활성이라서 명시적으로 켜 줘야 합니다.

켜면 어떻게 되냐면요. HikariCP가 아이들 상태인 커넥션에 주기적으로 가벼운 검증 쿼리를 던져 줍니다. 그러면 경로상의 방화벽이나 NAT 입장에서 "쓰이고 있는 연결"로 취급되니까, 아이들 타임아웃으로 인한 조용한 절단을 막을 수 있습니다. 값은 30초에서 60초, 그러니까 30000~60000ms 정도입니다. 그리고 설정상 `keepaliveTime`은 `maxLifetime`보다 작아야 의미가 있으니, 거기는 꼭 세트로 확인합니다.

그런데 이건 대증요법이기도 합니다. 근본적으로는 방화벽 아이들 타임아웃보다 짧은 `maxLifetime`을 설정해서, 애초에 오랫동안 놀고 있는 커넥션을 안 갖는 구성이 정석이에요. 저는 둘 다 넣는 쪽인데요, `maxLifetime`으로 수명을 관리하고 `keepaliveTime`으로 경로의 사활을 유지하는 형태로 씁니다.

거기에 끊긴 커넥션을 잡아 버렸을 때의 보험으로, `connectionTestQuery`가 아니라 JDBC4의 `isValid()` 검증에 맡기고 `validationTimeout`도 짧게 설정해 둡니다.

### Q18. コネクションリークが発生していると疑われる場合、Spring Bootでどのように検出・調査しますか？
(커넥션 누수 탐지 및 조사 방법)

**🇯🇵 回答**

まず `leakDetectionThreshold` を設定します。たとえば20秒に設定すると、その時間を超えて返却されないコネクションについて、それを借りた時点のスタックトレースを警告ログに出してくれます。これが決定的なんですよね。「どのメソッドが返していないか」が一発で分かります。本番でも常時入れておいて問題ないくらい軽いです。

並行して、ActuatorとMicrometerで `hikaricp.connections.active` と `pending` を監視します。リークの典型的な兆候は、負荷が下がってもactiveが減らずに、階段状に増えていくパターンです。単なる負荷不足なら負荷と一緒に上下しますから、そこで見分けがつきます。

原因として実際に多いのは三つです。一つ目は `DataSource` から直接コネクションを取得して try-with-resources を使っていない箇所。二つ目は `@Transactional` の中で外部API呼び出しをしていて、相手が遅いとその間ずっとコネクションを握り続けているケース。これは厳密にはリークじゃなくて「長時間占有」なんですが、症状は同じです。三つ目はOpen Session In Viewが有効なままで、ビューのレンダリングまでコネクションを保持しているケースですね。

対策としては、トランザクション境界からI/O待ちを外に出すこと、そして `@Transactional` の付与範囲をレビュー項目に入れることを提案します。

**🇰🇷 답변**

먼저 `leakDetectionThreshold`를 설정합니다. 예를 들어 20초로 설정하면, 그 시간을 넘겨서 반환되지 않은 커넥션에 대해 그걸 빌린 시점의 스택 트레이스를 경고 로그로 남겨 줍니다. 이게 결정적이에요. "어느 메서드가 반환을 안 하는지"를 한 번에 알 수 있습니다. 프로덕션에서도 상시 켜 둬도 될 만큼 가볍고요.

병행해서 Actuator랑 Micrometer로 `hikaricp.connections.active`와 `pending`을 모니터링합니다. 누수의 전형적인 징후는, 부하가 내려가도 active가 안 줄고 계단식으로 늘어나는 패턴입니다. 단순 부하 부족이면 부하랑 같이 오르내리니까 거기서 구분이 됩니다.

원인으로 실제로 많은 건 세 가지입니다. 첫째, `DataSource`에서 직접 커넥션을 얻으면서 try-with-resources를 안 쓴 부분. 둘째, `@Transactional` 안에서 외부 API를 호출해서, 상대가 느리면 그동안 계속 커넥션을 쥐고 있는 케이스. 이건 엄밀히는 누수가 아니라 "장시간 점유"인데 증상은 똑같습니다. 셋째, Open Session In View가 켜진 채로 뷰 렌더링까지 커넥션을 유지하는 케이스고요.

대책으로는 트랜잭션 경계에서 I/O 대기를 밖으로 빼는 것, 그리고 `@Transactional` 붙이는 범위를 리뷰 항목에 넣는 걸 제안합니다.

### Q19. Webセキュリティ（XSS, CSRF）の攻撃タイプと防御方法をアーキテクチャの観点でどう実装しますか？
(XSS/CSRF 공격 타입과 아키텍처 관점의 방어 구현)

**🇯🇵 回答**

まず、この二つは原因が違うので、対策も分けて考えます。

XSSは、攻撃者のスクリプトが自分のサイトのオリジンで実行されてしまう問題です。防御の基本は、入力時のバリデーションじゃなくて、出力時のコンテキストに応じたエスケープです。HTML本文なのか、属性値なのか、JavaScriptの中なのか、URLの中なのかで、エスケープの規則が違うんですよ。なのでここは自前で実装せず、ThymeleafやReactの自動エスケープに任せます。危ないのは `th:utext` や `dangerouslySetInnerHTML` を使うところなので、リッチテキストを扱う場合はサーバー側でDOMPurifyやOWASP Java HTML Sanitizerを通して、ホワイトリスト方式で許可タグだけ残します。多層防御としてCSPヘッダーを設定して、インラインスクリプトを禁止します。

CSRFは原因が違います。ユーザーの認証済みCookieが、攻撃者のサイトからのリクエストにも自動で送られてしまうことが原因です。対策はSynchronizer Tokenパターンで、サーバーが発行したトークンをリクエストに含めさせて検証します。Spring Securityならデフォルトで有効です。加えてCookieに `SameSite=Lax` を付けると、クロスサイトからの自動送信そのものを止められます。

アーキテクチャの判断として一点付け加えます。Cookie認証をやめてAuthorizationヘッダーのBearerトークンにすれば、CSRFはほぼ構造的に消えます。ただ、トークンをlocalStorageに置くとXSSで即座に盗まれるので、リスクがXSSに移るだけなんですよね。私はリフレッシュトークンはhttpOnly Cookieに置いて、アクセストークンはメモリ保持、という構成を採ることが多いです。どちらの脅威を重く見るかを決めて設計する、というのが本質だと思っています。

**🇰🇷 답변**

먼저, 이 둘은 원인이 다르니까 대책도 나눠서 생각합니다.

XSS는 공격자의 스크립트가 자기 사이트의 오리진에서 실행돼 버리는 문제입니다. 방어의 기본은 입력 시 검증이 아니라, 출력 시 컨텍스트에 맞는 이스케이프입니다. HTML 본문이냐, 속성값이냐, JavaScript 안이냐, URL 안이냐에 따라 이스케이프 규칙이 다르거든요. 그래서 여기는 직접 구현하지 않고 Thymeleaf나 React의 자동 이스케이프에 맡깁니다. 위험한 건 `th:utext`나 `dangerouslySetInnerHTML`을 쓰는 부분이라, 리치 텍스트를 다룰 때는 서버 쪽에서 DOMPurify나 OWASP Java HTML Sanitizer를 통해 화이트리스트 방식으로 허용 태그만 남깁니다. 다층 방어로 CSP 헤더를 설정해서 인라인 스크립트를 금지하고요.

CSRF는 원인이 다릅니다. 사용자의 인증된 쿠키가 공격자 사이트에서 온 요청에도 자동으로 실려 간다는 게 원인입니다. 대책은 Synchronizer Token 패턴으로, 서버가 발급한 토큰을 요청에 포함시켜서 검증합니다. Spring Security는 기본으로 켜져 있습니다. 여기에 쿠키에 `SameSite=Lax`를 붙이면 크로스 사이트에서의 자동 전송 자체를 막을 수 있습니다.

아키텍처 판단으로 한 가지 덧붙이겠습니다. 쿠키 인증을 버리고 Authorization 헤더의 Bearer 토큰으로 가면 CSRF는 구조적으로 거의 사라집니다. 다만 토큰을 localStorage에 두면 XSS로 즉시 탈취되니까, 리스크가 XSS로 옮겨갈 뿐이에요. 저는 리프레시 토큰은 httpOnly 쿠키에 두고 액세스 토큰은 메모리에 보관하는 구성을 자주 씁니다. 어느 위협을 더 무겁게 볼지를 정하고 설계하는 게 본질이라고 생각합니다.

### Q20. HTTP/HTTPSの違いとSSL/TLSハンドシェイクプロセスを説明してください。
(HTTP/HTTPS의 차이와 TLS 핸드셰이크)

**🇯🇵 回答**

HTTPは平文の通信なので、経路上で盗聴も改ざんもできてしまいます。HTTPSはHTTPの下にTLS層を挟んで、三つのことを提供します。通信内容の暗号化、改ざんの検知、そしてサーバーが本物であることの認証ですね。

ハンドシェイクの流れは、TLS 1.2だとこうなります。まずクライアントがClientHelloで、対応している暗号スイートとランダム値を送ります。サーバーがServerHelloで使う暗号スイートを決めて、証明書を返します。クライアントは証明書チェーンをルートCAまで検証して、ドメイン名や有効期限も確認します。その後ECDHEで鍵交換のパラメータをやり取りして、双方が同じ共通鍵、つまりセッションキーを導き出します。最後にFinishedを交換して、以降は対称鍵で高速に通信する、という流れです。

ポイントは二つあります。一つは、公開鍵暗号は重いので鍵交換にだけ使って、実データは対称鍵で暗号化するというハイブリッド構成になっていること。もう一つは、ECDHEを使うことで前方秘匿性が得られることです。つまりサーバーの秘密鍵が後から漏れても、過去の通信は復号できない、ということですね。

TLS 1.3ではこの往復が1-RTTに短縮されて、レジューム時は0-RTTも可能になりました。運用面では、TLSはLBやリバースプロキシで終端して証明書管理を一箇所に集約する、HSTSヘッダーで平文へのダウングレードを防ぐ、証明書は自動更新にしておく。これが基本の構成になります。

**🇰🇷 답변**

HTTP는 평문 통신이라서 경로상에서 도청도 변조도 가능합니다. HTTPS는 HTTP 아래에 TLS 계층을 끼워서 세 가지를 제공합니다. 통신 내용의 암호화, 변조 탐지, 그리고 서버가 진짜라는 인증입니다.

핸드셰이크 흐름은 TLS 1.2 기준으로 이렇습니다. 먼저 클라이언트가 ClientHello로 지원하는 암호 스위트랑 랜덤값을 보냅니다. 서버가 ServerHello로 쓸 암호 스위트를 정하고 인증서를 반환합니다. 클라이언트는 인증서 체인을 루트 CA까지 검증하고, 도메인명이랑 유효기간도 확인합니다. 그다음 ECDHE로 키 교환 파라미터를 주고받아서 양쪽이 같은 공통 키, 그러니까 세션 키를 뽑아냅니다. 마지막에 Finished를 교환하고, 그 뒤로는 대칭키로 빠르게 통신하는 흐름입니다.

포인트는 두 가지입니다. 하나는 공개키 암호가 무거우니까 키 교환에만 쓰고, 실제 데이터는 대칭키로 암호화하는 하이브리드 구성이라는 것. 다른 하나는 ECDHE를 쓰면 전방 비밀성이 확보된다는 겁니다. 서버 비밀키가 나중에 유출돼도 과거 통신은 복호화할 수 없다는 얘기죠.

TLS 1.3에서는 이 왕복이 1-RTT로 줄었고, 재개할 때는 0-RTT도 가능해졌습니다. 운영 면에서는 TLS를 LB나 리버스 프록시에서 종단시켜서 인증서 관리를 한 곳에 모으고, HSTS 헤더로 평문 다운그레이드를 막고, 인증서는 자동 갱신으로 해 둔다. 이게 기본 구성입니다.

# 2. 리더십, 협업 및 문제 해결

### Q21. チーム開発で気をつけていることは何ですか？
(팀 개발에서 주의하는 점)

**🇯🇵 回答**

自分一人のアウトプットより、チーム全体のスループットを上げること。これを意識しています。具体的には三つあります。

一つ目は、属人化を作らないことです。特定の機能を私しか触れない状態って、短期的には速いんですけど、組織としてはリスクなんですよね。なので設計判断は背景と却下案まで含めてADRとして残して、レビューを通して必ず二人以上が理解している状態を保ちます。

二つ目は、機械的なことは人間がレビューしないことです。フォーマットとか命名規則の指摘に人のレビュー時間を使うのは、もったいないです。FormatterとLinterをCIで強制します。レビューは設計と仕様の議論に集中させたいので。

三つ目は、PRを小さく保つことです。1000行のPRって、実質レビューされないんですよ。機能単位で分割して、レビュー待ちで止まらない状態を作ります。

指標としては、新しくジョインしたメンバーが初回のPRを出すまでの時間を見ています。ここが長いチームは、ドキュメントか環境構築か、どこかが壊れているサインだと思っています。

**🇰🇷 답변**

제 개인의 아웃풋보다 팀 전체의 스루풋을 올리는 것. 이걸 의식합니다. 구체적으로 세 가지가 있습니다.

첫째, 속인화를 만들지 않는 것입니다. 특정 기능을 저만 만질 수 있는 상태는 단기적으로는 빠른데, 조직으로 보면 리스크거든요. 그래서 설계 판단은 배경이랑 기각안까지 포함해서 ADR로 남기고, 리뷰를 통해서 반드시 두 명 이상이 이해하고 있는 상태를 유지합니다.

둘째, 기계적인 건 사람이 리뷰하지 않는 것입니다. 포맷이나 명명 규칙 지적에 사람의 리뷰 시간을 쓰는 건 아깝습니다. Formatter랑 Linter를 CI로 강제합니다. 리뷰는 설계랑 스펙 논의에 집중시키고 싶어서요.

셋째, PR을 작게 유지하는 것입니다. 1000줄짜리 PR은 실질적으로 리뷰가 안 됩니다. 기능 단위로 나눠서 리뷰 대기로 멈추지 않는 상태를 만듭니다.

지표로는 새로 합류한 멤버가 첫 PR을 낼 때까지의 시간을 봅니다. 여기가 긴 팀은 문서든 환경 구축이든 어딘가 깨져 있다는 신호라고 생각합니다.

### Q22. コードレビューにおいて、あなたが最も重視しているポイントは何ですか？
(코드 리뷰에서 가장 중시하는 포인트)

**🇯🇵 回答**

一番重視しているのは、「後から変更するコストが高い部分」に集中することです。

変数名は後でいくらでも直せます。でもレイヤー間の依存方向とか、ドメインモデルの責務分割、DBスキーマは、後から直すのがものすごく高いんですよ。だからそこに時間を使います。

次に、テストが正常系だけじゃなくて、境界値と異常系を押さえているかを見ます。実装コードよりテストコードのほうを注意深く読むこともあります。あとは外部呼び出しにタイムアウトが設定されているか、トランザクション境界が適切か、N+1が発生していないか。この辺りは、レビューでしか見つからない種類の指摘ですね。

伝え方も同じくらい重要だと思っています。私は指摘に必ずラベルを付けます。`must` は直してほしい、`imo` は提案、`nits` は好みなので無視していい。これがないと、ジュニアは全部を「命令」として受け取って萎縮してしまいます。それから「なぜこう書いたのか」を先に質問します。私が知らない制約がある場合が実際にあるので。

そして最後に、レビューの速さも品質だと考えています。24時間以上放置されたPRって、レビューの精度自体が落ちるんですよ。あとは設計レビューを実装前に入れて、実装後に「そもそも設計から違う」という一番残酷な指摘をしなくて済むようにしています。

**🇰🇷 답변**

제일 중시하는 건 "나중에 바꾸는 비용이 높은 부분"에 집중하는 겁니다.

변수명은 나중에 얼마든지 고칠 수 있습니다. 그런데 레이어 간 의존 방향이나 도메인 모델의 책임 분리, DB 스키마는 나중에 고치는 게 엄청나게 비싸거든요. 그래서 거기에 시간을 씁니다.

다음으로 테스트가 정상 케이스만이 아니라 경계값이랑 예외 케이스를 잡고 있는지를 봅니다. 구현 코드보다 테스트 코드를 더 주의 깊게 읽는 경우도 있습니다. 그리고 외부 호출에 타임아웃이 설정돼 있는지, 트랜잭션 경계가 적절한지, N+1이 발생하지 않는지. 이런 건 리뷰에서만 발견되는 종류의 지적입니다.

전달하는 방식도 그만큼 중요하다고 생각합니다. 저는 지적에 반드시 라벨을 붙입니다. `must`는 고쳐 달라, `imo`는 제안, `nits`는 취향이니까 무시해도 된다. 이게 없으면 주니어는 전부를 "명령"으로 받아들여서 위축됩니다. 그리고 "왜 이렇게 썼는지"를 먼저 물어봅니다. 제가 모르는 제약이 있는 경우가 실제로 있거든요.

마지막으로 리뷰의 속도도 품질이라고 봅니다. 24시간 넘게 방치된 PR은 리뷰 정확도 자체가 떨어져요. 그리고 설계 리뷰를 구현 전에 넣어서, 구현 후에 "애초에 설계부터 틀렸다"는 제일 잔인한 지적을 안 해도 되게 합니다.

### Q23. 非エンジニア部門（ビジネス側）と要件を調整する際、合意形成を図るために工夫していることは？
(비엔지니어 부문과의 요건 조정 및 합의 형성)

**🇯🇵 回答**

一番意識しているのは、「できません」で終わらせないことです。必ず選択肢とコストの形で返します。

たとえば「リアルタイムで集計を出したい」という要望に対して、技術的に難しいと説明しても話は進まないんですよね。そうじゃなくて、「完全なリアルタイムなら追加でこれくらいの工数とインフラコストがかかります。5分遅れを許容していただければ、既存構成のまま1スプリントで出せます」という形で並べます。判断材料を渡せば、ビジネス側は自分たちで優先順位を決められますから。決定権はビジネス側にある、という前提を崩さないのが大事だと思っています。

もう一つは、要望の背景にある目的を必ず聞くことです。「この画面にこのボタンが欲しい」の裏に「解約率を下げたい」という目的があるなら、ボタンより効果的な手段を提案できることがあります。言われた通りに作るのって、実は不親切な場合があるんですよ。

技術的負債の話をするときも同じです。「コードが汚い」じゃなくて「今のままだと機能追加のリードタイムが毎回2週間伸びます」と、ビジネスの言葉に翻訳します。あとは認識のズレを文字で埋めるより、簡単なモックや画面キャプチャを1枚見せるほうが圧倒的に速いので、早い段階で形を見せることを心がけています。

**🇰🇷 답변**

제일 의식하는 건 "안 됩니다"로 끝내지 않는 것입니다. 반드시 선택지랑 비용의 형태로 돌려줍니다.

예를 들어 "실시간으로 집계를 보고 싶다"는 요구에 기술적으로 어렵다고 설명해도 얘기가 안 나아가거든요. 그게 아니라 "완전한 실시간이면 추가로 이 정도 공수랑 인프라 비용이 듭니다. 5분 지연을 허용해 주시면 기존 구성 그대로 1스프린트에 낼 수 있습니다"라는 식으로 늘어놓습니다. 판단 재료를 드리면 비즈니스 쪽에서 스스로 우선순위를 정할 수 있으니까요. 결정권은 비즈니스 쪽에 있다는 전제를 안 무너뜨리는 게 중요하다고 생각합니다.

또 하나는 요구 뒤에 있는 목적을 반드시 물어보는 것입니다. "이 화면에 이 버튼을 원한다"의 뒤에 "해지율을 낮추고 싶다"는 목적이 있다면, 버튼보다 효과적인 수단을 제안할 수 있는 경우가 있습니다. 말한 대로 만드는 게 사실은 불친절한 경우가 있어요.

기술 부채 얘기를 할 때도 똑같습니다. "코드가 더럽다"가 아니라 "지금 이대로면 기능 추가 리드타임이 매번 2주 늘어납니다"라고 비즈니스 언어로 번역합니다. 그리고 인식 차이를 글로 메우는 것보다 간단한 목업이나 화면 캡처 한 장을 보여주는 게 압도적으로 빠르니까, 이른 단계에 형태를 보여주는 걸 신경 씁니다.

### Q24. 次世代のリーダーや若手エンジニアの育成において、どのようなメンタリングを行ってきましたか？
(젊은 엔지니어 육성 및 멘토링 경험)

**🇯🇵 回答**

方針としては、答えを渡さずに、答えにたどり着く道筋を渡すこと。これを意識しています。

具体的には、質問が来たときに即答しないようにしています。「今どこまで調べた?」「そのログはどう読んだ?」と聞いて、本人の中にある仮説を言葉にしてもらいます。デバッグの仕方そのものを渡さないと、次も同じ質問が来ますから。ただ、本人が詰まって時間だけ溶けている状態は避けたいので、事前に「30分調べて分からなければ必ず聞いて」というルールを決めておきます。

タスクの与え方は段階的にします。最初は仕様が明確で影響範囲が小さいもの。次に設計判断が含まれるもの。その次に他チームとの調整が必要なもの、というふうに広げていきます。特に意識しているのは、可逆的な失敗はさせるということです。ロールバックできる範囲での失敗って、一番学習効率が高いんですよ。逆に不可逆な部分は必ず私がレビューに入ります。

1on1では、目の前のタスクの話だけじゃなくて、本人が何をやりたいのかを聞くようにしています。インフラに興味がある人にひたすら画面実装を振っていても伸びませんから。育成というより、本人の目標とチームの必要が重なる場所を探す作業だと捉えています。

**🇰🇷 답변**

방침으로는, 답을 주지 않고 답에 도달하는 경로를 주는 것. 이걸 의식합니다.

구체적으로는 질문이 왔을 때 바로 답하지 않으려고 합니다. "지금 어디까지 조사했어요?", "그 로그는 어떻게 읽었어요?"라고 물어서 본인 안에 있는 가설을 말로 꺼내게 합니다. 디버깅하는 방법 자체를 주지 않으면 다음에도 같은 질문이 오거든요. 다만 본인이 막혀서 시간만 녹는 상태는 피하고 싶어서, 미리 "30분 조사해서 모르겠으면 반드시 물어보라"는 룰을 정해 둡니다.

태스크를 주는 방식은 단계적으로 합니다. 처음에는 스펙이 명확하고 영향 범위가 작은 것. 다음은 설계 판단이 포함된 것. 그다음은 타 팀과의 조정이 필요한 것, 이런 식으로 넓혀 갑니다. 특히 의식하는 건 되돌릴 수 있는 실패는 하게 한다는 겁니다. 롤백 가능한 범위의 실패는 학습 효율이 제일 높거든요. 반대로 되돌릴 수 없는 부분은 반드시 제가 리뷰에 들어갑니다.

1on1에서는 눈앞의 태스크 얘기만이 아니라 본인이 뭘 하고 싶은지를 물어봅니다. 인프라에 관심 있는 사람한테 계속 화면 구현만 던져도 안 크니까요. 육성이라기보다는 본인의 목표랑 팀의 필요가 겹치는 지점을 찾는 작업이라고 봅니다.

# 3. 커리어 비전 및 가치관

### Q25. コーディング試験や課題について、さらに質を上げるにはどのように改善しますか？
(제출 과제를 더 개선한다면?)

> 💡 이 질문의 핵심은 "제약을 인지하고 있었는가"입니다. 몰라서 안 한 게 아니라, 판단해서 안 했다는 걸 보여주면 됩니다.

**🇯🇵 回答**

今回は課題の時間制約とスコープを考えて、意図的に入れなかった部分がいくつかあります。実プロダクションを想定するなら、優先順位を付けてこの順で改善します。

まず一番効果が大きいのは、可観測性です。現状はログが素のテキストなので、構造化ログにしてリクエストIDを通して、主要な処理のレイテンシをメトリクスとして出せるようにします。障害のときに原因が追えないシステムって、機能が正しくても運用できないんですよね。

次に耐障害性です。外部呼び出しに明示的なタイムアウトとリトライを入れます。リトライが前提になるので、登録系のエンドポイントは冪等キーで重複実行を防ぐようにします。

三つ目がパフォーマンスです。今回はインメモリのMapでキャッシュしていますが、複数インスタンス構成を想定するとRedisに寄せる必要があります。あわせて、参照系のクエリにEXPLAINをかけてインデックスを見直します。

最後にテストです。現状は単体テストが中心なので、Testcontainersを使って実DBに対する結合テストを足したいですね。特にトランザクション境界の挙動って、モックでは検証できないので。

**🇰🇷 답변**

이번에는 과제의 시간 제약이랑 스코프를 고려해서 의도적으로 안 넣은 부분이 몇 가지 있습니다. 실제 프로덕션을 상정한다면 우선순위를 매겨서 이 순서로 개선하겠습니다.

먼저 제일 효과가 큰 건 관측 가능성입니다. 지금은 로그가 평문 텍스트라서, 구조화 로그로 바꾸고 요청 ID를 관통시켜서 주요 처리의 레이턴시를 메트릭으로 낼 수 있게 합니다. 장애 났을 때 원인을 못 쫓는 시스템은 기능이 맞아도 운영을 못 하거든요.

다음은 내장애성입니다. 외부 호출에 명시적인 타임아웃이랑 재시도를 넣습니다. 재시도가 전제가 되니까, 등록 계열 엔드포인트는 멱등 키로 중복 실행을 막게 합니다.

세 번째가 성능입니다. 이번엔 인메모리 Map으로 캐시했는데, 다중 인스턴스 구성을 상정하면 Redis로 옮길 필요가 있습니다. 같이 조회 계열 쿼리에 EXPLAIN을 걸어서 인덱스를 다시 봅니다.

마지막이 테스트입니다. 지금은 단위 테스트 중심이라, Testcontainers로 실제 DB에 대한 통합 테스트를 추가하고 싶습니다. 특히 트랜잭션 경계 동작은 목으로는 검증이 안 되니까요.

### Q26. エンジニアとして、3年後、5年後にどのようなキャリアビジョンを描いていますか？
(3년 후, 5년 후 커리어 비전)

**🇯🇵 回答**

3年後の目標は、システム全体の設計に責任を持てるテックリードとして機能している状態です。具体的には、機能単位の実装だけじゃなくて、非機能要件、つまり可用性やコスト、運用性まで含めてアーキテクチャの判断ができること。そしてその判断をチームやビジネス側に説明して、合意を取れる立場ですね。そのためには御社のドメイン知識を早く吸収する必要があると考えています。

5年後は、そこにデータとAIの領域を重ねたいと思っています。私はこれまで、大量データを安全に流すインフラの部分を主に担当してきました。これからは、その基盤の上でAI活用が実際にビジネス価値を出すところまで繋げられるエンジニアが必要になると思っていて、そこに自分の強みを置きたいんです。派手なモデルを作る側じゃなくて、それを本番で安定して動かし続ける側の専門性ですね。

キャリアパスとしては、マネジメント専任よりも、技術で意思決定しながらチームを引っ張るアーキテクト寄りを志向しています。ただ、育成やチームビルディングも自分の役割だと思っているので、そこは切り離さずにやっていきたいです。

**🇰🇷 답변**

3년 후 목표는 시스템 전체 설계에 책임질 수 있는 테크 리드로 기능하는 상태입니다. 구체적으로는 기능 단위 구현만이 아니라 비기능 요건, 그러니까 가용성이나 비용, 운영성까지 포함해서 아키텍처 판단을 할 수 있는 것. 그리고 그 판단을 팀이랑 비즈니스 쪽에 설명해서 합의를 얻을 수 있는 위치입니다. 그러려면 귀사의 도메인 지식을 빨리 흡수해야 한다고 생각합니다.

5년 후에는 거기에 데이터랑 AI 영역을 겹치고 싶습니다. 저는 지금까지 대량 데이터를 안전하게 흘려보내는 인프라 쪽을 주로 담당해 왔습니다. 앞으로는 그 기반 위에서 AI 활용이 실제로 비즈니스 가치를 내는 지점까지 연결할 수 있는 엔지니어가 필요해질 거라고 보고 있고, 거기에 제 강점을 두고 싶습니다. 화려한 모델을 만드는 쪽이 아니라, 그걸 프로덕션에서 안정적으로 계속 돌리는 쪽의 전문성이요.

커리어 패스로는 매니지먼트 전임보다는, 기술로 의사결정하면서 팀을 이끄는 아키텍트 쪽을 지향합니다. 다만 육성이나 팀 빌딩도 제 역할이라고 생각하니까, 그건 떼어 놓지 않고 같이 해 나가고 싶습니다.

### Q27. 普段、どのように最新の技術をキャッチアップしていますか？最近読んだ技術書は？
(기술 캐치업 방법 / 최근 읽은 기술서)

> ⚠️ 책 제목을 말하면 **반드시** 내용 질문이 따라옵니다. 실제로 읽은 책만 말하세요.

**🇯🇵 回答**

情報源は意識的に階層を分けています。

日々のインプットは、公式ドキュメントとリリースノートを一次情報として見ます。Spring Bootみたいに使っているフレームワークは、マイナーバージョンのリリースノートまで追います。ブレイキングチェンジや非推奨化を後から知ると、移行コストが跳ね上がるので。そのうえで各社のエンジニアブログやカンファレンスの登壇資料を見て、他社が実際にどう運用しているかを補います。

ただ、記事を読むだけでは身につかないんですよね。なので気になった技術は必ず小さく手元で動かします。最近だとProtobufとSchema RegistryをKafkaと組み合わせた構成を、個人のSpring Bootプロジェクトで実際に組んでみて、スキーマの互換性チェックがどう効くかを確認しました。ビルドツールとの相性で詰まった部分も含めて、動かさないと分からないことが多いなと実感しました。

書籍は、流行より原理を扱うものを選んでいます。最近は『データ指向アプリケーションデザイン』を読み返しました。選んだ理由は、分散システムで整合性と可用性のどちらを取るかという判断を、自分の言葉で説明できるようになりたかったからです。特にトランザクションの分離レベルの章は、実際にDockerでDBを立てて異常現象を再現しながら読みました。読んだだけだと分かった気になるだけなので。

**🇰🇷 답변**

정보원은 의식적으로 계층을 나눕니다.

일상적인 인풋은 공식 문서랑 릴리스 노트를 1차 정보로 봅니다. Spring Boot처럼 쓰고 있는 프레임워크는 마이너 버전 릴리스 노트까지 따라갑니다. 브레이킹 체인지나 deprecated를 나중에 알면 마이그레이션 비용이 확 뛰거든요. 그 위에서 각 회사의 엔지니어 블로그랑 콘퍼런스 발표 자료를 보면서 다른 회사가 실제로 어떻게 운영하는지를 보완합니다.

그런데 글만 읽어서는 안 익혀지더라고요. 그래서 관심 가는 기술은 반드시 작게 직접 돌려 봅니다. 최근에는 Protobuf랑 Schema Registry를 Kafka와 조합한 구성을 개인 Spring Boot 프로젝트에서 실제로 짜 보면서, 스키마 호환성 체크가 어떻게 동작하는지 확인했습니다. 빌드 툴이랑 궁합 문제로 막힌 부분까지 포함해서, 돌려 보지 않으면 모르는 게 많다는 걸 실감했습니다.

책은 유행보다 원리를 다루는 걸 고릅니다. 최근에는 『데이터 중심 애플리케이션 설계(DDIA)』를 다시 읽었습니다. 고른 이유는 분산 시스템에서 정합성이랑 가용성 중에 뭘 취할지에 대한 판단을 제 언어로 설명할 수 있게 되고 싶었기 때문입니다. 특히 트랜잭션 격리 수준 장은 실제로 Docker로 DB를 띄워서 이상 현상을 재현하면서 읽었습니다. 읽기만 하면 이해한 착각만 남으니까요.

### Q28. 현업 엔지니어 면접관 대상 (기술 과제 공감형)

**🇰🇷 번역**

"한 가지 여쭙고 싶은데요, 귀사의 기술 블로그를 보고 마이크로서비스로 전환을 진행하고 계신다고 이해했습니다. 지금 그 전환 과정에서 가장 병목이 되는 부분은 어디일까요? 서비스 간 데이터 정합성인지, 아니면 운영이랑 모니터링의 복잡화인지, 실제로 손을 움직이고 계신 입장에서의 이야기를 들을 수 있으면 감사하겠습니다."

## 부록: 역질문 시 금기 3가지

| 하지 말 것 | 이유 / 대안 |
|---|---|
| 「残業はどれくらいですか？」 (야근은 얼마나 하나요?) | 1차·2차 면접에서 묻지 마세요. 최종 면접이나 오퍼 면담에서 「チームの働き方について教えてください」(팀의 업무 방식을 알려주세요)로 우회 |
| 「特にありません」 (특별히 없습니다) | 의욕 없음으로 직결. 최소 3개는 준비하고, 앞에서 이미 답이 나왔으면 「先ほどご説明いただいたので大丈夫です」+ 새 질문 1개 |
| 조사하면 나오는 것 (사업 내용, 매출 등) | 사전 조사 안 했다는 증거. 반드시 「〜と理解しております。その上で〜」(~라고 이해하고 있습니다. 그 위에서~) 구조로 조사한 사실을 먼저 깔고 질문 |

## 부록: Part 1·2 공통 발화 요령

1. **결론 먼저** — 「〜と考えます」로 시작하고 근거를 뒤에 붙입니다.
2. **트레이드오프를 반드시 한 문장** — 「ただし〜というデメリットもあるので」가 시니어 판정 라인입니다.
3. **모르면 솔직하게 + 접근법** — 「実務では使ったことがありませんが、〜という理解です。もし導入するなら〜から検証します」가 아는 척보다 훨씬 높은 평가를 받습니다.
