### Q170. API Gateway vs Service Mesh

**🇯🇵** 「API Gatewayは、外部と内部の南北トラフィックを制御します。Service Meshは内部サービス間の東西トラフィック、それにmTLSの暗号化やトレーシングを、サイドカープロキシで制御します。**両者は代替関係ではなく補完関係です。外部からの入口はGateway、内部の網目状の通信はMeshが担当します。**」

**🇰🇷** API Gateway는 외부랑 내부 사이의 남북 트래픽을 제어합니다. Service Mesh는 내부 서비스 사이의 동서 트래픽이랑 mTLS, 트레이싱을 사이드카 프록시로 제어합니다. **둘은 대체 관계가 아니라 보완 관계입니다.** 외부에서 들어오는 입구는 Gateway가, 내부의 그물망 통신은 Mesh가 맡습니다. (→ Q35, Q36)

### Q171. Redis vs Memcached

**🇯🇵** 「Memcachedは単純な文字列キャッシュに特化したマルチスレッド型です。Redisはシングルスレッドですが、List、Set、Sorted Setみたいな多様なデータ構造と、永続化まで提供します。**選定基準は用途です。単純なキャッシュだけならMemcached。待機列やランキング、分散ロックみたいにデータ構造を活かした使い方があるならRedisです。**」

**🇰🇷** Memcached는 단순 문자열 캐시에 특화된 멀티스레드형입니다. Redis는 싱글스레드지만 List, Set, Sorted Set 같은 다양한 자료구조랑 영속화까지 제공합니다. **선정 기준은 용도입니다. 단순 캐시만이면 Memcached. 대기열이나 랭킹, 분산 락처럼 자료구조를 살릴 데가 있으면 Redis입니다.** (→ Q61, Q124, Q148)

### Q172. Elasticsearchの逆索引(Inverted Index)
(Elasticsearch의 역색인)

**🇯🇵** 「本の巻末の索引と同じ発想です。文書を単語単位に分解して、『どの単語がどの文書に入っているか』を逆向きにマッピングしておきます。**RDBMSのLIKE検索が全件スキャンになるのに対して(Q158)、逆索引は単語から文書を直接引けるので速いんです。**」

**🇰🇷** 책 뒤에 붙은 색인이랑 같은 발상입니다. 문서를 단어 단위로 쪼개서 "어느 단어가 어느 문서에 들어 있는지"를 거꾸로 매핑해둡니다. **RDBMS의 LIKE 검색이 풀 스캔이 되는 것과 달리(Q158), 역색인은 단어에서 문서를 바로 뽑을 수 있어서 빠릅니다.**

### Q173. Java 17/21 LTSへ移行する理由
(Java 17/21 LTS로 이행하는 이유)

**🇯🇵** 「Recordクラスで不変オブジェクトを簡潔に書けること。それとJava 21の仮想スレッドで、WebFluxみたいな複雑な非同期フレームワークなしに高スループットが得られる点です。**それに加えて、旧バージョンはセキュリティパッチの提供が終わります。だから移行は機能の話だけじゃなくて、リスク管理の問題でもあります。**」

**🇰🇷** Record 클래스로 불변 객체를 간결하게 쓸 수 있다는 것. 그리고 Java 21의 가상 스레드로, WebFlux 같은 복잡한 비동기 프레임워크 없이도 높은 처리량을 얻을 수 있다는 점입니다. **여기에 더해서, 구버전은 보안 패치 제공이 끝납니다. 그래서 이행은 기능 얘기만이 아니라 리스크 관리 문제이기도 합니다.** (→ Q12, Q93, Q164)

### Q174. コンテナ環境でのJVMメモリ設定の注意点
(컨테이너 환경에서의 JVM 메모리 설정 주의점)

**🇯🇵** 「昔のJVMはコンテナのメモリ制限を認識できませんでした。Host OSのメモリを基準にヒープを確保してOOMを起こしていたんです。今は `-XX:MaxRAMPercentage` で、コンテナに割り当てられたメモリの比率に応じて動的に調整します。**注意点は、JVMのメモリはヒープだけじゃないということです。メタスペースやスレッドスタックも消費するので、コンテナのlimitぎりぎりまでヒープを設定するとOOM Killerに殺されます。**」

**🇰🇷** 예전 JVM은 컨테이너 메모리 제한을 인식 못 했습니다. Host OS 메모리를 기준으로 힙을 잡아서 OOM을 냈어요. 지금은 `-XX:MaxRAMPercentage`로, 컨테이너에 할당된 메모리 비율에 맞춰서 동적으로 조정합니다. **주의점은 JVM 메모리가 힙만이 아니라는 겁니다. 메타스페이스랑 스레드 스택도 먹으니까, 컨테이너 limit 코앞까지 힙을 잡으면 OOM Killer한테 죽습니다.** (→ Q39, Q66)

### Q175. シャーディング適用時の最大の困難
(샤딩 적용 시의 가장 큰 어려움)

**🇯🇵** 「二つあります。違うシャード間のJOINができなくなって、アプリ側で結合しなきゃいけないこと。それと、特定のシャードにデータが偏ったときの、シャードキー再設計とデータ再分配が極めて苦痛なことです。**この再分配の苦しさこそが、Q65でお話しした「シャーディングは最後の手段」という判断の根拠そのものです。**」

**🇰🇷** 두 가지입니다. 다른 샤드끼리 JOIN이 안 돼서 앱에서 합쳐야 한다는 것. 그리고 특정 샤드에 데이터가 몰렸을 때, 샤드 키 재설계랑 데이터 재분배가 엄청나게 고통스럽다는 것. **이 재분배의 고통이야말로 Q65에서 말씀드린 "샤딩은 최후의 수단"이라는 판단의 근거 그 자체입니다.**

### Q176. CAP定理のCP/APの代表的DB
(CAP 정리의 CP/AP 대표 DB)

**🇯🇵** 「CP系がMongoDBとHBase、AP系がCassandraとDynamoDBです。**ただし実際には設定で変えられる部分があります。例えばCassandraも、書き込みと読み取りのConsistency Levelを上げれば一貫性寄りに調整できます。二値じゃなくてスペクトラムだ、という理解が正確です。**」

**🇰🇷** CP 계열이 MongoDB랑 HBase, AP 계열이 Cassandra랑 DynamoDB입니다. **다만 실제로는 설정으로 바꿀 수 있는 부분이 있습니다. 예를 들어 Cassandra도 쓰기랑 읽기의 Consistency Level을 올리면 일관성 쪽으로 조정할 수 있어요. 둘 중 하나가 아니라 스펙트럼이라는 이해가 정확합니다.** (→ Q37)

### Q177. Refresh Token Rotation

**🇯🇵** 「Refresh Tokenを1回限りにして、使うたびに新しいものを発行する手法です。**さらに重要なのは、無効化済みの古いトークンで再発行要求が来た場合です。それを盗難のシグナルとして検知して、そのユーザーの全セッションを強制的に無効化する。この再利用検知の仕組みがセットになって初めて意味を持ちます。**」

**🇰🇷** Refresh Token을 1회용으로 만들어서, 쓸 때마다 새걸 발급하는 기법입니다. **더 중요한 건, 이미 무효화된 옛날 토큰으로 재발급 요청이 왔을 때입니다. 그걸 탈취 신호로 잡아내서 그 사용자의 모든 세션을 강제로 무효화합니다. 이 재사용 탐지 장치가 세트로 붙어야 비로소 의미가 있습니다.** (→ Q101)

### Q178. Docker Image容量の最適化
(Docker 이미지 용량 최적화)

**🇯🇵** 「Multi-stage buildでビルドツールを除外して、実行に必要なランタイムだけを残します。**それに加えて、レイヤーの順序も効きます。変更頻度の低いもの、依存関係のインストールですね。これを先に置いて、頻度の高いアプリコードを後に置く。そうするとビルドキャッシュが効いて、CI時間も短縮できます。**」

**🇰🇷** Multi-stage build로 빌드 도구를 빼고, 실행에 필요한 런타임만 남깁니다. **거기에 더해서 레이어 순서도 영향이 큽니다. 변경 빈도가 낮은 것, 그러니까 의존성 설치요. 이걸 먼저 두고, 자주 바뀌는 앱 코드를 뒤에 둡니다. 그러면 빌드 캐시가 먹어서 CI 시간도 줄어듭니다.**

### Q179. S3への大容量データの高速アップロード
(S3로의 대용량 데이터 고속 업로드)

**🇯🇵** 「Multipart Uploadでファイルを分割して並列に転送します。**副次的な利点もあって、失敗した部分だけ再送すれば済むんです。大容量ファイルで一部が失敗しても、最初からやり直す必要がありません。**」

### Q180. Repeatable Readで発生しうる現象
(Repeatable Read에서 발생할 수 있는 현상)

**🇯🇵** 「Phantom Readです。他のトランザクションが新しいレコードを挿入して、結果の件数が変わる現象ですね。**ただしMySQLのInnoDBは、ギャップロックによってRepeatable Readでもファントムをほぼ防ぎます。DB製品によって挙動が違うので、標準の定義だけじゃなくて、使っているDBの実装を確認すべきです。**」

**🇰🇷** Phantom Read입니다. 다른 트랜잭션이 새 레코드를 넣어서 결과 건수가 바뀌는 현상이요. **다만 MySQL InnoDB는 갭 락으로 Repeatable Read에서도 팬텀을 거의 막습니다. DB 제품마다 동작이 다르니까, 표준 정의만 볼 게 아니라 지금 쓰는 DB의 구현을 확인해야 합니다.** (→ Q48)

### Q181. @Async使用時の注意点
(@Async 사용 시 주의점)

**🇯🇵** 「独自のExecutorを設定しないと、デフォルトのSimpleAsyncTaskExecutorが毎回スレッドを作って、システムが枯渇します。**もう一点あります。@Asyncも@Transactionalと同じくプロキシベースなので、同じクラス内の自己呼び出しでは効きません。Q98と全く同じ落とし穴です。**」

**🇰🇷** 자체 Executor를 설정 안 하면 기본 SimpleAsyncTaskExecutor가 매번 스레드를 만들어서 시스템이 고갈됩니다. **하나 더 있습니다. @Async도 @Transactional이랑 마찬가지로 프록시 기반이라, 같은 클래스 안에서 자기 자신을 호출하면 안 먹힙니다. Q98이랑 완전히 같은 함정입니다.**

### Q182. KafkaのExactly-Once用コンポーネント
(Kafka의 Exactly-Once용 컴포넌트)

**🇯🇵** 「トランザクショナルプロデューサーと、`isolation.level=read_committed` の設定です。**ただしQ100でお話しした通り、これが保証するのはKafkaクラスタの内部までです。外部DBへの反映は、自前の冪等設計が別途必要になります。**」

### Q183. MongoDBのスキーマ設計:正規化 vs 非正規化
(MongoDB 스키마 설계: 정규화 vs 비정규화)

**🇯🇵** 「読み取り性能のために非正規化して、関連データを一つのDocumentに埋め込むのが基本です。**ただし、埋め込んだ配列が無制限に増える設計は避けます。MongoDBには1ドキュメントのサイズ上限がありますし、埋め込みデータを更新すると全体の書き換えが発生するからです。**」

**🇰🇷** 읽기 성능을 위해서 비정규화하고, 관련 데이터를 하나의 Document에 임베딩하는 게 기본입니다. **다만 임베딩한 배열이 무제한으로 늘어나는 설계는 피합니다. MongoDB에는 도큐먼트 하나의 크기 상한이 있고, 임베딩한 데이터를 갱신하면 전체를 다시 쓰게 되니까요.** (→ Q49)

### Q184. GitOps(ArgoCD等)の利点
(GitOps(ArgoCD 등)의 이점)

**🇯🇵** 「あるべき状態をGitに宣言しておいて、クラスタ側がGitを監視して自動的に同期します。Pull型ですね。だから追跡性に優れます。**セキュリティ面での本質的な利点は、CIツールにクラスタへの認証情報を渡さなくて済むことです。Push型だとこれが必要になります。**」

### Q185. LLMのTemperatureパラメータ
(LLM의 Temperature 파라미터)

**🇯🇵** 「0に近いほど決定論的で一貫した回答になって、1に近いほど創造的で多様な回答になります。**実務では、RAGみたいに事実の正確さが求められる用途では0近辺に設定します。**」

### Q186. RAGのChunk Sizeが小さすぎる/大きすぎる場合
(RAG의 Chunk Size가 너무 작거나 너무 클 때)

**🇯🇵** 「小さすぎると文脈が失われます。大きすぎると無関係な内容が混ざって、ノイズとトークンコストが増えます。**この二律背反への解として、Q55でお話しした親子検索が有効です。検索は小さいチャンクで精度高く行って、LLMには大きい親単位を渡す、というやり方ですね。**」

**🇰🇷** 너무 작으면 문맥이 날아갑니다. 너무 크면 상관없는 내용이 섞여서 노이즈랑 토큰 비용이 늘어납니다. **이 딜레마의 해법으로 Q55에서 말씀드린 부모-자식 검색이 유효합니다. 검색은 작은 청크로 정확하게 하고, LLM한테는 큰 부모 단위를 넘기는 방식이요.**

### Q187. NodePort vs LoadBalancer

**🇯🇵** 「NodePortは全ノードの特定ポートを開けて外部アクセスを許可します。LoadBalancerはクラウドベンダーのLBをプロビジョニングします。**実務では、Serviceごとにクラウドのロードバランサーが作られてコストが膨らむのを避けるために、Ingressで一つのLBに集約する構成が一般的です。**」

**🇰🇷** NodePort는 모든 노드의 특정 포트를 열어서 외부 접근을 허용합니다. LoadBalancer는 클라우드 벤더의 LB를 프로비저닝합니다. **실무에서는 Service마다 클라우드 LB가 생겨서 비용이 불어나는 걸 피하려고, Ingress로 LB 하나에 모으는 구성이 일반적입니다.**

### Q188. Stream APIのmapとflatMap
(Stream API의 map과 flatMap)

**🇯🇵** 「mapは1要素を1要素に写像します。flatMapは1要素を複数要素に展開して、単一のストリームに平坦化します。**典型的な用途は、ネストしたコレクション、List of Listですね。これを単一のリストに展開する場合です。**」

**🇰🇷** map은 1요소를 1요소로 사상합니다. flatMap은 1요소를 여러 요소로 펼쳐서 하나의 스트림으로 평탄화합니다. **전형적인 용도는 중첩된 컬렉션, List of List요. 이걸 단일 리스트로 펼치는 경우입니다.**

### Q189. 複合インデックス(A, B)でBだけを条件にした場合
(복합 인덱스 (A, B)에서 B만 조건으로 걸었을 때)

**🇯🇵** 「インデックスが使えないか、非効率なIndex Skip Scanになります。常に先行列のAが条件に含まれている必要があります。**これはQ5でお話しした通り、B+Treeが先行列でソートされているからです。Aが不定だと木を辿れません。だから複合インデックスの列順は、実際のクエリの条件パターンから決めるべきなんです。**」

**🇰🇷** 인덱스를 못 타거나 비효율적인 Index Skip Scan이 됩니다. 항상 선행 컬럼인 A가 조건에 들어가 있어야 합니다. **이건 Q5에서 말씀드린 대로 B+Tree가 선행 컬럼으로 정렬돼 있기 때문입니다. A가 뭔지 모르면 트리를 못 탑니다. 그래서 복합 인덱스의 컬럼 순서는 실제 쿼리의 조건 패턴에서 정해야 합니다.**

### Q190. ジュニア時代と比べたコードへのマインドの変化
(주니어 때와 비교한 코드에 대한 마음가짐의 변화)

**🇯🇵** 「『とにかく動くように書く』から、『未来の同僚が読みやすくて、捨てやすいように書く』へ変わりました。**特に「捨てやすさ」を意識するようになったのが大きな変化です。要件は必ず変わります。だから完璧に作り込むより、変更や削除が容易な構造にする方が、長期的な価値が高いと考えるようになりました。**」

## Part 11 (Q170~200) 요점

**🇯🇵** 単答形式(Q170〜190)で差がつくのは、**定義の後に「ただし」で始まる一文を足せるか**です。@Asyncのプロキシ問題(Q181)、Repeatable Readのギャップロック(Q180)、CAP定理がスペクトラムであること(Q176)。どれも定義だけなら誰でも言えます。でもその先の一文が、実務経験を証明します。逆質問(Q191〜200)は、**質問の内容そのものより「その質問をするために何を調べて、何を考えてきたか」が評価対象**です。

**🇰🇷** 단답형(Q170~190)에서 차이가 나는 건 **정의 뒤에 "다만"으로 시작하는 한 문장을 붙일 수 있느냐**입니다. @Async의 프록시 문제(Q181), Repeatable Read의 갭 락(Q180), CAP 정리가 스펙트럼이라는 것(Q176). 전부 정의만이면 누구나 말할 수 있어요. 그런데 그 뒤의 한 문장이 실무 경험을 증명합니다. 역질문(Q191~200)은 **질문의 내용 자체보다 "그 질문을 하려고 뭘 조사하고 뭘 생각해 왔는가"가 평가 대상**입니다.
