# Part 4. 마이크로서비스 및 분산 아키텍처

### Q31. モノリスからMSAへ移行する際の最大の課題
(모놀리스에서 MSA로 전환할 때의 최대 과제)

**🇯🇵 回答**

技術的な最大の課題はデータ整合性です。モノリスなら一つのトランザクションでロールバックできたものが、サービスごとにDBが分かれた瞬間にできなくなります。

対応はSagaパターンでの補償トランザクションですが、見落とされがちなのがDB更新とイベント発行の原子性です。コミット直後にプロセスが落ちてイベントが飛ばない、という状態が起きます。なのでOutboxパターンで、イベントを同じトランザクション内でDBに書きます。

ただ、実際に移行を難しくするのは技術ではなく、サービス境界の切り方だと思っています。境界を間違えると、機能を一つ追加するのに三つのサービスを同時にデプロイすることになる。これが分散モノリスで、モノリスの結合度とMSAの運用コストを両方背負います。だから迷ったら大きめに切って、後から分割します。

あと、分散トレーシングがない状態で分けると障害時に原因が分からなくなるので、可観測性を先に整えることを条件にしています。

**🇰🇷 답변**

기술적인 최대 과제는 데이터 정합성입니다. 모놀리스라면 하나의 트랜잭션으로 롤백할 수 있던 게, 서비스별로 DB가 나뉘는 순간 안 되게 됩니다.

대응은 Saga 패턴의 보상 트랜잭션인데요, 놓치기 쉬운 게 DB 갱신과 이벤트 발행의 원자성입니다. 커밋 직후에 프로세스가 죽어서 이벤트가 안 날아가는 상태가 생깁니다. 그래서 Outbox 패턴으로 이벤트를 같은 트랜잭션 안에서 DB에 씁니다.

다만 실제로 전환을 어렵게 만드는 건 기술이 아니라 서비스 경계를 나누는 방식이라고 생각합니다. 경계를 잘못 잡으면 기능 하나 추가하는 데 세 개 서비스를 동시에 배포하게 됩니다. 이게 분산 모놀리스인데, 모놀리스의 결합도와 MSA의 운영 비용을 둘 다 짊어집니다. 그래서 애매하면 크게 잘라 놓고 나중에 분할합니다.

그리고 분산 트레이싱이 없는 상태로 나누면 장애 때 어디서 실패했는지 모르게 되니까, 관측 가능성을 먼저 갖추는 걸 조건으로 겁니다.

### Q32. サービス間通信 REST vs gRPC の使い分け
(서비스 간 통신 REST vs gRPC 구분)

**🇯🇵 回答**

外部公開やフロントエンドとの通信はREST、内部のサービス間はgRPC。これを基本にします。

RESTを外部に使う理由は、ブラウザからそのまま叩けること、HTTPキャッシュが効くこと、そしてデバッグとドキュメントのエコシステムが豊富なことです。外部の開発者にバイナリプロトコルを強いるのは障壁が高すぎますから。

内部にgRPCを使う理由は、ペイロードが小さいこと、HTTP/2の多重化で接続を使い回せること、そしてスキーマからコードが生成されるので破壊的変更をビルド時に検出できることです。実運用ではこの三つ目が一番効きます。

注意点として、gRPCはHTTP/2の長寿命接続を使うので、L4ロードバランサーだと最初に繋がったPodに固定されて負荷が偏ります。L7プロキシかクライアント側ロードバランシングが必要です。

そもそも同期RPCを使うか自体も先に検討します。即時性が要らないものはKafkaのイベント連携にしたほうが可用性は上がります。

**🇰🇷 답변**

외부 공개나 프론트엔드와의 통신은 REST, 내부 서비스 간은 gRPC. 이걸 기본으로 합니다.

REST를 외부에 쓰는 이유는 브라우저에서 바로 호출할 수 있다는 점, HTTP 캐시가 듣는다는 점, 그리고 디버깅과 문서화 생태계가 풍부하다는 점입니다. 외부 개발자에게 바이너리 프로토콜을 강요하는 건 장벽이 너무 높으니까요.

내부에 gRPC를 쓰는 이유는 페이로드가 작다는 점, HTTP/2 다중화로 접속을 재사용할 수 있다는 점, 그리고 스키마에서 코드가 생성되니까 파괴적 변경을 빌드 타임에 잡을 수 있다는 점입니다. 실운영에서는 이 세 번째가 제일 효과적입니다.

주의점으로, gRPC는 HTTP/2 장수명 접속을 쓰니까 L4 로드밸런서면 처음 연결된 Pod에 고정돼서 부하가 치우칩니다. L7 프록시나 클라이언트 사이드 로드밸런싱이 필요합니다.

애초에 동기 RPC를 쓸지 자체도 먼저 검토합니다. 즉시성이 필요 없는 건 Kafka 이벤트 연계로 하는 편이 가용성이 올라갑니다.

### Q33. 分散トレーシングとは
(분산 트레이싱이란)

**🇯🇵 回答**

一つのユーザーリクエストが複数のサービスを横断するときに、その全経路を一本の線として追跡する仕組みです。

入り口でリクエストにTrace IDを付けて、各サービスでの処理をSpanという単位で記録します。SpanにはID、親SpanのID、開始と終了の時刻が入るので、集めるとリクエスト全体の木構造とそれぞれの所要時間が復元できます。

肝はIDを次のサービスに引き継ぐ伝播の部分です。ここは自前で実装せず、W3C Trace Contextに従ってOpenTelemetryに任せます。

一番効くのは、「APIが遅い」という報告に対して、どのサービスの処理が何ミリ秒かかっているかを推測ではなく事実として出せることです。私はログにもTrace IDを必ず含めます。

運用上の論点はサンプリングです。全件保存はコストが現実的でないので数%に絞りますが、するとエラーのトレースが取れないことがある。可能ならエラーを優先して残すテールベースサンプリングを検討します。

**🇰🇷 답변**

하나의 사용자 요청이 여러 서비스를 횡단할 때, 그 전체 경로를 하나의 선으로 추적하는 장치입니다.

입구에서 요청에 Trace ID를 붙이고, 각 서비스에서의 처리를 Span이라는 단위로 기록합니다. Span에는 ID, 부모 Span의 ID, 시작과 종료 시각이 들어가니까, 모으면 요청 전체의 트리 구조와 각각의 소요 시간이 복원됩니다.

핵심은 ID를 다음 서비스로 넘기는 전파 부분입니다. 여기는 직접 구현하지 않고 W3C Trace Context를 따라 OpenTelemetry에 맡깁니다.

제일 효과적인 건 "API가 느리다"는 보고에 대해 어느 서비스의 처리가 몇 밀리초 걸리는지를 추측이 아니라 사실로 낼 수 있다는 겁니다. 저는 로그에도 Trace ID를 반드시 넣습니다.

운영상의 논점은 샘플링입니다. 전건 저장은 비용이 비현실적이라 몇 %로 좁히는데, 그러면 에러의 트레이스를 못 잡는 경우가 생깁니다. 가능하면 에러를 우선해 남기는 테일 기반 샘플링을 검토합니다.

### Q34. サーキットブレーカーパターンの目的と動作原理
(서킷 브레이커 패턴의 목적과 동작 원리)

**🇯🇵 回答**

目的は障害の連鎖を止めることです。呼び先が落ちているのに呼び続けると、呼び元のスレッドがタイムアウト待ちで埋まって、無関係な機能まで巻き込んで停止します。

動作は三つの状態です。通常はCLOSEDで素通し。失敗率が閾値を超えるとOPENになります。このとき最低試行回数も条件に入れるのが重要です。これがないと最初の1回の失敗で遮断されるので。OPENの間は即座に失敗を返し、一定時間でHALF-OPENに移って数件だけ試し、回復していればCLOSEDに戻ります。

設計上の要点は、遮断したときに何を返すかです。エラーにするのではなく、キャッシュした古い値を返すといったフォールバックを業務側と決めておきます。

もう一つ、サーキットブレーカーは単独では機能しません。全ての外部呼び出しに適切なタイムアウトがあること、リトライに指数バックオフとジッターを入れること。タイムアウトなしのリトライは、落ちかけた相手にトドメを刺すだけなので。

**🇰🇷 답변**

목적은 장애의 연쇄를 멈추는 것입니다. 호출 대상이 죽었는데 계속 호출하면 호출자의 스레드가 타임아웃 대기로 꽉 차서, 무관한 기능까지 휘말려 정지합니다.

동작은 세 가지 상태입니다. 평소에는 CLOSED로 통과. 실패율이 임계치를 넘으면 OPEN이 됩니다. 이때 최소 시행 횟수도 조건에 넣는 게 중요합니다. 이게 없으면 첫 1회 실패로 차단되니까요. OPEN인 동안은 즉시 실패를 반환하고, 일정 시간 뒤 HALF-OPEN으로 옮겨 몇 건만 시도해 보고, 회복됐으면 CLOSED로 돌아갑니다.

설계상의 요점은 차단했을 때 뭘 반환하느냐입니다. 에러로 하는 게 아니라, 캐시한 오래된 값을 반환하는 식의 폴백을 업무 쪽과 정해 둡니다.

또 하나, 서킷 브레이커는 단독으로는 기능하지 않습니다. 모든 외부 호출에 적절한 타임아웃이 있을 것, 재시도에 지수 백오프와 지터를 넣을 것. 타임아웃 없는 재시도는 죽어가는 상대한테 확인사살하는 것뿐이라서요.

### Q35. ゼロトラストセキュリティとmTLS
(제로 트러스트 보안과 mTLS)

**🇯🇵 回答**

ゼロトラストは、「社内ネットワークの内側だから安全」という前提を捨てる考え方です。従来の境界防御は一箇所侵入されると横移動で全体が抜かれる。そこで「どのネットワークにいるか」ではなく「誰であるか」で毎回検証します。

その実装の中核がmTLSです。通常のTLSはクライアントがサーバーを検証する片方向ですが、mTLSはサーバーもクライアントの証明書を検証します。これで互いの身元を暗号的に証明でき、証明書を持たないプロセスは通信できなくなります。

実運用で難しいのは証明書のライフサイクル管理です。数十のサービスに配って短い有効期限で自動ローテーションする、これを自前で作るのは現実的ではないので、Istioのようなサービスメッシュでサイドカーに任せる構成が一般的です。

一点補足すると、mTLSは認証であって認可ではありません。「誰か」は証明できても「何をしてよいか」は別です。ここを混同すると、証明書さえあれば何でも呼べる状態になります。

**🇰🇷 답변**

제로 트러스트는 "사내 네트워크 안쪽이니까 안전하다"는 전제를 버리는 사고방식입니다. 기존의 경계 방어는 한 군데 뚫리면 횡이동으로 전체가 털립니다. 그래서 "어느 네트워크에 있는가"가 아니라 "누구인가"로 매번 검증합니다.

그 구현의 핵심이 mTLS입니다. 일반 TLS는 클라이언트가 서버를 검증하는 단방향인데, mTLS는 서버도 클라이언트의 인증서를 검증합니다. 이러면 서로의 신원을 암호학적으로 증명할 수 있고, 인증서가 없는 프로세스는 통신을 못 합니다.

실운영에서 어려운 건 인증서 라이프사이클 관리입니다. 수십 개 서비스에 배포하고 짧은 유효기간으로 자동 로테이션하는 걸 직접 만드는 건 비현실적이라, Istio 같은 서비스 메시로 사이드카에 맡기는 구성이 일반적입니다.

한 가지 보충하면, mTLS는 인증이지 인가가 아닙니다. "누구인가"는 증명해도 "뭘 해도 되는가"는 별개입니다. 여기를 혼동하면 인증서만 있으면 뭐든 호출 가능한 상태가 됩니다.

### Q36. APIゲートウェイの役割
(API 게이트웨이의 역할)

**🇯🇵 回答**

クライアントからの単一の入り口として、全リクエストを受けて適切なサービスにルーティングする層です。

ここに集約するのは横断的関心事です。認証トークンの検証、レート制限、TLS終端、共通のログとメトリクス。全サービスが必要とするけれど、ビジネスロジックではないものをまとめます。認証ロジックが十数のサービスに散らばって仕様がずれる、という事故を防げます。

注意点が二つあります。一つ目は、ゲートウェイが単一障害点になること。冗長化と性能余裕は必ず確保します。

二つ目、こちらが重要なんですが、ゲートウェイにビジネスロジックを入れないことです。ここに条件分岐を書き始めると、全サービスがゲートウェイのデプロイに依存して分散モノリスに戻ります。入れていいのは「全サービス共通で、ドメイン知識を必要としない処理」だけ。この線引きを最初に決めます。

クライアントごとの最適化が要る場合は、別にBFF層を置きます。

**🇰🇷 답변**

클라이언트로부터의 단일 진입점으로서, 모든 요청을 받아 적절한 서비스로 라우팅하는 계층입니다.

여기에 모으는 건 횡단 관심사입니다. 인증 토큰 검증, 레이트 리밋, TLS 종단, 공통 로그와 메트릭. 모든 서비스가 필요로 하지만 비즈니스 로직은 아닌 것들을 모읍니다. 인증 로직이 십수 개 서비스에 흩어져서 스펙이 어긋나는 사고를 막을 수 있고요.

주의점이 두 가지 있습니다. 첫째, 게이트웨이가 단일 장애점이 된다는 것. 이중화와 성능 여유는 반드시 확보합니다.

둘째, 이쪽이 중요한데요, 게이트웨이에 비즈니스 로직을 안 넣는 겁니다. 여기에 조건 분기를 쓰기 시작하면 모든 서비스가 게이트웨이 배포에 의존해서 분산 모놀리스로 돌아갑니다. 넣어도 되는 건 "모든 서비스 공통이고 도메인 지식이 필요 없는 처리"뿐. 이 선을 처음에 정합니다.

클라이언트별 최적화가 필요하면 별도로 BFF 계층을 둡니다.

### Q37. 分散システムにおける結果整合性
(분산 시스템의 결과적 일관성)

**🇯🇵 回答**

更新が全ノードに即座に反映されるわけではないけれど、時間が経てば最終的に同じ状態に収束する。そういう一貫性モデルです。

なぜこれを選ぶかというと、CAP定理の帰結です。ネットワーク分断は必ず起きるという前提に立つと、強一貫性を保つには分断中に応答を止めるしかない。可用性を優先するなら、一時的な不整合を許容する選択になります。

設計で重要なのは、どこまでの遅延なら業務が成立するかを事前に決めることです。在庫表示が数秒古いのは許容できても、決済の残高は許容できませんよね。全システムを一律にはせず、ドメインごとに判断します。

実装では三つ入れます。冪等性。バージョン番号による古い更新の排除。そしてユーザー体験の考慮です。自分が投稿した直後に一覧に出ないと壊れて見えるので、自分の更新だけはプライマリから読みます。技術的に正しくても、ユーザーに不整合が見えたら失敗ですから。

**🇰🇷 답변**

갱신이 모든 노드에 즉시 반영되지는 않지만, 시간이 지나면 최종적으로 같은 상태로 수렴한다. 그런 일관성 모델입니다.

왜 이걸 고르냐면 CAP 정리의 귀결입니다. 네트워크 분단은 반드시 일어난다는 전제에 서면, 강일관성을 지키려면 분단 중에 응답을 멈추는 수밖에 없습니다. 가용성을 우선한다면 일시적인 불일치를 허용하는 선택이 됩니다.

설계에서 중요한 건 어느 정도의 지연까지면 업무가 성립하는지를 미리 정하는 것입니다. 재고 표시가 몇 초 오래된 건 허용해도 결제 잔고는 허용할 수 없잖아요. 전체 시스템을 일률적으로 하지 않고 도메인별로 판단합니다.

구현에서는 세 가지를 넣습니다. 멱등성. 버전 번호를 통한 오래된 갱신 배제. 그리고 사용자 경험 고려입니다. 자기가 올린 직후에 목록에 안 나오면 고장난 것처럼 보이니까, 자신의 갱신만은 프라이머리에서 읽습니다. 기술적으로 옳아도 사용자한테 불일치가 보이면 실패니까요.

# Part 5. 클라우드 네이티브 및 대규모 트래픽

### Q38. Dockerコンテナと仮想マシンの違い
(Docker 컨테이너와 가상 머신의 차이)

**🇯🇵 回答**

最大の違いは、OSカーネルを共有するかどうかです。

VMはハイパーバイザーの上にゲストOSを丸ごと起動するので、カーネルを含めた完全な隔離が得られます。その代わりメモリを数GB単位で消費して、起動に数十秒かかります。

コンテナはホストOSのカーネルを共有します。namespacesで見え方を分離して、cgroupsで使用量を制限しているだけです。実体は隔離されたプロセスなので、起動は一秒未満、メモリも数十MBから動きます。

この差がもたらす価値は密度とスピードです。同じサーバーに何倍も詰め込めますし、イメージがレイヤーでキャッシュされるのでCI/CDが速い。

一方トレードオフも明確です。カーネルを共有するということは隔離の壁が薄いということで、カーネルの脆弱性を突かれると外に出られる可能性があります。信頼できないコードを動かす場合はVMやgVisorを検討します。コンテナが常にVMの上位互換というわけではないです。

**🇰🇷 답변**

가장 큰 차이는 OS 커널을 공유하느냐 여부입니다.

VM은 하이퍼바이저 위에 게스트 OS를 통째로 띄우니까 커널을 포함한 완전한 격리를 얻습니다. 대신 메모리를 수 GB 단위로 소비하고 기동에 수십 초가 걸립니다.

컨테이너는 호스트 OS의 커널을 공유합니다. namespaces로 보이는 범위를 분리하고 cgroups로 사용량을 제한할 뿐입니다. 실체는 격리된 프로세스라서 기동은 1초 미만, 메모리도 수십 MB부터 돌아갑니다.

이 차이가 가져오는 가치는 밀도와 속도입니다. 같은 서버에 몇 배를 담을 수 있고, 이미지가 레이어로 캐시되니까 CI/CD가 빠릅니다.

한편 트레이드오프도 명확합니다. 커널을 공유한다는 건 격리의 벽이 얇다는 뜻이라, 커널 취약점을 찔리면 밖으로 나갈 가능성이 있습니다. 신뢰할 수 없는 코드를 돌릴 때는 VM이나 gVisor를 검토합니다. 컨테이너가 항상 VM의 상위 호환은 아닙니다.

### Q39. Kubernetesを導入する最大のメリット
(쿠버네티스 도입의 최대 장점)

**🇯🇵 回答**

最大のメリットは、あるべき状態を宣言すれば、そこに収束させ続けてくれることだと思っています。

具体的には三つです。第一に自己修復。Podが落ちてもノードが死んでも、定義したレプリカ数になるよう自動で再作成されます。第二にオートスケールで、負荷に応じてHPAがPod数を増減させます。第三にローリングアップデートとロールバックが標準機能であることです。

地味ですが実務で効くのがサービスディスカバリですね。Podは再作成のたびIPが変わりますが、Service経由で名前解決するので呼ぶ側は意識しなくてよくなります。

ただ正直に申し上げると、Kubernetesは無料ではありません。運用の複雑さは確実に増えます。特に必須なのがrequests/limitsの設定と、liveness・readinessプローブの適切な実装です。ここを雑にすると再起動ループに入ります。サービス数が少ない段階なら、マネージドのコンテナサービスのほうが合理的なことも多いです。

**🇰🇷 답변**

가장 큰 장점은, 있어야 할 상태를 선언하면 거기로 계속 수렴시켜 준다는 점이라고 생각합니다.

구체적으로는 세 가지입니다. 첫째 자가 치유. Pod가 죽어도 노드가 죽어도 정의한 레플리카 수가 되도록 자동으로 재생성됩니다. 둘째 오토스케일로, 부하에 따라 HPA가 Pod 수를 늘리고 줄입니다. 셋째 롤링 업데이트와 롤백이 표준 기능이라는 것입니다.

수수하지만 실무에서 효과적인 게 서비스 디스커버리입니다. Pod는 재생성될 때마다 IP가 바뀌는데, Service를 통해 이름 해결을 하니까 호출하는 쪽은 신경 안 써도 됩니다.

다만 솔직히 말씀드리면 쿠버네티스는 공짜가 아닙니다. 운영 복잡도는 확실히 늘어납니다. 특히 필수인 게 requests/limits 설정과 liveness·readiness 프로브의 적절한 구현입니다. 여기를 대충 하면 재시작 루프에 빠집니다. 서비스 수가 적은 단계라면 매니지드 컨테이너 서비스가 더 합리적인 경우도 많습니다.

### Q40. Blue-Greenデプロイとカナリアリリースの違い
(Blue-Green 배포와 카나리 릴리스의 차이)

**🇯🇵 回答**

Blue-Greenは、新バージョンの環境を丸ごと立ち上げて、確認してからトラフィックを一気に100%切り替える方式です。利点は切り戻しが数秒で済むこと。欠点は環境を二面持つのでコストが倍かかることと、切り替えた瞬間に全ユーザーが乗るので検知が遅れると影響が全体に及ぶことです。

カナリアは1%、5%、10%と段階的に流していきます。その間エラー率とレイテンシを監視して比率を上げます。影響範囲を限定できるのが価値で、本番でしか出ない問題を少数のユーザーで検知できます。欠点は判定の自動化とメトリクスがないと機能しないことです。

実務で本当に難しいのは、どちらの方式でもDBスキーマの変更です。ロールバックしてもDBは戻せないので、カラム追加と削除を同一リリースでやらない拡張・縮小方式を徹底します。

使い分けとしては、影響が読みにくい変更はカナリア、限定的で早く出したいものはBlue-Greenですね。

**🇰🇷 답변**

Blue-Green은 새 버전 환경을 통째로 띄워서 확인한 다음, 트래픽을 한 번에 100% 전환하는 방식입니다. 이점은 롤백이 몇 초면 끝난다는 것. 단점은 환경을 두 벌 유지하니까 비용이 배로 든다는 것과, 전환하는 순간 모든 사용자가 타니까 탐지가 늦으면 영향이 전체에 미친다는 겁니다.

카나리는 1%, 5%, 10%로 단계적으로 흘려보냅니다. 그동안 에러율과 레이턴시를 모니터링해서 비율을 올립니다. 영향 범위를 한정할 수 있는 게 가치라서, 프로덕션에서만 나오는 문제를 소수 사용자로 탐지할 수 있습니다. 단점은 판정 자동화와 메트릭이 없으면 기능하지 않는다는 겁니다.

실무에서 진짜 어려운 건 어느 방식이든 DB 스키마 변경입니다. 롤백해도 DB는 못 되돌리니까, 컬럼 추가와 삭제를 같은 릴리스에서 안 하는 확장·축소 방식을 철저히 지킵니다.

구분해서 쓰자면, 영향을 읽기 어려운 변경은 카나리, 한정적이고 빨리 내고 싶은 건 Blue-Green입니다.

### Q41. KafkaとRabbitMQの違い
(Kafka와 RabbitMQ의 차이)

**🇯🇵 回答**

根本的な違いは、Kafkaが「ログ」で、RabbitMQが「キュー」だという点です。

RabbitMQはメッセージブローカーで、コンシューマーがACKを返した時点でメッセージが消えます。一件ずつの配送保証と柔軟なルーティング、優先度や遅延配送が強みで、タスク分配に向いています。

Kafkaは分散コミットログです。メッセージはディスクに追記され、消費されても保持期間まで消えません。コンシューマーはオフセットを持つだけです。ここから二つの強みが出ます。過去に遡っての再処理ができること。そして同じデータを複数の用途で独立に読めることです。

使い分けは、イベントストリーミングや再処理が必要ならKafka。細かいルーティングや優先度、低レイテンシなタスクキューならRabbitMQです。

一点、Kafkaの順序保証はパーティション単位です。同じキーは同じパーティションに行くので注文内の順序は保証されますが、全体の順序は保証されません。ここを誤解すると本番で順序逆転の事故になります。

**🇰🇷 답변**

근본적인 차이는 Kafka가 "로그"이고 RabbitMQ가 "큐"라는 점입니다.

RabbitMQ는 메시지 브로커라서 컨슈머가 ACK를 반환한 시점에 메시지가 사라집니다. 건별 배송 보증과 유연한 라우팅, 우선순위나 지연 배송이 강점이고 태스크 분배에 적합합니다.

Kafka는 분산 커밋 로그입니다. 메시지는 디스크에 추가되고 소비되어도 보존 기간까지 안 사라집니다. 컨슈머는 오프셋을 가질 뿐입니다. 여기서 두 가지 강점이 나옵니다. 과거로 거슬러 올라간 재처리가 된다는 것. 그리고 같은 데이터를 여러 용도로 독립적으로 읽을 수 있다는 것입니다.

구분해서 쓰자면, 이벤트 스트리밍이나 재처리가 필요하면 Kafka. 세밀한 라우팅이나 우선순위, 저지연 태스크 큐면 RabbitMQ입니다.

한 가지, Kafka의 순서 보증은 파티션 단위입니다. 같은 키는 같은 파티션으로 가니까 주문 안에서의 순서는 보증되지만, 전체 순서는 보증이 안 됩니다. 여기를 오해하면 프로덕션에서 순서 역전 사고가 납니다.

### Q42. トラフィック急増時にKafkaでシステムを守る
(트래픽 급증 시 Kafka로 시스템을 지키기)

**🇯🇵 回答**

考え方は負荷平準化です。瞬間的なピークをそのままDBに流さず、Kafkaに一度受け止めて、コンシューマーが処理できる速度でだけ引き取ります。

APIの設計もこれに合わせます。リクエストを受けたら最低限の検証だけしてpublishし、即座に202 Acceptedと受付IDを返します。完了は別のエンドポイントかWebSocketで通知します。同期でDBまで書き切ろうとするから詰まるので、同期パスを最短にするのが本質です。

コンシューマー側では書き込みをバッチにまとめ、重複が来る前提で冪等キーによる排除を入れます。

ただ正直に言うと、キューは万能ではありません。キューは負荷を遅らせるだけで、消してはくれないんですよ。到着レートが処理能力を継続的に超えれば、ラグは無限に伸びます。だから前段でレート制限を入れます。特にコンシューマーはパーティション数より増やせないので、パーティション数は将来の並列度を見越して設計時に決めておきます。

**🇰🇷 답변**

사고방식은 부하 평준화입니다. 순간적인 피크를 그대로 DB로 흘리지 않고, Kafka에 한 번 받아 두고 컨슈머가 처리할 수 있는 속도로만 가져갑니다.

API 설계도 여기에 맞춥니다. 요청을 받으면 최소한의 검증만 하고 publish한 다음, 즉시 202 Accepted와 접수 ID를 반환합니다. 완료는 별도 엔드포인트나 WebSocket으로 알립니다. 동기로 DB까지 다 쓰려고 하니까 막히는 거라서, 동기 경로를 최단으로 하는 게 본질입니다.

컨슈머 쪽에서는 쓰기를 배치로 묶고, 중복이 온다는 전제로 멱등 키를 통한 제거를 넣습니다.

다만 솔직히 말하면 큐는 만능이 아닙니다. 큐는 부하를 미룰 뿐이지 없애 주지는 않습니다. 도착 레이트가 처리 능력을 지속적으로 넘으면 랙은 무한히 늘어납니다. 그래서 앞단에 레이트 리밋을 넣습니다. 특히 컨슈머는 파티션 수보다 늘릴 수 없으니, 파티션 수는 미래의 병렬도를 내다보고 설계 시점에 정해 둡니다.

### Q43. Kafkaコンシューマーの再処理戦略
(Kafka 컨슈머 재처리 전략)

**🇯🇵 回答**

前提として、同じパーティション内でリトライを繰り返すのは避けます。Kafkaはオフセット順に処理するので、一件が詰まるとその後ろが全部止まります。ヘッドオブラインブロッキングですね。一件の不正データで数万件が止まります。

そこでノンブロッキングリトライを採ります。失敗したメッセージは元のトピックでは処理済みとしてコミットして、リトライ専用トピックに移します。5秒後、1分後、10分後と間隔を広げながら再試行させ、それでも失敗したらDLQに退避します。Spring Kafkaなら `@RetryableTopic` で宣言的に組めます。

ただしトレードオフとして、リトライトピックに移した時点で順序は崩れます。同一口座の入出金のように順序が業務要件に含まれる場合、この方式は使えません。

エラーの分類も重要です。必須項目が欠けたデータは何度やっても失敗するので、即座にDLQへ送ります。そしてDLQは件数のアラートと再投入の運用手段まで用意して初めて完成だと考えています。

**🇰🇷 답변**

전제로, 같은 파티션 안에서 재시도를 반복하는 건 피합니다. Kafka는 오프셋 순으로 처리하니까 한 건이 막히면 그 뒤가 전부 멈춥니다. 헤드 오브 라인 블로킹이죠. 한 건의 불량 데이터로 수만 건이 멈춥니다.

그래서 논블로킹 재시도를 씁니다. 실패한 메시지는 원래 토픽에서는 처리 완료로 커밋하고, 재시도 전용 토픽으로 옮깁니다. 5초 후·1분 후·10분 후로 간격을 넓히면서 재시도시키고, 그래도 실패하면 DLQ로 대피시킵니다. Spring Kafka라면 `@RetryableTopic`으로 선언적으로 짤 수 있습니다.

다만 트레이드오프로, 재시도 토픽으로 옮긴 시점에 순서는 깨집니다. 같은 계좌의 입출금처럼 순서가 업무 요건에 포함된 경우에는 이 방식을 못 씁니다.

에러 분류도 중요합니다. 필수 항목이 빠진 데이터는 몇 번을 해도 실패하니까 즉시 DLQ로 보냅니다. 그리고 DLQ는 건수 알림과 재투입 운영 수단까지 준비해야 비로소 완성이라고 생각합니다.

### Q44. コネクションリークの検出と調査 【Q18の深掘り版】
(커넥션 누수 탐지와 조사 — Q18 심화판)

> ⚠️ Q18과 동일한 질문입니다. 여기서는 "누수인가, 장시간 점유인가, 애초에 풀 부족인가"의 판별 프로세스에 축을 둔 다른 버전입니다.

**🇯🇵 回答**

まず、症状が似ている三つを切り分けます。プールが枯渇するという現象は同じでも、原因が「返却されていない」「返却は遅いが返ってはいる」「単純にプールが小さい」の三つに分かれて、対処が全く違うからです。

判別はメトリクスの形を見ます。負荷が下がっても `active` が減らず階段状に増えるならリーク。負荷に連動して増減するけれどピークで `pending` が出るなら、占有か容量不足です。その二つは平均の貸出時間で分かります。数百ミリ秒なら容量不足、数秒以上なら何かを待っています。

リークだと判断したら `leakDetectionThreshold` を設定します。借りた時点のスタックトレースが出るので、犯人のメソッドが特定できます。

原因で多いのは、try-with-resources を使っていない箇所、`@Transactional` の内側で外部APIを呼ぶケース、OSIVが有効なケースの三つです。二番目は厳密にはリークではないですが、対処は同じでI/O待ちを境界の外に出すことです。

**🇰🇷 답변**

먼저, 증상이 비슷한 세 가지를 구분합니다. 풀이 고갈된다는 현상은 같아도 원인이 "반환되지 않음", "반환은 느리지만 돌아옴", "단순히 풀이 작음" 세 가지로 갈리고 대처가 완전히 다르기 때문입니다.

판별에는 메트릭의 형태를 봅니다. 부하가 내려가도 `active`가 안 줄고 계단식으로 계속 늘면 누수. 부하에 연동해서 증감하는데 피크에서 `pending`이 나오면 점유거나 용량 부족입니다. 그 둘은 평균 대출 시간으로 알 수 있습니다. 수백 밀리초면 용량 부족, 수 초 이상이면 뭔가를 기다리고 있는 겁니다.

누수라고 판단되면 `leakDetectionThreshold`를 설정합니다. 빌린 시점의 스택 트레이스가 나오니까 범인 메서드를 직접 특정할 수 있습니다.

원인으로 많은 건 try-with-resources를 안 쓴 부분, `@Transactional` 안쪽에서 외부 API를 호출하는 케이스, OSIV가 켜진 케이스 세 가지입니다. 두 번째는 엄밀히는 누수가 아니지만 대처는 같아서, I/O 대기를 경계 밖으로 빼는 것입니다.

### Q45. オートスケーリングのトリガー条件設計
(오토스케일링 트리거 조건 설계)

**🇯🇵 回答**

CPU使用率だけをトリガーにするのは、多くのアプリケーションで不適切だと考えています。Webアプリの大半はI/O待ちが主なので、DBが遅くてリクエストが詰まっていてもCPUは低いままなんですよ。CPUが上がった頃には手遅れです。

だからアプリの特性に合わせたカスタムメトリクスを使います。API層ならリクエストレートかp95レイテンシ、Kafkaコンシューマーならコンシューマーラグが最も適切です。KEDAを使えば外部メトリクスでのスケールが組めます。

必ず考慮する点が三つあります。第一に、スケールアウトには数十秒から数分かかるので、閾値は限界の手前、使用率70%程度で先に発火させること。第二にフラッピング防止で、スケールインには長めの安定化ウィンドウを置くこと。

第三に、下流の限界を必ず確認することです。Podを10倍にしてもDBの最大接続数は変わらないので、無邪気にスケールするとDB側を落とします。プールサイズ×最大Pod数がDBの上限を超えないよう逆算しておきます。

**🇰🇷 답변**

CPU 사용률만 트리거로 삼는 건 많은 애플리케이션에서 부적절하다고 생각합니다. 웹 앱은 대부분 I/O 대기가 주라서, DB가 느려서 요청이 밀려도 CPU는 낮게 유지되거든요. CPU가 올라갔을 때는 이미 늦습니다.

그래서 앱 특성에 맞춘 커스텀 메트릭을 씁니다. API 계층이면 요청 레이트나 p95 레이턴시, Kafka 컨슈머면 컨슈머 랙이 가장 적절합니다. KEDA를 쓰면 외부 메트릭 기반 스케일을 구성할 수 있습니다.

반드시 고려하는 점이 세 가지 있습니다. 첫째, 스케일 아웃에는 수십 초에서 수 분이 걸리니까 임계치는 한계 앞에서, 사용률 70% 정도에서 먼저 발화시킬 것. 둘째 플래핑 방지로, 스케일 인에는 긴 안정화 윈도를 둘 것.

셋째, 하류의 한계를 반드시 확인할 것입니다. Pod를 10배로 해도 DB 최대 접속 수는 안 변하니까, 순진하게 스케일하면 DB 쪽을 죽입니다. 풀 사이즈 × 최대 Pod 수가 DB 상한을 안 넘도록 역산해 둡니다.
