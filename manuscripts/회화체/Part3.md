### Q31. モノリスからMSAへ移行する際の最大の課題
(모놀리스에서 MSA로 전환할 때의 최대 과제)

**🇯🇵 回答**

技術的な最大の課題は、データ整合性です。モノリスなら一つのトランザクションでロールバックできたものが、サービスごとにDBが分かれた瞬間にできなくなります。

対応としてはSagaパターンで補償トランザクションを設計します。ただ、ここで見落とされがちなのがDB更新とイベント発行の原子性なんですよね。DBにコミットした直後にプロセスが落ちて、イベントが飛ばない、という状態が起きます。なのでOutboxパターンで、イベントを同じトランザクションの中でDBに書いて、別のプロセスがそれをKafkaに送る構成にします。

ただ、実際に移行を難しくしているのは技術じゃないと思っています。サービス境界の切り方のほうです。境界を間違えると、機能を一つ追加するのに三つのサービスを同時にデプロイしなきゃいけない、という状況が生まれます。これが分散モノリスと呼ばれる最悪の状態で、モノリスの結合度とMSAの運用コストを両方背負うことになります。だからDDDの境界づけられたコンテキストで慎重に切って、迷ったら大きめに切っておいて後から分割する、という方針を採ります。

あともう一つ、運用の準備が先に必要です。分散トレーシングとログ集約がない状態でサービスを分けると、障害のときに「どこで失敗したのか」が誰にも分からなくなります。私はMSA化の前に可観測性を整えることを、必ず条件にしています。

**🇰🇷 답변**

기술적인 최대 과제는 데이터 정합성입니다. 모놀리스라면 하나의 트랜잭션으로 롤백할 수 있던 게, 서비스별로 DB가 나뉘는 순간 안 되게 됩니다.

대응으로는 Saga 패턴으로 보상 트랜잭션을 설계합니다. 그런데 여기서 놓치기 쉬운 게 DB 갱신이랑 이벤트 발행의 원자성이에요. DB에 커밋한 직후에 프로세스가 죽어서 이벤트가 안 날아가는 상태가 생깁니다. 그래서 Outbox 패턴으로 이벤트를 같은 트랜잭션 안에서 DB에 쓰고, 별도 프로세스가 그걸 Kafka로 보내는 구성으로 갑니다.

다만 실제로 전환을 어렵게 만드는 건 기술이 아니라고 생각합니다. 서비스 경계를 나누는 방식 쪽이에요. 경계를 잘못 잡으면 기능 하나 추가하는 데 세 개 서비스를 동시에 배포해야 하는 상황이 생깁니다. 이게 분산 모놀리스라고 부르는 최악의 상태인데, 모놀리스의 결합도랑 MSA의 운영 비용을 둘 다 짊어지게 됩니다. 그래서 DDD의 바운디드 컨텍스트로 신중하게 나누고, 애매하면 크게 잘라 놨다가 나중에 분할하는 방침을 씁니다.

그리고 하나 더, 운영 준비가 먼저 필요합니다. 분산 트레이싱이랑 로그 집약이 없는 상태로 서비스를 나누면, 장애 났을 때 "어디서 실패했는지"를 아무도 모르게 됩니다. 저는 MSA화 전에 관측 가능성을 갖추는 걸 반드시 조건으로 겁니다.

### Q32. サービス間通信 REST vs gRPC の使い分け
(서비스 간 통신 REST vs gRPC 구분)

**🇯🇵 回答**

外部公開やフロントエンドとの通信はREST、内部のサービス間はgRPC。これを基本にします。

RESTを外部に使う理由は三つあります。ブラウザからそのまま叩けること、HTTPキャッシュが効くこと、そしてデバッグやドキュメント化のエコシステムが圧倒的に豊富なことです。外部の開発者に使ってもらうAPIでバイナリプロトコルを強いるのは、導入の障壁が高すぎますから。

内部にgRPCを使う理由も三つです。Protocol Buffersのバイナリシリアライズでペイロードが小さいこと。HTTP/2の多重化で接続を使い回せること。そしてスキーマからコードが自動生成されるので、フィールド追加のときの破壊的変更をビルド時に検出できること。実運用ではこの三つ目が一番効きます。

ただし注意点があります。gRPCはHTTP/2の長寿命接続を使うので、L4ロードバランサーだと最初に繋がったPodに固定され続けて、負荷が偏ってしまうんですよ。L7対応のプロキシか、クライアント側ロードバランシングが必要になります。

そしてもう一つ。そもそも同期RPCを使うかどうか自体を、先に検討します。gRPCもRESTも同期呼び出しである限り、呼び先が落ちれば呼び元も影響を受けますから。在庫更新後の通知とかポイント付与みたいに即時性が要らないものは、Kafkaを介したイベント連携にして、そもそも同期の依存を作らないほうが可用性は上がります。

**🇰🇷 답변**

외부 공개나 프론트엔드와의 통신은 REST, 내부 서비스 간은 gRPC. 이걸 기본으로 합니다.

REST를 외부에 쓰는 이유는 세 가지입니다. 브라우저에서 바로 호출할 수 있다는 점, HTTP 캐시가 듣는다는 점, 그리고 디버깅이랑 문서화 생태계가 압도적으로 풍부하다는 점이요. 외부 개발자가 쓸 API에 바이너리 프로토콜을 강요하는 건 진입 장벽이 너무 높으니까요.

내부에 gRPC를 쓰는 이유도 세 가지입니다. Protocol Buffers의 바이너리 직렬화로 페이로드가 작다는 점. HTTP/2 다중화로 접속을 재사용할 수 있다는 점. 그리고 스키마에서 코드가 자동 생성되니까 필드 추가할 때의 파괴적 변경을 빌드 타임에 잡을 수 있다는 점. 실운영에서는 이 세 번째가 제일 효과적입니다.

단, 주의점이 있습니다. gRPC는 HTTP/2 장수명 접속을 쓰기 때문에, L4 로드밸런서면 처음 연결된 Pod에 계속 고정돼서 부하가 치우칩니다. L7 대응 프록시나 클라이언트 사이드 로드밸런싱이 필요해집니다.

그리고 하나 더. 애초에 동기 RPC를 쓸지 말지 자체를 먼저 검토합니다. gRPC든 REST든 동기 호출인 이상, 호출 대상이 죽으면 호출자도 영향을 받으니까요. 재고 갱신 후의 알림이나 포인트 적립처럼 즉시성이 필요 없는 건 Kafka를 통한 이벤트 연계로 해서, 애초에 동기 의존을 안 만드는 편이 가용성이 올라갑니다.

### Q33. 分散トレーシングとは
(분산 트레이싱이란)

**🇯🇵 回答**

一つのユーザーリクエストが複数のサービスを横断するときに、その全経路を一本の線として追跡する仕組みです。

具体的には、入り口でリクエストにTrace IDを付けて、各サービスでの処理をSpanという単位で記録します。SpanにはID、親SpanのID、開始と終了の時刻が入ります。なのでこれを集めると、リクエスト全体の木構造と、それぞれにかかった時間が復元できるんですね。

肝になるのは、IDを次のサービスに引き継ぐ伝播の部分です。ここは自前で実装せず、W3C Trace Contextの標準ヘッダーに従って、OpenTelemetryのライブラリに任せます。ベンダーロックインを避けられるのも理由の一つです。

導入して一番効くのは、「APIが遅い」という報告に対して、どのサービスのどの処理が何ミリ秒かかっているかを、推測じゃなくて事実として出せることです。私はここで、ログにもTrace IDを必ず含めるようにしています。トレースで遅い箇所を特定して、同じIDでログを引くとその時の詳細が分かる、という流れを作れますから。

運用上の論点はサンプリングです。全リクエストを保存するとコストが現実的じゃないので、通常は数%に絞ります。ただそうすると、エラーのトレースが取れないことがあるんですよ。可能ならエラーや遅延したリクエストを優先して残す、テールベースサンプリングを検討します。

もう一点。非同期の区間でトレースが途切れるのは、コンテキストがThreadLocalに乗っているからです。これが厄介なのは、例外を出さずに静かに起きることなんですよね。ダッシュボードでトレースが途中で切れているのを見て、初めて気づくことが多いです。

**🇰🇷 답변**

하나의 사용자 요청이 여러 서비스를 횡단할 때, 그 전체 경로를 하나의 선으로 추적하는 장치입니다.

구체적으로는 입구에서 요청에 Trace ID를 붙이고, 각 서비스에서의 처리를 Span이라는 단위로 기록합니다. Span에는 ID, 부모 Span의 ID, 시작이랑 종료 시각이 들어갑니다. 그래서 이걸 모으면 요청 전체의 트리 구조랑 각각에 걸린 시간이 복원됩니다.

핵심이 되는 건 ID를 다음 서비스로 넘기는 전파 부분입니다. 여기는 직접 구현하지 않고, W3C Trace Context 표준 헤더를 따라서 OpenTelemetry 라이브러리에 맡깁니다. 벤더 락인을 피할 수 있다는 것도 이유 중 하나고요.

도입해서 제일 효과적인 건, "API가 느리다"는 보고에 대해서 어느 서비스의 어느 처리가 몇 밀리초 걸리는지를 추측이 아니라 사실로 낼 수 있다는 겁니다. 저는 여기서 로그에도 Trace ID를 반드시 넣습니다. 트레이스로 느린 지점을 특정하고, 같은 ID로 로그를 뽑으면 그때의 상세를 알 수 있는 흐름을 만들 수 있으니까요.

운영상의 논점은 샘플링입니다. 전체 요청을 저장하면 비용이 비현실적이니까 보통 몇 %로 좁힙니다. 그런데 그러면 에러의 트레이스를 못 잡는 경우가 생기거든요. 가능하면 에러나 지연된 요청을 우선해서 남기는 테일 기반 샘플링을 검토합니다.

한 가지 더요. 비동기 구간에서 트레이스가 끊기는 건 Context가 ThreadLocal에 실려 있기 때문입니다. 이게 까다로운 게, 예외를 안 내고 조용히 일어난다는 거예요. 대시보드에서 트레이스가 중간에 잘려 있는 걸 보고 나서야 알아채는 경우가 많습니다.

### Q34. サーキットブレーカーパターンの目的と動作原理
(서킷 브레이커 패턴의 목적과 동작 원리)

**🇯🇵 回答**

目的は、障害の連鎖を止めることです。呼び先が落ちているのに呼び続けると、呼び元のスレッドがタイムアウト待ちで埋まってしまいます。すると無関係な機能まで巻き込んで停止するんですよ。これを防ぐために、失敗が続いたら呼び出しそのものを遮断します。

動作は三つの状態で説明できます。通常はCLOSEDで素通しします。直近の呼び出しのうち失敗率が閾値を超えるとOPENになります。このとき「最低試行回数」も条件に入れるのが重要です。これがないと、最初の1回が失敗しただけで遮断されてしまうので。OPENの間は呼び出さずに即座に失敗を返して、一定時間が経つとHALF-OPENに移ります。そこで数件だけ試して、回復していればCLOSEDに戻ります。

設計上の要点は、遮断したときに何を返すかです。ただエラーにするんじゃなくて、キャッシュした古い値を返すとか、機能を縮退させて表示だけ消すとか、そういうフォールバックを業務側と決めておきます。

もう一つ強調したいのは、サーキットブレーカーは単独では機能しないということです。前提として、全ての外部呼び出しに適切なタイムアウトが設定されていること。そしてリトライには指数バックオフとジッターを入れること。この二つが必要です。タイムアウトなしのリトライって、落ちかけた相手にトドメを刺すだけなんですよね。

具体的な数値で言うと、私は通常minimumNumberOfCallsを5、失敗率の閾値を50%、OPEN状態の待機時間を30秒、HALF-OPENでの試行呼び出しを3件から始めます。数値を挙げること自体が「実際に設定したことがある」という根拠になりますので。

**🇰🇷 답변**

목적은 장애의 연쇄를 멈추는 것입니다. 호출 대상이 죽었는데 계속 호출하면, 호출자의 스레드가 타임아웃 대기로 꽉 차 버립니다. 그러면 무관한 기능까지 휘말려서 정지하거든요. 이걸 막으려고 실패가 이어지면 호출 자체를 차단합니다.

동작은 세 가지 상태로 설명할 수 있습니다. 평소에는 CLOSED로 통과시킵니다. 최근 호출 중 실패율이 임계치를 넘으면 OPEN이 됩니다. 이때 "최소 시행 횟수"도 조건에 넣는 게 중요합니다. 이게 없으면 첫 1회 실패만으로 차단돼 버리니까요. OPEN인 동안은 호출하지 않고 즉시 실패를 반환하고, 일정 시간이 지나면 HALF-OPEN으로 옮겨 갑니다. 거기서 몇 건만 시도해 보고 회복됐으면 CLOSED로 돌아갑니다.

설계상의 요점은 차단했을 때 뭘 반환하느냐입니다. 그냥 에러로 하는 게 아니라, 캐시한 오래된 값을 반환한다든가, 기능을 축소해서 표시만 없앤다든가, 그런 폴백을 업무 쪽이랑 정해 둡니다.

또 하나 강조하고 싶은 건, 서킷 브레이커는 단독으로는 기능하지 않는다는 겁니다. 전제로 모든 외부 호출에 적절한 타임아웃이 설정돼 있을 것. 그리고 재시도에는 지수 백오프랑 지터를 넣을 것. 이 두 가지가 필요합니다. 타임아웃 없는 재시도는 죽어가는 상대한테 확인사살하는 거나 마찬가지거든요.

구체적인 수치로 말씀드리면, 저는 보통 minimumNumberOfCalls를 5, 실패율 임계치를 50%, OPEN 상태 대기 시간을 30초, HALF-OPEN에서의 시험 호출을 3건으로 시작합니다. 숫자를 대는 것 자체가 "실제로 설정해 봤다"는 근거가 되니까요.

### Q35. ゼロトラストセキュリティとmTLS
(제로 트러스트 보안과 mTLS)

**🇯🇵 回答**

ゼロトラストは、「社内ネットワークの内側だから安全」という前提を捨てる考え方です。従来は境界防御、つまりファイアウォールの内側を信頼していました。でも一箇所侵入されると、横移動で全体が抜かれてしまうんですよね。そこで「どのネットワークにいるか」じゃなくて「誰であるか」で毎回検証する、という方針に切り替えます。

その実装の中核がmTLSです。通常のTLSは、クライアントがサーバーの証明書を検証する片方向ですよね。mTLSはサーバーもクライアントの証明書を検証します。これでサービス同士が互いの身元を暗号的に証明できて、証明書を持たないプロセスは通信そのものができなくなります。通信内容も暗号化されるので、内部ネットワークの盗聴にも耐えます。

実運用で難しいのは、証明書のライフサイクル管理です。数十のサービスに証明書を配って、短い有効期限で自動ローテーションする。これを自前で作るのは現実的じゃありません。なのでIstioのようなサービスメッシュを使って、サイドカーに証明書の発行と更新を任せる構成が一般的です。

一点補足させてください。mTLSは認証であって、認可ではありません。「誰か」は証明できますが、「何をしてよいか」は別の話です。サービスAはサービスBの読み取りAPIだけ呼べる、といったポリシーを別途定義する必要があります。ここを混同すると、証明書さえあれば何でも呼べる状態になってしまいます。

**🇰🇷 답변**

제로 트러스트는 "사내 네트워크 안쪽이니까 안전하다"는 전제를 버리는 사고방식입니다. 예전에는 경계 방어, 그러니까 방화벽 안쪽을 신뢰했습니다. 그런데 한 군데 뚫리면 횡이동으로 전체가 털리거든요. 그래서 "어느 네트워크에 있는가"가 아니라 "누구인가"로 매번 검증하는 방침으로 바꿉니다.

그 구현의 핵심이 mTLS입니다. 일반 TLS는 클라이언트가 서버 인증서를 검증하는 단방향이잖아요. mTLS는 서버도 클라이언트 인증서를 검증합니다. 이러면 서비스끼리 서로의 신원을 암호학적으로 증명할 수 있고, 인증서가 없는 프로세스는 통신 자체가 안 됩니다. 통신 내용도 암호화되니까 내부 네트워크 도청에도 견딥니다.

실운영에서 어려운 건 인증서 라이프사이클 관리입니다. 수십 개 서비스에 인증서를 배포하고, 짧은 유효기간으로 자동 로테이션하는 것. 이걸 직접 만드는 건 비현실적입니다. 그래서 Istio 같은 서비스 메시를 써서 사이드카에 인증서 발급이랑 갱신을 맡기는 구성이 일반적입니다.

한 가지 보충하겠습니다. mTLS는 인증이지 인가가 아닙니다. "누구인가"는 증명하지만 "뭘 해도 되는가"는 별개 얘기예요. 서비스 A는 서비스 B의 읽기 API만 호출 가능하다, 이런 정책을 따로 정의해야 합니다. 여기를 혼동하면 인증서만 있으면 뭐든 호출 가능한 상태가 돼 버립니다.

### Q36. APIゲートウェイの役割
(API 게이트웨이의 역할)

**🇯🇵 回答**

クライアントからの単一の入り口として、全リクエストを受けて適切なサービスにルーティングする層です。

ここに集約するのは横断的関心事です。認証トークンの検証、レート制限、TLS終端、共通のログとメトリクス出力、CORS設定。つまり全サービスが必要とするけれど、本質的なビジネスロジックではないものをまとめます。メリットは、各サービスがこれらを実装しなくてよくなることです。認証ロジックが十数のサービスに散らばって仕様がずれる、という事故を防げます。

同時に、注意すべき点が二つあります。

一つ目は、ゲートウェイが単一障害点になることです。冗長化と、ゲートウェイ自体の性能余裕は必ず確保します。

二つ目、こっちのほうが重要なんですが、ゲートウェイにビジネスロジックを入れないことです。ここに条件分岐やデータ変換を書き始めると、全サービスがゲートウェイのデプロイに依存するようになって、結局分散モノリスに戻ってしまいます。ゲートウェイに入れていいのは「全サービスに共通で、ドメイン知識を必要としない処理」だけ。この線引きを最初に決めます。

なお、クライアントごとにレスポンスを最適化したい場合は、ゲートウェイとは別にBFF層を置きます。ゲートウェイに詰め込まないための分離ですね。

**🇰🇷 답변**

클라이언트로부터의 단일 진입점으로서, 모든 요청을 받아 적절한 서비스로 라우팅하는 계층입니다.

여기에 모으는 건 횡단 관심사입니다. 인증 토큰 검증, 레이트 리밋, TLS 종단, 공통 로그랑 메트릭 출력, CORS 설정. 그러니까 모든 서비스가 필요로 하지만 본질적인 비즈니스 로직은 아닌 것들을 모읍니다. 장점은 각 서비스가 이것들을 구현 안 해도 된다는 겁니다. 인증 로직이 십수 개 서비스에 흩어져서 스펙이 어긋나는 사고를 막을 수 있고요.

동시에 주의할 점이 두 가지 있습니다.

첫째, 게이트웨이가 단일 장애점이 된다는 겁니다. 이중화랑 게이트웨이 자체의 성능 여유는 반드시 확보합니다.

둘째, 이쪽이 더 중요한데요, 게이트웨이에 비즈니스 로직을 안 넣는 겁니다. 여기에 조건 분기나 데이터 변환을 쓰기 시작하면 모든 서비스가 게이트웨이 배포에 의존하게 돼서, 결국 분산 모놀리스로 돌아가 버립니다. 게이트웨이에 넣어도 되는 건 "모든 서비스에 공통이고 도메인 지식이 필요 없는 처리"뿐. 이 선을 처음에 정합니다.

그리고 클라이언트별로 응답을 최적화하고 싶으면 게이트웨이랑 별도로 BFF 계층을 둡니다. 게이트웨이에 몰아넣지 않기 위한 분리입니다.

### Q37. 分散システムにおける結果整合性
(분산 시스템의 결과적 일관성)

**🇯🇵 回答**

更新が全ノードに即座に反映されるわけではないけれど、時間が経てば最終的に全ノードが同じ状態に収束する。そういう一貫性モデルです。

なぜこれを選ぶかというと、CAP定理の帰結なんですよね。ネットワーク分断は必ず起きるという前提に立つと、強一貫性を保つには分断中に応答を止めるしかありません。可用性を優先するなら、一時的な不整合を許容するという選択になります。実際、Kafkaを介したサービス間の連携は、本質的にこのモデルになります。

設計する上で重要なのは、どこまでの遅延なら業務が成立するかを事前に決めることです。商品ページの在庫表示が数秒古いのは許容できても、決済の残高が古いのは許容できませんよね。だから全システムを一律に結果整合性にするんじゃなくて、ドメインごとに判断します。

実装上は三つ必ず入れます。第一に冪等性です。リトライで同じイベントが二度届いても結果が変わらないようにします。第二にイベントの順序と重複への対処で、バージョン番号やタイムスタンプで古い更新を弾きます。第三にユーザー体験の考慮です。自分が投稿した直後に一覧に出てこないと壊れて見えるので、自分の更新だけはプライマリから読む、といった工夫を入れます。技術的に正しくても、ユーザーに不整合が見えたら失敗ですから。

**🇰🇷 답변**

갱신이 모든 노드에 즉시 반영되지는 않지만, 시간이 지나면 최종적으로 모든 노드가 같은 상태로 수렴한다. 그런 일관성 모델입니다.

왜 이걸 고르냐면 CAP 정리의 귀결이거든요. 네트워크 분단은 반드시 일어난다는 전제에 서면, 강일관성을 지키려면 분단 중에 응답을 멈추는 수밖에 없습니다. 가용성을 우선한다면 일시적인 불일치를 허용한다는 선택이 됩니다. 실제로 Kafka를 통한 서비스 간 연계는 본질적으로 이 모델이 됩니다.

설계할 때 중요한 건, 어느 정도의 지연까지면 업무가 성립하는지를 미리 정하는 것입니다. 상품 페이지의 재고 표시가 몇 초 오래된 건 허용해도, 결제 잔고가 오래된 건 허용할 수 없잖아요. 그래서 전체 시스템을 일률적으로 결과적 일관성으로 하는 게 아니라 도메인별로 판단합니다.

구현상으로는 세 가지를 반드시 넣습니다. 첫째 멱등성입니다. 재시도로 같은 이벤트가 두 번 도착해도 결과가 안 바뀌게 합니다. 둘째 이벤트 순서랑 중복에 대한 대처로, 버전 번호나 타임스탬프로 오래된 갱신을 걸러냅니다. 셋째 사용자 경험 고려입니다. 자기가 올린 직후에 목록에 안 나오면 고장난 것처럼 보이니까, 자신의 갱신만은 프라이머리에서 읽는 식의 장치를 넣습니다. 기술적으로 옳아도 사용자한테 불일치가 보이면 실패니까요.

# Part 5. 클라우드 네이티브 및 대규모 트래픽

### Q38. Dockerコンテナと仮想マシンの違い
(Docker 컨테이너와 가상 머신의 차이)

**🇯🇵 回答**

最大の違いは、OSカーネルを共有するかどうかです。

VMはハイパーバイザーの上にゲストOSを丸ごと起動します。なのでカーネルを含めた完全な隔離が得られます。その代わりメモリを数GB単位で消費して、起動に数十秒かかります。

一方コンテナは、ホストOSのカーネルを共有します。namespacesでプロセスやネットワークの見え方を分離して、cgroupsでCPUやメモリの使用量を制限しているだけなんですね。実体は隔離されたプロセスなので、起動は一秒未満、メモリも数十MBから動きます。

この差が実務にもたらす価値は、密度とスピードです。同じサーバーに何倍もの数を詰め込めますし、イメージがレイヤー構造でキャッシュされるのでCI/CDが速い。そして「開発環境では動いたのに」という問題が、依存関係ごとイメージに固めることで解消されます。

一方でトレードオフも明確です。カーネルを共有するということは、隔離の壁がVMより薄いということです。カーネルの脆弱性を突かれるとコンテナの外に出られる可能性がありますし、ホストと異なるカーネルを必要とするOSは動きません。なのでマルチテナントで信頼できないコードを動かす場合は、VMかgVisorのようなサンドボックスを検討します。用途で使い分けるべきもので、コンテナが常にVMの上位互換というわけではないです。

**🇰🇷 답변**

가장 큰 차이는 OS 커널을 공유하느냐 여부입니다.

VM은 하이퍼바이저 위에 게스트 OS를 통째로 띄웁니다. 그래서 커널을 포함한 완전한 격리를 얻습니다. 대신 메모리를 수 GB 단위로 소비하고 기동에 수십 초가 걸립니다.

반면 컨테이너는 호스트 OS의 커널을 공유합니다. namespaces로 프로세스랑 네트워크가 보이는 범위를 분리하고, cgroups로 CPU랑 메모리 사용량을 제한할 뿐이에요. 실체는 격리된 프로세스라서 기동은 1초 미만, 메모리도 수십 MB부터 돌아갑니다.

이 차이가 실무에 가져오는 가치는 밀도랑 속도입니다. 같은 서버에 몇 배의 수를 담을 수 있고요, 이미지가 레이어 구조로 캐시되니까 CI/CD가 빠릅니다. 그리고 "개발 환경에서는 됐는데"라는 문제가 의존 관계째로 이미지에 굳혀지면서 해소됩니다.

한편 트레이드오프도 명확합니다. 커널을 공유한다는 건 격리의 벽이 VM보다 얇다는 뜻입니다. 커널 취약점을 찔리면 컨테이너 밖으로 나갈 가능성이 있고, 호스트랑 다른 커널이 필요한 OS는 안 돌아갑니다. 그래서 멀티테넌트로 신뢰할 수 없는 코드를 돌릴 때는 VM이나 gVisor 같은 샌드박스를 검토합니다. 용도로 나눠 써야 하는 거지, 컨테이너가 항상 VM의 상위 호환은 아닙니다.

### Q39. Kubernetesを導入する最大のメリット
(쿠버네티스 도입의 최대 장점)

**🇯🇵 回答**

最大のメリットは、あるべき状態を宣言すれば、そこに収束させ続けてくれることだと思っています。

具体的には三つの形で現れます。第一に自己修復です。Podが落ちてもノードが死んでも、定義したレプリカ数になるよう自動で再作成されます。夜間にプロセスが落ちて朝まで気づかない、ということがなくなります。第二にオートスケールで、負荷に応じてHPAがPod数を増減させます。第三にローリングアップデートとロールバックが標準機能として使えることです。

そしてもう一つ、地味ですが実務で効くのがサービスディスカバリです。Podは死んで再作成されるたびIPが変わりますが、Service経由で名前解決するので、呼ぶ側は相手のIPを意識しなくてよくなります。

ただし正直に申し上げると、Kubernetesは無料ではありません。運用の複雑さは確実に増えます。特に効果を出すために必須なのが、リソースのrequests/limits設定と、liveness・readinessプローブの適切な実装です。ここを雑にすると、起動途中のPodにトラフィックが流れたり、逆にヘルスチェックが厳しすぎて再起動ループに入ったりします。チーム規模が小さくてサービス数も少ない段階なら、マネージドのコンテナサービスのほうが合理的なことも多いと思っています。

**🇰🇷 답변**

가장 큰 장점은, 있어야 할 상태를 선언하면 거기로 계속 수렴시켜 준다는 점이라고 생각합니다.

구체적으로는 세 가지 형태로 나타납니다. 첫째 자가 치유입니다. Pod가 죽어도 노드가 죽어도, 정의한 레플리카 수가 되도록 자동으로 재생성됩니다. 야간에 프로세스가 죽어서 아침까지 모르는 일이 없어집니다. 둘째 오토스케일로, 부하에 따라 HPA가 Pod 수를 늘리고 줄입니다. 셋째 롤링 업데이트랑 롤백을 표준 기능으로 쓸 수 있다는 겁니다.

그리고 하나 더, 수수하지만 실무에서 효과적인 게 서비스 디스커버리입니다. Pod는 죽고 재생성될 때마다 IP가 바뀌는데, Service를 통해 이름 해결을 하니까 호출하는 쪽은 상대의 IP를 신경 안 써도 됩니다.

다만 솔직히 말씀드리면 쿠버네티스는 공짜가 아닙니다. 운영 복잡도는 확실히 늘어납니다. 특히 효과를 내려면 필수인 게 리소스 requests/limits 설정이랑, liveness·readiness 프로브의 적절한 구현입니다. 여기를 대충 하면 기동 중인 Pod로 트래픽이 흐르거나, 반대로 헬스체크가 너무 빡빡해서 재시작 루프에 빠집니다. 팀 규모가 작고 서비스 수도 적은 단계라면 매니지드 컨테이너 서비스가 더 합리적인 경우도 많다고 생각합니다.

### Q40. Blue-Greenデプロイとカナリアリリースの違い
(Blue-Green 배포와 카나리 릴리스의 차이)

**🇯🇵 回答**

Blue-Greenは、新バージョンの環境を丸ごと立ち上げて、動作確認をしてからトラフィックを一気に100%切り替える方式です。最大の利点は切り戻しが数秒で済むことですね。問題が起きたらロードバランサーの向き先を戻すだけですから。欠点は環境を二面持つのでインフラコストが倍かかること、そして切り替えた瞬間に全ユーザーが新バージョンに乗るので、検知が遅れると影響が全体に及ぶことです。

カナリアは、新バージョンに1%、5%、10%と段階的にトラフィックを流していきます。その間エラー率とレイテンシを監視して、問題なければ比率を上げていく方式ですね。影響範囲を限定できるのが最大の価値で、本番でしか出ない問題を少数のユーザーで検知できます。欠点は、判定の自動化と十分なメトリクスがないと機能しないこと。そして2バージョンが同時に動く期間が長くなることです。

実務で本当に難しいのは、どちらの方式でもDBスキーマの変更なんですよ。ロールバックしてもDBは戻せないので、カラム追加と削除を同一リリースでやらない、いわゆる拡張・縮小方式を徹底します。新旧どちらのコードでも動くスキーマを一度経由してから、後続リリースで古いカラムを消します。

使い分けとしては、影響が読みにくい大きな変更やパフォーマンス特性が変わる変更はカナリア。影響が限定的で早く出したいものはBlue-Green、という感じです。両者を併用して、機能単位の出し分けはフィーチャーフラグで別管理するのが今の主流だと思っています。

**🇰🇷 답변**

Blue-Green은 새 버전 환경을 통째로 띄워서 동작 확인을 한 다음, 트래픽을 한 번에 100% 전환하는 방식입니다. 최대 이점은 롤백이 몇 초면 끝난다는 거예요. 문제가 생기면 로드밸런서 방향만 되돌리면 되니까요. 단점은 환경을 두 벌 유지하니까 인프라 비용이 배로 든다는 것, 그리고 전환하는 순간 모든 사용자가 새 버전으로 옮겨가니까 탐지가 늦으면 영향이 전체에 미친다는 겁니다.

카나리는 새 버전에 1%, 5%, 10%로 단계적으로 트래픽을 흘려보냅니다. 그동안 에러율이랑 레이턴시를 모니터링해서 문제없으면 비율을 올려가는 방식이고요. 영향 범위를 한정할 수 있는 게 최대 가치라서, 프로덕션에서만 나오는 문제를 소수 사용자로 탐지할 수 있습니다. 단점은 판정 자동화랑 충분한 메트릭이 없으면 기능하지 않는다는 것. 그리고 두 버전이 동시에 도는 기간이 길어진다는 겁니다.

실무에서 진짜 어려운 건 어느 방식이든 DB 스키마 변경이에요. 롤백해도 DB는 못 되돌리니까, 컬럼 추가랑 삭제를 같은 릴리스에서 안 하는, 이른바 확장·축소 방식을 철저히 지킵니다. 신·구 어느 코드에서도 돌아가는 스키마를 한 번 거친 다음에, 후속 릴리스에서 옛 컬럼을 지웁니다.

구분해서 쓰자면, 영향을 읽기 어려운 큰 변경이나 성능 특성이 바뀌는 변경은 카나리. 영향이 한정적이고 빨리 내고 싶은 건 Blue-Green, 이런 식입니다. 양쪽을 병용하고 기능 단위의 노출 제어는 피처 플래그로 따로 관리하는 게 지금 주류라고 생각합니다.

### Q41. KafkaとRabbitMQの違い
(Kafka와 RabbitMQ의 차이)

**🇯🇵 回答**

根本的な違いは、Kafkaが「ログ」で、RabbitMQが「キュー」だという点です。

RabbitMQはメッセージブローカーです。コンシューマーがACKを返した時点で、メッセージはキューから消えます。一件ずつの配送保証と、Exchangeによる柔軟なルーティング、優先度や遅延配送といった機能が強みですね。タスク分配やRPC的な用途に向いています。

Kafkaは分散コミットログです。メッセージはディスクに追記されて、消費されても保持期間が来るまで消えません。コンシューマーは自分がどこまで読んだかというオフセットを持つだけです。この構造から二つの強みが出てきます。一つは過去に遡っての再処理で、バグを直したあとオフセットを戻して同じデータを流し直せます。もう一つは、同じデータを複数の用途で独立に読めることです。リアルタイム処理と分析基盤への転送が、互いに干渉しません。あと順次書き込みなのでスループットも桁違いです。

使い分けとしては、イベントストリーミング、大量ログ、複数の下流で同じデータを使う、再処理が必要。こういう場合はKafkaです。細かいルーティング、優先度、遅延メッセージ、少量でも低レイテンシなタスクキュー。こういう場合はRabbitMQを選びます。

一点付け加えると、Kafkaは順序保証がパーティション単位である点に注意が必要です。同じキーは同じパーティションに行くので、注文IDをキーにすればその注文内の順序は保証されます。でも全体の順序は保証されません。ここを誤解すると、本番で順序逆転の事故になります。

**🇰🇷 답변**

근본적인 차이는 Kafka가 "로그"이고 RabbitMQ가 "큐"라는 점입니다.

RabbitMQ는 메시지 브로커입니다. 컨슈머가 ACK를 반환한 시점에 메시지가 큐에서 사라집니다. 건별 배송 보증이랑 Exchange를 통한 유연한 라우팅, 우선순위나 지연 배송 같은 기능이 강점이고요. 태스크 분배나 RPC적인 용도에 적합합니다.

Kafka는 분산 커밋 로그입니다. 메시지는 디스크에 추가되고, 소비되어도 보존 기간이 올 때까지 안 사라집니다. 컨슈머는 자기가 어디까지 읽었는지의 오프셋을 가질 뿐이에요. 이 구조에서 두 가지 강점이 나옵니다. 하나는 과거로 거슬러 올라간 재처리로, 버그를 고친 뒤에 오프셋을 되돌려서 같은 데이터를 다시 흘릴 수 있습니다. 다른 하나는 같은 데이터를 여러 용도로 독립적으로 읽을 수 있다는 것. 실시간 처리랑 분석 기반으로의 전송이 서로 간섭하지 않습니다. 그리고 순차 쓰기라서 스루풋도 자릿수가 다릅니다.

구분해서 쓰자면, 이벤트 스트리밍, 대량 로그, 여러 하류에서 같은 데이터를 쓰는 경우, 재처리가 필요한 경우. 이럴 땐 Kafka입니다. 세밀한 라우팅, 우선순위, 지연 메시지, 소량이어도 저지연인 태스크 큐. 이럴 땐 RabbitMQ를 고릅니다.

한 가지 덧붙이면, Kafka는 순서 보증이 파티션 단위라는 점에 주의가 필요합니다. 같은 키는 같은 파티션으로 가니까, 주문 ID를 키로 하면 그 주문 안에서의 순서는 보증됩니다. 그런데 전체 순서는 보증이 안 돼요. 여기를 오해하면 프로덕션에서 순서 역전 사고가 납니다.

### Q42. トラフィック急増時にKafkaでシステムを守る
(트래픽 급증 시 Kafka로 시스템을 지키기)

**🇯🇵 回答**

考え方は負荷平準化です。瞬間的なピークをそのままDBに流すんじゃなくて、Kafkaに一度受け止めて、コンシューマーが処理できる速度でだけ引き取ります。書き込みは順次追記なので、Kafka自体は非常に高いスループットに耐えます。

APIの設計もこれに合わせます。リクエストを受けたら最低限の検証だけしてKafkaにpublishして、即座に202 Acceptedと受付IDを返します。ユーザーには別のエンドポイントかWebSocketで完了を通知します。同期でDBまで書き切ろうとするから詰まるので、同期パスを最短にするのが本質ですね。

コンシューマー側では、DBへの書き込みをバッチにまとめてラウンドトリップを減らして、リトライで重複が来る前提で冪等キーによる重複排除を入れます。

ただし、正直に言うとキューは万能じゃありません。キューは負荷を遅らせるだけで、消してはくれないんですよ。到着レートが処理能力を継続的に超えていれば、ラグは無限に伸びてデータは古くなり続けます。だから前段でレート制限を入れて過剰な流入自体を止めること、そしてスケールの限界を事前に把握しておくことが必要です。

特にコンシューマーはパーティション数より増やせません。なのでパーティション数は、将来の並列度を見越して設計時に決めておきます。ここは後から増やしにくいポイントです。

**🇰🇷 답변**

사고방식은 부하 평준화입니다. 순간적인 피크를 그대로 DB로 흘리는 게 아니라, Kafka에 한 번 받아 두고 컨슈머가 처리할 수 있는 속도로만 가져갑니다. 쓰기가 순차 추가라서 Kafka 자체는 아주 높은 스루풋을 견딥니다.

API 설계도 여기에 맞춥니다. 요청을 받으면 최소한의 검증만 하고 Kafka에 publish한 다음, 즉시 202 Accepted랑 접수 ID를 반환합니다. 사용자한테는 별도 엔드포인트나 WebSocket으로 완료를 알립니다. 동기로 DB까지 다 쓰려고 하니까 막히는 거라서, 동기 경로를 최단으로 하는 게 본질입니다.

컨슈머 쪽에서는 DB 쓰기를 배치로 묶어서 라운드트립을 줄이고, 재시도로 중복이 온다는 전제로 멱등 키를 통한 중복 제거를 넣습니다.

다만 솔직히 말하면 큐는 만능이 아닙니다. 큐는 부하를 미룰 뿐이지 없애 주지는 않거든요. 도착 레이트가 처리 능력을 지속적으로 넘으면, 랙은 무한히 늘어나고 데이터는 계속 오래됩니다. 그래서 앞단에 레이트 리밋을 넣어서 과도한 유입 자체를 막는 것, 그리고 스케일의 한계를 미리 파악해 두는 게 필요합니다.

특히 컨슈머는 파티션 수보다 늘릴 수 없습니다. 그래서 파티션 수는 미래의 병렬도를 내다보고 설계 시점에 정해 둡니다. 여기는 나중에 늘리기 어려운 지점이에요.

### Q43. Kafkaコンシューマーの再処理戦略
(Kafka 컨슈머 재처리 전략)

**🇯🇵 回答**

前提として、同じパーティション内でリトライを繰り返すのは避けます。Kafkaはオフセット順に処理するので、一件が詰まるとその後ろが全部止まってしまうんですよ。ヘッドオブラインブロッキングというやつです。一件の不正データで数万件が止まります。

そこでノンブロッキングリトライを採ります。失敗したメッセージは元のトピックでは処理済みとしてコミットして、リトライ専用トピックに移します。リトライトピックは遅延の段階を分けて用意して、5秒後、1分後、10分後というふうに間隔を広げながら再試行させます。ここでも失敗したらDLQに退避させます。Spring Kafkaなら `@RetryableTopic` でこの構成を宣言的に組めます。

ただしトレードオフを明示すべきで、リトライトピックに移した時点でそのメッセージの順序は崩れます。順序が業務要件に含まれる場合、たとえば同一口座の入出金みたいなケースでは、この方式は使えません。その場合は該当キーの処理を一時停止させるか、そもそも順序に依存しない設計に変えるかを検討します。

エラーの分類も重要です。相手のタイムアウトみたいな一時的エラーはリトライで回復しますが、必須項目が欠けたデータは何度やっても失敗します。こういうのは即座にDLQへ送るほうが無駄がありません。

最後にDLQは、入れて終わりでは意味がないです。件数をメトリクス化してアラートを出して、再投入する運用手段まで用意して、初めて完成だと考えています。

**🇰🇷 답변**

전제로, 같은 파티션 안에서 재시도를 반복하는 건 피합니다. Kafka는 오프셋 순으로 처리하니까, 한 건이 막히면 그 뒤가 전부 멈춰 버리거든요. 헤드 오브 라인 블로킹이라는 거죠. 한 건의 불량 데이터로 수만 건이 멈춥니다.

그래서 논블로킹 재시도를 씁니다. 실패한 메시지는 원래 토픽에서는 처리 완료로 커밋하고, 재시도 전용 토픽으로 옮깁니다. 재시도 토픽은 지연 단계를 나눠서 준비해서, 5초 후·1분 후·10분 후 이런 식으로 간격을 넓히면서 재시도시킵니다. 여기서도 실패하면 DLQ로 대피시키고요. Spring Kafka라면 `@RetryableTopic`으로 이 구성을 선언적으로 짤 수 있습니다.

다만 트레이드오프를 명시해야 하는데, 재시도 토픽으로 옮긴 시점에 그 메시지의 순서는 깨집니다. 순서가 업무 요건에 포함된 경우, 예를 들어 같은 계좌의 입출금 같은 케이스에서는 이 방식을 못 씁니다. 그럴 땐 해당 키의 처리를 일시 정지시키거나, 애초에 순서에 의존하지 않는 설계로 바꿀지를 검토합니다.

에러 분류도 중요합니다. 상대의 타임아웃 같은 일시적 에러는 재시도로 회복되지만, 필수 항목이 빠진 데이터는 몇 번을 해도 실패합니다. 이런 건 즉시 DLQ로 보내는 게 낭비가 없습니다.

마지막으로 DLQ는 넣고 끝이면 의미가 없어요. 건수를 메트릭화해서 알림을 걸고, 재투입하는 운영 수단까지 준비해야 비로소 완성이라고 생각합니다.

### Q44. コネクションリークの検出と調査 【Q18の深掘り版】
(커넥션 누수 탐지와 조사 — Q18 심화판)

> ⚠️ Q18과 동일한 질문입니다. 여기서는 "누수인가, 장시간 점유인가, 애초에 풀 부족인가"의 판별 프로세스에 축을 둔 다른 버전입니다.

**🇯🇵 回答**

まず、症状が似ている三つを切り分けるところから始めます。プールが枯渇しているという現象は同じでも、原因が「返却されていない(リーク)」「返却は遅いが返ってはいる(長時間占有)」「単純にプールが小さい(容量不足)」の三つに分かれて、対処が全く違うからです。

判別にはメトリクスの形を見ます。負荷が下がっても `hikaricp.connections.active` が減らずに階段状に増え続けるなら、リークです。負荷に連動して増減するけれどピークで `pending` が発生するなら、占有か容量不足ですね。占有か容量不足かは、平均の貸出時間を見れば分かります。数百ミリ秒なら容量不足、数秒以上なら何かを待っています。

リークだと判断したら `leakDetectionThreshold` を設定します。これは指定時間を超えて返却されないコネクションについて、借りた時点のスタックトレースを警告ログに出力するものです。犯人のメソッドが直接特定できます。それでも分からなければスレッドダンプを取って、どのスレッドがどこで止まっているかを確認します。

原因として実際に多いのは三つです。`DataSource` から直接取得して try-with-resources を使っていない箇所。`@Transactional` の内側で外部API呼び出しをしていて、相手の遅延をそのまま持ち込んでいるケース。そしてOSIVが有効で、ビュー描画までセッションを保持しているケースです。二番目は厳密にはリークじゃないんですが、症状も対処も同じで、トランザクション境界からI/O待ちを外に出すのが解決策になります。

**🇰🇷 답변**

먼저, 증상이 비슷한 세 가지를 구분하는 것부터 시작합니다. 풀이 고갈된다는 현상은 같아도 원인이 "반환되지 않음(누수)", "반환은 느리지만 돌아옴(장시간 점유)", "단순히 풀이 작음(용량 부족)" 세 가지로 갈리고, 대처가 완전히 다르기 때문입니다.

판별에는 메트릭의 형태를 봅니다. 부하가 내려가도 `hikaricp.connections.active`가 안 줄고 계단식으로 계속 늘면 누수입니다. 부하에 연동해서 증감하는데 피크에서 `pending`이 발생하면 점유거나 용량 부족이고요. 점유인지 용량 부족인지는 평균 대출 시간을 보면 알 수 있습니다. 수백 밀리초면 용량 부족, 수 초 이상이면 뭔가를 기다리고 있는 겁니다.

누수라고 판단되면 `leakDetectionThreshold`를 설정합니다. 이건 지정한 시간을 넘겨서 반환되지 않은 커넥션에 대해, 빌린 시점의 스택 트레이스를 경고 로그로 출력해 주는 겁니다. 범인 메서드를 직접 특정할 수 있어요. 그래도 모르겠으면 스레드 덤프를 떠서 어느 스레드가 어디서 멈춰 있는지 확인합니다.

원인으로 실제로 많은 건 세 가지입니다. `DataSource`에서 직접 얻으면서 try-with-resources를 안 쓴 부분. `@Transactional` 안쪽에서 외부 API를 호출해서 상대의 지연을 그대로 끌어들이는 케이스. 그리고 OSIV가 켜져 있어서 뷰 렌더링까지 세션을 유지하는 케이스입니다. 두 번째는 엄밀히는 누수가 아닌데, 증상도 대처도 같아서 트랜잭션 경계에서 I/O 대기를 밖으로 빼는 게 해결책이 됩니다.

### Q45. オートスケーリングのトリガー条件設計
(오토스케일링 트리거 조건 설계)

**🇯🇵 回答**

CPU使用率だけをトリガーにするのは、多くのアプリケーションで不適切だと考えています。Webアプリの大半はI/O待ちが主なので、DBの応答が遅くてリクエストが詰まっていても、CPUは低いままなんですよ。CPUが上がった頃には、もう手遅れです。

だからアプリの特性に合わせたカスタムメトリクスを使います。API層ならリクエストレートかp95レイテンシ、あるいはスレッドプールの使用率。Kafkaコンシューマーならコンシューマーラグが最も適切で、ラグが一定件数を超えたらPodを増やす、というのが一番素直な指標です。KEDAを使えば、こうした外部メトリクスでのスケールが素直に組めます。

設計上、必ず考慮する点が三つあります。

第一に、スケールアウトには時間がかかること。イメージのpull、JVMの起動とウォームアップまで含めると数十秒から数分かかるので、閾値は限界の手前、たとえば使用率70%程度で先に発火させます。

第二にフラッピング防止です。スケールインには長めの安定化ウィンドウを設定します。増減を繰り返すと接続断が頻発しますから。

第三に、下流の限界を必ず確認すること。Podを10倍にしてもDBの最大接続数は変わらないので、無邪気にスケールするとDB側を落とします。1Podあたりのプールサイズ×最大Pod数が、DBの上限を超えないよう逆算しておきます。

最後に、急激なスパイクは事後のスケールでは間に合わないので、イベントが分かっている場合はスケジュールベースで事前にスケールさせます。

**🇰🇷 답변**

CPU 사용률만 트리거로 삼는 건 많은 애플리케이션에서 부적절하다고 생각합니다. 웹 앱은 대부분 I/O 대기가 주니까, DB 응답이 느려서 요청이 밀려도 CPU는 낮게 유지되거든요. CPU가 올라갔을 때는 이미 늦습니다.

그래서 앱 특성에 맞춘 커스텀 메트릭을 씁니다. API 계층이면 요청 레이트나 p95 레이턴시, 아니면 스레드 풀 사용률. Kafka 컨슈머면 컨슈머 랙이 가장 적절하고, 랙이 일정 건수를 넘으면 Pod를 늘리는 게 제일 자연스러운 지표입니다. KEDA를 쓰면 이런 외부 메트릭 기반 스케일을 무리 없이 구성할 수 있습니다.

설계상 반드시 고려하는 점이 세 가지 있습니다.

첫째, 스케일 아웃에는 시간이 걸린다는 것. 이미지 pull, JVM 기동이랑 워밍업까지 포함하면 수십 초에서 수 분 걸리니까, 임계치는 한계 앞에서, 예를 들어 사용률 70% 정도에서 먼저 발화시킵니다.

둘째 플래핑 방지입니다. 스케일 인에는 긴 안정화 윈도를 설정합니다. 늘었다 줄었다를 반복하면 접속 단절이 빈발하니까요.

셋째, 하류의 한계를 반드시 확인할 것. Pod를 10배로 해도 DB 최대 접속 수는 안 변하니까, 순진하게 스케일하면 DB 쪽을 죽입니다. 1Pod당 풀 사이즈 × 최대 Pod 수가 DB 상한을 안 넘도록 역산해 둡니다.

마지막으로, 급격한 스파이크는 사후 스케일로는 못 따라가니까, 이벤트를 아는 경우에는 스케줄 기반으로 미리 스케일시킵니다.
