> *Optimizing Cloud Native Java* 2판(2024) 14장 요약. **책의 기준 시점은 2024년 8월, JDK 21** 이다.
> 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판 14장 「고성능 로깅과 메시징」의 자리에 들어왔지만 내용은 전혀 다르다.** 1판 14장은

## 1. 이 장의 핵심 주장

1. 분산 시스템의 출발점은 **분산 컴퓨팅의 8가지 오류**(Deutsch·Gosling)다. 마이크로서비스는 분산 연결 수를
   늘려 오류의 영향을 키운다 — "확장하려고 분산했는데 정반대가 될 수 있다."
2. 기본 빌딩 블록: **세대 시계(generation clock)**, 불변 객체, **세그먼트 ID 할당**, **WAL(write-ahead log)**,
   **2단계 커밋**, 직렬화 선택, **파티셔닝·복제**, CAP.
3. 합의는 **Paxos**(제안자/수락자/학습자, 쿼럼)와 **Raft**(리더 선출 + 로그 복제, 세 역할·두 상태). 둘 다
   **FLP 불가능성** 때문에 라이브락을 이론적으로 배제하지 못하고 무작위 지연으로 확률만 낮춘다.
4. 실전 사례 — **Cassandra**(AP, 일관성 수준, 경량 트랜잭션은 Paxos), **Infinispan**(jgroups-raft, `Cache extends Map`),
   **Kafka**(순서 있는 복제 로그, 파티션 = 순서 단위, **KRaft**).
5. Fighting Animals 에 Kafka 로 병원 서비스를 붙이고 Infinispan 으로 부상 동물을 공유한다 — 그러면서
   **부분 가용성**(병원이 죽으면 전체를 죽일 것인가)과 **인프라 컴포넌트의 관측 가능성**을 묻는다.

## 2. 절별 상세 요약

### 2-1. 기본 분산 자료구조

| 블록 | 요지 | 관련 오류 |
|---|---|---|
| **세대 시계** | 단조 증가 값을 모든 메시지·복제 로그에 붙인다. 리더가 잠시 끊겼다 돌아오면 팔로워는 옛 세대의 메시지를 버린다 | 토폴로지 변화 |
| **불변 객체** | 직렬화만 되면 잃어버린 갱신 없이 네트워크로 보낼 수 있다 | — |
| **세그먼트 ID** | 리더가 `AtomicLong` 으로 100만 개 단위 세그먼트를 나눠 주고 팔로워는 로컬 카운터로 발급 → 네트워크 왕복·경합이 거의 사라진다. 대가: 팔로워 간 순서 없음, 다운 시 구멍, 리더 재시작 시 0 부터(영속 저장으로 완화). UUID 도 대안 | 지연 0 아님 |
| **WAL** | 영속 저장소의 순서 있는 추가 전용 로그. 크래시 복구, 체크포인트 후 적용·삭제 | — |
| **2단계 커밋** | 준비(리더 WAL → 팔로워 WAL → 약속) / 커밋(최종 표시 → 적용 → ACK). 단순·원자적·라이브니스. **단점**: 노드 수에 선형, 하나만 실패해도 처음부터, 가장 느린 노드가 지연을 정하고, 준비 중에는 자원이 **블로킹**된다. 실전 구현은 타임아웃과 GC 일시정지 같은 일시 장애를 다뤄야 한다(Kleppmann 참고) | 네트워크 신뢰성 |
| **직렬화** | 자바 내장 직렬화는 *"보이지 않는 공개 생성자"*(Goetz) — 보안 사고의 온상이라 대부분 라이브러리로. JSON 은 단순·가독·범용이지만 크기가 성능을 깎고, 고성능이면 Protobuf·Avro 같은 바이너리. 20년 전 XML 직렬화가 서비스 성능의 관문이었던 것처럼 원칙은 그대로 | 전송 비용·대역폭 |
| **파티셔닝·복제** | 수평(행)/수직(열). 키 해시로 분할(Kafka 방식). 복제본 동기 1개가 기본, 롤링 업데이트 중에도 보호하려면 2개. **동기 복제본마다 잠금**이 필요해 많을수록 비싸다(분산판 잃어버린 갱신 방지). write-through 는 확실하지만 느리고 write-behind 는 창이 있다. **재파티셔닝을 관측하라** — 노드 수에 최소 선형, 때로 제곱 | 네트워크 신뢰성 |
| **CAP** | 셋 중 둘. 파티션 시 가용성을 택하면 조각마다 로컬 일관성만(스플릿 브레인). 데이터센터 안에서는 완전 파티션이 드물어 WAN 문제로 보는 견해도 있다 | 신뢰성·토폴로지 |

### 2-2. 합의 프로토콜

- 관측 팁: 클러스터 전이 이벤트가 어떻게 생겼는지 알고 **첫 발생에는 알림하지 마라** — 정상 운영에서도
  드물게 일어난다. ZooKeeper 라면 "연속 두 모니터링 간격 동안 리더 다수" 는 있어선 안 된다.
- **Paxos**: 1a Prepare(N) → 1b Promise → 2a Accept(N, V) → 2b Accepted(더 높은 N 을 약속하지 않았을 때만).
  쿼럼이면 진행. 학습자(ZooKeeper 의 observer)는 투표 없이 결과만 받아 읽기 부하를 줄인다. Cassandra·DynamoDB·
  Chubby. ZooKeeper 의 ZAB 은 Paxos 변종(각주).
- **FLP(1985)**: 비동기 시스템에서 안전성·라이브니스·내결함성 중 둘만. 무작위 지연이 우회책.
- **Raft**: 리더 선출 + 로그 복제. 역할 Leader/Follower/Candidate, 상태 Stable/Election. 리더가 100ms 마다
  하트비트(`AppendEntry` 의 빈 페이로드). 하트비트가 끊기면 `RequestVote`. 텀(=세대 시계). 쿼럼에 복제되면
  커밋 인덱스 전진. 로그가 최신인 후보만 이길 수 있고 선거 타임아웃이 무작위라 실전에서 라이브락은 없지만
  증명은 못 한다. 책은 메시지를 **record** 로 보여 준다. 구현이 맞다는 보장은 별개 — jgroups-raft 가 검증된 예.

### 2-3. 사례

**Cassandra** — 자바, 컬럼 지향, 기본 AP, **쿼리 단위로 일관성 수준** 조정: `ONE` < `LOCAL_QUORUM` < `QUORUM` < `ALL`
(빠른 순). `ALL` 은 노드 하나 죽으면 쓰기가 실패해 AP 설계와 어긋난다 — 쓰고 싶어진다면 **아키텍처 냄새**.
CQL 은 SQL 과 겉이 같지만 조인·서브쿼리가 없고 `INSERT`/`DELETE` 의미가 다르다("`var x = 15;` 는 자바에서도
JS 에서도 유효하지만 뜻이 다르다"). 테이블은 사실 컬럼 패밀리, 키스페이스는 복제 단위(앱당 하나가 보통).
**경량 트랜잭션**(`INSERT ... IF NOT EXISTS`)은 Paxos 로 선형화 가능성을 주고 `SERIAL` 수준을 쓴다 — 일반 연산과 섞지 마라.

**Infinispan** — Red Hat, JBoss Cache 후속. 분산 캐시 + 키-값 저장소, 영속 스토어 플러그인. **jgroups** 가
발견·장애 감지·전송, **jgroups-raft** 가 내결함성. AP, 복제 계수 설정. `Cache extends java.util.Map`("기계를 넘는
큰 HashMap"), JTA/XA 참여 가능(끄면 빠르다), jgroups 에 OTel 트레이싱 확장.

**Kafka** — 처리량 우선 설계의 pub/sub, 클라이언트-브로커. 심장은 **순서 있는 복제 로그**: 추가만 있고 갱신이
없어 읽기·쓰기가 순차라 프리페치·캐시·배칭이 먹힌다. 토픽 = 파티션 묶음의 라벨. **파티션 하나는 컨슈머 하나가,
컨슈머 하나는 여러 파티션을** → 활성 컨슈머 수 ≤ 파티션 수(대기 컨슈머는 핫 스탠바이). 순서는 **파티션 안에서만**.
`ProducerRecord{topic, partition, headers, key, value, timestamp}` — 보통 키 해시로 파티션이 정해져 같은 키는
같은 순서. 파티션을 직접 주거나 라운드로빈이면 순서를 잃는다. 전송 계층 인증으로 "네트워크는 안전하다" 오류를
완화(토픽별 읽기/쓰기 권한 → 멀티테넌트·GDPR). **ZooKeeper 에서 자체 Raft 인 KRaft 로** 전환 — 컴포넌트가 줄어든다.

### 2-4. Fighting Animals 확장

- 병원 서비스 선택지: Cassandra 공유 테이블 / Infinispan 맵 / **Kafka** 메시지. 웹 서비스 자체를 jgroups-raft
  클러스터로 묶는 것은 스테이트리스라 과하다 — 로드밸런싱은 K8s 에 맡긴다.
- Kafka 3노드(`debezium/kafka:2.7.0.Final`, `KAFKA_CONTROLLER_QUORUM_VOTERS`, **KRaft**), 잎 서비스(Feline·Fish·
  Mustelid)가 `KafkaProducer<String,String>` 으로 `ProducerRecord("FELINE", uuid, cat)` 전송. 토픽 자동 생성 로그.
  기동·종료가 눈에 띄게 느려지고 로그가 시끄럽다 — 단일 노드로 피할 수 있지만 선출과 KRaft 를 보여 주려 3노드.
- 병원은 **Quarkus + SmallRye Reactive Messaging**: `@Incoming` 반복 애너테이션으로 세 토픽, `Message<String>` →
  `getMetadata(IncomingKafkaRecordMetadata)` 로 토픽 추출, **수동 `message.ack()`**, 반환 `CompletionStage<Void>`.
  ⚠️ 수동 ACK 면 **모든 경로(예외 포함)에서 ack** 하지 않으면 오프셋이 안 나가 재소비된다.
- 능동 병원: `quarkus-infinispan-client`, `@Remote("animals") RemoteCache<String,String>` 에 `put(topic, payload)`.
  잎 서비스는 `RemoteCacheManager` 로 부상 동물을 조회해 `do { … } while (injured.equals(cat))` 로 피한다.
  Kafka 는 1노드로 줄인다(`docker compose up --remove-orphans` 로 옛 컨테이너 정리).
- **부분 가용성**: HTTP → Kafka → 병원 → 캐시는 부분 비동기다. 병원이 죽으면? 요청이 빨라서 어차피 부상 동물이
  뽑힐 수 있으니 **병원 장애가 전체 장애가 되면 안 된다** — Kafka·Infinispan 도 같은 논리. 그리고 예제에서 껐던
  Infinispan 의 OpenTelemetry 는 운영에서는 필수다.

## 3. 1판(2018)과 달라진 점

- **주제 교체.** 1판 14장의 로깅 라이브러리 성능(Log4j 2 ✅ 23회)·Aeron/Agrona(✅ 59회)는 2판 전권에서 사라졌다.
  2판의 Kafka·Raft·Paxos·Cassandra·Infinispan 은 1판에 전부 0회 ✅.
- 1판 12장 「동시성 기법」의 단일 머신 개념(잃어버린 갱신·라이브락·`AtomicLong`)을 **분산으로 일반화**하는 서술이
  이 장의 뼈대다("분산판 Lost Update", "분산 LiveLock").
- 관심사가 "지연 마이크로초" 에서 "합의·가용성·관측" 으로 옮겨 갔다. 저지연 자바가 필요하면 1판 14장을 따로 봐야 한다.

| 책의 서술 | 지금 | 근거 |
|---|---|---|

| `debezium/kafka:2.7.0.Final`, Infinispan 14.0.21 | 고정 버전 예시. 이 저장소의 `verify-labs-kafka` 는 compose 의 Kafka 로 돈다(버전은 `compose.yaml`) | ✅ 존재 |
| Cassandra 는 기본 AP | 변함없음(문서) | 📄 |
| `ForkJoinPool.commonPool-worker` 가 Infinispan 기동 로그에 보인다 | commonPool 병렬성은 지금도 `availableProcessors - 1` | ✅ 17·21·25 (procs=4 → 3), CN-09A |

JVM 버전 때문에 틀리는 문장은 없다. **바뀌는 것은 인프라 버전**이고, 그건 책도 "배포 전에 올려라"고 쓴다.

## 6. 면접에서 쓸 수 있는 문장

- "Kafka 의 순서 보증은 토픽이 아니라 파티션 단위입니다. 키 해시로 파티션이 정해지니 같은 키 안에서만 순서가
  지켜지고, 파티션을 직접 지정하거나 라운드로빈으로 바꾸는 순간 그것도 잃습니다."
- "2단계 커밋은 이해하기 쉽지만 가장 느린 노드가 지연을 정하고 준비 단계에서 자원이 묶입니다. 그래서 규모가
  커지면 Raft 같은 쿼럼 기반 합의로 갑니다."
- "Cassandra 에서 `ALL` 일관성을 쓰고 싶어진다면 설계 어딘가가 잘못됐다는 신호입니다. AP 데이터베이스에 CP 를
  요구하는 것이니까요."
