## 1. 이 장의 핵심 주장

1. **좋은 성능 테스트는 정량적**이다 — 숫자로 답이 나오는 질문을 먼저 적어라. "성능 테스트" 라고 뭉뚱그리지 말고
   지연·처리량·스트레스·부하·내구·용량 계획·성능 저하(degradation) 중 무엇인지 정하라.
2. **평균은 지연 측정에 쓸모가 없다.** JVM 의 응답 분포는 정규분포가 아니라 **긴 꼬리**이고, 이상치가 곧 불만 고객이다.
   표준편차·분산은 "기본적으로 쓸모없다". 대신 **로그 스케일 퍼센타일**(평균 → 90 → 99 → 99.9 …)과 HdrHistogram.
3. 세 황금률: 무엇을 신경 쓰는지 정하고 재는 법을 찾아라 / **쉬운 것이 아니라 중요한 것을** 최적화하라 / 가장 큰 기여분부터.
4. **하향식(top-down)** — 전체 시스템 벤치마크가 코드 조각 측정보다 **쉽고 정확하다.** 대수의 법칙이 편이 되기 때문이다.
5. 테스트 환경은 운영의 **정확한 복제**여야 한다. 아니면 예측력이 없다. 이것을 아끼는 것은 거의 항상 잘못된 절약이다.
6. 오차에는 **무작위 오차**(정밀도)와 **계통 오차**(정확도)가 있다. 뭄바이에서 런던 서비스를 재면 120~150ms 왕복이
   전부를 덮는다 — 앱 문제가 아니라 **테스트 설정이 운영을 복제하지 못한** 계통 오차다.
7. **상관은 인과가 아니다.** 그리고 사람은 패턴을 보고 싶어 한다 — 인지 편향(환원주의·확인 편향·전장의 안개·위험 회피)이
   부록 B 의 안티패턴을 낳는다.

## 2. 절별 상세 요약

### 2-1. 성능 테스트의 종류

| 테스트 | 묻는 질문 | 주의 |
|---|---|---|
| **지연(latency)** | 트랜잭션 종단 시간은? | 가장 흔하고 경영진이 좋아해서 **여기에만 집착**하기 쉽다. 평균은 무의미(§2-4) |
| **처리량** | 현재 용량으로 동시 트랜잭션 몇 개? | 지연과 **쌍대**다 — 지연은 알려진 처리량에서, 처리량은 지연이 터지지 않는 범위에서 말해야 한다. 최대 처리량 = 지연 분포가 갑자기 바뀌는 **변곡점** 직전 |
| **스트레스** | 시스템의 한계점은? | 정상 상태(보통 현재 피크)에서 천천히 올려 관측값이 나빠지기 직전이 답 |
| **부하(load)** | 이 예상 부하를 견디는가? (예/아니오) | 신규 고객 온보딩·캠페인·바이럴 대비 |
| **내구(endurance/soak)** | 오래 돌리면 무엇이 드러나나? | 느린 누수·캐시 오염·단편화(동시 모드 실패 → 5장). 오래 걸리고 비싸며 **지름길이 없다.** 배포가 잦은 MSA 에는 안 맞을 수 있다 — "운영에서 테스트" 하게 되는 이유 |
| **용량 계획** | 자원을 더 주면 기대대로 늘어나는가? | 스트레스와 닮았지만 **미래 지향**. 계획 활동의 일부 |
| **성능 저하(partial failure)** | 일부가 죽으면 어떻게 되나? | 클러스터(K8s) 시대에 개발자도 알아야 한다. **Chaos Monkey** — 운영에서 무작위로 프로세스를 죽인다. "충분히 큰 시스템은 항상 어딘가 고장 나 있다. 완벽히 동작하는 시스템은 작아서 생기는 인공물이다" |

### 2-2. 모범 사례

- **하향식**: 전체 앱의 성능 행동에서 시작한다. 마이크로벤치마크는 부록 A 로 격리했다.
- **테스트 환경**: CPU 수·OS·자바 버전은 물론 웹 서버·DB·MQ 까지 같아야 한다. 외부 서비스는 목으로. 클라우드는
  "가축이지 반려동물이 아니다(livestock, not pets)" 식 불변 인프라로 환경 복제를 쉽게 만들었지만 — 테스트 환경이
  운영에 숨은 의존을 갖지 않는지, 인증/인가가 더미가 아닌지, 껐다 켜는 절차가 있는지 봐야 한다.
- **요구사항 식별**: 성능은 코드만이 아니라 컨테이너·OS·하드웨어의 합이다. 비기능 요구(NFR)는 시스템 전체의 관측값으로
  적는다 — "95퍼센타일 100ms 단축", "같은 하드웨어로 5배 처리량", "클러스터 50% 저하 시에도 목표의 25% 이내",
  "10ms 줄여 이탈률 25% 감소". 킥오프에서 이해관계자와 열어 놓고 정하라. SLO 는 10장.
- **SDLC 의 일부로**: 회귀 테스트를 상시화하려면 전용 환경과 개발-인프라 협업이 필수.
- **자바 특유의 문제**: 컴파일되지 않은 메서드는 (a) 충분히 자주 안 불렸거나 (b) 너무 커서다 — (b)가 훨씬 드물다(6장).

### 2-3. 안티패턴의 원인 (Carey Flichel 의 다섯 가지)

**지루함**(`Collections.sort()` 면 되는데 정렬을 직접 짠다) · **이력서 채우기** · **사회적 압력**(주니어가 말을 못 꺼낸다,
속도 경쟁으로 결정을 서두른다) · **이해 부족**(Hibernate 를 잘 모른 채 다른 프로젝트에서 봤다고 도입 → 주말에 통째로 뜯어냄) ·
**오해된/존재하지 않는 문제**(재지 않고 해결책부터). 대책은 열린 소통과 **프로토타입으로 사실 근거 수집**. 카탈로그는 부록 B.

### 2-4. JVM 성능을 위한 통계

- Deming: *"신은 믿되, 나머지는 데이터를 가져와라."* 황금 기준은 **Georges·Buytaert·Eeckhout 2007** — JVM 처럼
  동적인 시스템에서는 **30회 실행**이 필요하다는 규칙의 출처.
- **무작위 오차**: 환경의 예측 불가한 변화, 가우시안으로 모델링. 측정 하네스는 믿을 만하다고 가정하므로 원인은 환경뿐.
- **계통 오차**: 상관된 방향으로 치우친다. JMeter 예 — 한 서비스가 선형으로 느려지는 것은 자원 고갈 후보(누수라고 단정하지는 말 것),
  나머지가 전부 180ms 근처인 것은 **뭄바이→런던 왕복**이었다. 런던에서 다시 재니 사라졌다.
- **비정규 통계**: JVM 에는 "핫 패스"(전부 JIT 됨, GC 없음)라는 **최선의 경우**가 있어서 "조금 더 빠른" 호출이 없다 —
  가우시안의 기본 가정 위반. 고객 다수가 불평하는 게 아니라면 **평균 개선은 유용한 목표가 아니다.** 이상치가 관심사다.

  ```
  50.0%  23 ns     90.0%  30 ns     99.0%  43 ns     99.9%  164 ns
  99.99% 248 ns    99.999% 3,458 ns 99.9999% 17,463 ns
  ```
  1,000번에 1번은 평균의 10배, 100,000번에 1번은 100배. 이런 분포를 **HDR(high dynamic range)** 라 부른다.
- **HdrHistogram**(Gil Tene, 책 시점 2.1.12): 연속 GC 사이 간격의 히스토그램 예제. 온라인 포매터로 시각화.
  **조정된 누락(coordinated omission)** — 측정 시스템이 피측정 시스템과 무심코 보조를 맞춰 이상치를 놓치거나 요청을 건너뛰는 현상 — 탐지에도 쓴다.

### 2-5. 통계 해석

- **허위 상관**: A→B, B→A, C→A·B(공통 원인, 모유 수유와 IQ), 우연(닭 소비량과 원유 수입). 위험한 것은 터무니없는 쪽이
  아니라 **그럴듯한 쪽**이다(오락실 매출과 CS 박사 수). Feynman: *"자신을 속이지 말라 — 자신이 가장 속이기 쉬운 사람이다."*
- 할당률 그래프 예: 하루 동안 350~700MB/s, 5시간 뒤 하락, 9~10시간에 최저 — 업무량이 시간대를 따르는 정상 신호.
- **모자/코끼리 문제**(어린 왕자): HTTP 응답 시간 히스토그램은 하나의 모양처럼 보이지만 **2xx(긴 꼬리·다봉)** + **4xx(즉시 응답)**
  + **5xx(오래 걸린 뒤 실패)** 의 합이다. 일반 관측값을 **의미 있는 하위 모집단으로 분해**하라. 읽기/쓰기로 더 쪼갤 수도 있다.
  PayPal 의 "Statistics for Software", **Datasaurus Dozen**(같은 통계량, 전혀 다른 모양).

### 2-6. 인지 편향

| 편향 | 요지 | 부록 B 의 대응 |
|---|---|---|
| **환원주의** | 쪼개서 이해하면 전체를 안다는 가정 — 복잡계는 창발한다 | 큰 그림 놓치기 |
| **확인 편향** | 운영과 다른 데이터로 NoSQL 이 빠르다고 "증명" | 반짝이는 것에 홀림 |
| **전장의 안개(행동 편향)** | 장애 중 "뭐라도 해야" 해서 움직임을 속도로 착각 | 비난의 당나귀 |
| **위험 회피** | 성능 프로필이 바뀔까 봐 변경을 못 한다 — 신뢰할 수 있는 회귀 테스트로만 줄어든다 | — |

컴포넌트 하나도 앱마다 다르게 최적화되니 **앱 전체를 봐야** 선입견이 빠진다. Duke Leto: *"함정이 어디 있는지 아는 것이 피하는 첫걸음."*

## 4. JDK 25 기준 평가

**JVM 버전에 결부된 문장이 없다.** 고칠 것이 없고, 라이브러리 버전(HdrHistogram 2.1.12)만 책 시점이다 📄.
"컴파일되지 않은 메서드는 너무 커서일 수 있다" — `DontCompileHugeMethods`(8000 바이트) 는 JDK 25 에도 있다 📄(플래그
표에서 뽑지 않았다 — 확인하지 않았다고 적는다).
