## 1. 이 장의 핵심 주장

1. 프로파일링은 **실행(execution)** 과 **할당(allocation)** 두 갈래이고, 도구는 항상 숫자를 내놓지만 그 숫자가
   문제와 관련 있다는 보장이 없다(Goetz: *"they measure something; we're just not sure what"*).
2. **프로파일러를 켜기 전에 이미 문제가 식별돼 있어야 한다**(Knuth). CPU 100% user 라도 **GC 로그부터**
   확인하라 — GC 가 바쁘면 다음 단계는 GC 튜닝이지 실행 프로파일링이 아니다.
3. 전통적 샘플링 프로파일러는 **세이프포인트 편향**이 있다 — 모든 스레드가 세이프포인트에 도달해야 하고,
   세이프포인트 상태만 표본이 된다. 언롤된 카운티드 루프는 아예 표본이 잡히지 않는다.
4. **perf / Async Profiler / JFR** 이 편향 없는 현대 도구다. Honest Profiler 는 유지되지 않으니 옮겨라.
5. **JFR 을 클라우드 운영 도구로** 쓰려면 새 패턴이 필요하다 — 링 버퍼(`maxage` vs `maxsize` 의 메모리 함정),
   이벤트 스트리밍, Cryostat, OTel 프로파일링 신호.
6. 메모리 프로파일링 — 히스토그램(`jmap -histo` vs `-histo:live` 의 STW 트레이드오프), TLAB 이벤트,
   `jdk.OldObjectSample` 누수 힌트, 힙 덤프(원본의 3~4배, STW, 파드가 죽을 수 있다), MAT.

## 2. 절별 상세 요약

### 2-1. 언제 프로파일링하는가

- 문제 식별 경로: CI 회귀 테스트(마이크로벤치마크보다 **통합 테스트 형태**로), UAT/성능 환경, 운영의 카나리,
  데이터 증가로 드러나는 인덱스 부족.
- 회귀 원인이 앱 코드가 아니라 **라이브러리 업그레이드**일 수 있다. CI 에 회귀 테스트가 있으면 배포를 막는다.
- 실행 프로파일링이 답인 상황: CPU 포화(단, GC 배제 후), **락 경합**(코어를 다 못 쓴다), 새로 들어온 비싼
  SELECT(N+1 포함). 스테이징에 데이터가 적어 운영에서만 보이는 문제도 있다.

### 2-2. GUI 도구

- **VisualVM** — 실행·메모리 프로파일러가 있고 무료지만 운영용으로는 부족. 개발/QA 에서 출발점.
- **JFR/JMC** — BEA JRockit 출신, Java 11 에서 JFR 이 OpenJDK 로 기증되고 JMC 는 독립 프로젝트로.
  **JFR 은 OpenJDK 8u272 로 백포트**됐다. JMC 는 Eclipse Adoptium 등에서 받는다.
  녹화 시작 방법 셋: JVM 플래그 / 동적 attach / `jcmd`. 자동 분석 화면 → Method Profiling.
  데스크톱 프로파일링을 10·11장의 관측 기법과 어떻게 잇는가가 문제다(→ 2-5).

### 2-3. 샘플링과 세이프포인트 편향

- New Relic 에이전트의 100ms 샘플링이 "감당 가능한 오버헤드"의 경험칙. 너무 자주면 오버헤드, 너무 드물면 놓친다.
- Pepperdine: *"프로파일러를 쓸 때쯤이면 세부를 채우는 중이어야지, 놀라고 있으면 안 된다."*
- 세이프포인트 편향의 두 결과: **(a)** 모든 스레드가 세이프포인트에 도달해야 표본을 딴다 → 오버헤드,
  **(b)** 세이프포인트 상태만 보인다 → 분포 왜곡. `GetCallTrace()` 는 스레드 N 개면 N 번 세이프포인트.
  **JEP 312(스레드 로컬 핸드셰이크, Java 11+)** 가 이를 크게 줄였고 Shenandoah·ZGC 의 기반이기도 하다.
- 카운티드 루프 예: `LIMIT` 이 크면 백브랜치마다 세이프포인트 폴이 있지만, 작으면 **언롤**되어 루프가 끝날
  때까지 세이프포인트가 없다 → 표본이 루프 크기에 민감하게 좌우된다.
- ⚠️ 책이 세이프포인트 시간 추적용으로 적은 `-XX:+PrintGCApplicationStoppedTime` 은 **JDK 9 통합 로깅에서
  사라진 플래그**다(✅ 17·21·25 전부 기동 실패). 2판 원고가 1판 문장을 그대로 옮긴 곳이다. 지금은
  `-Xlog:safepoint` (필요하면 `-Xlog:safepoint*:file=...`).

### 2-4. 현대 프로파일러

| 도구 | 원리 | 제약 |
|---|---|---|
| **perf** | 리눅스 커널의 하드웨어 성능 카운터(명령 수·캐시 미스·분기 예측 실패) | JIT 코드 심벌을 위해 **perf-map-agent** 필요. `-XX:+PreserveFramePointer`(8u60+, 기본 꺼짐, 켜면 최적화 하나를 포기) 권장. **컨테이너/seccomp 에서 perf_events 가 없을 수 있다** |
| **Async Profiler** | `SIGPROF` 로 스레드를 **개별** 인터럽트 → 비공개 `AsyncGetCallTrace` → 락프리 링 버퍼 → 별도 스레드가 기록. 전역 동기화 없음 | HotSpot 계열(Adoptium·Amazon·Microsoft·Oracle·Red Hat·Zulu)만. perf 가 도는 OS(리눅스)만. 헤드리스 수집 도구로 주로 씀 |
| **Honest Profiler** | 같은 API | **유지되지 않는다 — 신규 사용 금지, 기존은 이전** |
| **JFR** | HotSpot 내장 이벤트 엔진 | 아래 2-5 |

- **플레임 그래프** 읽기: x 축은 **시간이 아니라 알파벳순 스택 모집단**, y 축은 스택 깊이, 폭이 빈도, 맨 위가
  CPU 에 있던 프레임. 색은 원래 무작위였고 지금은 의미(자바/네이티브)를 넣기도 한다. **플레임 차트**는 x 축이
  시간이라 단일 스레드(JS)에 맞고 자바에는 덜 유용하다.
- **스키드(skid)**: 비순차 CPU 에서 이벤트가 실제 원인 명령이 아닌 뒤 명령에 태깅된다.
- **숨은 세이프포인트 편향**: AGCT 로 스택은 편향 없이 따도 **마지막 프레임의 해석은 디버그 정보에 의존**하고,
  그 정보가 기본으로 세이프포인트에만 있다 → `-XX:+DebugNonSafepoints` 를 가능한 한 일찍 켠다.
- Async Profiler 의 **`timer_create` 엔진**은 perf_events 없는 컨테이너에서도 돌고 파일 디스크립터를
  안 쓰지만 커널 스택은 못 딴다(Go 1.18 프로파일러도 같은 방식 채택 📄).

### 2-5. JFR

- 프로파일 둘: **Continuous(default.jfc)** 와 **Profiling(profile.jfc)** — 후자는 할당 상세가 있지만 오버헤드 ↑.
  오버헤드: Oracle 은 ~1%, 저자 경험은 할당 포함 ~3%. **MPLR 2023 "Don't Trust Your Profiler"** 논문이
  JFR·Async·Honest 를 체계적으로 비교(Georges 2007 방법론). 결론: 상시 켜 둘 만한 범위다. Datadog·New Relic 의
  프로파일러가 JFR 데이터 위에 있다.
- 이벤트는 타입이 있다: `jdk.CPULoad{jvmUser, jvmSystem, machineTotal}`, GC 단계별 이벤트, 임계값이 있는
  `jdk.JavaMonitorEnter`(예: 10ms 이상만).
- 녹화 만들기 셋: JMC / `jcmd <pid> JFR.start|dump|stop` / `-XX:StartFlightRecording:<options>`.
  분석은 `jfr print --events CPULoad,JavaMonitorEnter recording.jfr`(XML·JSON 출력도), 프로그램에서는
  `RecordingFile` 을 순회하고 `Predicate<RecordedEvent>` → `Map` 매퍼로 디코드. SAP 의 JFR 이벤트 브라우저,
  Gunnar Morling 의 **JFR Analytics**(SQL 로 JFR 질의, JDBC).

### 2-6. 운영 도구로서의 JFR

- JFR 은 "덤프 파일을 개발 장비로 복사해 오프라인 분석"하던 시대의 도구다. 클라우드에서는 새 패턴이 필요하다.
- **링 버퍼 패턴**: `-XX:StartFlightRecording:disk=true,filename=/sandbox/service.jfr,maxage=4h,settings=profile`
  → 사고 **뒤에** 덤프해도 4시간을 거슬러 볼 수 있다.
- ⚠️ **`maxage` 의 함정**: JFR 은 이벤트 기반이라 데이터량이 활동량(GC 횟수 등)에 비례하고 **상한이 없다.**
  컨테이너 메모리 한계 근처에서 활동이 튀면 버퍼가 한계를 넘겨 **OOM 킬러가 앱을 죽인다.** 그래서
  `maxsize` 를 쓰는 팀이 있다 — 대신 되돌아볼 시간 창이 보장되지 않는다. 디스크 스풀도 있으니 스테이트리스
  컨테이너의 I/O 축출도 조심.
- **JFR Event Streaming**(`RecordingStream`, 17·21 에 있음 — 실제로는 JDK 14 부터 📄): 이벤트 콜백을 받아
  에이전트나 관측 스레드가 즉시 반응. 관측 도구의 기반으로 훨씬 적합하지만 "Java 17+ 점유율 35%" 라는
  2024-04 수치 때문에 다른 도구들이 생겼다.
- **Cryostat**(Red Hat): K8s 안에서 JFR 녹화를 원격 시작·중지·조회·분석. 토폴로지 뷰·Grafana·자동 규칙·
  스마트 트리거. cert-manager·OLM·OperatorHub 필요. Cryostat 파드 자체도 토폴로지에 보인다.
- **JFR 과 OTel 프로파일링**: 네 번째 기둥 논의가 OTel 워킹그룹에서 진행 중. JFR 이 데이터 소스가 되려면
  스트리밍 기반이어야 하고(17+ 한정), **트레이스 ID 와 JFR 표본을 연결할 간단한 방법이 없다**(2024-08).
  `opentelemetry-java-instrumentation` 은 JFR 기반 JVM 메트릭 구현을 이미 싣고 있다.

### 2-7. 프로파일러 고르기

GUI 가 필요한가 / 운영용인가 개발용인가 / 설정에 얼마나 투자할 수 있나 / 오버헤드 제약은.
VisualVM(JMX 직결 필요) · JMC(JFR 덤프만, 스트리밍 미지원) · JFR(내장 헤드리스 엔진) · perf(리눅스 하드웨어
이벤트, 브리지 필요) · Async Profiler(perf_events 위, 편향 없음, 통합은 JFR 보다 적음). JProfiler·YourKit 은
"한때 확실히 우월했지만 격차가 좁혀졌다".

### 2-8. 메모리 프로파일링

- **히스토그램**: `jmap -histo`(빠름, 가비지 포함) vs `jmap -histo:live`(정확, **STW GC 필요**).
  대부분의 앱에서 `String` 이 1위이고 그 안의 `byte[]`(Java 8 은 `char[]`, JEP 254)가 최소 그만큼 있다.
  "도메인 객체 수가 내 앱에 맞는 자릿수인가?" 가 빠른 점검.
- **TLAB 이벤트**: `jdk.ObjectAllocationInNewTLAB` / `jdk.ObjectAllocationOutsideTLAB`(슬로 패스)로 할당 속도를
  계산. JMC Allocations 뷰. `jdk.OldObjectSample` 이 누수 후보를 제시.
- **힙 덤프**: `jmap -dump:live,format=b,file=heap.bin <pid>`. 원본 힙의 **300~400%** 크기, 네트워크로 꺼내야
  하고, 워크스테이션 메모리가 모자라면 페이징 지옥. `live` 는 STW → 클라우드에서는 **파드가 죽을 수 있다.**
  분석은 **Eclipse MAT**(도미네이터·누수 의심 리포트).
- hprof 에이전트는 JVMTI 참조 구현이었을 뿐인데 실사용이 늘어 Java 9 에서 제거됐다. hprof **포맷**은 `jmap` 이 유지.

## 4. JDK 25 기준 평가

위 배너 표에 더해:

- **JEP 509 (JFR CPU-Time Profiling, 25, 실험·리눅스)** — `jdk.CPUTimeSample` 이벤트. 책의 "JFR 은 벽시계
  실행 샘플" 서술은 25 부터 **CPU 시간 기준 표본**이라는 선택지가 생겼다는 말로 보충해야 한다. ✅ 이벤트 존재
  확인, 동작 품질은 확인하지 않았다.
- **JEP 518 (JFR Cooperative Sampling, 25)** — 표본 채취를 세이프포인트에서 협력적으로 하되 편향은 피하도록
  스택 워킹을 재설계. 📄 (이벤트 이름으로는 드러나지 않아 실행 확인 불가)
- **JEP 520 (JFR Method Timing & Tracing, 25)** — `jdk.MethodTiming`·`jdk.MethodTrace` 이벤트로 **바이트코드
  계측 기반** 메서드 타이밍. 책이 "메서드 진입/이탈 전부 추적은 비용이 커서 샘플링한다"고 쓴 대목의 반례가
  JDK 안에 생겼다(선택한 메서드에만). ✅ 이벤트 존재.
- `jdk.VirtualThreadPinned` 이벤트는 21·25 모두 있고 필드 구조도 같다 ✅ — 다만 25 에서는 `synchronized`
  로는 더 이상 피닝이 일어나지 않으므로(JEP 491, ✅ CN-13A) 이 이벤트가 찍히는 상황이 네이티브 프레임 등으로 줄었다.
- JFR 이벤트 스트리밍은 **JDK 14(JEP 349)** 부터다 — 책의 "17·21 에 있다"는 참이지만 하한이 아니다. 📄
- `jfr` 도구는 17·21·25 모두 있고 `jcmd`·`jmap`·`jhsdb` 도 그대로다 ✅. `jconsole`·`jmc` 는 이 머신의 데비안
  패키지 분할 때문에 없는 것이지 JDK 에서 빠진 것이 아니다(✅ 21 패키지에는 `jconsole` 이 있었다).

## 6. 면접에서 쓸 수 있는 문장

- "CPU 가 100% 라고 바로 프로파일러를 켜지 않습니다. GC 로그가 조용한지부터 봅니다. GC 가 바쁘면 다음 단계는
  GC 튜닝입니다."
- "샘플링 프로파일러가 세이프포인트에서만 표본을 뜨면 언롤된 루프는 아예 안 보입니다. 그래서 Async Profiler 나
  JFR 처럼 편향 없는 도구를 쓰고, `DebugNonSafepoints` 로 마지막 프레임 해석도 보정합니다."
- "운영에서 JFR 을 링 버퍼로 켜 두면 사고 뒤에 거슬러 볼 수 있습니다. 다만 `maxage` 는 상한이 없어 컨테이너
  메모리 한계에서 OOM 킬을 부를 수 있으니 `maxsize` 와 저울질해야 합니다."
