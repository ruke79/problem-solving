# 1장 — 최적화와 성능의 정의 (Optimization and Performance Defined)

> *Optimizing Cloud Native Java* 2판(2024) 1장 요약. **착수 순서 밖**(용어 정의 장). 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판 1장의 개정판.** 본문의 80% 가 그대로이고, 파이프 비유의 확장 · JMC 그림 · **「클라우드 시스템의 성능」 신설 절**이 더해졌다. 2판 전체의 관점 — "배포 단위는 JVM 프로세스가 아니라 컨테이너" — 가 여기서 선언된다.

---

## 1. 이 장의 핵심 주장

1. **성능 분석은 실증과 인간 심리의 혼합**이다(1판과 같다). 1판 이후 **상황은 더 날카로워졌다** — 워크로드가 클라우드로 옮겨 가고 분산 시스템 측면이 더해져, 성능을 신경 써야 하는 엔지니어 수가 늘었다. 2판이 주는 네 가지: 단일 JVM 앱 코드 성능의 심층 · JVM 내부 · **현대 클라우드 스택과 JVM 의 상호작용** · **클러스터에서 도는 자바 앱의 첫 관찰**.
2. **잘못된 길**(1997~98년 기사, 모놀리식 메서드 조언) — 그대로. "가상 디스패치는 **대다수일지도 모르는** 호출 지점에서 제거됐다"로 표현이 조금 조심스러워졌다. 팁 모음이 아니고, 마법의 스위치·비법·숨겨진 알고리즘은 **없다.**
3. **자바 성능 개요**: Gosling 의 "블루칼라 언어". HotSpot 성숙으로 고성능 계산에 적합해진 시점을 **"2005년쯤"** 으로 명시. 관리되는 서브시스템 → 비정규 분포 → 표준편차 부적합, 이상치 중요(저지연 트레이딩·**티켓 예매**), 샘플링의 한계, 측정 오버헤드. **클라우드 네이티브에서도 같은 고민** — 쿠버네티스의 자동 관리, **데이터 수집 비용 vs 결론에 필요한 양의 균형**(10장).
4. **실험 과학**: "JVM 은 빠르고 릴리스마다 빨라지지만 자바 앱은 여전히 느릴 수 있다." 6단계 절차, 비기능 요구사항, Petroski·Goldratt. 통계 입문은 **2장**, 클러스터로의 일반화 = **관측가능성(10장)**.
5. **성능 분류법 7개**(처리량·지연·용량·사용률·효율·확장성·저하) — **파이프 비유를 끝까지 밀었다**: 처리량 = 초당 리터(속도 × 단면적) · 지연 = 한 리터가 파이프를 지나는 시간(길이 × 속도, **지름과 무관**) · 용량 = 저수지(용량 ↑ 처리량 그대로) 또는 좁은 입구(초크 포인트) · 사용률 = 좁은 입구 뒤의 낮은 수위 · 저하 = **풍선 파이프**(임계를 넘으면 처리량 0) vs 튼튼한 파이프(누수, 입구에서 튕겨 나가는 물 = 요청 거부). **사용률 절에 클라우드 문장** — "많은 앱에서 CPU 보다 메모리가 더 낭비되고, 마이크로서비스에서는 **네트워크가 진짜 병목**".
6. **관측량의 상관** — JIT 역설(6장), 은행 사례. 그대로.
7. **그래프 읽기**: 팔꿈치 · 선형 확장 · 암달(13장; 95% 병렬화, 32 프로세서로 12배, 상한 20배) · **JMC 의 톱니**(Eclipse Adoptium 배포) · **JMC 의 할당률**(8 GiB/s 를 목표로 했으나 하드웨어 한계로 **4~5 GiB/s**) · 누수의 서서히 저하. "할당이 막힌 것과 누수는 다른 문제".
8. **클라우드 시스템의 성능(신설)**: 클라우드 = 네트워크로 협력하는 JVM 노드의 클러스터 → 단일 노드 복잡성 위에 **한 층 더**. 운영자의 아홉 질문 — 작업 분배 · 새 버전/설정 롤아웃 · 노드 이탈 · 노드 합류 · **잘못 설정된 노드** · **다르게 동작하는 노드** · 클러스터 제어 코드의 문제 · 전체 장애 · **의존 인프라의 병목**. 신참에게 안 보이는 두 가지 — ① **배포 단위는 JVM 프로세스가 아니라 컨테이너**이고, 클러스터 내부 동작은 엔지니어에게 불투명하다(10장 관측가능성) ② **효율·사용률이 곧 비용** — 케이지의 서버(CapEx, 자산) → 대여(OpEx, 부채), 재무 부서의 감시. 클러스터는 **시간에 따라 구성원이 바뀐다**(호스트 기반 시스템과의 근본 차이).

## 4. JDK 25 기준 평가

**JVM 버전에 결부된 문장이 없다.** 덧붙일 것 —

- "JIT 임계를 넘으면 빨라진다"는 25 에서도 같은 기본값(`Tier3InvocationThreshold` 200, `Tier4InvocationThreshold` 5000, `CompileThreshold` 10000) ✅.
- 할당률 4~5 GiB/s 한계는 이 환경에서 재지 않았다. `verify-labs-perfbook` PERF-08A 는 32 MB 힙에 768 MB 를 흘려 GC 43회를 세지만 **할당률을 재는 케이스는 아니다.**
- "컨테이너가 배포 단위"의 JVM 측 귀결(CPU 1개 → Serial, 메모리 25% → 힙)은 CN-04A·04B ✅.

## 6. 면접에서 쓸 수 있는 문장

- "지연은 파이프의 길이고 처리량은 단면적입니다. 파이프를 굵게 해도(스레드를 늘려도) 한 요청의 지연은 줄지 않습니다."
- "클라우드에서 사용률은 성능 지표이자 비용입니다. 서버가 자산에서 부채로 바뀌었기 때문에 효율 개선이 곧 청구서 감소입니다."
- "클라우드에서 배포 단위는 JVM 프로세스가 아니라 컨테이너입니다. 그래서 컨테이너의 CPU·메모리 제한이 곧 JVM 의 GC 와 힙을 정합니다."
