## 1. 이 장의 핵심 주장

1. GC 의 두 규칙 — **살아 있는 객체를 절대 거두지 말 것**(위반하면 세그폴트·조용한 손상), 모든 가비지를 거둘 것(이건 유연하다). "GC 가 문제"라는 인식은 초기의 유산이고 지금은 최고 수준이다. `System.gc()` 는 실용적으로 쓸모없다.
2. **마크 앤 스윕** 입문판(할당 목록·마크 비트·루트에서 도달 가능한 그래프 = 라이브 객체 그래프). 용어집: STW·동시·병렬·정확/보수·이동·압축·**퇴거(evacuating)**. "동시"는 이진이 아니라 **눈금**이다.
3. HotSpot 런타임: 자바 값은 프리미티브 아니면 **참조**뿐. **oop**(ordinary object pointer) — instanceOop/arrayOop, 헤더 = **마크 워드**(인스턴스 메타데이터) + **klass 워드**(클래스 메타데이터, 힙 밖의 klass 를 가리킴; `Class<?>` 객체와 다르다 — klass 에는 vtable, `Class` 에는 `Method` 배열).
   **압축 oop**(`-XX:+UseCompressedOops`, 64비트 기본): klass 워드·참조 필드·객체 배열 원소가 32비트. 끄면 힙 10~50% 증가 — 끄는 것은 「스위치 만지작거리기」. 배열은 길이 32비트가 더 붙는다(인덱스가 32비트인 이유).
   **GC 루트**: 스택 프레임·JNI·레지스터·코드 루트·전역·클래스 메타데이터.
4. GC 행동의 두 동인 — **할당률**(MB/s, JFR 로 추정 가능)과 **객체 수명**(훨씬 재기 어렵고 더 근본적). **약한 세대 가설(WGH)**: 수명 분포는 쌍봉이다 → Eden 과 장수 영역을 나눠 따로 거둔다. **죽은 객체를 거두는 비용은 0** 이다(살아 있는 것만 본다).
5. **TLAB**: Eden 을 스레드별 버퍼로 잘라 주어 할당이 **포인터 범프 O(1)**. 동적 크기 조정. TLAB 을 더 못 주면 영 GC. **반구(hemispheric) 수집** = 서바이버 두 공간(한쪽은 늘 비어 있다). "클래식" 힙: Eden → S0/S1(세대 카운트) → 올드(테뉴어드). **카드 테이블**(올드 512바이트마다 1바이트, 쓰기 장벽 `cards[*oop >> 9] = 0`)로 올드→영 참조를 추적. G1 은 연속 세대가 아니라 **리전**(5장).
6. **병렬 수집기**(Java 8 이하 기본, 처리량 최적화, 완전 STW): Parallel GC(영) / ParNew(폐기된 CMS 짝) / ParallelOld(올드, 단일 연속 공간 **압축**; 영은 퇴거). 17 부터 CMS 가 없어 병렬은 하나. 영 컬렉션은 살아 있는 것만 만져 몇 ms(서브 ms 도). 올드는 기본 7배 크고 마크 시간이 살아 있는 객체 수에 비례 → **STW 가 힙 크기에 선형**. "조금만 고치면 되지 않나"는 40년 연구를 무시하는 것이다.
   **Serial/SerialOld** 는 코어 하나만 쓰는 STW — 멀티코어에서는 명백히 잘못이지만 **컨테이너에서 자동 선택될 수 있다**(9장).
7. **할당의 역할**: GC 는 고정 주기가 아니라 **필요할 때** 일어난다(10장의 "이벤트라 집계해야 한다"). 단순 모델(힙 2GB, 할당 100MB/s, 수명 200ms → 4초마다 영 GC 20MB 생존, 올드 승격 0) vs **버스트**(1GB/s 1초 → 서바이버보다 큰 생존 집단이 **조기 승격**되어 올드에 500MB 의 곧 죽을 객체가 쌓인다). 조기 승격이 튜닝의 출발점.
   `ModelAllocator` 시뮬레이터, Amazon **HyperAlloc**(Heapothesys). 주기적 GC 설정은 "GC 를 이기려는" 시도라 대개 해롭다(각주).

## 2. 절별 상세 요약

### 2-1. 마크 앤 스윕과 용어
`jmap -histo` 출력 예(상위: `[B` 1,500만 바이트, `[C`, `[I`, `HashMap$Node`, `String` …). 순간 뷰(VisualVM Sampling, VisualGC)는 부족하고 **JFR 이나 GC 로그**로 "힙이 얼마나 크고 어떻게 변하고 누수가 있나"를 봐야 한다. G1 은 Java 9 부터 기본이고 동시 측면이 있다.

### 2-2. HotSpot 런타임 표현
`record Entry<K,V>(int hash, K key, V value, Entry<K,V> next)` 와 `Entry.class` 의 그림. oop 계층(Java 22): oop → instanceOop / **stackChunkOop**(가상 스레드 스택 청크!) / arrayOop → objArrayOop / typeArrayOop. HotSpot 은 힙을 **시스템콜 없이 유저 공간에서** 관리한다(5장).

### 2-3. 할당과 수명
WGH 그림. "올드→영 참조는 적다"가 WGH 의 부차적 부분. 생성-생존-회수 사이클이 GC 의 전제.

### 2-4. 운영 GC 기법
TLAB(그림 4-6), 반구 수집·서바이버(VisualGC 그림 4-7), 클래식 힙(그림 4-8), 카드 테이블과 리멤버드 셋 예고, 퇴거 수집기.

### 2-5. 병렬 수집기
영 병렬 컬렉션 순서(TLAB 없음 → 전 스레드 정지 → 루트 + 카드 테이블로 마킹 → 빈 서바이버로 퇴거·세대 카운트 증가 → Eden·서바이버 비움 → 재개). TLAB 밖 할당(큰 객체)은 적어야 한다. ParallelOld 는 8 까지 기본이었고 지속 처리량 워크로드에서는 G1 을 이길 수 있으나 **"17 쯤이면 Parallel 이 G1 을 이기는 워크로드를 찾기 매우 어렵다 — 바꾸기 전에 재라"**(각주). TLAB 의 스레드 사유성은 **할당 시점에만** 참이다(`int[] anInt` 를 새 스레드에 넘기는 예).

### 2-6. 할당의 역할
위 §1-7. 표 두 개(정상 상태 GC0~GC2 / 버스트 GC0~GC3).

## 4. JDK 25 기준 평가

배너 표에 더해:

- **컴팩트 객체 헤더(JEP 519)** — 25 에서 정식 기능(플래그 기본 `false`, `UnlockExperimentalVMOptions` 불필요) ✅. 200만 개 `new Object()` 로 잰 객체당 바이트: 기본 **16.0**, 켜면 **8.0** ✅(CN-05C). 배열 헤더의 길이 필드도 마크 워드 뒤로 당겨진다 📄. 이 장의 "헤더 = 두 머신 워드" 서술은 **기본값에서는 참, 플래그를 켠 JVM 에서는 한 워드**로 읽어야 한다. JDK 25 의 CDS 아카이브도 `classes_coh.jsa`(compact object headers 용)가 따로 있다 ✅(`lib/server/` 목록).
- **GC 에르고노믹** — 4코어 이 머신 기본 G1 ✅, `ActiveProcessorCount=1` 이면 Serial ✅, 2면 G1 ✅. `MaxRAM=1g` 로는 Serial 이 되지 않았다 ✅ — 서버급 판정은 물리(또는 cgroup) 메모리를 보지 `MaxRAM` 을 보지 않는다. 1792MB 임계값 자체는 이 샌드박스에서 실험하지 못했다 📄.
- **힙 기본 크기** — `MaxRAM=2g` → `Runtime.maxMemory()` 495MB, `MaxRAMPercentage=50` → 1,024MB ✅.
- **GC 빈 이름** — Serial `[Copy][MarkSweepCompact]`, Parallel `[PS Scavenge][PS MarkSweep]`, G1 `[G1 Young Generation][G1 Concurrent GC][G1 Old Generation]` ✅ 25. 모니터링에서 수집기 종류를 알아내는 가장 싼 방법이다.
- TLAB 관련 플래그 기본: `UseTLAB=true`, `ResizeTLAB=true`, `TLABSize=0`(동적) ✅ 25. `NewRatio=2`, `SurvivorRatio=8`, `MaxTenuringThreshold=15` ✅ — 책의 "올드는 영의 7배" 는 `NewRatio=2`(영 1 : 올드 2)와 다르다; 이 수치는 Parallel 의 옛 기본(`NewRatio` 별도) 이야기로 읽힌다 📄(확인하지 않았다).
- 압축 oop `UseCompressedOops=true`, `ObjectAlignmentInBytes=8` ✅.

## 6. 면접에서 쓸 수 있는 문장

- "GC 비용은 죽은 객체가 아니라 살아 있는 객체에 비례합니다. 그래서 영 GC 는 몇 ms 이고, 올드는 힙 크기에 선형으로 늘어납니다."
- "컨테이너에 CPU 를 1개 주면 JVM 은 G1 이 아니라 Serial 을 고릅니다. 메모리를 아무리 줘도 그렇습니다. 이 결정은 `MaxRAM` 이 아니라 보이는 CPU 수와 물리 메모리로 합니다."
- "할당 버스트가 오면 서바이버에 안 들어가는 생존 객체가 올드로 조기 승격돼 곧 죽을 객체가 올드를 채웁니다. 튜닝은 대개 여기서 시작합니다."
- "JDK 25 의 컴팩트 객체 헤더를 켜면 헤더가 12 에서 8바이트로 줄어 필드 없는 객체는 16 에서 8바이트가 됩니다. 기본은 아직 꺼져 있습니다."
