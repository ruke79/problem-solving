# 11장 — 자바에서 관측 가능성 구현하기 (Implementing Observability in Java)

> *Optimizing Cloud Native Java* 2판(2024) 11장 요약. **책의 기준 시점은 2024년 8월, JDK 21,
> OpenTelemetry BOM 1.40.0** 이다. 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판(2018)에는 이 장이 없다.** Micrometer·Prometheus·OpenTelemetry 는 1판 전권에 한 번도
> 나오지 않는다(키워드 검색 0회 ✅). 이 장은 예제 앱 *Fighting Animals*(8장)의 브랜치를 옮겨 다니며
> 설명하므로, 요약은 코드보다 **아키텍처 결정과 그 이유**에 무게를 뒀다.

## 1. 이 장의 핵심 주장

1. **Micrometer 는 메트릭의 파사드**(SLF4J 가 로깅의 파사드이듯)다. 백엔드 차이(차원 유무·집계 위치·
   푸시/폴)는 익스포터가 흡수하고 개발자는 `Meter` API 만 본다.
2. **Prometheus 는 스크레이프**한다 — 모든 서비스가 HTTP 엔드포인트를 열어야 하고, 그래서
   remote-write 도 있다. "Prometheus 를 쓴다"는 말은 구성이 워낙 다양해 **되물어야** 한다.
3. **OpenTelemetry(OTel)는 계측과 반출에 집중**하고 백엔드가 아니다. OpenTracing·OpenCensus 는 폐기됐다.
   Java 구현은 트레이스·메트릭 먼저, **로그는 2023년 말 1.0**.
4. 트레이싱은 **수동 계측이 금방 감당 불가**가 되므로 에이전트 자동 계측이 답이다.
5. 로그는 OTel 의 Logs Bridge API 를 직접 쓰지 말고 **Logback 어펜더**(또는 파일 스크레이프)로 흘려라.
6. 권장 스택: **에이전트로 트레이스+JVM 메트릭, Micrometer OTLP 레지스트리로 앱 메트릭, SLF4J/Logback
   OTLP 어펜더로 로그**, 그 앞에 **클러스터당 OTel Collector 하나**를 간접 계층으로.

## 2. 절별 상세 요약

### 2-1. Micrometer

- Spring 에서 출발해 독립한 **JVM 전용** 라이브러리. 이기종 스택이라면 대안을 봐야 한다.
- 백엔드: Azure Monitor·CloudWatch·Datadog·Dynatrace·Elastic·JMX·New Relic·**OTLP**·**Prometheus**·SignalFx·StatsD.
- **레지스트리**: `SimpleMeterRegistry`(메모리, 테스트) · `LoggingMeterRegistry`(주기적 로그) ·
  `CompositeMeterRegistry`(다중 발행) · `Metrics.globalRegistry`. Spring 은 테스트용을 자동 배선한다.
- **계측기(instrument)**:

| 계측기 | 뜻 | 책의 예 |
|---|---|---|
| `Counter` | **단조 증가**만 | `battles.total` — `registry.counter()` 또는 `Counter.builder().register()` |
| `Gauge` | 오르내리는 현재값. **`Number` 를 상속한 캐리어**가 필요 — JDK 에 `AtomicDouble` 이 없어 직접 만든다(`FelinePercent`). 관찰 시점의 값만 보인다 | `battles.felinePercent` |
| `Timer` | 합·개수·창 내 최댓값. 히스토그램·퍼센타일·SLO 경계 추가 가능. `recordCallable`/`record` | `response.time` — 단, **분산 시스템의 메서드 성능은 타이머보다 트레이싱** |
| `DistributionSummary` | 시간이 아닌 값의 분포(더 많은 메모리, 그래도 손실 요약) | `attacker.win.size` — 0.5~1.0 균등 분포 |
| 기타 | `LongTaskTimer`·`TimeGauge`·`FunctionCounter`·`FunctionTimer` | |

- **MeterFilter** — 등록 거부/허용, 이름·태그 변환, 분포 통계 설정. `DENY`/`NEUTRAL`/`ACCEPT` 는 체인이고
  **순서가 의미 있다**(추가만 되고 덮어쓰지 않는다). 세 메서드가 전부 default 라 함수형 인터페이스가 아니다.
  `configure()` 를 덮어쓰면 `jvm*` 메트릭에 p90/p99/p99.9/p99.99 를 붙일 수 있다.
- 책이 다시 못 박는다: **개수·합은 차원/인스턴스 간 재집계가 되지만 미리 계산된 퍼센타일은 안 된다.**
- **런타임 메트릭**: `MeterBinder.bindTo(registry)` — `JvmMemoryMetrics`(`jvm.memory.used/max`),
  `ProcessorMetrics`(`system.cpu.usage`, `system.load.average.1m`), `ExecutorServiceMetrics`(스레드 풀).
  Spring Boot 는 자동 설치, 그 외에는 직접 바인딩.

### 2-2. Prometheus

- CNCF 프로젝트(SoundCloud 출신). **순수 숫자 정규 시계열**만 — 로그·트레이스용이 아니다.
- **스크레이프** 모델 → 서비스가 알려져 있거나 발견 가능해야 한다. 단명 잡과 K8s 보안 모델을 위해 remote-write.
- **PromQL** 은 SQL 이 아니라 시계열 DSL. `process_cpu_usage{job="animal"}[6h]` 는 **범위 벡터**(표에만),
  그래프는 **즉시 벡터**가 필요하다. `=~"m.*"` 정규식 선택.
- Micrometer 와 붙이기: `micrometer-registry-prometheus` 런타임 의존 +
  `management.endpoints.web.exposure.include=health,info,prometheus` → `/actuator/prometheus` 노출.
  책의 `prometheus.yml` 은 **실제 네트워크에서 동작하도록 시험**한 것이다 — 인터넷 예제 다수는 localhost 에서만 된다.
- 출력을 보면 대부분이 **JVM 메트릭**(`jvm_memory_committed_bytes{area="nonheap",id="CodeHeap 'profiled nmethods'"}` 등)이고
  앱 메트릭(`battles_total`)은 아래쪽이다. Prometheus 는 자기 자신도 같은 방식으로 관측한다(Go 런타임 메트릭,
  고루틴 수) — **관측 신호를 나르는 시스템은 그 자체가 관측 가능해야 한다**는 원칙의 예다.
  (책은 고루틴이 "14장에서 다룰 가상 스레드"와 비슷하다고 쓰는데, 가상 스레드는 **13장**이다 — 참조 오기.)

### 2-3. OpenTelemetry

- OpenTracing + OpenCensus 합병. 2023년에 1.0. 폴리글랏·분산 시스템에 가장 잘 맞는다.
- 프로젝트 영역: **명세**(신호 형식·시맨틱 컨벤션·OTLP) · **언어 구현**(API/SDK/계측 라이브러리) ·
  **자바 에이전트** · **Collector**(수신-처리-반출 라우터, 프로토콜 변환기).
- 안정성 약속: API 3년, 플러그인 인터페이스·생성자 1년(책 각주: opentelemetry-java 는 이보다 약할 수 있다).
- 자바 저장소 넷: `opentelemetry-java`(API/SDK) · `opentelemetry-java-instrumentation`(라이브러리 계측 100+ 과
  에이전트) · `-contrib` · `-examples`.
- **왜 OTel 인가**: 시스템 복잡도가 오르며 벤더마다 계측 라이브러리를 따로 유지하는 것이 비효율이 됐고,
  벤더의 가치는 UX·백엔드·비용으로 옮겨 갔다. 느리다는 비판이 있지만 **안정적인 공통 시맨틱 컨벤션**의 이득이 크다.
- **OTLP**: 인코딩·전송·전달만 정의. HTTP/2 또는 gRPC(protobuf). 자바 코어 기본은 HTTPS/protobuf.
- **Collector**: Go, YAML 설정. `receivers`/`processors`/`connectors`/`exporters`/`extensions`, 그리고
  `service.pipelines` 에 신호별 파이프라인. 기본 `localhost:4317`. 자기 텔레메트리는 `service.telemetry` 에.
  원칙 — 사용성·성능·관측 가능성·확장성·통합(트레이스·메트릭·로그 한 코드베이스).

### 2-4. 트레이싱 — 수동 vs 자동

- **수동**(`manual_tracing` 브랜치): BOM(`opentelemetry-bom:1.40.0`) + api/sdk/autoconfigure/exporter-otlp,
  `AutoConfiguredOpenTelemetrySdk.initialize()` 빈, 컨트롤러마다 `extractContext → makeCurrent → serverSpan →
  finally span.end()`. **서비스마다 같은 코드를 넣어야 빈틈이 없다** — 두 컨트롤러만 봐도 양이 상당하다.
  `Tracer` 는 로거처럼 생성자에서 한 번 만든다. Collector → Jaeger(`jaegertracing/all-in-one:1.52.0`,
  gRPC 4317 충돌을 피해 14317 로 재매핑).
- **자동**(`auto_tracing_only`): 에이전트 jar 경로만 JVM 인자로. **POM 에 OTel 의존 0, 스팬 코드 0.**
  Java 8+ 어디서나. 동적 attach 도 가능. Quarkus 같은 내장 지원 프레임워크에서는 **에이전트를 쓰면 안 된다.**
  `-Dotel.exporter.otlp.endpoint=http://otel-collector:4317/`(또는 `OTEL_EXPORTER_OTLP_ENDPOINT`).
- **샘플링**: 오류(4xx/5xx)는 100%, 성공은 고볼륨이면 1% 까지. 통계적 대표성만 있으면 회귀는 보인다.
  2장의 "모자/코끼리 문제" — 응답 범주마다 정보량이 다르다.

### 2-5. 메트릭 — 원시 OTel API vs Micrometer

- 원시 API(`otel_metrics_raw_api`): `LongCounter`, `ObservableDoubleGauge.buildWithCallback(...)`(관찰 시에만
  콜백, 여러 게이지 간 순서 미정). **actuator 를 빼야** Spring 내장 Micrometer 와 충돌하지 않는다.
- Micrometer + OTLP(`micrometer_with_otel`): `micrometer-registry-otlp` 만 추가, **컨트롤러 코드는
  `micrometer_only` 와 동일**. `management.otlp.metrics.export.url=http://otel-collector:4318/v1/metrics`,
  `step=10s`. 책 시점에 이 레지스트리는 **압축 HTTP 만 지원, gRPC 미지원** → Collector 에 4318 을 열어야 한다.
- OTel 메트릭은 JMX 로 JVM 지표를 얻고 JFR 통합도 있다.

### 2-6. 로그

- OTel 에 Logs Bridge API 가 있지만 **대부분의 팀은 쓰지 말아야** 한다(기존 관행을 너무 많이 바꾼다).
  대안 둘: (1) 파일 어펜더 + Collector 파일 스크레이프(중립적이지만 경직), (2) **로깅 프레임워크용 OTel
  계측 라이브러리**(초기 노력 ↑, 유지 노력 ↓). 책은 (2).
- 로그만은 **OTel 에 직접 의존하지 않는 파사드가 없다** — `opentelemetry-logback-appender-1.0:2.0.0-alpha`,
  `logback.xml` 에 `OpenTelemetryAppender`, `ApplicationReadyEvent` 에서 `OpenTelemetryAppender.install(openTelemetry)`.
  개발자는 계속 SLF4J 만 쓴다.

### 2-7. 권장 스택

```
트레이스: Java agent      → OTLP → Collector → Jaeger
메트릭:   Micrometer      → OTLP → Collector → Prometheus (스크레이프 또는 remote-write)
로그:     SLF4J/Logback   → OTLP → Collector → Loki
```

Collector 는 **클러스터당 하나**가 보통이고 다중 발행·아키텍처 변경을 앱과 분리해 준다. 유일한 답이 아니라
"전체 아키텍처를 이해한 뒤 자기 상황에 맞게 고르는" 출발점이다.

## 3. 1판(2018)과 달라진 점

- **장 신설.** 1판 14장은 Log4j 2 vs Logback vs java.util.logging 의 **성능**(할당·가비지 없는 로깅,
  비동기 어펜더)을 다뤘다. 2판은 로깅 라이브러리 성능 비교를 통째로 버리고 **"로그를 어디로 어떻게 흘릴 것인가"**
  로 관심을 옮겼다.
- 1판의 Aeron/Agrona/SBE 저지연 메시징(59회 언급 ✅)은 2판 어디에도 없다(0회 ✅). 메시징은 14장 Kafka 로
  대체됐고, 관심사가 "마이크로초 지연" 에서 "분산 시스템 운영" 으로 이동했다.

## 4. JDK 25 기준 평가

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| OTel BOM 1.40.0, Jaeger 1.52.0, Collector 0.91.0 을 **고정 버전**으로 | 책 스스로 "배포 전에 올려라"고 쓴다. 지금 최신 버전은 이 저장소에서 확인하지 않았다 | 📄 |
| `opentelemetry-logback-appender-1.0` 이 `2.0.0-alpha` | 로그 계측은 알파였다. 이후 안정화 여부는 미확인 | 📄 |
| Micrometer OTLP 레지스트리는 HTTP 만 | 시점 서술. 미확인 | 📄 |
| 이 저장소의 Spring Boot 3.3.5 가 끌어오는 Micrometer | `verify-labs-cloudnative` 빌드가 BOM 으로 해석한 버전을 리포트에 남긴다(CN-11A `fact`) | ✅ 실행 시 기록 |
| 프로세스·JVM 메트릭 이름(`jvm_memory_committed_bytes{id="CodeHeap 'profiled nmethods'"}`) | JDK 25 도 코드 캐시가 세 힙으로 나뉘어 같은 풀 이름이 나온다 | ✅ 25 `SegmentedCodeCache=true`, CN-06B 가 풀 이름을 확인 |
| 고루틴 ≈ 가상 스레드 | 맞다. JDK 25 에서는 `synchronized` 피닝까지 풀렸다(JEP 491) | ✅ CN-13A |

**JVM 버전 때문에 틀리는 문장은 없다.** 라이브러리 버전이 전부 "책 시점 고정"이라는 것만 기억하면 된다.

## 5. 이 장을 우리 랩에 비춰 보면

| 책의 명제 | 이 저장소의 근거 | 상태 |
|---|---|---|
| `Counter` 는 단조 증가, `Timer` 는 개수·합·최댓값, `MeterFilter.denyNameStartsWith` 는 등록을 막는다 | `verify-labs-cloudnative` **CN-11A** — `SimpleMeterRegistry` 로 확인 | 2판 랩 케이스 |
| 미리 계산된 퍼센타일은 재집계할 수 없다 | **CN-10A** | 2판 랩 케이스 |
| Prometheus 스크레이프 엔드포인트·Collector·Jaeger | 인프라가 필요하다. 이 저장소의 compose 에는 없다 — **검증하지 않았다** | 미검증 (정직한 고지) |
| 자동 계측 에이전트 | 에이전트 실행은 `verify-labs` 의 `observability` 분류에서 다루지 않는다 | 미검증 |

## 6. 면접에서 쓸 수 있는 문장

- "Micrometer 는 메트릭의 SLF4J 입니다. 백엔드가 차원을 지원하는지, 클라이언트에서 집계하는지, 푸시인지 폴인지는
  레지스트리가 흡수합니다."
- "트레이싱을 수동으로 넣으면 아는 경로만 계측하게 되고, 그 맹점이 문제 위치를 오판하게 합니다. 그래서
  에이전트 자동 계측을 기본으로 두고 필요한 곳만 수동 스팬을 더합니다."
- "로그는 OTel Logs Bridge 를 직접 부르지 않고 Logback 어펜더로 흘립니다. 개발자는 SLF4J 만 계속 씁니다."
