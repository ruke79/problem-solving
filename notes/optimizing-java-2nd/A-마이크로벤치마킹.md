# 부록 A — 마이크로벤치마킹 (Microbenchmarking)

> *Optimizing Cloud Native Java* 2판(2024) 부록 A 요약. **착수 순서 1순위**(2장과 한 묶음).
> 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판 5장 「마이크로벤치마킹과 통계」의 JMH 절이 부록으로 내려온 것**이다. 통계 절은 2장으로 갔다.
> 저자들이 본문에서 뺀 이유를 부록 첫머리에 다시 쓴다 — 대다수 개발자에게 이 기법은 필요 없고, 필요하다면 JMH 뿐이다.

---

## 1. 이 장의 핵심 주장

1. 벤치마크는 **과학 실험**이다 — 한 번에 하나만 바꾸는 공정한 테스트, 최소한 **반복 가능**해야 한다.
   Shipilëv: *"숫자 자체는 중요하지 않다. 그 숫자에서 어떤 모델을 끌어내느냐가 중요하다."*
2. 마이크로벤치마크가 어려운 근본 이유: **실행 코드를 JIT·GC·OS·하드웨어에서 떼어낼 수 없다.** 큰 집합(전체 시스템)에서는
   평균화되지만 작은 조각에서는 배경 잡음과 분리되지 않는다.
3. 순진한 벤치마크의 함정 — 워밍업 없음, GC 미통제, **결과를 쓰지 않아 죽은 코드가 됨**, 오차 범위 없음, 멀티스레드 시작 동기화.
4. **하지 마라.** 해야 한다면 세 경우뿐 — OpenJDK/플랫폼 개발자, 범용 라이브러리(Guava·Eclipse Collections), 극한 저지연.
   기준: 코드 경로 < 1ms(가급적 < 100µs), 할당률 < 1MB/s, CPU ~100% 사용·시스템 시간 < 10%, **이미 프로파일러로** 지배 메서드 2~3개를 안다.
5. 해야 한다면 **JMH**. JVM 을 만드는 사람들이 만들어 JVM 릴리스마다 함정을 따라간다. 애너테이션 프로세싱으로 코드를 **생성**하고
   (리플렉션이 아니라), 루프 최적화가 걸리지 않게 반복 수를 고른다. **Blackhole** 이 죽은 코드 제거·상수 접기·거짓 공유·쓰기 벽을 막는다.
6. JMH 를 써도 **통제된 실험이라고 가정하지 마라** — 정렬 벤치마크의 차이가 알고 보니 GC 였다.

## 2. 절별 상세 요약

### 2-1. 순진한 벤치마크 해부 — `ClassicSort`

1,000개 난수를 150,000번 복사·정렬해 ops/s 를 계산하는 코드. 문제들:

| 함정 | 무엇이 잘못됐나 | 어떻게 보이나 |
|---|---|---|
| **워밍업 없음** | 운영에서는 몇 시간 돈 뒤의 코드인데 측정 중에 JIT 가 돌아간다 — 통제 안 된 변수 | `-XX:+PrintCompilation`: `Integer::compareTo` 가 레벨 3 → 4 로 다시 컴파일되고 `made not entrant` 가 찍힌다 |
| **GC 미통제** | `System.gc()` 는 무시될 수 있다. 측정 구간에 GC 가 끼는지 알 수 없다 | `-verbose:gc`: `[GC (Allocation Failure) 524800K->632K(2010112K), 0.0009038 secs]` (⚠️ 이 로그 형식은 Java 8 것 — §4) |
| **죽은 코드** | `copy` 를 쓰지 않으니 JIT 가 정렬 자체를 없앨 수 있다 | 측정 대상이 사라진다 |
| **오차 범위 없음** | 평균 하나로는 통제 안 된 변수도, 코드가 느린 것도 구분 못 한다 | — |
| **멀티스레드** | 모든 스레드가 완전히 시작된 뒤 재야 한다. 전원 관리·머신 경합까지 변수 | 오차 범위 폭발 |

해법 둘: **시스템 전체만 벤치마크**(대부분의 경우) 또는 이런 문제를 대신 다뤄 주는 **공통 프레임워크**(JMH).

### 2-2. 하지 마라 — 실화

며칠째 메서드 하나를 노려보던 동료. 새 버전이 구 버전보다 느렸고 코드를 떼어내 작은 벤치마크를 짜고 있었다.
함께 보니 **CPU 가 포화** — 실행 프로파일러(12장)의 정석 사용처 — 10분 프로파일링으로 원인은 **새 인프라 라이브러리**였다.
*"개발자는 자기 코드가 범인이라는 생각에 사로잡혀 큰 그림을 놓친다."*

### 2-3. JMH

- Google Caliper 등 이전 시도들은 JVM 진화를 못 따라갔다. JMH 는 OpenJDK 팀이 자기들 용도로 만들었다.
- Maven 아키타입 `jmh-java-benchmark-archetype`. `@Benchmark`, `OptionsBuilder().include(...).warmupIterations(100)
  .measurementIterations(5).forks(1).jvmArgs(...)`, 커맨드라인이 `main()` 설정을 덮는다.
- `@State(Scope.Benchmark|Group|Thread)` 로 상태 수명 관리. 멀티스레드 상태는 특히 조심.
- **Blackhole**: 반환값은 암묵적으로, 여러 값은 파라미터로 주입해 명시적으로 `consume`. 네 가지 보호 — 죽은 코드 제거 방지,
  반복 계산의 상수 접기 방지, 거짓 공유 방지, **쓰기 벽** 보호. 구현을 보면 `volatile int i1=1, i2=2` 에 `if (i == i1 & i == i2)`
  (절대 참이 안 되지만 컴파일러는 실행해야 한다, 비트 AND 로 분기 균일화), 객체는 이스케이프 분석이 비교를 없앨 수 있어
  `tlr` 난수와 마스크로 **거의 안 일어나는 조건**에서만 대입. *"운영 코드에 이런 게 있으면 해고감"*이지만 문서화가 훌륭하다.
- 고급 기능: `@CompilerControl`(인라인 금지/강제/컴파일 제외), Blackhole 로 CPU 부하 시뮬레이션, `GCProfiler`·`StackProfiler`.

### 2-4. `SortBenchmark` — JMH 로도 속는다

```
classicSort   thrpt 200 14373.039 ± 111.586 ops/s
standardSort  thrpt 200 12656.107 ±  84.849 ops/s   (stream().sorted())
parallelSort  thrpt 200  7917.702 ±  87.757 ops/s
```

"클래식이 스트림보다 빠르다"고 결론 내기 쉽다 — 오차도 작다. 그런데 `GCProfiler` 를 붙이니 classicSort 는 반복당 GC ~1회,
parallelSort 는 반복당 4~5회. **차이의 원인은 정렬이 아니라 GC** 였다. 통제된 환경이라는 가정은 미끄럽다. JITWatch(6장)로
바이트코드 수준을 볼 수도 있다.

### 2-5. 결론

하지 마라 → 해야 하면 JMH → 결과를 공개하고 동료와 논의하라 → 자주 틀릴 각오를 하라. 마이크로벤치마크의 순기능은
**비정규 분포와 JVM 의 동적 행동을 몸으로 배우게** 한다는 것. **Spring Boot 나 Quarkus 로 웹 서비스를 만든다면 JMH 는 거의 확실히 필요 없다.**

## 4. JDK 25 기준 평가

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| `-XX:+PrintCompilation` 출력 형식(시각·순번·레벨·메서드·`made not entrant`) | 17·21·25 동일하게 나온다 | ✅ **PERF-10D** 가 이 출력을 파싱한다 |
| `-verbose:gc` 로그 `[GC (Allocation Failure) 524800K->632K(...), 0.0009 secs]` | **Java 8 형식이다.** 9+ 는 통합 로깅 형식 `[0.123s][info][gc] Pause Young (Normal) (G1 Evacuation Pause) 24M->3M(64M) 1.234ms` | ✅ 25 에서 `-verbose:gc` 실행(→ `01-최신-JDK-기준-평가.md`), **PERF-08A** 가 새 형식을 파싱 |
| JMH 를 쓰라 | 이 저장소에 **`verify-labs-jmh`** 를 신설했다. 벤치마크 자체는 JDK 25 에서도 같은 원칙 | ✅ 실행 결과는 그 모듈 README |
| 죽은 코드 제거 | 25 의 C2 도 결과를 버리는 순수 계산 루프를 없앤다 | ✅ **CN-A01** (expectFlaky) |

## 6. 면접에서 쓸 수 있는 문장

- "메서드 하나를 벤치마크하기 전에 프로파일러로 그 메서드가 지배적이라는 것부터 확인합니다. 그렇지 않으면 바늘을 찾는 겁니다."
- "직접 `nanoTime` 으로 재면 워밍업·죽은 코드 제거·GC 를 통제하지 못합니다. 꼭 재야 하면 JMH 로, Blackhole 에 결과를 넣습니다."
- "JMH 결과도 통제된 실험이라고 가정하지 않습니다. 오차가 작아도 원인이 GC 일 수 있어서 `-prof gc` 를 같이 봅니다."
