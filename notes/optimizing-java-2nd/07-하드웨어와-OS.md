# 7장 — 하드웨어와 운영체제 (Hardware and Operating Systems)

> *Optimizing Cloud Native Java* 2판(2024) 7장 요약. **착수 순서 5순위**(기반 지식). 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판 3장 「하드웨어와 OS」의 개정판.** 내용은 거의 그대로이고 **위치가 3장 → 7장(GC·JIT 뒤)** 으로 옮겨져 "클라우드 스택(8장)으로 가기 전의 마지막 단일 호스트 장"이 됐다.
> 2024년 수치(3nm 트랜지스터, 메모리 대역폭 17+ GB/s/코어, 시스템 70~90 GB/s)와 가상 스레드·컨테이너 참조가 더해졌다.

---

## 1. 이 장의 핵심 주장

1. **무어의 법칙은 실질적으로 끝났다**(3nm, 2nm 는 비싸고 느리다). 하드웨어가 복잡해졌고 소프트웨어도 그것을 쓰려면 복잡해진다("소프트웨어가 세상을 먹는다"). 자바는 이 추세의 수혜자였다.
2. **메모리가 병목**: 클럭은 수백 배 빨라졌는데 메모리는 못 따라갔다(Hennessy·Patterson 그림) → **캐시 계층**(L1/L2 코어 전용, L3 공유, 노스브리지 너머 메인 메모리). **MESI**(Modified/Exclusive/Shared/Invalid, 64바이트 라인, 한 프로세서가 E/M 로 가면 나머지는 I). write-through → write-back. 대역폭 = 메모리 클럭 × 버스 폭 × 인터페이스 수 × 2(DDR).
3. **`Caching` 예제**: `touchEveryItem()`(모든 int) 과 `touchEveryLine()`(16개마다) — 직관은 16배 차이인데 **거의 같다.** 지배 효과는 메모리 버스를 통한 캐시 채우기. 100MB 를 ~3ms(2.86ms) → 유효 대역폭 ~3.5GB/s. "이론 한계로 설계하면 실망한다 — 경험값을 기준선으로". 하드웨어 프리페처가 규칙적 스트라이드를 감지한다. **할당률 상한의 잣대**.
4. 현대 프로세서 기능: **TLB**(페이지 테이블 캐시; TLAB 과 혼동 금지), **분기 예측·추측 실행**(파이프라인 최대 20사이클 정지, Meltdown/Spectre), **하드웨어 메모리 모델**(x86 은 스토어 재배열 안 함, ARMv7/POWER 는 거의 다 함 — 표 7-2) → JMM 이 약한 이유. **기계적 공감**(Martin Thompson, 재키 스튜어트).
5. **OS**: MMU·페이지 테이블·TLB. **스케줄러** — 런 큐, 타임 퀀텀(옛 OS 10/100ms), 스레드 생애주기(그림 7-6, 플랫폼 스레드 이야기 — 가상 스레드는 캐리어가 이 모델을 따른다). "코드는 도는 시간보다 기다리는 시간이 많다" → 관측 잡음(2장). 1ms 슬립 1,000회 실험: 유닉스 10~20% 오버헤드, 옛 Windows XP 180%(2.8초), 벤치마크를 감지해 속이는 OS 도 있었다.
6. **JVM 과 OS**: 네이티브 메서드·JNI. `System.currentTimeMillis()` → `JVM_CurrentTimeMillis()` → `os::javaTimeMillis()`(OS 별 소스). **컨텍스트 스위치**(유저→커널 모드 스위치는 TLB·캐시를 비워 돌아온 뒤에도 느리다, Soares·Stumm 그림). **vDSO** — `gettimeofday()` 처럼 특권이 필요 없는 syscall 을 유저 공간 매핑으로(리눅스만). 자바는 시간을 자주 읽으므로 반가운 이득.
7. **단순 시스템 모델**: 하드웨어/OS · JVM(또는 컨테이너) · 앱 코드 · 외부 시스템 · 유입 트래픽. "잘 도는 앱 = 자원을 효율적으로 쓰는 앱". **첫 단계는 어느 자원 한계에 부딪혔는지 알아내는 것.** OS 자체가 자원을 많이 먹으면 안 된다.
   - **CPU**: `vmstat 1`(r/b, swpd/free/buff/cache, si/so, bi/bo, in/cs, us/sy/id/wa/st) · `ifstat` · `iostat`. CPU 바운드면 유저 100% 를 목표. 100% 가 아니면 "왜?" — 락의 비자발적 컨텍스트 스위치? I/O 블로킹? `cs` 열이 높으면 그중 하나. 더 깊게는 JMC·JFR.
   - **GC**: HotSpot 힙은 유저 공간에서 관리(`sbrk()` 없음) → **시스템 CPU 가 높으면 GC 가 아니다**, 유저 100% 면 GC 일 수 있다 → **GC 로그를 봐라**(비용은 잡음 수준, 운영에서 반드시 켜라, 관측 도구의 집계 메트릭은 개별 이벤트를 잃는다).
   - **I/O**: 추상화가 없다("스피닝 러스트"). 대부분의 자바 앱은 I/O 를 포화시키지 않는다. 가상화 환경의 **시끄러운 이웃**.
8. **기계적 공감** 결론 — 캐시 라인 **거짓 공유**(같은 라인의 두 변수를 두 스레드가 갱신 → 핑퐁 무효화). 자바는 필드 배치를 보장하지 않으므로 **패딩**으로 다른 라인에.

## 4. JDK 25 기준 평가

**JVM 버전에 결부된 문장이 없다.** 하드웨어·OS 이야기라 25 에서 고칠 것이 없고, 다음만 짚어 둔다.

- 거짓 공유 회피의 자바 측 도구 `@Contended` 는 `jdk.internal.vm.annotation` 에 있어 앱이 쓰려면 `--add-exports` 가 필요하다(1판 검토 §4 에서 17 확인 ✅). 25 도 같다 📄.
- `Caching` 예제의 "16배가 아니라 같다"는 명제는 이 저장소의 **CN-07A**(행/열 순회)와 같은 원리를 다른 모양으로 잰 것이다 — 2판 그대로의 코드는 옮기지 않았다.
- vDSO·컨텍스트 스위치 비용은 리눅스 커널 이야기 📄.

## 6. 면접에서 쓸 수 있는 문장

- "배열의 모든 원소를 만지는 것과 16개마다 만지는 것이 거의 같은 시간이 걸립니다. 지배적인 비용은 연산이 아니라 캐시 라인을 메모리에서 끌어오는 것이기 때문입니다."
- "시스템 CPU 시간이 높으면 GC 가 아닙니다. HotSpot 은 힙을 유저 공간에서 관리하니까요. 유저 CPU 100% 면 GC 로그부터 봅니다."
- "x86 은 스토어끼리 재배열하지 않지만 ARM 은 합니다. 그래서 JMM 은 약하게 정의돼 있고, x86 에서 안 나던 동시성 버그가 ARM 서버에서 납니다."
