# 8장 — 클라우드 스택의 구성 요소 (Components of the Cloud Stack)

> *Optimizing Cloud Native Java* 2판(2024) 8장 요약. **착수 순서 6순위**(클라우드 신규 장). 표기 — ✅ 실행해 확인 · 📄 문서로만 아는 것.
>
> **1판에 없던 신규 장.** 책 제목의 "Cloud Native" 가 여기서 시작한다. 8~9장은 자바가 아니라 **JVM 이 놓이는 자리**(가상화 → 컨테이너 → 오케스트레이션)를 설명하고, 10~12장(관측가능성)의 배경이 된다.
> JVM 버전에 결부된 문장은 마지막 「자바의 관심사」 절뿐이다.

---

## 1. 이 장의 핵심 주장

1. **클라우드 네이티브의 정의는 표준 단체가 준다.** MicroProfile 6.1(Config·Fault Tolerance·Health·Metrics·OpenAPI·Telemetry·JWT·REST Client)과 CNCF 의 정의("동적·확장 가능한 환경에서 구축·실행되는 애플리케이션 — 컨테이너·서비스 메시·마이크로서비스·불변 인프라·선언적 API"). CNCF 랜드스케이프와 **성숙도(sandbox → incubating → graduated)** 로 어떤 도구를 골라도 되는지 판단한다.
2. **가상화의 층**: 하이퍼바이저 타입 1(베어메탈: KVM·Hyper-V·ESXi)·타입 2(호스트 OS 위: VirtualBox) → VM. 그 위에 **컨테이너** — 별도 커널이 없고 호스트 커널을 공유한다. 격리는 **리눅스 네임스페이스**(pid·net·mnt·uts·ipc·user·cgroup)로, 자원 제한은 **cgroups**(CPU·메모리·I/O)로 한다. "컨테이너는 가벼운 VM 이 아니라 격리된 프로세스"라는 것이 이후 자바 절의 전제다.
3. **OCI 이미지 = 레이어의 스택.** Dockerfile 의 각 명령이 읽기 전용 레이어를 만들고 맨 위에 쓰기 가능한 컨테이너 레이어가 얹힌다. **멀티스테이지 빌드**(빌드용 JDK 이미지 → 실행용 JRE/UBI 이미지) 와 **Jib**(Docker 데몬 없이 Maven/Gradle 에서 레이어 이미지 생성 — 의존성·리소스·클래스를 별도 레이어로 나눠 캐시 적중률을 올린다) 을 권한다.
4. **이미지 크기는 기본 이미지가 정한다.** 책의 수치: UBI-micro 37.1MB, UBI-minimal 147.8MB, Temurin Windows 서버코어 2.27GB. 작은 이미지는 전송·기동·공격 표면 모두에 유리하지만 **디버깅 도구(jcmd·jstack·셸)가 없다** 는 대가가 있다 — 12장이 `jcmd` 를 컨테이너 밖에서 어떻게 쓰는지로 이어진다.
5. **트래픽 방향**: **north-south**(외부 ↔ 클러스터, 인그레스/로드밸런서) 와 **east-west**(서비스 ↔ 서비스, 서비스 메시). 지연·관측이 각각 다른 곳에서 일어난다.
6. 예제 프로젝트 **Fighting Animals** — 이 장부터 15장까지 이어지는 미니 서비스(브랜치별로 Dockerfile → Compose → K8s → Argo 로 진화). 이 저장소에는 옮기지 않았다.
7. **자바의 관심사**(이 장의 유일한 JVM 부분):
   - 자바 워크로드의 **70% 이상이 컨테이너**에서 돌고 그중 **절반 가까이가 CPU 1개**로 뜬다는 조사 인용 → 그 JVM 은 **에르고노믹스가 SerialGC 를 고른다**.
   - JDK 17 은 **cgroups v2** 를 인식한다(JDK-8230305). 컨테이너 안에서 JVM 은 자기가 보는 CPU·메모리로 스스로를 구성한다.
   - **1GB 메모리 쿼터 → 기본 힙 256MB**(`MaxRAMPercentage` 25%). "왜 힙이 이렇게 작지?" 의 답.
   - `-XX:MaxRAM`·`MaxRAMPercentage`·`ActiveProcessorCount` 가 컨테이너 튜닝의 손잡이.

## 4. JDK 25 기준 평가

책은 JDK 21 기준이며, 이 장의 JVM 문장은 25 에서도 그대로다. 우리가 실행으로 확인한 것:

| 책의 문장 | JDK 25 실행 결과 | 상태 |
|---|---|---|
| CPU 1개 → Serial, 2개 → G1 | `-XX:ActiveProcessorCount=1` → SerialGC, `=2` → G1 (MaxRAM=8g 를 줘도 1 CPU 면 Serial) | ✅ CN-04A |
| `MaxRAM` 으로 힙 상한을 정한다 | `-XX:MaxRAM=2g` → `maxMemory` 495MB(25%), `MaxRAMPercentage=50` → 1024MB | ✅ CN-04B |
| MaxRAM 이 "서버 클래스" 판정에 영향 | **영향 없음** — CPU 2 + MaxRAM=1g 도 G1. 서버 클래스 판정은 CPU 수와 **실제** 물리 메모리를 본다. 책은 이 구분을 하지 않는다 | ✅ CN-04A(첫 판 REFUTED 에서 얻은 관측) |
| `commonPool` 병렬도 = CPU−1 | 4 CPU → 3, `ActiveProcessorCount=2` → 1 | ✅ CN-09A |
| cgroups v2 인식 | 이 컨테이너 환경에서 cgroup 한계를 바꿔 볼 수 없어 **미실행** | 📄 |
| 1GB 쿼터 → 256MB 힙 | 위와 같은 이유로 MaxRAM 으로 대신 확인(2g → 495MB) | ✅ 간접 |

25 에서 더해진 것 📄: `-XX:+UseCompactObjectHeaders`(JEP 519, 25 정식) 가 컨테이너 힙 예산에 직접 영향을 준다(CN-05C 에서 객체 16→8바이트 ✅). AOT 캐시(JEP 483/514)는 이미지 빌드 단계에서 만들어 넣는 것이 자연스럽다 — 단, **클래스패스가 JAR 이어야** 한다(CN-06A ✅).

## 6. 면접에서 쓸 수 있는 문장

- "컨테이너에 CPU 1개를 주면 JVM 은 자기를 서버 클래스가 아니라고 판단해 SerialGC 로 뜹니다. G1 을 원하면 명시해야 합니다."
- "컨테이너 메모리 1GB 를 줬는데 힙이 256MB 인 것은 버그가 아니라 `MaxRAMPercentage` 기본 25% 입니다. 나머지는 메타스페이스·코드 캐시·스레드 스택·네이티브 몫입니다."
- "이미지를 UBI-micro 로 줄이면 37MB 지만 `jcmd` 도 셸도 없습니다. 진단은 사이드카나 임시 디버그 컨테이너로 해야 합니다."
