## 1. 이 장의 핵심 주장

1. **관측 가능성은 모니터링의 연장·일반화**다. 신비로운 개념이 아니라 (1) 운영 시스템을 계측해
   데이터를 만들고 (2) **완전히 분리된 시스템**으로 내보내 저장하고 (3) 미리 정하지 않은 질문을
   던질 수 있는 분석 도구를 제공하는 세 단계다.
2. 관측 데이터는 **장애 중인 시스템 바깥에** 있어야 하고, 관측 시스템은 운영 시스템과
   **같은 시점에 업그레이드하면 안 된다.**
3. **세 기둥(Three Pillars)** — 메트릭·로그·트레이스는 데이터의 모양·부피 증가 방식이 근본적으로
   달라서 별도 데이터 소스로 다뤄야 하고, 그래서 오픈소스 도구가 기둥 하나씩에 갇혀 있다.
4. **프로파일링을 네 번째 기둥으로 보려는 흐름**이 있으나 오버헤드 때문에 온디맨드/연속 두 방식으로
   갈라졌다(12장으로 이어진다).
5. 안티패턴 둘 — **메트릭에 억지로 밀어 넣기**(특히 퍼센타일 재집계), **상관 ID 로그로 트레이싱 흉내내기**.
6. 장애 유형(회귀·불안정 컴포넌트·스플릿 브레인·썬더링 허드·연쇄 장애·복합 장애)마다 **어느 기둥이
   먼저 신호를 주는지**가 다르다.

## 2. 절별 상세 요약

### 2-1. 무엇이고 왜인가

- 세 갈래에서 왔다: **제어 이론**("바깥에서 내부 상태를 얼마나 추론할 수 있는가"), **"클라우드는
  다르다"**(불변 인프라라 SSH 로 들어가 디버깅하는 운영이 불가능), **APM 시장**(New Relic·Dynatrace·
  AppDynamics 가 오픈소스 컴포넌트를 채택하며 "관측 가능성 벤더"로 재정의).
- Charity Majors 인용: *"미리 질문을 정의하지 않아도 되어야 한다."* 장애 분석은 **가설 검정에 가까운
  탐색**이라 그래프와 쿼리 도구가 기본 UI 다.
- "모니터링은 운영팀 일"이라는 사고방식을 버려야 한다 — 내부 구조를 모르면 건강 상태를 판단할 수 없다.

### 2-2. 세 기둥

| 기둥 | 정의 | 부피가 늘어나는 방식 | 형태 |
|---|---|---|---|
| **메트릭** | 일정 주기로 집계된 숫자(카운터·게이지·히스토그램). 타임스탬프·이름·값·**차원**(태그) 네 부분 | **요청량과 무관** — 고정 주기라서 | 시계열 |
| **로그** | 특정 시점의 불변 이벤트 기록. 비정형 텍스트 + 심각도. 심각도 없는 구조화 레코드는 **이벤트**(구조화 로그) | 요청량과 단순 관계 없음, 규율이 나쁘면 **초선형** | 텍스트 |
| **트레이스** | 최상위 서비스 호출 하나의 기록. **스팬**의 트리. `trace_id`·`span_id`·`parent_id` 로 연결 | **요청량에 선형**(샘플링해도 대체로) | 구조화·지속시간 |

- **차원(dimension)의 조건**: 값끼리 **집계가 의미 있어야** 한다(system/user CPU 는 합쳐도 되지만
  방마다 온도는 안 된다). 카디널리티는 낮아야 하고, 여러 차원이면 **곱**이 최대 카디널리티다.
  사용자 ID 100만 개는 차원이 될 수 없다.
- **GC 이벤트를 메트릭으로 만들 때의 주의**: GC 는 고정 주기가 아니라 이벤트다. 고정 창으로 집계하는
  순간 정보가 사라진다 — 히스토그램으로 남기더라도 원래 이벤트보다 못하다는 것을 기억하라.
- 로그는 **중앙 집중(centralized) 로깅**이 표준이고, 진짜 분산 로깅은 극단적 경우뿐이다. ELK
  (Logstash·Elasticsearch·Kibana) 스택은 비싸다 — DevOps 는 보통 UI 로만 쓴다.
- 트레이스 컨텍스트는 **W3C Trace Context** 헤더로 전파한다(책: 2024년 3월 기준 W3C Recommendation 📄).
  비동기 메시징의 트레이싱은 아직 정리 중이라 책은 **동기 요청-응답만** 다룬다.
- **샘플링**: OpenTelemetry 기본은 *ParentBased Always On* — 부모가 없으면 샘플링, 있으면 부모를 따른다.
  즉 **트레이스 시작점이 결정**하므로 성공/실패를 알기 전에 결정된다. 실패 트레이스(4xx/5xx)를 100%
  남기려면 **tail-based 샘플링**이 필요한데 이것은 여전히 어렵다.
- 트레이스 시각화는 traceview(Jaeger)가 보통인데 너무 저수준이다 — 저자들은 "새로운 시각화 형태가
  절실하다"고 쓴다(2024년 8월).

### 2-3. 메트릭 아키텍처 패턴

| 축 | 선택지 | 비고 |
|---|---|---|
| 차원 지원 | 차원(태그) vs 이름 접미사로 밀어 넣기 | `jvm.memory.used{area=heap,id=G1 Eden Space}` vs `jvm_memory_used_heap_G1_Eden_Space` |
| 이름 규약 | 점(OpenTelemetry) vs 스네이크(Prometheus, 단 Prometheus 도 라벨이라는 차원이 있다) | |
| 집계 위치 | 클라이언트 측 vs 서버 측 | **Prometheus 는 서버 측**, 대부분은 클라이언트 측 |
| 전달 방식 | 서버 폴(스크레이프) vs 클라이언트 푸시 | Prometheus 는 스크레이프. 단명 잡·보안상 엔드포인트를 못 여는 경우를 위해 **remote-write** 도 있다 |

### 2-4. 수동 계측 vs 자동 계측

- 수동 트레이싱의 진짜 문제는 코드 결합이 아니라 **"무엇을 추적해야 하는지 이미 안다고 가정"**하는 것이다.
  모르는 질문에 답하려고 관측하는데 아는 경로만 계측하면 **맹점**이 생기고, 맹점은 문제 위치에 대한
  거짓 인상을 준다.
- 로깅은 거의 항상 수동이지만 빠진 로그는 사고 후에 추가하면 되는 "사소한 불편"이다. 트레이싱은 다르다.
- 그래서 트레이싱은 **자바 에이전트(바이트코드 위빙)** 나 프레임워크 내장 지원으로 자동화한다.
  Quarkus 는 `quarkus-opentelemetry` 의존성만 넣으면 기본으로 `localhost:4317` 에 OTLP/gRPC 로 보낸다
  (책 각주: 상류 OpenTelemetry 기본값은 2024년 초에 **4318 HTTP/protobuf** 로 바뀌었다 📄).
- 메트릭은 수동(앱 고유 지표) + 자동(라이브러리·JVM 지표)의 **혼합**이 보통이다 — 11장 Micrometer 로 이어진다.

### 2-5. 안티패턴

**메트릭에 억지로 밀어 넣기**
- 메트릭은 이벤트 분포를 시계열로 **압축**한 것이다. 분포의 모양은 되돌릴 수 없이 사라진다 —
  `errors.per.hour` 로는 "분당 1건" 과 "마지막 0.1초에 60건" 이 같아 보인다.
- **퍼센타일을 집계하지 마라.** 퍼센타일은 원본 모집단이 있어야 계산된다. 미리 계산된 퍼센타일의
  평균은 *"진실로 위장한 거짓"* 이다(Brendan Gregg 인용과 함께).
- 다 모으지 마라 — "이 메트릭이 어떤 문제를 디버깅하는가?" 에 답 못 하면 필요 없는 메트릭이다.
  5분 CPU 평균처럼 너무 굵은 것은 알아챘을 때 이미 K8s 가 파드를 죽이고 있다.

**상관 ID 로그로 트레이싱 흉내내기**
- 로그 레벨이 전부 맞고, ID 생성 방식이 같고, ID 에 PII 가 없고(저자가 실제로 본 base64 PII ID 사례),
  로그 시스템이 **100% 흐름을 감당**해야만 성립한다. 100% 저장·100% 계산 비용에 컴포넌트마다 커스텀
  통합까지 — 결국 트레이싱보다 비싸다.

### 2-6. 관측 가능성으로 장애 진단하기

| 장애 유형 | 무엇이 일어나나 | 먼저 보이는 신호 |
|---|---|---|
| **성능 회귀** | 코드/설정 변경이 CPU·할당률·지연에 영향 | 메트릭 전후 비교, 특히 **카나리**(9장)와 함께. SLO + 오차 예산으로 알림 |
| **불안정 컴포넌트** | 특정 경로·요청에서만 불안정 → 배포 완료 후 발현 | **트레이스** 오류율 비교. **계절성**이 변경 시점과 발현 시점을 벌려 놓으니 **최근성 편향**을 경계 |
| **스플릿 브레인** | 통신 장애로 클러스터가 조각나 리더가 둘 | 노드마다 "내가 아는 리더"를 보고하게 하고 리더가 둘이면 알림. 재파티셔닝은 **분산 STW** — Kafka 에서는 그동안 아무 스레드도 읽지 못한다 |
| **썬더링 허드** | 재시작 등으로 다수 클라이언트가 동시에 경합 자원에 몰림(캐시 미스 폭주 포함) | 사용자 요청과 **무관한** 백엔드 부하 급증. 활성 커넥션 수의 **도함수**. 완화는 바운디드 큐로 배압 |
| **연쇄 장애** | 한 인스턴스 실패 → 나머지 부하 증가 → 도미노 | 전력망 비유의 한계: 소프트웨어는 영구 손상이 없고, **제어면이 데이터면과 분리돼 있으면** 트래픽을 덜어낼 수 있다. 그래서 관측 인프라는 데이터면과 분리돼야 한다 |
| **복합 장애** | 하류 지연 → 상류 타임아웃 → 헬스체크 실패 → 파드 재시작 → Kafka 재파티션 → 연쇄 | 트레이스로 하류 지연과 상류 타임아웃을 **상관**시킨다. 블레임 없는 회고로 관측을 개선 |

### 2-7. 벤더냐 오픈소스냐

- 세 기둥의 데이터가 너무 달라 **모든 관측 요구를 덮는 단일 OSS 프로젝트는 없다.** OpenTelemetry 가
  가장 가깝지만 범위가 **계측과 반출**에 한정된다.
- OSS 는 "직접 SaaS 파이프라인 조립" 또는 "클러스터 안에 전부"(eBPF 기반 포함, 단 클러스터 하나에 갇힘).
- 벤더가 여전히 우위인 것: 알림·서버리스 모니터링·합성/실사용자 모니터링·이상 탐지·**이벤트 상관**.
  마지막이 OSS 에서 가장 급한 빈칸이다.
- 비용 구조: 호스트에서 집계해 보내는 방식이 보통이고, 전부 보내는 방식은 리전 안에서만 현실적이다
  (하이퍼스케일러 이그레스 비용). 관측 시스템은 그 자체가 크리티컬 시스템이라 인건비까지 포함해 셈해야 한다.

## 3. 1판(2018)과 달라진 점

- **장 자체가 신설**이다. 1판에는 "observability" 라는 단어가 개념으로 등장하지 않는다.
- 1판 14장의 로깅 절(Log4j 2·Logback 성능, 로거 설계)은 2판에서 **"로그는 세 기둥 중 하나"** 라는
  위치로 재편됐고 라이브러리 성능 비교는 사라졌다.
- 1판이 다루던 저지연 메시징(Aeron·Agrona)은 사라지고, 그 자리를 **장애 유형 분류와 관측 아키텍처**가 차지했다.

## 4. JDK 25 기준 평가

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| GC 이벤트는 고정 주기가 아니라 메트릭화에 주의 | 변함없다. JDK 25 도 GC 는 이벤트(JFR `jdk.GCPhasePause` 등)로 나온다 | ✅ 25 `jfr metadata` 에 이벤트 존재 |
| OTel 기본 포트 4317 gRPC (Quarkus 예시) | 책 각주대로 상류 기본은 4318/HTTP 로 바뀌었다 | 📄 책 각주 |
| W3C Trace Context 가 2024-03 Recommendation | 확인하지 않았다 | 📄 미확인 |
| "트레이스 상관은 아직 미해결"(2024-08) | 이 저장소에서 확인할 방법이 없다 — 시점 서술로 읽어야 한다 | 📄 |

JVM 버전에 결부된 주장이 없어서 **이 장은 JDK 25 에서 고칠 것이 없다.** 시점 표시("at time of writing,
August 2024")가 붙은 문장만 그렇게 읽으면 된다.

## 6. 면접에서 쓸 수 있는 문장

- "메트릭은 요청량과 무관하게, 트레이스는 요청량에 비례해서, 로그는 규율에 따라 초선형으로 자랍니다.

  건강하지 않은 시스템을 건강하게 보이게 만듭니다."
- "상관 ID 를 로그에 심는 것은 트레이싱의 대체가 아닙니다. 로그를 100% 저장하고 100% 계산해야 성립하는
