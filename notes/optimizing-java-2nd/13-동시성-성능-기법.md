## 1. 이 장의 핵심 주장

1. 공짜 점심은 끝났다(Sutter 2005). 클럭은 ~3GHz 에서 멈췄고 **데이터 병렬 vs 태스크 병렬**을 구분해야 한다. JVM 은 GC·JIT 스레드 덕에 단일 스레드 앱도 멀티코어 이득을 본다.
2. **암달의 법칙** `T(N) = S + (T − S)/N` — 직렬 5% 면 최대 20배. **당황스러울 만큼 병렬(embarrassingly parallel)** 한 것만 무한히 확장된다. 공유 상태가 들어오는 순간 직렬 부분이 돌아온다.
3. `i = i + 1` 은 원자적이지 않다(`getfield`/`iadd`/`putfield`) → **잃어버린 갱신**. `volatile` 은 가시성만 주고 복합 연산은 못 지킨다. "대부분 잘 도는 동시 프로그램 ≠ 올바른 동시 프로그램"(Dijkstra).
4. **JMM 은 약한 메모리 모델**이다(강한 모델은 캐시 무효화가 버스를 삼킨다). 최소 요구일 뿐이라 강한 하드웨어에서 숨어 있던 버그가 약한 하드웨어에서 터진다. 개념: happens-before · synchronizes-with · as-if-serial · release-before-acquire.
   `synchronized` 의 세 한계(읽기/쓰기 구분 없음, 메서드/블록 단위, 시도 후 포기 불가). **읽기도 잠가야** 가시성이 보장된다. Java 9 가 JMM 을 C++11 쪽으로 확장.
5. **메서드 핸들**은 현대식 리플렉션 — `Lookup` 컨텍스트로 접근 제어를 우회 불가하게, **시그니처 다형성**으로 `invoke:(Ljava/lang/String;)I` 같은 정적 타입이 바이트코드에 남는다. `Unsafe` 의 자리를 메서드/Var 핸들이 이어받는다.
6. **CAS** 는 하드웨어에 있지만 JMM 의 일부가 아니다. `AtomicInteger` 는 VarHandle 로 이렇게 쓸 수 있다: `do { v = (int) V.getVolatile(this); } while (!V.compareAndSet(this, v, newValue));` — 재시도 루프는 경합에 선형으로 나빠진다. 락프리라 데드락은 없다. **스핀락**(x86 `xchg`)은 CPU 를 태우는 대가.
7. `java.util.concurrent` — `Lock`(`tryLock`, 조건, 메서드 넘는 락), `ReentrantLock`(비경합 시 락프리 CAS, `AbstractQueuedSynchronizer` + `LockSupport.park/parkNanos/parkUntil`), `ReentrantReadWriteLock`(`AgeCache`; 그래도 동시 컬렉션이 더 낫다), `Semaphore`(공정 모드, 비소유 스레드가 release 가능), `ConcurrentHashMap`(세그먼트, 스냅샷 이터레이터, 초기 크기), `CopyOnWrite*`, `CountDownLatch`(일회용)/`CyclicBarrier`(누가 리셋하나), **Executor** 팩토리 넷, `Future`.
8. **Fork/Join** — 작업 분할 + **작업 훔치기**. `commonPool()` 크기 = `availableProcessors() − 1`, 그런데 16-4-2 머신이 16 을 돌려준 사례(Goetz: "VM 은 OS 를 믿고 OS 는 하드웨어를 믿는다") → `-Djava.util.concurrent.ForkJoinPool.common.parallelism`. `parallelStream()` 은 commonPool 을 쓰며 **작은 컬렉션에서는 더 느리다**(암달).
9. **액터**(Pekko — Akka 의 라이선스 변경 후 포크): 불변 메시지·공유 상태 없음·시간 제한 처리기에 맞으면 빠른 승리, 요청-응답·공유 상태·무제한 실행이면 다른 추상화.
10. **가상 스레드**(Java 21): 스레드 병목(스택 1MB × 20,000 = 20GB)의 답. JVM 이 만들고 캐리어 풀(ForkJoinPool)을 공유, 스택 프레임은 힙 객체, "블로킹" I/O 는 실제로 논블로킹으로 바뀌어 캐리어를 양보(Java 17 의 소켓 NIO 재구현이 기반). **자동 가상화는 없다** — 명시적으로 만들어야 한다. `Thread.ofVirtual()`/`ofPlatform()` 빌더, `newVirtualThreadPerTaskExecutor()`(블록 스코프 executor, `AutoCloseable`). 한계: 선점 없음, **JNI·`synchronized` 피닝**(→ §4), 항상 데몬, 객체 풀과 안 맞음, 도구가 아직 대량 vthread 에 약함, ThreadLocal 은 ScopedValue 로.

## 2. 절별 상세 요약

### 2-1. 병렬성 입문
데이터 병렬(급여 처리를 코어별 직원 블록으로) vs 태스크 병렬(스레드·Executor, REST 요청당 스레드). 암달 그림 13-3. 공유 상태 → JMM.

### 2-2. 자바 동시성 기초
`Counter.increment()` 바이트코드와 A/B 스레드 인터리빙 표(초기 7 → 둘 다 8). 단일 CPU·OS 스케줄링만으로 재현된다. `volatile` 오해. `CounterExample` 출력의 중복 값. 동기화는 설계가 필요하고 아니면 오히려 느려진다 — **병렬화는 성능 테스트가 뒷받침해야 한다.** 비경합 `synchronized` 는 예전보다 훨씬 싸다.

### 2-3. JMM
JSR 133(Java 5). 강한/약한 모델과 MESI(7장). 최소 요구. 네 개념. `synchronized` = 모니터 소유 스레드의 뷰가 메인 메모리와 synchronizes-with. 비동기화 접근에는 아무 보장이 없다. 협력 메커니즘 — 한 스레드라도 규칙을 어기면 깨진다. JSR-133 Cookbook(추상 장벽; 인텔에서는 일부 no-op). Java 9 확장(C++11 호환). Shipilëv "Close Encounters of the JMM Kind".

### 2-4. 동시성 라이브러리 만들기
"스레드 핫(thread hot)" 성능 — 경합 없이 실행에 시간을 쓰는 프로필. 빌딩 블록: 락·세마포어 / 원자 / 블로킹 큐 / 래치 / Executor. 라이브러리는 OS 대신 **유저 공간**에서.
- **메서드·Var 핸들**: `invokedynamic` 의 BSM 이 돌려주는 콜 타깃. 리플렉션 `Method.invoke(receiver, Object[])` 바이트코드(가변 인자 박싱) vs `MethodHandle.invoke:(Ljava/lang/String;)I`. `MethodHandles.lookup()` 컨텍스트 = `setAccessible()` 해킹의 대체. 프레임워크가 `Unsafe` 로 하던 일의 앞길.
- **원자와 CAS**: 위 §1-6. "직접 원자 정수를 만들지 마라 — 표준 라이브러리가 이미 메서드 핸들(허용되는 곳에서는 Unsafe)을 쓴다."
- **락과 스핀락**: intrinsic 락은 OS 를 부른다 → 짧은 임계 구역에는 큰 오버헤드 → 스핀. 대가: 사용률·전력·발열.

### 2-5. 라이브러리 요약
스레드는 "동시성의 어셈블리어". §1-7 의 각 항목. `ExecutorService` 선택은 **경험적 튜닝**(코어 수 vs 스레드 수, 컨텍스트 스위치). `ThreadFactory`. 컬렉션 선택에는 JMH·마이크로벤치마크를 고려하라(부록 A).

### 2-6. Fork/Join 과 병렬 스트림
`ForkJoinTask` 는 스레드보다 가벼운 엔티티, 순수 함수·당황스러울 만큼 병렬한 일에만. 작업 훔치기는 분할 없이도 유용. commonPool 지연 초기화. 스트림 = 불변 시퀀스, 내부 반복, `Spliterator`. "맹목적으로 `parallelStream()` 으로 바꾸지 마라 — 이득은 직접적이고 측정 가능해야 한다."

### 2-7. 가상 스레드
- 그린 스레드(1.2/1.3 시대) → 1:1 플랫폼 스레드 → 21 의 vthread. `Thread.start()` = `clone()` 시스템콜. 프로세스 메모리 레이아웃(그림 13-7)의 스택 세그먼트.
- 설계 네 가지: JVM 이 관리 / 전용 플랫폼 스레드 없음(캐리어 공유) / 스택 세그먼트 정적 예약 대신 유연한 모델 / **(적어도 일부) I/O 를 하는 태스크용**.
- 컨텍스트 스위치가 유저 공간에서 → 더 싸다. 캐리어는 그냥 `ExecutorService`(OS 에는 플랫폼 스레드로 보임). `yield()` 로 캐리어를 내놓을 수 있지만 권장하지 않음.
- 클래스 계층: `Thread` 의 sealed 하위에 final `VirtualThread`. `Thread` 를 상속하면 항상 플랫폼 스레드. `Thread.currentThread()` 는 vthread 를 돌려주고 캐리어 프레임은 스택 트레이스에 안 보인다. Kotlin 코루틴은 컴파일러 상태 머신이라 다르다.
- **한계 목록**(책 원문): 블로킹 I/O 에서만 양보(선점 없음) / **JNI 와 `synchronized` 가 피닝**(j.u.c 락은 아님) / 항상 데몬·보통 우선순위 / 객체 풀 패턴과 안 맞음(단명이라 약한 참조가 쓸모없어짐) / JMC·JFR 에 부담, 새 관측 패턴 필요 / ThreadLocal 은 복잡하니 ScopedValue.
- Do/Don't: 새 직관을 배워라, 공짜 점심이 아니다, 계산 집약 태스크에 쓰지 마라(양보할 블로킹이 없다), Go 개발자 친구에게 고루틴 패턴을 물어라.
- **패턴**: NIO 논블로킹 API 를 직접 쓸 이유가 사라진다 — 블로킹 API 로 짜고 런타임에 맡긴다(async-await·"색깔 있는 함수" 회피가 Loom 의 설계 목표, 리액티브 도입은 비목표). 일부 스레드를 가상으로 **바꿔 보고 실제 시스템에서 측정**하라. `try (var executor = Executors.newVirtualThreadPerTaskExecutor())` 안에서 `serverSocket.accept()` → `executor.submit(() -> handle(socket))` — **fire-and-forget** 웹 서버, `volatile boolean isShutdown` 의 **Volatile Shutdown 패턴**.

### 2-8. 요약(책)
전환 시: 직선 처리 성능부터 정확히 재라 / 바꾸고 개선을 시험하라 / 테스트를 재실행하기 쉽게. 피할 것: 병렬 스트림 남발, 수동 락 자료구조, j.u.c 재발명. 지향: 동시 컬렉션으로 스레드 핫, 락 줄이기, 태스크 추상화.

## 4. JDK 25 기준 평가

배너 표의 근거를 풀어 쓴다.

- **`synchronized` 피닝(JEP 491, JDK 24)** — 책의 한계 목록에서 가장 중요한 항목이 **더 이상 참이 아니다.** 실험: `-Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1` 로 캐리어를 하나로 만들고,
  vthread A 가 `synchronized (LOCK) { Thread.sleep(600) }` 하는 동안 vthread B 의 시작 지연을 쟀다. **21: 607ms(PINNED), 25: 10ms(NOT pinned)** ✅. 21 에서 `-Djdk.tracePinnedThreads=full` 은 `reason:MONITOR` 스택을 찍었고, 25 에서는 아무것도 찍히지 않았다(JEP 491 은 이 프로퍼티를 제거했다고 적는다 📄).
  JFR `jdk.VirtualThreadPinned` 이벤트는 21·25 모두 있고 필드도 같다 ✅ — 이제는 네이티브 프레임 등 남은 피닝 사유에만 찍힌다. **JNI/네이티브 프레임 피닝은 그대로**다 📄. → **CN-13A**
- **ScopedValue(JEP 506, JDK 25 정식)** — `ScopedValue.where(V, "ok").run(...)` 가 프리뷰 플래그 없이 돈다 ✅. 중첩 재바인딩은 스코프 안에서만, 스코프를 벗어나면 `isBound()==false` 이고 `get()` 은 `NoSuchElementException` ✅. 스코프 안에서 `Thread.ofVirtual().start()` 한 자식은 **바인딩을 물려받지 않는다** ✅(상속은 `StructuredTaskScope` 를 통해서만 📄). → **CN-13C**
- **구조적 동시성(JEP 505)** — 25 에서도 프리뷰. `StructuredTaskScope.open()` 은 `--enable-preview --source 25` 로만 컴파일된다 ✅(21 의 프리뷰 API 와 모양이 다르다 — 21 에서는 `open()` 이 없어 컴파일 실패 ✅).
- **Unsafe(JEP 471 JDK 23 폐기, JEP 498 JDK 24 기본 경고)** — 25 에서 `allocateMemory` 호출 시 4줄 경고, `--sun-misc-unsafe-memory-access=deny` 면 `UnsupportedOperationException`, `=allow` 면 조용 ✅. 21 에는 그 옵션 자체가 없다(`Unrecognized option`) ✅. `AtomicInteger` 는 17·21·25 모두 **아직 `jdk.internal.misc.Unsafe` 필드 `U`** 를 쓴다 ✅ — 책의 VarHandle 예제는 "이렇게 대체할 수 있다"는 예시이지 JDK 의 실제 구현이 아니다. → **CN-15A**
- **commonPool** — `availableProcessors()−1`(4 → 3) ✅ 17·21·25. `-XX:ActiveProcessorCount=2` 면 procs=2, commonPool=1 ✅. → **CN-09A**
- **가상 스레드 기본 성질** — 데몬 ✅, `Executors.newVirtualThreadPerTaskExecutor()` 는 태스크마다 새 vthread ✅(→ **CN-13B**).
- "Java 17 에서 소켓 API 가 NIO 로 재구현" — 정확히는 **JDK 13(JEP 353)** 📄. 결론(vthread 의 기반)은 그대로.
- Pekko·JCiP·Sutter 인용은 시점과 무관.

## 6. 면접에서 쓸 수 있는 문장

- "가상 스레드가 `synchronized` 안에서 블로킹하면 캐리어를 놓지 못한다는 말은 JDK 21 까지입니다. 24 부터는 모니터 구현이 바뀌어 `synchronized` 에서도 언마운트됩니다. 남은 피닝 사유는 네이티브 프레임입니다."
- "`volatile` 은 가시성만 보장합니다. `i++` 처럼 읽고-더하고-쓰는 복합 연산은 `AtomicInteger` 의 CAS 나 락이 필요합니다."
- "`parallelStream()` 은 commonPool 을 쓰고 commonPool 은 코어 수 − 1 입니다. 컨테이너에서 CPU 를 1개로 제한하면 병렬성이 1 이 되니 병렬 스트림 이득이 사라집니다."
- "ThreadLocal 을 가상 스레드에 쓰면 수백만 개가 생길 수 있습니다. JDK 25 정식이 된 ScopedValue 는 스코프가 끝나면 값이 풀리고 자식에게 자동 상속되지 않습니다."
