## 1. 이 장의 핵심 주장

1. "성능 테스트" 라고 뭉뚱그리지 말라. **좋은 성능 테스트는 정량적**이며, 답해야 할 숫자 질문을 적고 경영진/고객에게 확인하라.
2. 일곱 종류 — 지연 · 처리량 · 부하 · 스트레스 · 내구 · 용량 계획 · 성능 저하 — 는 목표가 다르고 겹친다.
3. 세 황금률: 무엇을 신경 쓰는지 정하고 재는 법을 찾아라 / **쉬운 것이 아니라 중요한 것을** 최적화하라 / 큰 것부터 쳐라.
4. **하향식(top-down)**: 전체 애플리케이션이 코드 조각보다 벤치마크하기 쉽다(5장에서 상세).
5. 테스트 환경은 운영의 **정확한 복제**. 아니면 예측력이 없다. 인프라를 아끼는 것은 장애 비용을 셈하지 않은 거짓 절약이다.
6. 안티패턴의 뿌리는 기술이 아니라 **사람**이다 — Flichel 의 다섯 원인(지루함·이력서·동료 압력·이해 부족·존재하지 않는 문제)과
   네 인지 편향(환원주의·확인·전장의 안개·위험 회피).

## 2. 절별 상세 요약

### 2-1. 성능 테스트의 종류

| 테스트 | 질문 | 이 장의 서술 |
|---|---|---|
| 지연 | 트랜잭션 종단 시간은? | 경영진의 관심사라 가장 흔하고, 그래서 다른 테스트의 질문을 가린다. **평균은 쓸모없다**(5장 통계) |
| 처리량 | 동시 트랜잭션 몇 개까지? | 지연과 **등가**에 가깝다 — 지연은 통제된 처리량에서 말하고, 처리량 테스트 중에는 지연을 감시한다. 최대 처리량 = 지연 분포가 갑자기 바뀌는 **변곡점** |
| 부하 | 이 부하를 견디나? (예/아니오) | 신규 고객·캠페인·바이럴 대비 |
| 스트레스 | 한계점은? | 현재 피크에서 천천히 올려 관측값이 나빠지기 직전 |
| 내구(soak) | 오래 돌리면? | 느린 누수·캐시 오염·**CMS 의 동시 모드 실패로 이어지는 단편화**. 저지연 시스템은 풀 GC 의 STW 를 못 견뎌 이 테스트가 흔하다 |
| 용량 계획 | 자원을 늘리면 기대대로? | 스트레스와 닮았지만 미래 지향, 계획 활동 |
| 성능 저하(부분 실패) | 일부가 죽으면? | 클러스터 멤버 손실·**RAID 디스크 손실**·대역폭 급감. 금융권은 페일오버 테스트를 극도로 진지하게 한다. **Chaos Monkey**(Netflix) — 운영에서 실제 프로세스를 무작위로 죽인다; 최고 수준의 위생·설계·운영 성숙도가 전제 |

### 2-2. 모범 사례

- **하향식**. 테스트 팀에 필요한 것: 테스트 환경, 무엇을 재고 최적화할지에 대한 명확한 이해, SDLC 안에서의 위치.
- **테스트 환경 만들기**: 앱 서버(CPU 수·OS·자바 버전)뿐 아니라 웹 서버·DB·로드밸런서·방화벽까지. 복제 못 하는 외부 서비스는 목.
  기존 QA 환경을 시간 분할해 쓰는 것은 관리·일정 부담이 크다. 전통 환경은 "같은 머신을 사서 같이 설정"이면 되는데 경영진이 비용에 저항한다 —
  **거의 항상 거짓 절약**. 클라우드·오토스케일·"가축이지 반려동물이 아니다(livestock, not pets)" 는 환경 복제를 **더 어렵게도** 만들지만,
  안 쓸 때 꺼 두는 환경을 가능하게 한다(켜고 끄는 절차가 필요).
- **성능 요구사항 식별**: 2장의 단순 시스템 모델대로 성능은 코드·컨테이너·OS·하드웨어의 합 → **NFR** 은 시스템 전체 관측값으로.
  "95퍼센타일 100ms 단축", "같은 하드웨어로 5배", "평균 응답 30% 개선" / "고객당 자원 비용 50% 절감", "클러스터 50% 저하에도 목표의 25% 이내",
  "**지연 25ms 당 이탈률 25%** 감소". 킥오프에서 이해관계자와 합의.
- **자바 특유의 문제**: 동적 자기 관리(메모리 영역 튜닝, JIT). 컴파일 안 된 메서드는 (a) 덜 불렸거나 (b) 너무 크다 — (b)는 드물다.
  **초기 성능 작업 하나는 컴파일 로그를 켜서 핵심 경로의 메서드가 컴파일되는지 확인하는 것**(9장).
- **SDLC 의 일부로**: 회귀 테스트 상시화. 전용 환경 없이는 사실상 불가능.

### 2-3. 안티패턴 소개와 원인

- 안티패턴 = 많은 프로젝트에서 관찰되는 바람직하지 않은 행동. 분류하면 **패턴 언어**가 생겨 논의하고 없앨 수 있다.
- 출시 전날 UAT(운이 좋으면) 또는 운영에서 터지는 장애 — 성능 테스트를 안 했거나 팀의 "닌자"가 가정을 남기고 사라졌다(닌자는 그런 데 능하다).
- Carey Flichel 의 다섯 원인: **지루함**(`Collections.sort()` 대신 직접 정렬) · **이력서 채우기** · **동료 압력**(주니어의 "임포스터 증후군", 속도 경쟁) ·
  **이해 부족**(Hibernate 과정에서 만난, 주말에 Hibernate 를 뜯어내야 했던 수강생) · **오해된/존재하지 않는 문제**(재지 않고 해결).

### 2-4. 안티패턴 카탈로그

8개 항목 — **반짝이는 것에 홀림 / 단순한 것에 홀림 / 성능 튜닝 마법사 / 민간 전승으로 튜닝 / 비난의 당나귀 / 큰 그림 놓치기 / UAT 는 내 데스크톱 /
운영 같은 데이터는 어렵다(DataLite)** — 와 「스위치 만지작거리기」 상자. 항목별 **예시 발언·현실·논의·해결**은 2판 부록 B 와 글자 수준으로
같으므로 [`../optimizing-java-2nd/B-성능-안티패턴-카탈로그.md`](../optimizing-java-2nd/B-성능-안티패턴-카탈로그.md) 를 보라. 1판에만 있는 문장:

- 튜닝 마법사의 "현실": *"마법사가 실제로 하는 일은 복장 규정에 도전하는 것뿐이다."*
- 민간 전승의 JVM 버전 예: *"7 이나 6 에서 되던 것이 현재 버전(**Java 8**)에서 안 될 수 있고, 7 에서 유효한 스위치가 **다가오는 9** 에서 기동을 막기도 한다."*
  → ✅ 실제로 그렇게 됐다. `-XX:+PrintGCTimeStamps`·`PrintTenuringDistribution` 은 JDK 17 에서 `Unrecognized VM option`(§0 검토 8장).
- 스위치 개수: **Java 8u131 기준 700개 넘게**, 진단 모드로 100개쯤 더. ✅ 이 머신에서 세면 17: 559 / 21: 533 / 25: 513 — 줄고 있다.
- 큰 그림 놓치기의 8단계(운영 측정 → UAT 에서 하나씩 → 같은 스트레스 지점 → 대표 데이터 → 시험 → 재시험 → 남이 점검 → 페어 논의).

### 2-5. 인지 편향

- 비난의 당나귀 = **확인 편향 + 최근성 편향**. Works for Me("UAT 에서 됐으니 운영 장비 문제") 와 그 반대(전부 소프트웨어 탓)는 쌍대.
- **환원주의**: 복잡계는 창발한다. **확인 편향**: 운영과 다른 데이터로 NoSQL 이 빠르다고 증명. **전장의 안개(행동 편향)**: 장애 중 "뭐라도" —
  인프라 변경·라이브러리 변경·가장 바쁜 날에만 나오는 레이스. 충분한 로깅·모니터링이면 명확한 신호가 나와야 하는데 실패 시나리오를 시험한 앱이 드물다.
  **위험 회피**: 신뢰할 수 있는 단위·회귀 테스트만이 줄인다; 장애에서 배우지 못하는 형태로 나타난다.

## 4. 1판에만 있는 것 — 엘스버그의 역설

사람이 확률을 얼마나 못 다루는지 보여 주는 사고 실험. 공 90개(파랑 30, 나머지는 빨강/초록 미상). **첫 내기**: A) 파랑이면 $100 / B) 빨강이면 $100 → 대부분 A(알려진 1/3).
**둘째 내기**: C) 파랑 또는 초록 / D) 빨강 또는 초록 → 거의 전원 D(알려진 2/3). **A 와 D 를 함께 고르는 것은 비합리적**이다 — A 를 골랐다는 것은
"초록이 빨강보다 많다"는 의견이므로 논리적으로는 C 와 짝지어야 한다. 사람은 "알려진 미지"를 "알려지지 않은 미지"보다 선호한다(럼즈펠드의 표현).
성능 팀이 **익숙한 위험을 과대평가하고 낯선 개선을 과소평가**하는 이유의 모델로 읽으면 된다.

## 7. 면접에서 쓸 수 있는 문장

- "성능 테스트를 하겠다고 하면 먼저 어떤 숫자 질문에 답할지 적습니다. 지연·처리량·스트레스·내구는 서로 다른 질문입니다."
