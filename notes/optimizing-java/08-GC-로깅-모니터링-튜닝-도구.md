## 1. 이 장의 핵심 주장

1. **GC 로그는 최고의 정보원**이다 — 특히 프로세스가 죽은 뒤의 "미제 사건" 분석에. **모든 진지한 앱은 GC 로그를 만들고, 앱 출력과 별도 파일에 둔다.** 오버헤드는 관측 불가 수준(HotSpot 은 논블로킹으로 쓴다, ~0%)이므로 **운영에서 항상 켠다.** 30분 실행, 50 MB/s 할당에 ~600 KB.
2. **필수 플래그**(Java 8 기준 — §4 에서 다시 쓴다): `-Xloggc:gc.log` · `-XX:+PrintGCDetails`(`-verbose:gc` 의 대체) · `-XX:+PrintTenuringDistribution`(사람은 못 읽지만 **도구가 조기 승격을 계산하는 원자료**) · `-XX:+PrintGCTimeStamps`(VM 시작 후 초) · `-XX:+PrintGCDateStamps`(벽시계 — 앱 로그와 대조). 회전: `UseGCLogFileRotation`·`NumberOfGCLogFiles`·`GCLogFileSize`.
3. **GC 로그 vs JMX**: 로그는 **이벤트 구동**·저비용·50+ 항목, JMX 는 **샘플링**·RMI 비용·10 항목 미만. JMX 는 수집이 언제 돌았는지, 전후 힙 상태를 모른다 → 할당률·조기 승격 분석 불가, 장기 추세용. 게다가 RMI 는 방화벽 포트·프록시·**파이널라이제이션 의존** — RMI 를 쓰는 앱은 **한 시간에 한 번 풀 GC** 가 기본으로 걸린다.
4. **로그 파싱은 직접 하지 말라** — 형식이 마이너 릴리스마다 바뀌고, 홈메이드 파서는 **가장 필요한 순간에 깨진다.** 도구: **Censum**(jClarity, 상용; 할당률·조기 승격·유휴 이탈·누수·용량 계획·OS 간섭 자동 분석) · **GCViewer**(오픈소스, 기능 적음, 일부 형식만) · GarbageCat(간헐적 유지). 같은 데이터도 도구마다 시각화가 다르다(톱니의 두 그림).
5. **기본 튜닝 — 세 가지 사실**: ① GC 가 원인인지 확인·배제하는 것은 **싸다** ② UAT 에서 GC 플래그 켜는 것도 싸다 ③ 메모리·실행 프로파일러 셋업은 **비싸다.** 네 요인 — **할당 · 일시정지 민감도 · 처리량 · 객체 수명**, 그중 **할당이 가장 중요**. 플래그는 **한 번에 하나**, 효과를 완전히 이해하고, 조합의 부작용을 기억하라. `MaxPermSize` 는 Java 8 에서 무시된다 — 지워라.
6. **GC 가 범인인지 확인하는 검사**(vmstat): CPU ~100% · 그중 90%+ 유저 · GC 로그가 활발 → 셋 다면 GC 부터 튜닝. 결과가 "GC 는 OK / 아니다"로 명쾌하다.
7. **할당 이해**: Young 수집 사이의 데이터량 ÷ 간격 = 할당률(도구에 맡겨라). **지속 1 GB/s 이상이면 GC 튜닝으로 못 고친다** — 코드에서 할당을 줄여야. 네 영역 — 사소하고 피할 수 있는 할당(디버그 로그) · 박싱 · 도메인 객체 · 비-JDK 프레임워크 객체. 히스토그램 상위는 보통 `char[]`·`byte[]`·`double[]`·Map 엔트리·`Object[]`·내부 구조. **TLAB 할당 경로** — TLAB → 새 TLAB → Eden 직접 → Young GC → **Tenured 직접**(큰 배열만 여기까지 간다). `PretenureSizeThreshold`·`MinTLABSize` 는 벤치마크 없이 만지지 말 것. 할당 스파이크 → Young GC 가 촘촘해져 **조기 승격**; `MaxTenuringThreshold`(책: "기본 4, 1~15") 는 높이면 복사 증가, 낮추면 Tenured 압력.
8. **일시정지 이해**: 개발자는 일시정지에 **인지 편향**이 있다 — 사람 눈은 초당 5회, 100~200ms 는 웹 앱에서 안 보인다. 세 대역 — **>1s / 1s~100ms / <100ms**. 표 8-4 초기 수집기 선택(힙 크기 × 대역): <2GB Parallel/Parallel/CMS … >20GB Parallel-G1/G1/CMS. "G1 이 성숙하면 Parallel 의 자리를 넓힐 것". 동시 수집기라도 **먼저 할당을 줄여라** — 동시 모드 실패 확률이 준다.
9. **수집기 스레드와 GC 루트**: 루트 스캔 시간은 앱 스레드 수·코드 캐시 크기·힙 크기에 좌우. 큰 `Object[]` 는 **단일 스레드**가 훑는다(작업 훔치기 불가) — 긴 체인일수록 마킹이 나빠진다. **코드 캐시 루트 스캔은 단일 스레드(Java 8 기준)**. 카드 테이블 — 1바이트 = 512바이트 → **Old 1 GB 당 2 MB**. JMH `SimulateCardTable`(20 GB 힙, 30 MB 카드) ≈ **108.9 ops/s → 카드 스캔 ~10 ms** = Young 일시정지의 대략적 하한.
10. **Parallel GC 튜닝**: 가장 단순 — 완전 STW·높은 처리량·부분 수집 없음·힙 크기에 선형 일시정지. ~4 GB 이하에서 효과적. 옛 크기 플래그(`NewRatio`·`SurvivorRatio`·`NewSize`·`MaxNewSize`·`Min/MaxHeapFreeRatio`; Young = 1/(N+1), Eden = (K−2)/K) 는 **에르고노믹스가 더 잘하므로 최후 수단.**
11. **CMS 튜닝**: 어렵다는 평판은 부당하지 않다. "일시정지 나쁨 → 동시 수집기 좋음"은 단순 논리 — **진짜 저지연이 필요할 때만 최후 수단으로.** 플래그 ~100개(8u131) → 스위치 만지작·민간 전승·큰 그림 놓치기 안티패턴. 동시 수집 중 **코어 절반이 GC** → **연속(back-to-back) 수집** 이 동시 모드 실패 직전 신호이고 그때 처리량은 50% 감소 — 견딜 수 있는가? `ConcGCThreads` 를 줄이면 더 위험. STW 두 번(Initial Mark·Remark). `CMSInitiatingOccupancyFraction`(기본 75%) + `UseCMSInitiatingOccupancyOnly`(적응 끄기) — 폭발적 할당엔 여유를 늘려(값을 낮춰) CMF 를 줄인다. **단편화 CMF** 는 `-XX:PrintFLSStatistics=1`(Total Free Space·Max Chunk Size·Number of Blocks·Av. Block Size·Tree Height)로 예측 — Parallel 로 떨어지는 긴 STW 를 미리 안다.
12. **G1 튜닝**: 목표는 "최대 힙과 `MaxGCPauseMillis` 만 주면 알아서" — **아직 거기 못 갔다.** 실험 옵션(`G1NewSizePercent`·`G1MaxNewSizePercent`)엔 `UnlockExperimentalVMOptions`. Kirk Pepperdine 의 **regions**(JavaFX) 로 리전 배치 시각화. 초기 G1 내부가 많이 바뀌어 **옛 글들은 민간 전승** — Java 9 기본 수집기가 되니 튜닝 관행이 아직 형성 중. CMS 대비 G1 의 약속 = **증분 압축으로 CMF 회피**: 높고 안정된 할당률·단명 객체 워크로드는 **큰 Young + 테뉴어링 최대(15) + 견딜 수 있는 가장 긴 일시정지 목표.**
13. **jHiccup**(Gil Tene, HdrHistogram 계열): JVM 이 연속 실행되지 못한 "딸꾹질"을 잰다 — GC STW 뿐 아니라 OS·플랫폼 효과도. `-javaagent:jHiccup.jar` 또는 `jHiccup -p <pid>`, `.hlog` → `jHiccupLogProcessor`. 7장의 Shenandoah 비교 그래프가 이걸로 만들어졌다. ModelAllocator 를 Censum 으로 보면 **HotSpot 이 힙 크기의 안정 상태를 못 찾는다** — 에르고노믹스 세부에 과도하게 신경 쓰지 말라.

## 4. JDK 17 / 25 기준 보정 — 플래그 표를 통합 로깅으로 다시 쓴다

**책의 표 8-1 을 지금 JVM 에 그대로 넣으면 기동이 실패한다.** JDK 17 에서 실행한 결과(PERF-08A ✅, `00-검토` §2):

| 책의 플래그 | JDK 17/21/25 | 대체 |
|---|---|---|
| `-Xloggc:gc.log` | 아직 받아 준다(`-Xlog:gc:file=` 로 번역) | `-Xlog:...:file=gc.log` |
| `-XX:+PrintGCDetails` | **경고 후 기동** — "deprecated … Use -Xlog:gc* instead" ✅ | `gc*` 태그 |
| `-XX:+PrintTenuringDistribution` | **Unrecognized — 기동 실패** ✅ | `gc+age=trace` |
| `-XX:+PrintGCTimeStamps` | **Unrecognized — 기동 실패** ✅ | 데코레이터 `uptime` |
| `-XX:+PrintGCDateStamps` | **Unrecognized — 기동 실패** ✅(`00-검토`) | 데코레이터 `time` |
| `UseGCLogFileRotation`·`NumberOfGCLogFiles`·`GCLogFileSize` | 제거 📄 | 출력 옵션 `filecount=5,filesize=10M` |
| `-XX:MaxPermSize` | 제거(경고 후 무시) 📄 | `-XX:MaxMetaspaceSize` |

**지금의 "필수 GC 로깅 한 줄"**(같은 정보를 전부 담는다):

```
-Xlog:gc*,gc+age=trace,safepoint:file=gc.log:time,uptime,level,tags:filecount=5,filesize=10M
```

`-Xlog:gc` 한 줄의 출력 형식(PERF-08A 가 파싱하는 그것 ✅):

```
[0.190s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 13M->1M(32M) 1.013ms
```

전후 힙·총 힙·일시정지 시간·원인이 한 줄에 있다 — **책이 로그에서 읽으라던 것은 그대로**이고 만드는 명령만 바뀌었다. 32 MB 힙에 768 MB 를 흘리면 Young 일시정지 43회, 전부 "후 힙 < 전 힙" ✅.

그 밖의 보정:

| 책의 문장 | 지금 | 상태 |
|---|---|---|
| Censum 이 스트리밍 API 로 JMX 의 이점을 지운다 | Censum 단종(jClarity 2019 인수). **JFR 이벤트 스트리밍**(JDK 14) 이 그 자리 — `jdk.GCPhasePause`·`jdk.GarbageCollection` | ✅ CN-12A(스트리밍 동작) |
| 로그 파서를 직접 짜지 말라 | **그대로 맞다.** PERF-08A 첫 판이 "(G1 Evacuation Pause)" 의 숫자 1 에 걸려 한 줄도 못 읽었다 — 책의 경고를 스스로 재현했다 | ✅ |
| `MaxTenuringThreshold` 기본 4 | **기본 15**(G1·Parallel·Serial; 4 는 옛 CMS 값에 가깝다) | ✅ JDK 25 `PrintFlagsFinal` |
| 표 8-4 (Parallel/G1/CMS) | CMS 제거(JDK 14). 지금의 표: **1 CPU 컨테이너 = Serial(에르고노믹스)** · 처리량 = Parallel · 기본 = G1 · <1 ms 일시정지 = **세대형 ZGC**(21 옵션, 24 부터 유일) · Shenandoah(25 세대형 정식) | ✅ CN-04A·05A·05B |

| G1 은 실험 옵션이 많고 관행이 형성 중 | `G1NewSizePercent` 등은 **여전히 experimental**. 기본 `MaxGCPauseMillis` 200, `GCTimeRatio` 12, 리전 2 MB(3.4 GB 힙) | ✅ JDK 25 |
| JMX/RMI → 시간당 풀 GC | `sun.rmi.dgc.*` 기본 1시간은 그대로이나, JDK 9+ 에서 `System.gc()` 는 G1 의 동시 풀 사이클로도 처리 가능(`-XX:+ExplicitGCInvokesConcurrent`) | 📄 |
| jHiccup | 유지 중(Azul). JFR `jdk.SafepointBegin`·`-Xlog:safepoint` 가 같은 정보 | 📄 |

## 6. 면접에서 쓸 수 있는 문장

- "GC 로그는 운영에서 항상 켭니다. 비용은 잡음 수준이고, 장애 뒤 분석은 로그가 유일한 근거입니다. 다만 `PrintGCDetails` 는 옛 플래그라 지금은 `-Xlog:gc*` 한 줄입니다."
- "GC 튜닝 전에 세 가지를 봅니다. CPU 가 100% 인가, 그중 유저가 90% 이상인가, GC 로그가 바쁜가. 셋 다면 GC 부터 봅니다. 지속 할당률이 1 GB/s 를 넘으면 튜닝이 아니라 코드에서 할당을 줄여야 합니다."
- "일시정지 목표는 사람 기준으로 정합니다. 웹 앱에서 100~200ms 는 안 보입니다. 1초 미만·100ms 미만이 진짜 요구인지부터 확인하고 수집기를 고릅니다."
