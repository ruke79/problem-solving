# 6장 — 가비지 컬렉션 이해 (Understanding Garbage Collection)

> *Optimizing Java* 1판(2018) 6장 요약. [`00-검토`](00-검토-2018년-책과-현재.md) §7 의 **착수 순서 4순위**(GC 이론).
> §7 의 보정("CMS 절은 동시 수집기 일반으로") 은 **7장**에 해당하고, 이 장은 CMS 를 4회만 스치므로 **거의 그대로 옮겨도 된다.**
> 표기 — ✅ 실행해 확인(JDK 17.0.19 / 21.0.10 / 25.0.4) · 📄 문서로만 아는 것.

## 1. 이 장의 핵심 주장 (2판 4장과 같다)

마크 앤 스윕 → 용어집(STW·동시·병렬·정확/보수·이동·압축·퇴거) → HotSpot 런타임(oop·마크 워드·klass 워드·압축 oop·GC 루트·아레나) →
할당률과 객체 수명 → **약한 세대 가설** → TLAB·반구 수집·서바이버·카드 테이블 → 병렬 수집기(Parallel/ParNew/ParallelOld, 영·올드 컬렉션, 한계) →
할당의 역할(단순 모델, `ModelAllocator`, 버스트와 **조기 승격**). 자세한 절별 요약은 [2판 4장 §2](../optimizing-java-2nd/04-GC-이해.md).

## 2. 1판에만 있는 것

- **PermGen 과 klassOop**: "Java 7 이하에서는 klass 워드가 힙 안의 **PermGen** 을 가리키고 klass 자체가 객체 헤더를 가진 `klassOop` 이었다. Java 8 부터 klass 는 힙 밖(메타스페이스, JVM 의 C 힙 안)에 있어 헤더가 필요 없다."
  → 2판은 8+ 만 설명한다. **JDK 17·21·25 도 메타스페이스**(`MetaspaceSize=22MB` 초기, `MaxMetaspaceSize` 무제한 ✅ 25 플래그).
- **oop 계층(OpenJDK 8)**: oop → instanceOop / methodOop / arrayOop / symbolOop / klassOop(7 이하) / markOop. → 2판(Java 22)은 oop → instanceOop / **stackChunkOop** / arrayOop → objArrayOop / typeArrayOop. `methodOop`·`symbolOop`·`klassOop` 은 8 에서 이미 힙 밖 메타데이터가 됐다 📄.
- **아레나**: "HotSpot GC 는 아레나라는 메모리 영역 단위로 일한다" 한 문단 — 2판 삭제.
- **Censum**으로 할당률을 정밀 측정 → 2판은 **JFR** 로 바꿨다(Censum 단종).
- **"G1 이 9 부터 기본이 될 것이라는 Oracle 의 의도"** 예고 → ✅ 실현(17·21·25 기본 G1).
- 용어집의 "동시" 설명: "진정한 동시 알고리즘은 사실상 없다 — CMS 는 '대부분 동시'" → 2판은 "동시는 눈금이다" + G1 언급으로 바꿨다.
- Firefox SpiderMonkey 가 자바 GC 의 기능(정확성·압축)을 따라온다는 비유 → 2판 삭제.
- 영 GC 일시정지 "2GB JVM 에서 몇 ms, 10ms 미만이 매우 흔함" → 2판 "몇 ms, 서브 ms 도".
- 병렬 수집기 각주 없음 → 2판은 "17 쯤이면 Parallel 이 G1 을 이기는 워크로드를 찾기 어렵다, 재라" 를 각주로.
- 2판이 **더한** 것(1판에 없는 것): `System.gc()` 무용론·Rust/Go 비교(1판에도 Go/Rust 는 있다), GC = 이벤트 → 10장 메트릭, HyperAlloc, Serial 의 컨테이너 자동 선택 경고, 주기적 GC 각주, `record Entry` 예.

## 3. JDK 17 / 25 기준 — 어긋나는 것

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| "Java 8 이하 기본은 병렬 수집기" | 9 부터 G1. 17·21·25 이 머신 기본 `Using G1` | ✅ |
| ParNew 는 CMS 와 짝 | CMS·ParNew 모두 14 에서 제거 — `-XX:+UseParNewGC` 도 `Unrecognized`(1판 검토 §2 에서 17 확인) | ✅ |
| 헤더 = 마크 워드 + klass 워드(압축 32비트) | 기본은 그대로(`new Object()` 16바이트). **25 의 컴팩트 객체 헤더**(JEP 519) 를 켜면 8바이트 | ✅ CN-05C |
| 압축 oop 기본(7+) | 그대로 `UseCompressedOops=true`, `ObjectAlignmentInBytes=8` | ✅ |
| Censum 으로 할당률 | JFR `jdk.ObjectAllocationSample`(17+ 저오버헤드 샘플링 이벤트) | ✅ 이벤트 존재(17·21·25 `jfr metadata`) |
| VisualGC / VisualVM | VisualVM 은 9 부터 별도 배포 | 📄 |
| "GC 로그로 분석(8장)" | 로그 형식이 통합 로깅으로 바뀌었다 | ✅ PERF-08A |
| 서버급 판정 → Serial | 컨테이너 CPU 1개면 Serial(1판은 언급 없음) | ✅ CN-04A |

## 5. 면접에서 쓸 수 있는 문장

- "자바 8 부터 클래스 메타데이터는 힙 밖 메타스페이스에 있습니다. PermGen 의 `OutOfMemoryError: PermGen space` 는 이제 없고, 대신 메타스페이스는 기본 상한이 없어 클래스 누수가 네이티브 메모리로 번집니다."
- "TLAB 덕분에 할당은 포인터 하나 옮기는 O(1)입니다. 그래서 자바에서 객체 생성 비용을 걱정하기보다 그 객체가 얼마나 사는지를 걱정해야 합니다."
