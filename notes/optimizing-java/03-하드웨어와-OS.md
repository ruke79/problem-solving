## 1. 이 장의 핵심 주장

1. **무어의 법칙**(18개월마다 트랜지스터 2배, 1965) 은 "실질적으로 끝났다"고 볼 이유가 충분하다. 트랜지스터 예산을 쓰느라 하드웨어가 복잡해졌고, 소프트웨어도 그것을 쓰려면 복잡해진다("소프트웨어가 세상을 먹는다" — Andreessen). 자바는 이 추세의 **수혜자**였다.
2. **메모리가 병목**: 2+ GHz 프로세서는 첫 IBM PC 의 4.77 MHz 보다 수백 배 빠른데 메모리는 못 따라갔다(Hennessy·Patterson 그림) → **캐시 계층**(L1/L2 코어 전용, L3 공유, 노스브리지 너머 메인 메모리). **MESI**(64바이트 라인, Modified/Exclusive/Shared/Invalid, 한 프로세서가 E/M 로 가면 나머지는 I; 버스에 의도를 방송). write-through → write-back. 대역폭 = 메모리 클럭 × 버스 폭(64비트) × 인터페이스 수(2) × 2(DDR) → **2015년 상용 하드웨어 이론 최대 8~12 GB/s**.
3. **`Caching` 예제**: `touchEveryItem()`(모든 int) vs `touchEveryLine()`(16개마다) — 직관은 16배, **실제는 거의 같다**(100MB 를 ~2.86ms, 유효 대역폭 ~3.5 GB/s; 이상치 30~35%). 지배 효과는 캐시 채우기. 하드웨어 **프리페처**가 규칙적 스트라이드를 감지한다. **할당률 상한의 잣대**.
4. **현대 프로세서 기능**: **TLB**(페이지 테이블 캐시; 없으면 L1 에 있어도 16사이클; JVM 의 TLAB 과 혼동 금지) · **분기 예측·추측 실행**(파이프라인 최대 20사이클 정지; 2018년 초 보안 사고 = Meltdown/Spectre) · **하드웨어 메모리 모델**(표 3-2 — x86/AMD64 는 스토어-스토어 재배열 안 함, ARMv7/POWER 는 거의 다 함) → **JMM 이 약하게 정의된 이유**. **기계적 공감**(Martin Thompson, 재키 스튜어트).
5. **OS**: MMU·페이지 테이블. **스케줄러** — 런 큐, 타임 퀀텀(옛 OS 10/100ms), 그린 스레드는 버려졌다, 스레드 생애주기 그림 3-6. "코드는 도는 시간보다 기다리는 시간이 많다" → 관측 잡음. **1ms 슬립 1,000회**: 유닉스 10~20% 오버헤드, Windows XP 180%(2.8초), 벤치마크를 감지해 속이는 OS 도 있었다.
6. **시간**: `System.currentTimeMillis()` → `JVM_CurrentTimeMillis()` → `os::javaTimeMillis()`(BSD 는 `gettimeofday`, Windows 는 1601년 기준 100ns `FILETIME`, `UseFakeTimers`). Windows 는 시계 정확도가 하드웨어마다 달라 타이밍이 들쭉날쭉.
7. **컨텍스트 스위치**: 유저→커널 **모드 스위치**는 TLB·캐시를 비워 **돌아온 뒤에도 느리다**(Soares·Stumm FlexSC 그림 3-7). **vDSO**(리눅스) — `gettimeofday()` 처럼 특권이 필요 없는 syscall 을 유저 공간 매핑으로. 자바는 시간을 자주 읽어 반가운 이득.
8. **단순 시스템 모델**: 하드웨어/OS · JVM · 앱 코드 · 외부 시스템 · 유입 트래픽. **기본 탐지 전략** — 첫 단계는 **어느 자원 한계에 부딪혔는지** 알기. OS 자체가 자원을 먹으면 안 된다.
   - **CPU**: `vmstat 1`(r/b · swpd/free/buff/cache · si/so · bi/bo · in/cs · us/sy/id/wa/st). CPU 바운드면 유저 100% 목표. 아니면 "왜?" — `cs` 가 높으면 락의 비자발적 스위치나 I/O 블로킹. 락 경합은 VisualVM 스레드 뷰·스레드 프로파일러로.
   - **GC**: HotSpot 힙은 유저 공간(`sbrk()` 없음) → **시스템 CPU 가 높으면 GC 가 아니다**, 유저 100% 면 GC 가 흔한 범인 → **GC 로그를 봐라**(비용은 잡음 이하, 운영에서 반드시 켜라 — 7장·8장).
   - **I/O**: 추상화가 없다("스피닝 러스트"). 대부분의 자바 앱은 I/O 를 포화시키지 않는다. **커널 우회 I/O** — NIC 버퍼를 유저 공간으로 직접 매핑(이중 복사·경계 넘기 회피), 자바는 지원이 없어 네이티브 라이브러리에 의존(그림 3-9); NIO 가 비슷한 정신.
9. **기계적 공감 — 거짓 공유**: 같은 캐시 라인의 두 변수를 두 스레드가 갱신 → 핑퐁 무효화. 자바는 필드 배치를 보장하지 않아 **패딩**으로 다른 라인에(14장 Agrona 큐의 `p1..p15`).
10. **가상화**: 호스트 OS 위 프로세스로 게스트 OS(그림 3-10). "진짜" 가상화의 세 조건(베어메탈과 같은 동작 · 하이퍼바이저가 모든 하드웨어 접근을 중재 · 오버헤드 미미). 게스트의 특권 명령은 비특권 명령으로 다시 쓰고 커널 자료구조를 **섀도잉**한다. 하드웨어 보조가 있어도 **분석·튜닝의 복잡도가 한 층 는다.**
11. **JVM 과 OS**: `native` 메서드, JNI, `java.lang.Object` 의 네이티브 메서드들(`hashCode`·`clone`·`notify`·`wait`). `System.c` 의 `registerNatives` 로 매핑되는 호출 스택(그림 3-11).

## 4. JDK 17 / 25 기준 평가

**JVM 버전에 결부된 문장이 없다.** 덧붙일 것:

- 거짓 공유 패딩의 표준 도구 `@Contended` 는 `jdk.internal.vm.annotation` 에 있어 앱이 쓰려면 `--add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED` 가 필요하다 — 17 에서 확인 ✅(`00-검토` §4). 25 도 같다 📄.
- "시스템 CPU 가 높으면 GC 가 아니다"는 그대로다. 단 **ZGC·Shenandoah 는 동시 스레드가 유저 CPU 를 계속 쓰므로** "유저 100% = GC" 판별에 GC 로그가 더 중요해졌다 📄. 로그를 만드는 명령은 `-Xlog:gc*`(PERF-08A ✅).
- 가상화 절의 "복잡도가 한 층 는다"는 컨테이너에서 **JVM 이 cgroup 한계를 읽어 스스로를 구성**하는 것으로 구체화됐다 — CPU 1개 → SerialGC ✅ CN-04A, 메모리 한계의 25% → 힙 ✅ CN-04B.
- 커널 우회 I/O 는 자바 표준에 여전히 없다. 네이티브 라이브러리 호출의 표준 경로가 JNI → **FFM API**(JDK 22 정식) 로 바뀌었다 ✅ CN-15B(25 에서 `strlen` 호출, `--enable-native-access` 없으면 경고).
