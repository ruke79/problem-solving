## 1. 이 장의 핵심 주장

1. 벤치마크는 **과학 실험**이다 — 공정한 테스트(변수 하나만), 최소한 **반복 가능**. Feynman: *"자신을 속이지 마라."*
2. 자바 코드는 JIT·GC·OS·하드웨어에서 분리되지 않는다. 큰 집합에서는 평균화되고 작은 조각에서는 안 된다 — **그래서 마이크로벤치마크가 어렵다.**
3. 순진한 벤치마크 `ClassicSort` 의 함정: 워밍업 없음(`PrintCompilation` 에 `made not entrant`), GC 미통제(`-verbose:gc`), **죽은 코드**, 오차 범위 없음, 멀티스레드 시작 동기화.
4. 세 사용처(범용 라이브러리·플랫폼 개발자·극한 저지연)와 네 기준(< 1ms/100µs, 할당 < 1MB/s, CPU ~100%·시스템 < 10%, 프로파일러로 지배 메서드 2~3개 확인) 밖이면 **하지 마라.**
   Goetz: *"마이크로벤치마크의 무서운 점은 항상 숫자를 내놓는다는 것이다. 무엇을 쟀는지 모를 뿐."*
5. 해야 하면 **JMH** — 애너테이션 프로세싱으로 코드 생성, 루프 최적화를 피하는 반복 수, **Blackhole**(죽은 코드·상수 접기·거짓 공유·쓰기 벽), `@State`, `@CompilerControl`.
6. JMH 로도 속는다 — `SortBenchmark` 의 클래식 vs 스트림 차이는 **GC** 였다(`GCProfiler`).
7. 통계: 무작위 오차(정밀도) vs 계통 오차(정확도, 뭄바이→런던 120~150ms), 허위 상관(닭과 원유, 오락실과 박사), **비정규 긴 꼬리 → 로그 퍼센타일 + HdrHistogram(2.1.9)**,
   해석의 **모자/코끼리 문제**(2xx/4xx/5xx 분해).

## 2. 절별 상세 요약

### 2-1. 자바 성능 측정 입문

- 벤치마크를 "블랙박스" 실험으로. Shipilëv: *"숫자 자체가 아니라 거기서 끌어내는 모델이 중요하다."* Donne: *"어떤 사람도 섬이 아니다."*
- **`ClassicSort`**(N=1,000 난수, I=150,000회 복사·정렬, ops/s 출력):
  - `java -Xms2048m -Xmx2048m -XX:+PrintCompilation ClassicSort` → `Integer::compareTo` 가 레벨 3 → 4, 이전 버전 `made not entrant`, `ComparableTimSort::*` 컴파일 — 측정 중에 JIT 가 돈다.
  - `-verbose:gc` → `[GC (Allocation Failure) 524800K->632K(2010112K), 0.0009038 secs]`(**Java 8 형식**, 로그 상세는 7장) — 측정 구간에 GC 가 낀다. `System.gc()` 는 무시될 수 있다.
  - `copy` 는 죽은 코드 → JIT 가 정렬을 없앨 수 있다. 오차 범위 없이 평균 하나로는 통제 실패도 못 본다. 멀티스레드는 시작 동기화·전원 관리·경합까지.
- 두 길: 시스템 전체만 벤치마크(대부분) / OpenJDK 를 따라가는 공통 프레임워크(JMH). **대부분의 개발자에게 JMH 절은 참고 자료이고 통계 절로 건너뛰어도 된다.**

### 2-2. JMH 입문

- **하지 마라 — 실화**: 며칠째 메서드 하나를 노려보던 동료. CPU 포화 → 실행 프로파일러 10분 → 원인은 새 인프라 라이브러리. *"개발자는 자기 코드가 범인이라는 생각에 사로잡힌다."*
- 사용처 셋: **범용 라이브러리**(Guava, Eclipse Collections — 원래 Goldman Sachs 기여) / **OpenJDK·플랫폼 개발자**(JMH 의 원래 사용자) / **극한 저지연**(금융 트레이딩).
- 네 기준(위). Shipilëv: *"**디스어셈블리/코드 생성 분석이 없는 나노벤치마크는 믿지 마라. 끝.**"*
- **JMH 프레임워크**: Google Caliper 등은 JVM 진화를 못 따라갔다. JVM 을 만드는 엔지니어들이 만들어 릴리스마다 함정을 안다. 리플렉션이 아니라 **애너테이션 프로세싱으로 소스 생성**(JUnit 과 다르다), 루프 최적화가 걸리지 않는 반복 수로 감싼다.
- 실행: Maven 아키타입 `jmh-java-benchmark-archetype`, `@Benchmark`, `OptionsBuilder().include(...).warmupIterations(100).measurementIterations(5).forks(1).jvmArgs("-server","-Xms2048m","-Xmx2048m")`,
  커맨드라인이 `main()` 을 덮는다. `@State(Scope.Benchmark|Group|Thread)`.
- **Blackhole**: 반환값은 암묵적, 여러 값은 파라미터 주입. 네 보호. 구현 — `volatile int i1=1, i2=2; if (i == i1 & i == i2) nullBait.i1 = i;`(절대 참이 아니지만 컴파일러는 남겨야 하고 `&` 로 분기 균일화),
  객체는 이스케이프 분석이 비교를 없앨 수 있어 `tlr` 선형 합동 난수 + `tlrMask` 로 **거의 안 일어나는** 대입. *"운영 코드에 있으면 해고감."* 문서화가 훌륭하다.
- 고급: `@CompilerControl`(인라인 금지/강제/컴파일 제외), Blackhole 로 CPU 부하 시뮬레이션.
- **`SortBenchmark`**: `@Warmup(5×1s) @Measurement(5×1s) @Fork(1) Mode.Throughput`, classicSort/standardSort(`stream().sorted()`)/parallelSort.
  결과 14,373 / 12,656 / 7,918 ops/s(±1%). "클래식이 빠르다"고 결론 내기 쉽지만 `GCProfiler` 를 붙이면 classicSort 반복당 GC ~1회, parallelSort 4~5회 — **원인은 GC**.
  "통제된 실험" 가정은 미끄럽다. JITWatch(9장)로 바이트코드 수준을 볼 수 있다.

### 2-3. JVM 성능을 위한 통계

- Bloomberg: *"신은 믿되, 나머지는 데이터를 가져와라."*
- **오차의 종류**: 무작위(정밀도) / 계통(정확도). 과녁 그림 넷.
- **계통 오차 예**: JMeter(JP GC 확장) — 한 서비스의 선형 증가 = 자원 고갈 후보(누수라고 단정 말 것), 나머지 180ms 근처 = **뭄바이→런던 왕복**. 런던에서 다시 재니 사라졌다.
- **무작위 오차**: 가우시안 — 하지만 JVM 에는 안 맞는다(아래).
- **허위 상관**: 닭 소비 vs 원유 수입(Vigen), 오락실 매출 vs CS 박사. 위험한 것은 그럴듯한 쪽. Feynman 의 격언의 한 측면.
- **비정규 통계**: 이상치 = 느린 트랜잭션 = 불만 고객. "핫 패스" 라는 최선의 경우가 있어 "무작위로 조금 빠른" 호출이 없다 → 표준편차·분산·고차 모멘트는 **기본적으로 쓸모없다.**
  평균 개선은 대개 목표가 아니다. **로그 퍼센타일**: 평균 23ns 인 게터가 1/1,000 은 164ns, 1/100,000 은 3,458ns. HDR(high dynamic range) 분포.
  **HdrHistogram**(Gil Tene, Azul; Mike Barker·Darach Ennis·Coda Hale; 책 시점 **2.1.9**): GC 간격 히스토그램 예제, `outputPercentileDistribution`, 온라인 포매터.
- **해석**: Weinberg *"항상 사람 문제다."* **Censum 스크린샷**(할당률 350~700MB/s, 5시간 뒤 하락, 9~10시간 최저)— ⚠️ Censum 은 단종됐다(§0 검토).
  **모자/코끼리**: HTTP 응답 히스토그램 = 2xx(긴 꼬리, 다봉) + 4xx(즉시) + 5xx(오래 걸린 뒤 실패). 하위 모집단으로 분해하라. PayPal "Statistics for Software".

## 6. 면접에서 쓸 수 있는 문장

- "메서드 하나의 벤치마크 결과를 믿으려면 최소한 워밍업·죽은 코드 제거·GC 를 통제해야 하고, 그건 JMH 가 해 줍니다. 그래도 `-prof gc` 로 GC 가 결과를 만든 게 아닌지 봅니다."
- "JVM 응답 시간은 정규분포가 아닙니다. 표준편차는 의미가 없고, p99·p99.9 를 로그 스케일로 봅니다."
- "응답 시간 히스토그램이 이상하게 생겼으면 2xx·4xx·5xx 로 쪼개 봅니다. 404 는 즉시 오고 500 은 타임아웃 뒤에 옵니다."
