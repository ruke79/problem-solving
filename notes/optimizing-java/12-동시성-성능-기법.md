# 12장 — 동시성 성능 기법 (Concurrent Performance Techniques)

> *Optimizing Java* 1판(2018) 12장 요약. [`00-검토`](00-검토-2018년-책과-현재.md) §7 의 **착수 순서 3순위** — "**가상 스레드만 보충하면 된다**"(§4 에 보충).
> 표기 — ✅ 실행해 확인(JDK 17.0.19 / 21.0.10 / 25.0.4) · 📄 문서로만 아는 것.
>
> **2판(2024)에서는** [13장](../optimizing-java-2nd/13-동시성-성능-기법.md) 으로 개정됐다. 골격(암달·잃어버린 갱신·JMM·CAS·j.u.c·Fork/Join·병렬 스트림·액터)은 같고,
> 1판에만 있는 것은 **`Unsafe` 절과 `Unsafe` 로 쓴 `AtomicInteger`**, **LMAX Disruptor 표**, **Akka**(2판은 Pekko)다.

## 1. 이 장의 핵심 주장

1. 공짜 점심의 끝(Sutter 2005). **암달의 법칙** `T(N) = S + (T−S)/N` — 직렬 5% 면 최대 20배. 당황스러울 만큼 병렬한 일만 무한 확장.
2. `increment()` 의 바이트코드(`getfield`/`iadd`/`putfield`)와 두 스레드 인터리빙 → **잃어버린 갱신**(7 → 둘 다 8). `volatile` 은 해결이 아니다. 동기화를 아무 데나 넣으면 느려진다 — **성능 테스트가 병렬화를 뒷받침해야 한다.**
3. **JMM**(JSR 133): 약한 모델, 최소 요구, happens-before 등 네 개념, `synchronized` 의 한계 셋, **읽기도 잠가라**, JSR-133 Cookbook, Java 9 의 C++11 방향 확장.
4. 라이브러리는 유저 공간에서. **CAS** 는 하드웨어에 있지만 JMM 밖 → **`sun.misc.Unsafe`** 로 접근. Unsafe 가 가능하게 하는 것(생성자 없이 할당, 원시 메모리, CAS)과 프레임워크 기능(빠른 직렬화, 오프힙, 커스텀 펜스, JNI 대체…). "사실상 표준이자 쓰레기장", Java 9 에서 `jdk.unsupported` 모듈로.
   `AtomicIntegerExample` — `unsafe.objectFieldOffset(...)`, `getAndSetInt` 의 `do { v = getIntVolatile } while (!compareAndSwapInt)` 재시도 루프(경합에 선형 저하).
5. **스핀락**(x86 `xchg`) — OS 를 부르는 intrinsic 락보다 짧은 임계 구역에 유리, CPU 를 태운다.
6. `Lock`/`ReentrantLock`(비경합 CAS, AQS, `LockSupport.park*`)/`ReentrantReadWriteLock`(`AgeCache`)/`Semaphore`/`ConcurrentHashMap`/`CopyOnWrite*`/`CountDownLatch`·`CyclicBarrier`/`Executors` 팩토리 넷/`ThreadFactory`/코어 수 vs 스레드 수.
7. **Fork/Join**(Java 7): 분할 + 작업 훔치기, `commonPool()` = `availableProcessors()−1`, 16-4-2 머신이 16 을 돌려준 Kabutz 사례, `-Djava.util.concurrent.ForkJoinPool.common.parallelism`. Akka 도 훔치기 때문에 FJP 를 쓴다.
8. **스트림/병렬 스트림**(Java 8): 내부 반복, `Spliterator` + commonPool. **작은 컬렉션에서는 직렬이 훨씬 빠르다** — "재라, 추측하지 마라".
9. **락프리 — LMAX Disruptor**: `ArrayBlockingQueue` 대비 수배(표 12-1: Unicast 1P-1C 5.3M → 26.0M ops/s 등). `volatile` 변수로 스핀. **기계적 공감**(Martin Thompson, 재키 스튜어트).
10. **액터 — Akka**: 불변 메시지·공유 상태 없음·시간 제한 처리기에 맞으면 빠른 승리; 요청-응답·공유 상태·무제한 실행이면 다른 추상화.

## 2. 절별 상세 요약

(2판 13장 요약의 §2-1 ~ §2-6 과 내용이 겹치므로 여기서는 **1판에만 있는 절**을 상세히 적는다.)

### 2-1. Unsafe
- "이름이 힌트다." HotSpot 에 직접 결합돼 깨지기 쉽다. 그러나 사실상 모든 주요 프레임워크의 구현에 들어 있다. Java 9 에서 `jdk.unsupported` 모듈에 두었고 "앞으로 몇 버전에 걸쳐 크게 진화할 것"이라고 예고.
- `AtomicIntegerExample extends Number` 전체 코드: `private volatile int value`, `Unsafe.getUnsafe()`, `objectFieldOffset(getDeclaredField("value"))`, `getAndSet` → `unsafe.getAndSetInt(this, valueOffset, newValue)`, 네이티브 `getIntVolatile`/`compareAndSwapInt`.
- "직접 재시도 루프로 원자 증가를 만들지 마라 — Unsafe 구현이 이미 그렇게 한다."

### 2-2. LMAX Disruptor
| 시나리오 | ArrayBlockingQueue | Disruptor |
|---|---|---|
| Unicast 1P–1C | 5,339,256 | 25,998,336 |
| Pipeline 1P–3C | 2,128,918 | 16,806,157 |
| Sequencer 3P–1C | 5,539,531 | 13,403,268 |
| Multicast 1P–3C | 1,077,384 | 9,377,871 |
(ops/s, GitHub 프로젝트 페이지 수치 📄.) `private volatile int proceedValue; while (i != proceedValue) { /* busy loop */ }` — 코어가 스핀하므로 데이터가 오면 컨텍스트 스위치 없이 즉시 처리. 대가는 사용률·전력·발열. 이런 처리량은 저수준 이해와 **기계적 공감**을 요구한다.

### 2-3. Akka
Scala 로 쓰였고 Java API 있음. 세 동기(도메인 모델의 가변 상태 캡슐화가 어렵다 / 락은 처리량을 크게 깎는다 / 데드락·라이브니스). 스레드 실패·복구의 표준 방식 제공. 다중 프로세스·다중 머신·페일패스트.

### 2-4. 나머지 절
2판 13장 요약의 해당 절과 같다: 병렬성 입문 · 자바 동시성 기초 · JMM · 원자와 CAS · 락과 스핀락 · j.u.c 락 · 읽기/쓰기 락 · 세마포어 · 동시 컬렉션 · 래치와 배리어 · Executor 와 태스크 추상화 · Fork/Join · 스트림.

## 3. §7 의 보충 — 가상 스레드 (책에 없는 것)

1판은 15장에서 "Project Loom 이라는 것이 있다"(2회) 정도로만 언급한다. 지금 이 장을 읽는 사람은 다음을 함께 알아야 한다.

- **Java 21 정식(JEP 444)**. 스레드 병목(스택 1MB × 20,000 = 20GB)의 답. JVM 이 만들고 캐리어 풀(ForkJoinPool)을 공유하며 스택 프레임은 힙 객체. "블로킹" I/O 는 논블로킹으로 바뀌어 캐리어를 양보한다(소켓 NIO 재구현 JDK 13). **자동 가상화는 없다.**
- 이 장의 명제에 미치는 영향:
  - 「Executor 선택 — 코어 수 vs 스레드 수」: **I/O 가 섞인 태스크라면** 풀 크기 고민 대신 `Executors.newVirtualThreadPerTaskExecutor()` 로 태스크당 스레드. 계산 집약 태스크에는 여전히 플랫폼 풀(양보할 블로킹이 없다).
  - 「스핀락·락프리」: vthread 안에서 스핀하면 캐리어를 점유한다 — vthread 와 스핀은 상극.
  - 「Fork/Join」: 캐리어 풀 자체가 ForkJoinPool 이다. commonPool 과는 별개의 스케줄러(`jdk.virtualThreadScheduler.parallelism`).
  - `synchronized` 와의 관계는 버전에 따라 다르다: **21 에서는 `synchronized` 안에서 블로킹하면 캐리어에 피닝**, **24 부터는 아니다(JEP 491)** — ✅ 캐리어 1개 실험에서 21 은 607ms 지연, 25 는 10ms(→ `verify-labs-cloudnative` **CN-13A**).
  - ThreadLocal 대신 **ScopedValue**(25 정식, JEP 506) ✅ **CN-13C**.
- 상세는 [2판 13장 요약 §2-7·§4](../optimizing-java-2nd/13-동시성-성능-기법.md).

## 5. JDK 17 / 25 기준 — 어긋나는 것

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| `Unsafe` 는 "앞으로 크게 진화" | **JDK 23 JEP 471 로 메모리 접근 메서드(CAS 포함) 제거 예정 폐기, 24 JEP 498 로 호출 시 기본 경고**, 25 에서 `allocateMemory` 호출 → `WARNING: A terminally deprecated method in sun.misc.Unsafe has been called`; `--sun-misc-unsafe-memory-access=deny` 면 `UnsupportedOperationException` | ✅ 25, **CN-15A** |
| `Unsafe.getUnsafe()` 를 앱에서 | 17·21·25 모두 리플렉션(`theUnsafe`)으로는 아직 얻을 수 있다 | ✅ |
| `AtomicInteger` 는 Unsafe 위에 | **그대로다** — 17·21·25 의 `AtomicInteger` 필드는 `jdk.internal.misc.Unsafe U` 와 `long VALUE`(오프셋). VarHandle 로 바뀌지 않았다 | ✅ 리플렉션, **PERF-15A** |
| commonPool = 코어 − 1 | 그대로(4 → 3) | ✅ 17·21·25 |
| Akka | 2022 년 라이선스 변경 → Apache **Pekko** 포크 | 📄 (2판 각주) |
| Disruptor 수치 | 프로젝트 페이지의 옛 수치 — 시험하지 않았다 | 📄 |
| 스레드 = OS 스레드 | 21 부터 **가상 스레드**가 예외 | ✅ §3 |
| JMM 의 Java 9 확장 | 그대로(VarHandle 의 접근 모드가 그 결과) | 📄 |

## 7. 면접에서 쓸 수 있는 문장

- "`sun.misc.Unsafe` 는 JDK 23 부터 메모리 접근 메서드가 제거 예정으로 폐기됐고 24 부터는 호출하면 경고가 납니다. 대체는 `VarHandle` 과 FFM API 입니다."
- "`AtomicInteger` 는 CAS 재시도 루프입니다. 경합이 심하면 재시도가 늘어 선형으로 나빠지니 `LongAdder` 처럼 셀을 나누는 구조를 씁니다."
- "스레드 풀 크기를 코어 수에 맞추는 조언은 CPU 바운드 이야기입니다. I/O 가 섞인 요청 처리라면 JDK 21 의 가상 스레드로 태스크당 스레드를 쓰는 편이 단순합니다."
