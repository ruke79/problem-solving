# *Optimizing Java* (2018) — 지금 요약해도 되는가

> Benjamin J. Evans · James Gough · Chris Newland, ***Optimizing Java***
> (O'Reilly, 2018) 를 **요약과 성능 테스트의 새 바탕으로 삼기 전에**,
> 2018년 서술 중 지금과 어긋나는 것을 먼저 훑은 문서다.
>
> **결론부터 — 쓸 만하다. `notes/java-performance/`(2014년 책)보다 확실히 낫다.**
> 다만 **8장·13장은 실행 불가능한 내용이 상당하고**, **15장의 미래 예측은 18건 중 4건이
> 빗나갔다**(§5 성적표). 아래가 그 목록이다.

## 0. 받은 자료의 상태

| | |
|---|---|
| 받은 것 | **1~15장 전권**(약 48만 자). 처음에 2~14장을 받고, **1장·15장을 뒤이어 받아 전권이 됐다** |
| 중복 | `Foreword.pdf` 는 **2장과 내용이 같다** |
| 기준 JDK | **Java 8 중심 + Java 9 상세 + Java 10 예고.** 15장이 "미래"를 통째로 다룬다 |

### ⚠️ 이 문서의 이전 판에 오류가 6건 있었다 — 15장을 못 본 채로 썼기 때문이다

처음 검토할 때 15장이 없었고, 나는 **"전 장 검색 결과"라고 말하며 없다고 단정했다.**
15장을 받고 나니 **여섯 가지가 전부 틀렸다.**

| 이전 판에 쓴 것 | 실제 |
|---|---|
| "**ZGC 0회 언급**" | **틀렸다.** 15장 결론이 *"new garbage collectors such as Oracle's ZGC"* 로 언급한다 |
| "**VarHandle 0회**" | **틀렸다.** 15장에 「VarHandles in Java 9」 절이 통째로 있다 |
| "**가상 스레드 0회, Loom 1회**" | **틀렸다.** 15장 「Future Directions in Concurrency」가 Project Loom 을 정면으로 다룬다 |
| "**Valhalla 0, Panama 0**" | **틀렸다.** Valhalla·값 타입에 긴 절이 있고 Panama 도 결론에서 언급된다 |
| "**Graal 0, jaotc 0**" | **틀렸다.** Graal·Truffle·Metropolis 절이 있고 `jaotc` 명령 예시까지 나온다 |
| "**Compact Strings 를 책이 모른다**"는 뉘앙스 | **틀렸다.** 15장이 `byte[] value` / `coder` 필드까지 소스로 보여 준다 |

**교훈은 자료 탓이 아니라 내 서술 탓이다.** 없는 장을 두고 "0회"라고 쓰면
**"검색해 보니 없더라"가 아니라 "책에 없다"로 읽힌다.** 부분 자료로 전체를 단정한 것이
잘못이고, `docs/00` §8 이 금지하는 바로 그것이다. 아래 §2 의 해당 항목은 전부 고쳤다.

> **다만 결론은 바뀌지 않았다.** 15장은 이것들을 **"미래 전망"으로** 다루지
> **실무 지침으로 다루지 않는다.** ZGC 는 이름 한 번, 가상 스레드는 "Loom 이라는
> 프로젝트가 있다" 수준이다. **요약할 때 보충이 필요하다는 판단은 그대로다.**

## 2. 지금과 어긋나는 것 — 장별

### ⚠️ 8장 (GC Logging) — **가장 크게 어긋난다**

책이 **"Mandatory GC flags"(필수 GC 플래그)** 라고 표로 못 박은 5개를
JDK 17 에 그대로 주면 이렇게 된다. ✅ 실행해 확인했다.

```
-Xloggc:gc.log                 → 경고 후 -Xlog:gc 로 대체됨
-XX:+PrintGCDetails            → 경고 후 -Xlog:gc* 로 대체됨
-XX:+PrintTenuringDistribution → Unrecognized VM option   ← 기동 실패
-XX:+PrintGCTimeStamps         → Unrecognized VM option   ← 기동 실패
-XX:+PrintGCDateStamps         → Unrecognized VM option   ← 기동 실패
```

**5개 중 3개는 애플리케이션이 뜨지 않는다.** 2018년 책인데도 이런 이유는
**Java 8 기준으로 썼기 때문**이다(통합 로깅은 Java 9, JEP 158).
지금은 이렇게 쓴다.

```bash
-Xlog:gc*,gc+age=trace:file=gc.log:time,uptime,level,tags:filecount=5,filesize=10M
```

> 8장은 **GC 로그를 어떻게 읽는가**가 본질이고 그 부분은 유효하다.
> 문제는 **로그를 만드는 명령이 통째로 바뀌었다는 것**이다. 요약할 때
> 플래그 표는 그대로 옮기면 안 되고 통합 로깅으로 다시 써야 한다.

### ⚠️ 8장·13장 — **Censum / jClarity 의존 (28회 언급)**

책은 GC 로그 분석과 세이프포인트 진단을 **jClarity 의 Censum** 에 크게 기댄다
("상용 도구", API 로 GC 로그 스트리밍 가능 등).

**jClarity 는 2019년 Microsoft 에 인수됐고 Censum 은 단종됐다.**
지금 같은 일을 하려면 GCeasy, GCViewer, JFR 쪽으로 대체해야 한다.

> 이건 **책의 잘못이 아니라 시간의 문제**지만, 요약에 그대로 옮기면
> **구할 수 없는 도구를 권하는 문서**가 된다.

### ⚠️ 13장 (Profiling) — hprof

> *"The hprof profiler has shipped with the JDK since version 5."*

✅ **JDK 17 에는 없다**(JEP 240, Java 9 에서 제거).

```
$ java -agentlib:hprof=cpu=samples -version
Error occurred during initialization of VM
Could not find agent library hprof on the library path
```

13장의 다른 도구(JFR·JMC·YourKit·VisualVM·JITWatch)는 지금도 유효하다.
다만 **async-profiler 는 전권에 한 번도 안 나온다**(1~15장 전체 검색). 지금 리눅스 실무의
사실상 표준이라 요약한다면 **책에 없는 것을 보충해야 하는 자리**다.

### 6·7장 (GC) — CMS 106회

- **CMS 는 JDK 14 에서 삭제됐다.** ✅ `-XX:+UseConcMarkSweepGC` 는 `Unrecognized VM option`.
  책은 CMS 를 **현역으로** 다룬다(106회 언급, `CMSInitiatingOccupancyFraction` 튜닝 등).
- **ZGC 는 15장 결론에 이름 한 번뿐**(*"new garbage collectors such as Oracle's ZGC"*).
  6·7장에는 절도 설명도 없다. **지금 대용량 힙의 첫 후보인데 사실상 다뤄지지 않는다** —
  ZGC 는 JDK 11 실험 → **JDK 15 정식**이 됐다.
- **Shenandoah 를 "실험적, 프로덕션에 쓸 준비 안 됨"** 이라고 쓴다.
  ✅ JDK 17 에서는 `-XX:+UnlockExperimentalVMOptions` 없이 그냥 기동된다 —
  **JDK 15 에서 정식 기능이 됐다**(JEP 379).
- **`ParallelOldGC`**(10회 언급) ✅ `Unrecognized VM option`(JDK 15 제거).

> 6장의 GC 이론(약한 세대 가설·마킹·대피·STW)과 7장의 **동시 수집기가 왜 어려운가**는
> 그대로 유효하다. `notes/java-performance/00-JDK-17-차이.md` 에 적은 것과 같은 요령으로,
> **"CMS" 를 "동시 수집기 일반"으로 바꿔 읽으면** 대부분 살아 있다.

### 11장 (Language Techniques) — Compact Strings

책은 **문자열이 `char[]` 로 저장된다**는 전제로 메모리를 계산한다
(8장에도 *"char[]: The characters that comprise strings"* 가 있다).

✅ **JDK 9 부터 `String.value` 는 `byte[]`** 다(Compact Strings).
ASCII 10자가 **10바이트**(책 전제로는 20바이트). **11장의 문자열 메모리 계산은 다시 해야 한다.**

### 9·10장 (Code Execution / JIT)

**가장 잘 버틴 장이다.** 인라이닝·이스케이프 분석·역최적화·세이프포인트(66회)·
계층형 컴파일 서술은 그대로 유효하고, JITWatch(32회)도 살아 있다.

다만 **AOT 를 "JIT 과 대비되는 접근"으로 개념 설명**하고, 15장은 한 걸음 더 나가
**`jaotc` 사용법과 Graal JIT 활성화 플래그까지 싣는다.** 둘 다 ✅ **JDK 17 에서 제거**됐다
(JEP 410). 자세한 결과는 §5 의 성적표 참고.

### 12·14장 (Concurrency / Logging·Messaging)

- **12장 본문은 `sun.misc.Unsafe` 로 저수준 접근을 설명하고, 15장이 `VarHandle` 을
  대체재로 소개한다.** ✅ JDK 17·21 모두 `Unsafe` 접근은 아직 되지만, 메모리 접근
  메서드는 폐기·제거 수순이다. **재미있는 것은 15장이 *"AtomicInteger 는 순환 의존 때문에
  아직 Unsafe 를 쓴다"* 고 적었는데, ✅ JDK 17·21 에서도 여전히 그렇다는 점이다**(§5 참고).
- **12장에 가상 스레드는 없다.** 15장이 Project Loom 을 "경량 실행 단위 + `ForkJoinPool`
  스케줄러"로 예고했고 **그 예측은 정확히 맞았지만**(JDK 21), 12장의 스레드 풀 사이징
  서술 자체는 그 전제 위에서 다시 봐야 한다.
- **14장은 Log4j 2(23회)·Aeron(41회)·Agrona(25회)** 중심이다. Aeron·Agrona 는 지금도 현역.
  Log4j 는 **2021년 Log4Shell(CVE-2021-44228) 이후 권고가 달라졌으므로**
  버전·설정을 그대로 옮기면 안 된다.

### 2·3·4·5장 — 거의 그대로

- **1장**: 최적화와 성능의 정의. **버전 언급이 0회인 완전 불변 장이다.**
  아이러니하게도 이 장의 도입부가 *"1997년 글이 구글 상위에 남아 낡은 조언을 계속
  퍼뜨렸다"* 는 이야기다 — **2018년 책을 2026년에 쓰는 우리에게 그대로 걸리는 경고다.**
- **2장**: JVM 구조·바이트코드·인터프리터. 유효. 단 **배포판 이야기가 낡았다** —
  2019년 Oracle JDK 라이선스 변경과 그 뒤 Temurin·Corretto·Zulu 구도가 책에 없다.
- **3장**: 하드웨어·OS·캐시. **거의 영향 없음.**
- **4장**: 성능 테스트 패턴과 안티패턴. **거의 영향 없음** — 이 저장소 원칙과 가장 잘 맞는 장.
- **5장**: JMH 와 통계. **거의 영향 없음.** JMH 는 지금도 표준이다.

## 5. 15장의 예측 성적표 — 책이 본 미래 vs 실제

**이 절이 이번 검토에서 가장 값어치 있는 부분이다.** 15장은 2018년 시점에서 미래를
전망했고, 우리는 그 미래에 살고 있다. `✅` 는 JDK 17/21 에서 실행해 확인한 것이다.

### 맞은 것 (10)

| 15장의 예측 | 실제 |
|---|---|
| **6개월 릴리스 주기**(Java 10~), 기능 릴리스 + LTS | **그대로 됐다.** 지금 JDK 25 까지 왔다 |
| **Compact Strings** — `value` 가 `byte[]`, `coder` 필드 | ✅ 확인. `CompactStrings = true`, `String.value` 는 `byte[]` |
| **분할 코드 캐시** | ✅ `SegmentedCodeCache = true {ergonomic}` |
| **`invokedynamic` 문자열 연결**(`makeConcatWithConstants`) | ✅ 바이트코드에서 확인. `StringBuilder` 가 사라졌다 |
| **G1 이 Java 9 기본 수집기** | ✅ `[info][gc] Using G1` |
| **JEP 307** G1 병렬 풀 GC | Java 10 에 들어갔다 |
| **JEP 310** AppCDS | Java 10. 이후 기본 아카이브·동적 아카이브로 확장됐다 |
| **JEP 312** Thread-Local Handshakes | Java 10. **단 §아래 "빗나간 방식" 참고** |
| **constant dynamic** ("invokedynamic 의 상수 풀판") | **Java 11 에 `CONSTANT_Dynamic` 으로 들어갔다**(JEP 309) |
| **Project Loom** — 경량 실행 단위 + `ForkJoinPool` 스케줄러 | **JDK 21 가상 스레드로 정확히 그렇게 나왔다.** 기본 스케줄러도 `ForkJoinPool` 이다 |
| **SubstrateVM** → JVM 없이 도는 네이티브 바이너리 | **GraalVM Native Image 로 주류가 됐다**(Spring Boot 3 AOT·Quarkus). 단 *"수 KB"* 는 과했다 — 실제로는 수십 MB |
| **Project Panama**(결론에서 언급) | **FFM API 로 JDK 22 정식**이 됐다 |

### 빗나간 것 (4) — **여기가 중요하다**

| 15장의 예측 | 실제 |
|---|---|
| **"C2 는 수명이 끝났고 Graal 이 대체한다"**<br>(Metropolis·JVMCI·`-XX:+UseJVMCICompiler`) | ❌ **정반대가 됐다.** Graal JIT 은 **JDK 17 에서 제거**됐고(JEP 410) **C2 가 여전히 현역**이다. ✅ 확인: `jdk.internal.vm.compiler` 모듈은 **이름만 남고 속이 비어 있다**(`module-info.class` 뿐, `org/graalvm` 클래스 **0개**). 플래그를 줘도 에러는 안 나지만 **뒤에 컴파일러가 없다.** Graal 은 **JDK 밖의 GraalVM 제품으로** 살아남았다 |
| **`jaotc` AOT** — *"지원이 다음 릴리스들에서 확대될 것"* | ❌ **확대가 아니라 제거됐다**(JDK 17, JEP 410). ✅ `jaotc` 바이너리 없음. 지금 AOT 는 GraalVM native-image 와 **JDK 24 의 AOT 캐시(Leyden)** 쪽이다 |
| **값 타입(Valhalla)** — *"저자들의 최선의 추측은 2019년 릴리스 중 하나"* | ❌ **7년이 지난 지금도 정식 출시되지 않았다.** Valhalla 는 여전히 진행 중이다. **책이 가장 크게 빗나간 예측** |
| **`--illegal-access` 로 내부 API 접근을 제어** | ❌ **JDK 17 에서 제거됐다.** ✅ 확인: `Ignoring option --illegal-access=permit; support was removed in 17.0`. 강한 캡슐화가 기본이 됐다 |

### 맞았지만 방식이 달라진 것 (2)

| | |
|---|---|
| **JEP 312 의 효용으로 든 "편향 락 개선"** | 핸드셰이크 자체는 들어왔지만, **편향 락이 통째로 사라져**(JDK 15 비활성·폐기) 그 용도는 무의미해졌다. **문제를 개선한 게 아니라 문제를 없앴다** |
| **"LTS 만 Oracle 상용 JDK, 나머지는 GPL"** | 초기엔 맞았으나 **Oracle 이 JDK 17 부터 NFTC 로 다시 무료화**했다. 그리고 책에 없던 **Temurin·Corretto·Zulu 구도**가 실무 표준이 됐다 |

### 7년 뒤에도 그대로인 것 — 한 가지

15장은 *"AtomicInteger 는 순환 의존 때문에 아직 `VarHandle` 로 옮겨지지 않았고
`Unsafe` 를 쓴다"* 고 적었다. ✅ **JDK 17 과 21 을 `javap` 로 열어 보니 여전히 `Unsafe` 다.**
**책이 "곧 바뀔 것"처럼 쓴 것이 7년째 그대로인 사례**이고, 요약할 때 그대로 옮겨도 되는 문장이다.

```
$ javap -p -c java.util.concurrent.atomic.AtomicInteger | grep -oE 'Unsafe|VarHandle' | sort -u
JDK 17 → Unsafe
JDK 21 → Unsafe
```

### 이 성적표가 요약에 주는 함의

**15장은 "요약"보다 "대조"로 쓰는 게 맞다.** 예측을 그대로 옮기면 절반은 틀린 문서가 되고,
**"이렇게 예측했고 이렇게 됐다"로 쓰면 오히려 지금 가장 읽을 가치가 있는 장이 된다.**
특히 **C2/Graal 예측이 빗나간 것**은 "권위 있는 저자도 플랫폼의 방향을 틀리게 본다"는
사례라서, 이 저장소의 §8 정직성 원칙과도 잘 맞는다.

## 6. 확인하지 않은 것 — 정직한 고지

1. **성능 수치는 하나도 재보지 않았다.** 책의 벤치마크 결과가 지금도 재현되는지는
   **모른다.** 요약을 만들 때 수치를 옮긴다면 "책의 값이고 우리가 잰 것이 아니다"를
   반드시 붙여야 한다(`docs/02` §1-2).
2. **처음에는 1장·15장 없이 검토했고, 그 상태로 "책에 없다"를 단정해 6건을 틀렸다**(§0).
   지금은 전권을 봤지만, **부분 자료로 전체를 단정하지 않는다**는 교훈이 이 문서의 이력에 남았다.
3. **PDF 추출 텍스트가 원본이다.** 표와 그림 캡션이 흩어졌고, 특히 8장의 플래그 표는
   추출 과정에서 칸이 붙어 버렸다(`-XX:+PrintGCDetailsLogs GC event details` 처럼).
   **플래그 이름은 실행으로 다시 확인했지만, 표의 나머지 설명은 원문 대조가 필요하다.**
   15장의 바이트코드 예시와 그림(Figure 15-1~4)도 마찬가지로 캡션만 남았다.
4. **JDK 18~25 의 변화는 범위 밖이다.** 이 저장소 기준이 JDK 17 이라 거기까지만 봤다.
   가상 스레드·`Unsafe` 폐기·Leyden 은 **"책에 없다"고만 적고 검증하지 않았다.**
5. **Log4Shell 이후의 Log4j 권고 변화는 확인하지 않았다.** 14장을 요약한다면
   **그 장만은 별도 조사가 필요하다.**
6. **§5 성적표의 "실제" 칸 중 실행으로 확인한 것은 ✅ 표시한 것뿐이다.**
   릴리스 주기·JEP 채택 시점·GraalVM 의 현재 위치 같은 것은 **문서 기반 서술이고 검증하지 않았다.**
   특히 **Valhalla 의 현재 진행 상태는 이 환경에서 확인할 방법이 없어** "정식 출시되지 않았다"만 적었다.

## 7. 그래서 어떻게 할 것인가 — 제안

요약과 성능 테스트를 추가하신다면 이 순서를 권한다.

| 우선순위 | 장 | 이유 |
|---|---|---|
| **1** | **4·5장** | 방법론·JMH·통계. **영향 0**이고 이 저장소 `docs/02` §1-2 를 강화한다. 요약이 그대로 쓸모 있다 |
| **2** | **9·10장** | JIT. 가장 잘 버텼고, 기존 `PERF-04`(JIT 워밍업)와 바로 이어진다 |
| **3** | **11·12장** | 언어·동시성. **Compact Strings 와 가상 스레드만 보충**하면 된다. `PERF-09A/09B` 와 짝 |
| **4** | **6·7장** | GC 이론. **CMS 절은 "동시 수집기 일반"으로 다시 쓰고 ZGC 를 보충**해야 한다 |
| **5** | **3·2장** | 하드웨어·JVM 개요. 배경 지식 |
| **마지막** | **8·13장** | **가장 손이 많이 간다.** 플래그 표를 통합 로깅으로 다시 쓰고, Censum·hprof 를 현재 도구로 갈아야 한다 |
| **별도** | **1·15장** | **1장은 그대로 옮겨도 된다**(불변). **15장은 요약이 아니라 §5 같은 "예측 vs 실제" 대조표로** 만드는 것이 훨씬 값어치 있다 |

**성능 테스트로 만들기 좋은 후보**(기존 `verify-labs-perfbook` 에 붙일 수 있는 것):

- **5장 — JMH 도입.** 지금 `docs/02` §9-4 에 *"JMH 가 필요해 못 한 것 3건"* 이 남아 있다.
  이 책이 JMH 를 정면으로 다루므로 **그 3건을 해소할 근거가 생긴다.** 다만 §4 「벤치마크가
  아니다」의 전제가 바뀌므로 **별도 모듈로 분리해야 한다**(이미 `docs/00` 「이어서 할 일」 5번에 적힌 결론).
- **10장 — 역최적화(deoptimization) 관측.** 호출 횟수·컴파일 로그로 결정적 판정이 가능하다.
- **11장 — Compact Strings 실측.** 위 §4 의 방법 그대로 케이스가 된다.
- **8장 — 통합 로깅 파싱.** 책의 "GC 로그 읽는 법"을 **현재 형식으로** 재현하는 케이스.
- **15장 — 예측 검증 케이스.** §5 에서 실행으로 확인한 것들(`CompactStrings`·
  `SegmentedCodeCache`·`--illegal-access` 제거·Graal 모듈 공동화·`AtomicInteger` 의 `Unsafe`)은
  **그대로 `PERF-A01`(VanishedFlagsCase) 형태의 케이스가 된다.** 상시 실행하면
  **다음 JDK 에서 또 무엇이 바뀌는지 자동으로 잡힌다.**
