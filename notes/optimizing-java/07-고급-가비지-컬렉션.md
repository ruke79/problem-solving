# 7장 — 고급 가비지 컬렉션 (Advanced Garbage Collection)

> *Optimizing Java* 1판(2018) 7장 요약. [`00-검토`](00-검토-2018년-책과-현재.md) §7 의 **착수 순서 4순위** — 보정 지시가 있는 장이다:
> **"CMS 절은 '동시 수집기 일반'으로 다시 쓰고 ZGC 를 보충해야 한다."** 이 요약은 그 지시대로 CMS 를 **역사 + 동시 수집기의 일반 원리**로 정리하고(§2),
> ZGC 는 [2판 5장 요약](../optimizing-java-2nd/05-고급-GC.md) 으로 보낸다. 표기 — ✅ 실행해 확인(JDK 17.0.19 / 21.0.10 / 25.0.4) · 📄 문서.
>
> **2판(2024)에서는** [5장](../optimizing-java-2nd/05-고급-GC.md) 이 됐다. 1판에만 있는 것: **CMS 본문(65회)**, **C4(Azul Zing) 절**, 레거시 수집기 표(iCMS·폐기 조합), "G1 은 CMS 만큼 저지연이 아닐 수 있다"는 2018년의 평가.

---

## 1. 이 장의 핵심 주장

1. GC 는 플러거블이고 만능은 없다. 관심사 다섯(일시정지 길이·처리량·빈도·회수 효율·일관성). 일시정지에만 매달리지 마라. **"Oracle/OpenJDK 10 기준 주류 수집기 셋"**(Parallel·CMS·G1).
2. 동시 GC 이론 — Dijkstra, **세이프포인트**(JVM 은 스레드를 세우지 못하고 나가는 것만 막는다; 폴은 바이트코드 사이·메서드 종료·루프 백브랜치), **트라이컬러 마킹**·SATB·불변식·쓰기 장벽 vs 픽스업 큐.
3. **CMS** — 테뉴어드 전용 저지연 수집기, ParNew 와 짝. 6단계(Initial Mark[STW] → Concurrent Mark → Concurrent Preclean → Remark[STW] → Concurrent Sweep → Concurrent Reset).
   관측 효과: 앱 정지 짧아짐 / 풀 GC 사이클은 더 오래 / 사이클 중 처리량 감소 / 메모리 더 씀 / CPU 훨씬 더 씀 / **압축 안 함 → 단편화**. 기본으로 코어 절반을 쓴다.
   **동시 모드 실패(CMF)** 두 원인: 할당 압력(조기 승격으로 테뉴어드 여유 소진) / **단편화**(연속 공간 부족) → 완전 STW ParallelOld 폴백. 75% 점유에서 시작(적응형). 60개 넘는 플래그 — 만지작거리지 마라.
4. **G1** — 6 실험·7 재작성·**8u40 안정**, "9 에서 Oracle 이 사용자 영향과 무관하게 기본으로 강행". 리전(1~64MB, 2,048~4,095개), 거대 객체, RSet, 5단계(Initial Mark[STW] → Concurrent Root Scan → Concurrent Mark → Remark[STW] → Cleanup[STW]), `MaxGCPauseMillis=200`("100ms 미만은 안정적으로 어렵다"), `G1HeapRegionSize`(1~64). **"진짜 저지연에서는 아직 CMS 만큼 아니다, 언젠가 도전할 수 있을지 불분명"**.
5. **Shenandoah** — Red Hat, **실험적·운영 불가**(2018). 4단계(Initial Mark → Concurrent Marking → Final Marking → Concurrent Compaction), **Brooks 포인터**(객체당 한 워드), CAS 로 추측 복사 경쟁. IcedTea/Fedora 에만, 아니면 소스 빌드. **비세대형**.
6. **C4(Azul Zing)** — 64비트 전용 상용 VM. 단일 64비트 헤더 워드(**kid** 클래스 ID 25비트 + 락 정보 32비트, 압축 oop 없음), **LVB(Loaded Value Barrier, 자가 치유 장벽)** — 로드된 참조가 항상 현재 위치를 가리키게 로드 시점에 한 번 고친다. 참조 구조체(`inPageVA 21 | PageNumber 21 | NMT 1 | SpaceID 2`), NMT 비트 목표 상태 플립. 단계 Mark → Relocate → Remap. **hand-over-hand 압축**(가상/물리 페이지 분리, 커널 호출 사용 — HotSpot 과 다름). 영·올드 수집기 상시 동작. ReadyNow·Falcon JIT.
7. **Balanced(IBM J9)** — 2판 5장과 같다(리전·PGC·GMP·GGC·arraylet·NUMA). "IBM 이 오픈소스화 중(Open J9)".
8. **레거시** — Serial/SerialOld("8 에서 폐기, 쓰지 마라"), **iCMS**(`-XX:+CMSIncrementalMode`, 9 에서 제거), 폐기 조합 표(DefNew+CMS, ParNew+SerialOld, `-Xincgc`, CMS foreground 플래그들 — 8 폐기·9 제거). **Epsilon**(JEP, 운영 금지, JMH·회귀·무할당 테스트용).

## 2. §7 의 보정 — CMS 절을 "동시 수집기 일반"으로 읽기

CMS 는 **JDK 14 에서 제거됐다**(✅ 17·21·25 `-XX:+UseConcMarkSweepGC` → `Unrecognized VM option`). 그러나 이 장의 CMS 절이 가르치는 것은 **모든 동시 수집기에 그대로 적용된다.** 이렇게 바꿔 읽는다.

| CMS 의 서술 | 동시 수집기 일반 원리 | 지금 어디서 보이나 |
|---|---|---|
| 코어 절반을 GC 에 쓰고 나머지로 앱이 돈다 | 동시 단계는 **앱 처리량을 깎는다.** 그 시간의 영 GC 는 코어가 적어 더 오래 걸린다 | G1 혼합 GC(`ConcGCThreads = max(1,(ParallelGCThreads+2)/4)` ✅ 25 `ConcGCThreads=1`, 4코어), ZGC·Shenandoah 의 동시 스레드 |
| Initial Mark / Remark 두 STW | 동시 수집기도 **짧은 STW 가 몇 개 남는다**(루트 스냅샷, 픽스업) | G1: Concurrent Start·Remark·Cleanup / Shenandoah: Init Mark·Final Mark·Init/Final Update Refs / ZGC: 세 개의 짧은 세이프포인트(1ms 목표) |
| 동시 모드 실패 → ParallelOld 폴백 | **마킹이 할당을 못 따라가면 풀 GC** — 동시 수집기의 근본 약점 | G1 의 풀 GC("concurrent mode failure"), Shenandoah 의 "Pacer"·"Degenerated GC", ZGC 의 할당 정지(`jdk.ZAllocationStall` 이벤트 ✅ 17·21·25) |
| 75% 점유에서 미리 시작 | **일찍 시작해 여유(headroom)를 둔다** | G1 IHOP 45% 적응형(`G1ReservePercent`), ZGC 비용 모델, Shenandoah 휴리스틱 |
| 압축하지 않아 단편화 → CMF | 압축하지 않으면 언젠가 연속 공간이 모자란다 | G1 은 퇴거로 "통계적 압축", Shenandoah·ZGC 는 **동시 압축**(Brooks/색칠 포인터)으로 이 약점을 없앴다 |
| 60개 넘는 플래그, 만지작거리지 마라 | 동시 수집기일수록 **튜닝 없이 쓰는 것이 설계 목표** | ZGC "튜닝 불필요가 목표", Shenandoah "특별한 설정 불필요" |
| ParNew 라는 별도 영 수집기가 필요(승격 조정) | 영·올드가 동시에 움직이면 **조정 문제**가 생긴다 | 세대형 ZGC(21+)·세대형 Shenandoah(25) 가 같은 문제를 다시 푼다 |

**보충 — ZGC**: 1판은 ZGC 를 15장에서 이름만 부른다. 2판 5장 요약 §1-5 와 §4 를 보라 — **25 에서는 세대형 ZGC 만 남았다**(✅ CN-05A).

## 3. 2판(2024)에서 어떻게 바뀌었나

| 항목 | 1판 7장 | 2판 5장 | 근거 |
|---|---|---|---|
| CMS | 본문 절, 65회 | 틈새 수집기 역사 노트, 16회 | ✅ 키워드 |
| G1 평가 | "저지연에서는 CMS 만 못하다" | "훌륭한 범용 수집기, 11·17·21 에서 계속 개선" | ✅ 통독 |
| G1 리전 | 1~64MB | 1~512MB(Java 21) | ✅ |
| G1 단계 | Initial Mark → Concurrent Root Scan → Concurrent Mark → Remark → Cleanup | Concurrent Start(STW+영 GC) → Concurrent Mark → Remark → Cleanup | ✅ |
| G1 튜닝 플래그 | `MaxGCPauseMillis`·`G1HeapRegionSize` | + `G1ReservePercent`·`-G1UseAdaptiveIHOP`·`InitiatingHeapOccupancyPercent`, 컨테이너 코어 1 경고 | ✅ |
| Shenandoah | 실험, 4단계, Brooks 워드 | 정식, 9단계, **13 부터 Brooks 워드 제거(로드 참조 장벽)**, 진화 연표 | ✅ |
| **C4(Zing)** | 절 있음 | **삭제** | ✅ |
| ZGC | 없음 | 정식 절 + 세대형 | ✅ |
| Balanced | J9(오픈소스화 중) | OpenJ9(오픈소스) | ✅ |
| 레거시 표(iCMS·폐기 조합)·Serial 폐기 서술 | 있음 | 삭제. Serial 은 4장에서 "컨테이너에서 자동 선택" 경고로 | ✅ |
| Epsilon | 있음 | 유지(JEP 318 번호 명시) | ✅ |

## 4. JDK 17 / 25 기준 — 어긋나는 것

| 책의 서술 | 지금 | 근거 |
|---|---|---|
| CMS 현역, `-XX:+UseConcMarkSweepGC` | **14 에서 제거** — 기동 실패 | ✅ 17·21·25 |
| iCMS·`-Xincgc`·CMS foreground 플래그 | 9 에서 제거 | 📄 (17 에서 `UseConcMarkSweepGC` 자체가 없으니 조합도 없다 ✅) |
| Serial 은 "8 에서 폐기" | **폐기되지 않았다** — 17·21·25 모두 있고 **컨테이너 CPU 1개면 자동 선택**된다 | ✅ CN-04A (책의 서술이 틀렸거나 특정 조합 이야기) |
| G1 리전 1~64MB | 21 부터 512MB 까지; 25 이 머신 3.4GB 힙에서 2MB | ✅ |
| "100ms 미만 목표는 안정적으로 어렵다" | 2판은 "한 자릿수 GB 힙이면 200 근처에도 안 간다" — 6년 사이 G1 이 좋아졌다 | 📄 |
| Shenandoah 실험·소스 빌드 | 15 정식, 17·21·25 의 비-Oracle 빌드에 포함(이 머신 Ubuntu 빌드 ✅), **25 세대형 모드** | ✅ CN-05B |
| Shenandoah Brooks 워드(Integer 20→28바이트) | 13 부터 마크 워드 비트로 대체 — 추가 워드 없음 | 📄 (2판 5장) |
| Zing/C4 | Azul Platform Prime 으로 개명 📄. 이 저장소에 없다 | 📄 |
| Java 10 기준 주류 셋 | 25 기준 넷(Serial·Parallel·G1·Z) + Shenandoah·Epsilon, **세 동시 수집기 모두 세대형 있음** | ✅ |

## 6. 면접에서 쓸 수 있는 문장

- "CMS 는 14 에서 제거됐지만 CMS 가 가르친 것은 남았습니다. 동시 수집기는 앱 처리량을 깎고, 짧은 STW 가 몇 개 남고, 마킹이 할당을 못 따라가면 풀 GC 로 떨어집니다. G1·ZGC·Shenandoah 전부 같은 구조입니다."
- "동시 모드 실패의 두 원인은 할당 압력과 단편화였습니다. G1 은 퇴거로, ZGC 와 Shenandoah 는 동시 압축으로 단편화 쪽을 없앴고, 할당 압력 쪽은 지금도 IHOP·비용 모델로 일찍 시작하는 수밖에 없습니다."
- "Serial 은 폐기된 수집기가 아닙니다. 컨테이너에 CPU 를 1개 주면 지금도 자동으로 선택됩니다."
