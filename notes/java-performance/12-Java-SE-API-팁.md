## 1. 버퍼드 I/O — 14년이 지나도 여전히

> **저자의 고백**: 2000년에 Java Performance Group에 합류했을 때 버퍼드 I/O가 가장 뜨거운
> 주제 중 하나였다. **14년 뒤 이 책에서 빼려고 했다.** 그런데
> - **이 책 개요를 쓰기 시작한 주에, 버퍼링 안 된 I/O가 성능을 크게 갉아먹는 무관한 두 프로젝트에
>   버그를 제기했다**
> - **몇 달 뒤 이 책 예제를 작업하면서, 내 "최적화"가 왜 이렇게 느린지 머리를 긁적였다.
>   그러다 깨달았다: 멍청아, I/O를 제대로 버퍼링하는 걸 잊었잖아.**

**`InputStream.read()` 와 `OutputStream.write()` 는 한 문자씩 다룬다.**
> **`FileInputStream` 의 `read()` 는 참을 수 없이 느리다** — **호출마다 1바이트를 가져오려고
> 커널로 들어가야 한다.** 대부분의 OS에서 커널이 I/O를 버퍼링해 두어 다행히 호출마다 디스크
> 읽기가 일어나지는 않는다. **하지만 그 버퍼는 커널에 있지 애플리케이션에 있지 않고, 한 번에
> 1바이트씩 읽는다는 것은 호출마다 비싼 시스템 콜을 한다는 뜻이다.**

**규칙**
- **파일 바이너리 I/O** → 항상 `BufferedInputStream`/`BufferedOutputStream` 으로 감싼다
- **파일 문자(문자열) I/O** → 항상 `BufferedReader`/`BufferedWriter`
- **소켓 스트림도 같다.** 소켓에서 한 바이트씩 I/O 하는 것은 꽤 느리다

### ⚠️ `ByteArrayInputStream`/`ByteArrayOutputStream` 은 미묘하다

> **이 클래스들은 본질적으로 이미 큰 인메모리 버퍼다.**
> **버퍼링 필터로 감싸면 데이터가 두 번 복사된다** — 필터 스트림의 버퍼로 한 번,
> `ByteArrayInputStream` 의 버퍼로 한 번.
> **다른 스트림이 관여하지 않는다면 이 경우 버퍼드 I/O는 피해야 한다.**

### 다른 필터 스트림이 끼면 복잡해진다

```java
// 버퍼링이 필요 없는 경우 — ObjectOutputStream 이 곧바로 ByteArrayOutputStream 으로
ByteArrayOutputStream baos = new ByteArrayOutputStream();
ObjectOutputStream oos = new ObjectOutputStream(baos);

// 버퍼링이 필요한 경우 — 중간에 GZIPOutputStream 이 있다
ByteArrayOutputStream baos = new ByteArrayOutputStream();
GZIPOutputStream zip = new GZIPOutputStream(baos);
BufferedOutputStream bos = new BufferedOutputStream(zip);   // ★
ObjectOutputStream oos = new ObjectOutputStream(bos);
```

> **`ObjectOutputStream` 은 어느 경우든 다음 스트림으로 한 바이트씩 보낸다.**
> **다음 스트림이 최종 목적지(`ByteArrayOutputStream`)면 버퍼링이 필요 없다.**
> **중간에 다른 필터 스트림(`GZIPOutputStream`)이 있으면 버퍼링이 종종 필요하다** —
> **GZIP은 한 바이트씩보다 데이터 블록에 대해 훨씬 효율적으로 동작하기 때문**이다.
>
> **두 스트림 사이에 버퍼드 스트림을 끼울지에 대한 일반 규칙은 없다.** 관여하는 스트림 종류에
> 달렸지만, **가능성 있는 경우들은 모두 (`ObjectOutputStream` 의 단일 바이트가 아니라)
> 버퍼드 스트림에서 온 바이트 블록을 받으면 더 잘 동작한다.**

> **⚠️ 이 경우가 스트림 인코더·디코더에 특히 해당한다.**
> **바이트와 문자를 변환할 때 가능한 한 큰 조각으로 동작하는 것이 최선의 성능을 준다.
> 인코더·디코더에 단일 바이트나 문자를 먹이면 성능이 나빠진다.**

**저자가 실제로 저지른 실수의 대가**

| 연산 | 직렬화 | 역직렬화 |
|---|---|---|
| **버퍼링 안 한 압축/해제** | **60.3초** | **79.3초** |
| 버퍼링한 압축/해제 | 26.8초 | 12.7초 |

> **I/O를 제대로 버퍼링하지 못한 결과가 최대 6배의 성능 페널티였다.**

## 2. 클래스로딩 — Java 7의 병렬화

**클래스로딩 성능이 나쁜 근본 이유**
- **클래스 데이터(바이트코드)에 빨리 접근할 수 없다** — 디스크나 네트워크에서 로드하고,
  클래스패스의 여러 JAR 중에서 찾고, 여러 클래스로더 중에서 찾아야 한다
- **Java WebStart는 네트워크에서 읽은 클래스를 숨김 디렉터리에 캐시**해서 다음번에 로컬 디스크에서
  더 빨리 읽는다
- **JAR 파일 수를 줄이는 것도 클래스로딩을 빠르게 한다**

### 병렬화를 막던 두 가지

**① 디스크** — 같은 디스크에 저장돼 있으면 동시에 도는 두 클래스로더가 같은 장치에 읽기를
발행한다. **OS가 꽤 잘 다루지만 디스크가 병목이 될 가능성이 충분히 있다.**

**② ⚠️ Java 7 이전 `ClassLoader` 클래스 설계 자체 — 더 큰 문제**

**위임 모델**: 서블릿 앱의 클래스로더가 클래스를 필요로 하면 → 웹앱 클래스로더 → **시스템(클래스패스)
클래스로더** → **부트스트랩 클래스로더**(핵심 JDK 클래스)로 위임된다.
**기능적으로는 말이 된다 — `java.lang.String` 의 바이트코드는 계층의 다른 클래스로더에 우연히
(또는 악의적으로) 포함된 구현이 아니라 부트스트랩에서 와야 한다.**

> **⚠️ Java 7 이전에는 클래스를 로드하는 메서드가 `synchronized` 였다 — 한 번에 하나의
> 클래스로더만 시스템 클래스로더에 위임할 수 있었다.**
> **여러 클래스로더를 쓰는 병렬성이 극적으로 감소했다.**
>
> **Java 7은 클래스 이름 기반의 락 집합으로 이 상황을 해결한다.**
> **이제 같은 클래스를 찾는 두 클래스로더는 여전히 락을 두고 경합하지만, 다른 클래스를 찾는
> 클래스로더들은 계층 안에서 병렬로 실행될 수 있다.**
>
> Java 7이 제공하는 클래스로더(`URLClassLoader` 등)는 **parallel-capable** 이다.

### 자기 클래스로더를 parallel-capable로 만들기

**클래스로더는 기본적으로 parallel-capable이 아니다. 두 단계가 필요하다.**

**① 클래스로더 계층에 사이클이 없어야 한다**
> **순환 클래스로더 계층은 꽤 드물다.** 게다가 유지보수가 아주 어려운 코드가 된다 —
> **사이클의 어느 지점에서는 부모에게 넘기지 않고 직접 요청을 만족시켜야 하기 때문**(안 그러면
> 위임이 무한 루프가 된다). **기술적으로는 병렬성을 켤 수 있지만 (이미 복잡한 코드 위에)
> 뒤엉킨 과정이다.**
> **성능 좋은 자바 코드의 한 원칙이 흔한 관용구를 쓰고 컴파일러가 쉽게 최적화할 수 있는 단순한
> 코드를 쓰는 것이므로, 이 경우는 권하지 않는다.**

**② 정적 초기화 블록에서 등록한다**
```java
public class MyCustomClassLoader extends SecureClassLoader {
    static { registerAsParallelCapable(); }
}
```
> **⚠️ 이 호출은 각 구체 클래스로더 구현 안에서 이뤄져야 한다.**
> **`SecureClassLoader` 자체는 parallel-capable이지만 서브클래스는 그 설정을 물려받지 않는다.**
> `MyCustomClassLoader` 를 확장하는 두 번째 클래스가 있다면 **그 클래스도 자기 자신을 등록해야 한다.**
>
> **클래스로더를 쓰는 권장 방식은 `findClass()` 를 오버라이드하는 것이다.**
> **`loadClass()` 를 오버라이드하는 커스텀 클래스로더는 각 클래스로더 인스턴스에서 클래스
> 이름당 `defineClass()` 가 정확히 한 번만 호출되도록 보장해야 한다.**

### 실측 — 이 절의 핵심 트레이드오프

**클래스패스가 비었을 때 (1,500개 클래스 × 100회)**

| 스레드 수 | JDK 7 | JDK 6 |
|---|---|---|
| **1** | **30.353초** | **27.696초** |
| 2 | 34.811초 | 31.409초 |
| 4 | **48.106초** | 72.208초 |
| 8 | **117.34초** | 184.45초 |

> **⚠️ 흥미로운 결론 두 가지.**
> **첫째, 병렬 로딩을 가능하게 한 JDK 7의 더 복잡한 코드가 가장 단순한 경우에 실제로 작은
> 페널티를 도입했다 — 더 단순한 코드가 더 빠르다는 원칙의 사례다.**
> 스레드 2개에서도 새 모델이 약간 느린데, **이 경우 부모 클래스로더에서 보내는 시간이 사실상
> 없기 때문**이다. 락이 유지되는 시간이 프로그램의 다른 부분에서 쓰는 시간에 크게 압도된다.
>
> **스레드 4개에서 상황이 바뀐다.** (여기서 4스레드는 4 CPU 머신의 다른 프로세스와 CPU를 두고
> 경쟁한다 — 특히 플래시 페이지를 띄운 브라우저가 CPU 하나의 40%쯤을 쓰고 있다.
> **그래서 JDK 7에서도 확장이 선형이 아니다.**) **하지만 확장이 훨씬 낫다.**
> **JDK 6에서는 이제 부모 클래스로더 락 주변에 심한 경합이 있다.** 이유는 둘 —
> **① CPU 경쟁이 사실상 락 유지 시간을 늘렸고 ② 락을 두고 경쟁하는 스레드가 두 배가 됐다.**

**클래스패스에 266개 항목이 있을 때** (GlassFish 배포판의 JAR 수)

| 스레드 수 | JDK 7 | JDK 6 |
|---|---|---|
| 1 | 98.146초 | 92.129초 |
| **2** | **111.16초** | **316.01초** |
| **4** | **150.98초** | **708.24초** |
| **8** | **287.97초** | **1461.5초** |

> **이제 스레드 2개만으로도 경합이 꽤 심하다 — parallel-enabled 클래스로더가 없으면 클래스
> 로드에 3배가 걸린다.** 이미 부담받는 시스템에 부하가 주입되면서 확장이 더 나빠져
> **결국 7배까지 느려진다.**

> **흥미로운 트레이드오프**: **더 복잡한 코드를 배포해 단일 스레드 경우에 성능을 약간 해칠 것인가,
> 아니면 다른 경우를 위해 최적화할 것인가** — 특히 마지막 예처럼 성능 차이가 아주 클 때.
> **이런 성능 트레이드오프는 늘 일어나고, JDK 팀은 두 번째를 기본으로 택했다.**
> **플랫폼으로서는 두 선택지를 다 제공하는 것이 좋은 생각이다**(기본은 하나뿐일지라도).
> ```
> -XX:+AlwaysLockClassLoader   # 기본 false. JDK 6 동작을 켠다
> ```
> **여러 클래스로더에서 동시에 클래스를 로드하는 스레드가 없는 긴 시작 사이클은 이 플래그로
> 약간 이득을 볼 수 있다.**

## 3. 난수 생성기 세 가지

| 클래스 | 특성 |
|---|---|
| `java.util.Random` | **주 연산(`nextGaussian()`)이 `synchronized`** |
| `java.util.concurrent.ThreadLocalRandom` | 스레드마다 자기 생성기 → **동기화 문제 없음** |
| `java.security.SecureRandom` | **알고리즘 자체가 다르다** |

> **`Random` 의 그 메서드는 난수를 가져오는 모든 메서드가 쓰므로, 어떻게 쓰든 그 락이 경합될 수
> 있다** — 두 스레드가 같은 생성기를 동시에 쓰면 하나가 기다려야 한다.
> **(7장에서 봤듯 스레드 로컬 버전은 생성이 비싼 객체를 재사용하기 때문에도 상당한 성능 이득을 준다.)**

### ⚠️ `SecureRandom` — 성능 자체가 무작위가 된다

**`Random`(과 상속받은 `ThreadLocalRandom`)은 전형적인 의사난수 알고리즘**이다.
**정교하지만 결국 결정론적이다.** 초기 시드를 알면 정확한 수열을 알아낼 수 있다.
**좋은 의사난수 생성기는 정말 무작위처럼 보이는(그리고 확률적 기대에도 맞는) 수열을 낼 수 있지만
진짜 무작위는 아니다.**

**`SecureRandom` 은 시스템 인터페이스로 무작위 데이터를 얻는다.** 방식은 OS별이지만
**일반적으로 진짜 무작위 사건(마우스 이동 등)에 기반한 데이터**를 제공한다.
**엔트로피 기반 무작위성**이라 하고 **SSL 암호화가 가장 잘 알려진 예다.**

> **⚠️ 불행히도 컴퓨터는 제한된 양의 엔트로피만 생성하므로, 보안 난수 생성기에서 많은 난수를
> 얻는 데 아주 오래 걸릴 수 있다.**
> **`nextRandom()` 호출은 시스템의 미사용 엔트로피 양에 따라 부정확한 시간이 걸린다.
> 엔트로피가 없으면 필요한 엔트로피가 생길 때까지 호출이 멈춘 것처럼 보인다 — 때로는 몇 초씩.**
> **그래서 성능 측정이 꽤 어려워진다: 성능 자체가 무작위가 된다.**
>
> **SSL 연결을 많이 만들거나 보안 난수가 많이 필요한 애플리케이션에서 자주 문제가 된다.**
> **그런 애플리케이션의 성능 테스트를 할 때는 타이밍의 분산이 아주 클 것임을 알아야 한다.**
> **그 분산을 다룰 방법은 2장에서 논의한 대로 아주 많은 샘플 테스트를 돌리는 것 외에 없다.**
> 다른 대안은 **OS 벤더에 연락해 추가적인(또는 더 나은) 엔트로피 소스가 있는지 알아보는 것**이다.
>
> **급하면 세 번째 대안**: 프로덕션에서는 `SecureRandom` 을 쓰더라도 **성능 테스트는 `Random` 으로
> 돌린다.** 모듈 수준 테스트라면 말이 된다 — **그 테스트는 같은 기간에 프로덕션 시스템보다 더
> 많은 난수(더 많은 SSL 소켓)를 필요로 할 테니까.**
> **하지만 결국 예상 부하를 `SecureRandom` 으로 테스트해서 프로덕션 시스템이 충분한 난수를
> 얻을 수 있는지 확인해야 한다.**

## 4. JNI — 성능 문제의 해법이 아니다

> **가능한 가장 빠른 코드를 쓰고 싶다면 JNI를 피하라.**
> **잘 작성된 자바 코드는 현재 JVM에서 대응하는 C나 C++ 코드만큼 빠르게 돈다 (더 이상 1996년이
> 아니다).**
> 언어 순수주의자들은 계속 논쟁할 것이고, **다른 언어로 쓴 애플리케이션이 같은 자바 애플리케이션보다
> 빠른 예를 분명 찾을 수 있다**(다만 그런 예들은 종종 잘못 작성된 자바 코드를 담고 있다).
> **하지만 그 논쟁은 이 절의 요점을 놓친다 — 애플리케이션이 이미 자바로 작성돼 있다면, 성능을
> 이유로 네이티브 코드를 부르는 것은 거의 항상 나쁜 생각이다.**

**JNI가 유용한 때는 있다** — OS 고유 기능 접근, 이미 있는 상용 네이티브 라이브러리 활용.
**그때의 질문은 어떻게 가장 효율적인 JNI 코드를 쓸 것인가다.**

> **답: 자바에서 C로의 호출을 최대한 줄여라. JNI 경계를 넘는 것이 꽤 비싸다.**
> **어차피 글루 코드를 써야 하므로, 시간을 들여 굵은(coarse-grained) 인터페이스를 새로 만들어라** —
> **한 번에 C 라이브러리로 여러 호출을 수행하도록.**

### ⚠️ 반대 방향은 반드시 그렇지 않다

| calculateError | calc | random | JNI 전이 | 총 시간 |
|---|---|---|---|---|
| Java | Java | Java | 0 | **12.4초** |
| Java | Java | **C** | **10,000,000** | **32.1초** |
| Java | **C** | **C** | 10,000 | 24.4초 |
| **C** | Java | Java | 10,000 | **12.4초** |
| **C** | **C** | **C** | 0 | **12.4초** |

> **가장 안쪽 메서드만 JNI로 구현하면 경계를 가장 많이 넘는다(1천만 번).** 1만 번으로 줄이면
> 오버헤드가 크게 준다. **0으로 줄이면 최선이다 — 다만 순수 자바 구현이 전부 네이티브인 구현만큼
> 빠르다.**
>
> **⚠️ 그리고 C에서 자바로 되부르는 것은 큰 성능 페널티가 없다**(관여하는 파라미터에 따라).
> **이유**: 단순 참조에도 **주소 변환**이 필요하다. **자바→C 호출은 대상 객체(`this`)를 암묵적으로
> C 함수에 넘긴다. C→자바 호출은 객체를 전혀 넘기지 않는다.**

### ⚠️ 배열·문자열 pinning — 가장 비싼 실수

> **배열 기반 데이터 연산은 네이티브 코드에서 특별 처리가 필요하다.** `String` 도 포함된다
> (문자열 데이터가 본질적으로 문자 배열이므로).
> **개별 원소에 접근하려면 객체를 메모리에 pin하는 특별 호출**이 필요하다
> (`String` 은 **UTF-16에서 UTF-8로 변환**도). 다 쓰면 **JNI 코드에서 명시적으로 해제**해야 한다.
>
> **⚠️ 배열이 pin된 동안 GC가 돌 수 없다. 그래서 JNI 코드에서 가장 비싼 실수 중 하나가
> 오래 도는 코드에서 문자열이나 배열을 pin하는 것이다. GC가 돌지 못하게 막아 사실상 모든
> 애플리케이션 스레드를 JNI 코드가 끝날 때까지 블로킹한다.**
> **배열이 pin된 임계 구역을 최대한 짧게 만드는 것이 극도로 중요하다.**
>
> **⚠️ 때로 이 목표가 JNI 경계 호출을 줄이는 목표와 충돌한다. 그 경우 후자(짧은 pinning)가 더
> 중요하다 — JNI 경계를 여러 번 넘게 되더라도 배열·문자열을 pin하는 구간을 최대한 짧게 하라.**

## 5. 예외 — 평판만큼 비싸지 않다

> **자바 예외 처리는 비싸다는 평판이 있다. 일반 제어 흐름보다는 다소 비싸지만, 대부분의 경우
> 그 추가 비용은 우회하려 노력할 만한 가치가 없다.**
> **반면 공짜가 아니므로 일반 메커니즘으로 쓰여서도 안 된다.**
> **지침: 좋은 프로그램 설계의 일반 원칙에 따라 예외를 써라 — 주로, 예상치 못한 일이 일어났음을
> 나타낼 때만 던져라.**

**두 가지 요소**
1. **try-catch 블록 설정 자체가 비싼가?**
   > **아주 오래전에는 그랬을 수 있지만 수년간 그렇지 않았다.**
   > **인터넷은 기억이 길어서, 단지 try-catch 때문에 예외를 피하라는 권고를 보게 될 것이다.
   > 그 권고는 낡았다 — 현대 JVM은 예외를 꽤 효율적으로 처리하는 코드를 생성한다.**
2. **(대부분의) 예외가 그 지점의 스택 트레이스를 얻는다는 것.**
   **이 연산이 비쌀 수 있다. 특히 스택이 깊으면.**

**실측 — 100,000회 중 100% 예외 (최악의 경우)**

| 방식 | 얕은 스택(3) | 깊은 스택(100) |
|---|---|---|
| **코드가 명시적으로 예외 생성** | **381 ms** | **10,673 ms** |
| **시스템 생성 예외(NPE)** | **15 ms** | **15 ms** |
| 방어적 프로그래밍(null 검사) | 2 ms | 2 ms |

> **세 가지 흥미로운 차이가 있다.**
>
> **① 명시적으로 예외를 만드는 경우 얕은 스택과 깊은 스택의 시간 차이가 유의미하다.
> 스택 트레이스 구성에 시간이 걸리고 그것은 스택 깊이에 의존한다.**
>
> **② ⚠️ 코드가 명시적으로 만드는 경우와 JVM이 null 역참조에서 만드는 경우의 차이 (표의 앞 두 줄).**
> **어느 시점에 컴파일러가 시스템 생성 예외를 최적화한다 — JVM이 매번 새로 만드는 대신 같은
> 예외 객체를 재사용하기 시작한다.** 호출 스택과 무관하게 그 객체가 재사용되고,
> **그 예외는 실제로 호출 스택을 담지 않는다**(`printStackTrace()` 가 아무 출력도 안 낸다).
> **이 최적화는 전체 스택 예외가 꽤 오래 던져진 뒤에야 일어나므로, 테스트에 충분한 워밍업이
> 없으면 그 효과를 보지 못한다.**
>
> **③ 방어적 프로그래밍이 최선의 성능이다. 이 예에서는 놀랍지 않다 — 루프 전체가 no-op가 되니까.
> 그 숫자는 에누리해서 봐라.**

**실측 — 1% 예외 (제대로 쓰인 경우)**

| 방식 | 얕은 스택 | 깊은 스택 |
|---|---|---|
| 코드 예외 | 56 ms | 157 ms |
| 시스템 예외 | 51 ms | 52 ms |
| 방어적 프로그래밍 | 50 ms | 50 ms |

> **이제 `toString()` 처리 시간이 계산을 지배한다. 깊은 스택으로 예외를 만드는 페널티는 여전히
> 있지만, 미리 null을 검사하는 이득은 거의 사라졌다.**
> **그러므로 예외를 무분별하게 쓰는 성능 페널티는 예상보다 작다.**

```
-XX:-StackTraceInThrowable   # 기본 true. 스택 트레이스 생성을 끈다
```
> **⚠️ 이건 좋은 생각인 경우가 드물다.**
> **스택 트레이스는 예상치 못하게 무엇이 잘못됐는지 분석할 수 있게 하려고 있다. 이 플래그를
> 켜면 그 능력을 잃는다.**
> **그리고 실제로 스택 트레이스를 조사해 거기서 찾은 것에 기반해 예외를 복구하는 코드가 있다
> (CORBA 참조 구현이 그렇게 동작한다). 그 자체가 문제지만, 결론은 스택 트레이스를 끄면
> 코드가 알 수 없게 깨질 수 있다는 것이다.**

**JDK 자체의 예외 처리 성능 이슈**
- **많은 컬렉션 클래스가 없는 항목을 꺼낼 때 예외를 던진다.** `Stack.pop()` 은 비었으면
  `EmptyStackException`. **먼저 길이를 검사하는 방어적 프로그래밍이 대개 낫다**
  (**반면 `Stack` 은 다른 많은 컬렉션과 달리 `null` 객체를 지원하므로 `pop()` 이 `null` 로 빈
  스택을 나타낼 수도 없다**)
- **⚠️ JDK 안에서 가장 악명 높은 예**: **클래스로딩.** `ClassLoader.loadClass()` 는 찾을 수 없는
  클래스를 요청받으면 `ClassNotFoundException` 을 던진다.
  > **그건 사실 예외적 조건이 아니다. 개별 클래스로더가 애플리케이션의 모든 클래스를 로드할 줄
  > 알 것으로 기대되지 않는다 — 그래서 클래스로더 계층이 있는 것이다.**
  > **수십 개 클래스로더가 있는 환경에서는 계층을 뒤지는 동안 아주 많은 예외가 만들어진다.**
  > 앞의 클래스로딩 예제는 **스택 트레이스 생성을 끄면 3% 빨라진다.**
  > **그래도 그런 차이는 규칙이라기보다 예외다. 그 예제는 아주 긴 클래스패스를 가진
  > 마이크로벤치마크이고, 그런 상황에서도 호출당 차이는 밀리초 수준이다.**

## 6. String 성능

**다른 장에서 다룬 것들**
- **인터닝** (7장), **인코딩**(`Charset.encode()/decode()` 는 한두 문자씩 처리하면 아주 느리다 —
  **전체 버퍼를 처리하도록 설정하라**), **네트워크 인코딩**(10장)

### 문자열 결합 — 한 줄이면 괜찮다

```java
String answer = integerPart + "." + mantissa;
```
**javac의 문법 설탕이 이걸로 바꾼다** — **꽤 성능이 좋다:**
```java
String answer = new StringBuilder(integerPart).append(".").append(mantissa).toString();
```

**⚠️ 조각내면 문제가 생긴다**
```java
String answer = integerPart;
answer += ".";
answer += mantissa;
```
**이렇게 번역된다:**
```java
String answer = new StringBuilder(integerPart).toString();
answer = new StringBuilder(answer).append(".").toString();
answer = new StringBuilder(answer).append(mantissa).toString();
```
> **그 모든 임시 `StringBuilder` 와 중간 `String` 객체가 비효율적이다.**
>
> **규칙: 단일(논리적) 줄에서 할 수 있는 경우가 아니면 결합으로 문자열을 만들지 마라.
> 그리고 결합된 문자열이 다음 반복에서 쓰이지 않는 경우가 아니면 루프 안에서 문자열 결합을
> 쓰지 마라. 그 외에는 항상 명시적으로 `StringBuilder` 를 써라.**
>
> **1장에서 "성급하게" 최적화해야 할 때 — 그 표현이 단순히 "좋은 코드를 쓴다"는 뜻으로 쓰일 때 —
> 가 있다고 주장했다. 이것이 대표적인 예다.**

## 7. 로깅 — 성능 엔지니어가 사랑하고 미워하는 것

> **저자의 고백**: **"프로그램이 왜 느린가"** 라는 질문을 받으면 **가장 먼저 로그를 달라고 한다.**
> **"돌아가는 코드의 성능을 검토해 달라"** 는 요청을 받으면 **즉시 모든 로깅 문장을 끄라고 권한다.**

**세 가지 로그**
- **GC 로그** — 별도 파일로 보낼 수 있고 JVM이 크기를 관리한다.
  **⚠️ 프로덕션에서도 `-XX:+PrintGCDetails` 는 오버헤드가 아주 낮고 뭔가 잘못됐을 때 이득이
  아주 커서 항상 켜 둬야 한다**
- **Java EE 액세스 로그** — 매 요청마다 갱신된다. **눈에 띄는 영향이 있고, 끄면 확실히 성능이
  개선된다.** 진단 가능성 관점에서는 (저자 경험상) 그리 도움되지 않는다.
  **하지만 비즈니스 요구사항 측면에서는 종종 필수이므로 그 경우 켜 둬야 한다**
  > **많은 앱 서버가 Apache `mod_log_config` 표준을 지원**해 요청마다 무엇을 로깅할지 정확히
  > 지정할 수 있다. **핵심은 비즈니스 요구를 충족하면서 최대한 적게 로깅하는 것이다.**
  >
  > **⚠️ HTTP 액세스 로그(그리고 일반적으로 모든 로그)에서는 모든 정보를 숫자로 로깅하는 것이
  > 좋다** — **호스트명 대신 IP 주소**, `"Monday, June 3, 2013 17:23:00 -0600"` 같은 문자열 대신
  > **타임스탬프(에포크 이후 초)**. **시간과 메모리를 쓰는 데이터 변환을 최소화하라.
  > 로그는 나중에 후처리해서 변환할 수 있다**
- **애플리케이션 로그** — 세 가지 원칙

### 애플리케이션 로그의 세 원칙

**① 데이터와 레벨의 균형**
> JDK에는 표준 로깅 레벨이 **일곱 개**이고 로거는 기본으로 **세 개(`INFO` 이상)** 를 출력한다.
> **이것이 프로젝트 안에서 자주 혼란을 만든다** — `INFO` 는 꽤 흔하고 애플리케이션 흐름을 기술해야
> 할 것처럼 들린다("이제 태스크 A를 처리 중", "이제 태스크 B"...).
> **⚠️ 특히 스레드가 많고 확장 가능한 애플리케이션(Java EE 앱 서버 포함)에서는 그만큼의 로깅이
> 성능에 해로운 영향을 준다**(너무 수다스러워 쓸모없게 될 위험은 말할 것도 없고).
> **더 낮은 레벨의 로깅 문장을 쓰는 것을 두려워하지 마라.**
>
> **공용 저장소에 체크인할 때는 개발자인 자신의 필요가 아니라 프로젝트 사용자의 필요를 고려하라.**
> **메시지가 최종 사용자나 시스템 관리자에게 말이 안 된다면 기본으로 켜는 것이 도움이 안 된다.
> 단지 시스템을 느리게 하고 (최종 사용자를 혼란스럽게) 할 뿐이다.**

**② 세밀한 로거**
> 클래스당 로거 하나는 설정이 번거로울 수 있지만 **출력을 더 잘 제어할 수 있어 종종 그럴 가치가
> 있다. 작은 모듈의 클래스 집합이 로거를 공유하는 것이 좋은 타협이다.**
>
> **⚠️ 기억할 요점**: **프로덕션 문제 — 특히 부하 중에 일어나거나 성능 관련인 문제 — 는 환경이
> 크게 바뀌면 재현하기 까다롭다. 로깅을 너무 많이 켜면 원래 문제가 더 이상 드러나지 않을 만큼
> 환경이 바뀌는 경우가 많다.**
> **그러므로 코드의 작은 부분집합에만 로깅을 켤 수 있어야 한다**(처음에는 `FINE` 의 작은 집합,
> 그다음 `FINER`·`FINEST`).
>
> **이 두 원칙 사이에서, 시스템 성능에 영향을 주지 않고 프로덕션 환경에서 작은 메시지 부분집합을
> 켤 수 있어야 한다. 대개 그건 어차피 요구사항이다 — 프로덕션 관리자는 시스템이 느려지면 로깅을
> 켜지 않을 것이고, 시스템이 느려지면 문제 재현 가능성이 줄어든다.**

**③ ⚠️ 로깅이 켜져 있지 않아도 부작용이 있는 코드를 쓰기 쉽다**
> **이것도 "성급하게" 최적화하는 것이 좋은 경우다.**
> **로깅할 정보가 메서드 호출, 문자열 결합, 또는 어떤 종류의 할당(예: `MessageFormat` 인자용
> `Object` 배열 할당)을 포함할 때는 반드시 `isLoggable()` 로 먼저 검사하라.**

## 8. 컬렉션 API

> **Java 7이 제공하는 컬렉션 클래스는 최소 58개다.**
> **첫 규칙은 애플리케이션의 알고리즘적 필요에 맞는 컬렉션을 쓰는 것이다. 자바에 특유한 조언이
> 아니라 본질적으로 자료구조 101이다.**
> `LinkedList` 는 검색에 부적합, 무작위 접근이면 `HashMap`, 정렬 유지가 필요하면 애플리케이션에서
> 정렬하지 말고 `TreeMap`, 인덱스 접근이면 `ArrayList`(다만 중간 삽입이 잦으면 아니다).
> **어느 컬렉션을 고르냐는 결정적이지만 그 선택은 다른 언어와 다르지 않다.**
>
> **다만 자바 컬렉션에는 고려할 특이점이 몇 가지 있다.**

### 동기화 vs 비동기화

> **왜 `Vector` 와 `Hashtable` 이 동기화돼 있나 — 역사**
> **자바 초기(Java 1.2 이전)에는 이것들이 JDK의 유일한 컬렉션 클래스였다.** 그때는 Collections
> Framework의 공식 정의가 없었고, 그냥 원래 자바 플랫폼이 제공한 유용한 클래스였다.
>
> **자바가 처음 나왔을 때 스레딩은 대부분의 개발자에게 잘 이해되지 않았고, 자바는 개발자가
> 스레드 환경 코딩의 함정을 피하기 쉽게 만들려 했다. 그래서 이 클래스들은 스레드 안전했다.**
>
> **불행히도 초기 자바에서는 동기화 — 심지어 비경합 동기화조차 — 가 엄청난 성능 문제였다.
> 그래서 첫 대규모 개정에서 Collections Framework는 정반대 접근을 취했다: 모든 새 컬렉션은
> 기본적으로 비동기화.**
> **그때 이후 동기화 성능이 극적으로 개선됐지만 여전히 공짜가 아니고, 비동기화 컬렉션이라는
> 선택지가 모두가 더 빠른 프로그램을 쓰는 데 도움이 된다**(가끔 비동기화 컬렉션을 동시 수정해
> 버그가 나긴 하지만).

**실측 — 5억 회 연산, 경합 없는 단일 스레드**

| 모드 | 총 시간 | 연산당 시간 |
|---|---|---|
| **CAS 연산** | 6.6초 | **13 ns** |
| **`synchronized` 메서드** | 11.8초 | **23 ns** |
| **비동기화 메서드** | 3.9초 | **7.8 ns** |

> **9장에서 CAS와 전통적 동기화 비교 마이크로벤치마크가 스레드 경우에는 비현실적이라고 했다.
> 그런데 데이터가 단일 스레드로만 접근된다면? 그 경우 이 마이크로벤치마크는 유효하다** —
> **경합이 있을 수 없고, 질문이 "자원 접근을 과도하게 동기화한 페널티가 얼마인가"이므로.**
>
> **어떤 데이터 보호 기법이든 단순 비동기화 접근보다 작은 페널티가 있다는 것이 분명하다.
> 하지만 이건 5억 회 연산의 마이크로벤치마크다 — 연산당 차이는 15나노초 수준이다.**
> **대상 애플리케이션에서 그 연산이 충분히 자주 실행되면 페널티가 다소 눈에 띌 것이다.
> 대부분의 경우 그 차이는 애플리케이션의 다른 영역에 있는 훨씬 큰 비효율에 압도된다.**

> **동기화된 `Vector` 와 비동기화 `ArrayList` 중 무엇을 쓸까?**
> `ArrayList` 접근이 약간 빠르고 접근 빈도에 따라 측정 가능한 차이가 있을 수 있다
> (**9장에서 봤듯 특정 하드웨어에서는 `synchronized` 메서드의 과도한 호출이 성능에 꽤 아플 수 있다**).
>
> **반면 이건 코드가 절대 두 스레드 이상에서 접근되지 않는다는 가정이다. 오늘은 사실일 수 있지만
> 내일은? 바뀔 수 있다면 지금 동기화 컬렉션을 쓰고 결과적인 성능 영향을 완화하는 편이 낫다.
> 이건 설계 선택이고, 코드를 미래에 대비해 스레드 안전하게 만들 가치가 있는지는 상황에 달렸다.**
>
> **비동기화 컬렉션과 CAS 기반 컬렉션(`HashMap` vs `ConcurrentHashMap`) 사이라면 성능 차이는
> 더욱 덜 중요하다. CAS 기반 클래스는 비경합 환경에서 사실상 오버헤드가 없다**
> (다만 해시맵의 메모리 차이는 뒤에서 다룬다).

### 컬렉션 크기 정하기

> **배열을 쓰는 컬렉션인지 아는 법**: **초기 크기를 지정할 수 있는 생성자가 있으면 내부적으로
> 배열을 쓰는 것이다.**

- **`ArrayList`**: `elementData` 배열이 기본 **10**으로 시작. 11번째 삽입 시 확장 —
  **새 배열 할당, 기존 내용 복사, 새 항목 추가**
- **`ArrayList` 의 리사이징 알고리즘**: 기존 크기의 **약 절반을 더한다** → 10, 15, 22, 33, ...
- **`HashMap`**: `HashMap$Entry` 배열. 키의 해시코드로 위치를 정한다
- **`LinkedList`** 는 배열이 아니라 내부 `Node` 클래스를 쓴다

> **어떤 알고리즘을 쓰든 낭비되는 메모리가 생기고(그것이 GC 시간에 영향을 준다), 리사이징마다
> 비싼 배열 복사가 일어난다.**
> **최소화하려면 최종 크기를 최대한 정확히 추정해 생성하라.**

> **컬렉션이 아닌 클래스의 데이터 확장**
> `ByteArrayOutputStream`, `StringBuilder`, `StringBuffer` 도 내부 배열에 데이터를 담는다.
> **대부분 같은 알고리즘을 쓴다 — 리사이징마다 두 배로 늘린다.**
> **이는 평균적으로 내부 배열이 현재 담긴 데이터보다 25% 크다는 뜻이다.**
> **메모리 사용은 `ArrayList` 예보다 크고 복사 횟수는 적지만 원칙은 같다.**
> **생성 시 크기를 정할 수 있고 최종 데이터량을 추정할 수 있다면 크기 파라미터를 받는 생성자를 써라.**

### 컬렉션과 메모리 효율

> **⚠️ 희소하게 쓰이는 컬렉션 — 원소가 하나둘뿐인 것 — 이 특히 문제다. 광범위하게 쓰이면 아주
> 많은 메모리를 낭비할 수 있다.**
> 대응은 **생성 시 크기를 정하거나, 애초에 컬렉션이 정말 필요한지 고려하는 것.**

> **크기가 중요하다 — 저자의 비유**
> **"배열을 빨리 정렬하려면?"에 대부분의 개발자는 퀵소트라고 답한다. 좋은 성능 엔지니어는
> 배열 크기를 알고 싶어 한다** — 충분히 작으면 **삽입 정렬**이 가장 빠르다.
> **자바 `Arrays.sort()` 구현은 47개 미만이면 삽입 정렬이 빠르다고 가정한다.**
>
> **마찬가지로 `HashMap` 은 키로 항목을 찾는 가장 빠른 방법이지만, 키가 하나뿐이라면 단순한
> 객체 참조에 비해 과잉이다. 키가 몇 개뿐이어도 참조 몇 개를 유지하는 편이 완전한 `HashMap` 보다
> 메모리를 훨씬 덜 쓰고 GC에 (긍정적인) 영향을 준다.**

> **JDK 7u40의 컬렉션 메모리 최적화**
> **미사용 컬렉션이 많은 애플리케이션에서 문제가 되므로, JDK 7u40은 `ArrayList` 와 `HashMap` 에
> 새 최적화를 도입했다 — 기본적으로(생성자에 크기를 안 주면) 백킹 스토어를 아예 할당하지 않고,
> 첫 항목이 추가될 때 할당한다.**
> **7장의 지연 초기화 기법의 사례이고, 여러 흔한 애플리케이션 테스트에서 GC 필요가 줄어
> 성능이 개선됐다.**
> **⚠️ 백킹 스토어 크기는 어차피 매 접근마다 검사해야 했으므로, 할당됐는지 검사하는 데 성능
> 페널티가 없었다**(다만 초기 백킹 스토어 생성 시간이 객체 생성 시점에서 첫 데이터 삽입
> 시점으로 옮겨졌다).

**`HashMap` vs `ConcurrentHashMap` 메모리**

| 객체 | 크기 |
|---|---|
| **Java 7 이전 `ConcurrentHashMap`(빈/희소)** | **1 KB 초과** (작은 크기를 줘도) |
| **Java 7 `ConcurrentHashMap`** | **208 바이트** |
| 빈 `HashMap`(크기 미지정) | 128 바이트 |
| `HashMap`(크기 1) | 72 바이트 |

> **작은 맵이 많은 애플리케이션에서는 이 크기 차이가 여전히 중요할 수 있지만, Java 7의 최적화가
> 그 차이를 훨씬 덜 유의미하게 만들었다.**
> **메모리가 중요하고 맵 수가 많은 애플리케이션에서 `ConcurrentHashMap` 을 피하라는 기존
> 성능 권고(저자 본인의 것 포함)가 있다.** 그 권고들은 **(경합 시) 더 빠른 맵 접근과, 더 큰 맵이
> 유발하는 GC 압박 증가의 트레이드오프**에 기반한다.
> **그 트레이드오프는 여전히 유효하지만 이제 균형이 `ConcurrentHashMap` 을 쓰는 쪽으로 훨씬 기울었다.**

## 9. AggressiveOpts

```
-XX:+AggressiveOpts   # 기본 false
```
> **목적은 시험적으로 최적화를 도입하는 것이다.** 시간이 지나면 이 플래그가 켜는 최적화가
> JVM의 기본 설정이 될 것으로 기대할 수 있다. **Java 6에서 실험된 많은 것이 Java 7u4에서
> 기본이 됐다. JDK 릴리스마다 이 플래그를 재테스트해서 여전히 긍정적인지 봐야 한다.**

**대체 구현**: `java.math`(`BigDecimal`, `BigInteger`, `MutableBigDecimal`),
`java.text`(`DecimalFormat`, `DigitalList`, `NumberFormat`),
`java.util`(`HashMap`, `LinkedHashMap`, `TreeMap`).
**기능적으로 같지만 구현이 더 효율적이다. Java 8에서는 제거됐다** — 기본 클래스에 통합됐거나
다른 방식으로 개선됐다.

> **⚠️ 왜 Java 7에서 플래그로만 켜지나 — 애플리케이션 코드의 미묘한 버그를 유발할 수 있기 때문이다.**
> **예: 공격적 `HashMap` 구현의 이터레이터가 키를 표준 구현과 다른 순서로 반환한다.**
> **애플리케이션은 애초에 이 이터레이터의 순서에 의존해서는 안 되지만, 많은 애플리케이션이
> 그 실수를 저질렀다.** 호환성 이유로 더 효율적인 구현이 원래 구현을 덮어쓰지 않았다.
>
> **Java 8이 이 클래스들을 제거하므로, 그것들이 보존하던 버그 호환성이 업그레이드 시 깨질 수
> 있다 — 애초에 더 나은 코드를 쓰라는 표시다.**

**함께 켜지는 기타 플래그**
- `AutoFill` (더 나은 루프 최적화), `DoEscapeAnalysis` — **둘 다 JDK 7u4+ 기본**
- **`AutoBoxCacheMax` 를 기본 128에서 20,000으로** — 더 많은 값을 오토박싱해 특정 애플리케이션
  성능이 약간 개선된다(**메모리를 약간 더 쓰는 대가로**)
- **`BiasedLockingStartupDelay` 를 2,000에서 500으로** — 편향 락이 더 일찍 시작된다
- **`OptimizeStringConcat`** — JIT가 **`StringBuilder` 객체 생성 자체를 최적화로 없앨 수 있다.**
  JDK 7u4부터 기본 true

## 10. 람다와 익명 클래스 (Java 8)

**성능은 사실상 같다.**

| 구현 | 시간 (µs) |
|---|---|
| 익명 클래스 | 87.2 |
| 람다 | 87.9 |

> **숫자는 늘 인상적으로 공식적으로 보이지만, 여기서 두 구현의 성능이 기본적으로 동등하다는 것
> 외에는 아무것도 결론지을 수 없다.** 테스트의 무작위 변동 때문이기도 하고,
> **이 호출들이 `System.nanoTime()` 으로 측정됐기 때문**이기도 하다.
> **타이밍이 그 수준에서 믿을 만큼 정확하지 않다.**

> **흥미로운 점**: 익명 클래스를 쓰는 코드는 **메서드 호출마다 새 객체를 만든다.**
> 메서드가 많이 불리면(벤치마크에서는 당연히 그래야 한다) **그 익명 클래스의 인스턴스가 빠르게
> 만들어지고 버려진다.**
> **5장에서 봤듯 그런 사용은 성능에 영향이 아주 작다.** 할당(과 더 중요하게는 초기화)에 아주 작은
> 비용이 있고, **빨리 버려지므로 GC를 실제로 느리게 하지 않는다.**
>
> **람다의 전형적 사용은 루프 반복마다 새 객체를 만들지 않는다** — 어떤 코너 케이스가 람다 쪽에
> 유리할 수 있는 지점이다. **그래도 그 차이가 중요한 마이크로벤치마크조차 구성하기 어렵다.**

### ⚠️ 예외 — 클래스로딩

> **람다 코드가 익명 클래스 생성의 문법 설탕이라고 결론짓고 싶어진다**(특히 장기적으로 성능이
> 같으니까). **하지만 그렇게 동작하지 않는다** —
> **람다 코드는 JDK 8의 특수 헬퍼 클래스를 통해 호출되는 정적 메서드를 만든다.
> 익명 클래스는 실제 자바 클래스다 — 별도 클래스 파일이 있고 클래스로더에서 로드된다.**

**매 `calc()` 실행이 새 클래스로더에서 수행되게 하면:**

| 구현 | 시간 (µs) |
|---|---|
| 익명 클래스 | **267** |
| **람다** | **181** |

> **⚠️ 이 수치들에 대한 한 가지**: 컴파일을 위해 적절한 워밍업 후 측정됐다.
> **그런데 워밍업 동안 다른 일도 일어난다 — 클래스 파일이 디스크에서 처음 읽힌다.
> OS가 그 파일들을 메모리(OS 파일시스템 버퍼)에 유지한다.**
> **그래서 코드의 맨 첫 실행은 훨씬 오래 걸린다.** 이후 호출은 여전히 OS를 부르지만 파일이
> 메모리에 있어 빨리 반환된다.
> **그러므로 익명 클래스 구현의 결과는 실제 디스크 읽기를 포함하지 않아 그렇지 않았을 때보다
> 좋게 나온 것이다.**

> **결론**: **람다냐 익명 클래스냐는 성능 차이가 없으므로 프로그래밍 편의로 정해야 한다.
> 람다는 클래스로 구현되지 않으므로, 클래스로딩 동작이 중요한 환경에서만 예외적으로 약간 빠르다.**

## 11. 스트림과 필터 성능 (Java 8)

### 지연 순회 (Lazy Traversal)

```java
Optional<String> t = al.stream()
    .filter(symbol -> symbol.charAt(0) != 'A')
    .filter(symbol -> symbol.charAt(1) != 'A')
    .filter(symbol -> symbol.charAt(2) != 'A')
    .filter(symbol -> symbol.charAt(3) != 'A')
    .findFirst();
```

> **`filter()` 는 사실 포인터를 설정하는 것 외에 아무것도 하지 않는다.**
> **`findFirst()` 가 호출될 때까지 어떤 데이터 처리도 수행되지 않는다 — 'A'와 비교하는 일이
> 아직 하나도 없었다.**
>
> **대신 `findFirst()` 가 이전 스트림(필터 4가 반환한 것)에게 원소를 요청한다.** 그 스트림에는
> 아직 원소가 없으므로 필터 3의 스트림에게 콜백하고, 이런 식으로 이어진다.
> **필터 1이 리스트에서 첫 원소를 가져와 첫 글자가 'A'인지 검사한다.** 아니면 콜백을 완료하고
> 그 원소를 하류로 반환한다. 맞으면 일치하는 원소를 찾을 때까지(또는 배열이 소진될 때까지)
> 계속 순회한다. **필터 2도 비슷하게 동작한다.**

**즉시(eager) 대안과의 비교 — 456,976개 네 글자 심볼, 알파벳순 정렬**

| 구현 | 시간 |
|---|---|
| **Filter / `findFirst`** | **0.359초** |
| **Iterator / `findFirst`** | **48.706초** |

> **즉시 구현이 덜 효율적인 이유 두 가지.**
> **① `ArrayList` 의 임시 인스턴스를 많이 만들어야 한다.**
> **② 지연 구현에서는 `findFirst()` 가 원소를 얻는 즉시 처리가 멈출 수 있다** — 필터를 실제로
> 통과해야 하는 항목이 부분집합뿐이라는 뜻이다.
> **즉시 구현은 마지막 리스트가 만들어질 때까지 전체 리스트를 여러 번 처리해야 한다.**
>
> **즉시 구현은 `BBBB` 를 만나기 전 18,278개만 처리하고 멈출 수 있는데도, 이터레이터가 그 답을
> 찾는 데 두 자릿수 더 오래 걸린다.**

### 전체 데이터를 처리해야 한다면?

| 구현 | 시간 |
|---|---|
| **여러 필터 (4개)** | **18.0초** |
| **단일 필터** | **6.5초** |
| 이터레이터 / count | 6.8초 |

> **필터가 이터레이터보다 훨씬 빠를 수 있는 한 이유는 단순히 알고리즘적 최적화 기회를 활용할 수
> 있기 때문이다 — 지연 필터 구현은 필요한 일을 다 하면 언제든 처리를 끝낼 수 있어 더 적은
> 데이터를 처리한다.**
>
> **전체를 처리하는 경우에도 단일 필터가 이터레이터보다 약간 빠르다.**
> **⚠️ 다만 여러 필터에는 오버헤드가 있다 — 좋은 필터를 쓰도록 하라.**

## 이 장을 우리 랩에 비춰 보면

**이 장은 우리 랩의 `jvm`·`concurrency` 분류와 가장 많이 겹친다.**

| 이 장의 내용 | 우리 랩에서의 대응 |
|---|---|
| **버퍼링 안 한 I/O가 6배 느리다** | 3장에서 본 `iostat` 진단과 이어진다. **검증 케이스 없음 — 좋은 후보** |
| **클래스로더 병렬성 (JDK 6에서 7배 차이)** | **9장 `jstack` 사례(SAX 파서 41스레드)와 같은 이야기.** 케이스 없음 |
| `ThreadLocalRandom` | **`CON-04`**(스레드 로컬), 7장 |
| **`SecureRandom` 성능이 무작위다** | **`SEC-04`**(bcrypt work factor)와 이어지는 보안-성능 트레이드오프 |
| **예외는 생각보다 안 비싸다 / 깊은 스택이 비싸다** | 검증 케이스 **없음** — 381ms vs 10,673ms 는 좋은 후보 |
| **JVM이 시스템 예외를 재사용해 스택을 없앤다** | **`OBS-02`**(traceId 전부 0, 예외 없음)와 사고방식이 이어진다 |
| **문자열 결합은 한 줄이면 괜찮다** | **`JVM-02`**(리터럴 vs `new String`)가 인접 주제 |
| **컬렉션 크기 지정 / 희소 컬렉션 낭비** | **`JVM-05`**(record 방어적 복사), 7장 객체 크기 |
| **`ConcurrentHashMap` 208바이트 (Java 7)** | **`CON-01`**(`ConcurrentHashMap.merge` 원자성) |
| **CAS 13ns / synchronized 23ns / 비동기화 7.8ns** | **`CON-02`** — 우리 케이스가 정확히 이 비교다 |
| **로깅에 `isLoggable()` 검사** | **`OBS-*`** 와 이어진다. 케이스 없음 |
| 람다 vs 익명 클래스는 성능이 같다 | 케이스 없음 |
| **스트림 지연 순회 (0.359초 vs 48.706초)** | 케이스 없음 — **수치가 극적인 후보** |

> **`CON-02` 는 이 장의 표(CAS 13ns / synchronized 23ns)를 우리 환경에서 다시 재는 케이스다.**
> 그리고 **저자가 "이 절대 수치는 테스트를 돌린 머신이 완전히 결정한다. 더 현실적인 측정을 하려면
> 목표 환경과 같은 하드웨어에서 돌려야 한다"** 고 못 박은 것이,
> 우리 리포트가 **"자릿수만 신뢰하라"** 고 고지하는 근거와 정확히 같다.

> - **반복적으로 생성되는 예외는 스레드 스택을 제공하는 데 시간을 쓸 필요가 없다**

> - **클래스로더가 동기화 락 때문에 병렬로 돌 수 없었다**
>
> **이 지속적인 점진 개선 과정이 바로 자바 성능 튜닝의 전부다.**

> 이해하는 것까지 — **이 책의 도구와 프로세스가 당신 자신의 코드에서도 비슷한 지속적 개선을
> 제공할 수 있게 해 줄 것이다.**
