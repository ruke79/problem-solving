# 4장. JIT 컴파일러 다루기 (Working with the JIT Compiler)

> **JIT 컴파일러는 JVM의 심장이다.** JVM에서 성능에 이보다 큰 영향을 주는 것은 없다.
> 다행히 대부분의 상황에서 기본 몇 가지 외에 튜닝할 것이 거의 없다.

---

## 1부. JIT 컴파일러 개요

### 컴파일 언어 vs 인터프리터 언어

CPU는 어셈블리/바이너리라는 비교적 적은 수의 명령만 실행할 수 있다. 모든 프로그램은 이 명령으로
번역돼야 한다.

**컴파일 언어(C++, Fortran)** — 정적 컴파일러가 특정 CPU를 겨냥한 바이너리를 만든다.
AMD와 Intel은 기본 명령 집합을 공유하고, 새 CPU는 대개 이전 버전의 명령을 실행할 수 있다.
**반대는 성립하지 않는다** — 새 CPU가 도입한 명령은 옛 CPU에서 돌지 않는다.

**인터프리터 언어(PHP, Perl)** — 인터프리터만 있으면 어느 CPU에서든 같은 소스가 돈다. 실행되는
줄마다 바이너리로 번역한다.

**핵심 트레이드오프**: 인터프리터는 **이식성**이 있지만 느리다. 루프를 생각해 보면, 인터프리터는
루프 안에서 실행될 때마다 같은 줄을 **다시 번역**한다.

좋은 컴파일러가 고려하는 요소의 예 — **바이너리 문장의 순서**. 어셈블리 명령이 다 같은 시간을
쓰지 않는다. 레지스터 두 개를 더하는 건 1사이클, 주 메모리에서 값을 가져오는 건 여러 사이클이다.
**좋은 컴파일러는 데이터 로드 명령을 먼저 내고, 다른 명령 몇 개를 실행한 뒤, 데이터가 준비됐을 때
덧셈을 실행하는 바이너리를 만든다.** 한 번에 한 줄만 보는 인터프리터는 그런 코드를 만들 정보가 없다.

> 인터프리터의 이식성에도 한계가 있다. SPARC용 바이너리가 Intel에서 안 도는 건 당연하고,
> **Sandy Bridge의 최신 AVX 명령을 쓰는 바이너리는 옛 Intel 프로세서에서도 안 돈다.**
> 그래서 상용 소프트웨어는 꽤 오래된 프로세서 버전에 맞춰 컴파일하고 최신 명령을 안 쓰는 게 흔하다.

### 자바의 중간 지대

자바 애플리케이션은 **컴파일된다.** 다만 특정 CPU용 바이너리가 아니라 **이상화된 어셈블리 언어
(자바 바이트코드)** 로 컴파일된다. 이 바이트코드를 `java` 바이너리가 실행한다. 이것이 인터프리터
언어의 플랫폼 독립성을 준다. 그리고 이상화된 바이너리를 실행하는 것이므로, **실행하면서
플랫폼 바이너리로 컴파일할 수 있다.** 이 컴파일이 프로그램 실행 중에 일어나므로 **"just in time"** 이다.

### 핫스팟(Hot Spot) 컴파일

**전형적인 프로그램에서는 코드의 작은 부분집합만 자주 실행되고, 성능은 주로 그 구간이 얼마나
빨리 실행되는가에 달려 있다.** 이 임계 구간이 **핫스팟**이고, 많이 실행될수록 "더 뜨겁다"고 한다.

JVM은 코드를 즉시 컴파일하지 **않는다.** 두 가지 이유가 있다.

**① 한 번만 실행될 코드라면 컴파일은 낭비다.** 컴파일해서 (한 번) 실행하는 것보다 바이트코드를
해석하는 게 빠르다. 반대로 자주 불리는 메서드나 반복이 많은 루프라면 컴파일 비용을 여러 번의
빠른 실행이 상쇄한다. **인터프리터 코드를 먼저 실행하는 이유가 여기 있다 — 컴파일러가 어느
메서드가 컴파일할 만큼 자주 불리는지 알아내야 하니까.**

**② 최적화 때문이다.** 특정 메서드나 루프를 많이 실행할수록 그 코드에 대한 정보가 쌓인다.

**`equals()` 예시** — 인터프리터가 `b = obj1.equals(obj2)` 를 만나면 어느 `equals()` 를 실행할지
알기 위해 `obj1` 의 타입을 **조회**해야 한다. 이 동적 조회는 시간이 걸린다.
시간이 지나 JVM이 "이 문장이 실행될 때마다 `obj1` 은 `java.lang.String` 이더라" 하고 관찰하면,
**`String.equals()` 를 직접 호출하는 컴파일 코드**를 만들 수 있다. 컴파일됐기 때문만이 아니라
**어느 메서드를 부를지 조회하는 단계를 건너뛰기 때문에** 빨라진다.

물론 그렇게 단순하지는 않다 — 다음번에 `obj1` 이 `String` 이 아닐 수 있으므로 그 가능성도
처리하는 코드를 만들어야 한다. **하지만 이런 최적화는 코드를 한동안 실행하며 관찰한 뒤에야
가능하다. 이것이 JIT 컴파일러가 기다리는 두 번째 이유다.**

> **레지스터와 주 메모리**
> ```java
> public void calculateSum(int n) {
>     for (int i = 0; i < n; i++) sum += i;   // sum 은 인스턴스 변수
> }
> ```
> 언젠가는 `sum` 이 주 메모리에 있어야 한다. 하지만 주 메모리 접근은 여러 사이클이 드는 비싼
> 연산이다. **반복마다 주 메모리에서 읽고 쓰면 성능이 처참해진다.** 그래서 컴파일러는
> 레지스터에 초깃값을 싣고, 레지스터로 루프를 돌리고, **정해지지 않은 어느 시점에** 최종 결과를
> 주 메모리에 저장한다.
>
> **이 최적화가 스레드 동기화의 의미(9장)를 애플리케이션 동작에 결정적으로 만든다.**
> 한 스레드는 다른 스레드의 레지스터에 있는 값을 볼 수 없다. **동기화는 레지스터가 정확히 언제
> 주 메모리에 저장되어 다른 스레드가 볼 수 있게 되는지를 알게 해 준다.**
> **이스케이프 분석**이 켜져 있으면 레지스터 사용은 상당히 공격적이 된다.

## 2부. 기본 튜닝 — client냐 server냐 (아니면 둘 다)

두 컴파일러가 있고, **어느 쪽을 쓸지 고르는 것이 대개 필요한 컴파일러 튜닝의 전부다.**
자바를 설치하기 전부터 고려해야 한다 — 자바 바이너리마다 다른 컴파일러를 담고 있으니까.

- **client (C1)**, **server (C2)** — JVM 개발자들은 C1/C2로 부른다
- 이름이 하드웨어를 암시하지만 **사실 그렇지 않다.** 특히 15년이 지난 오늘날 "클라이언트"
  노트북에도 CPU 4~8개와 8GB 메모리가 있다(자바 개발 당시 중급 서버보다 강력하다)

> **컴파일러 플래그는 형식이 다르다.** 대부분의 자바 플래그와 달리 `-XX` 를 안 쓴다 —
> `-client`, `-server`, `-d64` 처럼 단순한 단어다.
> 예외가 계층형 컴파일 `-XX:+TieredCompilation` 인데, **이건 server 컴파일러를 전제한다.**
> 그래서 `java -client -XX:+TieredCompilation ...` 은 **조용히 계층형 컴파일을 끈다.**

### 근본적 차이 — 컴파일 공격성

**client는 server보다 일찍 컴파일을 시작한다.** 그래서 실행 초반에는 client가 빠르다(그만큼
더 많이 컴파일해 뒀으니까).

**엔지니어링 트레이드오프**는 server가 기다리는 동안 얻는 **지식**이다. 그 지식으로 더 나은
최적화를 한다. **최종적으로 server가 만든 코드가 더 빠르다.** 어느 쪽이 이득인지는
**프로그램이 얼마나 오래 도는가**와 **시작 시간이 얼마나 중요한가**에 달렸다.

### 계층형 컴파일 (Tiered Compilation)

"client로 시작해서 뜨거워지면 server로 바꾸면 되지 않나?" — 그것이 계층형 컴파일이다.

- Java 7 초기 릴리스의 실험적 버전은 **잘 작동하지 않았다**(두 컴파일러의 아키텍처 차이 때문)
- **Java 7u4부터 대부분 해결**되어 대개 최고 성능을 낸다
- **Java 7에서는 기본이 아니다** — 특히 **코드 캐시 크기를 넘기기 쉽다**(뒤에서 다룸)
- **Java 8에서는 기본 활성**

### 시작 시간 최적화

| 애플리케이션 | -client | -server | +TieredCompilation |
|---|---|---|---|
| HelloWorld | 0.08 | 0.08 | 0.08 |
| NetBeans | **2.83** | 3.92 | 3.07 |
| BigApp | **51.5** | 54.0 | 52.0 |

- **HelloWorld** — 어느 쪽도 이점이 없다. 컴파일러가 기여할 만큼 코드가 안 돈다
- **NetBeans** — 시작 시 클래스 1만 개를 로드한다. **server가 38.5% 느리고, 1초 차이는 확실히
  느껴진다.** 계층형은 8%만 느려서 사소한 차이다
- **BigApp** — 클래스 2만 개 이상. 앱 서버이므로 당연히 server를 써야 한다.
  **여기서 1장의 교훈이 나온다 — 문제가 항상 JVM인 건 아니다.** 디스크에서 읽어야 할 JAR 파일이
  너무 많아서 그게 성능의 관문이다(아니었으면 client의 이점이 더 컸을 것이다)

> **시작 시간이 중요한가?**
> GUI 프로그램도 전체 성능이 시작 성능보다 중요하다는 강한 주장이 가능하다. server가 GUI 코드를
> 최적화하면 UI가 약간 더 반응적이 되지만 사용자는 알아채기 어렵다. **그런데 프로그램이 다른
> 계산을 많이 한다면 그건 중요하다.** NetBeans의 광범위한 코드 리팩터링은 server에서 더 빠르다.
>
> 벤더가 기본값을 정하는데, **시작 시간은 리뷰어가 가장 먼저 언급하는 것이라 대개 시작 시간에
> 맞춰 튜닝돼 있다.** 당신의 경험이 다르다면 주저 말고 server나 계층형으로 바꿔라.

### 배치 작업 최적화

| 주식 수 | -client | -server | +Tiered |
|---|---|---|---|
| 1 | **0.142** | 0.176 | 0.165 |
| 10 | **0.211** | 0.348 | 0.226 |
| 100 | **0.454** | 0.674 | 0.472 |
| 1,000 | 2.556 | 2.158 | **1.910** |
| 10,000 | 23.78 | 14.03 | **13.56** |

- 1~100 종목: **client 승** (시작이 빠르니까)
- 그 이상: **server, 특히 계층형 승**
- **계층형은 항상 순수 server보다 약간 낫다.** 이론적으로는 핫스팟을 다 컴파일하고 나면 server가
  같거나 나아야 하는데, **어느 애플리케이션에나 드물게 실행되는 작은 구간이 있다.**
  최선이 아니더라도 그걸 컴파일하는 편이 인터프리터로 실행하는 것보다 낫다. 게다가 뒤에서
  보겠지만 **server는 영원히 돌아도 모든 코드를 컴파일하지 않을 가능성이 높다.**

### 장기 실행 애플리케이션

| 워밍업 | -client | -server | +Tiered |
|---|---|---|---|
| 0초 | 15.87 | 23.72 | **24.23** |
| 60초 | 16.00 | 23.73 | **24.26** |
| 300초 | 16.85 | 24.42 | **24.43** |

> **장기 실행 애플리케이션에는 항상 server를, 되도록 계층형 컴파일과 함께 써라.**

## 3부. 자바 바이너리와 컴파일러 버전

JIT 컴파일러는 **세 가지 버전**이 있다: 32비트 client(`-client`), 32비트 server(`-server`),
64비트 server(`-d64`).

> **32비트냐 64비트냐**
> 32비트 OS면 32비트 JVM만 가능하다. **64비트 OS라고 반드시 64비트 자바를 써야 하는 건 아니다.**
>
> **힙이 약 3GB 미만이면 32비트 자바가 더 빠르고 메모리를 덜 쓴다.** JVM 내부 메모리 참조가
> 32비트뿐이고, 64비트 CPU에서도 32비트 참조 조작이 더 싸며, 메모리도 덜 쓴다.
> 8장의 **압축 oops(compressed ordinary object pointers)** 가 64비트 JVM 안에서도 32비트 주소를
> 쓰게 해 주지만, **그래도 64비트 JVM의 풋프린트가 더 크다** — 네이티브 코드는 여전히 64비트 주소를 쓴다.
>
> **32비트의 단점**: 전체 프로세스 크기가 4GB 미만이어야 한다(일부 Windows는 3GB, 일부 구형
> Linux는 3.5GB). 여기에 힙·permgen·JVM의 네이티브 코드와 네이티브 메모리가 다 포함된다.
> `long`·`double` 을 많이 쓰는 프로그램은 CPU의 64비트 레지스터를 못 써서 느려지지만 아주 예외적이다.
>
> **32비트 주소 공간에 들어가는 프로그램은 32비트 JVM에서 5~20% 빠르다.** 이 장의 주식 배치
> 프로그램은 저자 데스크톱에서 **20% 빨랐다.**

**설치가 복잡하다.** 대부분의 플랫폼에서 32/64비트가 따로 설치되어 별도 경로로 참조해야 한다.
**Solaris는 예외로 64비트 설치가 32비트 위에 겹쳐져서** 세 컴파일러 모두 같은 경로에서 쓸 수 있다.
(HotSpot 개발자들이 Solaris를 주 개발 시스템으로 쓰다 보니 문서와 논의가 종종 혼란스럽다.)

**호환성 때문에 인자가 엄격히 지켜지지 않는다.** 64비트 JVM에 `-client` 를 줘도 64비트 server가
쓰인다. 32비트 JVM에 `-d64` 를 주면 에러가 난다.

| 설치 | -client | -server | -d64 |
|---|---|---|---|
| Linux 32비트 | 32 client | 32 server | 에러 |
| Linux 64비트 | **64 server** | 64 server | 64 server |
| Mac OS X | **64 server** | 64 server | 64 server |
| Solaris 32비트 | 32 client | 32 server | 에러 |
| Solaris 64비트 | 32 client | 32 server | 64 server |
| Windows 32비트 | 32 client | 32 server | 에러 |
| Windows 64비트 | **64 server** | 64 server | 64 server |

**인자를 안 주면?** JVM이 머신을 보고 런타임에 결정한다 — OS와 CPU 개수 조합으로.

| OS | 기본 컴파일러 |
|---|---|
| Windows 32비트, CPU 수 무관 | `-client` |
| Windows 64비트 | `-server` |
| MacOS | `-server` |
| Linux/Solaris 32비트, CPU 1개 | `-client` |
| Linux/Solaris 32비트, CPU 2개 이상 | `-server` |
| Linux 64비트 | `-server` |
| Solaris 겹침 설치, CPU 1개 | `-client` |
| Solaris 겹침 설치, CPU 2개 이상 | `-server` (32비트 모드) |

**기본값 확인 방법**: `java -version` 의 마지막 줄이 실제로 쓰일 컴파일러를 보여 준다.
지정한 컴파일러를 지원하지 않아도 **실제로 쓰이는 것**이 표시된다.

> 이 기본값들은 "32비트 Windows에서는 시작 시간이 항상 가장 중요하고, Unix 계열은 장기 실행
> 성능에 관심이 많다"는 관념에 기반한다. **예외는 늘 있다** — 현대 Windows도 32비트 모드로
> 강력한 서버를 돌릴 수 있고, Unix 머신에서도 앱 서버의 간단한 자바 관리 명령은 client가 낫다.

## 4부. 중급 튜닝

### 코드 캐시 튜닝

JVM은 컴파일한 어셈블리 명령을 **코드 캐시**에 담는다. **크기가 고정이고, 다 차면 더 이상
컴파일할 수 없다.**

**위험**: 일부 핫스팟만 컴파일되고 나머지는 **아주 느린 인터프리터 코드로 실행된다.**

**client나 계층형 컴파일에서 더 자주 문제가 된다.** 순수 server는 컴파일 대상 클래스가 캐시를 채울
가능성이 낮지만(대개 소수만 컴파일), **client는 대상이 훨씬 많다.**

경고 메시지:
```
Java HotSpot(TM) 64-Bit Server VM warning: CodeCache is full. Compiler has been disabled.
Java HotSpot(TM) 64-Bit Server VM warning: Try increasing the code cache size using -XX:ReservedCodeCacheSize=
```
**놓치기 쉽고, 일부 Java 7 버전은 계층형 컴파일에서 이 메시지를 제대로 출력하지 않는다.**

| JVM 종류 | 기본 코드 캐시 |
|---|---|
| 32비트 client, Java 8 | 32 MB |
| 32비트 server + 계층형, Java 8 | **240 MB** |
| 64비트 server + 계층형, Java 8 | **240 MB** |
| 32비트 client, Java 7 | 32 MB |
| 32비트 server, Java 7 | 32 MB |
| 64비트 server, Java 7 | 48 MB |
| 64비트 server + 계층형, Java 7 | **96 MB** |

**Java 7의 계층형 기본값은 부족한 경우가 많다.**

**얼마나 필요한지 알아낼 좋은 방법이 없다.** 늘려야 할 때는 감으로 하는 작업이고, **보통 기본값의
2배나 4배**로 잡는다.

```
-XX:ReservedCodeCacheSize=N   # 최대 크기 (이것만 설정하면 대개 충분)
-XX:InitialCodeCacheSize=N    # 초기 크기 (Intel에서 client 160KB, server 2,496KB)
```
크기 조정은 백그라운드에서 일어나고 성능에 별 영향이 없다.

**아주 크게 잡으면 단점이 있나?** 대상 머신의 자원에 달렸다. 1GB로 지정하면 JVM이 **네이티브
메모리 1GB를 예약**한다. 필요할 때까지 **할당**되지는 않지만 **예약**은 되므로 가상 메모리가
충분해야 한다. **32비트 JVM이면 전체 프로세스가 4GB를 못 넘는다**(힙 + JVM 자체 코드 + 네이티브
라이브러리 + 스레드 스택 + 애플리케이션 네이티브 메모리 + 코드 캐시).

> **64비트 머신에서는 값을 크게 잡아도 실질적 영향이 거의 없다.** 프로세스 공간이 모자라지 않고
> 추가 예약은 대개 OS가 받아 준다.

모니터링은 `jconsole` 의 Memory 패널 → Memory Pool Code Cache 차트.

### 컴파일 임계치 (Compilation Thresholds)

컴파일은 **두 개의 카운터**에 기반한다.
1. **메서드가 호출된 횟수**
2. **메서드 안의 루프가 백브랜치(branch back)한 횟수** — 루프가 끝까지 갔거나 `continue` 같은
   분기문을 실행한 횟수

JVM이 메서드를 실행할 때 **두 카운터의 합**을 보고 컴파일 대상인지 정한다. 대상이면 큐에 넣는다.
이것이 **표준 컴파일(standard compilation)** 이다.

**아주 긴 루프나 끝나지 않는 루프**라면? 메서드 호출을 기다릴 수 없다. 그래서 루프가 한 번 돌 때마다
백브랜치 카운터를 올리고 검사한다. 임계치를 넘으면 **메서드 전체가 아니라 루프가** 컴파일 대상이 된다.

이것이 **OSR(On-Stack Replacement)** 이다. **루프를 컴파일하는 것만으로는 부족하고, 루프가 아직
돌고 있는 동안 컴파일된 버전을 실행하기 시작할 수 있어야 하기 때문**이다. 컴파일이 끝나면 JVM이
스택 위의 코드를 교체하고, **다음 반복부터 훨씬 빠른 컴파일 코드가 실행된다.**

```
-XX:CompileThreshold=N   # client 기본 1,500 / server 기본 10,000
```

> **OSR 컴파일 임계치 바꾸기 (거의 하지 않는다)**
> ```
> OSR trigger = CompileThreshold × ((OnStackReplacePercentage − InterpreterProfilePercentage) / 100)
> ```
> `InterpreterProfilePercentage` 기본 33. client의 `OnStackReplacePercentage` 는 933이라
> **백브랜치 카운터가 13,500**에 도달해야 OSR이 시작된다. server는 140이라 **10,700**.
> **OSR은 벤치마크(특히 마이크로벤치마크)에서는 자주 트리거되지만 실제 애플리케이션 코드에서는
> 덜 트리거된다.**

#### 왜 임계치를 낮추라는 권고가 많은가

**결정적 사실 — 카운터는 시간이 지나면 감소한다.**

**세이프포인트에 도달할 때마다** 각 카운터 값이 줄어든다. 실질적으로 **카운터는 메서드/루프의
"최근" 뜨거움을 나타내는 상대적 척도**다.

**부작용**: **어느 정도 자주 실행되는 코드가 영원히 컴파일되지 않을 수 있다.** 프로그램이 영원히
돌아도. 이런 메서드를 **미지근한(lukewarm)** 메서드라고 부른다. 임계치를 낮추는 것이 이득인
경우가 여기다. **그리고 이것이 계층형 컴파일이 대개 순수 server보다 약간 빠른 또 다른 이유다.**

벤더가 벤치마크에서 임계치를 8,000으로 낮추는 두 가지 이유:
1. 워밍업 시간을 조금 절약한다
2. **그렇지 않으면 영원히 컴파일되지 않을 server 메서드를 컴파일할 수 있다**

### 컴파일 과정 들여다보기

**튜닝이 아니라 가시성**을 주는 플래그들이다.

```
-XX:+PrintCompilation   # 기본 false
```

출력 형식(Java 7부터 표준화):
```
timestamp compilation_id attributes (tiered_level) method_name size deopt
```

- **timestamp** — 컴파일이 **끝난** 시각 (JVM 시작 = 0 기준)
- **compilation_id** — 내부 태스크 ID. 대개 단조 증가하지만 **순서가 어긋날 수 있다.**
  컴파일 스레드끼리 상대적으로 빠르거나 느린 것뿐이고, **특정 태스크가 유난히 느렸다고 결론짓지
  마라**(다만 **OSR은 느리고 순서가 어긋나 보이는 일이 잦다**)
- **attributes** — 5글자
  - `%` : OSR 컴파일
  - `s` : 동기화된 메서드
  - `!` : 예외 핸들러가 있는 메서드
  - `b` : 블로킹 모드 컴파일 (현재 버전에서는 기본으로 절대 안 나온다)
  - `n` : 네이티브 메서드 래퍼용 컴파일
- **tiered_level** — 계층형이 아니면 비어 있다
- **method_name** — `ClassName::method`
- **size** — **자바 바이트코드의 크기**(컴파일된 코드 크기가 아니다). **그래서 코드 캐시 크기를
  예측하는 데는 쓸 수 없다**
- **deopt** — `made not entrant` / `made zombie`

> **`jstat` 으로 컴파일 들여다보기**
> `PrintCompilation` 없이 시작한 프로그램에도 제한적 가시성을 얻을 수 있다.
> ```
> % jstat -compiler 5003
> Compiled Failed Invalid   Time   FailedType FailedMethod
>      206      0       0     1.97          0
> ```
> **컴파일에 실패한 메서드 수와 마지막 실패 메서드 이름**도 나온다. 프로파일에서 "이 메서드가
> 컴파일이 안 돼서 느린 게 아닐까" 싶으면 **가설을 쉽게 검증**할 수 있다.
> ```
> % jstat -printcompilation 5003 1000    # 1초마다 반복
> ```

**`COMPILE SKIPPED` 메시지** — 컴파일에 문제가 생겼다는 뜻이다. 예상되는 경우는 두 가지:
- **Code cache filled** — `ReservedCodeCacheSize` 를 늘려야 한다
- **Concurrent classloading** — 컴파일 중에 클래스가 변경됐다. **JVM이 나중에 다시 컴파일하므로
  로그 뒷부분에 재컴파일이 보여야 한다**

캐시가 찬 경우를 빼면 **재시도돼야 정상**이다. 안 되면 컴파일을 막는 에러가 있는 것이고,
**대개 컴파일러 버그다.** 통상의 해법은 **컴파일러가 다룰 수 있게 코드를 더 단순하게 리팩터링**하는 것이다.

**실제 출력 예시 해석:**
```
  28015  850             net.sdo.StockPrice::getClosingPrice (5 bytes)
  28179  905  s          net.sdo.StockPriceHistoryImpl::process (248 bytes)
  28226   25 %           net.sdo.StockPriceHistoryImpl::<init> @ 48 (156 bytes)
 106805 1568   !         net.sdo.StockServlet::processRequest (197 bytes)
```
- 첫 주식 관련 메서드가 **앱 서버 시작 28초 뒤**, **849개 메서드가 먼저 컴파일된 뒤**에야 컴파일됐다.
  앱 서버 시작에 2초가 걸렸고 **나머지 26초는 요청을 기다리는 유휴 시간**이었다
- `process` 는 `s`(동기화), `processRequest` 는 `!`(예외 핸들러) — 코드와 일치한다
- 내부 클래스는 `outer$inner` 형태로 나온다
- **생성자 `<init>` 는 큰 루프를 담고 있어 OSR 컴파일 대상**이다. 컴파일 ID가 **25**인데
  900번대가 컴파일될 때에야 나타난다. **OSR의 전형이다 — 스택 교체는 설정이 어렵지만 그동안
  다른 컴파일은 계속된다**
- ⚠️ **`25 %` 를 25%로 읽고 나머지 75%를 궁금해하기 쉽다.** 숫자는 컴파일 ID이고 `%` 는 OSR 표시일 뿐이다

## 5부. 고급 튜닝

> 이 절의 값들은 바꿀 수 있지만 **바꿀 이유가 거의 없다.** 상당 부분 JVM 엔지니어가 JVM 동작을
> 진단하려고 만든 것이다.

### 컴파일 스레드

컴파일 큐는 **하나 이상의 백그라운드 스레드**가 처리한다. **컴파일은 비동기이고, 이건 좋은 일이다** —
컴파일되는 동안에도 프로그램이 계속 실행된다.

**큐는 엄격한 FIFO가 아니다.** 호출 카운터가 높은 메서드가 **우선순위**를 갖는다. 프로그램이 막
시작해 컴파일할 코드가 많을 때도 **가장 중요한 코드가 먼저 컴파일되게** 해 준다.
(이것도 컴파일 ID가 순서를 벗어나 보이는 이유다.)

- client: 컴파일 스레드 1개
- server: 2개
- **계층형: CPU 수의 이중 로그가 들어간 복잡한 식으로 결정**

| CPU 수 | C1 스레드 | C2 스레드 |
|---|---|---|
| 1 | 1 | 1 |
| 2 | 1 | 1 |
| 4 | 1 | 2 |
| 8 | 1 | 2 |
| 16 | 2 | 6 |
| 32 | 3 | 7 |
| 64 | 4 | 8 |
| 128 | 4 | 10 |

```
-XX:CICompilerCount=N   # 총 스레드 수. 계층형이면 1/3(최소 1)이 C1, 나머지(최소 1)가 C2
```

**언제 조정하나?**
- **단일 CPU 시스템** — 스레드 1개가 약간 유리할 수 있다. 주식 배치를 단일 CPU에서 컴파일 스레드
  1개로 제한하니 **초기 계산이 약 10% 빨랐다.** 다만 워밍업 기간에 한정된 이점이라 반복이
  늘수록 효과가 사라진다
- **계층형에서 JVM을 여러 개 동시에 돌릴 때** — 스레드 수가 시스템을 압도하기 쉽다. 줄이면
  전체 처리량이 개선될 수 있다(대신 워밍업이 길어진다)
- **여분 CPU가 많을 때** — 이론적으로 워밍업 중에 이득이지만 **현실에서는 얻기 극히 어렵다.**
  그만큼 CPU가 남는다면 **처음에 빨리 컴파일하는 것보다 실행 전체에서 CPU를 활용하는 무언가를
  하는 편이 훨씬 낫다**

```
-XX:+BackgroundCompilation   # 기본 true. false면 컴파일이 끝날 때까지 실행이 대기한다
-Xbatch                       # 백그라운드 컴파일을 끈다
```

### 인라이닝 (Inlining)

> **컴파일러가 하는 가장 중요한 최적화 중 하나.**

```java
Point p = getPoint();
p.setX(p.getX() * 2);
```
컴파일된 코드는 본질적으로 이렇게 실행된다:
```java
Point p = getPoint();
p.x = p.x * 2;
```

**자바 초기에는 이런 캡슐화가 메서드 호출 비용 때문에 성능상 나쁘다는 조언이 흔했다.**
지금은 JVM이 일상적으로 인라이닝한다.

```
-XX:-Inline   # 끌 수 있지만 절대 그러지 않는다 — 주식 배치 성능이 50% 넘게 떨어진다
```

**가시성이 거의 없다.** 소스에서 JVM을 빌드하면 디버그 버전에서 `-XX:+PrintInlining` 을 쓸 수
있지만, **최선은 프로파일을 보고 상단에 인라이닝됐어야 할 단순한 메서드가 있으면 플래그로
실험해 보는 것**이다.

**결정 기준은 뜨거움과 크기**다.
- 뜨거운지는 **내부 계산**으로 정하고 **튜닝 파라미터의 영향을 직접 받지 않는다**
- 자주 불려서 인라이닝 대상이면 → **바이트코드 325바이트 미만**일 때만 (`-XX:MaxFreqInlineSize=N`)
- 그렇지 않으면 → **35바이트 미만**일 때만 (`-XX:MaxInlineSize=N`)

> **`MaxInlineSize` 를 올리라는 권고에서 자주 간과되는 점**
> 35보다 크게 잡으면 메서드가 **처음 불릴 때** 인라이닝될 수 있다. 하지만 **자주 불리는
> 메서드라면**(성능이 훨씬 중요한 경우) **어차피 결국 인라이닝된다**(325바이트 미만이라면).
> 그러므로 순효과는 **워밍업 시간을 줄이는 것**이고, **장기 실행 애플리케이션에는 큰 영향이 없을
> 가능성이 높다.**

### 이스케이프 분석 (Escape Analysis)

```
-XX:+DoEscapeAnalysis   # 기본 true
```

```java
for (int i = 0; i < 100; i++) {
    Factorial factorial = new Factorial(i);
    list.add(factorial.getFactorial());
}
```

`factorial` 객체는 **루프 안에서만 참조되고 다른 코드가 접근할 수 없다.** 그래서 JVM은:
- `getFactorial()` 이 `synchronized` 라도 **동기화 락을 얻을 필요가 없다**
- 필드 `n` 을 메모리에 저장할 필요가 없다 — **레지스터에 유지**. 객체 참조도 레지스터에
- **실제 객체를 할당할 필요조차 없다** — 개별 필드만 추적하면 된다

> **요약**
> 1. 이스케이프 분석은 컴파일러가 하는 최적화 중 **가장 정교하다.** **마이크로벤치마크가
>    빗나가게 만드는 대표적 원인**이다.
> 2. **제대로 동기화되지 않은 코드에 "버그"를 도입하는 경우가 잦다.**
>
> 드물게 잘못 판단하는 경우가 있는데, 그러면 끄는 것이 더 빠르고 안정적일 수 있다.
> 하지만 **최선의 대응은 해당 코드를 단순화하는 것이다 — 단순한 코드가 더 잘 컴파일된다.**
> (그리고 그건 버그이므로 보고해야 한다.)

### 역최적화 (Deoptimization)

컴파일러가 이전 컴파일을 **되돌려야** 하는 것. 성능이 떨어진다 — 적어도 재컴파일될 때까지는.
두 가지가 있다: **not entrant** 와 **zombie**.

#### Not Entrant 코드

**원인 ①: 클래스/인터페이스 동작 때문**

`StockPriceHistory` 인터페이스에 구현이 둘 있다 — 기본(`StockPriceHistoryImpl`)과
로깅 추가(`StockPriceHistoryLogger`). URL의 `log` 파라미터로 갈린다.

`log` 없이 여러 번 호출하면 컴파일러는 `sph` 의 실제 타입이 `StockPriceHistoryImpl` 임을 보고
그 지식에 기반해 인라이닝과 최적화를 한다. 나중에 `?log=true` 로 호출하면 **그 가정이 거짓이 되고
이전 최적화가 무효가 된다.** → **역최적화 트랩**이 발생하고 이전 최적화가 버려진다.

```
 841113   25 %  net.sdo.StockPriceHistoryImpl::<init> @ -2 (156 bytes)  made not entrant
 841113  937  s net.sdo.StockPriceHistoryImpl::process (248 bytes)      made not entrant
1322722   25 %  net.sdo.StockPriceHistoryImpl::<init> @ -2 (156 bytes)  made zombie
```

> **역최적화는 성능상 나쁜 일처럼 들리지만 반드시 그렇지는 않다.**
> - 로깅 없는 경로만: **24.4 OPS**
> - 로깅 경로로 전환 후 다시 로깅 없는 경로로: 재컴파일 후 **여전히 24.4 OPS**
> - 두 경로를 **뒤섞어서** 컴파일러가 어느 쪽인지 가정할 수 없게 하면: **24.3 OPS**
>   (로깅 경로 단독이 24.1이므로 딱 평균값이다)
>
> **트랩을 처리하는 순간을 빼면 역최적화는 성능에 유의미한 영향을 주지 않았다.**

**원인 ②: 계층형 컴파일의 구현 방식**

계층형에서는 client가 컴파일한 뒤 server가 다시 컴파일한다. server 코드가 준비되면 **JVM이
client 코드를 not entrant로 표시하고 새 코드로 대체한다.** 그래서 계층형으로 돌리면
**컴파일 로그에 not entrant가 잔뜩 나온다. 당황하지 마라 — 이 "역최적화"는 사실 코드를 더 빠르게
만드는 중이다.**

**구분하는 법은 tier level을 보는 것이다.**
```
40915   84 %  3  ...::<init> @ 48 (156 bytes)        # 레벨 3 OSR
40923 3697    3  ...::<init> (156 bytes)             # 레벨 3 표준
41418   87 %  4  ...::<init> @ 48 (156 bytes)        # 레벨 4 OSR
41434   84 %  3  ...::<init> @ -2 (156 bytes) made not entrant   # 레벨 3 OSR 폐기
41458 3749    4  ...::<init> (156 bytes)             # 레벨 4 표준
41469 3697    3  ...::<init> (156 bytes) made not entrant
42772 3697    3  ...::<init> (156 bytes) made zombie
```

#### Zombie 코드

not entrant로 표시했던 코드를 **회수**했다는 뜻이다. `StockPriceHistoryImpl` 코드가 not entrant가
된 뒤에도 그 클래스의 객체들이 남아 있었는데, **GC가 그것들을 다 회수하자 컴파일러가 그 메서드들을
zombie로 표시할 수 있게 됐다.**

**성능에는 좋은 일이다.** 컴파일된 코드는 고정 크기 코드 캐시에 있으므로, zombie로 식별되면
**코드 캐시에서 제거해 다른 클래스가 컴파일될 공간을 만들 수 있다.**

**잠재적 단점**: 그 클래스가 나중에 다시 로드되어 많이 쓰이면 재컴파일·재최적화가 필요하다.
하지만 위 시나리오에서 성능에 눈에 띄는 영향이 없었다. **일반적으로 zombie 코드 재컴파일로
생기는 작은 재컴파일은 대부분의 애플리케이션에서 측정 가능한 영향이 없다.**

### 계층형 컴파일 레벨

**컴파일러가 둘이 아니라 실행 레벨이 다섯이다** — client 컴파일러에 세 레벨이 있기 때문.

| 레벨 | 의미 |
|---|---|
| 0 | 인터프리터 코드 |
| 1 | 단순 C1 컴파일 코드 |
| 2 | 제한적 C1 컴파일 코드 |
| 3 | **완전 C1 컴파일 코드** |
| 4 | **C2 컴파일 코드** |

**가장 흔한 경로: 0 → 3 → 4.** client 컴파일러는 최적화에 활용할 사용 정보를 얻을 때까지 기다린다.

**예외 경로들**
- **server 큐가 꽉 찼으면** → server 큐에서 빼내 **레벨 2**로 컴파일한다(C1이 호출·백엣지 카운터만
  쓰고 프로파일 피드백은 요구하지 않는 레벨). 빨리 컴파일되고, 나중에 C1이 프로파일 정보를 모으면
  레벨 3, server 큐가 한가해지면 레벨 4로 간다
- **client 큐가 꽉 찼으면** → 레벨 3 대기 중인 메서드가 레벨 4 대상이 될 수 있다. 그러면
  **레벨 2로 빨리 컴파일한 뒤 레벨 4로 전환**한다
- **사소한(trivial) 메서드**는 레벨 2나 3에서 시작했다가 사소함 때문에 **레벨 1**로 간다
- **server가 어떤 이유로 컴파일할 수 없으면** 역시 레벨 1로 간다
- **역최적화되면 레벨 0으로 간다**

> **튜닝 조언**: 최선은 0 → 3 → 4다. **레벨 2로 자주 컴파일되고 여분 CPU가 있다면 컴파일 스레드
> 수를 늘리는 것을 고려하라**(server 큐가 줄어든다). **여분 CPU가 없다면 할 수 있는 건
> 애플리케이션 크기를 줄이는 것뿐이다.**

## 장 요약

> **튜닝 관점에서 답은 단순하다 — 거의 모든 것에 server 컴파일러 + 계층형 컴파일을 써라.
> 이것으로 컴파일러 관련 성능 문제의 90%가 해결된다. 코드 캐시만 충분히 크게 잡으면 된다.**

> **컴파일러 성능에 대한 마지막 한마디 — `final` 키워드**
> 한 장 내내 컴파일을 다루면서 `final` 이 안 나온 것에 놀랐을 수 있다. 어떤 서클에서는 `final` 이
> JIT의 인라이닝 등에 도움을 준다고 믿는다.
> **아득한 과거에는 일리가 있었을지 모르지만 아주 오랫동안 사실이 아니었다**(애초에 사실이었던
> 적이 있는지도 의문이다). **`final` 은 말이 될 때 쓰면 된다** — 바꾸고 싶지 않은 불변 객체나
> 원시값, 특정 내부 클래스의 파라미터 등. **하지만 `final` 의 유무는 성능에 영향을 주지 않는다.**

이 장의 배경 지식이 1장·2장의 권고를 뒷받침한다.

1. **작은 메서드, 특히 getter/setter를 두려워하지 마라** — 쉽게 인라이닝된다. 메서드 오버헤드가
   비쌀 거라는 느낌은 **이론적으로는 맞다**(인라이닝을 끄면 성능이 크게 떨어진다). 하지만
   **실제로는 컴파일러가 그 문제를 해결한다.**
2. **컴파일 대기 코드는 큐에 쌓인다.** 큐에 코드가 많을수록 최적 성능 도달이 늦어진다.
3. **코드 캐시는 크기를 정할 수 있지만(그리고 정해야 하지만) 여전히 유한한 자원이다.**
4. **코드가 단순할수록 더 많은 최적화가 가능하다.** 프로파일 피드백과 이스케이프 분석이 훨씬 빠른
   코드를 만들 수 있지만, **복잡한 루프 구조와 큰 메서드가 그 효과를 제한한다.**

마지막으로, 프로파일 상단에 있으면 안 될 것 같은 메서드가 놀랍게 나타난다면, **이 장의 내용으로
컴파일러가 무엇을 하고 있는지 들여다보고 당신이 작성한 방식을 컴파일러가 처리할 수 있는지
확인하라.**
