# 5장. 가비지 컬렉션 입문 (An Introduction to Garbage Collection)

> ⚠️ **JDK 17 기준 차이** — **기본 수집기가 G1 로 바뀌었고 CMS 는 삭제(JDK 14)됐다.** `UseConcMarkSweepGC`·`UseParNewGC`·`UseParallelOldGC` 는 **JDK 17 에서 기동 자체가 실패**한다. ZGC·Shenandoah·Epsilon 이 추가됐다.
> 전체 대조는 [`00-JDK-17-차이.md`](00-JDK-17-차이.md) 참고.

> **코드를 다시 쓰는 것을 빼면, GC 튜닝이 자바 애플리케이션 성능을 개선하기 위해 할 수 있는
> 가장 중요한 일이다.**

현재 JVM에는 네 가지 주요 컬렉터가 있다 — **시리얼**(단일 CPU용), **처리량(병렬)**,
**동시(CMS)**, **G1**. 성능 특성이 꽤 다르지만 기본 개념을 공유하므로, 이 장은 개요를 다루고
다음 장에서 각각을 깊이 다룬다.

## 1부. GC 개요

### 참조 카운팅으로는 안 된다

자바의 매력 중 하나는 개발자가 객체 수명주기를 명시적으로 관리하지 않아도 된다는 것이다.

> 저자의 솔직한 소회: 자바 프로그램의 메모리 사용을 최적화하는 데 많은 시간을 쓰는 입장에서는
> 이 방식이 기능이 아니라 약점처럼 보일 수도 있다. **하지만 지난 15년간 자바 메모리 문제를
> 다루는 데 쓴 시간이, 그 전 10년간 다른 언어에서 dangling·null 포인터 버그를 찾고 고치는 데 쓴
> 시간보다 적었다.**

기본적으로 GC는 **더 이상 쓰이지 않는 객체를 찾아 그 메모리를 해제하는 것**이다.
"참조가 없는 객체를 찾는 것"이라고 설명하기도 하는데(참조 개수를 세는 것을 암시), **그런
참조 카운팅으로는 불충분하다.**

- **연결 리스트** — 헤드를 뺀 모든 객체가 다른 객체에게 가리켜진다. 하지만 **헤드를 아무도
  참조하지 않으면 리스트 전체가 미사용**이므로 해제할 수 있다
- **순환 리스트** — 꼬리가 머리를 가리키면 **모든 객체에 참조가 있다.** 그런데 리스트 자체를
  아무도 참조하지 않으니 **어떤 객체도 실제로 쓸 수 없다**

그래서 JVM은 **주기적으로 힙을 탐색**해 미사용 객체를 찾아야 한다.

### 단편화와 압축

빈 메모리를 추적해 재사용하는 것만으로는 대개 불충분하다. **어느 시점엔가 메모리를 합쳐서
단편화를 막아야 한다.**

**저자의 예시**: 1,000바이트 배열과 24바이트 배열을 번갈아 할당하는 루프가 힙을 채운다.
24바이트 배열이 전부 미사용이 되어 해제되면 → **힙 안에 빈 영역이 생기지만 24바이트보다 큰 것을
할당할 수 없다.** 1,000바이트 배열들을 옮겨 연속되게 만들고 빈 메모리를 한 영역에 모아야
필요한 만큼 할당할 수 있다.

> **GC 성능은 이 세 가지 기본 연산이 지배한다.**
> ① 미사용 객체 찾기 ② 그 메모리를 사용 가능하게 만들기 ③ 힙 압축하기
> **컬렉터마다 이 연산에 대한 접근이 달라서 성능 특성이 달라진다.**

### Stop-the-world 일시 정지

**애플리케이션 스레드가 돌지 않을 때 이 연산들이 훨씬 간단해진다.** GC가 객체 참조를 추적하거나
객체를 메모리에서 옮길 때, 애플리케이션 스레드가 그 객체를 쓰고 있지 않아야 한다. **특히 객체를
옮길 때** — 그 연산 중에 객체의 메모리 위치가 바뀌므로 어떤 애플리케이션 스레드도 접근할 수 없다.

> 모든 애플리케이션 스레드가 멈추는 이 구간이 **stop-the-world 일시 정지**다.
> **일반적으로 애플리케이션 성능에 가장 큰 영향을 주며, 이 정지를 최소화하는 것이 GC 튜닝의
> 핵심 고려사항이다.**

## 2부. 세대별 가비지 컬렉터

세부는 다르지만 **모든 GC는 힙을 세대(generation)로 나눈다.**

- **올드(old, tenured) 제너레이션**
- **영(young) 제너레이션** — 다시 **에덴(eden)** 과 **서바이버 공간(survivor spaces)** 으로 나뉜다
  (에덴을 영 제너레이션 전체를 가리키는 말로 잘못 쓰는 경우가 있다)

### 왜 세대를 나누나 — 많은 객체가 아주 짧게 쓰인다

```java
sum = new BigDecimal(0);
for (StockPrice sp : prices.values()) {
    BigDecimal diff = sp.getClosingPrice().subtract(averagePrice);
    diff = diff.multiply(diff);
    sum = sum.add(diff);
}
```

**`BigDecimal` 은 불변**이다. 산술 연산을 하면 새 객체가 만들어지고 이전 객체는 버려진다.
1년치 주가(약 250회 반복)에 이 루프를 돌리면 **중간값 저장용으로만 750개의 `BigDecimal` 객체**가
만들어진다. 그것들은 다음 반복에서 버려진다. `add()` 등의 JDK 라이브러리 코드 안에서는 **더 많은
중간 객체**가 만들어진다.

> **이 아주 작은 코드에서 엄청나게 많은 객체가 만들어지고 아주 빨리 버려진다.**
> 자바에서 흔한 일이므로, GC는 **많은(때로는 대부분의) 객체가 일시적으로만 쓰인다는 사실을
> 활용하도록 설계됐다.**

### 마이너 GC와 두 가지 이점

객체는 먼저 **영 제너레이션**에 할당된다. 영 제너레이션이 차면 GC가 모든 애플리케이션 스레드를
멈추고 영 제너레이션을 비운다. 미사용 객체는 버리고, 사용 중인 객체는 다른 곳으로 옮긴다.
이것이 **마이너 GC**다.

**이점 ① 영 제너레이션은 힙의 일부이므로 처리가 빠르다.** 전체 힙을 한 번에 처리하는 것보다
애플리케이션 스레드가 훨씬 짧게 멈춘다.
**트레이드오프**: 전체 힙이 찰 때까지 기다리는 것보다 **더 자주** 멈춘다.
**하지만 더 자주여도 짧은 정지가 거의 항상 큰 이득이다.**

**이점 ② 영 제너레이션은 수집될 때 자동으로 압축된다.** 객체는 에덴(영 제너레이션의 대부분)에
할당되고, 수집 시 에덴의 **모든 객체가 옮겨지거나 버려진다** — 살아 있는 것은 서바이버 공간이나
올드 제너레이션으로. **모든 객체가 옮겨지므로 압축이 공짜로 따라온다.**

> **모든 GC 알고리즘은 영 제너레이션 수집 시 stop-the-world 정지를 갖는다.**

### 풀 GC와 동시 컬렉터

객체가 올드 제너레이션으로 옮겨지다 보면 결국 거기도 찬다. **여기서 GC 알고리즘의 가장 큰 차이가
나타난다.**

- **단순한 알고리즘** — 모든 스레드를 멈추고, 미사용 객체를 찾아 해제하고, 힙을 압축한다.
  이것이 **풀 GC**이고 **대개 긴 정지**를 일으킨다
- **동시(concurrent) 컬렉터 (CMS, G1)** — 계산적으로 더 복잡하지만, **애플리케이션 스레드가
  도는 동안 미사용 객체를 찾는 것**이 가능하다. 그래서 **저지연(low-pause)** 컬렉터라고 부른다
  (**"무정지(pauseless)"라고 부르는 건 틀렸다**)

**동시 컬렉터의 트레이드오프**: 정지가 더 적고 짧지만 **전체 CPU를 더 쓴다.**
**CMS와 G1도 긴 풀 GC 정지를 할 수 있고, 그것을 피하는 것이 이 알고리즘 튜닝의 핵심 요소다.**

### 어느 컬렉터를 고를 것인가 — 목표에 달렸다

**개별 요청 응답 시간을 재는 애플리케이션(Java EE 서버 등)**:
- 개별 요청은 정지 시간, **특히 풀 GC의 긴 정지**에 영향받는다. 응답 시간에 대한 정지의 영향을
  최소화하는 게 목표라면 **동시 컬렉터가 적합**하다
- **평균 응답 시간이 이상치(90퍼센타일)보다 중요하다면 처리량 컬렉터가 대개 낫다**
- 긴 정지를 피하는 이득은 **추가 CPU 사용**이라는 비용을 치른다

**배치 애플리케이션**:
- **CPU가 충분하면** 동시 컬렉터로 풀 GC 정지를 피해 작업이 더 빨리 끝난다
- **CPU가 제한적이면** 동시 컬렉터의 추가 소비 때문에 배치가 더 오래 걸린다

## 3부. 네 가지 GC 알고리즘

### 시리얼 컬렉터 (Serial)

가장 단순하다. **클라이언트급 머신**(Windows 32비트 JVM이나 단일 프로세서 머신)의 기본값.

- **단일 스레드**로 힙을 처리한다
- 마이너·풀 GC 모두 **모든 애플리케이션 스레드를 멈춘다**
- 풀 GC 시 **올드 제너레이션을 완전히 압축**한다

```
-XX:+UseSerialGC
```
> **⚠️ 대부분의 JVM 플래그와 달리 `-XX:-UseSerialGC` 로 끌 수 없다.** 시리얼이 기본인 시스템에서는
> **다른 GC 알고리즘을 지정해서** 끈다.

### 처리량 컬렉터 (Throughput / Parallel)

**서버급 머신**(멀티 CPU Unix 머신, 모든 64비트 JVM)의 기본값.

- **여러 스레드**로 영 제너레이션을 수집해 마이너 GC가 훨씬 빠르다
- **올드 제너레이션도 여러 스레드로 처리할 수 있다.** JDK 7u4 이후 기본 동작이고, 이전
  Java 7에서는 `-XX:+UseParallelOldGC` 로 켠다
- 여러 스레드를 쓰므로 **병렬(parallel) 컬렉터**라고도 부른다
- **마이너·풀 GC 모두 모든 스레드를 멈추고**, 풀 GC 시 올드 제너레이션을 완전히 압축한다

```
-XX:+UseParallelGC -XX:+UseParallelOldGC
```

### CMS 컬렉터

**처리량·시리얼 컬렉터의 풀 GC 긴 정지를 없애기 위해** 설계됐다.

- **마이너 GC 때는 모든 스레드를 멈춘다**(여러 스레드로 수행)
- ⚠️ **영 제너레이션 수집 알고리즘이 처리량 컬렉터와 다르다** — CMS는 `-XX:+UseParNewGC`,
  처리량은 `-XX:+UseParallelGC`
- **풀 GC 때 스레드를 멈추는 대신, 하나 이상의 백그라운드 스레드가 주기적으로 올드 제너레이션을
  스캔해 미사용 객체를 버린다.** 애플리케이션 스레드는 마이너 컬렉션 때와, 백그라운드 스레드가
  올드 제너레이션을 스캔하는 특정 시점의 아주 짧은 구간에만 멈춘다

**트레이드오프**
- **CPU 사용 증가** — 애플리케이션 스레드가 도는 동시에 백그라운드 GC 스레드가 힙을 스캔할
  충분한 CPU가 있어야 한다
- **백그라운드 스레드는 압축을 하지 않는다** → **힙이 단편화될 수 있다**

> **⚠️ CMS의 실패 모드**: 백그라운드 스레드가 작업을 마칠 CPU를 못 받거나, **힙이 너무
> 단편화되어 객체를 할당할 수 없으면, CMS는 시리얼 컬렉터의 동작으로 되돌아간다** — 모든
> 스레드를 멈추고 **단일 스레드로** 올드 제너레이션을 정리·압축한다. 그다음 다시 동시 백그라운드
> 처리를 시작한다(다음에 또 너무 단편화될 때까지).

```
-XX:+UseConcMarkSweepGC -XX:+UseParNewGC   # 둘 다 기본 false
```

### G1 컬렉터 (Garbage First)

**약 4GB 이상의 큰 힙을 최소 정지로 처리**하도록 설계됐다.

- 힙을 여러 **리전(region)** 으로 나누지만 **여전히 세대별 컬렉터**다. 일부 리전이 영 제너레이션이고,
  영 제너레이션은 여전히 모든 스레드를 멈추고 살아 있는 객체를 옮겨서 수집한다(여러 스레드로)
- **동시 컬렉터** — 올드 제너레이션은 백그라운드 스레드가 처리하고, 대부분의 작업에서
  애플리케이션 스레드를 멈출 필요가 없다
- **올드 제너레이션이 리전으로 나뉘어 있어서 한 리전에서 다른 리전으로 복사하는 방식으로
  정리할 수 있다 → 정상 처리 중에 (적어도 부분적으로) 힙을 압축한다.**
  그래서 **G1 힙은 단편화될 가능성이 훨씬 낮다** (여전히 가능하긴 하다)

```
-XX:+UseG1GC   # 기본 false
```

> **명시적 GC를 일으키고 막기**
> GC는 보통 JVM이 필요하다고 판단할 때 일어난다. 자바는 강제할 방법도 준다 — `System.gc()`.
> **이걸 부르는 건 거의 항상 나쁜 생각이다.** 이 호출은 **CMS나 G1로 돌고 있어도 항상 풀 GC를
> 트리거**하므로 스레드가 비교적 오래 멈춘다. 그리고 **애플리케이션을 더 효율적으로 만들지도
> 않는다** — GC를 원래보다 일찍 일으킬 뿐, 성능 영향을 옮기는 것에 불과하다.
>
> **예외는 있다.** 벤치마크에서 워밍업 후 측정 사이클 전에 GC를 강제하는 것은 말이 된다.
> **힙 분석 시 힙 덤프를 뜨기 전에 풀 GC를 강제하는 것도 대개 좋다**(대부분의 힙 덤프 방법이
> 어차피 풀 GC를 한다). `jcmd <pid> GC.run` 이나 `jconsole` 의 Perform GC 버튼으로도 된다.
>
> **또 다른 예외는 RMI다** — 분산 GC의 일부로 **매시간 `System.gc()` 를 호출한다.**
> `-Dsun.rmi.dgc.server.gcInterval=N`, `-Dsun.rmi.dgc.client.gcInterval=N` (밀리초,
> Java 7 기본 3600000).
>
> **서드파티 코드가 `System.gc()` 를 잘못 부른다면** `-XX:+DisableExplicitGC` (기본 false)로
> 완전히 막을 수 있다.

## 4부. GC 알고리즘 고르기

**시리얼 컬렉터는 애플리케이션이 100MB 미만을 쓸 때만 쓸 만하다.** 그 정도 힙은 처리량 컬렉터의
병렬 수집이나 CMS·G1의 백그라운드 수집으로 도움받을 게 없다. **이 크기 지침이 시리얼 컬렉터의
쓸모를 제한한다.** 대부분의 프로그램은 처리량 컬렉터와 동시 컬렉터 사이에서 골라야 한다.

### 배치 작업

풀 GC 사이클 하나가 0.5초이고 5분 실행 중 20번 일어나면 → **3.4% 성능 페널티**
(정지가 없었다면 300초가 아니라 290초에 끝났을 것이다).

**CPU가 남으면 동시 컬렉터가 좋은 성능 향상을 준다. 핵심은 백그라운드 GC 스레드가 쓸 CPU가
충분한가다.**

> **단일 CPU에서 애플리케이션 스레드 하나가 CPU 100%를 쓰는 경우를 생각해 보자.**
> 처리량 컬렉터면 GC가 주기적으로 돌면서 애플리케이션 스레드를 멈춘다. 동시 컬렉터면 OS가
> 어떤 때는 애플리케이션 스레드를, 어떤 때는 백그라운드 GC 스레드를 실행한다.
> **순효과는 같다 — OS가 다른 스레드를 실행하는 동안 애플리케이션 스레드는 사실상 멈춘 것이다**
> (훨씬 짧은 시간이긴 하지만).

| GC | 4 CPU (CPU 사용률) | 1 CPU (CPU 사용률) |
|---|---|---|
| CMS | **78.09초 (30.7%)** | 120.0초 (100%) |
| Throughput | 81.00초 (27.7%) | **111.6초 (100%)** |

**4 CPU**: CMS가 3초 빠르다. 애플리케이션 스레드 하나가 계속 도니 25%를 쓰고, **CMS 백그라운드
스레드가 주기적으로 CPU 하나를 통째로 쓴다**(약 5%의 시간 동안) → 평균 30%.
처리량 컬렉터는 GC 스레드 4개가 **GC 사이클 동안 4 CPU를 100%** 쓴다 → 평균 28%.

**1 CPU**: CPU가 항상 바쁘다. 이제 **CMS 백그라운드 스레드의 추가 오버헤드가 단점이 되고**
처리량 컬렉터가 9초 먼저 끝난다.

> **평균 CPU 사용률과 GC — 중요한 함정**
> 테스트 중 평균 CPU만 보면 GC 사이클 중에 벌어지는 흥미로운 그림을 놓친다.
>
> **처리량 컬렉터**: 대부분의 시간은 애플리케이션 스레드만 돌아 25%. **GC가 시작되면 100%.**
> 실제 CPU는 **톱니 모양**인데 평균은 직선으로 보고된다.
>
> **동시 컬렉터(CMS)**: 애플리케이션이 25%로 시작 → 쓰레기가 충분히 쌓이면 CMS 백그라운드
> 스레드가 CPU 하나를 더 써서 **50%** → 끝나면 다시 25%. **100% 피크가 없다**(마이너 컬렉션 때
> 아주 짧은 스파이크는 있지만 무시할 만큼 짧다).
>
> **⚠️ CPU 사용률 규칙으로 트리거되는 모니터링 시스템이 있다면 아주 중요하다.**
> **풀 GC의 100% 스파이크나, 백그라운드 동시 처리의 훨씬 길지만 낮은 스파이크로 CPU 알림이
> 울리지 않게 해야 한다. 이 스파이크들은 자바 프로그램의 정상적인 현상이다.**

> **요약**
> 1. **CPU 대부분을 쓰는 배치 작업**은 대개 **처리량 컬렉터**가 낫다.
> 2. **CPU를 다 쓰지 않는 배치 작업**은 대개 **동시 컬렉터**가 낫다.

### 처리량 테스트

GlassFish에 2GB 힙, 이전 10개 요청을 각 사용자 HTTP 세션에 저장(GC 압박을 높이려고), 4 CPU.

| 클라이언트 수 | Throughput TPS (CPU) | CMS TPS (CPU) |
|---|---|---|
| 1 | 30.43 (29%) | **31.98 (31%)** |
| 10 | **81.34 (97%)** | 62.20 (85%) |

- **CPU 여유 있을 때**: CMS가 **5% 더 높은 TPS**. 처리량 컬렉터는 **풀 GC 정지 24번** 동안 요청을
  처리 못 했고 그게 정상 상태 시간의 약 5%였다
- **CPU 제한될 때**: CMS가 **23.5% 낮은 TPS.** 게다가 **CMS가 CPU를 100% 가까이 쓰지도 못했다** —
  백그라운드 CMS 스레드에 CPU 사이클이 부족해 **동시 모드 실패(concurrent mode failure)** 가
  발생했기 때문이다. 그러면 JVM이 **단일 스레드 풀 GC**를 수행해야 하고, 그 구간에는 4 CPU 머신이
  25%만 바쁘므로 평균 CPU 사용률이 떨어진다

### 응답 시간 테스트

생각 시간 250ms → 고정 부하 29 TPS.

| 세션 크기 | Throughput 평균 / 90% / 99% / CPU | CMS 평균 / 90% / 99% / CPU |
|---|---|---|
| 10개 | 0.092 / **0.171** / 0.813 / 41% | 0.104 / 0.211 / **0.260** / 46% |
| 50개 | 0.180 / **0.218** / 3.617 / 55% | **0.107** / 0.222 / **0.315** / 53% |

**10개 저장** — 두 컬렉터 비교의 **전형적인 결과**다. 처리량 컬렉터가 **평균과 90퍼센타일에서 더
빠르다.** 하지만 **99퍼센타일은 CMS가 크게 유리**하다 — 처리량 쪽의 풀 GC가 **1%의 연산을
현저히 느리게** 만들었다. CMS는 그 개선을 위해 CPU를 약 10% 더 쓴다.

**50개 저장** — GC 영향이 훨씬 커졌다. **처리량 컬렉터의 평균 응답 시간이 CMS보다 훨씬 나쁘다.**
99퍼센타일을 3초 넘게 만든 **아주 큰 이상치들** 때문이다. **흥미롭게도 90퍼센타일은 여전히
처리량 컬렉터가 낮다** — 풀 GC를 하지 않는 동안에는 여전히 우위를 보인다.

> **저자의 솔직한 단서**: 이런 경우는 첫 번째보다 훨씬 드물다. **어떤 의미에서 CMS는 여기서
> 운이 좋았다** — 힙에 라이브 데이터가 많아 풀 GC 시간이 처리량 컬렉터의 응답 시간을 지배할
> 정도면, **CMS도 동시 모드 실패를 겪는 경우가 많다.** 이 예에서는 CMS 백그라운드 처리가
> 수요를 따라가기에 충분했을 뿐이다.

> **요약**
> 1. 응답 시간이나 처리량을 잴 때, 처리량 vs 동시 컬렉터의 선택은 **백그라운드 스레드가 쓸 CPU의
>    양에 달렸다.**
> 2. **처리량 컬렉터가 평균 응답 시간이 더 낮은 경우가 많고, 동시 컬렉터가 90·99퍼센타일이 더
>    낮은 경우가 많다.**
> 3. **처리량 컬렉터가 풀 GC를 과도하게 하면, 동시 컬렉터가 평균 응답 시간도 더 낮은 경우가 많다.**

### CMS vs G1

**대략적 기준: 4GB 미만 힙에서는 CMS가 G1보다 낫다.** CMS가 더 단순한 알고리즘이라 단순한
경우(작은 힙)에는 더 빠를 가능성이 높다. **큰 힙에서는 작업을 나누는 방식 때문에 G1이 대개 낫다.**

**왜 그런가**
- **CMS 백그라운드 스레드는 객체를 해제하기 전에 올드 제너레이션 전체를 스캔해야 한다.**
  힙이 차기 전에 스캔과 해제를 못 끝내면 **동시 모드 실패** → **모든 스레드를 멈추고 단일
  스레드로 풀 GC.** 아주 심한 성능 페널티다. 여러 백그라운드 스레드를 쓰도록 튜닝할 수 있지만
  **힙이 커질수록 그 스레드들이 할 일이 많아진다**
- **G1은 올드 제너레이션을 리전으로 쪼개므로 여러 백그라운드 스레드가 스캔 작업을 나누기 쉽다.**
  G1도 동시 모드 실패를 겪을 수 있지만 **가능성이 낮다**
- **CMS는 힙 단편화 때문에도 풀 GC로 되돌아간다**(긴 풀 GC 때를 빼면 압축을 안 하니까).
  **G1은 진행하면서 압축한다.** G1도 단편화될 수 있지만 설계상 가능성이 낮다

> **무형의 요소들도 있다.**
> - **처리량 컬렉터가 셋 중 가장 오래됐다** — JVM 엔지니어가 잘 만들 기회가 더 많았다
> - **G1은 상대적으로 새 알고리즘이라 설계가 예상하지 못한 코너 케이스를 만날 가능성이 높다**
> - G1은 튜닝 손잡이가 적은데, 관점에 따라 좋을 수도 나쁠 수도 있다
> - **G1은 Java 7u4까지 실험적이었고**, 일부 튜닝 기능은 Java 7u10부터 쓸 수 있다.
>   **Java 8에서 Java 7 초기 릴리스 대비 성능이 크게 좋아졌다**
>
> **어떤 애플리케이션은 어느 컬렉터로도 동시 모드 실패를 피하도록 튜닝하는 것이 불가능하다.**
> 성능 목표가 동시 컬렉터의 목표와 맞아 보여도 **처리량 컬렉터가 더 나은 선택일 수 있다.**

## 5부. 기본 GC 튜닝

### 힙 크기 정하기

**균형의 문제다.**
- **너무 작으면** GC에 시간을 너무 쓰고 애플리케이션 로직에 충분히 못 쓴다
- **아주 크게 잡는 것도 답이 아니다** — **정지 시간은 힙 크기에 의존**하므로 힙이 커지면 정지가
  길어진다. 빈도는 줄지만 **길이가 전체 성능을 늦춘다**

#### ⚠️ 두 번째 위험 — 스와핑

OS는 가상 메모리로 물리 메모리를 관리한다. 8GB RAM 머신이 16GB처럼 보일 수 있다.
**여러 애플리케이션을 돌리는 시스템에는 잘 맞는다** — 대부분이 동시에 활성이 아니니까.
**자바 애플리케이션에는 잘 맞지 않는다.**

12GB 힙 프로그램을 이 시스템에서 돌리면 OS가 8GB는 RAM에, 4GB는 디스크에 둔다.
**JVM은 이 사실을 모른다** — 스와핑은 OS가 투명하게 처리한다. 그래서 **JVM은 자기가 쓰라고 들은
12GB를 기꺼이 다 채운다.** 디스크↔RAM 스왑이 일어나며 심한 성능 페널티가 발생한다.

> **더 나쁜 건, 이 스와핑이 반드시 일어나는 한 순간이 풀 GC 때라는 것이다.** JVM이 힙 전체에
> 접근해야 하니까. **풀 GC 중에 스와핑하면 정지가 원래보다 자릿수가 다르게 길어진다.**
> 동시 컬렉터를 쓰면 백그라운드 스레드가 힙을 훑을 때 디스크에서 데이터를 가져오는 긴 대기 때문에
> 뒤처져서 **비싼 동시 모드 실패**로 이어진다.

> **힙 크기의 첫 번째 규칙: 머신의 물리 메모리보다 큰 힙을 절대 지정하지 마라.**
> JVM을 여러 개 돌린다면 **그 힙들의 합**에 적용된다. JVM 자체와 다른 애플리케이션을 위한
> 공간도 남겨야 한다 — **일반적인 OS 프로필에서는 최소 1GB.**

#### 기본값

```
-Xms N   # 초기값
-Xmx N   # 최대값
```

| OS와 JVM | 초기 힙 | 최대 힙 |
|---|---|---|
| Linux/Solaris 32비트 client | 16 MB | 256 MB |
| Linux/Solaris 32비트 server | 64 MB | Min(1GB, 물리 메모리의 1/4) |
| **Linux/Solaris 64비트 server** | **Min(512MB, 물리의 1/64)** | **Min(32GB, 물리의 1/4)** |
| MacOS 64비트 server | 64 MB | Min(1GB, 물리의 1/4) |
| Windows 32비트 client | 16 MB | 256 MB |
| Windows 64비트 server | 64 MB | Min(1GB, 물리의 1/4) |

물리 메모리 192MB 미만 머신에서는 최대 힙이 **물리 메모리의 절반**(96MB 이하).

**초기값과 최대값을 두는 이유**는 JVM이 작업 부하에 따라 동작을 조정할 수 있게 하기 위해서다.
**초기 힙에서 GC를 너무 많이 한다고 판단하면 "적절한" 양이 될 때까지, 혹은 최대에 닿을 때까지
계속 힙을 늘린다.**

> **많은 애플리케이션에서는 힙 크기를 설정할 필요가 아예 없다.** 대신 **GC 알고리즘의 성능 목표**를
> 지정한다 — 감내할 정지 시간, GC에 쓸 시간 비율 등(6장).

**힙을 늘려야 한다면** — 정해진 규칙은 없지만 **경험칙: 풀 GC 후 30% 점유되도록 잡아라.**
계산 방법: 애플리케이션이 **정상 상태**(캐시를 다 로드하고 최대 클라이언트 연결을 만든 상태)에
도달할 때까지 돌린 뒤, `jconsole` 로 붙어 **풀 GC를 강제**하고 완료 후 사용 메모리를 관찰한다.
(처리량 GC라면 GC 로그를 봐도 된다.)

> **최대값을 명시해도 자동 크기 조정은 일어난다.** 힙은 기본 초기 크기에서 시작해 GC 성능 목표를
> 맞추려고 커진다. **필요보다 큰 힙을 지정하는 데 메모리 페널티가 반드시 있는 건 아니다** —
> 목표를 맞출 만큼만 커진다.
>
> **반대로 정확히 얼마가 필요한지 안다면 초기와 최대를 같은 값으로 두는 게 낫다**
> (`-Xms4096m -Xmx4096m`). **크기를 조정할지 판단할 필요가 없어져 GC가 약간 더 효율적이다.**

### 세대 크기 정하기

**성능적 함의는 명확하다.** 영 제너레이션이 상대적으로 크면 → 덜 자주 수집되고 올드로 승격되는
객체가 적다. **하지만 올드가 상대적으로 작아지므로 더 자주 차고 풀 GC를 더 많이 한다.**

**모든 플래그가 영 제너레이션 크기를 조정하고, 올드는 나머지를 갖는다.**

```
-XX:NewRatio=N      # 영:올드 비율. 기본 2
-XX:NewSize=N       # 영 제너레이션 초기 크기
-XX:MaxNewSize=N    # 영 제너레이션 최대 크기
-Xmn N              # NewSize와 MaxNewSize를 같은 값으로
```

```
초기 영 제너레이션 크기 = 초기 힙 크기 / (1 + NewRatio)
```
**기본적으로 영 제너레이션은 초기 힙의 33%로 시작한다.**

`NewSize` 를 설정하면 `NewRatio` 계산보다 **우선한다.** 기본값은 없다(다만 `PrintFlagsFinal` 은
1MB로 보고한다). 힙이 커지면 영 제너레이션도 `MaxNewSize` 까지 커지며, 기본적으로 이 최대값도
`NewRatio` 로 계산되되 **최대 힙 크기** 기준이다.

> **최소·최대 범위로 영 제너레이션을 튜닝하는 것은 꽤 어렵다.**
> **힙 크기가 고정이면(`-Xms` = `-Xmx`) `-Xmn` 으로 영 제너레이션도 고정하는 것이 대개 낫다.**
> 동적 힙이 필요하면서 더 큰(또는 작은) 영 제너레이션이 필요하면 **`NewRatio` 에 집중하라.**

### permgen과 메타스페이스

JVM이 클래스를 로드하면 **클래스 메타데이터**를 추적해야 한다. **별도의 힙 공간**에 담긴다 —
Java 7에서는 **permgen**, Java 8에서는 **메타스페이스**.

**둘은 정확히 같은 것이 아니다.** Java 7의 permgen에는 클래스 데이터와 무관한 잡다한 객체도 있는데
Java 8에서는 그것들이 일반 힙으로 옮겨졌다. Java 8은 이 영역에 담는 메타데이터의 종류 자체를
근본적으로 바꿨다. **다만 사용자는 그게 뭔지 애초에 모르므로 실질적 영향은 없다.**

> **⚠️ permgen/메타스페이스는 클래스의 실제 인스턴스(`Class` 객체)나 리플렉션 객체(`Method` 등)를
> 담지 않는다.** 그것들은 일반 힙에 있다. 이 영역의 정보는 **컴파일러와 JVM 런타임만 쓴다.**

| JVM | 기본 초기 | permgen 기본 최대 | **메타스페이스 기본 최대** |
|---|---|---|---|
| 32비트 client | 12 MB | 64 MB | **무제한** |
| 32비트 server | 16 MB | 64 MB | **무제한** |
| 64비트 | 20.75 MB | 82 MB | **무제한** |

```
-XX:PermSize=N       -XX:MaxPermSize=N        # Java 7
-XX:MetaspaceSize=N  -XX:MaxMetaspaceSize=N   # Java 8
```

> **메타스페이스가 너무 크다면?**
> 기본이 무제한이라 **(특히 32비트 JVM에서) Java 8 애플리케이션이 메타스페이스를 채워
> 메모리 부족이 날 수 있다.** 8장의 **NMT(Native Memory Tracking)** 도구가 진단에 도움이 된다.
> `MaxMetaspaceSize` 를 낮출 수 있지만 **그러면 결국 메타스페이스가 차면서 `OutOfMemoryError` 가
> 난다. 진짜 해법은 클래스 메타데이터가 왜 너무 큰지 알아내는 것이다.**

**⚠️ 이 영역의 크기 조정에는 풀 GC가 필요하므로 비싼 연산이다.** 프로그램 시작 중(클래스를 로드하며)
풀 GC가 많다면 대개 permgen/메타스페이스 크기 조정 때문이므로 **초기 크기를 늘리면 시작이 개선된다.**
Java 7에서 클래스를 많이 정의하는 애플리케이션은 최대값도 늘려야 한다(앱 서버는 보통 128MB,
192MB 이상을 지정한다).

> **이름과 달리 permgen의 데이터는 영구적이지 않다**(그래서 메타스페이스가 훨씬 나은 이름이다).
> **클래스도 다른 것들처럼 GC 대상이 될 수 있다.** 앱 서버에서 아주 흔한 일이다 — 배포·재배포마다
> 새 클래스로더를 만들고, 옛 클래스로더는 참조가 끊겨 GC 대상이 되며 그것이 정의한 클래스들도
> 마찬가지다. **긴 개발 사이클 동안 배포 중에 풀 GC가 트리거되는 것은 드문 일이 아니다.**
>
> 진단은 **힙 덤프(7장)** 로 어떤 클래스로더가 존재하는지 보는 것이 좋다 — **클래스로더 누수**가
> permgen을 채우는지 알 수 있다. `jmap -permstat`(Java 7) / `-clstats`(Java 8)도 있지만
> **가장 안정적인 명령이 아니라 권장할 수 없다.**

### 병렬성 제어

시리얼을 뺀 모든 알고리즘이 여러 스레드를 쓴다.

```
-XX:ParallelGCThreads=N
```

이 플래그가 영향을 주는 곳:
- `-XX:+UseParallelGC` 의 영 제너레이션 수집
- `-XX:+UseParallelOldGC` 의 올드 제너레이션 수집
- `-XX:+UseParNewGC` 의 영 제너레이션 수집
- `-XX:+UseG1GC` 의 영 제너레이션 수집
- **CMS의 stop-the-world 단계**(풀 GC는 제외)
- **G1의 stop-the-world 단계**(풀 GC는 제외)

이 연산들이 애플리케이션을 멈추므로 **JVM은 정지 시간을 최소화하려고 가능한 한 많은 CPU를 쓴다.**
기본적으로 **CPU당 스레드 하나, 8개까지.** 그 뒤로는 **CPU 8분의 5마다 하나씩** 추가한다.

```
ParallelGCThreads = 8 + ((N - 8) * 5 / 8)
```

**이 수가 너무 클 때가 있다.**
- **8 CPU 머신에서 1GB 힙**이면 **4~6개**가 그 힙을 나누는 게 약간 더 효율적이다
- **128 CPU 머신의 83개 GC 스레드**는 아주 큰 힙이 아닌 한 너무 많다

> **여러 JVM을 한 머신에서 돌린다면 GC 스레드 총합을 제한하는 것이 좋다.**
> GC 스레드는 돌 때 아주 효율적이고 **각각 CPU 하나를 100% 소비한다**(앞 예제에서 처리량
> 컬렉터의 평균 CPU가 예상보다 높았던 이유다).
>
> **16 CPU에 JVM 4개** — 각 JVM이 기본 13개 GC 스레드를 갖는다. 넷이 동시에 GC를 하면
> **CPU를 갈망하는 52개 스레드가 경합**한다. 각 JVM을 4개로 제한하는 편이 효율적이다.
> **동시에 GC할 가능성이 낮더라도**, 한 JVM이 13스레드로 GC하면 나머지 JVM의 애플리케이션
> 스레드는 **16개 중 13개 CPU가 GC로 100% 바쁜 머신에서 CPU를 두고 경쟁**해야 한다.

**⚠️ 이 플래그는 CMS나 G1의 백그라운드 스레드 수를 설정하지는 않는다**(영향은 준다). 6장 참조.

### 적응형 크기 조정 (Adaptive Sizing)

힙·세대·서바이버 공간의 크기가 실행 중에 변할 수 있다. **최선 노력(best-effort) 방식이고 과거
성능에 의존한다** — 미래의 GC 사이클이 최근 것과 비슷하리라는 가정이다. **많은 워크로드에서
합리적인 가정이고, 할당률이 갑자기 바뀌어도 JVM은 새 정보로 다시 적응한다.**

**두 가지 중요한 이점**
1. **작은 애플리케이션이 힙 크기를 과다 지정할 걱정을 안 해도 된다.** 앱 서버 관리용 명령행
   프로그램은 수명이 짧고 메모리를 거의 안 쓴다. **기본 힙이 1GB까지 클 수 있는데도 16(또는 64)MB만
   쓴다.** 적응형 크기 조정 덕분에 이런 애플리케이션은 따로 튜닝할 필요가 없다
2. **많은 애플리케이션이 힙 크기 튜닝을 아예 신경 쓸 필요가 없다.** 기본보다 큰 힙이 필요하면
   그것만 지정하고 나머지는 잊으면 된다

**끄는 경우**
```
-XX:-UseAdaptiveSizePolicy      # 기본 true
-XX:+PrintAdaptiveSizePolicy    # GC 로그에 크기 조정 상세를 남긴다
```
크기 조정에는 **약간의 시간이 들고 대부분 GC 정지 중에 일어난다.** GC 파라미터와 힙 크기 제약을
정밀하게 튜닝했다면 꺼도 된다. **뚜렷하게 다른 국면(phase)을 거치는 애플리케이션에서 한 국면에
최적화하고 싶을 때도 유용하다.**

**서바이버 공간을 제외하면**, `-Xms` = `-Xmx` 이고 영 제너레이션의 초기·최대가 같으면
**사실상 꺼진 것과 같다.**

## 6부. GC 도구

### GC 로그가 핵심이다

```
-verbose:gc  또는  -XX:+PrintGC     # 단순 로그 (서로 별칭, 기본 비활성)
-XX:+PrintGCDetails                 # 훨씬 많은 정보 — 권장 (기본 false)
-XX:+PrintGCTimeStamps              # JVM 시작 기준 상대 시각
-XX:+PrintGCDateStamps              # 실제 날짜 문자열 (포맷팅이 있어 아주 미세하게 덜 효율적)
-Xloggc:<filename>                  # 파일로 (PrintGCDetails 없으면 단순 로그가 자동 활성)
```

> **단순 로그만으로 GC에서 무슨 일이 일어나는지 진단하기는 대개 너무 어렵다.**

**로그 회전** — 몇 달간 디스크를 채울 수 있는 장기 실행 서버에 유용하다.
```
-XX:+UseGCLogFileRotation   # 기본 비활성
-XX:NumberOfGCLogFiles=N    # 기본 0 = 무제한
-XX:GCLogFileSize=N         # 기본 0 = 무제한
```
> **⚠️ 세 옵션에 값을 모두 지정해야 기대대로 동작한다.** 파일 크기가 8KB 미만이면 8KB로 올림된다.

**GC Histogram** 같은 도구가 로그를 읽어 차트와 표를 준다. 저자의 예시 화면에서는
**JVM이 시간의 41%(!)를 GC에 쓰고 풀 GC 한 번에 7초 넘게** 걸린다 —
**메모리 사용을 확실히 개선해야 하는 애플리케이션이다.**

### 실시간 모니터링

**`jconsole`** Memory 패널 — 힙 전체, 또는 에덴/서바이버/올드/permanent 각각을 그래프로 볼 수 있다.

**`jstat`** — 스크립트용 최선의 도구. 9가지 옵션(`jstat -options` 로 전체 목록).

```
% jstat -gcutil <pid> 1000
  S0     S1     E      O      P     YGC     YGCT    FGC    FGCT     GCT
 51.71   0.00  99.12  60.00  99.93     98    1.985     8    2.397    4.382
  0.00  42.08   5.55  60.98  99.93     99    2.016     8    2.397    4.413
```

**읽는 법**
- 모니터링 시작 시점에 이미 영 컬렉션 **98회**(`YGC`), 총 **1.985초**(`YGCT`),
  풀 GC **8회**(`FGC`), **2.397초**(`FGCT`), 총 GC 시간 **4.382초**(`GCT`)
- **에덴(`E`)이 99.12%로 차 있을 때 모니터링을 시작**했다 → 다음 1초에 영 컬렉션이 일어났다
- 에덴이 **5.55%로 줄고**, **서바이버 공간(`S0`/`S1`)이 자리를 바꿨고**, 소량이 올드(`O`)로
  승격되어 60% → **60.98%**
- **permanent(`P`)는 거의 변화가 없다** — 필요한 클래스를 이미 다 로드했으니 전형적이다

> **GC 로깅을 켜는 걸 잊었다면 이것이 좋은 대체재다.**

> **요약**
> 1. **GC 로그는 GC 문제 진단에 필요한 핵심 데이터다. 프로덕션 서버에서도 일상적으로 수집해야 한다.**
> 2. `PrintGCDetails` 로 더 나은 로그를 얻는다.
> 3. GC 로그를 파싱하고 이해하는 프로그램이 널리 있다.
> 4. `jstat` 은 살아 있는 프로그램의 GC에 좋은 가시성을 준다.

## 장 요약

> **많은 애플리케이션에서 필요한 튜닝은 적절한 GC 알고리즘을 고르고, 필요하면 힙 크기를 늘리는
> 것뿐이다. 그다음은 적응형 크기 조정이 주어진 힙으로 좋은 성능을 내도록 JVM이 자동 튜닝하게 한다.**

더 복잡한 애플리케이션은 특히 알고리즘별로 추가 튜닝이 필요하다 → 6장.
