# 6장. 가비지 컬렉션 알고리즘 (Garbage Collection Algorithms)

> ⚠️ **JDK 17 기준 차이** — **이 파일이 가장 크게 어긋난다.** CMS 관련 서술(동시 사이클·동시 모드 실패·승격 실패·iCMS)은 **실행할 수 없는 역사 자료**다 — 다만 "동시 수집기가 왜 실패하는가"의 구조로 읽으면 G1·ZGC 에 그대로 쓰인다. **G1 부분(리전·혼합 GC·거대 객체·테뉴어링·TLAB)은 지금도 유효**하다.
> 전체 대조는 [`00-JDK-17-차이.md`](00-JDK-17-차이.md) 참고.

> 5장의 기본 튜닝으로 충분하지 않을 때, **실제로 쓰는 GC 알고리즘의 구체적 동작**을 살펴
> 파라미터를 어떻게 바꿔야 GC 영향을 최소화할지 정해야 한다.
>
> **개별 컬렉터를 튜닝하는 데 필요한 핵심 데이터는 그 컬렉터를 켰을 때의 GC 로그다.**
> 그래서 이 장은 각 알고리즘을 **로그 출력의 관점**에서 본다.

---

# 1부. 처리량 컬렉터 (Throughput Collector)

두 가지 기본 연산뿐이다 — **영 제너레이션 수집**과 **올드 제너레이션 수집**.

### 마이너 GC 로그 읽기

```
17.806: [GC [PSYoungGen: 227983K->14463K(264128K)]
             280122K->66610K(613696K), 0.0169320 secs]
             [Times: user=0.05 sys=0.00, real=0.02 secs]
```

| 항목 | 의미 |
|---|---|
| `17.806` | 프로그램 시작 17.806초 후 |
| `PSYoungGen: 227983K->14463K` | 영 제너레이션이 **227MB → 14MB**(서바이버 공간에) |
| `(264128K)` | 현재 영 제너레이션 전체 크기 **264MB** |
| `280122K->66610K` | **힙 전체**(영+올드) 점유가 **280MB → 66MB** |
| `(613696K)` | 이 시점 힙 전체 크기 **613MB** |
| `real=0.02` | 실제 경과 0.02초 |
| `user=0.05` | **CPU 시간이 실제 시간보다 크다** — 영 수집을 **여러 스레드**(이 설정에서는 4개)로 했기 때문 |

### 풀 GC 로그 읽기

```
64.546: [Full GC [PSYoungGen: 15808K->0K(339456K)]
          [ParOldGen: 457753K->392528K(554432K)] 473561K->392528K(893888K)
          [PSPermGen: 56728K->56728K(115392K)], 1.3367080 secs]
          [Times: user=4.44 sys=0.01, real=1.34 secs]
```

- 영 제너레이션이 **0바이트**가 된다(서바이버 공간 포함 전부 비운다)
- 올드가 **457MB → 392MB**
- **permgen 크기는 변하지 않는다** — 대부분의 풀 GC에서 수집되지 않는다.
  **permgen 크기가 바뀌는 것이 permgen이 수집됐는지 알 수 있는 유일한 방법이다**
  (permgen이 꽉 차면 JVM이 permgen 수집을 위한 풀 GC를 돌린다)
- **실제 1.3초, CPU 4.4초** — 할 일이 훨씬 많다

> 풀 GC 후 힙 상태: **영 제너레이션은 완전히 비고, 올드는 압축되어 앞쪽에 몰리고 나머지가
> 빈 공간**이 된다.

### 적응형 vs 정적 힙 크기 튜닝

**두 가지 트레이드오프가 있다.**

**① 고전적인 시간 대 공간** — 큰 힙은 메모리를 더 쓰고, 그 대가로 (어느 정도까지는) 처리량이 높아진다.

**② GC 수행 시간** — 힙을 키우면 풀 GC 횟수는 줄지만 **GC 시간이 길어져 평균 응답 시간이
오히려 나빠질 수 있다.** 마찬가지로 영 제너레이션에 힙을 더 주면 풀 GC 정지가 짧아지지만
**올드 GC 빈도가 늘어난다.**

**저자의 실측 그래프 (GlassFish 주식 서블릿)**
- **256MB 힙**: 시간의 **36%** 를 GC에 쓴다. 처리량이 제한된다
- 힙을 키우면 처리량이 **급격히 증가** — **1,500MB까지**
- 그 뒤로는 증가가 완만하다. **GC 바운드가 아니게 된다**(GC에 약 6%). **수확 체감**
- **4,500MB 이후 처리량이 약간 감소** — 두 번째 트레이드오프에 도달했다.
  **추가 메모리가 GC 사이클을 훨씬 길게 만들고, 빈도가 낮아도 전체 처리량에 영향을 준다**

> 이 데이터는 **적응형 크기 조정을 끄고**(`-Xms` = `-Xmx`) 얻었다. 실험으로 최적 크기를 찾을 수
> 있지만 **대개 JVM에게 맡기는 편이 쉽다**(적응형이 기본이므로 보통 그렇게 된다).

### 두 개의 목표 플래그

```
-XX:MaxGCPauseMillis=N   # 감내할 최대 정지 시간. 기본 설정 안 됨
-XX:GCTimeRatio=N        # GC에 쓸 시간 비율. 기본 99
```

> **⚠️ `MaxGCPauseMillis` 를 0이나 50ms 같은 아주 작은 값으로 두고 싶어진다. 조심하라.**
> 이 목표는 **마이너와 풀 GC 양쪽에 적용된다.** 아주 작은 값을 쓰면 **50ms에 청소할 수 있는
> 아주 작은 올드 제너레이션**을 갖게 되고, JVM이 **아주아주 빈번한 풀 GC**를 수행해 성능이
> 처참해진다. **현실적으로, 실제로 달성 가능한 값을 써라.**

```
애플리케이션 스레드가 이상적으로 돌 시간 비율 = GCTimeRatio / (1 + GCTimeRatio)
```

기본값 99 → 0.99, 즉 **99%를 애플리케이션 처리에, 1%를 GC에.**

> **⚠️ 기본값의 숫자 배치에 속지 마라.** `GCTimeRatio` 가 95라고 GC가 5%까지 돈다는 뜻이 아니다 —
> **1.94%** 라는 뜻이다.

저자가 쓰는 역산 공식:
```
GCTimeRatio = 처리량목표 / (1 - 처리량목표)
```
95%(0.95) 목표 → **`GCTimeRatio` = 19.**

**JVM이 두 플래그를 쓰는 순서**
1. **`MaxGCPauseMillis` 가 우선한다.** 설정됐다면 정지 목표를 맞출 때까지 영·올드 크기를 조정
2. 그다음 **시간 비율 목표**를 맞출 때까지 힙 전체 크기를 키운다
3. 둘 다 맞으면 **두 목표를 만족하는 가장 작은 힙**이 되도록 줄인다

> **정지 시간 목표가 기본으로 설정되지 않으므로, 자동 힙 크기 조정의 통상적 효과는
> `GCTimeRatio` 목표를 맞출 때까지 힙이 커지는 것이다.**
>
> **저자의 현장 감각**: 기본값 99는 **꽤 낙관적**이다. 저자는 **GC에 3~6%를 쓰면서 잘 동작하는**
> 애플리케이션을 훨씬 자주 본다. 메모리가 심하게 제약된 환경에서는 **10~15%** 를 쓰기도 하는데,
> GC가 성능에 상당한 영향을 주지만 전체 목표는 여전히 충족된다.
> **다른 목표가 없다면 저자는 시간 비율 19(GC에 5%)로 시작한다.**

**실측 ① — GC가 적은 애플리케이션 (세션 저장 없음)**

| GC 설정 | 최종 힙 | GC 시간 비율 | OPS |
|---|---|---|---|
| 기본 | 649 MB | 0.9% | 9.2 |
| `MaxGCPauseMillis=50ms` | 560 MB | 1.0% | 9.2 |
| `Xms=Xmx=2048m` | 2 GB | 0.04% | 9.2 |

> **더 많은 것이 항상 더 좋은 건 아니다.** 2GB 힙은 GC 시간을 줄이지만 **GC가 여기서 지배적
> 성능 요인이 아니므로 처리량이 늘지 않는다. 늘 그렇듯 엉뚱한 영역을 최적화하는 데 시간을
> 쓴 것은 도움이 되지 않았다.**

**실측 ② — 세션에 이전 50개 요청 저장 (GC가 힘든 경우)**

| GC 설정 | 최종 힙 | GC 시간 비율 | OPS |
|---|---|---|---|
| 기본 | 1.7 GB | 9.3% | 8.4 |
| **`MaxGCPauseMillis=50ms`** | **588 MB** | **15.1%** | **7.9** |
| `Xms=Xmx=2048m` | 2 GB | 5.1% | **9.0** |
| `Xmx=3560M; MaxGCRatio=19` | 2.1 GB | 8.8% | **9.0** |

- JVM은 이 테스트에서 **1% 목표를 결코 만족시킬 수 없다.** 최선을 다해 1.7GB를 쓴다
- **비현실적인 정지 목표(50ms)를 주면 상황이 더 나빠진다.** 힙이 588MB로 유지되어
  **GC가 과도하게 잦아지고 처리량이 크게 떨어진다**
- **마지막 줄이 핵심이다** — 합리적 힙과 현실적 시간 비율(5%)을 주면 **JVM 스스로 약 2GB가
  최적임을 판단했고, 손으로 튜닝한 경우와 같은 처리량을 냈다**

# 2부. CMS 컬렉터

**세 가지 기본 연산**: ① 영 제너레이션 수집(모든 스레드 정지) ② 올드 제너레이션을 정리하는
**동시 사이클** ③ 필요하면 **풀 GC**.

### 영 수집

처리량 컬렉터와 아주 비슷하다.
```
89.853: [GC 89.853: [ParNew: 629120K->69888K(629120K), 0.1218970 secs]
                1303940K->772142K(2027264K), 0.1220090 secs]
                [Times: user=0.42 sys=0.02, real=0.12 secs]
```

### 동시 사이클의 여섯 단계

> 사이클이 끝나도 **올드 제너레이션은 압축되지 않는다.** 객체가 할당된 영역과 빈 영역이 섞여 있다.
> **영 수집이 에덴에서 올드로 객체를 옮길 때 JVM이 그 빈 영역을 쓰려고 시도한다.**

**① initial mark — 모든 스레드 정지**
```
89.976: [GC [1 CMS-initial-mark: 702254K(1398144K)]
                772530K(2027264K), 0.0830120 secs]
```
힙의 **GC 루트 객체를 전부 찾는** 단계. 올드가 1,398MB 중 702MB 점유. **0.08초 정지.**

**② mark — 동시 (정지 없음)**
```
90.059: [CMS-concurrent-mark-start]
90.887: [CMS-concurrent-mark: 0.823/0.828 secs]  [Times: user=1.11 real=0.83]
```
> 마킹 단계일 뿐이라 힙 점유에 대한 데이터가 없다. **데이터가 있었다면 0.83초 동안 애플리케이션
> 스레드가 계속 실행되며 영 제너레이션에 할당한 객체 때문에 힙이 커진 것을 보였을 것이다.**

**③ preclean — 동시**
```
90.887: [CMS-concurrent-preclean-start]
90.892: [CMS-concurrent-preclean: 0.005/0.005 secs]
```

**④ abortable preclean — 동시. 여기가 CMS 설계의 묘미다**
```
90.892: [CMS-concurrent-abortable-preclean-start]
92.392: [GC ... ParNew ...]                       ← 영 수집이 끼어든다
94.473: [CMS-concurrent-abortable-preclean: 3.451/3.581 secs]
```

> **왜 preclean을 두 번 하나?**
> **remark 단계는 동시가 아니라 모든 스레드를 멈춘다.** CMS는 **영 수집이 일어난 직후 바로
> remark가 따라오는 상황을 피하고 싶어 한다** — 그러면 애플리케이션이 **연달아 두 번** 멈추니까.
> **목표는 연속 정지를 막아 정지 길이를 최소화하는 것이다.**
>
> 그래서 abortable preclean은 **영 제너레이션이 약 50% 찰 때까지 기다린다.** 이론적으로
> **영 수집과 영 수집의 딱 중간**이라 연속 정지를 피할 최선의 기회다.
>
> **이 예에서**: 90.8초에 시작 → 약 1.5초 기다려 92.392초에 정규 영 수집 발생 → CMS는 과거
> 행동으로 다음 영 수집이 **약 4.2초 뒤**일 것으로 계산 → **2.1초 뒤(94.4초)에 preclean을
> 종료("abort")** 한다. (**이 단계는 그렇게 멈추는 것이 유일한 방법이라 "abort"라고 부른다.**)

**⑤ remark — 모든 스레드 정지**
```
94.474: [GC[YG occupancy: 466937 K (629120 K)]
        94.474: [Rescan (parallel) , 0.1850000 secs]
        94.659: [weak refs processing, 0.0000370 secs]
        94.659: [scrub string table, 0.0011530 secs]
                [1 CMS-remark: 734079K(1398144K)] ..., 0.1863430 secs]
```
**0.18초 정지.**

**⑥ sweep — 동시, 그리고 reset — 동시**
```
94.661: [CMS-concurrent-sweep-start]
95.223: [GC ... ParNew ...]          ← 영 수집이 또 끼어든다
95.474: [CMS-concurrent-sweep: 0.680/0.813 secs]
95.474: [CMS-concurrent-reset-start]
95.479: [CMS-concurrent-reset: 0.005/0.005 secs]
```

> **영 수집은 올드 수집 단계와 동시에 일어날 수 있다.** sweep 단계 동안 임의의 횟수만큼
> 영 수집이 있을 수 있고(abortable preclean 때문에 최소 한 번은 있다).

**얼마나 회수됐는지는 로그가 알려주지 않는다.** reset 줄에 힙 점유 정보가 없다.
**알아내려면 다음 영 수집을 봐야 한다.**
- 사이클 시작 전(89.853초): 힙 772MB 중 서바이버 69MB → **올드 약 703MB**
- 사이클 후(98.049초): **올드 약 504MB**
- → **CMS 사이클이 약 199MB를 정리했다**

### CMS의 세 가지 문제 신호

**① 동시 모드 실패 (concurrent mode failure)**
```
267.006: [GC ... [ParNew: 629120K->629120K(629120K), 0.0000200 secs]
        267.006: [CMS267.350: [CMS-concurrent-mark: 2.683/2.804 secs]
        (concurrent mode failure):
        1378132K->1366755K(1398144K), 5.6213320 secs] ...
```
**영 수집이 일어났는데 승격될 객체를 담을 공간이 올드에 부족한 경우.** CMS가 사실상 풀 GC를
수행한다. **모든 스레드가 5.6초 정지.**
> **이 연산은 단일 스레드다. 그래서 오래 걸리고, 힙이 커질수록 동시 모드 실패가 더 나빠진다.**

**② 승격 실패 (promotion failure) — 더 나쁘다**
```
6043.903: [GC ... [ParNew (promotion failed): 614254K->629120K(629120K), 0.16 secs]
        6044.217: [CMS: 1342523K->1336533K(2027264K), 30.7884210 secs] ...
        [Times: user=28.13 sys=0.38, real=28.13 secs]
```
**올드에 공간은 충분한데 빈 공간이 단편화되어 승격에 실패한 경우.** CMS는 공간이 충분하다고
가정했다(아니었으면 동시 모드 실패를 선언했을 것). 그 가정이 틀렸다.

**영 수집 도중(이미 모든 스레드가 멈춘 상태에서) 올드 제너레이션 전체를 수집하고 압축한다.**
- **좋은 소식**: 압축됐으니 단편화 문제가 (당분간) 해결됐다
- **나쁜 소식**: **28초 정지.** 동시 모드 실패보다 훨씬 길다 — **동시 모드 실패는 객체를 해제만
  하지만 이건 힙 전체를 압축하기 때문**

**③ 동시 GC 메시지 없는 풀 GC**
```
279.803: [Full GC 279.803: [CMS: 88569K->68870K(1398144K), 0.6714090 secs]
                [CMS Perm : 81919K->77654K(81920K)], 0.6716570 secs]
```
**permgen이 차서 수집이 필요한 경우.** `CMS Perm` 크기가 줄어든 것에 주목.
**기본적으로 CMS는 permgen(메타스페이스)을 수집하지 않으므로, 차면 풀 GC가 필요하다.**

### 동시 모드 실패 해결하기

**CMS 튜닝의 주된 관심사는 동시 모드 실패와 승격 실패가 없게 하는 것이다.**

**경주(race)의 구조**: 올드가 어느 정도(**기본 70%**) 차면 동시 사이클이 시작되고 백그라운드
스레드가 스캔을 시작한다. **CMS는 나머지 30%가 차기 전에 스캔과 해제를 끝내야 한다.
지면 동시 모드 실패다.**

**세 가지 대응**
1. **올드 제너레이션을 키운다** — 세대 비율을 바꾸거나 힙 전체를 늘린다
2. **백그라운드 스레드를 더 자주 돌린다**
3. **백그라운드 스레드를 더 많이 쓴다**

> **적응형 크기 조정과 CMS**
> CMS도 `MaxGCPauseMillis`·`GCTimeRatio` 로 크기를 정한다. **하지만 중요한 차이가 하나 있다 —
> 풀 GC가 일어나지 않는 한 영 제너레이션의 크기는 절대 변경되지 않는다.**
> **CMS의 목표가 풀 수집을 하지 않는 것이므로, 잘 튜닝된 CMS 애플리케이션은 영 제너레이션
> 크기를 결코 조정하지 않는다.**
>
> **프로그램 시작 중에 동시 모드 실패가 잦을 수 있다** — CMS가 힙과 permgen을 적응적으로
> 조정하는 중이니까. **초기 힙(과 permgen)을 크게 잡고 시작하는 것이 좋은 생각일 수 있다.**

**백그라운드 스레드를 더 자주 돌리기**
```
-XX:CMSInitiatingOccupancyFraction=N
-XX:+UseCMSInitiatingOccupancyOnly
```
> **둘 다 설정하면 CMS를 이해하기도 쉬워진다** — 그러면 CMS가 **올드가 찬 비율만 보고**
> 백그라운드 스레드 시작을 결정한다. `UseCMSInitiatingOccupancyOnly` 는 기본 `false` 이고,
> 그러면 **더 복잡한 알고리즘**을 쓴다. **더 일찍 시작해야 한다면 가장 단순한 방식으로 하는 게 낫다.**

**적정값 찾는 법**: 로그에서 동시 모드 실패를 찾고, **가장 최근의 CMS 사이클이 언제 시작했는지
거슬러 본다.** `CMS-initial-mark` 줄이 시작 시점의 올드 점유율을 보여 준다.
위 예에서 702MB/1,398MB = **약 50%.** 그게 충분히 빠르지 않았으므로 **50보다 낮게 설정해야 한다.**
(기본값이 70인데 50에 시작한 이유는 `UseCMSInitiatingOccupancyOnly` 가 설정되지 않았기 때문이다.)

> **0으로 두고 싶은 유혹 — 트레이드오프를 알고 하라.**
>
> **첫째, CPU 시간.** 백그라운드 CMS 스레드가 계속 돌고 **각각 CPU 하나를 100% 소비한다.**
> 여러 스레드가 동시에 도는 짧은 구간에는 CPU가 치솟는다.
>
> **반면 그 CPU 사이클을 쓰는 게 꼭 문제는 아니다.** 최선의 경우에도 백그라운드 스레드는
> 언젠가 돌아야 하므로 **머신에는 항상 그 CPU가 있어야 한다.**
>
> **그 CPU를 다른 일에 쓸 수 있나? 보통 아니다.** 다른 애플리케이션은 **CMS 스레드가 언제 도는지
> 알 방법이 없다.** 결과적으로 둘이 CPU를 두고 경쟁하고, **CMS 스레드가 경주에서 질 가능성이
> 높아진다.**
>
> **둘째(훨씬 중요), 정지.** CMS 사이클의 특정 단계는 모든 스레드를 멈춘다. **CMS를 쓰는 주된
> 이유가 GC 정지 영향을 줄이는 것인데, 필요 이상으로 자주 돌리면 역효과다.** 백그라운드 GC를
> 계속 돌리면 **전체 정지가 과도해져 결국 성능이 떨어진다.**
>
> **트레이드오프를 받아들일 수 없다면, `CMSInitiatingOccupancyFraction` 을 힙의 라이브 데이터
> 양 + 최소 10~20% 보다 높게 잡지 마라.**

**백그라운드 스레드 수 조정**
```
-XX:ConcGCThreads=N
ConcGCThreads = (3 + ParallelGCThreads) / 4     # 정수 연산
```
`ParallelGCThreads` 4까지 → 1개, 5~8 → 2개, ...

**너무 많으면 애플리케이션 스레드에서 CPU를 뺏는다** — 사실상 프로그램에 작은 정지가 생긴다.
**CPU가 많은 시스템에서는 기본값이 너무 클 수도 있다.** 동시 모드 실패가 없다면 **줄여서 CPU를
아낄 수 있다.**

### permgen을 위한 CMS 튜닝

**앱 서버에 계속 (재)배포하는 개발자에게 가장 자주 일어난다.**

```
-XX:+CMSPermGenSweepingEnabled           # Java 7, 기본 false
-XX:CMSInitiatingPermOccupancyFraction=N # 기본 80%. 올드와 독립적인 트리거
-XX:+CMSClassUnloadingEnabled            # ★ 반드시 함께
```

> **⚠️ permgen 스위핑을 켜는 것만으로는 절반이다.** 참조되지 않는 **클래스를 실제로 해제하려면
> `CMSClassUnloadingEnabled` 를 설정해야 한다.** 안 그러면 잡다한 객체 몇 개만 해제되고
> **클래스 메타데이터는 전혀 해제되지 않는다.** permgen 데이터의 대부분이 클래스 메타데이터이므로
> **이 플래그는 항상 함께 써야 한다.**
>
> **Java 8에서는 CMS가 기본으로 메타스페이스에서 언로드된 클래스를 정리한다**
> (`CMSClassUnloadingEnabled` 가 기본 `true`).

### 증분 CMS (iCMS)

> **⚠️ Java 8에서 폐기 예정(deprecated)이다.** 여전히 존재하지만 Java 9에는 없을 수 있다.
> **멀티 CPU가 모든 시스템의 표준이 되면서**(저자 왈 "내 전화기도 쿼드코어다") **iCMS의 근거가
> 약해졌다. CPU가 제한된 시스템에서는 G1을 고려하라** — G1의 백그라운드 스레드도 백그라운드
> 사이클 중에 주기적으로 멈춰 CPU 경쟁을 제한한다.

```
-XX:+CMSIncrementalMode
-XX:CMSIncrementalSafetyFactor=N
-XX:CMSIncrementalDutyCycleMin=N
-XX:-CMSIncrementalPacing
```

**듀티 사이클** 원리로 동작한다 — 백그라운드 스레드가 애플리케이션에 시간을 양보하기 전까지
얼마나 스캔할지. **OS 레벨에서는 이미 시분할되고 있고, 이 플래그들은 "자발적으로 멈추는" 시간을
제어한다.**

듀티 사이클은 **영 수집 사이의 시간** 기준으로 계산된다. 기본으로 그 시간의 **20%** 동안 돌 수 있다
(기본 듀티 10% + 안전 계수 10%). 부족하면 동시 모드 실패가 난다.

**`CMSIncrementalSafetyFactor` 부터 올려라**(최대 90 → 증분 사이클이 100% 시간 동안 돈다).
`CMSIncrementalDutyCycleMin` 을 직접 올릴 수도 있지만, **JVM이 승격량을 모니터링하며 자동
조정하므로 스스로 낮출 수 있다.** 버스트가 있는 애플리케이션이면 계산이 자주 틀리므로
**듀티 사이클을 명시하고 `CMSIncrementalDutyCycle` 을 꺼서 자동 조정을 막아야 한다.**

# 3부. G1 컬렉터

**힙의 개별 리전(기본 약 2,048개)에서 동작하는 동시 컬렉터.** 각 리전은 올드나 뉴에 속할 수 있고
**세대별 리전이 연속일 필요가 없다.**

> **올드 제너레이션에 리전을 두는 아이디어**: 백그라운드 스레드가 참조되지 않는 객체를 찾을 때,
> **어떤 리전은 다른 리전보다 쓰레기가 많다.** 리전의 실제 수집에는 여전히 스레드 정지가 필요하지만,
> **G1은 대부분이 쓰레기인 리전에 집중해 그것만 비우는 데 조금의 시간만 쓸 수 있다.**
> **이것이 Garbage First라는 이름의 유래다.**

**영 제너레이션에는 해당하지 않는다** — 영 GC 때는 영 제너레이션 전체가 해제되거나 승격된다.
그래도 영 제너레이션을 리전으로 정의하는데, **부분적으로는 리전이 미리 정의되어 있으면 세대
크기 조정이 훨씬 쉬워지기 때문**이다.

**네 가지 주요 연산**: 영 수집 / 백그라운드 동시 사이클 / **혼합(mixed) 수집** / 필요시 풀 GC.

### 영 수집

```
23.430: [GC pause (young), 0.23094400 secs]
   [Eden: 1286M(1286M)->0B(1212M)
        Survivors: 78M->152M Heap: 1454M(4096M)->242M(4096M)]
   [Times: user=0.85 sys=0.05, real=0.23 secs]
```
에덴에서 **1,286MB**가 빠져나갔고(크기는 1,212MB로 조정), 그중 **74MB가 서바이버로**
(78MB→152MB), 나머지는 해제됐다. **힙 전체 점유가 1,212MB 줄어든 것으로 해제를 확인할 수 있다.**

### 동시 사이클

> **세 가지를 관찰해야 한다.**
> **①** 영 제너레이션 점유가 바뀌었다 — **동시 사이클 중에 영 수집이 최소 한 번(어쩌면 여러 번)
> 일어난다**
> **②** 일부 리전이 **X로 표시**됐다 — 마킹 사이클이 **대부분 쓰레기라고 판정한** 올드 리전들이다
> (여전히 데이터를 담고 있다)
> **③ 사이클이 끝난 뒤 올드 제너레이션이 오히려 더 찼다.** 마킹 중에 일어난 영 수집이 데이터를
> 승격했기 때문이다. 게다가 **마킹 사이클은 올드의 데이터를 실제로 해제하지 않는다 —
> 대부분 쓰레기인 리전을 식별할 뿐이고, 그 데이터는 나중 사이클에서 해제된다.**

**단계별로**

**① initial-mark — 스레드 정지. 영 수집과 함께 수행한다**
```
50.541: [GC pause (young) (initial-mark), 0.27767100 secs]
```
> **initial mark도 모든 스레드 정지가 필요하므로, G1은 영 GC 사이클을 활용해 그 일을 한다.**
> 영향은 크지 않았다 — **CPU 사이클을 20% 더 썼지만 정지는 아주 조금만 길어졌다.**
> (다행히 병렬 G1 스레드용 여유 CPU가 있었다. 없었다면 정지가 더 길었을 것이다.)

**② 루트 리전 스캔 — 동시. 하지만 중요한 함정이 있다**
```
50.819: [GC concurrent-root-region-scan-start]
51.408: [GC concurrent-root-region-scan-end, 0.5890230]
```
> **⚠️ 이 단계는 영 수집에 의해 중단될 수 없다.** 스캔 중에 영 제너레이션이 차버리면,
> **모든 스레드를 멈춘 영 수집이 루트 스캔이 끝날 때까지 기다려야 한다** — 평소보다 긴 정지.
> 로그에서는 이렇게 보인다:
> ```
> 350.994: [GC pause (young)
>         351.093: [GC concurrent-root-region-scan-end, 0.6100090]
>         351.093: [GC concurrent-mark-start], 0.37559600 secs]
> ```
> GC 정지가 루트 스캔 종료 **전에** 시작됐고(출력이 서로 끼어 있다) 이는 **기다렸다**는 표시다.
> 타임스탬프상 약 **100ms** 기다렸다. **자주 일어나면 G1을 더 잘 튜닝해야 한다는 신호다.**

**③ 동시 마킹 → ④ remark(정지) → ⑤ cleanup(정지) → ⑥ 동시 cleanup**
```
111.382: [GC concurrent-mark-start] ... 120.905: [GC concurrent-mark-end, 9.5225160 sec]
120.910: [GC remark ... 0.0718990 secs]
120.985: [GC cleanup 3510M->3434M(4096M), 0.0111040 secs]
120.996: [GC concurrent-cleanup-start] / -end
```
**동시 마킹은 중단될 수 있으므로 이 단계에는 영 수집이 일어날 수 있다.**

> **여기까지 왔지만 실제로 해제된 것은 거의 없다.** cleanup 단계에서 약간 회수됐을 뿐,
> G1이 한 일은 **대부분 쓰레기인 올드 리전을 식별한 것**이다.

### 혼합 GC (Mixed GC)

**정상 영 수집을 하면서 동시에 백그라운드 스캔이 표시한 리전 일부를 수집**하기 때문에 "혼합"이다.

```
79.826: [GC pause (mixed), 0.26161600 secs]
   [Eden: 1222M(1222M)->0B(1220M)
        Survivors: 142M->144M Heap: 3200M(4096M)->1964M(4096M)]
```

표시된 리전에서 **살아 있는 데이터는 다른 리전으로 옮겨진다.**
> **이것이 G1이 CMS보다 단편화된 힙을 덜 겪는 이유다 — 이렇게 객체를 옮기는 것 자체가
> 진행하면서 힙을 압축하는 것이다.**

**힙 전체 사용량이 에덴에서 빠진 1,222MB보다 더 줄었다.** 차이(16MB)가 작아 보이지만,
**같은 시점에 서바이버 일부가 올드로 승격됐고, 각 혼합 GC는 대상 올드 리전의 일부만 정리한다.**

**혼합 GC 사이클은 표시된 리전이 (거의) 다 수집될 때까지 계속되고**, 그다음 G1은 정규 영 GC로
돌아간다. 결국 다음에 해제할 리전을 정하기 위해 또 동시 사이클을 시작한다.

### G1의 네 가지 풀 GC 유발 요인

**① 동시 모드 실패 (concurrent mode failure)**
```
51.408: [GC concurrent-mark-start]
65.473: [Full GC 4095M->1395M(4096M), 6.1963770 secs]
71.669: [GC concurrent-mark-abort]
```
마킹 사이클이 끝나기 전에 올드가 찼다. **G1이 마킹 사이클을 중단한다.**
→ **힙을 늘리거나, 백그라운드 처리를 더 일찍 시작하거나, 사이클을 더 빨리 돌게(스레드 추가) 튜닝**

**② 승격 실패 (promotion failure)**
마킹을 끝내고 혼합 GC를 시작했지만, **충분히 정리하기 전에 너무 많이 승격되어 올드가 부족해졌다.**
로그에서 **혼합 GC 바로 뒤에 풀 GC**가 온다.
→ **혼합 수집이 더 빨리 일어나야 한다. 영 수집마다 올드 리전을 더 많이 처리해야 한다**

**③ 대피 실패 (evacuation failure)**
```
60.238: [GC pause (young) (to-space overflow), 0.41546900 secs]
```
영 수집 시 **서바이버와 올드에 살아남은 객체를 담을 공간이 부족**하다.
→ **힙이 대체로 꽉 찼거나 단편화됐다는 표시.** G1이 보상하려 하지만 **결국 풀 GC로 끝난다.**
쉬운 해법은 힙 증가

**④ 거대(humongous) 할당 실패**
아주 큰 객체를 할당하는 애플리케이션에서 발생.
> **⚠️ 표준 GC 로그로는 이 상황을 진단할 도구가 없다. 뚜렷한 이유 없이 풀 GC가 일어난다면
> 거대 할당 문제일 가능성이 높다.**

### G1 튜닝

**주요 목표는 풀 GC를 요구하는 동시 모드 실패·대피 실패가 없게 하는 것이다.**
같은 기법이 **루트 리전 스캔을 기다리는 영 GC가 잦은 경우**에도 쓰인다.

**네 가지 대응**
1. 힙 전체 또는 세대 비율로 **올드를 키운다**
2. **백그라운드 스레드를 늘린다**(CPU가 충분하다면)
3. **G1 백그라운드 활동을 더 자주** 수행한다
4. **혼합 GC 사이클에서 하는 일의 양을 늘린다**

> **하지만 G1의 목표 중 하나가 "그렇게 많이 튜닝할 필요가 없어야 한다"는 것이다.**
> **G1은 주로 플래그 하나로 튜닝한다 — `-XX:MaxGCPauseMillis=N`.**
> **처리량 컬렉터와 달리 G1에서는 기본값이 있다: 200ms.**
>
> 정지가 이 값을 넘기 시작하면 G1이 보상한다 — 영:올드 비율 조정, 힙 크기 조정, 백그라운드
> 처리 조기 시작, **테뉴어링 임계치 변경**, 그리고 **(가장 크게) 혼합 GC 사이클에서 처리하는
> 올드 리전 수의 증감.**
>
> **⚠️ 늘 그렇듯 트레이드오프**: 값을 줄이면 영 크기가 줄어 목표를 맞추지만 **영 GC가 잦아진다.**
> 게다가 **혼합 GC에서 수집할 수 있는 올드 리전 수가 줄어 동시 모드 실패 가능성이 커진다.**

**백그라운드 스레드**
```
ConcGCThreads = (ParallelGCThreads + 2) / 4    # CMS보다 한 단계 늦게 증가
```

**더 자주 (또는 덜) 돌리기**
```
-XX:InitiatingHeapOccupancyPercent=N   # 기본 45
```
> **⚠️ CMS와 달리 이 설정은 올드가 아니라 힙 전체 사용량 기준이다.**
> **그리고 이 값은 상수다 — G1은 정지 목표를 맞추려고 이 숫자를 절대 바꾸지 않는다.**
>
> - **너무 높으면** 동시 단계가 완료되기 전에 나머지 힙이 차서 **풀 GC**를 하게 된다
> - **너무 낮으면** 필요 이상으로 백그라운드 GC 처리를 한다. CPU 사이클은 어차피 있어야 하니
>   추가 CPU 사용이 꼭 중요한 건 아니지만, **애플리케이션을 멈추는 작은 정지가 더 많아진다는
>   심각한 페널티가 있다. 그 정지들은 빠르게 누적되므로 너무 잦은 백그라운드 스위핑은 피해야 한다.**
>
> **동시 사이클 후 힙 크기를 확인하고, `InitiatingHeapOccupancyPercent` 를 그보다 높게 설정하라.**

**혼합 GC 사이클 튜닝**

> **핵심 구조**: 동시 사이클 후 G1은 **이전에 표시된 올드 리전이 전부 수집될 때까지 새 동시
> 사이클을 시작할 수 없다.** 그래서 **혼합 GC에서 리전을 더 많이 처리하면(혼합 GC 횟수가 줄면)
> 마킹 사이클을 더 일찍 시작할 수 있다.**

혼합 GC의 작업량은 **세 요인**에 달렸다.
1. **애초에 대부분 쓰레기로 판정된 리전 수** — 직접 영향을 줄 방법이 없다.
   **리전이 35% 쓰레기면 수집 대상이 된다**
   (실험 빌드의 `-XX:G1MixedGCLiveThresholdPercent=N`)
2. **`-XX:G1MixedGCCountTarget=N`** — 그 리전들을 처리할 **최대 혼합 GC 사이클 수. 기본 8.**
   **줄이면 승격 실패를 극복할 수 있다**(혼합 GC 정지가 길어지는 대가).
   반대로 혼합 GC 정지가 너무 길면 늘린다 — 다만 **다음 동시 사이클을 너무 늦추면 동시 모드
   실패가 날 수 있다**
3. **`MaxGCPauseMillis`** — `G1MixedGCCountTarget` 은 **상한**이다. 정지 목표 안에 시간이 남으면
   **G1은 표시된 올드 리전의 1/8보다 많이 수집한다.** 그래서 **`MaxGCPauseMillis` 를 늘리면
   혼합 GC마다 더 많은 올드 리전을 수집할 수 있고, 결과적으로 동시 사이클을 더 일찍 시작할 수 있다**

# 4부. 고급 튜닝

## 테뉴어링과 서바이버 공간

**왜 서바이버 공간이 있나** — 5장의 `BigDecimal` 루프를 생각해 보자. **루프 중간에 GC가 일어나면
아주 수명이 짧은 `BigDecimal` 객체들이 운이 나쁘다** — 방금 만들어져 사용 중이라 해제할 수 없지만,
**올드로 옮길 만큼 오래 살지도 않을 것이다.**

**서바이버 공간은 객체에게 영 제너레이션에 머물며 수집될 추가 기회를 준다.**

**동작 방식**
- 첫 영 수집: 에덴 → **서바이버 0**
- 다음 수집: 에덴 + **서바이버 0** → **서바이버 1**. 이제 에덴과 서바이버 0이 완전히 빈다
- 그다음: 에덴 + 서바이버 1 → 서바이버 0. 반복
- 서바이버 공간은 **"to"와 "from"** 이라고도 하며, **매 수집마다 두 공간 사이에서 포인터가 바뀐다**

**올드로 옮겨지는 두 경우**
1. **대상 서바이버 공간이 찼을 때** — 에덴에 남은 살아 있는 객체가 **곧바로 올드로** 간다
2. **테뉴어링 임계치**를 넘었을 때 — 서바이버에 머물 수 있는 GC 사이클 수의 한계

**크기 플래그**
```
서바이버 공간 크기 = 영 크기 / (InitialSurvivorRatio + 2)     # 기본 8 → 각 10%
최대 서바이버 크기 = 영 크기 / (MinSurvivorRatio + 2)         # 기본 3 → 최대 20%
```
> **⚠️ 이름이 직관에 반한다** — **비율의 최솟값이 서바이버 공간의 최댓값**을 준다.

```
-XX:TargetSurvivorRatio=N   # GC 후 서바이버가 몇 % 차게 할지. 기본 50
```
고정하려면 `SurvivorRatio` 를 설정하고 `UseAdaptiveSizePolicy` 를 끈다
(**단, 그러면 올드·뉴 세대에도 적용된다**).

**테뉴어링 임계치**
```
-XX:InitialTenuringThreshold=N   # 처리량·G1: 7, CMS: 6
-XX:MaxTenuringThreshold=N       # 처리량·G1: 15, CMS: 6
```
**JVM이 1과 최댓값 사이에서 계속 최적값을 계산한다.**

> **항상 테뉴어 / 절대 테뉴어 안 함**
> **초기 임계치를 최댓값과 같게 시작해도 JVM은 그 값을 낮출 수 있다.**
> - `-XX:+AlwaysTenure`(기본 false) — `MaxTenuringThreshold=0` 과 사실상 같다.
>   **아주아주 드문 상황**이다. 영 수집에서 살아남은 객체가 **항상 올드로 승격**된다
> - `-XX:+NeverTenure`(기본 false) — 초기·최대 임계치를 무한처럼 다루고 **JVM이 임계치를 낮추는
>   것도 막는다.** 서바이버에 공간이 있는 한 어떤 객체도 승격되지 않는다

### 진단 — `-XX:+PrintTenuringDistribution`

> **가장 중요하게 볼 것: 서바이버 공간이 너무 작아서 마이너 GC 때 객체가 에덴에서 올드로 곧바로
> 승격되고 있는가.** 그러면 **수명이 짧은 객체가 올드를 채워 풀 GC가 너무 자주 일어난다.**

**처리량 컬렉터의 로그는 힌트만 준다:**
```
Desired survivor size 39059456 bytes, new threshold 1 (max 15)
```
서바이버 하나의 희망 크기가 660MB 영 제너레이션 중 39MB(약 11%). **명확한 답은 없지만,
JVM이 테뉴어링 임계치를 1로 조정했다는 사실이 대부분의 객체를 어차피 올드로 직접 승격하고
있다고 판단했음을 가리킨다.**

**G1이나 CMS는 더 유익한 출력을 준다:**
```
Desired survivor size 35782656 bytes, new threshold 2 (max 6)
 - age   1:   33291392 bytes,   33291392 total
 - age   2:    4098176 bytes,   37389568 total
```
희망 크기 **35MB인데 승격할 데이터가 37MB** → **서바이버가 넘치고 있다.**

### 대응 — 이 절의 판단이 미묘하다

> **개선 가능한지는 애플리케이션에 매우 의존한다.** 객체가 몇 GC 사이클보다 오래 살 거라면
> **어차피 올드로 갈 것이므로 서바이버와 임계치를 조정해도 별 도움이 안 된다.**
> **몇 사이클 뒤에 사라질 객체라면** 서바이버를 더 효율적으로 만들어 성능을 얻을 수 있다.

- **서바이버를 키우면**(비율을 낮추면) **에덴에서 메모리를 뺏어 온다.** 객체가 실제로 할당되는
  곳이므로 **마이너 GC 전에 할당할 수 있는 객체가 줄어든다. 그래서 대개 권장하지 않는다**
- **영 제너레이션을 키우면** 역효과일 수 있다 — 승격은 덜 되지만 **올드가 작아져 풀 GC가 잦아진다**
- **힙 전체를 키울 수 있다면 그것이 최선이다.** 좋은 절차는 **힙(또는 최소한 영 제너레이션)을
  늘리면서 서바이버 비율을 낮추는 것** — 그러면 에덴보다 서바이버가 더 많이 커진다.
  **영 수집 횟수는 비슷하게 유지되면서 풀 GC는 줄어든다**
- 서바이버가 절대 넘치지 않게 조정됐다면, **`MaxTenuringThreshold` 를 올려 몇 사이클 더
  머물게 할 수 있다.** ⚠️ **다만 오래 머물면 향후 영 수집 때 서바이버 공간이 부족해져
  다시 직접 승격이 시작될 가능성이 높아진다**

## 큰 객체 할당

### TLAB (Thread-Local Allocation Buffer)

> **에덴에서의 할당이 빠른 한 가지 이유는 각 스레드가 객체를 할당하는 전용 영역(TLAB)을
> 갖기 때문이다.** 공유 공간에 직접 할당하면 빈 공간 포인터를 관리하는 **동기화**가 필요하다.
> **스레드마다 전용 할당 영역을 두면 동기화가 필요 없다.**
> (**락 경합을 막는 스레드 로컬 변수의 변형이다** — 9장)

**중요한 것은 TLAB이 작다는 점이다. 큰 객체는 TLAB에 할당할 수 없고, 힙에서 직접 할당해야 하며
동기화 때문에 추가 시간이 든다.**

**TLAB이 찼을 때 JVM의 선택 (예: TLAB 100KB 중 75KB 사용, 30KB 요청)**
- **TLAB을 "은퇴(retire)"시키고 새로 할당** → **에덴 공간 25KB 낭비**
- **객체를 힙에 직접 할당하고 기존 TLAB 유지** → 다음 객체가 남은 25KB에 맞기를 기대

**TLAB 크기는 세 가지에 기반한다**: 스레드 수, 에덴 크기, **스레드의 할당률.**

> **두 종류의 애플리케이션이 TLAB 튜닝에서 이득을 본다**: ① 큰 객체를 많이 할당하는 것
> ② **에덴 크기 대비 스레드 수가 상대적으로 많은 것**
>
> `-XX:-UseTLAB` 로 끌 수 있지만 **성능 향상이 커서 끄는 건 언제나 나쁜 생각이다.**

**할당률에 기반하므로 최적 TLAB 크기를 확정적으로 예측하는 것은 불가능하다.**
대신 **TLAB 밖 할당이 일어나는지 모니터링**한다.

**JFR이 다른 도구보다 훨씬 강력한 또 하나의 경우다.**
- **정상 예시**: 5초간 TLAB 밖 할당 49개, 최대 크기 48바이트. **최소 TLAB 크기가 1.35MB이므로,
  이 객체들은 크기 때문이 아니라 할당 시점에 TLAB이 꽉 차 있었기 때문에 힙에 할당된 것이다.**
  영 GC 직전(에덴이 차면서)에 전형적이다. 총 1.59KB — 걱정할 수준이 아니다
- **문제 예시**: TLAB 안 952.96MB vs **TLAB 밖 568.32MB.** 애플리케이션이 더 작은 객체를 쓰거나
  더 큰 TLAB에 할당하도록 튜닝하면 이득이 있다.
  **JFR에는 실제 할당된 객체와 할당 시점 스택까지 보여 주는 탭이 있어 문제를 아주 빨리 짚어낸다**

**오픈소스 JVM(JFR 없음)에서는 `-XX:+PrintTLAB`:**
```
TLAB: gc thread: 0x00007f3c10b8f800 [id: 18519] desired_size: 221KB
    slow allocs: 8  refill waste: 3536B alloc: 0.01613    11058KB
    refills: 73 waste  0.1% gc: 10368B slow: 2112B fast: 0B
```
- `gc` = **GC 중에 출력됐다는 뜻**이고 스레드 자체는 일반 애플리케이션 스레드다
- **`slow allocs: 8`** = 지난 영 수집 이후 **힙에서 8개 할당**. 그 스레드 전체 할당의 **1.613%**
- **`waste 0.1%`** 는 세 가지에서 온다 — 현재 GC 시작 시 TLAB의 빈 공간 10,336바이트,
  은퇴한 다른 TLAB의 빈 공간 2,112바이트, 특수 "fast" 할당자로 할당된 0바이트

```
TLAB totals: thrds: 66  refills: 3234 max: 105
        slow allocs: 406 max 14 waste: 1.1% ...
```
66개 스레드가 총 3,234번 리필(최대 105), **힙 할당 406회(한 스레드 최대 14회).**

**TLAB 크기 조정**
```
-XX:TLABSize=N               # 초기 크기만. 0 = 동적 계산
-XX:-ResizeTLAB              # GC마다 재조정 방지 (기본 true)
-XX:TLABWasteTargetPercent=N # refill waste 임계치. 기본 TLAB의 1%
-XX:TLABWasteIncrement=N     # 힙 할당마다 증가. 기본 4
-XX:MinTLABSize=N            # 기본 2KB. 최대는 약 1GB로 변경 불가
```
> **`TLABWasteIncrement` 의 역할**: 힙 밖 할당이 일어날 때마다 목표 퍼센트를 올려
> **스레드가 임계치에 도달해 계속 힙에 할당하는 것을 막는다** — 목표가 올라갈수록 TLAB이 은퇴할
> 가능성이 커진다. `TLABWasteTargetPercent` 를 조정하면 **TLAB 크기도 함께 바뀌므로 효과가
> 항상 예측 가능하지는 않다.**

> **큰 객체를 많이 할당하는 애플리케이션은 TLAB 튜닝이 필요할 수 있다 — 다만 애플리케이션에서
> 더 작은 객체를 쓰는 것이 대개 더 나은 접근이다.**

### 거대 객체 (Humongous Objects)

**TLAB 밖 객체도 가능하면 에덴에 할당된다. 에덴에 안 맞으면 올드에 직접 할당해야 한다.**
그러면 **정상 GC 수명주기를 못 타므로, 수명이 짧으면 GC에 악영향**이다.
**그 경우 할 수 있는 건 애플리케이션이 그런 단명 거대 객체를 필요로 하지 않게 바꾸는 것뿐이다.**

**G1에서는 다르게 취급된다 — G1 리전보다 크면 올드에 할당한다.**

**G1 리전 크기**
```
region_size = 1 << log(Initial Heap Size / 2048);   # 2의 거듭제곱
```
**리전 크기는 동적이 아니라 시작 시 `-Xms` 기준으로 정해진다.**

| 힙 크기 | 기본 G1 리전 크기 |
|---|---|
| 4GB 미만 | 1 MB |
| 4~8 GB | 2 MB |
| 8~16 GB | 4 MB |
| 16~32 GB | 8 MB |
| 32~64 GB | 16 MB |
| 64GB 초과 | 32 MB |

```
-XX:G1HeapRegionSize=N   # 2의 거듭제곱이어야 한다. 아니면 가까운 아래 거듭제곱으로 내림
```

> **G1 리전 크기와 큰 힙 — 거대 객체와 무관한 또 하나의 튜닝 사유**
> `-Xms2G -Xmx32G` 처럼 범위가 아주 넓으면 **리전 크기가 1MB**가 된다. 힙이 완전히 확장되면
> **32,000개 리전**이다. **G1 알고리즘은 리전 수가 2,048에 가깝다는 전제로 설계됐다.**
> **예상 힙 크기에서 2,048개에 가깝도록 리전 크기를 키워라.**

**G1의 거대 객체 할당 문제**
> **거대 객체는 연속된 G1 리전에 할당돼야 한다.** 리전이 1MB이고 3.1MB 배열을 할당하려면
> **올드 제너레이션에서 연속된 리전 4개를 찾아야 한다**(마지막 리전의 0.9MB는 낭비).
> **이것은 G1의 정상적인 압축 방식 — 얼마나 찼는지에 따라 임의의 리전을 해제하는 것 — 을 무너뜨린다.**
> **G1은 연속 리전을 찾기 위해 풀 GC를 수행해야 하는 경우가 많다.**
>
> **올드에 직접 할당되므로 영 수집에서 해제될 수 없다. 단명 객체라면 컬렉터의 세대별 설계도
> 무너진다.** 밝은 면은 **자기가 점유한 리전의 유일한 객체이므로 빨리 해제될 수 있다**는 것이다.
> 거대 객체는 **혼합 GC가 아니라 동시 사이클의 cleanup 단계에서 해제된다.**

**진단**: `PrintAdaptiveSizePolicy` 를 켜야 한다.
```
5.349: [G1Ergonomics (Concurrent Cycles) request concurrent cycle initiation
    reason: occupancy higher than threshold, occupancy: 483393536 bytes,
    allocation request: 524304 bytes, ...
    source: concurrent humongous allocation]
```
연속 리전을 못 찾으면 **힙 확장 시도 → 실패 → 풀 GC:**
```
25.270: [G1Ergonomics (Heap Sizing) did not expand the heap,
    reason: heap expansion operation failed]
25.270: [Full GC 1535M->1521M(3072M), 1.0358230 secs]
```

**해법 계산**: **G1은 리전의 50% 넘게 차지하면 거대 객체로 본다.** 문제 객체가 524,304바이트면
**리전이 최소 1.1MB** 여야 하고, **2의 거듭제곱이므로 2MB로 설정**해야 한다.
> **다만 더 나은 다음 단계는 JVM을 그 객체에 맞춰 튜닝하는 것이 아니라 객체 크기를 줄이는 것이다.**

> **적용 조건**: 최소 G1 리전이 1MB이므로 **512KB 이상 객체를 할당해야 이 얘기가 해당된다.**

## AggressiveHeap — 쓰지 마라

`-XX:+AggressiveHeap`(기본 false)는 **메모리가 많은 아주 큰 머신에서 JVM 하나를 돌릴 때 적절한
여러 인자를 쉽게 설정하려던 초기 시도**다. **64비트 JVM에만 적용된다.**

> **더 이상 권장되지 않는다**(공식 폐기는 아니다). **문제는 실제로 채택하는 튜닝을 감춰서
> JVM이 무엇을 설정하는지 알아내기 아주 어렵다는 것이다.** 일부 값은 이제 머신 정보에 기반해
> **ergonomic하게 더 잘 설정되므로, 이 플래그를 켜면 오히려 성능이 나빠지는 경우가 실제로 있다.**
> 저자는 이 플래그를 넣고 나중에 그 값을 덮어쓰는 명령행을 자주 봤다.
> (**기록해 두자면 그건 동작한다 — 현재는 뒤에 오는 값이 앞을 덮는다. 다만 보장된 동작은 아니다.**)

| 플래그 | 설정값 |
|---|---|
| `Xmx` | 전체 메모리의 절반, 또는 전체 메모리 − 160MB 중 작은 값 |
| `Xms` | `Xmx` 와 동일 |
| `NewSize` | `Xmx` 의 3/8 |
| `UseLargePages` | true |
| `ResizeTLAB` | false |
| `TLABSize` | 256 KB |
| `UseParallelGC` | true |
| `YoungPLABSize` | 256 KB (기본 4KB) |
| `OldPLABSize` | 8 KB (기본 1KB) |
| `ThresholdTolerance` | 100 (기본 10) |
| **`ScavengeBeforeFullGC`** | **false (기본 true)** |
| `BindGCTaskThreadsToCPUs` | true (기본 false) |

**책에서 여기서만 다루는 개념들**
- **PLAB (promotion-local allocation buffer)** — GC 중 세대를 스캐빈징할 때 쓰는 **스레드별 영역.**
  각 스레드가 특정 PLAB로 승격할 수 있어 **동기화가 필요 없다(TLAB과 유사).**
- **`ScavengeBeforeFullGC=false`** — 풀 GC 전에 영 GC를 하지 않는다는 뜻인데
  **대개 나쁜 일이다.** 수집 가능한 영 제너레이션의 쓰레기 객체가 **올드 객체의 수집을 막을 수
  있기 때문**이다. 어느 시점(적어도 특정 벤치마크)에는 말이 됐겠지만 **일반적 권고는 바꾸지 마라**
- **GC 스레드를 CPU에 바인딩** — **GC 스레드가 머신에서 도는 유일한 것이고 힙이 아주 클 때만**
  말이 된다. 일반적으로는 **GC 스레드가 아무 CPU에서나 돌 수 있는 편이 낫다**

## 힙 크기의 완전한 제어 — 기본값이 어떻게 계산되나

```
-XX:MaxRAM=N   # 보통 JVM이 머신을 보고 계산한다. 다만 상한이 있다:
               #   client 컴파일러 1GB / 32비트 server 4GB / 64비트 128GB
```

```
기본 Xmx = MaxRAM / MaxRAMFraction        # MaxRAMFraction 기본 4
```
> **그래서 기본 힙 크기가 달라진다.** 물리 메모리가 `MaxRAM` 보다 작으면 그것의 1/4이다.
> **하지만 RAM이 수백 GB여도 JVM이 기본으로 쓰는 최대는 32GB다 — 128GB의 1/4.**

```
-XX:ErgoHeapSizeLimit=N   # 기본 0(무시). MaxRAM/MaxRAMFraction 보다 작으면 이 값을 쓴다
```

**메모리가 아주 적은 머신에서는 OS에 충분히 남기려 한다:**
```
if ((96MB * MinRAMFraction) > 물리 메모리) {     # MinRAMFraction 기본 2
    기본 Xmx = 물리 메모리 / MinRAMFraction;
}
```
**이것이 192MB 머신에서 최대 힙이 96MB 이하가 되는 이유다.**

```
기본 Xms = MaxRAM / InitialRAMFraction    # InitialRAMFraction 기본 64
```
> **단 하나의 단서**: 그 값이 5MB 미만이면 — 엄밀히는 `-XX:OldSize=N`(기본 4MB) +
> `-XX:NewSize=N`(기본 1MB)보다 작으면 — **그 합이 초기 힙 크기가 된다.**

## 장 요약 — 저자의 의사결정 체크리스트

> **풀 GC 정지를 어느 정도 감내할 수 있는가?**
> 감내할 수 있다면 **처리량 컬렉터**가 최고 성능을 주면서 CPU와 힙을 덜 쓴다.
> 아니라면 동시 컬렉터 — **작은 힙은 CMS나 G1, 큰 힙은 G1.**

> **기본 설정으로 필요한 성능이 나오는가?**
> **먼저 기본값을 시도하라.** GC 기술이 성숙하면서 ergonomic 튜닝이 계속 좋아지고 있다.
> 안 나온다면 **GC가 정말 문제인지 확인하라.** GC 로그를 보고 GC에 얼마나 쓰는지, 긴 정지가
> 얼마나 자주 나는지 본다. **바쁜 애플리케이션이 GC에 3% 이하를 쓴다면 튜닝으로 얻을 게 많지 않다**
> (이상치를 줄이는 게 목표라면 시도해 볼 수는 있다).

> **정지 시간이 목표에 어느 정도 근접했는가?**
> 근접했다면 **최대 정지 시간 조정만으로 충분할 수 있다.**
> **정지가 너무 길지만 처리량은 괜찮다면 영 제너레이션(풀 GC 정지라면 올드)을 줄여라** —
> 더 많지만 더 짧은 정지를 얻는다.

> **GC 정지는 짧은데 처리량이 부족한가?**
> **힙(또는 최소한 영 제너레이션)을 키워야 한다.**
> **⚠️ 더 많은 것이 항상 좋은 건 아니다** — 큰 힙은 긴 정지로 이어진다. 동시 컬렉터에서도
> 큰 힙은 기본적으로 큰 영 제너레이션을 뜻하므로 **영 수집 정지가 길어진다.**

> **동시 컬렉터인데 동시 모드 실패로 풀 GC가 나는가?**
> CPU가 있다면 **동시 GC 스레드를 늘리거나 `InitiatingHeapOccupancyPercent` 로 백그라운드
> 스위프를 일찍 시작하라.** **G1은 대기 중인 혼합 GC가 있으면 동시 사이클이 시작되지 않으므로
> 혼합 GC 횟수 목표를 줄여 보라.**

> **동시 컬렉터인데 승격 실패로 풀 GC가 나는가?**
> **CMS의 승격 실패는 힙이 단편화됐다는 뜻이고 할 수 있는 게 별로 없다.** 더 큰 힙이나 이른
> 백그라운드 스위프가 도움이 될 때가 있다. **G1을 대신 시도하는 편이 나을 수 있다.**
> **G1의 대피 실패(to-space overflow)도 본질적으로 같은 뜻이지만, G1이 백그라운드 스위핑을
> 더 일찍 하고 혼합 GC를 더 빨리 하면 단편화를 해결할 수 있다.**
