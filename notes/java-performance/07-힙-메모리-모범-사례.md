# 7장. 힙 메모리 모범 사례 (Heap Memory Best Practices)

> **GC 튜닝은 중요하지만, 더 나은 프로그래밍 관행으로 더 큰 성능 향상을 얻는 경우가 많다.**

이 장에는 **서로 충돌하는 두 목표**가 있다.

- **첫 번째 일반 규칙: 객체를 아껴 만들고 최대한 빨리 버려라.** 메모리를 덜 쓰는 것이 GC 효율을
  높이는 최선의 방법이다
- **반대로, 어떤 종류의 객체는 자주 다시 만드는 것이 (GC 성능이 좋아지더라도) 전체 성능을
  나쁘게 만든다.** 재사용하면 상당한 성능 향상이 있다

**객체를 재사용하면 오래 살아남아 GC에 영향을 준다. 하지만 신중하게 재사용하면 전체 성능은
좋아진다.** 이 장은 두 접근과 그 트레이드오프를 다룬다.

# 1부. 힙 분석

> ⚠️ 이 도구들은 **대부분 살아 있는 객체만 다룬다.** 어떤 경우는 **풀 GC를 강제**해서 그렇게 하므로
> **도구 사용 후 애플리케이션 동작이 영향받을 수 있다.** 어느 쪽이든 시간과 자원이 들어서
> **프로그램 실행 측정 중에는 대체로 쓸모가 없다.**

## 힙 히스토그램 — 가볍고 빠른 첫 단계

> 뒤에서 `Calendar` 객체 지연 초기화 예제로 **640바이트**를 아끼는데, 애플리케이션이 그런 객체를
> 하나만 만든다면 **측정 가능한 차이가 없다.** **어떤 종류의 객체가 메모리를 많이 쓰는지 분석해야
> 노력을 집중할 수 있다.**

```bash
jcmd <pid> GC.class_histogram     # 살아 있는 객체만. 풀 GC를 강제하지 않는다
jmap -histo <pid>                 # 수집 대상(죽은) 객체도 포함
jmap -histo:live <pid>            # 풀 GC를 강제한 뒤
```

```
 num     #instances         #bytes  class name
   1:        789087       31563480  java.math.BigDecimal
   2:        237997       22617192  [C
   3:        137371       20696640  <constMethodKlass>
   ...
   7:         37059        9238848  [B
```

**읽는 법**
- **`Klass` 관련 객체가 상위에 오는 것은 흔하다** — 클래스 로딩의 메타데이터
- **문자 배열(`[C`)과 `String` 이 상위인 것도 아주 흔하다** — 가장 흔히 만들어지는 자바 객체
- **바이트 배열(`[B`)과 객체 배열(`[Ljava.lang.Object;`)** 도 흔하다 — 클래스로더가 여기 데이터를 담는다
- 이 표기법은 **JNI가 객체 타입을 식별하는 방식**에서 왔다

이 예에서 **`BigDecimal` 이 1위**인 것은 추적할 만하다 — 예제 코드가 **일시적** `BigDecimal` 을
많이 만드는 건 알지만, **그렇게 많이 힙에 남아 있는 건 평소 예상과 다르다.**

> **히스토그램은 아주 작아서 자동화 시스템의 모든 테스트마다 수집해 두면 꽤 유용하다.**
> 다만 몇 초가 걸리므로 **성능 측정 정상 상태 중에는 뜨지 마라.**

## 힙 덤프

```bash
jcmd <pid> GC.heap_dump /path/to/heap_dump.hprof     # 기본으로 풀 GC. -all 로 죽은 객체 포함
jmap -dump:live,file=/path/to/heap_dump.hprof <pid>  # live 옵션이 풀 GC 강제
```

**분석 도구 세 가지**
- **`jhat`** — 원조. 힙 덤프를 읽고 작은 HTTP 서버를 띄워 웹 페이지 링크로 본다
- **`jvisualvm`** — 실행 중 프로그램에서 덤프를 뜨거나 기존 덤프를 연다. 최대 유지 객체를 보고
  임의 쿼리를 실행할 수 있다
- **`mat`** (Eclipse Memory Analyzer Tool) — **덤프 하나 이상**을 로드하고 분석한다.
  문제가 있을 만한 곳을 제안하는 리포트를 만들고 **SQL 같은 쿼리**를 실행한다

### 얕은(shallow) / 깊은(deep) / 유지(retained) 크기

> **유지 메모리(retained memory)**: **그 객체가 수집 대상이 되면 해제될 메모리의 양.**
>
> 저자의 그림: `String Trio` 객체의 유지 메모리는 자기 자신 + `Sally` + `David` 이다.
> **`Michael` 은 포함되지 않는다** — 다른 참조가 있어서 `String Trio` 가 해제돼도 GC 대상이
> 되지 않기 때문이다.
>
> - **얕은 크기**: 객체 자신의 크기. 다른 객체 참조는 **4바이트나 8바이트만** 포함하고 대상 객체
>   크기는 안 넣는다
> - **깊은 크기**: 그 대상 객체들의 크기까지 포함
> - **깊은 크기와 유지 메모리의 차이는 공유된 객체에 있다.** `Flute Duo` 의 **깊은 크기는
>   `Michael` 을 포함하지만 유지 크기는 포함하지 않는다**

**힙 공간을 많이 유지하는 객체를 힙의 도미네이터(dominator)라고 한다.**
소수의 객체가 힙 대부분을 지배한다면 쉽다 — 더 적게 만들거나, 더 짧게 유지하거나, 객체 그래프를
단순화하거나, 더 작게 만들면 된다. **말이 쉽지만 적어도 분석은 단순하다.**

### 하지만 대개는 탐정 노릇이 필요하다

**저자의 실제 사례** — 세션에 강하게, 전역 해시맵에 약하게 캐시하는 GlassFish 주식 서블릿.
힙에 객체가 **1.4GB** 있는데 **단독으로 참조되는 최대 객체 집합이 겨우 6MB**(놀랍지 않게도
GlassFish OSGi 클래스로딩 프레임워크의 일부).
**가장 많은 메모리를 직접 유지하는 객체를 봐도 문제가 풀리지 않는다.**

**히스토그램 뷰가 유용한 두 번째 단계다.** 같은 타입 객체를 집계하니
**700만 개 `TreeMap$Entry` 가 1.4GB를 유지**한다는 것이 훨씬 명확해진다.

### GC 루트로 바로 가는 것이 꼭 도움되는 건 아니다

**GC 루트**는 정적·전역 참조를 가진 시스템 객체로, 긴 객체 사슬을 통해 문제의 객체를 참조한다.
**보통 시스템/부트스트랩 클래스패스에 로드된 클래스의 정적 변수에서 온다.** 여기에는
**`Thread` 클래스와 모든 활성 스레드**가 포함된다 — 스레드는 **스레드 로컬 변수**나
**대상 `Runnable` 객체를 통한 참조**로 객체를 유지한다.

> **⚠️ 객체에 참조가 여러 개면 GC 루트도 여러 개다.** 참조는 **역방향 트리 구조**다.
> `TreeMap$Entry` 하나를 두 객체가 참조하고, 각각을 다시 두 객체가, 각각을 다시 세 객체가...
> **루트를 거슬러 갈수록 참조가 폭발하므로 어떤 객체든 GC 루트가 여럿일 가능성이 높다.**

> **더 생산적인 방법**: **탐정처럼 객체 그래프에서 대상 객체가 공유되는 가장 낮은 지점을 찾는 것.**
> 들어오는 참조를 추적해 **중복 경로가 식별될 때까지** 따라간다.
> 이 사례에서 `StockPriceHistoryImpl` 참조는 두 참조자를 갖는다 — 세션 속성 데이터를 담는
> `ConcurrentHashMap` 과 전역 캐시인 `WeakHashMap`.

> **저자의 솔직한 단서**: 이 예에서 쓰인 객체 타입 덕에 분석이 평소보다 쉬웠다.
> **주 데이터가 `BigDecimal` 대신 `String` 이고 `TreeMap` 대신 `HashMap` 이었다면 훨씬 어려웠을
> 것이다.** 힙 덤프에는 수십만 개의 다른 문자열과 수만 개의 다른 `HashMap` 이 있으니까.
> **경험칙: 엔트리(`HashMap$Entry`)가 아니라 컬렉션 객체(`HashMap`)부터 시작하고, 가장 큰
> 컬렉션을 찾아라.**

# 2부. OutOfMemoryError — 네 가지 원인

> **⚠️ OOM이 났다고 자동으로 힙이 문제라고 결론짓지 마라.** **왜** 났는지 봐야 한다
> (그 이유는 예외 출력의 일부다).

### ① 네이티브 메모리 부족

```
Exception in thread "main" java.lang.OutOfMemoryError: unable to create new native thread
```
**힙과 전혀 무관하다.** 32비트 JVM의 최대 프로세스 크기는 4GB(일부 Windows 3GB, 구형 Linux 3.5GB).
**3.8GB 힙을 지정하면 그 한계에 위험하게 가까워진다.** 64비트에서도 OS에 가상 메모리가 부족할 수 있다.

> **에러 메시지가 네이티브 메모리 할당을 언급하면 힙 튜닝은 답이 아니다.** 8장을 봐야 한다.

### ② permgen / 메타스페이스 부족

```
Exception in thread "main" java.lang.OutOfMemoryError: PermGen space   # Java 7
Exception in thread "main" java.lang.OutOfMemoryError: Metaspace       # Java 8
```

**두 가지 근본 원인**
1. **단순히 클래스가 기본 공간보다 많다** → 크기를 늘린다
2. **클래스로더 메모리 누수 — 더 까다롭다.** Java EE 앱 서버에서 가장 자주 일어난다.
   앱마다 자기 클래스로더에서 돌고(격리를 위해), 개발 중 변경할 때마다 재배포하면서 새 클래스로더가
   만들어지고 옛것은 스코프를 벗어난다. **옛 클래스로더가 스코프를 벗어나지 않으면 클래스
   메타데이터를 해제할 수 없고 결국 permgen이 찬다.**
   **이 경우 크기를 늘려도 에러를 미룰 뿐이다.**

> **앱 서버 환경이면 벤더에 연락해 누수를 고치게 하는 것 외에 할 게 별로 없다.**
> **직접 클래스로더를 만들고 버리는 코드를 쓴다면** 클래스로더가 제대로 버려지는지 확인하라 —
> **특히 어떤 스레드도 컨텍스트 클래스로더를 임시 클래스로더로 설정하지 않도록.**
> 디버깅에는 힙 덤프 분석이 유용하다 — **히스토그램에서 `ClassLoader` 인스턴스를 전부 찾아
> GC 루트를 추적**한다.

### ③ 힙 부족

```
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
```
permgen 경우와 비슷하다 — **정말로 힙이 더 필요하거나, 메모리 누수이거나.**
**첫째면 힙 증가로 해결되고, 둘째면 미룰 뿐이다.**

**누수라면 몇 분 간격으로 연속 힙 덤프를 떠서 비교하라.** `mat` 에 그 기능이 있다 —
**덤프 두 개를 열면 히스토그램 차이를 계산해 준다.**

> **자동 힙 덤프 — OOM은 예측 불가라 언제 덤프를 뜰지 알기 어렵다**
> ```
> -XX:+HeapDumpOnOutOfMemoryError   # 기본 false
> -XX:HeapDumpPath=<path>           # 기본 java_pid<pid>.hprof (현재 작업 디렉터리)
> -XX:+HeapDumpAfterFullGC
> -XX:+HeapDumpBeforeFullGC
> ```
> 여러 개가 생성되면 파일명에 **일련번호가 붙는다.**

**컬렉션 클래스가 자바 메모리 누수의 가장 잦은 원인이다** — 애플리케이션이 컬렉션에 넣고
절대 해제하지 않는다.
**최선의 해결은 더 이상 필요 없을 때 선제적으로 버리도록 로직을 바꾸는 것.**
약한/부드러운 참조를 쓰는 컬렉션이 자동으로 버려 주지만 **비용이 따른다**(뒤에서).

### ④ GC 오버헤드 한계 도달

```
Exception in thread "main" java.lang.OutOfMemoryError: GC overhead limit exceeded
```

**네 조건이 모두 충족돼야 던져진다.**
1. 풀 GC에 쓴 시간이 `-XX:GCTimeLimit=N`(**기본 98**, 즉 98%)을 넘는다
2. 풀 GC가 회수한 메모리가 `-XX:GCHeapFreeLimit=N`(**기본 2**, 즉 힙의 2% 미만)보다 적다
3. **위 두 조건이 연속 5회 풀 GC 사이클 동안 참**이었다 (**이 값은 튜닝 불가**)
4. `-XX:+UseGCOverheadLimit` 이 true (기본)

> **OOM 없이 연속 풀 GC가 5번 넘게 일어나는 것은 흔하다.** 98%를 GC에 쓰더라도 **매번 힙의
> 2% 넘게 해제하고 있을 수 있기 때문**이다. 그 경우 `GCHeapFreeLimit` 을 올리는 것을 고려하라.
>
> **마지막 발버둥**: 앞의 두 조건이 **연속 4회** 참이면 **다섯 번째 풀 GC 전에 JVM의 모든 소프트
> 참조가 해제된다.** 그래서 에러를 막는 경우가 많다(애플리케이션이 소프트 참조를 쓴다면).

# 3부. 메모리를 덜 쓰기

> **효과가 곱해진다**: 메모리를 덜 쓰면 힙이 덜 자주 차고 GC 사이클이 줄어든다.
> **영 수집이 줄면 객체의 테뉴어링 나이가 덜 자주 올라가고 → 올드로 승격될 가능성이 낮아진다.**
> 그래서 풀 GC(또는 동시 GC) 횟수도 줄어든다. 그리고 풀 GC가 더 많은 메모리를 정리할 수 있으면
> 그것도 덜 자주 일어난다.

## 객체 크기 줄이기

| 타입 | 크기 |
|---|---|
| `byte` | 1 |
| `char`, `short` | 2 |
| `int`, `float` | 4 |
| `long`, `double` | 8 |
| **참조** | **32비트 JVM과 힙 32GB 미만 64비트 JVM에서 4, 큰 힙의 64비트에서 8** |

**보이지 않는 객체 헤더 필드**
- 일반 객체: **32비트 JVM 8바이트, 64비트 JVM 16바이트**(힙 크기 무관)
- 배열: **32비트나 힙 32GB 미만 64비트에서 16바이트, 그 외 24바이트**

**저자의 실측 (64비트 Java 7, 힙 32GB 미만)**

| | 얕은 | 깊은 | 유지 |
|---|---|---|---|
| `A { int i; }` | 16 | 16 | 16 |
| `B { int i; Locale l = Locale.US; }` | 24 | **216** | 24 |
| `C { int i; ConcurrentHashMap chm = new ConcurrentHashMap(); }` | 24 | 200 | **200** |

- **`B`**: `Locale` 참조가 8바이트를 더한다. **하지만 실제 `Locale` 객체는 다른 클래스와 공유된다.**
  클래스가 실제로 필요로 하지 않는다면 **참조를 위한 추가 바이트만 낭비**된다.
  그래도 **`B` 인스턴스를 많이 만들면 그 바이트가 쌓인다**
- **`C`**: 참조 바이트에 더해 **해시맵 객체 200바이트**가 추가된다. **쓰지 않는다면 아주 낭비다**

> **⚠️ 객체 정렬(alignment)과 객체 크기 — 이 절의 함정**
> 예제 클래스들에 논의되지 않은 `int i` 필드가 왜 있을까? **논의를 따라가기 쉽게 하려고 넣은 것이다.**
> `B` 가 `A` 보다 8바이트 크다는 게 예상대로 보이게 하려고.
>
> **그것이 중요한 세부를 가렸다 — 객체 크기는 항상 8바이트의 배수로 패딩된다.**
> - `A` 에 `i` 가 없어도 **여전히 16바이트**다. 4바이트가 `i` 대신 **패딩에 쓰일 뿐**
> - `i` 가 없으면 **`B` 도 16바이트** — 추가 객체 참조가 있는데도 `A` 와 같다
> - **패딩 때문에 `B` 인스턴스가 (4바이트) 참조 하나만 더 가졌는데도 `A` 보다 8바이트 크다**
>
> JVM은 **바이트 수가 홀수인 객체도 패딩해서, 그 객체의 배열이 하부 아키텍처에 최적인 주소 경계에
> 깔끔히 맞도록** 한다.
>
> **그래서 인스턴스 필드를 없애거나 크기를 줄여도 이득이 있을 수도 없을 수도 있다.
> 다만 하지 않을 이유도 없다.**

**덜 명백한 방법: 더 작은 데이터 타입.** 여덟 가지 상태를 추적한다면 `int` 대신 `byte` 로
**3바이트를 아낀다.** `double` 대신 `float`, `long` 대신 `int` 등이 **자주 인스턴스화되는 클래스에서
특히** 도움이 된다.

### 시간 대 공간 — 계산 결과를 필드에 담을까?

> **자바에서는 이 트레이드오프가 CPU 시간에도 적용된다** — 추가 메모리가 GC로 하여금 CPU를
> 더 쓰게 만들기 때문이다.

**JDK의 실제 판단 두 가지**
- **`String` 의 해시코드**는 **인스턴스 변수에 저장한다.** 계산이 시간이 걸리고,
  **재사용이 저장하지 않아 아끼는 메모리보다 거의 항상 낫다**
- **대부분 클래스의 `toString()` 은 결과를 캐시하지 않는다.** 인스턴스 변수와 문자열 양쪽에
  메모리를 쓰게 되니까. **새 문자열을 만드는 시간이 대개 더 낫다**
- **그리고**: `String` 의 해시값은 꽤 자주 쓰이고, `toString()` 표현은 꽤 드물게 쓰인다

> **명백히 사례별 상황(your-mileage-may-vary)이다. GC를 줄이는 것이 목표라면 균형은 재계산
> 쪽으로 기운다.**

## 지연 초기화 (Lazy Initialization)

```java
// 즉시 초기화
private Calendar calendar = Calendar.getInstance();
private DateFormat df = DateFormat.getDateInstance();

// 지연 초기화 — 실행할 때마다 상태를 검사하는 약간의 계산 비용
private void report(Writer w) {
    if (calendar == null) {
        calendar = Calendar.getInstance();
        df = DateFormat.getDateInstance();
    }
    ...
}
```

> **지연 초기화는 해당 연산이 드물게만 쓰일 때 가장 좋다.** 흔히 쓰인다면 **메모리가 실제로
> 절약되지 않으면서**(어차피 항상 할당되니까) **흔한 연산에 약간의 성능 페널티만 생긴다.**

> **지연 초기화 런타임 성능 — 페널티가 없을 수도 있다**
> JDK의 `ArrayList` 예시. **JDK 7u40에서 `elementData` 배열이 지연 초기화되도록 바뀌었다.**
> **그런데 `ensureCapacity()` 메서드가 이미 배열 크기를 검사하고 있었기 때문에 흔한 메서드에
> 성능 페널티가 없었다** — 초기화 검사 코드가 배열 크기 증가 검사 코드와 같으니까.
> ```java
> private static final Object[] EMPTY_ELEMENTDATA = {};
> private Object[] elementData = EMPTY_ELEMENTDATA;
> ```
> **정적 공유 0길이 배열**을 써서 `index` 와 `elementData.length` 가 둘 다 0에서 시작하므로
> `ensureCapacity()` 는 (본질적으로) 그대로 둘 수 있다.

### 스레드 안전한 지연 초기화

> **동기화를 넣으면 동기화가 성능 병목이 될 가능성이 열린다. 그 경우는 드물어야 한다.**
> 지연 초기화의 이득은 **드물게만 초기화될 때** 생기는데(자주 초기화하면 메모리가 절약되지 않으니까),
> **그러므로 병목이 되는 것은 "드물게 쓰이는 코드 경로가 갑자기 많은 스레드에게 동시에 쓰이는"
> 경우다. 있을 수 없는 일은 아니지만 가장 흔한 경우도 아니다.**

**중요한 구분**: `DateFormat` 은 **스레드 안전하지 않다.** 그러므로 락이 `Calendar` 를 포함하든
말든 상관없다 — **지연 초기화된 객체가 갑자기 많이 쓰이면 `DateFormat` 주변의 동기화가 어차피
문제가 된다.**

**`ConcurrentHashMap` 처럼 스레드 안전한 객체라면 이중 검사 락(double-checked locking)** 으로
병목을 푼다:

```java
private volatile ConcurrentHashMap instanceChm;   // ★ volatile 필수
public void doOperation() {
    ConcurrentHashMap chm = instanceChm;          // ★ 지역 변수 할당에 약간의 성능 이득
    if (chm == null) {
        synchronized(this) {
            chm = instanceChm;
            if (chm == null) {
                chm = new ConcurrentHashMap();
                ... 맵 채우기 ...
                instanceChm = chm;
            }
        }
        ...chm 사용...
    }
}
```
> **인스턴스 변수는 반드시 `volatile` 로 선언해야 하고, 지역 변수에 대입하면 약간의 성능 이득이
> 있다.** 상세는 9장.

### 즉시 비초기화 (Eager Deinitialization)

**변수를 `null` 로 설정해 더 빨리 수집되게 하는 것.** 이론상 좋아 보이지만 **제한된 상황에서만
유용하다.**

> **지연 초기화 후보가 즉시 비초기화 후보처럼 보인다.** 위 예에서 `report()` 가 끝나면
> `Calendar` 와 `DateFormat` 을 `null` 로 둘 수 있다.
> **하지만 이후 호출에서(또는 클래스 다른 곳에서) 쓰이지 않을 변수라면 애초에 인스턴스 변수로
> 만들 이유가 없다.** 메서드에 지역 변수로 만들면 메서드가 끝날 때 스코프를 벗어나 GC가 해제한다.

**흔한 예외는 컬렉션 프레임워크 같은 클래스** — **데이터 참조를 오래 들고 있다가 더 이상 필요
없다고 통보받는 클래스.**

```java
public E remove(int index) {
    ...
    elementData[--size] = null; // clear to let GC do its work
    return oldValue;
}
```
> **이 GC 주석은 (주석이 드문) JDK 소스 자체에 있다** — 이렇게 `null` 로 설정하는 것이 설명이
> 필요할 만큼 이례적인 연산이라서다.
>
> **추적해 보자**: 배열 마지막 원소를 제거하면 `size` 가 5에서 4로 줄어든다. 이제
> `elementData[4]` 에 저장된 것은 **접근할 수 없다** — 유효 크기를 넘었으니까.
> **`elementData[4]` 는 낡은 참조(stale reference)다.** `elementData` 배열은 오래 활성 상태로
> 남을 것이므로 **더 이상 참조할 필요 없는 것은 능동적으로 `null` 로 만들어야 한다.**

> **낡은 참조라는 개념이 핵심이다. 오래 사는 클래스가 객체 참조를 캐시했다가 버린다면 낡은
> 참조를 피하도록 신경 써야 한다. 그렇지 않은 경우에는 명시적으로 `null` 을 넣어도 성능 이득이
> 거의 없다.**

## 불변 객체와 정규(canonical) 객체

**`Boolean` 클래스가 최고의 예다.** 어떤 자바 애플리케이션에도 `Boolean` 인스턴스는 **둘이면
충분하다** — true 하나, false 하나.

> **불행히도 `Boolean` 클래스는 잘못 설계됐다.** **public 생성자가 있어서** 애플리케이션이
> 원하는 만큼 만들 수 있다. **더 나은 설계는 private 생성자만 두고, 파라미터에 따라
> `Boolean.TRUE` 나 `Boolean.FALSE` 를 반환하는 정적 메서드를 두는 것이었다.**
> (**`Boolean` 객체는 절대 만들지 말고 `Boolean.TRUE`/`Boolean.FALSE` 를 써야 한다는 건
> 당연할 것이다.**)

**커스텀 클래스의 정규화**
```java
public class ImmutableObject {
    private static WeakHashMap<ImmutableObject, ImmutableObject> map = new WeakHashMap();
    public ImmutableObject canonicalVersion(ImmutableObject io) {
        synchronized(map) {
            ImmutableObject canonicalVersion = map.get(io);
            if (canonicalVersion == null) {
                map.put(io, new WeakReference(io));
                canonicalVersion = io;
            }
            return canonicalVersion;
        }
    }
}
```
> **메모리 누수를 막으려면 맵의 객체가 약하게 참조되도록 해야 한다.**
> **스레드 환경에서는 이 동기화가 병목이 될 수 있다.** JDK 클래스만 쓴다면 쉬운 해결책이 없다 —
> **약한 참조용 동시 해시맵을 제공하지 않기 때문**이다. JSR 166에 `CustomConcurrentHashMap` 을
> 추가하자는 제안이 있었고 서드파티 구현이 여럿 있다.

## String 인터닝

> **문자열은 단연 가장 흔한 자바 객체다. 당신의 힙은 거의 확실히 문자열로 차 있다.**

**중복이 많은지 아는 데는 힙 분석이 필요하다.** Eclipse Memory Analyzer에 덤프를 로드하고
모든 `String` 의 유지 크기를 계산해 정렬한다. **저자의 예시**: 상위 세 문자열이 같아 보이고,
인터닝하면 **650KB**를 아낀다. 4·5번째도, 7~9번째도 마찬가지 — **다만 아래로 갈수록 아끼는
메모리가 줄어든다.**

### ⚠️ 인터닝 테이블 크기 — 이 절의 핵심 함정

**인터닝된 문자열 테이블은 네이티브 메모리에 있는 고정 크기 해시테이블이다.**
- **Java 7u40 이전 기본 1,009 버킷** → 평균적으로 **체이닝 충돌 전에 약 500개**
- **64비트 Java 7u40 이후 기본 60,013**

```
-XX:StringTableSize=N   # 소수(prime)일 때 가장 효율적이다
```

**저자의 실측 — 1,000만 개 문자열 생성 및 인터닝**

| 튜닝 | 시간 |
|---|---|
| **테이블 크기 1009** | **2.3시간** |
| 테이블 크기 100만 | 30.4초 |
| 테이블 크기 1000만 | 25.2초 |
| 커스텀 메서드 | 26.4초 |

> **크기를 잘못 잡은 인터닝 테이블의 페널티가 아주 심하다.**
>
> 마지막 케이스는 앞서 본 `canonicalVersion()` 을 **JSR 166 프리릴리스의
> `CustomConcurrentHashMap`**(약한 키·값)으로 구현한 것이다. 잘 튜닝된 인터닝 테이블 대비
> 성능 이득은 없었지만, **장점은 커스텀 맵의 크기를 전혀 튜닝할 필요가 없었다는 것**이다 —
> 초기 1,009에서 **필요에 따라 스스로 크기를 조정**했다. **최적 튜닝 대비 작은 페널티가 있었지만
> 훨씬 운영하기 쉬웠다.**

**모니터링**
```
-XX:+PrintStringTableStatistics   # JDK 7u6+, 기본 false. JVM 종료 시 출력

StringTable statistics:
Number of buckets       :    1009
Average bucket size     :    3008    ← 이상적으로는 0이나 1이어야 한다
Maximum bucket size     :    3186
```
> 실제로 0이 되진 않고 0.5 미만인데, **정수 연산이라 리포트에서 내림된다.**
> **평균이 1보다 크면 테이블 크기를 늘려라.**

```bash
jmap -heap <pid>    # JDK 7u6+
# ... 36361 interned Strings occupying 3247040 bytes.
```

> **테이블 크기를 너무 크게 잡는 페널티는 미미하다** — 버킷당 4~8바이트라, 최적보다 수천 개 더
> 있어도 **네이티브(힙 아닌) 메모리 몇 KB의 일회성 비용**이다.

> **인터닝과 `equals` — 흔한 미신**
> "인터닝하면 `==` 로 비교할 수 있어 빨라진다"는 생각은 **대부분의 경우 미신이다.**
> **`String.equals()` 는 꽤 빠르다** — 길이가 다르면 절대 같지 않다는 것부터 알고, 길이가 같으면
> 문자를 훑어 비교한다(적어도 다른 곳을 찾을 때까지).
> **`==` 비교가 부인할 수 없이 빠르지만, 인터닝 비용도 계산에 넣어야 한다.** 인터닝은
> (다른 것들과 함께) **문자열 해시코드를 계산**해야 하는데, 그건 **문자열 전체를 훑으며 각 문자에
> 연산을 하는 것**이다 — `equals()` 가 하는 것과 똑같이.
>
> **이득을 기대할 수 있는 유일한 경우는, 같은 길이의 문자열 집합에 대해 반복 비교를 많이 하는
> 애플리케이션이다.** 둘 다 이미 인터닝됐다면 `==` 가 빠르고 인터닝 비용은 한 번만 세면 된다.
> **하지만 일반적인 경우 비용은 대체로 같다.**

# 4부. 객체 수명주기 관리

## 객체 재사용 — 왜 GC 엔지니어가 싫어하나

> 저자의 표현: **"전 세계 GC 엔지니어들이 지금 신음하고 있다."**
> **객체 풀링은 그 이유로 GC 진영에서 널리 미움받고, 다른 여러 이유로 개발 진영에서도 미움받는다.**

**표면적 이유**: 재사용되는 객체는 힙에 오래 남고, 그만큼 새 객체를 만들 공간이 줄어 GC가 잦아진다.
**하지만 그건 이야기의 일부일 뿐이다.**

**더 깊은 이유 ①**: 새로 만들어진 풀 객체가 처리될 때마다 **GC 알고리즘이 복사하고 참조를 조정하는
작업**을 해야 한다 — 올드로 승격될 때까지.

**더 깊은 이유 ② — 이것이 핵심이다**:
> **풀 GC 수행 시간은 올드 제너레이션에 아직 살아 있는 객체 수에 비례한다.**
> **라이브 데이터의 양이 힙 크기보다도 중요하다** — **살아남는 객체가 적은 3GB 올드를 처리하는
> 것이 객체의 75%가 살아남는 1GB 올드를 처리하는 것보다 빠르다.**

**저자의 GC 로그 실측 (4코어 Linux, 4GB 힙, 1GB 고정 뉴)**
```
[Full GC ... [ParOldGen: 3145727K->3145727K(3145728K)] ... 0.5432730 secs]
[Full GC ... [ParOldGen: 3145727K->210K(3145728K)]     ... 0.0687770 secs]   ← 210KB만 남음
[Full GC ... [ParOldGen: 3145727K->3145727K(3145728K)] ... 0.7228880 secs]
```
> **가운데 출력에 주목** — 애플리케이션이 올드 참조 대부분을 정리해서 GC 후 데이터가 **210KB뿐**이다.
> 그 연산은 **겨우 70ms.** 다른 경우는 대부분이 여전히 살아 있어 **540~730ms**가 걸렸다.
> **다행히 이 테스트에는 GC 스레드가 4개 있었다. 단일 코어에서는 짧은 GC가 80ms, 긴 GC가
> 2,410ms(30배 넘게)였다.**

**동시 컬렉터를 써서 풀 GC를 피해도 상황이 크게 나아지지 않는다** — 동시 컬렉터의 마킹 단계
시간도 마찬가지로 **살아 있는 데이터 양에 의존**하기 때문이다.
**특히 CMS에서는 풀의 객체들이 서로 다른 시점에 승격될 가능성이 높아 단편화로 인한 동시 실패
가능성이 커진다.**

> **결론: 객체를 힙에 오래 둘수록 GC 효율이 떨어진다. 그러므로 객체 재사용은 나쁘다.**
> **이제 어떻게, 언제 재사용할지 이야기하자.** (저자의 유머)

### 그런데 JDK와 Java EE는 왜 재사용하나

**두 가지 공통점이 있다.**

**① 초기화에 시간이 오래 걸린다.** **자바에서 객체 할당 자체는 꽤 빠르고 싸다**(재사용 반대
논거는 이 부분에 집중하는 경향이 있다). **초기화 성능은 객체에 따라 다르다.**
> **초기화 비용이 아주 높은 객체만, 그리고 그 초기화 비용이 프로그램의 지배적 연산 중 하나일
> 때만 재사용을 고려하라.**

**② 공유 객체 수가 적다.** GC에 미치는 영향이 최소화된다 — **GC 사이클을 늦출 만큼 많지 않다.**
> **풀에 객체 몇 개는 GC 효율에 큰 영향이 없다. 풀 객체로 힙을 채우면 GC가 크게 느려진다.**

**JDK/Java EE가 재사용하는 것들과 그 이유**

| 대상 | 이유 |
|---|---|
| 스레드 풀 | 스레드 초기화가 비싸다 |
| JDBC 풀 | DB 커넥션 초기화가 비싸다 |
| EJB 풀 | EJB 초기화가 비쌀 수 있다(10장) |
| **큰 배열** | **자바는 배열 할당 시 모든 원소를 기본값(`null`/`0`/`false`)으로 초기화해야 한다.** 큰 배열에서는 시간이 꽤 든다 |
| **네이티브 NIO 버퍼** | `allocateDirect()` 는 **크기와 무관하게** 비싸다. **큰 버퍼 하나를 만들어 슬라이스해 쓰고 반납하는 편이 낫다** |
| 보안 클래스 | `MessageDigest`, `Signature` 등 초기화가 비싸다. **Apache 기반 XML 코드가 스레드 로컬로 저장한다** |
| 문자열 인코더/디코더 | JDK의 여러 클래스가 만들고 재사용한다. **대부분 소프트 참조이기도 하다** |
| `StringBuilder` 헬퍼 | **`BigDecimal` 이 중간 결과 계산에 재사용한다** |
| 난수 생성기 | `Random`, **특히 `SecureRandom`** 은 시드 설정이 비싸다 |
| DNS 조회 이름 | 네트워크 조회가 비싸다 |
| **ZIP 인코더/디코더** | **흥미로운 반전 — 초기화가 특별히 비싸지 않다. 그런데 해제가 아주 비싸다.** 네이티브 메모리 해제를 **파이널라이제이션에 의존**하기 때문 |

### 객체 풀 vs 스레드 로컬 변수

**객체 풀의 성능 특성**

| 항목 | 내용 |
|---|---|
| **GC 영향** | 객체를 많이 들고 있으면 GC 효율이 (때로는 아주 심하게) 떨어진다 |
| **동기화** | **풀은 필연적으로 동기화된다.** 자주 꺼내고 넣으면 경합이 심해져 **풀 접근이 새 객체 초기화보다 느려질 수 있다** |
| **스로틀링** | **이 성능 영향이 이득일 수 있다** — 희소 자원 접근을 조절한다 |

> **스로틀링이 왜 이득인가**: 2장에서 봤듯 **시스템이 감당할 수 있는 것 이상으로 부하를 올리면
> 성능이 떨어진다.** 스레드 풀이 중요한 이유가 이것이다. 스레드가 너무 많이 동시에 돌면 CPU가
> 압도되어 성능이 저하된다(9장 예제).
> **원격 시스템 접근에도 적용된다** — JDBC 커넥션을 DB가 감당할 수 있는 것보다 많이 만들면
> **DB 성능이 저하된다.** 이런 상황에서는 **풀 크기를 제한해 자원 수를 조절하는 편이 낫다 —
> 애플리케이션 스레드가 여유 자원을 기다려야 하더라도.**

**스레드 로컬 변수의 성능 특성**

| 항목 | 내용 |
|---|---|
| **수명주기 관리** | **훨씬 쉽고 싸다.** 풀은 다 쓰면 **반납해야 하지만**(안 그러면 아무도 못 쓴다), 스레드 로컬은 스레드 안에서 항상 사용 가능하고 명시적 반납이 필요 없다 |
| **카디널리티** | **보통 스레드 수와 저장 객체 수가 1:1이 된다.** 스레드가 처음 쓸 때까지 복사본이 만들어지지 않으므로 **더 적을 수는 있지만 더 많을 수는 없다.** 반면 **객체 풀은 임의로 크기를 정할 수 있다**(스레드 8개에 커넥션 12개 등). **스레드 로컬은 이것도, 자원 접근 스로틀링도 효과적으로 못 한다**(스레드 수 자체가 스로틀이 아닌 한) |
| **동기화** | **필요 없다.** `get()` 이 비교적 빠르다. **(항상 그랬던 건 아니다 — 초기 자바에서는 스레드 로컬 획득이 꽤 비쌌다. 과거의 나쁜 성능 때문에 피해 왔다면 현재 버전에서 다시 고려하라)** |

> **동기화 이야기에서 흥미로운 지점**
> 스레드 로컬의 이득은 종종 **객체 재사용의 절약이 아니라 동기화 비용 절약**으로 설명된다.
> Java 7의 `ThreadLocalRandom` 이 예다 — 이걸 안 썼으면 이 책의 많은 예제가 단일 `Random`
> 객체의 `next()` 에서 동기화 병목을 만났을 것이다.
>
> **그런데 그 동기화 문제는 매번 새 `Random` 인스턴스를 만들어도 똑같이 쉽게 풀렸을 것이다.**
> **하지만 그렇게 풀었다면 전체 성능에 도움이 되지 않았을 것이다** — `Random` 객체 초기화가
> 꽤 비싸서, 계속 새로 만드는 것이 **여러 스레드가 하나를 공유하는 동기화 병목보다 성능이
> 나빴을 것**이기 때문이다.

**실측 — 주식 배치 계산**

| 종목 수 | 새 `Random` 할당 | `ThreadLocalRandom` 재사용 |
|---|---|---|
| 1 | 0.174초 | 0.175초 |
| 10 | 0.258초 | 0.236초 |
| 100 | 0.564초 | 0.49초 |
| 1,000 | 2.308초 | 1.916초 |
| **10,000** | **17.32초** | **13.55초** |

> **교훈**: **객체 초기화가 오래 걸린다면 객체 풀이나 스레드 로컬을 두려워하지 마라.**
> **다만 늘 균형을 잡아라 — 범용 클래스의 큰 객체 풀은 해결하는 것보다 많은 성능 문제를 확실히
> 일으킨다. 이 기법은 초기화가 비싸고 재사용 객체 수가 적을 클래스에만 남겨 둬라.**

## 약한·부드러운 참조 (Indefinite References)

> **용어 정리**
> - **참조(Reference)**: 모든 종류의 참조. **보통의 인스턴스 변수는 강한 참조다**
> - **불확정 참조(Indefinite reference)**: 저자의 용어. **소프트나 위크 같은 특수 참조.
>   실제로는 객체의 인스턴스다**(예: `SoftReference` 인스턴스)
> - **참조 대상(Referent)**: **불확정 참조 인스턴스 안에 감싸인 (거의 항상 강한) 참조의 대상**

**객체 풀·스레드 로컬 대비 장점**: **결국 GC가 회수한다.** 객체 풀에 최근 조회 1만 건이 있고
힙이 부족해지면 **애플리케이션은 운이 없다** — 그 1만 개를 뺀 나머지가 쓸 수 있는 전부다.
불확정 참조로 저장하면 **JVM이 공간을 확보해 GC 처리량이 좋아진다.**

**단점**: **GC 효율에 약간 더 영향을 준다.**

**메모리 그림 (저자의 실제 수치)**
- 캐시 대상 객체 **512바이트**
- `SoftReference` 안에 넣으면 **40바이트가 추가**된다
- **불확정 참조도 다른 자바 객체와 똑같다** — 메모리를 소비하고, 다른 것(`cachedValue` 변수)이
  그것을 **강하게** 참조한다

> **더 큰 영향: 불확정 참조 객체가 회수되려면 최소 두 번의 GC 사이클이 걸린다.**
>
> 소프트 참조의 경우: **참조 대상이 최근에 쓰이지 않았다고 JVM이 판단할 때까지 남아 있다.**
> 그때 **첫 GC 사이클이 참조 대상을 해제하지만 불확정 참조 객체 자체는 해제하지 않는다.**
> 이제 그 객체는 **최소 두 개의 강한 참조**를 갖는다 — 애플리케이션이 만든 것과,
> **JVM이 참조 큐(reference queue)에 만든 새 강한 참조.** 이 모두가 정리돼야 회수된다.
>
> **보통은 참조 큐를 처리하는 코드가 정리한다.** 최악의 경우 큐가 즉시 처리되지 않아
> **여러 GC 사이클이 걸린다. 최선의 경우에도 두 사이클은 거쳐야 한다.**

> **GC 로그와 참조 처리**
> ```
> -XX:+PrintReferenceGC   # 기본 false
>
> [GC[SoftReference, 0 refs, 0.0000060 secs]
>         [WeakReference, 238425 refs, 0.0236510 secs]
>         [FinalReference, 4 refs, 0.0000160 secs] ...
> ```
> **위크 참조 238,425개가 영 수집에 23ms를 더했다.**

### 소프트 참조 — 사실상 큰 LRU 객체 풀

**해제 시점의 의사코드**
```
long ms = SoftRefLRUPolicyMSPerMB * AmountOfFreeMemoryInMB;
if (now - last_access_to_reference > ms) free the reference
```

두 값이 핵심이다.
- **`-XX:SoftRefLRUPolicyMSPerMB=N`** — 기본 **1,000**
- **힙의 빈 메모리 양** (GC 사이클 완료 후). **힙 크기가 동적이므로 JVM에 두 선택지가 있다** —
  **현재 크기의 빈 메모리**냐 **최대 용량으로 확장했을 때의 빈 메모리**냐.
  **client 컴파일러는 현재 힙 기준, server 컴파일러는 최대 가능 크기 기준.**

**예시 (server 컴파일러, 4GB 힙)**
- 풀 GC 후 50% 점유 → 빈 힙 2GB → **2,048초(약 34분) 동안 안 쓰인 소프트 참조가 해제된다**
- 75% 점유 → **1,024초**
- `SoftRefLRUPolicyMSPerMB=500` 이고 75% 점유 → **512초**

> **⚠️ 힙이 소프트 참조로 빨리 차면 튜닝이 필요한 경우가 많다.**
> 빈 힙 2GB에서 **2,048초 안에 1.7GB의 소프트 참조를 만들면 아무것도 해제 대상이 되지 않는다.**
> **다른 객체를 위한 공간이 300MB만 남고, 결과적으로 GC가 아주 잦아진다(전체 성능이 아주 나빠진다).**
>
> **JVM이 메모리를 완전히 소진하거나 심하게 스래싱하면 모든 소프트 참조를 정리한다.**
> `OutOfMemoryError` 를 던지지 않는 건 좋지만 **캐시 결과를 무차별적으로 버리는 것은 이상적이지
> 않다.** **참조 처리 GC 로그에 예상치 못하게 아주 많은 소프트 참조가 정리된다고 나오면
> `SoftRefLRUPolicyMSPerMB` 를 낮출 또 하나의 시점이다.**
>
> **반대로 값을 올릴 조건은 두 가지가 모두 충족될 때다** — ① 빈 힙이 많고 ② 소프트 참조가
> 드물게 접근된다. **꽤 이례적인 상황이다.** GC 정책 설정과 비슷하다 — **값을 올리면 "최후의
> 수단으로만 버려라"라고 JVM에 말한 것 같지만, 동시에 "정상 동작을 위한 여유를 남기지 마라"고
> 말한 것이기도 해서 GC에 시간을 너무 쓰게 될 가능성이 높다.**

> **주의: 소프트 참조를 너무 많이 쓰지 마라 — 힙 전체를 쉽게 채운다.**
> **이 주의는 인스턴스가 너무 많은 객체 풀에 대한 주의보다도 강하다.** 소프트 참조는 **객체 수가
> 너무 많지 않을 때 잘 동작한다.** 그렇지 않다면 **LRU 캐시로 구현한 크기 제한 있는 전통적
> 객체 풀**을 고려하라.

### 위크 참조 — 소프트 참조와 근본적으로 다르다

> **위크 참조는 참조 대상이 여러 스레드에서 동시에 쓰일 때 써야 한다.**
> 그렇지 않으면 **GC가 회수해 버릴 가능성이 너무 높다 — 오직 약하게만 참조되는 객체는 매 GC
> 사이클마다 회수된다.**

**위크 참조는 소프트 참조의 중간 상태를 거치지 않는다.** 강한 참조가 사라지면 **즉시 해제된다.**

> **흥미로운 효과 — 위크 참조가 힙 어디에 있느냐가 중요하다.**
> 참조 객체도 다른 자바 객체처럼 영 제너레이션에서 만들어져 올드로 승격된다.
> - **위크 참조가 아직 영 제너레이션에 있을 때 참조 대상이 해제되면** → **다음 마이너 GC에서
>   빨리 해제된다**
> - **참조 대상이 오래 남아 위크 참조가 올드로 승격되면** → **다음 동시/풀 GC 사이클까지
>   해제되지 않는다**

**저자의 사례로 이해하기**
- 사용자 A가 TPKS를 조회하면 **또 조회할 가능성이 높다** → **사용자의 HTTP 세션에 강한 참조**로
  둔다. 로그아웃하면 세션이 정리되고 메모리가 회수된다
- **사용자 B가 TPKS를 필요로 할 때 어떻게 찾나?** 메모리 어딘가에 있으니 다시 조회하고 싶지 않은데,
  서블릿 코드가 다른 사용자의 세션을 뒤질 수는 없다
- → **전역 캐시에 그 데이터의 위크 참조를 둔다.** 이제 B가 찾을 수 있다 — **A가 아직 로그아웃해
  세션을 정리하지 않았다면**

> **이것이 "동시 접근"의 의미다.** JVM에게 이렇게 말하는 셈이다:
> **"야, 누가 이 객체에 관심 있는 동안은 어디 있는지 알려 줘. 그런데 아무도 필요 없어지면
> 버려. 내가 다시 만들게."**
>
> 소프트 참조는 이렇게 말하는 것이다:
> **"야, 메모리가 충분하고 누군가 가끔 접근하는 것 같은 동안은 계속 들고 있어 봐."**

> **⚠️ 이 구분을 이해하지 못하는 것이 위크 참조에서 가장 자주 일어나는 성능 문제다.**
> **위크 참조가 소프트 참조와 같은데 더 빨리 해제될 뿐이라고 생각하는 실수를 하지 마라.**
> **소프트 참조 객체는 (대개) 몇 분에서 몇 시간 살아 있지만, 위크 참조 객체는 참조 대상이
> 남아 있는 동안에만 살아 있다**(그리고 다음 GC 사이클에 정리된다).

> **불확정 참조와 컬렉션 — `WeakHashMap` 의 숨은 비용**
> JDK는 `WeakHashMap` 과 `WeakIdentityMap` 을 제공한다. **편리하지만 두 가지 비용이 있다.**
> ① 불확정 참조가 GC에 주는 부정적 영향
> ② **클래스 자체가 주기적으로 참조되지 않는 데이터를 정리하는 연산을 해야 한다**
>
> **`WeakHashMap` 은 키에 위크 참조를 쓴다.** 약하게 참조된 키가 사라지면 그 키에 연결된 값을
> 정리해야 하는데, **그 연산은 맵이 참조될 때마다 수행된다.**
>
> **성능적 함의 두 가지**
> - **맵을 다시 쓸 때까지 위크 참조와 그 값이 실제로 해제되지 않는다.** 맵을 드물게 쓰면
>   **메모리가 원하는 만큼 빨리 해제되지 않는다**
> - **맵 연산의 성능이 예측 불가능해진다.** 보통 해시맵 연산은 아주 빠르고 그게 인기 이유인데,
>   **GC 직후의 `WeakHashMap` 연산은 참조 큐를 처리해야 해서 더 이상 고정된 짧은 시간이 아니다.**
>   **키가 아주 자주 해제되면 `WeakHashMap` 성능이 꽤 나빠질 수 있다**
>
> **가능하다면 애플리케이션이 컬렉션을 직접 관리하게 하라.**

### 파이널라이저 — 쓰지 마라

**모든 자바 클래스는 `Object` 에서 `finalize()` 를 상속받는다.** 좋은 기능처럼 들리고 몇몇
상황에서는 필요하지만, **실제로는 나쁜 아이디어이므로 쓰지 않으려 아주 노력해야 한다.**

**기능적으로도 나쁘고 성능적으로도 나쁘다.**

> **파이널라이저는 불확정 참조의 특수한 경우다.** JVM이 `java.lang.ref.Finalizer`(내부적으로
> `java.lang.ref.FinalReference`)라는 **비공개 참조 클래스**로 `finalize()` 를 정의한 객체를
> 추적한다. **`finalize()` 가 있는 객체를 할당하면 JVM은 객체 두 개를 할당한다** —
> 객체 자신과, 그 객체를 참조 대상으로 하는 `Finalizer` 참조.

**⚠️ 왜 다른 불확정 참조보다 훨씬 나쁜가**

> **소프트/위크 참조는 참조 대상이 GC 대상이 되면 참조 대상 자체가 즉시 해제된다.**
> 참조 객체는 참조 큐에 놓이지만 **더 이상 아무것도 가리키지 않는다**(`get()` 이 `null` 을 반환).
> **두 사이클 페널티가 참조 객체에만 적용된다.**
>
> **파이널 참조는 다르다.** `Finalizer` 구현이 참조 대상의 `finalize()` 를 부르려면 **참조 대상에
> 접근할 수 있어야 하므로, 파이널라이저 참조가 큐에 놓일 때 참조 대상을 해제할 수 없다.**
> 참조 큐가 파이널라이저를 처리하고 `Finalizer` 객체가 큐에서 제거되어 수집 대상이 된
> **그때서야 참조 대상도 해제된다.**
>
> **그래서 파이널라이저가 다른 불확정 참조보다 GC에 훨씬 큰 영향을 준다** — **참조 대상이
> 소비하는 메모리가 불확정 참조 객체가 소비하는 것보다 훨씬 클 수 있기 때문**이다.

**기능적 문제**: **`finalize()` 메서드가 참조 대상에 대한 새 강한 참조를 부주의하게 만들 수 있다.**
그러면 또 GC 페널티가 생기고(다시 강하게 참조되지 않을 때까지 해제 안 됨),
**기능적으로 큰 문제가 생긴다 — 다음에 그 객체가 수집 대상이 되면 `finalize()` 가 호출되지 않아
기대한 정리가 일어나지 않는다.**

> **JDK도 어쩔 수 없이 쓴다** — ZIP 파일 조작 클래스가 그렇다. ZIP 열기가 네이티브 메모리를
> 할당하는 네이티브 코드를 쓰는데, **개발자가 `close()` 를 잊으면 어떻게 되나?
> 파이널라이저가 `close()` 가 호출됐음을 보장할 수 있다.**
>
> **규칙: 파이널라이저를 피할 수 없는 상황이라면 그 객체가 접근하는 메모리를 최소로 유지하라.**

**대안 — 다른 불확정 참조로 직접 구현하기**

`PhantomReference` 를 쓰라는 권고가 있고 **좋은 선택이다**(참조 대상이 강하게 참조되지 않게 되면
참조 객체가 비교적 빨리 정리되고, 디버깅 시 목적이 분명하다). **다만 위크 참조로도 같은 목표를
달성할 수 있고, 위크 참조는 더 많은 곳에 쓸 수 있다.**

```java
private static class CleanupFinalizer extends WeakReference {
    private static ReferenceQueue<CleanupFinalizer> finRefQueue;
    private static HashSet<CleanupFinalizer> pendingRefs = new HashSet<>();  // ★
    private boolean closed = false;

    public CleanupFinalizer(Object o) {
        super(o, finRefQueue);
        allocateNative();
        pendingRefs.add(this);
    }
    public void setClosed() { closed = true; doNativeCleanup(); }
    public void cleanup()   { if (!closed) doNativeCleanup(); }
    private native void allocateNative();
    private native void doNativeCleanup();
}
```
참조 큐 처리는 **데몬 스레드**에서 한다.

> **⚠️ 이 예제의 까다로운 부분은 `pendingRefs` 집합이다.** 그것이 없으면
> **위크 참조 자체가 참조 큐에 놓일 기회를 갖기 전에 수집돼 버린다.**

**전통적 파이널라이저의 두 한계를 극복한다**
- **더 나은 성능** — 참조 대상의 메모리(여기서는 `data` 해시맵)가 **참조 대상이 수집되는 즉시**
  해제된다(파이널라이저 메서드에서 하는 게 아니라)
- **참조 대상이 정리 코드에서 부활할 방법이 없다** — 이미 수집됐으니까

> **그래도 파이널라이저에 대한 다른 반대는 이 코드에도 적용된다**: GC가 참조 대상을 언제 해제할지
> 보장할 수 없고, 참조 큐 스레드가 특정 객체를 언제 처리할지도 보장할 수 없다.
> **그런 객체가 많으면 큐 처리가 꽤 비싸진다. 모든 불확정 참조처럼 아껴 써야 한다.**

> **파이널라이저 큐 모니터링**
> ```bash
> jcmd <pid> GC.run_finalization    # 큐를 처리시킨다
> jmap -finalizerinfo <pid>         # 크기 확인 (jconsole VM Summary 탭에도 실시간 표시)
> ```
> **힙 덤프 분석 시 파이널라이저 큐에 객체가 없게 만들어 두면 편하다** — 어차피 해제될 것들이라
> **덤프에서 빼면 힙에서 다른 무슨 일이 일어나는지 보기 쉬워진다.**

## 장 요약

> **빠른 자바 프로그램은 메모리 관리에 결정적으로 의존한다. GC 튜닝도 중요하지만, 최대 성능을
> 얻으려면 애플리케이션 안에서 메모리를 효과적으로 써야 한다.**

> **현재 하드웨어 추세가 개발자로 하여금 메모리를 생각하지 않게 만든다** — 노트북에 16GB가
> 있는데 쓰지도 않는 8바이트 객체 참조 하나를 얼마나 걱정해야 하나?
> **그러면서 프로그래밍의 통상적인 시간/공간 트레이드오프가 "시간/공간-그리고-시간" 트레이드오프로
> 바뀔 수 있다는 것을 잊는다** — **힙 공간을 너무 많이 쓰면 GC가 더 필요해져 오히려 느려진다.**
> **자바에서 힙 관리는 여전히 중요하다.**

**관리의 상당 부분은 특수 메모리 기법(객체 풀, 스레드 로컬, 불확정 참조)을 언제 어떻게 쓸지에
집중된다. 신중하게 쓰면 성능이 크게 향상되지만, 남용하면 그만큼 쉽게 성능이 저하된다.
제한된 양에서 — 문제의 객체 수가 작고 한정적일 때 — 이 기법들은 꽤 효과적일 수 있다.**
