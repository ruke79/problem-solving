## 원칙 1 — 실제 애플리케이션을 테스트하라

테스트 대상 코드는 크게 세 부류로 나뉘고, **실제 애플리케이션에 가까울수록 결과가 좋다.**

### 마이크로벤치마크 (Microbenchmark)

아주 작은 단위를 재는 테스트다. `synchronized` 메서드 대 비동기화 메서드 호출 시간, 스레드 생성 대
스레드 풀 사용 오버헤드, 두 알고리즘 구현의 실행 시간 비교 같은 것들.

**좋아 보이지만 올바르게 작성하기가 대단히 어렵다.** 저자는 피보나치 50번째 수를 구하는
마이크로벤치마크를 예로 들어 함정을 하나씩 벗겨낸다.

#### 함정 ① — 결과를 사용하지 않으면 계산 자체가 사라진다

```java
long then = System.currentTimeMillis();
for (int i = 0; i < nLoops; i++) {
    double l = fibImpl1(50);   // 결과를 아무도 안 씀
}
long now = System.currentTimeMillis();
```

계산 결과가 프로그램 상태를 전혀 바꾸지 않으므로 **컴파일러가 계산을 통째로 버려도 된다.**
Java 7·8 컴파일러는 실제로 그렇게 한다. 루프 횟수나 구현과 무관하게 몇 밀리초만에 끝난다.

→ 해결: 결과를 **읽히게** 만든다. 지역 변수를 `volatile` 인스턴스 필드로 바꾼다.
싱글 스레드 벤치마크라도 `volatile` 이 필요하다.

> **스레드 마이크로벤치마크는 특히 위험하다.** 벤치마크 코드가 작으니 대부분의 시간이
> `synchronized` 블록 안에서 흘러간다. 전체의 50%만 동기화 구간이어도 스레드 두 개가 동시에
> 진입하려 할 확률이 매우 높다. 결국 **JVM이 경합을 어떻게 처리하는지를 재는 테스트**가 되어
> 버리고, 실제 코드에서는 거의 나타나지 않을 동기화 병목을 없애느라 시간을 쓰게 된다.

#### 함정 ② — 불필요한 연산이 섞이면 안 된다

연산이 하나뿐이면 똑똑한 컴파일러는 루프를 한 번만 돌리거나 반복 일부를 버릴 수 있다.
그렇다고 입력을 매번 난수로 만들면 **난수 생성 시간이 측정에 포함된다.**

→ 해결: 입력값을 **미리 배열로 계산해 둔다.**

```java
int[] input = new int[nLoops];
for (int i = 0; i < nLoops; i++) input[i] = random.nextInt();
long then = System.currentTimeMillis();
for (int i = 0; i < nLoops; i++) { ... fibImpl1(input[i]) ... }
```

#### 함정 ③ — 입력 범위가 실제 사용과 달라진다

임의의 난수를 쓰면 절반이 음수라 즉시 예외가 나고, 1476을 넘으면 `double` 로 표현할 수 없어
또 예외가 난다. 이때 **범위 검사를 앞에서 하는 느린 구현**이 원래 구현보다 빨라 보이는 역전이
일어난다. 실제 사용자는 100 미만만 넘긴다면 이 비교는 **완전히 틀린 답**을 준다.

> 1장의 원칙이 여기 걸린다 — **일반적인 경우(common case)를 최적화하라.**

#### 함정 ④ — 워밍업이 없으면 컴파일 성능을 재게 된다

Java는 코드를 많이 실행할수록 빨라진다(4장). 마이크로벤치마크에는 **워밍업 구간이 필수**다.
없으면 측정하려던 코드가 아니라 컴파일 과정을 재는 셈이 된다.

#### 그래도 남는 문제

- 루프·메서드 호출 오버헤드와 `volatile` 쓰기 비용이 측정에 섞인다.
- 컴파일러는 **프로파일 피드백**(어떤 메서드가 자주 불리는가, 호출 시 스택 깊이, 인자의 실제 타입)
  으로 최적화를 정한다. 그래서 **같은 코드라도 마이크로벤치마크 안에서와 실제 앱 안에서 다르게
  컴파일된다.**
- 반복 횟수를 키우면 총 차이는 초 단위로 보이지만 **1회당 차이는 나노초**다. 컬렉션처럼 수백만 번
  접근하는 곳이면 의미가 있지만(12장), 요청당 한 번 일어나는 연산이라면 나노초 회귀를 쫓느라
  더 중요한 최적화 시간을 잃는다.

### 매크로벤치마크 (Macrobenchmark)

**애플리케이션 자체를, 쓰는 외부 자원과 함께** 재는 것이 최선이다. LDAP 인증을 한다면 LDAP 호출을
포함한 상태로 테스트해야 한다. 모듈 테스트에서 스텁으로 대체하는 것은 몰라도, **전체 구성으로
반드시 한 번은 재야 한다.**

이유는 두 가지다.

**① 복잡한 시스템은 부분의 합이 아니다.** DB 호출을 목으로 대체하면 DB 성능 걱정은 없어지지만,
DB 커넥션은 버퍼로 힙을 많이 먹고, 네트워크는 데이터가 늘면 포화되고, 단순한 메서드 집합을
호출하는 코드는 JDBC 드라이버 같은 복잡한 코드와 **다르게 최적화**되며, CPU는 짧은 코드 경로를
더 효율적으로 파이프라이닝·캐싱한다.

**② 자원 배분의 문제다.** 저자의 유명한 예:

```
사용자 → LDAP(200 RPS) → 비즈니스 계산(100 RPS) → DB(100 RPS) → 계산 → 응답
```

비즈니스 계산이 회사가 돈을 버는 이유이고 가장 중요해 보인다. 그런데 이걸 100% 빠르게 만들어
200 RPS로 올려도 **전체 처리량은 여전히 100 RPS**다. DB가 100 RPS에서 막혀 있기 때문이다.
다른 병목을 손보기 전까지 비즈니스 로직 개선은 아무 효과가 없다.

> 시간이 낭비된 건 아니다. 다른 병목을 고치고 나면 그때 효과가 드러난다. **우선순위의 문제**다.
> 전체를 테스트하지 않으면 어디에 시간을 써야 이득인지 알 수 없다.

> **여러 JVM을 같은 하드웨어에서 돌릴 때가 특히 중요하다.** JVM은 기본적으로 머신 자원을 전부
> 자기가 쓴다고 가정하고 튜닝돼 있다. GC 사이클 동안 한 JVM은 모든 프로세서를 100%까지 몰아쓴다.
> 실행 전체 평균으로는 CPU 40%로 보여도 실제로는 어떤 구간은 30%, 어떤 구간은 100%다.
> 다른 애플리케이션과 함께 돌면 GC 때 100%를 못 받아 성능이 눈에 띄게 달라진다.

### 메조벤치마크 (Mesobenchmark) — 저자의 조어

Java SE 엔지니어와 EE 엔지니어가 "마이크로벤치마크"라는 말을 서로 다르게 쓴다는 관찰에서 나온
개념이다. "단순 JSP의 응답 시간"을 재는 EE 테스트는 소켓 관리·요청 파싱·JSP 탐색과 컴파일·응답
쓰기까지 상당한 코드가 돈다. 전통적 기준으로는 마이크로가 아니다. 그렇다고 보안·세션 관리가 없으니
매크로도 아니다. **그 중간이 메조벤치마크**다.

- 마이크로보다 함정이 적다 — 컴파일러가 통째로 날릴 죽은 코드가 있을 가능성이 낮다.
- 매크로보다 다루기 쉽다. 스레드를 붙이기도 쉽다.
- **자동화 테스트, 특히 모듈 수준 회귀 테스트에 적합하다.**

다만 완벽하지 않다. 저자가 든 예:

| 테스트 | 앱 서버 1 | 앱 서버 2 |
|---|---|---|
| 단순 JSP | 19 ms | 50 ms |
| 세션 있는 JSP | 75 ms | 50 ms |

단순 JSP만 보고 서버 1을 고른 개발자는, 실제 앱이 항상 세션을 만든다면 **틀린 선택**을 한 것이다.
서버 2는 매 요청마다 세션을 자동 생성하고 있었을 뿐이다.

> **요약**
> 1. 좋은 마이크로벤치마크는 쓰기 어렵고 가치가 제한적이다. 쓰더라도 대략적 개요용으로만.
> 2. 코드가 실제로 어떻게 도는지 아는 유일한 방법은 전체 애플리케이션 테스트다.
> 3. 메조벤치마크는 합리적인 타협이지만 전체 테스트의 대체재는 아니다.

## 책 전체의 공통 예제

주식의 "역사적" 최고·최저가와 표준편차를 계산하는 애플리케이션. 데이터는 전부 허구(난수 생성)다.

- `StockPrice` — 하루치 가격 범위. `BigDecimal` 로 통화를 저장한다(`double` 은 반올림 문제).
- `StockPriceHistory` — 기간별 컬렉션. 평균·표준편차·히스토그램은 **파생값**이라 **즉시(eager)
  계산과 지연(lazy) 계산을 비교하는 데 쓰인다.**
- 제곱근은 표준 API에 `BigDecimal` 용이 없어 **바빌로니아법**으로 직접 구현했다. 초기 추정값을
  일부러 나쁘게 둬서 계산에 시간이 걸리게 했다(비즈니스 로직 흉내).

> 저자가 여기서 1장 원칙을 다시 짚는다 — **더 나은 알고리즘을 쓰는 것이 JVM 튜닝이나 코딩
> 관행보다 코드를 빠르게 만드는 경우가 많다.**

Java EE 모드에서는 서블릿 → 스테이트리스 EJB → JPA 빈 → JSP 경로를 탄다.
중간 계층 캐싱 여부도 예제로 비교한다.

> **테스트 시스템**: AMD Athlon X4 640 (4코어), 8GB RAM, Ubuntu 12.04 LTS.
> 벤치마크는 소프트웨어만큼이나 **하드웨어의 측정**이기도 하다.

## 원칙 2 — 처리량·배치·응답 시간을 구분하라

### 경과 시간(배치) 측정

가장 단순하다. "25년치 주식 1만 종목의 표준편차 계산에 얼마나 걸리나."

Java에서는 **JIT 컴파일**이라는 주름이 하나 있다. 최적 성능에 도달하는 데 수 분이 걸릴 수 있어서
보통 워밍업 뒤에 측정한다.

> **워밍업이 컴파일만의 문제가 아니다.** JPA는 읽은 데이터를 캐시하므로 두 번째가 빠르다(11장).
> OS는 읽은 파일을 메모리에 페이징하므로 두 번째 읽기가 빠르다. **캐시가 있는 곳은 어디든**
> 워밍업이 문제가 된다.

반대로 **시작부터 끝까지의 성능이 중요한 경우도 많다.** 1만 건 리포트를 만드는 사용자에게는
앞 5천 건이 50% 느렸는지가 관심사가 아니다. 앱 서버조차 피크 성능 도달에 45분이 걸린다면,
그 45분 동안 접속한 사용자에게 워밍업 중 성능은 **실재하는 성능**이다.
그래서 이 책의 예제 상당수가 배치 지향이다.

### 처리량(Throughput) 측정

일정 시간에 처리한 작업량. 클라이언트-서버 테스트에서 처리량 측정은 **생각 시간(think time)이
0**이라는 뜻이다. 응답을 받으면 즉시 다음 요청을 보낸다. TPS/RPS/OPS로 보고한다.

⚠️ **클라이언트가 병목이 될 위험**이 항상 있다. 클라이언트 머신에 CPU가 모자라거나 요청 준비에
시간이 걸리면 **서버가 아니라 클라이언트를 재는 테스트**가 된다. 생각 시간 0 테스트가 스레드당
일이 많으므로 이 위험이 더 크다. 그래서 처리량 테스트는 보통 **응답 시간 테스트보다 적은 수의
클라이언트 스레드**로 돌린다.

> 처리량 테스트가 평균 응답 시간도 함께 보고하는 경우가 많은데, **처리량이 같지 않으면 그
> 숫자의 변화는 성능 문제의 근거가 아니다.** 0.5초 응답으로 500 OPS를 내는 서버가
> 0.3초 응답에 400 OPS인 서버보다 낫다.

### 응답 시간(Response Time) 테스트

클라이언트가 작업 사이에 **생각 시간만큼 잠든다.** 사용자가 URL을 입력하고, 페이지를 읽고, 링크를
누르고, 또 읽는 행동을 흉내낸다. 생각 시간이 들어가면 **처리량은 고정**되고, 그 고정된 부하에
서버가 얼마나 빨리 응답하는가가 지표가 된다.

> **생각 시간 vs 사이클 시간**
> - 생각 시간: 요청 후 무조건 30초 잔다 → 처리량이 응답 시간에 **의존**한다
>   (응답 1초면 0.032 OPS, 2초면 0.031 OPS).
> - 사이클 시간: 요청 간격 총합을 30초로 맞춘다(`sleep(30초 - 응답시간)`) → 처리량이 **고정**된다.
>
> 실제 도구는 사용자를 흉내내려고 생각 시간에 난수 변동을 준다. 스레드 스케줄링도 실시간이
> 아니다. 그래서 보고된 처리량은 실행마다 조금씩 다르다 — 다만 **기대값에서 크게 벗어났다면
> 테스트 실행에 뭔가 잘못된 것**이다.

### 평균이냐 백분위냐

이 절의 핵심이다. 저자는 두 그래프로 설명한다.

**정상적인 경우** — 응답 1~5초 범위, 평균 2.35초, 90퍼센타일 4초. 평균 < 90퍼센타일.

**이상치가 있는 경우** — 한 요청이 100초. 평균이 **5.95초**로 폭등하고 90퍼센타일은 **1.0초**다.
**둘의 위치가 역전된다.** 이 경우 집중해야 할 것은 이상치를 줄이는 것이다.

> Java 애플리케이션은 **GC 일시 정지** 때문에 이상치가 더 쉽게 생긴다. 100초까지는 아니어도,
> 평균 응답 시간이 작은 테스트에서는 GC 정지가 큰 이상치가 된다.
>
> **하나만 봐야 한다면 백분위가 낫다** — 다수 사용자에게 이득이 가니까. 하지만 **평균과
> 백분위를 함께** 보는 것이 더 낫다. 그래야 큰 이상치가 있는 경우를 놓치지 않는다.

> **부하 생성기**: 이 책은 Faban(오픈소스 Java 부하 생성기)을 쓴다. 딸린 `fhb` 로 간단한 URL을 잰다.
> ```
> % fhb -W 1000 -r 300/300/60 -c 25 http://host:port/StockServlet?stock=SDO
> ops/sec: 8.247   avg. time: 0.022   90th %: 0.030   95th %: 0.035   99th %: 0.035
> ```
> 클라이언트 25개(`-c`), 사이클 시간 1초(`-W`), 워밍업 5분 / 측정 5분 / 종료 1분(`-r`).

## 원칙 3 — 변동성을 이해하라

**같은 데이터를 처리해도 실행할 때마다 답이 다르다.** 배경 프로세스, 네트워크 혼잡도가 영향을 준다.
좋은 벤치마크는 오히려 **일부러 무작위성을 넣어** 현실을 흉내낸다. 그래서 문제가 생긴다 —
**두 실행의 차이가 진짜 회귀인가, 무작위 변동인가?**

여러 번 돌려 평균을 내면 될 것 같지만 그렇게 간단하지 않다.

### 저자의 예시 — 직관이 어떻게 배신하는가

| | 기준(baseline) | 대상(specimen) |
|---|---|---|
| 1회차 | 1.0초 | 0.5초 |
| 2회차 | 0.8초 | 1.25초 |
| 3회차 | 1.2초 | 0.5초 |
| **평균** | **1.0초** | **0.75초** |

평균만 보면 **25% 개선**이다. 3개 중 2개가 기준 평균보다 낮고 개선 폭도 크다. 좋아 보인다.

**그런데 t-검정을 하면 두 테스트의 성능이 같을 확률이 43%다.** 즉 다르다고 말할 수 있는 신뢰도는
57%밖에 안 된다. **결과의 변동이 크기 때문**이다. 변동이 클수록 평균 차이가 진짜인지 판단하기 어렵다.

### Student's t-test

- **귀무가설**: 두 테스트의 성능이 같다.
- **p-value**: 귀무가설이 참일 확률. 위 예에서 0.43.
- **α-value**: 통계적 유의성의 임계점. 관례적으로 0.1(90%), 0.05, 0.01을 쓴다.
- p-value가 1 − α 보다 크면 통계적으로 유의하다고 본다.

> **통계와 어법**
> 정확한 표현: "대상이 기준과 다를 확률이 57%이고, 그 차이의 최선의 추정치는 25%다."
> 흔한 표현: "25% 개선을 57% 신뢰 수준으로 확신한다." — 통계학자를 미치게 하지만 편한 축약이다.
> **57%는 "25% 개선을 57% 확신한다"가 아니라 "다르다는 것을 57% 확신한다"** 이다.
> 25%일 수도, 125%일 수도, 심지어 더 나빠졌을 수도 있다.

**데이터를 더 넣으면 어떻게 되나.** 같은 값 3개씩을 추가하면 p-value가 0.43 → **0.19**(81% 신뢰),
한 번 더 추가하면 **91%** — 통상적 유의 수준을 넘는다. **통계적으로 결론이 안 나는 흔한 이유는
표본이 부족해서다.**

> **통계적 유의성 ≠ 통계적 중요성**
> 변동이 작고 평균 1초인 기준과 1.01초인 대상은 p-value 0.01이 나올 수 있다 — **99% 확신하는 1% 차이.**
> 다른 테스트는 10% 회귀인데 p-value 0.2로 유의하지 않을 수 있다.
> **어느 쪽에 가장 귀한 자원(추가 조사 시간)을 써야 하나?**
> 확신은 덜해도 **10% 쪽**이다. 1% 차이가 더 확실하다고 해서 더 중요한 건 아니다.

> **요약**
> 1. 두 결과가 다른지 판단하려면 통계 분석이 필요하다. 눈에 보이는 차이가 우연이 아님을 확인해야 한다.
> 2. 엄밀한 방법은 t-검정이다.
> 3. t-검정은 **회귀가 존재할 확률**을 알려줄 뿐, **어떤 회귀를 쫓고 어떤 것을 무시할지**는 알려주지
>    않는다. 그 균형을 찾는 것이 성능 공학의 **예술**에 해당하는 부분이다.

## 원칙 4 — 일찍, 자주 테스트하라

이상적으로는 코드가 저장소에 들어갈 때 성능 테스트가 돌고, 회귀를 일으키는 코드는 커밋이 막혀야 한다.

**그런데 이 권고는 앞의 권고들 및 현실과 긴장 관계에 있다.** 좋은 성능 테스트는 최소 중형
메조벤치마크이고, 차이가 진짜인지 확인하려면 여러 번 반복해야 한다. 큰 프로젝트에서는 며칠~일주일이
걸려서 커밋 전 실행이 비현실적이다.

전형적인 개발 주기가 상황을 더 어렵게 만든다. 기능 동결일(feature freeze)이 있으면:

1. **일정 압박 때문에 개발자가 성능 수정을 미룬다.** 주기 초반에 1% 회귀를 넣은 개발자는 고치라는
   압박을 받지만, **동결일 저녁에 20% 회귀를 커밋한 개발자는 나중에 처리하면 된다.**
2. **코드가 바뀌면 성능 특성도 바뀐다.** 힙 사용량이 달라지고 컴파일 방식이 달라진다.

그래도 자주 테스트하는 것은 중요하다. 5% 회귀를 넣은 개발자에게 "아직 통합 안 된 기능이
들어오면 작은 수정으로 사라진다"는 계획이 있을 수 있다. 합리적이지만 몇 주간 그 5% 회귀를
안고 가야 하고, **그것이 다른 회귀를 가린다**는 부작용이 따른다. 반대로 아키텍처를 바꿔야 고쳐지는
회귀라면, 다른 코드가 그 구현에 의존하기 전에 일찍 잡는 게 낫다. **분석 능력과 정치력이 함께 필요한
줄타기다.**

### 지켜야 할 지침

**모든 것을 자동화하라(Automate everything)**
스크립트가 새 코드를 설치하고, 전체 환경으로 구성하고(DB 커넥션, 사용자 계정), 테스트를
**여러 번** 돌리고, **t-검정을 수행하고**, 신뢰 수준과 측정된 차이를 담은 리포트를 내야 한다.
그리고 실행 전에 머신이 알려진 상태인지 확인해야 한다 — 예상 못 한 프로세스가 없는지, OS 설정이
맞는지. **환경이 실행마다 같아야 성능 테스트가 재현 가능하다.**

**모든 것을 측정하라(Measure everything)**
- 실행 내내 샘플링한 시스템 정보: CPU·디스크·네트워크·메모리 사용량
- 애플리케이션 로그와 **GC 로그**
- 가능하면 Java Flight Recorder 기록(3장), 주기적 스레드 스택, 힙 히스토그램이나 힙 덤프
- 다른 시스템의 데이터도 — DB를 쓴다면 DB 머신의 시스템 통계와 진단 출력(오라클 AWR 리포트 등)

이 데이터가 회귀 분석을 안내한다.
- CPU 사용량이 늘었다 → 프로파일 정보에서 무엇이 더 걸리는지 본다
- GC 시간이 늘었다 → 힙 프로파일에서 무엇이 메모리를 더 먹는지 본다
- **CPU와 GC 시간이 둘 다 줄었다 → 어딘가의 경합이 성능을 떨어뜨렸을 가능성이 높다.**
  스택 데이터가 동기화 병목을 가리키고(9장), JFR로 지연을 찾고, DB 로그가 DB 경합을 가리킨다

> 회귀의 원인을 찾을 때는 **탐정 놀이**다. 단서가 많을수록 좋다. 1장에서 말했듯 회귀가 반드시
> JVM에 있는 것도 아니다.

**목표 시스템에서 실행하라(Run on the target system)**
싱글 코어 노트북과 256스레드 SPARC은 완전히 다르게 동작한다. 큰 머신은 스레드 경합이 줄어드는
대신 **작은 노트북에서는 보이지 않던 동기화 병목이 드러난다.**

덜 드러나지만 똑같이 중요한 차이들:
- **많은 튜닝 플래그가 하드웨어를 보고 기본값을 계산한다.**
- 코드가 플랫폼마다 다르게 컴파일된다.
- 캐시(소프트웨어, 특히 **하드웨어**)가 시스템과 부하에 따라 다르게 동작한다.

작은 하드웨어의 작은 테스트로 근사·외삽할 수는 있다. 하지만 **외삽은 예측일 뿐이고 예측은
틀릴 수 있다.** 대규모 시스템은 부분의 합 이상이며, 목표 플랫폼에서의 부하 테스트를 대체할 것은 없다.

## 장 요약

- **무엇을 테스트할지 고르는 것**부터가 경험과 직관의 영역이다. 마이크로벤치마크가 가장 도움이
  덜 되고, 모듈 테스트에서 다계층 환경까지 넓은 연속선이 있다. **결국 프로덕션에 배포되는 형태의
  전체 애플리케이션 테스트를 대체할 것은 없다.**
- **무엇이 진짜 회귀인지도 흑백이 아니다.** 프로그램은 항상 무작위적으로 동작하고, 무작위성이
  들어온 이상 100% 확신은 불가능하다. 통계 분석이 객관성을 높여 주지만 주관은 남는다.
- 이 토대 위에 **모든 것을 기록하는 자동화 테스트 시스템**을 올려야, 성능 분석가가 과학과 예술을
  함께 적용할 수 있다.
