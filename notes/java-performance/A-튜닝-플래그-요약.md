# 부록 A. 튜닝 플래그 요약 (Summary of Tuning Flags)

> ⚠️ **JDK 17 기준 차이** — **이 표의 플래그 중 여럿이 JDK 17 에서 아예 인식되지 않는다**(`UseConcMarkSweepGC`·`UseParNewGC`·`UseParallelOldGC`·`PermSize`·`UnlockCommercialFeatures` 등). **표를 그대로 믿지 말고 `-XX:+PrintFlagsFinal` 로 확인한 뒤 쓸 것.**
> 전체 대조는 [`00-JDK-17-차이.md`](00-JDK-17-차이.md) 참고.

> 이 부록은 책 전체에서 나온 플래그를 **10개 표**로 다시 모은 것이다.
> 각 항목은 `무엇을 하는가 / 언제 쓰는가 / 어느 장에서 설명했는가` 세 칸으로 되어 있다.
>
> **이 부록의 존재 자체가 이 책의 태도다.** 플래그는 알파벳순 사전이 아니라
> **"언제 쓰는가"로 묶여 있다.** 표에서 반복되는 문장이 두 종류인 것이 눈에 띈다 —
> **"이 문제를 겪고 있을 때만 만져라"** 와 **"이건 그냥 항상 켜라"**.
> 대부분의 플래그는 앞쪽이고, 뒤쪽은 손에 꼽을 만큼 적다.

---

## 표 A-1. JIT 컴파일러 튜닝 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 | 관련 장 |
| --- | --- | --- | --- |
| `-server` | 서버 컴파일러를 고른다 | **빠른 성능이 필요한 장기 실행 애플리케이션** | 4장 |
| `-client` | 클라이언트 컴파일러를 고른다 | **기동 시간이 가장 중요한 애플리케이션** | 4장 |
| `-XX:+TieredCompilation` | 계층형 컴파일(클라이언트+서버 둘 다)을 쓴다 | **가능한 최고의 성능을 원하고**, 늘어난 컴파일 코드를 담을 **네이티브 메모리가 충분할 때** | 4장 |
| `-XX:ReservedCodeCacheSize=<MB>` | JIT가 컴파일한 코드를 담을 공간을 예약한다 | **코드 캐시가 찼다는 경고를 봤을 때**, 그리고 **일반적으로 계층형 컴파일을 쓸 때** | 4장 (코드 캐시 튜닝) |
| `-XX:InitialCodeCacheSize=<MB>` | 코드 캐시의 초기 공간을 할당한다 | 코드 캐시 메모리를 **미리 잡아둬야 할 때 — 아주 드물다** | 4장 (코드 캐시 튜닝) |
| `-XX:CompileThreshold=<N>` | 메서드/루프가 컴파일되기 전까지 실행되는 횟수 | **서버 컴파일러에서** 더 많은 메서드가, 더 일찍 컴파일되게 한다. **계층형 컴파일을 안 쓸 때만 이따금 이점이 있다** | 4장 (컴파일 임계값) |
| `-XX:+PrintCompilation` | JIT 컴파일러의 동작 로그를 낸다 | **중요한 메서드가 컴파일되지 않는다고 의심될 때**, 또는 컴파일러가 뭘 하는지 궁금할 때 | 4장 (컴파일 과정 들여다보기) |
| `-XX:CICompilerCount=<N>` | JIT 컴파일러 스레드 수 | **계층형 컴파일에서 컴파일러 스레드가 너무 많이 뜰 때** (특히 여러 JVM을 돌리는 큰 머신) | 4장 (컴파일 스레드) |

> **표 A-1이 말하는 것**: JIT 쪽에서 실제로 손댈 일이 있는 건 사실상 `ReservedCodeCacheSize`
> 하나다. 나머지는 **진단용(`PrintCompilation`)이거나, 특수 상황용이다.**

## 표 A-2. GC 알고리즘 선택 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:+UseSerialGC` | 단순한 **단일 스레드** GC | **작은 힙(100 MB)** |
| `-XX:+UseParallelOldGC` | **여러 스레드로 올드 영역**을 수집(애플리케이션 스레드는 멈춤) | **이따금 긴 멈춤을 견딜 수 있고**, CPU 사용을 최소화하면서 **처리량을 최대화**하고 싶을 때 |
| `-XX:+UseParallelGC` | **여러 스레드로 영 영역**을 수집(애플리케이션 스레드는 멈춤) | `UseParallelOldGC` 와 **함께** 쓴다 |
| `-XX:+UseConcMarkSweepGC` | **백그라운드 스레드**로 올드 영역의 가비지를 **최소한의 멈춤**으로 제거 | 백그라운드 스레드에 쓸 **CPU 여유가 있고**, 긴 GC 멈춤을 원치 않으며, **힙이 상대적으로 작을 때** |
| `-XX:+UseParNewGC` | 여러 스레드로 영 영역 수집 | `UseConcMarkSweepGC` 와 **함께** 쓴다 |
| `-XX:+UseG1GC` | **영 영역은 멈추고 여러 스레드로**, **올드 영역은 백그라운드로 최소 멈춤** 수집 | 백그라운드 스레드에 쓸 **CPU 여유가 있고**, 긴 GC 멈춤을 원치 않으며, **힙이 작지 않을 때** |

> **CMS와 G1의 선택 기준이 딱 한 단어 차이다.** 조건 세 개 중 앞의 둘은 완전히 같고,
> 세 번째만 **"힙이 상대적으로 작을 때"(CMS)** vs **"힙이 작지 않을 때"(G1)** 로 갈린다.
> 저자가 6장에서 길게 설명한 것을 한 줄로 압축하면 이렇게 된다.

## 표 A-3. 모든 GC 알고리즘 공통 플래그

### 힙과 세대 크기

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-Xms` | 힙의 **초기** 크기 | 기본 초기 크기가 애플리케이션에 **너무 작을 때** |
| `-Xmx` | 힙의 **최대** 크기 | 기본 최대 크기가 **너무 작을(또는 너무 클) 때** |
| `-XX:NewRatio` | **영 : 올드 비율**. 올리면 영 영역 비중이 줄고, 내리면 늘어난다 | **초기 설정일 뿐이다** — 적응형 크기 조정을 끄지 않는 한 비율은 변한다(CMS는 예외로 영 영역 크기가 고정) |
| `-XX:NewSize` | 영 영역의 **초기** 크기 | 애플리케이션 요구사항을 **아주 정밀하게 튜닝했을 때** |
| `-XX:MaxNewSize` | 영 영역의 **최대** 크기 | 위와 같다 |
| `-Xmn` | 영 영역의 **초기이자 최대** 크기 | 위와 같다 |

> **`NewRatio` 항목에 달린 인과 설명이 이 표에서 가장 실전적이다.**
> **영 영역이 작아질수록 → 영 GC는 더 잦아지고, 풀 GC는 더 뜸해진다. 반대도 성립한다.**
> 이 한 문장이 세대 크기 튜닝의 전부다.

### 퍼머넌트 영역 / 메타스페이스

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:PermSize=N` **(JDK 7 전용)** | permgen 초기 크기 | **클래스를 많이 쓰는 애플리케이션**은 기본값에서 올린다 |
| `-XX:MaxPermSize=N` **(JDK 7 전용)** | permgen 최대 크기 | 위와 같다 |
| `-XX:MetaspaceSize=N` **(JDK 8 전용)** | 메타스페이스 초기 크기 | 위와 같다 |
| `-XX:MaxMetaspaceSize=N` **(JDK 8 전용)** | 메타스페이스 최대 크기 | **클래스 메타데이터가 쓰는 네이티브 공간을 제한하고 싶을 때 낮춘다** |

> **JDK 8의 `MaxMetaspaceSize` 는 "올려라"가 아니라 "제한하고 싶으면 낮춰라"로 적혀 있다.**
> permgen 시절과 방향이 정반대다. 기본값이 사실상 무제한이라 **폭주를 막는 안전장치** 쪽으로
> 용도가 바뀌었기 때문이다.

### 병렬성과 GC 로깅

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:ParallelGCThreads=N` | GC가 쓰는 스레드 수 | **JVM을 여러 개 돌리는 시스템에서는 낮춘다.** 아주 큰 시스템의 아주 큰 힙에서는 올리는 것을 고려 |
| `-verbose:gc` | 기본 GC 로깅 | **GC 로깅은 항상 켜야 하지만**, 더 자세한 로그가 대체로 낫다 |
| `-Xloggc:<path>` | GC 로그를 표준 출력이 아닌 파일로 | **항상.** 로그의 정보를 보존하기 위해 |
| `-XX:+PrintGC` | 기본 GC 로깅 | 위 `-verbose:gc` 와 같다 |
| `-XX:+PrintGCDetails` | **상세** GC 로깅 | **항상, 프로덕션에서도.** 로깅 오버헤드가 미미하다 |
| `-XX:+PrintGCTimeStamps` | 각 항목에 **상대 시각** | **항상.** 날짜 스탬프를 쓰는 경우만 예외 |
| `-XX:+PrintGCDateStamps` | 각 항목에 **시각(time-of-day)** | 타임스탬프보다 오버헤드가 약간 크지만 **처리하기 더 쉬울 수 있다** |
| `-XX:+PrintReferenceGC` | GC 중 **소프트/위크 레퍼런스 처리** 정보 | 그런 레퍼런스를 많이 쓰는 프로그램에서 **GC 오버헤드에 미치는 영향을 알고 싶을 때** |
| `-XX:+UseGCLogFileRotation` | GC 로그 회전 | **몇 주씩 돌아가는 프로덕션 시스템** — 로그가 공간을 많이 먹을 때 |
| `-XX:NumberOfGCLogFiles=N` | 회전 시 보존할 로그 파일 수 | 위와 같다 |
| `-XX:GCLogFileSize=N` | 회전 전 각 로그 파일 크기 | 위와 같다 |

> **"항상 켜라"가 이 표에 몰려 있다.** `-Xloggc`, `-XX:+PrintGCDetails`, `-XX:+PrintGCTimeStamps`.
> 저자가 5장에서 한 주장 — **"GC 로그는 프로덕션에서도 끄지 마라, 오버헤드가 사실상 없고
> 사후 분석에서 유일한 증거다"** — 가 부록에서도 그대로 반복된다.

### 적응형 크기 조정과 테뉴어링

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:+UseAdaptiveSizePolicy` | JVM이 GC 목표를 맞추려고 **힙 크기들을 스스로 조정** | **힙 크기를 정밀하게 튜닝했다면 끈다** |
| `-XX:+PrintAdaptiveSizePolicy` | **세대가 어떻게 재조정되는지**를 GC 로그에 추가 | JVM 동작을 이해하려 할 때. **G1에서는 이 출력으로 풀 GC가 거대 객체 할당 때문인지 확인** |
| `-XX:+PrintTenuringDistribution` | GC 로그에 **테뉴어링 정보** 추가 | 테뉴어링 옵션을 **조정해야 하는지, 어떻게 조정할지** 판단할 때 |
| `-XX:InitialSurvivorRatio=N` | 영 영역 중 **생존자 공간 몫** | **단명 객체가 올드로 너무 자주 승격되면 올린다** |
| `-XX:MinSurvivorRatio=N` | 적응형으로 잡히는 생존자 공간 몫 | **낮추면 생존자 공간 최대 크기가 줄어든다**(반대도 성립) |
| `-XX:TargetSurvivorRatio=N` | JVM이 생존자 공간에 **남겨두려는 여유 공간** | **올리면 생존자 공간이 작아진다**(반대도 성립) |
| `-XX:InitialTenuringThreshold=N` | 객체를 생존자 공간에 유지하려는 **초기 GC 사이클 수** | 객체를 더 오래 붙잡아두려면 올린다. **다만 JVM이 이 값을 다시 튜닝한다는 걸 알고 있어야 한다** |
| `-XX:MaxTenuringThreshold=N` | 위의 **최대치** | 올리면 더 오래 붙잡는다. **JVM은 초기값과 이 값 사이에서 실제 임계값을 조정한다** |

> **`MinSurvivorRatio` 와 `TargetSurvivorRatio` 는 방향이 반대다.** 전자는 내리면 작아지고,
> 후자는 올리면 작아진다. **이름만 보고 만지면 반대로 튜닝하게 된다** —
> 부록이 "vice versa"를 두 항목 모두에 붙여둔 이유다.

## 표 A-4. 처리량 수집기(throughput collector) 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:MaxGCPauseMillis=N` | 멈춤이 얼마나 길어야 하는지 **힌트**를 준다. 힙이 그 목표를 맞추려 **동적으로 크기 조정**된다 | **처리량 수집기 튜닝의 첫 단계.** 기본 계산 결과가 목표를 못 맞출 때 |
| `-XX:GCTimeRatio=N` | GC에 **얼마의 시간을 쓸 용의가 있는지** 힌트. 힙이 동적으로 조정된다 | 위와 같다 |
| `-XX:-AggressiveHeap` | 큰 메모리 머신에서 **단일 JVM에 큰 힙**을 쓰는 상황에 "최적화된" 플래그 묶음을 켠다 | **이 플래그는 안 쓰는 게 낫다. 대신 필요한 플래그를 개별로 지정하라** |

> **`AggressiveHeap` 의 "언제 쓰는가" 칸이 "쓰지 마라"인 게 이 부록에서 가장 솔직한 항목이다.**
> 표 A-9의 `AggressiveOpts` 도 비슷하게 **"테스트해 보되, JVM 버전이 바뀌면 같게 동작하지
> 않을 수 있음을 알고 있으라"** 로 적혀 있다. **"켜면 빨라지는 마법 플래그"는 없다**는 것이
> 이 책의 일관된 입장이다.

## 표 A-5. CMS 수집기 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:CMSInitiatingOccupancyFraction=N` | CMS가 **올드 영역 백그라운드 스캔을 언제 시작할지** 결정 | **CMS가 동시 모드 실패(concurrent mode failure)를 겪을 때 낮춘다** |
| `-XX:+UseCMSInitiatingOccupancyOnly` | `CMSInitiatingOccupancyFraction` **만으로** 스캔 시작 시점을 결정 | `CMSInitiatingOccupancyFraction` 을 지정했다면 **항상 같이** |
| `-XX:ConcGCThreads=N` | CMS 백그라운드 스캔 스레드 수 | **CPU 여유가 많고 CMS가 동시 모드 실패를 겪을 때** |
| `-XX:+CMSPermGenSweepingEnabled` | CMS가 **permgen도 청소**하게 한다 | **클래스 언로딩을 하는 애플리케이션 서버에서 CMS를 쓸 때** |
| `-XX:CMSInitiatingPermOccupancyFraction=N` | CMS가 permgen을 **언제 스캔할지** 결정 | permgen 청소를 켰는데도 **permgen이 덜 비워져 풀 GC가 날 때** |
| `-XX:+CMSClassUnloadingEnabled` | permgen 스캔 후 **클래스를 언로드**하게 한다 | permgen 청소를 켰다면 **항상 같이** |
| `-XX:+CMSIncrementalMode` | CMS를 **증분 모드**로 | **CPU가 부족한데 CMS를 돌려야 할 때** |
| `-XX:CMSIncrementalModeSafetyFactor=N` | 증분 CMS 백그라운드 스레드의 **실행 빈도**에 영향 | 증분 모드에서 **동시 모드 실패를 겪으면 올린다** |
| `-XX:CMSIncrementalDutyCycleMin=N` | 위와 같음 | 위와 같다. **다만 `CMSIncrementalMode` 만 켜는 쪽이 낫다** |
| `-XX:CMSIncrementalDutyCycleMax=N` | 위와 같음 | 위와 같다 |
| `-XX:+CMSIncrementalDutyCycle` | 위와 같음 | `CMSIncrementalDutyCycle` 계열을 쓸 때 |

> **CMS 플래그의 절반이 "동시 모드 실패"라는 한 증상을 가리킨다.** 6장에서 본 대로,
> **CMS 튜닝은 대체로 "백그라운드 수집을 더 일찍, 더 많은 스레드로 시작시키는" 한 방향이다.**
> 증분 모드 관련 네 개는 **"개별 플래그보다 `CMSIncrementalMode` 하나만 켜는 게 낫다"** 고
> 부록이 직접 말한다.

## 표 A-6. G1 수집기 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:MaxGCPauseMillis=N` | 멈춤 목표 **힌트**. G1 알고리즘이 그 목표를 맞추려 조정된다 | **G1 튜닝의 첫 단계.** **풀 GC를 막으려면 이 값을 올려 본다** |
| `-XX:ConcGCThreads=N` | G1 백그라운드 스캔 스레드 수 | **CPU 여유가 많고 G1이 동시 모드 실패를 겪을 때** |
| `-XX:InitiatingHeapOccupancyPercent=N` | G1 백그라운드 스캔 **시작 지점** | **동시 모드 실패를 겪으면 낮춘다** |
| `-XX:G1MixedGCCountTarget=N` | G1이 가비지 올드 리전을 비우는 데 쓰는 **혼합 GC 횟수** | **동시 모드 실패면 낮추고**, **혼합 GC 사이클이 너무 오래 걸리면 올린다** |
| `-XX:G1HeapRegionSize=N` | **G1 리전 크기** | **아주 큰 힙**이거나, 애플리케이션이 **아주아주 큰 객체를 할당할 때** 올린다 |

> **`MaxGCPauseMillis` 는 처리량 수집기와 G1 양쪽 표에 모두 있지만 방향이 다르다.**
> 처리량 수집기에서는 "힙이 동적으로 조정된다"이고, G1에서는 **"올려서 풀 GC를 막는다"** 다.
> **G1에서 멈춤 목표를 너무 공격적으로 잡으면 오히려 풀 GC로 무너진다**는 6장의 결론이
> 부록에도 그대로 들어와 있다.
>
> **`G1HeapRegionSize` 의 "아주아주 큰 객체" 는 거대 객체(humongous object) 문제다.**
> 리전의 절반을 넘는 객체는 올드 영역에 곧바로 잡히고, 이것이 풀 GC를 유발한다.
> 그래서 표 A-3의 `PrintAdaptiveSizePolicy` 설명에 **"G1을 쓸 때는 이 출력으로 풀 GC가
> 거대 객체 할당 때문인지 확인하라"** 가 붙어 있다. **두 표가 한 문제를 가리킨다.**

## 표 A-7. 메모리 관리 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 발생 시 **힙 덤프 생성** | 힙/permgen 때문에 OOM이 나는 애플리케이션에서 **메모리 누수 분석을 위해 켠다** |
| `-XX:HeapDumpPath=<path>` | 자동 힙 덤프 **파일명 지정** | 기본 `java_pid<pid>.hprof` 말고 다른 경로를 쓰고 싶을 때 |
| `-XX:SoftRefLRUPolicyMSPerMB=N` | **소프트 레퍼런스가 사용된 뒤 얼마나 오래 살아남는지** | **소프트 레퍼런스를 더 빨리 정리하려면 낮춘다.** 특히 메모리가 부족한 상황에서 |
| `-XX:MaxDirectMemorySize=N` | `ByteBuffer.allocateDirect()` 로 할당 가능한 **네이티브 메모리 양** | 다이렉트 메모리 할당을 **제한하고 싶을 때**. **64 MB 넘게 쓰려고 이 플래그를 설정할 필요는 이제 없다** |
| `-XX:+UseLargePages` | OS의 **라지 페이지**에서 페이지를 할당 | **OS가 지원하면 대체로 성능이 좋아진다** |
| `-XX:LargePageSizeInBytes=N` | 주어진 크기의 라지 페이지 할당 **(솔라리스 전용)** | 큰 솔라리스 시스템에서 **256 MB 정도로 올리면 최선** |
| `-XX:StringTableSize=N` | **인터닝된 문자열 해시테이블 크기** | 애플리케이션이 **문자열 인터닝을 많이 할 때 올린다** |
| `-XX:+UseCompressedOops` | 객체 참조에 **35비트 포인터를 흉내낸다** | **32 GB 미만 힙의 기본값이고, 끌 이유가 전혀 없다** |
| `-XX:+PrintTLAB` | GC 로그에 **TLAB 요약 정보** | **JFR을 못 쓰는 JVM에서** TLAB 할당이 효율적인지 확인할 때 |
| `-XX:TLABSize=N` | **TLAB 크기** | 애플리케이션이 **TLAB 밖에서 할당을 많이 할 때 올린다** |
| `-XX:-ResizeTLAB` | TLAB **크기 재조정을 끈다** | `TLABSize` 를 지정했다면 **반드시 같이 끈다** |

> **`UseCompressedOops` 설명이 이 표에서 가장 단호하다 — "끄는 데 이점이 있는 경우는 없다".**
> 7·8장에서 본 **32 GB 경계**가 여기서 한 줄로 요약된다. 힙을 33 GB로 잡으면
> 압축 oop이 꺼지면서 **31 GB로 잡았을 때보다 실질 용량이 줄어든다.**
>
> **`TLABSize` 와 `-ResizeTLAB` 은 짝이다.** 크기를 지정해 놓고 재조정을 켜두면
> JVM이 도로 바꿔 놓는다. 부록이 "반드시"라고 쓴 몇 안 되는 항목이다.

## 표 A-8. 스레드 처리 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-Xss<N>` | 스레드의 **네이티브 스택 크기** | **특히 32비트 JVM에서**, 줄이면 JVM의 다른 부분에 쓸 메모리가 늘어난다 |
| `-XX:-BiasedLocking` | JVM의 **편향 락 알고리즘을 끈다** | **스레드 풀 기반 애플리케이션의 성능에 도움이 되는 경우가 많다** |

> **표에서 유일하게 "끄는 것"이 기본 권고인 항목이 `BiasedLocking` 이다.**
> 9장에서 본 이유 — **편향 락은 "같은 스레드가 같은 락을 반복해서 잡는다"를 전제하는데,
> 스레드 풀은 정확히 그 전제를 깬다.** 작업이 매번 다른 스레드에 배정되므로
> 편향을 취소(revoke)하는 비용만 계속 든다.

## 표 A-9. 기타 JVM 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:+AlwaysLockClassLoader` | Java 7의 **병렬 클래스로딩을 Java 6 방식(비병렬)으로 되돌린다** | **큰 시스템에서 단일 스레드로만 클래스를 로드한다면** 기동 성능이 약간 나아질 수 있다 |
| `-XX:-StackTraceInThrowable` | 예외가 던져질 때 **스택 트레이스 수집을 하지 않는다** | **스택이 아주 깊고 예외가 빈번히 던져지는 시스템**에서, **예외를 덜 던지도록 코드를 고치는 게 불가능할 때** |
| `-XX:-RestrictContended` | **JDK 밖의 코드**가 `@Contended` 를 쓸 수 있게 한다 | 애플리케이션 코드가 **거짓 공유를 막으려고 `@Contended` 로 변수를 패딩할 때** |
| `-XX:-EnableContended` | **JDK 코드**가 `@Contended` 를 쓰는 것을 막는다 | **켜둔 채로 두는 게 낫다.** 끄면 일부 JDK 클래스의 공간을 조금 아낄 수 있다 |
| `-XX:+AggressiveOpts` | 몇몇 최적화를 켠다. **향후 릴리스에서 기본값이 될 가능성이 높은 것들** | **도움이 되는지 테스트해 볼 수는 있지만, JVM 버전이 바뀌면 같게 동작하지 않을 수 있음을 알고 있어야 한다** |

> **`-XX:-StackTraceInThrowable` 의 "언제 쓰는가" 문장이 이 부록의 태도를 압축한다.**
> **"예외를 덜 던지도록 코드를 고치는 게 불가능할 때"** — 즉 **플래그는 코드 수정의 대체재가
> 아니라 마지막 수단**이다. 12장에서 본 수치(깊은 스택에서 381 ms → 10,673 ms)가
> 그 배경이다.

## 표 A-10. Java Flight Recorder 플래그

| 플래그 | 무엇을 하는가 | 언제 쓰는가 |
| --- | --- | --- |
| `-XX:+FlightRecorder` | **JFR을 켠다** | **항상 권장.** 실제 기록이 일어나지 않는 한 오버헤드가 거의 없다(기록 중에는 사용 기능에 따라 달라지지만 그래도 비교적 작다) |
| `-XX:+FlightRecorderOptions` | **커맨드라인에서 기본 기록 옵션**을 설정 | JVM의 기본 기록을 어떻게 뜰지 제어할 때 |
| `-XX:+UnlockCommercialFeatures` | JVM이 **상용(비오픈소스) 기능**을 쓸 수 있게 한다 | **적절한 라이선스가 있다면, JFR을 켜기 위해 반드시 필요하다** |

> **이 표는 이 책이 쓰인 시점(JDK 8 시절)의 사정을 그대로 담고 있다.**
> `UnlockCommercialFeatures` 는 **오라클 JDK의 상용 기능 잠금 해제**용이었다.
> **JDK 11 이후 JFR이 오픈소스화되면서 이 플래그는 사라졌고**, JFR은
> `-XX:StartFlightRecording=...` 하나로 켤 수 있다. **부록에서 시대가 가장 많이
> 지난 항목이 여기다.**

## 이 부록을 우리 랩에 비춰 보면

| 부록의 플래그 | 우리 검증 케이스 |
| --- | --- |
| `-Xms` / `-Xmx` / `NewRatio` / GC 알고리즘 선택 | **`JVM-01`**(컨테이너 인식 힙), **`JVM-03`**(GC 선택) |
| `-XX:+PrintGCDetails` / `-Xloggc` — **"항상 켜라"** | **`OBS-01`**, **`OBS-02`** — 우리도 같은 이유로 로그를 증거로 남긴다 |
| `-XX:+HeapDumpOnOutOfMemoryError` | **`JVM-04`**(OOM 재현) |
| `-XX:+UseCompressedOops` **32 GB 경계** | 검증 케이스 **없음** — 32 GB 힙을 띄울 수 없어 **못 하는 것**이다 |
| `-XX:-BiasedLocking` (스레드 풀에서) | **`CON-01`**, **`CON-04`** — 스레드 풀 동작은 검증하지만 **편향 락 자체는 측정하지 않았다** |
| `-XX:-StackTraceInThrowable` (예외 비용) | 검증 케이스 **없음** — 12장 요약에 남긴 그대로 |
| `-XX:MaxDirectMemorySize` | **`JVM-05`**(네이티브 메모리) 와 이어진다 |
| `AggressiveHeap` / `AggressiveOpts` — **"쓰지 마라"** | 검증 케이스 없음. 다만 **"마법 플래그는 없다"** 는 이 랩의 전제와 같다 |

> **부록 A를 읽고 나서 우리 랩에 대해 정직하게 말할 수 있는 것**:
> 우리는 **힙/GC/OOM 쪽 플래그는 실행으로 확인했지만**, **편향 락, 압축 oop 경계, 예외 비용,
> TLAB, 라지 페이지는 한 번도 실행해 보지 않았다.** 이 중 **TLAB과 예외 비용은 컨테이너에서도
> 충분히 측정 가능하므로 "못 하는 것"이 아니라 "안 한 것"이다.**

## 표 전체를 관통하는 세 가지

1. **"항상 켜라"는 것은 손에 꼽는다.** `-Xloggc`, `-XX:+PrintGCDetails`,
   `-XX:+PrintGCTimeStamps`, `-XX:+FlightRecorder`, `-XX:+UseCompressedOops`(기본값),
   `-XX:+HeapDumpOnOutOfMemoryError`. **모두 "관측"이거나 "기본값"이지, 성능 플래그가 아니다.**
2. **성능 플래그는 전부 "이 증상을 겪고 있을 때"로 조건이 붙어 있다.**
   코드 캐시 경고, 동시 모드 실패, 승격 실패, 잦은 승격, 인터닝 과다 — **증상 없이 만지는
   플래그는 이 부록에 없다.**
3. **짝으로만 의미가 있는 플래그들이 있다.** `UseParallelGC`+`UseParallelOldGC`,
   `UseParNewGC`+`UseConcMarkSweepGC`, `CMSInitiatingOccupancyFraction`+`UseCMSInitiatingOccupancyOnly`,
   `CMSPermGenSweepingEnabled`+`CMSClassUnloadingEnabled`, `TLABSize`+`-ResizeTLAB`.
   **한쪽만 켜면 기대한 대로 동작하지 않는다.**
