# 8장. 네이티브 메모리 모범 사례 (Native Memory Best Practices)

> 힙은 자바 애플리케이션의 가장 큰 메모리 소비자이지만, **JVM은 상당한 양의 네이티브 메모리도
> 할당하고 사용한다.** 힙 설정이 OS의 네이티브 메모리와 어떻게 상호작용하는가는 전체 성능의
> 또 다른 중요한 요인이다.

---

## 1부. 풋프린트 (Footprint)

**네이티브 메모리 + 힙 메모리 = 애플리케이션의 총 풋프린트.**
네이티브 메모리는 JVM 내부 연산에 쓰이고, 애플리케이션에서도 할당할 수 있다
(**JNI의 `malloc()` 호출이나 NIO**).

> **OS 관점에서는 이 총 풋프린트가 성능의 열쇠다.** 전체를 담을 물리 메모리가 없으면 성능이
> 나빠지기 **시작할 수 있다.**
>
> **여기서 "수 있다"가 핵심 단어다.**
> - **네이티브 메모리의 일부는 시작할 때만 쓰인다**(예: 클래스패스의 JAR 로드에 연결된 메모리).
>   **그게 스왑아웃되어도 눈치채지 못할 것이다**
> - 한 자바 프로세스의 네이티브 메모리 일부는 **다른 자바 프로세스와 공유된다.** 더 작은 일부는
>   다른 종류의 프로세스와도 공유된다
>
> **그래도 대체로, 최적 성능을 위해서는 모든 자바 프로세스의 총 풋프린트가 머신의 물리 메모리를
> 넘지 않게 해야 한다**(다른 애플리케이션을 위한 여유도 남겨야 한다).

### 예약(reserved) vs 커밋(committed) — 이 장의 핵심 구분

`-Xms512m -Xmx2048m` 인 힙을 생각해 보자.

- **예약(reserved / virtual size)**: JVM이 OS에게 **"힙에 최대 2GB가 필요할 수 있다"** 고 알린 양.
  **OS는 JVM이 힙을 키울 때 그 메모리가 있을 것이라고 약속한다**
- **커밋(committed / allocated)**: **실제로 할당되어 실제로 쓰이는 512MB.**
  **힙 크기가 변하면 커밋 양도 변한다**

**측정 도구**
- Unix: `top`, `ps` → **RSS(resident set size)** 가 커밋 메모리의 좋은 추정치
- Windows: `perfmon`, `VMMap` → **워킹 셋(working set)**, 작업 관리자에 표시

> **⚠️ RSS는 두 가지 면에서 부정확하다.**
> ① **OS 레벨에서 JVM과 다른 프로세스가 공유하는 몇 페이지**(공유 라이브러리의 텍스트 부분)가
> **각 프로세스의 RSS에 모두 계산된다**
> ② 프로세스가 **어느 순간 실제로 페이징한 것보다 많이 커밋했을 수 있다**
>
> 그래도 **RSS를 추적하는 것은 총 메모리 사용을 모니터링하는 좋은 1차 방법이다.**
> **최신 Linux 커널의 PSS는 다른 프로그램과 공유된 데이터를 제거한 RSS의 개선판이다.**

> **과다 예약이 문제인가?**
> **성능만 보면 커밋 메모리만 중요하다 — 메모리를 너무 많이 예약해서 생기는 성능 문제는 없다.**
>
> **하지만 예약을 신경 써야 할 때가 있다. 특히 32비트 JVM에서다.**
> 32비트 앱의 최대 프로세스 크기가 4GB(또는 그 이하)이므로 과다 예약이 문제가 된다.
> **힙에 3.5GB를 예약한 JVM은 스택·코드 캐시 등을 위한 네이티브 메모리가 0.5GB밖에 안 남는다.**
> **힙이 실제로 1GB만 커밋해도 상관없다** — 3.5GB 예약 때문에 다른 연산용 메모리가 0.5GB로
> 제한된다.
>
> **64비트 JVM은 프로세스 크기로 제한되지 않지만 머신의 총 가상 메모리로 제한된다.**
> 물리 4GB, 가상 10GB인 작은 서버에서 최대 힙 6GB로 JVM을 시작하면 **6GB(+ 비힙)를 예약**한다.
> **힙이 실제로 얼마나 커지든, 두 번째 JVM은 4GB 미만만 예약할 수 있다.**
>
> **다른 조건이 같다면 JVM 구조를 넉넉히 잡고 JVM이 최적으로 쓰게 하는 게 편하다.
> 하지만 항상 가능한 건 아니다.**

**이 구분은 JVM이 할당하는 거의 모든 주요 메모리에 적용된다** — 코드 캐시도 초기값에서
최댓값으로 자라고, permgen/메타스페이스도 초기(커밋)에서 최대(예약) 사이에서 자란다.

> **⚠️ 한 가지 예외는 스레드 스택이다.** JVM이 스레드를 만들 때마다 OS가 그 스택용 네이티브
> 메모리를 할당한다(스레드가 끝날 때까지 커밋된 상태). **스레드 스택은 생성 시점에 전부
> 할당된다.**

### 풋프린트 최소화하기

| 대상 | 내용 |
|---|---|
| **힙** | 가장 큰 덩어리지만 **놀랍게도 총 풋프린트의 50~60%밖에 안 될 수 있다** |
| **스레드 스택** | **꽤 크다. 특히 64비트 JVM에서.** → 9장 |
| **코드 캐시** | 컴파일된 코드를 담는 네이티브 메모리 → 4장 (**공간 제한으로 전부 컴파일 못 하면 성능이 나빠진다**) |
| **다이렉트 바이트 버퍼** | 아래 절 |

### 네이티브 NIO 버퍼

`allocateDirect()` 로 만든 NIO 바이트 버퍼는 네이티브 메모리를 할당한다.

> **성능 관점에서 아주 중요하다 — 네이티브 코드와 자바 코드가 복사 없이 데이터를 공유하게 해 주기
> 때문이다.** 가장 흔한 예가 파일시스템·소켓 연산 버퍼다. **네이티브 NIO 버퍼에 쓰고 채널로
> 보내면 JVM과 C 라이브러리 사이에 데이터 복사가 없다. 힙 바이트 버퍼를 쓰면 JVM이 내용을
> 복사해야 한다.**

**⚠️ `allocateDirect()` 호출은 꽤 비싸므로 최대한 재사용해야 한다.**

**세 가지 재사용 전략**
1. **이상적: 스레드가 독립적이고 각자 다이렉트 바이트 버퍼를 스레드 로컬로 유지**
   ⚠️ **크기가 다양한 버퍼가 필요한 스레드가 많으면 네이티브 메모리를 너무 쓸 수 있다** —
   결국 모든 스레드가 최대 크기 버퍼를 갖게 되니까
2. **다이렉트 바이트 버퍼의 객체 풀**
3. **슬라이싱** — 아주 큰 버퍼 하나를 할당하고 `slice()` 로 부분을 떼어 쓴다
   ⚠️ **슬라이스 크기가 일정하지 않으면 다루기 어려워진다** — 원래 버퍼가 **힙이 단편화되는
   것과 같은 방식으로 단편화**된다. **힙과 달리 바이트 버퍼의 슬라이스는 압축할 수 없으므로,
   이 방식은 슬라이스 크기가 모두 균일할 때만 잘 작동한다**

```
-XX:MaxDirectMemorySize=N
```
> **Java 7부터 기본값은 0 = 무제한**(주소 공간 크기와 OS 프로세스 제한에 종속).
> 애플리케이션의 다이렉트 버퍼 사용을 제한하거나 **이전 릴리스(제한 64MB)와의 호환성**을 위해 쓴다.

## 2부. Native Memory Tracking (NMT) — Java 8부터

```
-XX:NativeMemoryTracking=off|summary|detail   # 기본 off
-XX:+PrintNMTStatistics                        # 종료 시 출력. 기본 false

jcmd <pid> VM.native_memory summary
```

**저자의 실제 출력 (초기 512MB, 최대 4GB 힙)**
```
Native Memory Tracking:
 Total: reserved=4787210KB, committed=1857677KB
- Java Heap        (reserved=4296704KB, committed=1470428KB)
- Class            (reserved=65817KB,   committed=60065KB)   (classes #19378)
- Thread           (reserved=84455KB,   committed=84455KB)   (thread #77)
                   (stack: reserved=79156KB, committed=79156KB)
- Code             (reserved=102581KB,  committed=15221KB)
- GC               (reserved=183268KB,  committed=173156KB)
- Compiler         (reserved=162KB,     committed=162KB)
- Symbol           (reserved=12093KB,   committed=12093KB)
- Memory Tracking  (reserved=22466KB,   committed=22466KB)
```

**해석**
- **예약 4.7GB인데 실제로는 1.8GB만 쓴다.** **꽤 전형적이다. 그리고 OS 도구가 보여 주는
  프로세스의 가상 크기에 특별히 주목하지 말아야 할 이유이기도 하다** — 그건 예약만 반영한다
- **Class**: 클래스 메타데이터용 네이티브 메모리. 19,378개 클래스를 담는 데 실제로 쓴 것보다
  더 많이 예약했다
- **Thread**: **스레드 77개, 스택 각 약 1MB**
- **Code**: JIT 코드 캐시. **19,378개 클래스는 그렇게 많지 않아서 코드 캐시 일부만 커밋됐다**
- **GC**: **GC 알고리즘이 처리에 쓰는 힙 밖 영역**
- **Compiler**: 컴파일러의 연산용(결과 코드는 코드 캐시에 들어간다)
- **Symbol**: **인터닝된 문자열 참조와 심볼 테이블 참조**
- **Memory Tracking**: **NMT 자신이 쓰는 공간**

> **`detail` 모드**는 전체 메모리 공간의 맵을 준다:
> ```
> [0x00000006c0000000 - 0x00000007c0000000] reserved 4194304KB for Java Heap
>         from [ReservedSpace::initialize(...)+0xc2]
>         [0x00000006c0000000 - 0x00000006fb100000] committed 967680KB
>             from [PSVirtualSpace::expand_by(unsigned long)+0x53]
> ```
> **JVM 엔지니어라면 정말 흥미로운 단서지만, 나머지 우리에게는 summary로 충분하다.**

**NMT가 주는 두 가지 핵심 정보**

**① 총 커밋 크기** — 프로세스가 실제로 소비할 물리 메모리 양. **RSS(워킹 셋)에 가깝지만,
OS 측정치는 커밋됐지만 프로세스 밖으로 페이징된 메모리를 포함하지 않는다.**
> **⚠️ 실제로 프로세스의 RSS가 커밋 메모리보다 작다면, 그것은 OS가 JVM 전체를 물리 메모리에
> 넣는 데 어려움을 겪고 있다는 신호인 경우가 많다.**

**② 개별 커밋 크기** — 힙·코드 캐시·메타스페이스의 **최댓값을 튜닝할 때, JVM이 실제로 그 메모리를
얼마나 쓰는지 아는 것이 도움된다.** 과다 할당은 보통 무해한 메모리 예약으로 끝나지만,
**예약 메모리가 중요한 상황에서는 NMT가 어디를 줄일 수 있는지 추적하게 해 준다.**

### 시간에 따른 추적

```bash
jcmd <pid> VM.native_memory baseline        # 현재 할당에 표시
# ... 시간이 지난 뒤 ...
jcmd <pid> VM.native_memory summary.diff
```
```
Total: reserved=5896078KB -3655KB, committed=2358357KB -448047KB
- Java Heap (reserved=4194304KB, committed=1920512KB -444927KB)
```
**커밋 크기가 베이스라인보다 448MB 줄었고, 그중 힙이 444MB.**
(나머지 4MB가 어디서 줄었는지는 출력의 나머지를 보면 된다.)
> **JVM의 풋프린트를 시간에 따라 조사하는 아주 유용한 기법이다.**

## 3부. OS를 위한 JVM 튜닝

## 라지 페이지 (Large Pages)

**페이지**는 OS가 물리 메모리를 관리하는 단위이자 **할당의 최소 단위**다. 1바이트를 할당해도
**OS는 페이지 하나 전체를 할당해야 한다.**

**페이지 매핑이 두 방식으로 처리된다**
- **전역 페이지 테이블** — OS가 스캔해서 특정 매핑을 찾는다
- **TLB (translation lookaside buffer)** — **가장 자주 쓰이는 매핑**을 담는다.
  **빠른 캐시에 있어서 TLB를 통한 페이지 접근이 페이지 테이블을 통한 것보다 훨씬 빠르다**

> **머신의 TLB 엔트리 수는 제한적이므로 TLB 히트율을 최대화하는 것이 중요해진다**(LRU 캐시처럼
> 동작한다). **각 엔트리가 페이지 하나를 나타내므로, 애플리케이션이 쓰는 페이지 크기를 늘리는
> 것이 유리한 경우가 많다.** 페이지가 더 많은 메모리를 나타내면 **프로그램 전체를 아우르는 데
> 필요한 TLB 엔트리가 줄고, 필요할 때 TLB에서 페이지를 찾을 가능성이 높아진다.**
>
> **일반적으로 모든 프로그램에 해당되고, 따라서 자바 앱 서버나 중간 크기 이상의 힙을 가진
> 자바 프로그램에도 해당된다.**

```
-XX:+UseLargePages
```

**OS별 기본값과 요구사항**

| OS | 상태 |
|---|---|
| **Windows** | **OS에서 활성화해야 한다** — 개인 사용자에게 "메모리에 페이지 잠금" 권한을 줘야 하고, **서버 버전 Windows에서만 가능**하다. 그렇게 해도 **플래그를 명시적으로 켜지 않으면 JVM은 일반 페이지를 쓴다** |
| **Linux** | **기본 비활성.** OS도 라지 페이지를 지원하도록 설정해야 한다 |
| **Solaris** | **OS 설정 불필요, 기본 활성** |

> **⚠️ 라지 페이지를 지원하지 않는 시스템에서 플래그를 켜면 경고 없이 일반 페이지를 쓴다.**
> **지원하지만 사용 가능한 라지 페이지가 없으면**(이미 다 쓰였거나 OS 설정이 잘못됐거나)
> **JVM이 경고를 출력한다.**

### Linux huge pages 설정 절차

```bash
# 1. 커널이 지원하는 huge page 크기 확인 (가장 흔한 값은 2MB)
grep Hugepagesize /proc/meminfo
#   Hugepagesize: 2048 kB

# 2. 필요한 개수 계산: 4GB 힙 + 2MB 페이지 = 2,048개
#    ★ 비힙 용도를 위해 10% 과대 추정 → 2,200개
#    ★ 개수는 Linux 커널에 전역으로 정의되므로 돌릴 모든 JVM에 대해 반복해야 한다

# 3. 즉시 적용
echo 2200 > /proc/sys/vm/nr_hugepages

# 4. /etc/sysctl.conf 에 저장 (재부팅 후 유지)
#    sys.nr_hugepages=2200

# 5. /etc/security/limits.conf 에 memlock 항목 추가
#    appuser soft memlock 4613734400
#    appuser hard memlock 4613734400
#    ★ limits.conf 를 수정하면 사용자가 다시 로그인해야 적용된다

# 검증
java -Xms4G -Xmx4G -XX:+UseLargePages -version
```
설정이 잘못됐으면:
```
Java HotSpot(TM) 64-Bit Server VM warning: Failed to reserve shared memory (errno = 22).
```

### Linux transparent huge pages (커널 2.6.32+)

**위 설정이 필요 없어진다.** 다만 **자바를 위해서는 여전히 활성화해야 한다.**

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
#   always [madvise] never          ← 기본값은 madvise
echo always > /sys/kernel/mm/transparent_hugepage/enabled
#   [always] madvise never
```
> **기본값 `madvise` 는 huge page를 쓰겠다고 커널에 명시적으로 알리는 프로그램에만 적용된다.
> JVM은 그 통보를 하지 않으므로 `always` 로 설정해야 한다.**
> **⚠️ 이 설정은 JVM뿐 아니라 시스템의 다른 모든 프로그램에도 영향을 준다.**

> **⚠️ transparent huge pages가 활성이면 `UseLargePages` 플래그를 지정하지 마라.**
> 명시적으로 설정하면 **JVM은 전통적 huge page가 설정돼 있으면 그것으로, 아니면 표준 페이지로
> 돌아간다.** **기본값으로 두면 transparent huge pages가 쓰인다**(설정돼 있다면).

### Windows large pages

MMC → Local Computer Policy → Computer Configuration → Windows Settings → Security Settings →
Local Policies → User Rights Assignment → **"Lock pages in memory"** 에 사용자/그룹 추가 → **재부팅.**

> **⚠️ 라지 페이지를 지원하지 않는 Windows("home" 버전 등)에서는 명령이 에러를 출력하지 않는다.**
> JVM이 OS가 지원하지 않는다는 것을 알면 **명령행 설정과 무관하게 `UseLargePages` 를 false로
> 설정한다.**

### 라지 페이지 크기

```
-XX:LargePageSizeInBytes=N   # 기본 0 = 프로세서별 라지 페이지 크기를 JVM이 고른다
```

> **엄밀히 말해 가능한 페이지 크기를 정하는 것은 프로세서다.** 현재 Intel과 SPARC은 4KB, 8KB,
> 2MB, 256MB 등 여러 크기를 지원한다. **하지만 실제로 어떤 크기를 할당할 수 있는지는 OS가 정한다.**
> - **Solaris**: 모든 프로세서 페이지 크기를 지원하고 **JVM이 어느 크기든 할당할 수 있다**
> - **Linux**: 커널 부팅 시 어떤 라지 페이지 크기를 쓸지 지정할 수 있고, **그것이 애플리케이션이
>   실제로 할당할 수 있는 유일한 크기다**
> - **Windows**: 라지 페이지 크기가 **2MB로 고정**

> **⚠️ 이 플래그는 모든 플랫폼에서 설정할 수 있고, 지정한 크기가 쓰였는지 아닌지 아무 표시가 없다.**
> Linux에서 아주 큰 힙을 할당하며 TLB 히트를 위해 `-XX:LargePageSizeInBytes=256M` 을 줘야겠다고
> 생각할 수 있다. **그렇게 해도 JVM은 불평하지 않지만 여전히 2MB 페이지만 할당한다.**
> 실제로 **`-XX:LargePageSizeInBytes=11111` 처럼 말이 안 되는 크기도 지정할 수 있다.**
> 그 크기를 쓸 수 없으므로 **JVM은 그냥 플랫폼 기본 라지 페이지 크기를 쓴다.**
>
> **그러므로 — 적어도 지금은 — 이 플래그는 Solaris에서만 정말 유용하다.**
> Solaris에서 기본값(SPARC 4MB)보다 큰 페이지를 쓰려면 다른 크기를 고른다.
> 가용 크기는 `pagesize -a` 로 확인한다.

> **라지 페이지를 쓰면 대개 애플리케이션이 측정 가능하게 빨라진다.
> 대부분의 OS에서 라지 페이지 지원을 명시적으로 활성화해야 한다.**

## 압축 oops (Compressed oops)

4장에서 32비트 JVM이 같은 작업에서 64비트보다 **5~20% 빠르다**고 했다(힙이 4GB 미만에 들어간다는
전제, 실제로는 3.5GB 미만, 일부 Windows에서는 3GB).

**성능 격차의 주된 이유는 64비트 객체 참조다** — **힙에서 32비트 참조(4바이트)의 두 배(8바이트)를
차지하므로 다른 데이터를 위한 공간이 줄어 GC 사이클이 늘어난다.**

### 어떻게 동작하나 — 35비트 포인터라는 아이디어

**oop = ordinary object pointer.** JVM이 객체 참조로 쓰는 핸들.
- 32비트 oop → **4GB**만 참조 가능 (32비트 JVM이 4GB 힙으로 제한되는 이유)
- 64비트 oop → 테라바이트 참조 가능

> **중간 지대: 35비트 oop이 있다면? 32GB를 참조하면서 힙에서 64비트 참조보다 적은 공간을 쓴다.**
> **문제는 35비트 레지스터가 없다는 것이다.**
>
> **대신 JVM은 참조의 마지막 3비트가 모두 0이라고 가정할 수 있다.**
> 이제 모든 참조를 힙에서 32비트로 저장한다. **64비트 레지스터에 저장할 때는 왼쪽으로 3비트
> 시프트(끝에 0 세 개 추가), 레지스터에서 저장할 때는 오른쪽으로 3비트 시프트(끝의 0 버림).**
>
> **이는 JVM이 8로 나누어떨어지지 않는 주소의 객체에 접근할 수 없다는 뜻이다.** 첫 oop 0x1은
> 시프트하면 0x8, 다음 0x2는 0x10(16). **객체는 8바이트 경계에 위치해야 한다.**
>
> **그런데 JVM에서 객체는 이미 8바이트 경계에 정렬돼 있다**(32비트·64비트 모두). **대부분의
> 프로세서에 최적인 정렬이다. 그러므로 압축 oops를 써도 잃는 것이 없다.**
>
> 첫 객체가 위치 0에 있고 57바이트를 차지하면 다음 객체는 위치 64에 저장된다 —
> **할당할 수 없는 7바이트 낭비.** 그 메모리 트레이드오프는 **8바이트 정렬 덕에 객체 접근이
> 빨라지므로 가치가 있다**(압축 oops를 쓰든 안 쓰든 일어난다).
>
> **그리고 이것이 JVM이 64GB를 접근할 36비트 참조를 흉내 내지 않는 이유다.** 그러면 객체가
> **16바이트 경계에 정렬**돼야 하고, **압축 포인터로 아끼는 것보다 정렬된 객체 사이에 낭비되는
> 메모리가 더 커진다.**

```
-XX:+UseCompressedOops   # Java 7+에서 최대 힙이 32GB 미만이면 기본 활성
```

### ⚠️ 실무적 함의 두 가지

**① 4GB~32GB 힙에는 압축 oops를 쓴다.**

**② 31GB 힙 + 압축 oops가 33GB 힙보다 대개 빠르다.**
> **33GB 힙이 더 크지만, 그 힙에서 포인터가 쓰는 추가 공간 때문에 더 큰 힙이 더 잦은 GC
> 사이클을 수행하고 성능이 나빠진다.**
>
> **그러므로 32GB 미만 힙이나, 32GB보다 몇 GB는 더 큰 힙을 써라.**
> 압축되지 않은 참조가 쓰는 공간을 메우기 위해 추가 메모리를 넣고 나면 GC 사이클이 줄어든다.
> **얼마나 필요한지에 대한 확실한 규칙은 없지만, 평균적인 힙의 20%가 객체 참조에 쓰인다고 보면
> 최소 38GB를 계획하는 것이 좋은 출발점이다.**
