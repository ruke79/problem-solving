# 1부. 기본 웹 컨테이너 성능

## 출력을 줄여라 — 이 장에서 가장 중요한 원칙

### 공백 줄이기

- **서블릿 코드에서 `PrintWriter` 호출에 공백을 넣지 마라.** 네트워크 전송에 시간이 걸린다
  (코드 처리 시간도 걸리지만 **네트워크 시간이 더 중요하다**)
- **`println()` 보다 `print()` 를 써라**
- 무엇보다 **HTML 구조를 반영하는 탭이나 스페이스를 쓰지 마라**

> **저자의 솔직한 절충**: 웹 페이지 소스를 보는 사람이 구조를 못 보게 된다.
> **사내 QA나 성능 그룹에게도 마찬가지다 — 소스가 페이지 구조를 반영하면 디버깅이 확실히 쉽다.
> 하지만 결국 나는 응답 시간을 개선하기 위해 소스를 포맷팅 에디터에 넣는 쪽을 감수하겠다.**
>
> **대부분의 앱 서버가 JSP에서 공백을 자동으로 잘라낼 수 있다.** Tomcat(과 Tomcat 기반 오픈소스
> Java EE 서버)에는 **`trimSpaces` 지시어**가 있어 앞뒤 공백을 제거한다.
> **JSP는 (적어도 사람에게) 올바른 들여쓰기로 개발·유지하면서 네트워크 전송 페널티는 안 낸다.**

### CSS·JavaScript 리소스 합치기

**개발자에게는 파일을 나누는 게 유지보수에 좋지만, 서빙할 때는 작은 파일 여러 개보다 큰 파일
하나를 보내는 것이 훨씬 효율적이다.**
> **Java EE 표준이 없고 대부분의 앱 서버에 자동으로 하는 방법도 없다.** 도와주는 개발 도구는 여럿 있다.

### 출력 압축 — ⚠️ 유일하게 보편적 개선이 아닌 항목

> **브라우저 앞의 사용자 관점에서 웹 요청 실행의 가장 긴 시간은 종종 서버에서 HTML을 되보내는
> 시간이다.**
> **성능 테스트에서 자주 놓친다** — 클라이언트-서버 테스트가 **빠른 LAN에서** 일어나기 때문이다.
> 실제 사용자가 "빠른" 광대역에 있어도 **연구실 머신 간 LAN보다 자릿수가 느리다.**

원본 요청이 압축 지원을 표시할 때만 한다(**모든 현대 브라우저가 지원한다**).
**서버 CPU를 더 쓰지만 작은 데이터가 대개 네트워크를 더 빨리 지나 순개선**이 된다.

> **⚠️ 그런데 이 절의 다른 최적화와 달리 보편적 개선이 아니다.**
> **LAN에서 압축을 켜면 성능이 떨어질 수 있다.** 아주 작은 페이지를 보내는 애플리케이션도 그렇다
> (대부분의 앱 서버는 지정 크기보다 클 때만 압축하게 해 준다).

### 동적 JSP 컴파일 끄기

기본적으로 대부분의 Java EE 서버는 **JSP를 배포된 자리에서 편집하면 다음 방문 때 반영**한다.
**새 JSP를 개발할 때는 유용하지만 프로덕션에서는 서버를 느리게 한다** — **접근할 때마다 파일의
최종 수정 시각을 확인해야 하기 때문**이다.
> **개발 모드(development mode)라고 불리는 이 튜닝은 프로덕션과 성능 테스트에서 꺼야 한다.**

### 실측 — 이 장에서 가장 인상적인 표

**10년치 주식 히스토리, 압축·트림 없이 약 100KB HTML. 단일 사용자, 생각 시간 100ms.**

| 적용한 최적화 | LAN | 광대역 | 공용 WiFi |
|---|---|---|---|
| 없음 | 20 ms | 26 ms | **1003 ms** |
| 공백 제거 | 20 ms | 10 ms | **43 ms** |
| 출력 압축 | **30 ms** | **5 ms** | **17 ms** |

> **⚠️ LAN에서는 압축이 오히려 느리다(20 → 30ms). 그런데 공용 WiFi에서는 1003ms → 17ms 다.**
>
> **이것이 애플리케이션이 실제로 배포될 환경에서 테스트하는 것의 중요성을 부각한다.
> 연구실 테스트만으로 튜닝을 정했다면 성능의 80%를 테이블에 남겨 뒀을 것이다.**
> 하드웨어 기반 에뮬레이터로 연구실에서 이런 연결성을 시뮬레이션할 수 있다.

> **문자열을 미리 인코딩해야 하나?**
> 앱 서버는 문자 변환에 많은 시간을 쓴다 — **자바 `String`(UTF-16)에서 클라이언트가 기대하는
> 바이트로.** 많은 문자열이 항상 같다(웹 페이지의 HTML 문자열은 데이터에 따라 바뀌지 않는다).
>
> **답은 앱 서버와 애플리케이션에 달렸다.**
> 서블릿에서는 `PrintWriter.print()` 대신 `ServletOutputStream.write()` 로 미리 인코딩한 바이트
> 배열을 보낼 수 있다. **동적 데이터는 여전히 `print()` 를 거쳐야 올바르게 인코딩된다.**
>
> **⚠️ 그런데 앱 서버가 이 출력 인터페이스를 구현하고 버퍼링하는 방식에 중요한 차이가 있다.**
> **어떤 서버에서는 서블릿 출력 스트림과 print writer 호출을 섞으면 네트워크 버퍼가 자주
> 플러시된다. 잦은 버퍼 플러시는 성능상 아주 비싸다 — 데이터를 다시 인코딩하는 것보다 비싸다.**
> 게다가 **큰 블록 인코딩이 작은 블록 인코딩보다 그리 비싸지 않다 — 애초에 인코더 호출을
> 설정하는 것이 비싼 부분이다.** 그래서 **작은 동적 데이터에 대한 잦은 인코더 호출을 미리
> 인코딩된 배열 전송과 교차시키면 오히려 느려질 수 있다.**
> **확실히 사례별(your-mileage-may-vary) 상황이다.**

# 2부. HTTP 세션 상태

## 세션 상태 메모리

> **HTTP 세션 데이터는 대개 오래 산다. 그래서 세션 상태 데이터로 힙을 채우기가 아주 쉽다.**
> GC가 너무 자주 돌아야 하는 문제로 이어진다. **게다가 7장에서 봤듯 힙의 라이브 데이터가
> 많을수록 개별 GC가 오래 걸린다.**

**애플리케이션 수준에서 다루는 것이 최선이다** — **세션에 무언가를 저장하기 전에 신중히 생각하라.
쉽게 재생성할 수 있는 데이터라면 세션 상태에서 빼는 것이 낫다.**

```xml
<session-timeout>30</session-timeout>   <!-- web.xml 기본값: 30분 -->
```
> **세션 데이터를 30분이나 유지하는 것은 긴 시간이다 — 사용자가 정말 29분 자리를 비웠다가
> 돌아올 것으로 기대하나?** 이 값을 줄이면 세션 데이터가 힙에 주는 영향을 확실히 완화할 수 있다.

> **앱 서버 구현이 도울 수 있는 영역**: 데이터가 30분간 사용 가능해야 하지만 **자바 힙에 남아
> 있어야 할 필요는 없다.** 앱 서버가 **10분 유휴 후 직렬화해 디스크나 원격 캐시로 옮길 수 있다.**
> 앱 서버 힙의 공간이 비면서 30분 보존 계약도 지킨다. **사용자가 29분 뒤 돌아오면 첫 요청이 조금
> 오래 걸리겠지만, 그동안 앱 서버 전체 성능은 더 좋았을 것이다.**

> **테스트할 때도 중요한 원칙이다.** 사용자들의 세션 관리에 대한 현실적 기대가 무엇인가?
> **아침에 한 번 로그인해 하루 종일 쓰나? 자주 오가며 버려진 세션을 잔뜩 남기나? 그 중간인가?**
> **답이 무엇이든 테스트 시나리오가 예상 사용을 반영해야 한다.** 그렇지 않으면 프로덕션 서버가
> 잘못 튜닝된다 — **힙이 성능 테스트가 측정한 것과 완전히 다른 방식으로 쓰일 테니까.**
>
> (이 책의 `fhb` 테스트는 클라이언트 스레드마다 **테스트 내내 단일 세션을 유지**한다.)

## 고가용성(HA) 세션 복제 — ⚠️ 개발자가 알아야 할 함정

**앱 서버는 매 요청마다 전체 세션 상태를 복제하거나, 바뀐 데이터만 복제할 수 있다.**
**두 번째가 거의 항상 더 성능이 좋다.**

**하지만 이게 동작하려면 개발자가 규칙을 따라야 한다.**

```java
HttpSession session = request.getSession(true);
ArrayList<StockPriceHistory> al =
    (ArrayList<StockPriceHistory>) session.getAttribute("saveHistory");
al.add(...some data...);
session.setAttribute("saveHistory", al);   // ★ 이 줄이 핵심
```

> **⚠️ 앱 서버는 이미 세션에 저장된 객체의 변경을 추적할 수 없다.**
>
> **단일(비복제) 서버에서는 마지막 `setAttribute()` 호출이 필요 없다** — 리스트가 이미 세션에
> 있으니까. 생략해도 이후 모든 요청이 이 서버로 오면 정상 동작한다.
>
> **생략한 상태에서 세션이 백업 서버로 복제되고 요청이 백업 서버에서 처리되면, 애플리케이션은
> 리스트의 데이터가 바뀌지 않은 것을 발견하게 된다.** 앱 서버가 **바뀐 데이터만 복사하는 것으로
> "최적화"** 했고, `setAttribute()` 호출이 없어 **리스트가 바뀐 것을 몰랐기 때문**이다.
>
> **이것은 Java EE 스펙의 다소 모호한 영역이다.** 스펙은 이 경우 `setAttribute()` 호출을
> 강제하지 않지만, **HA를 지원하는 거의 모든 Java EE 앱 서버가 이 관례를 쓴다.**
> 어떤 서버는 그것만이 유일한 방식이다. 다른 서버는 **매 호출마다 전체 세션을 복제하도록 설정할
> 수 있어서 `setAttribute()` 를 안 불러도 동작하지만, 성능은 훨씬 나쁘다.**
>
> **교훈: 세션에 저장된 객체의 값을 바꿀 때마다 `setAttribute()` 를 부르고, 앱 서버가 바뀐
> 속성만 복제하도록 설정하라.**

# 3부. 스레드 풀 (Java EE 관점)

**앱 서버는 대개 스레드 풀이 여럿이다** — 서블릿 요청용, 원격 EJB 요청용, JMS 요청용.
어떤 서버는 **각 트래픽 종류마다 여러 풀**을 쓸 수 있다(다른 URL의 서블릿 요청, 다른 원격 EJB 호출).

**별도 풀이 앱 서버 안에서 제한적인 우선순위 부여를 가능하게 한다.**

> **저자의 예시**: 4 CPU 머신, HTTP 풀 12스레드, EJB 풀 4스레드.
> 모든 스레드가 CPU를 두고 경쟁하지만, **모두 바쁠 때 서블릿 요청이 EJB 요청보다 CPU를 얻을
> 확률이 3배다. 사실상 서블릿에 3배 우선순위를 준 것이다.**

**⚠️ 한계 두 가지**
1. **"서블릿 요청이 없을 때만 EJB 요청이 돌게" 설정할 수는 없다.** EJB 풀에 스레드가 있는 한
   **서블릿 풀이 아무리 바빠도 그 스레드들은 CPU를 두고 동등하게 경쟁한다**
2. **서버가 그 외 유휴일 때 예상되는 작업량 아래로 특정 풀을 조이지 않도록 조심하라.**
   4 CPU 머신에서 JMS 풀이 3스레드면 **JMS 요청만 처리할 때 가용 CPU를 다 못 쓴다.**
   보상하려고 모든 풀을 비례해 늘리면 **스레드를 너무 많이 돌려 머신을 과포화시킬 위험**이 있다

> **이런 튜닝은 꽤 섬세하고 앱 서버로 들어오는 트래픽의 좋은 모델을 갖고 있어야 한다.
> 성능의 마지막 몇 퍼센트를 짜내는 데 쓰인다.**

# 4부. EJB 세션 빈

## EJB 풀 튜닝 — 객체 풀의 교과서적 예

**풀링이 없으면 EJB 호출에 이 단계들이 든다.**
1. EJB 객체 생성
2. 애노테이션 처리 및 자원 의존성 주입
3. `@PostConstruct` 메서드 호출
4. (상태 유지 빈) `@Init` 이나 `ejbCreate()` 호출
5. **비즈니스 메서드 실행**
6. `@PreRemove` 메서드 호출
7. (상태 유지 빈) `remove()` 호출

> **풀에서 얻으면 비즈니스 메서드만 실행하면 되고 나머지 6단계를 건너뛴다.**
> **7장에서 봤듯 객체 풀링이 일반적으로 유용하지는 않지만, 이건 초기화 비용이 풀링을 가치 있게
> 만드는 경우다.**

**저자의 실측 (GlassFish 4.0, 클라이언트 64개, `@PostConstruct` 에 sleep을 넣어 초기화 시간 흉내)**

| EJB 풀 크기 | 초기화 시간 | 평균 응답 시간 |
|---|---|---|
| 1 | 0 ms | 0.37초 |
| 64 | 0 ms | 0.37초 |
| **1** | **25 ms** | **0.40초** |
| 64 | 25 ms | 0.37초 |
| **1** | **50 ms** | **0.42초** |
| 64 | 50 ms | 0.37초 |

> **초기화 시간이 0이면 EJB 풀에 아무 이점이 없다.** 25ms·50ms이고 풀 크기가 1이면 —
> **매 호출마다 새 EJB를 만들어야 하므로 — 예측 가능한 페널티**가 생긴다.
>
> **풀에 (작은) 객체 64개뿐이라 GC 페널티를 도입할 가능성이 낮다.
> 이것이 성공적인 객체 풀의 또 하나의 핵심 특징이다 — 쓸 만할 때는 작게 유지하라.**

**크기 정하기**: **일반적 출발점은 앱 서버의 워커 스레드 수만큼 EJB 풀에 객체를 두는 것**이다
(요청당 최대 하나의 EJB가 필요한 것이 흔하므로). **⚠️ EJB 풀은 타입별이다** — EJB 클래스가
두 개면 풀도 두 개다.

```xml
<bean-pool>
  <steady-pool-size>8</steady-pool-size>
  <resize-quantity>2</resize-quantity>
  <max-pool-size>64</max-pool-size>
  <pool-idle-timeout-in-seconds>300</pool-idle-timeout-in-seconds>
</bean-pool>
```

> **너무 크게 잡는 페널티는 대개 크지 않다.** 미사용 인스턴스 때문에 GC가 약간 덜 효율적이지만,
> 풀 크기가 일반적으로 아주 작아서 영향이 크지 않다. **예외는 빈이 많은 메모리를 들고 있을 때다.**
>
> **앱 서버가 풀을 관리하는 흔한 방식은 최대 크기와 별도로 안정(steady) 크기를 두는 것이다.**
> 위 예에서 최대 10개 인스턴스만 쓰이는 트래픽이면 **10개만 만들어지고 64에 근접조차 안 한다.**
> 짧은 스파이크로 64개가 만들어져도, 트래픽이 잦아들면 **300초 유휴 후 파괴되어 GC 대상이 된다.
> 이것이 풀이 GC에 주는 영향을 최소화한다.**
>
> **그러므로 최대 크기보다 안정 크기 튜닝에 더 신경 써라.**

## EJB 캐시 (상태 유지 세션 빈)

**상태 유지 빈은 패시베이션(passivation) 대상이다** — 메모리를 아끼려고 앱 서버가 빈 상태를
직렬화해 디스크에 저장할 수 있다.

> **심각한 성능 페널티이고 대부분의 경우 피하는 게 최선이다.**
> **솔직히 말하면 저자는 거의 모든 경우에 피하라고 권한다.**
>
> **패시베이션을 옹호하는 통상적 논거**는 세션이 몇 시간·며칠 유휴인 시나리오다. 사용자가
> (며칠 뒤) 돌아오면 상태가 온전하기를 바란다는 것.
> **문제는 그 시나리오가 EJB 세션이 유일한 중요 상태라고 가정한다는 점이다.**
> 보통 EJB는 HTTP 세션과 연결되고, **그 세션을 며칠 유지하는 것은 권장되지 않는다.**
> **게다가 대개 추가적인 외부 상태도 있다.** (사용자 장바구니에 **더 이상 판매되지 않는 상품**이
> 있다면?)
>
> **오래 사는 상태가 필요하면 대개 표준 Java EE 상태 메커니즘을 우회해야 한다.**

**상태 유지 빈은 EJB 풀이 아니라 EJB 캐시에 있다.** **캐시를 동시 활성 세션 최대 수를 담을 만큼
크게 튜닝해야 한다.** 그렇지 않으면 **가장 최근에 안 쓰인 세션이 패시베이션된다.**
GlassFish 기본 캐시 크기는 **512**.

> **EJB 풀 모니터링 — 어떤 값을 쓸지 어떻게 아나?**
> 하나는 애플리케이션 동작과 예상 부하로 교육된 추측을 하는 것. **하지만 EJB가 너무 많이 만들어지고
> 있는지(또는 상태 유지 빈이 너무 많이 패시베이션되는지) 실제로 아는 유일한 방법은 앱 서버의
> 모니터링 기능을 쓰는 것이다.**
>
> **GlassFish 예시**: **파괴된 EJB 수가 0이 아니면** 풀에 가용 빈이 없어 생성 후 파괴됐다는 뜻이다.
> 그에 따라 **생성된 EJB 수가 최대 풀 크기보다 크다. EJB 풀이 과소 설정됐다는 표시다.**
>
> **⚠️ 모니터링 자체에 비용이 있다.** 저자가 EJB 컨테이너 모니터링 수준을 **HIGH**로 설정하니
> **총 처리량이 약 5% 떨어졌다.** 가시성에 치를 만한 작은 값이지만, **설정 가능한 모니터링을
> 제공하는 앱 서버라면 필요한 것에 맞춰 설정하라.** GlassFish의 **LOW는 영향이 무시할 만하고,
> 더 많은 정보가 필요할 때 동적으로 HIGH로 올릴 수 있다.**

## 로컬 vs 원격 인터페이스

**서블릿과 EJB가 같은 서버에 있으면 항상 로컬 인터페이스를 써야 한다.**

> **⚠️ 이유가 명백해 보이는 것과 다르다.** 원격 인터페이스가 네트워크 호출을 함의하니 그렇게
> 보이지만 **그게 이유가 아니다** — 서블릿과 원격 EJB가 같은 앱 서버에 배포되면
> **대부분의 서버가 네트워크 호출을 우회하고 일반 메서드 호출로 EJB 메서드를 부를 만큼 똑똑하다.**
>
> **진짜 이유는 두 인터페이스가 인자를 다루는 방식이다.**
> - **로컬 EJB**: 일반 자바 시맨틱. 원시값은 값으로, 객체는 참조로 전달
> - **원격 EJB**: **항상 값으로 전달해야 한다.** 네트워크에서 가능한 유일한 시맨틱이다 —
>   보내는 쪽이 직렬화해 바이트 스트림을 보내고 받는 쪽이 역직렬화해 객체를 재구성한다
>
> **서버가 네트워크를 피해 로컬 호출을 최적화해도 직렬화/역직렬화 단계는 우회할 수 없다.**
> (대부분의 서버는 대상 객체가 불변 — `String`, 원시값 — 이면 알아채고 직렬화를 건너뛴다.
> **하지만 일반적인 경우에는 불가능하다.**)
>
> **서버가 아무리 잘 작성돼 있어도 서버 안에서 원격 EJB 인터페이스를 쓰는 것은 항상 로컬보다 느리다.**

> **프로토콜**: 모든 원격 EJB는 **IIOP(CORBA)** 를 지원해야 한다. 상호운용성에는 훌륭하다.
> **Java EE 서버 벤더는 독점 프로토콜을 포함해 다른 프로토콜도 쓸 수 있고, 그 독점 프로토콜은
> 예외 없이 CORBA보다 빠르다**(그게 벤더가 애초에 만든 이유다).
> **원격 EJB 호출이 필요하고 상호운용성이 관심사가 아니라면 벤더가 제공하는 접근 프로토콜
> 옵션을 살펴보라.**

# 5부. XML과 JSON 처리

## 데이터 크기

**저자의 실측 (eBay 인기 상품 20개)**

| 형식 | 크기 |
|---|---|
| XML (원본, 공백 많음) | 23,031 바이트 |
| XML (트림 후) | 20,556 바이트 |
| **JSON (공백 전혀 없음)** | **16,078 바이트** |
| **XML 압축** | **3,742 바이트** |
| **JSON 압축** | **3,471 바이트** |

> **JSON 데이터에는 공백이 전혀 없어 사람이 읽기 어렵다. 말이 된다 — 사람의 가독성이 목표가
> 아니니까. 그런데 이상하게도 XML 데이터는 공백이 많은 잘 구조화된 형태다.**
> **25% 차이는 주로 XML 닫는 태그 때문이고, 그 태그들이 항상 XML 출력을 크게 만든다.**
>
> **흥미롭게도 XML을 JSON으로 자동 변환하는 사이트가 많은데, 순진한 접근을 취하는 경향이 있어
> JSON 출력이 XML보다 커지는 경우가 대부분이다** — 사람이 읽을 수 있는 JSON 출력에는 공백이
> 많고 불필요한 구조가 많기 때문이다.
>
> **압축하면 크기가 훨씬 가까워져 크기 차이가 덜 중요해진다.**

## 네 가지 처리 기법 (느린 순 → 빠른 순)

| 기법 | 설명 |
|---|---|
| **토큰 파서 (push)** | 파서가 토큰을 훑으며 객체의 메서드를 콜백 |
| **풀 파서 (pull)** | 프로그램이 파서에서 토큰을 요청(pull) |
| **문서 모델** | 문서형 객체로 변환해 애플리케이션이 훑는다 |
| **객체 표현** | 데이터 구조를 반영하는 미리 정의된 클래스로 변환 |

> **⚠️ 느린 순 → 빠른 순이지만, 기능적 차이가 성능 차이보다 중요하다.**
>
> **앞의 두 개(순수 파서)는 기능적 차이가 크지 않다** — 데이터를 한 번만 훑고 정보를 뽑는
> 알고리즘 대부분에 적응 가능하다. **하지만 단순 스캔이 파서가 할 수 있는 전부다.**
> **무작위 순서로 접근하거나 여러 번 조사해야 하는 데이터에는 이상적이지 않다.**
> 그러려면 내부 자료구조를 만들어야 하는데, **문서·객체 모델은 이미 구조화된 데이터를 제공한다.**
>
> **이것이 파서와 데이터 마셜러의 진짜 차이다.** 뒤의 둘은 마셜러다 — 데이터 처리에 파서를 써야
> 하지만, **더 복잡한 프로그램이 로직에서 쓸 수 있는 데이터 표현을 제공한다.**

**선택 기준**
- **한 번의 단순한 패스** → **가장 빠른 파서**로 충분
- **애플리케이션 정의 단순 구조로 저장** → 파서 직접 사용도 적절
- **데이터 형식이 중요하고 보존해야 함** → **문서 모델**. 읽고, 바꾸고, 새 스트림에 쓰기만 하면 된다
- **궁극의 유연성** → **객체 모델**. 익숙한 객체·속성 용어로 다룬다.
  **마셜링의 복잡함은 (대부분) 개발자에게 투명하고 그 부분이 조금 느려지지만,
  코드 작업의 생산성 향상이 그 문제를 상쇄할 수 있다**

> **예제의 목표는 20항목 문서에서 아이템 ID를 리스트에 저장하는 것이다. 일부 테스트는 앞의
> 10개만 필요로 한다. 이는 현실에서 자주 보이는 것을 흉내낸다 — 웹 인터페이스는 실제 필요보다
> 많은 데이터를 반환하는 경우가 많다.**
> **웹 서비스 설계 고려사항으로는 좋은 것이다 — 호출 설정에 시간이 걸리므로, (데이터를 너무
> 많이 가져오더라도) 원격 호출이 적은 편이 세밀한 원격 호출을 많이 하는 것보다 낫다.**

## 파서 선택

### 풀 파서 (StAX / JSON-P)

**개발자 관점에서 대개 쓰기 가장 쉽다.** JSON-P는 **풀 파서만 제공한다.**

| 처리 항목 | XML 파서 | JSON 파서 |
|---|---|---|
| **10** | **143 ms** | **68 ms** |
| 20 | 265 ms | 146 ms |

> **필요한 데이터만 처리하면 예측 가능한 성능 이득이 있다.**
> **10개에서 멈춰도 50%가 절약되지는 않는다**(다른 섹션은 여전히 파싱되니까) **하지만 차이는
> 여전히 유의미하다.**

### 푸시 파서 (SAX) — XML만

**토큰을 찾으면 콜백을 실행한다.**

> **⚠️ 프로그램 로직의 유일한 차이는 파싱 완료를 알리려면 예외를 던져야 한다는 것이다** —
> **XML 푸시 파싱 프레임워크가 파싱 중단을 감지할 유일한 방법이기 때문**이다.
> 예제는 실제 에러와 중단 신호를 구분하려고 `SAXDoneException` 서브클래스를 정의했다.

| 처리 항목 | XML StAX | **XML SAX** |
|---|---|---|
| 10 | 143 ms | **132 ms** |
| 20 | 265 ms | **231 ms** |

> **SAX가 StAX보다 빠른 경향이지만 차이가 작다 — 개발에서 어느 모델이 쓰기 쉬운가로 선택하라.**

### ⚠️ 파서 팩토리 조회 — 숨은 성능 함정

**XML 팩토리는 세 방법 중 하나로 지정되고, 다음 순서로 탐색된다.**

1. **시스템 프로퍼티** `-Djavax.xml.stream.XMLInputFactory=my.factory.class`
2. **`JAVA/jre/lib` 의 `jaxp.properties` 파일**
3. **클래스패스에서 `META-INF/services/javax.xml.stream.XMLInputFactory` 파일 탐색**
4. JDK 정의 기본 팩토리

> **⚠️ 세 번째 옵션에 상당한 성능 페널티가 있다. 특히 클래스패스가 아주 긴 환경에서.**
> **대체 구현이 지정됐는지 보려면 클래스패스의 모든 항목에서 `META-INF/services` 디렉터리를
> 뒤져야 한다. 그 탐색이 팩토리를 만들 때마다 반복되고, 클래스로더가 그 리소스 조회를 캐시하지
> 않으면(대부분의 클래스로더는 캐시하지 않는다) 팩토리 인스턴스화가 아주 비싸진다.**
>
> **⚠️ 그리고 결정적으로 — 이 방식이 기본 팩토리에도 영향을 준다.**
> **JDK는 클래스패스를 뒤지기 전까지 기본 팩토리를 쓸지 알 수 없다.**
> **그러므로 기본 팩토리를 쓰고 싶더라도 시스템 프로퍼티나 JRE 프로퍼티 파일에 기본 구현을
> 가리키도록 설정해야 한다.** 안 그러면 **비싼 3단계 탐색이 끝날 때까지 기본 팩토리(4번)가
> 쓰이지 않는다.**
>
> **처음 두 옵션의 단점**: **앱 서버의 모든 코드에 전역으로 적용된다.** 두 EE 애플리케이션이
> 서로 다른 파서 팩토리를 요구하면 서버는 (잠재적으로 느린) 클래스패스 기법에 의존해야 한다.
>
> **JSON은 설정이 조금 다르다** — 대체 구현 지정 방법이 **`META-INF/services` 경로뿐**이고
> (`javax.json.spi.JsonProvider`), **불행히도 전체 클래스패스 탐색을 우회할 방법이 없다.**

> **팩토리와 파서 재사용**
> **XML·JSON 파서 팩토리는 생성이 비싸다. 다행히 스레드 안전하므로 전역 정적 변수에 저장해
> 재사용하기 쉽다.**
> **일반적으로 실제 파서는 재사용할 수 없고 스레드 안전하지도 않다. 그래서 보통 필요할 때 만든다.**
> **SAX 파서의 한 가지 장점은 파서 객체를 재사용할 수 있다는 것이다** — 호출 사이에 `reset()` 을
> 부르면 된다. **다만 여전히 스레드 안전하지 않으므로 한 번에 한 스레드로 제한하라.**

### 대체 구현

| 처리 항목 | JDK StAX | **Woodstox StAX** |
|---|---|---|
| 10 | 143 ms | **125 ms** |
| 20 | 265 ms | **237 ms** |

| 처리 항목 | Java EE JSON | **Jackson JSON** |
|---|---|---|
| 10 | 68 ms | **40 ms** |
| 20 | 146 ms | **74 ms** |

> **저자의 신중한 단서**: 이 절은 **일부 구현의 스냅샷일 뿐이니 결과를 액면 그대로 받지 마라.**
> **요점은 항상 다른 파서 구현이 있을 것이고, 성능 면에서 서로 앞서거니 뒤서거니 할 것이라는
> 점이다.** 어느 시점엔 대체 파서가 참조 구현보다 빠를 것이고, **새 JDK나 JSON-P 참조 구현이
> 나오면 또 뒤집힐 수 있다.**
> (실제로 이 절의 수치는 참조 JSON 파서 1.0.2 버전인데 **초기 1.0보다 약 65% 빠르다.**)

## XML 검증(Validation) — 비싸다

> **이것이 XML이 JSON보다 나은 이점 하나다.** JSON 문서를 파싱할 때 검증 로직을 직접 넣을 수
> 있지만, **XML은 파서가 대신 해 준다. 그 이점에 성능 비용이 따른다.**

**성능 팁**
- **DTD 검증이 스키마보다 빠르지만 스키마가 더 유연하고 지금은 스키마가 우세하다**
- **스키마가 느린 이유 하나는 대개 서로 다른 파일에 지정된다는 것이다.**
  **스키마 파일을 통합하는 것이 검증 페널티를 줄이는 첫 번째 방법**이다.
  ⚠️ **다만 스키마 파일은 네임스페이스가 달라 (CSS나 JS처럼) 합치기 쉽지 않다**
- **⚠️ 스키마 파일을 어디서 로드하는가가 중요한 성능 이슈가 될 수 있다.**
  **네트워크에서 반복 로드하면 성능이 나빠진다. 이상적으로는 애플리케이션 코드와 함께 전달해
  로컬 파일시스템에서 로드해야 한다**

**⚠️ 기본 처리 방식은 파서를 재사용해도 새 문서를 파싱할 때마다 스키마를 다시 읽는다.**

**스키마 재사용의 두 옵션**
1. **`spf.setSchema(schema)`** (SAX만) — ⚠️ **이 경우 `setValidating(false)` 를 호출한다.
   `setSchema()` 와 `setValidating()` 은 상호 배타적인 검증 방식이다**
2. **`Validator` 클래스 인스턴스** — 파싱과 검증을 분리해 다른 시점에 수행할 수 있다.
   StAX와 쓰면 **특수 리더를 검증 스트림에 끼워 파싱 중에 검증**할 수 있다
   > **단점**: 10개를 읽은 뒤 처리를 깔끔하게 종료할 수 없다. 예외를 던질 수는 있지만
   > **기본 스키마 리스너가 예외를 던질 때 에러 메시지를 출력한다.**

| 파싱 모드 | SAX | StAX |
|---|---|---|
| 검증 없음 | 231 ms | 265 ms |
| **기본 검증** | **730 ms** | N/A |
| **스키마 재사용** | **649 ms** | **1392 ms** |

> **검증이 기능적으로 중요하면 반드시 쓰되, 파싱에 상당한 성능 페널티를 더한다는 것을 알아야 한다.
> 검증의 영향을 최소화하려면 항상 스키마를 재사용하라.**

## 문서 모델 (DOM / JsonObject)

| 소요 시간 | XML | JSON |
|---|---|---|
| 데이터 파싱 | 265 ms | 146 ms |
| **문서 구축** | **348 ms** | **197 ms** |

> **문서 구축 시간은 파싱 시간을 포함하므로, 구조 생성 시간이 XML 전체의 약 33%, JSON의 약 25%
> 임을 추론할 수 있다. 더 복잡한 문서는 더 큰 비율을 보일 수 있다.**

- **DOM은 `DocumentBuilder` 로 만든다.** 기본 팩토리는
  `javax.xml.parsers.DocumentBuilderFactory` 프로퍼티로 지정한다 —
  **파서와 마찬가지로 이 시스템 프로퍼티를 최적으로 설정하는 것이 중요하다**
- **`DocumentBuilder` 는 SAX 파서처럼 `reset()` 을 부르면 재사용 가능하다.
  `JsonReader` 는 재사용 불가**

### DOM 필터링

DOM level 3 속성(`LSParserFilter`)으로 파싱하면서 필터링할 수 있다.
`startElement()` 는 파싱 시작 시, `acceptNode()` 는 끝날 때 호출된다.
`FILTER_SKIP` 을 반환하면 최종 문서에서 빠진다.

| | 표준 DOM | **필터링 DOM** |
|---|---|---|
| DOM 생성 시간 | 348 ms | **417 ms** |
| **DOM 크기** | 101,440 바이트 | **58,824 바이트** |

> **필터링의 요점이 여기 있다 — 실제 파싱과 필터링은 전체 데이터를 담은 문서를 만드는 것보다
> 오래 걸린다. 하지만 문서가 메모리를 덜 차지하므로, 문서가 오래 살거나 그런 문서가 많이
> 쓰이면 GC 압박을 줄이는 유용한 기법이다.**

## 자바 객체 모델 (JAXB)

**JAXB는 내부적으로 StAX 파서를 쓰므로 최적 StAX 파서 설정이 JAXB 성능에 도움이 된다.**

> **`JAXBContext` 는 생성이 비싸다. 다행히 스레드 안전하므로 전역 컨텍스트 하나를 만들어
> 공유·재사용할 수 있다.**
> **`Unmarshaller` 는 스레드 안전하지 않아 스레드마다 새로 만들어야 한다. 하지만 재사용은
> 가능하므로 스레드 로컬(또는 풀)에 두면 문서를 많이 처리할 때 성능에 도움이 된다.**

| | 마셜(쓰기) | 언마셜(읽기) |
|---|---|---|
| DOM | 348 ms | 298 ms |
| **JAXB** | **414 ms** | **232 ms** |

> **JAXB 객체 생성이 파싱이나 DOM 생성보다 비싸다. 트레이드오프는 그 객체를 쓰는 것이 문서를
> 훑는 것보다 훨씬 빠르다는 것이다**(문서 접근용의 복잡한 API 대신 일반 자바 코드를 쓴다는 것은
> 말할 것도 없고). **게다가 JAXB에서 XML을 써 내는 것이 문서에서 쓰는 것보다 훨씬 빠르다.**

> **JAX-WS에서 XML 필터링하기**
> JAXB를 써도 XML 일부만 처리하고 싶을 수 있다. **보통 JAX-WS는 모든 XML을 JAXB 객체로 번역한다.
> 사용 편의성에는 좋지만, 일부만 필요하다면 JAXB 처리가 너무 비싸고 객체들이 힙을 너무 먹을 수 있다.**
> **이 경우 XML 데이터를 SOAP 메시지의 첨부(MIME `application/xml`)로 보내라.**
> **첨부는 JAXB 객체로 번역되지 않으므로 필터링 DOM 빌더나 단순 StAX 파서로 관심 있는 부분만
> 처리할 수 있다.**

# 6부. 객체 직렬화

**Java EE에서 두 가지 중요한 쓰임이 있다.**
- **서버 간 원격 EJB 호출**이 직렬화로 데이터를 교환한다
- **HTTP 세션 상태가 직렬화로 저장**되어 HA를 가능하게 한다

> **⚠️ 상상할 수 있는 거의 모든 객체의 직렬화 성능은 기본 코드에서 개선할 수 있다.
> 하지만 이건 확실히 성급하게 최적화하면 현명하지 못한 경우 중 하나다.**
> **특수 코드는 작성에 상당한 시간이 걸리고 유지보수가 어렵다. 직렬화 코드는 올바르게 쓰기가
> 까다로워서 최적화 시도가 잘못된 코드를 만들 위험을 높인다.**

## `transient` 필드 — 가장 안전한 최적화

**일반적으로 직렬화 비용을 개선하는 방법은 데이터를 덜 직렬화하는 것이다.**
`transient` 로 표시하면 기본적으로 직렬화되지 않는다.

## `writeObject()`/`readObject()` 재정의 — ⚠️ 위험하다

**단순 `Point` 객체 예 (10만 개)**
- 기본: 직렬화 **133ms**, 역직렬화 **741ms**
- 필드를 `transient` 로 하고 `writeInt()` 로 직접 쓰기: 직렬화 132ms, **역직렬화 468ms (30% 개선)**

**⚠️ 그런데 다음 예제는 성능은 좋지만 기능적으로 틀렸다.**

```java
public class TripHistory implements Serializable {
    private transient Point[] airportsVisited;
    // THIS CODE IS NOT FUNCTIONALLY CORRECT
    private void writeObject(ObjectOutputStream oos) throws IOException {
        oos.defaultWriteObject();
        oos.writeInt(airportsVisited.length);
        for (int i = 0; i < airportsVisited.length; i++) {
            oos.writeInt(airportsVisited[i].getX());
            oos.writeInt(airportsVisited[i].getY());
        }
    }
    // readObject 에서 new Point(...) 로 재생성
}
```

**성능은 확실히 좋다** — `Point` 10만 개 배열이 기본 직렬화로 **4.7초/6.9초**인데
이 "최적화"로 **2초/1.7초**가 된다.

> **⚠️ 그런데 이 코드는 틀렸다.**
> JFK 위치를 나타내는 배열의 참조들은 **원래 같은 객체를 가리켰다.** 그래서 그 데이터가 틀렸음을
> 발견하면 **JFK 참조 하나만 고치면 배열의 모든 객체가 반영한다.**
>
> **위 코드로 역직렬화하면 그 JFK 참조들이 각각 다른 객체가 된다.** 이제 하나를 바꾸면
> **그것만 바뀌고 나머지 JFK 참조 객체들과 다른 데이터를 갖게 된다.**
>
> **이것이 아주 중요한 원칙이다. 직렬화 최적화는 종종 객체 참조에 대한 특별 처리에 관한 것이기
> 때문이다. 제대로 하면 성능이 크게 오르고, 잘못하면 아주 미묘한 버그가 생긴다.**

### `StockPriceHistoryImpl` — 올바른 방식

**모든 지연 초기화 필드(`highPrice`, `lowPrice`, `averagePrice`, `stdDev`, `histogram`)는
`prices` 맵에서 계산할 수 있으므로 전부 `transient` 로 표시하고 특별 작업이 필요 없다.**
> **코드가 이미 지연 초기화를 하고 있어서 쉬웠다.** 즉시 초기화하더라도 **계산 필드를
> `transient` 로 표시하고 `readObject()` 에서 재계산할 수 있다.**
>
> **그리고 이것이 `prices` 와 `histogram` 사이의 객체 관계를 보존한다** — 히스토그램이
> 재계산될 때 **기존 객체들을 새 맵에 넣을 뿐**이다.

| 객체 | 직렬화 | 역직렬화 | 데이터 크기 |
|---|---|---|---|
| `transient` 없음 | 12.8초 | 11.9초 | 46,969 바이트 |
| **`histogram` transient** | **11.5초** | **10.1초** | **40,910 바이트** |

> **약 15%를 아꼈다. 하지만 이 테스트는 받는 쪽에서 `histogram` 을 재생성하지 않았다** —
> 받는 코드가 처음 접근할 때 만들어진다.
>
> **⚠️ 여기서 더 이례적인 경우가 나온다: `histogram` 이 항상 필요하고, 이 테스트의 모든
> 히스토그램 계산에 3.1초 넘게 걸린다면, 지연 초기화 케이스가 실제로는 성능 순손실이 된다.**
> (이 경우 히스토그램 계산은 아주 빠른 연산이라 해당하지 않는다.)
> **일반적으로 데이터 재계산이 그 데이터의 직렬화·역직렬화보다 비싼 경우를 찾기는 어려울 수
> 있다. 하지만 코드를 최적화할 때 고려할 점이다.**

## 직렬화 데이터 압축 — 반직관적인 결과

```java
private byte[] zippedPrices;
private transient SortedMap<Date, StockPrice> prices;
// writeObject 에서 GZIP 압축, readObject 에서 해제
```

**바이트 스트림 대상 (네트워크 없음, 10,000 객체)**

| 사용 사례 | 직렬화 | 역직렬화 | 데이터 크기 |
|---|---|---|---|
| 압축 없음 | 12.1초 | 8.0초 | 41,170 바이트 |
| 압축/해제 | 26.8초 | 12.7초 | **5,849 바이트** |
| **압축만 (지연 해제)** | 26.8초 | **0.494초** | **5,849 바이트** |

> **가장 흥미로운 것은 마지막 줄이다.** 보내기 전에 압축하지만 **`readObject()` 에서
> `unzipPrices()` 를 부르지 않는다.** 대신 필요할 때 — 클라이언트가 처음 `getPrice()` 를 부를 때 —
> 부른다. **그 호출이 없으면 역직렬화할 `BigDecimal` 이 몇 개뿐이라 아주 빠르다.**
>
> **클라이언트가 실제 가격을 전혀 필요로 하지 않을 가능성도 충분하다** — `getHighPrice()` 같은
> 집계 정보만 필요할 수 있다. **그 메서드들만 필요한 한 지연 압축 해제로 많은 시간을 아낀다.**
>
> **이 지연 압축 해제는 객체가 영속화될 때도 아주 유용하다**(앱 서버 장애 대비 백업으로 저장되는
> HTTP 세션 상태 등). **CPU 시간(압축 해제 생략)과 메모리(압축 데이터가 공간을 덜 차지) 양쪽을
> 아낀다.**
>
> **그러므로 로컬 고속 네트워크에서 돌더라도 — 특히 목표가 시간이 아니라 메모리 절약이라면 —
> 직렬화용으로 압축하고 지연 해제하는 것이 꽤 유용할 수 있다.**

**네트워크 전송 시 (10,000 객체)**

| 객체 | 같은 머신 | 광대역 WAN |
|---|---|---|
| 압축 없음 | 30.1초 | **150.1초** |
| 압축/해제 | 41.3초 | 54.3초 |
| **압축만 (지연 해제)** | **28.0초** | **44.1초** |

> **가능한 가장 빠른 네트워크 통신은 같은 머신의 두 프로세스 사이다** — 네트워크로 나가지 않고
> OS 인터페이스만 거친다. **그 경우에도 압축 + 지연 해제가 가장 빠른 성능을 냈다.**
> (**적어도 이 테스트에서는. 더 작은 데이터는 여전히 퇴보를 보일 수 있다.**)

## 중복 객체 참조 추적

> **기본 직렬화에서 `TreeMap` 을 쓰면**: 노드 A의 원시 필드를 쓰고, 재귀적으로 노드 B의
> `writeObject()` 를 부른다. B는 자기 원시 필드를 쓰고 재귀적으로 `parent` 필드 데이터를 쓴다.
> **그런데 잠깐 — 그 `parent` 는 이미 쓴 노드 A다.**
> **객체 직렬화 코드는 그것을 알아챌 만큼 똑똑하다 — 노드 A 데이터를 다시 쓰지 않고 앞서 쓴
> 데이터에 대한 객체 참조를 추가할 뿐이다.**
>
> **그 집합을 추적하는 것과 모든 재귀가 작은 성능 부담을 더한다. 하지만 `Point` 배열 예에서
> 봤듯 피할 수 없다.**

**`TreeMap` 이 하는 실제 최적화 두 가지**
1. **트리를 순회하며 키와 값만 쓴다. 직렬화가 키들 사이의 관계(정렬 순서) 정보를 전부 버린다.**
   역직렬화 시 `readObject()` 가 **다시 정렬해 트리를 만든다.**
   > **다시 정렬하는 것이 비싸게 들리지만 아니다 — 1만 개 주식 객체에서 모든 객체 참조를 쫓는
   > 기본 직렬화보다 약 20% 빠르다.**
2. **노드(Entry) 객체 자체를 쓰지 않고 키와 값을 직접 쓴다.**
   > **맵은 동일한 노드 둘을 담을 수 없으므로 노드에 대한 객체 참조를 보존할 걱정이 없다.**
   > **`Point` 예제에서 안 되던 코드와 아주 비슷해 보인다. 차이는 이 코드가 여전히 같을 수 있는
   > 객체는 객체로 쓴다는 것이다** — `TreeMap` 은 **같은 노드 둘은 못 갖지만 같은 값 둘은 가질 수
   > 있으므로 값은 객체 참조로 써야 한다.**

> **`Externalizable` 은 어떤가?**
> **실질적 차이는 비-`transient` 필드를 다루는 방식이다.** `Serializable` 은 `writeObject()` 가
> `defaultWriteObject()` 를 부를 때 비-`transient` 필드를 쓴다. **`Externalizable` 에는 그런
> 메서드가 없어서 전송하려는 모든 필드를 명시적으로 써야 한다.**
>
> **모든 필드가 `transient` 여도 `Serializable` 을 구현하고 `defaultWriteObject()` 를 부르는
> 편이 낫다.** 필드가 추가·삭제될 때 유지보수가 훨씬 쉽다.
> **그리고 성능 관점에서 `Externalizable` 에 내재적 이점이 없다 — 결국 중요한 것은 쓰이는
> 데이터의 양이다.**

# 7부. Java EE 네트워킹 API

**JAX-WS, JAX-RS, IIOP/RMI.**

> **아주 다른 프로토콜이고 기능 집합이 언제·왜 쓸지를 결정하는 주된 요인이다.**
> **"JAX-RS가 JAX-WS보다 빠른가" 하는 끝없는 논쟁이 있지만, 그 논쟁들은 필연적으로 양쪽으로
> 다 작성 가능한 최소공배수 애플리케이션을 가정한다.** 특정 보안 기능이 필요하면 성능과 무관하게
> **JAX-WS**이고, 기존 IIOP 인터페이스 서버와 통신해야 하면 그것이 선택을 결정한다.

## 데이터 전송 크기 — 상충하는 두 원칙

- **전송량은 최소화해야 한다**(압축, 문서 가지치기 등)
- **⚠️ 반면 네트워크 호출 설정 자체에 측정 가능한 오버헤드가 있다.**
  **인터페이스는 "굵게(coarse)" 설계해야 한다** — 한 번에 많은 데이터를 반환해 **클라이언트가
  해야 하는 총 네트워크 호출 수를 최소화**하는 편이 낫다
- **이 두 원칙은 서로 상충하므로 균형을 잡아야 한다**

**저자의 실측 (RESTful, 광대역)**

| 시나리오 | 평균 응답 시간 | 데이터 크기 |
|---|---|---|
| 1년치 데이터 | 90 ms | 30 KB |
| 1년 요약 | 30 ms | 60 바이트 |
| 5년치 데이터 | 300 ms | 186 KB |
| 요약 2회 요청 | 60 ms | 2호출 × 60바이트 |
| 요약 10회 요청 | 280 ms | 10호출 × 60바이트 |

> **1년치 전부를 가져오는 시간이 요약만 가져오는 것보다 특별히 길지 않다.
> 사용자가 개별 데이터 3개를 필요로 할 것으로 예상되면 한 번에 전부 반환하는 것이 항상 낫다.**
>
> **5년 요약은 다르다** — 마셜링과 전송에 훨씬 오래 걸려서, **사용자가 11번 드릴다운해야 총
> 시간이 비슷해진다.**

**마셜링된 응답을 캐시했다면 (여러 클라이언트가 같은 데이터를 요청)**

| 시나리오 | 평균 응답 시간 |
|---|---|
| 1년치 데이터 | **50 ms** (90 → 50) |
| 1년 요약 | 30 ms |
| **5년치 데이터** | **90 ms** (300 → 90) |
| 요약 2회 | 60 ms |
| 요약 10회 | 270 ms |

> **호출 오버헤드는 일정하므로 요약 케이스는 차이가 거의 없다. 1년·5년 전체 시나리오는 데이터
> 전송 시간만 남아 계산·마셜링이 필요했던 이전보다 훨씬 짧다.**
> **일반적으로 이 경우는 필요 없을 수도 있는 데이터를 많이 반환해도 성능 페널티가 크지 않다.**

> **네트워킹은 예전 같지 않다 — 저자의 마무리**
> 너무 늙은이처럼 들리고 싶진 않지만, **나는 300보드 모뎀으로 원격 네트워크에 접속하곤 했다.**
> (다행히 4피트 눈더미를 헤치고 5마일을 걸어 학교에 가진 않았다.) **그 상황에는 네트워크 호출을
> 너무 많이 하는 것에 대한 내재적 편견이 있다.**
>
> **오늘날 나는 브라우저 앞에 앉아 몇 글자 칠 때마다 구글 서버로 원격 호출을 한다.
> 구글은 그것이 200ms 이내면 내가 지연을 눈치채지 못한다고 계산했다.**
>
> **네트워크가 빨라질수록 이 절의 트레이드오프가 덜 중요해 보일 수 있다.**
> **반면 내 스마트폰은 빠른 3G만 잡아도 운이 좋고, 1년에 몇 번은 바다 한가운데서 위성으로
> 인터넷에 접속하는 행운을 누린다.**
>
> **더 빠른 하드웨어(나 네트워크)를 던지는 것은 항상 성능에 도움이 되지만, 그것을 성능 좋은
> 설계의 대체재로 여기지 마라.** 애플리케이션이 빠른 네트워크에 있음을 감지해 세밀한 호출을
> 할 수 있다면 훌륭한 선택 기능이다. **다만 어디에 배포되든 잘 동작하게 만들어라.**

| 이 장의 내용 | 우리 랩에서의 대응 |
|---|---|
| **출력을 줄여라 (LAN 20ms vs WiFi 1003ms)** | 검증 케이스 **없음** — 실제 네트워크가 필요 |
| HTTP 세션 상태가 힙을 채운다 | **`RES-10`**(스테이트리스 검증), 7장 힙 논의 |
| **HA에서 `setAttribute()` 를 안 부르면 복제가 안 된다** | **`MSA-02`**(결과적 일관성 버전 가드)와 사고방식이 같다 |
| EJB 풀 = 성공적 객체 풀 | **`DB-02`·`DB-06`**(커넥션 풀), 7장 |
| 앱 서버의 여러 스레드 풀로 우선순위 부여 | **`RES-09`**(벌크헤드) — 정확히 같은 구조 |
| **파서 팩토리 클래스패스 탐색이 락 경합을 만든다** | **9장 `jstack` 사례(SAX 파서 41스레드 블로킹)와 같은 이야기** |
| 원격 인터페이스는 같은 서버에서도 직렬화를 강제한다 | **`API-04`**(외부 API 계약), **`MSA-*`** 와 이어진다 |
| 직렬화 최적화의 객체 참조 함정 | 검증 케이스 **없음** — `Point` 배열 예제가 좋은 후보 |
| **압축 후 지연 해제가 가장 빠르다** | 검증 케이스 없음 — 수치가 극적(12.7초 → 0.494초) |

## 장 요약

> **Java EE 성능은 여러 요인에 달렸다. 늘 그렇듯 애플리케이션 코드의 품질이 가장 중요하고,
> 외부 자원을 아주 많이 쓰기 때문에 앱 서버의 성능 병목은 자바 계층 밖에 있는 경우가 많다.**
>
> **앱 서버 안에서 성능의 상당 부분은 Java EE 고유가 아닌 요인 — 특히 스레드 성능, 객체 풀,
> 네트워킹 성능 — 에 달렸다.**
>
> **앱 서버에서 가장 중요한 요인은 전송하거나 처리하는 데이터의 양이다** — 그것이 단순 HTML이든,
> XML 페이로드든, 직렬화된 객체 상태든, JSON 페이로드든.
