# 3장. 자바 성능 도구 상자 (A Java Performance Toolbox)

> ⚠️ **JDK 17 기준 차이** — **`jhat` 제거 · JFR 무료화(`UnlockCommercialFeatures` 없음) · GC 로그가 통합 로깅(`-Xlog`)으로 전면 교체.** 개념은 유효하지만 **명령이 다르다.**
> 전체 대조는 [`00-JDK-17-차이.md`](00-JDK-17-차이.md) 참고.

> **성능 분석의 본질은 가시성(visibility)이다.** 애플리케이션 안과 그 환경에서 무슨 일이
> 벌어지는지 아는 것. 그리고 가시성은 곧 도구다. 그러므로 성능 튜닝은 곧 도구다.

2장에서 "데이터 기반으로 접근하라"고 했다. 성능 **분석**도 마찬가지다. 프로그램이 정확히 무엇을
하고 있는지 데이터가 있어야 개선할 수 있다.

## 1부. 운영체제 도구

시작점은 자바와 무관하다. **OS가 주는 기본 모니터링 도구**다.

- Unix: `sar`(System Accounting Report)와 그 구성원 `vmstat`, `iostat`, `prstat`
- Windows: 그래픽 리소스 모니터, 명령행 `typeperf`

성능 테스트를 돌릴 때마다 **최소한 CPU·메모리·디스크** 정보를 수집해야 한다. 네트워크를 쓰면
네트워크도. 자동화한다면 명령행 도구를 써야 한다(Windows에서도). **인터랙티브로 돌리더라도
GUI 그래프를 눈대중으로 보고 추측하는 것보다 명령행 출력을 캡처해 두는 편이 낫다.** 나중에
분석할 때 그래프로 그리면 된다.

### CPU 사용률

두 범주로 나뉜다.
- **사용자 시간(user time)**: CPU가 애플리케이션 코드를 실행한 비율
- **시스템 시간(system time / Windows의 privileged time)**: 커널 코드를 실행한 비율.
  애플리케이션이 I/O를 하면 커널이 디스크에서 파일을 읽거나 버퍼를 네트워크에 쓰는 코드를
  실행한다. **하부 시스템 자원을 쓰는 모든 것이 시스템 시간을 늘린다.**

#### 핵심 명제 — CPU를 최대한 높게, 최대한 짧게

> 직관에 반해 보인다. 데스크톱이 CPU 100%로 버벅이는 걸 다들 겪어 봤으니까.

CPU 사용률은 **구간 평균**(5초, 30초, 최소 1초)이라는 점이 핵심이다.

- 10분 실행에 평균 50%인 프로그램을 튜닝해서 CPU가 100%가 되면 → **5분에 끝난다.**
- 또 두 배로 개선하면 → 2.5분 동안 CPU는 여전히 100%.

**CPU 숫자는 프로그램이 CPU를 얼마나 효과적으로 쓰는지의 지표이므로, 높을수록 좋다.**

#### `vmstat` 읽기

```
% vmstat 1
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa
 2  0      0 1797836 1229068 1508276 0    0     0     9 2250 3634 41  3 55  0
 2  0      0 1801772 1229076 1508284 0    0     0     8 2304 3683 43  3 54  0
```

매초 CPU가 450ms 바쁘다(사용자 42% + 시스템 3%). 550ms는 유휴다.

**CPU가 유휴인 이유는 세 가지다.**
1. **동기화 프리미티브에 블로킹**되어 락이 풀릴 때까지 실행할 수 없다
2. **무언가를 기다린다** — 예: DB 응답
3. **할 일이 없다**

앞의 둘은 **항상 손댈 수 있는 무언가를 가리킨다.** 락 경합을 줄이거나 DB를 튜닝해 응답을
빨리 받으면, 프로그램이 빨라지고 평균 CPU 사용률도 올라간다.

세 번째에서 혼란이 생긴다. **할 일이 있고 막힌 것도 없다면 CPU는 그 코드를 실행하는 데 사이클을
쓴다.** 자바만의 얘기가 아니다. 무한 루프 스크립트는 CPU 100%를 먹는다.

> 만약 이 스크립트가 CPU 100%를 안 먹는다면? OS가 할 일(`LOOPING` 한 줄 더 출력)이 있는데도
> **일부러 놀기로 선택했다**는 뜻이다. 놀아서 아무에게도 도움이 안 된다. 긴 계산을 하는
> 중이었다면 **답을 얻는 데 더 오래 걸릴 뿐**이다.

여기서 "혹시 다른 게 필요할지 모르니 CPU를 좀 놀려 두는 게 좋겠다"는 생각이 나온다. **하지만 OS는
당신이 다음에 뭘 할지 추측할 수 없다.** 기본적으로 할 수 있는 모든 것을 실행하지, CPU를 놀리지 않는다.

> **프로그램의 CPU를 제한하고 싶다면**
> SETI@home처럼 남는 사이클을 다 먹는 프로그램이 문제라면, OS별 메커니즘으로 인위적으로 조절하거나
> 프로세스 우선순위를 바꿀 수 있다. 우선순위 조정은 **유휴 사이클을 남기지 않으면서도** 백그라운드
> 작업이 CPU를 뺏지 않게 한다.

#### 자바 애플리케이션에서의 유휴 CPU

**배치형 애플리케이션** — 정해진 양의 일이 있으므로 유휴 CPU가 보이면 안 된다. CPU를 높이는 것이
항상 목표다. 100%인데도 최적화 여지가 있다면 **100%를 유지한 채** 더 빨리 끝내면 된다.

**서버형 애플리케이션** — 일이 없어서 유휴일 수 있다(다음 HTTP 요청 대기). 여기서 평균의 의미가
드러난다. 앞의 `vmstat` 출력은 **초당 요청 1개**를 받는 앱 서버였다. 요청 처리에 450ms가 걸렸으니
**실제로는 450ms 동안 CPU 100%, 550ms 동안 0%** 였다. 이것이 45%로 보고된 것이다.

같은 45%가 나오는 다른 경우: 0.5초마다 요청이 오고 처리에 225ms가 걸리면 → 225ms 바쁨, 275ms 유휴.

요청당 400ms로 최적화하면 전체 CPU는 **40%로 내려간다.** **CPU를 낮추는 것이 말이 되는 유일한
경우**다 — 들어오는 부하가 고정되어 있고 외부 자원에 제약되지 않을 때. 그리고 이건 부하를 더
넣을 여지가 생겼다는 뜻이기도 하다. **미시적으로 보면 여전히 "짧은 시간 동안 CPU 100%"** 를
달성한 것이고, 다만 그 스파이크가 너무 짧아서 도구가 100%로 잡지 못할 뿐이다.

#### 멀티 CPU에서의 추가 사항

멀티스레드·멀티 CPU에서 중요한 추가 사항 하나:
**할 일이 있는데도 CPU가 유휴일 수 있다.** 그 일을 처리할 **스레드가 없을 때**다.

전형적인 경우가 고정 크기 스레드 풀이다. 스레드 하나는 한 번에 태스크 하나만 실행하는데, 그 태스크가
블로킹되면(DB 응답 대기) 그 스레드는 그동안 새 태스크를 집을 수 없다. **할 일은 있는데 실행할
스레드가 없는 구간**이 생기고, 결과는 유휴 CPU다.

이 경우 스레드 풀을 키워야 한다. **하지만 유휴 CPU가 있다고 무조건 풀을 키우면 안 된다.**
락 병목이나 외부 자원 병목 때문일 수도 있다. **왜 CPU를 못 받는지 이해한 다음에 조치를 정해야 한다**(9장).

### CPU 실행 큐 (Run Queue)

실행 가능한(I/O 블로킹도 아니고 잠들지도 않은) 스레드 수.

**⚠️ Unix와 Windows의 의미가 다르다.**
- **Unix `run queue`** (`vmstat` 첫 번째 열): 실행 중이거나 **CPU가 있으면 실행할 수 있는** 모든
  스레드 수. 그래서 위 예에서 항상 최소 1이었다. 머신 전체가 대상이라 다른 프로세스 때문에
  가끔 2가 됐다.
- **Windows `processor queue`** (`typeperf`): **현재 실행 중인 스레드를 포함하지 않는다.**
  그래서 같은 단일 스레드 앱을 돌려도 0으로 나온다.

**목표**: Windows에서는 0, Unix에서는 CPU 수 이하. 절대적 규칙은 아니다(시스템 프로세스가 잠깐씩
올린다). 하지만 **의미 있는 기간 동안 너무 높다면 머신이 과부하**이므로 작업을 다른 머신으로
옮기거나 코드를 최적화해야 한다.

> **요약**
> 1. CPU 시간이 성능을 볼 때 **첫 번째로** 봐야 할 것이다.
> 2. 최적화의 목표는 CPU 사용률을 **올리는 것**(더 짧은 시간 동안)이지 내리는 것이 아니다.
> 3. **왜** CPU 사용률이 낮은지 이해한 다음에 튜닝에 뛰어들어라.

### 디스크 사용량

모니터링 이유는 **두 가지**다.

#### ① 애플리케이션의 I/O가 병목인지

까다롭다. **양쪽 방향으로 문제일 수 있기 때문**이다.
- 버퍼링을 제대로 안 하면(12장 예제) → **디스크 통계가 아주 낮게** 나온다
- 디스크가 감당 못 할 만큼 쓰면 → **아주 높게** 나온다

**두 상황 모두 개선 여지가 있다. 양쪽을 다 살펴야 한다.**

**낮은 처리량의 예:**
```
avg-cpu:  %user   %nice %system %iowait  %steal   %idle
          23.45    0.00   37.89    0.10    0.00   38.56
Device: ... w/s=24.20  wMB/s=0.14  w_await=6.08  %util=1.04
```
얼핏 좋아 보인다. `w_await` 6.08ms로 낮고 디스크는 1.04%만 쓴다. **그런데 단서가 있다 —
시스템 시간이 37.89%다.** 게다가 **0.14 MB/s를 쓰면서 초당 24.2회 쓰기**를 한다. 너무 잦다.
I/O가 병목이 됐고, 다음 단계는 애플리케이션이 어떻게 쓰기를 하는지 보는 것이다.

**높은 처리량의 예:**
```
avg-cpu:  %user  %system %iowait  %idle
          35.05    7.85   47.89    9.20
Device: ... w/s=163.40  wMB/s=81.09  avgqu-sz=142.74  w_await=871.17  %util=100.00
```
Linux는 **디스크 100% 사용**을 바로 알려주고, 프로세스가 **47.89%를 iowait에서** 보낸다고 알려준다.
원시 데이터만 있는 시스템에서도 알 수 있다 — `w_await` 871ms, 큐 크기 142, 초당 81MB 쓰기.

#### ② 시스템이 스와핑하는지

물리 메모리는 고정이지만 훨씬 큰 가상 메모리를 쓸 수 있다. 애플리케이션은 필요보다 많이
예약하고 보통 일부만 쓰므로, OS가 안 쓰는 부분을 디스크에 두고 필요할 때만 물리 메모리로 올린다.

이 방식은 대체로 잘 작동한다. **특히 인터랙티브·GUI 프로그램에서.** 하지만
- **서버 기반 애플리케이션에서는 덜 작동한다** — 메모리를 더 많이 쓰니까
- **자바 애플리케이션에서는 특히 나쁘게 작동한다 — 자바 힙 때문이다**(5장)

**스와핑하는 시스템은 전반적으로 성능이 나쁘다.** `vmstat` 의 `si`(swap in)·`so`(swap out) 열로도
알 수 있고, 디스크 활동도 스와핑의 지표다.

> **요약**
> 1. 디스크 모니터링은 **모든** 애플리케이션에 중요하다. 디스크에 직접 쓰지 않는 앱도 **시스템
>    스와핑**에 영향받는다.
> 2. 디스크에 쓰는 앱은 **비효율적으로 써서(처리량 부족)** 도, **너무 많이 써서(처리량 초과)** 도
>    병목이 될 수 있다.

### 네트워크 사용량

디스크와 비슷하다 — 비효율적으로 써서 대역폭이 낮거나, 인터페이스가 감당 못 할 만큼 많이 쓰거나.

**문제는 표준 시스템 도구가 부족하다는 것이다.** 보통 패킷 수와 바이트 수만 보여 주는데, 이것만으로는
**네트워크가 과소·과다 사용 중인지 알 수 없다.**

- Unix: `netstat` (대부분의 Linux 배포판에는 아예 없어 따로 설치해야 한다)
- Windows: `typeperf`. 여기서는 **GUI가 유리하다** — 표준 리소스 모니터가 사용률 %를 그래프로 준다.
  다만 자동화 테스트에는 쓸모가 없다.

**`nicstat` 같은 도구가 유용한 이유는 사용률을 계산해 주기 때문이다.**

```
% nicstat 5
Time      Int       rKB/s   wKB/s   rPk/s   wPk/s   rAvs    wAvs   %Util
17:05:17  e1000g1   225.7   176.2   905.0   922.5   255.4   195.6  0.33
```

마법은 없다. 직접 계산해도 된다 — **단, 대역폭은 bps로 재고 도구는 보통 Bps로 보고한다.**
1000메가비트 네트워크 = 125 MB/s. 위 예는 (0.22 + 0.16) ÷ 125 = 0.33%.

> **네트워크는 100% 사용률을 지속할 수 없다.** 로컬 이더넷은 **40%를 넘는 지속 사용률이면
> 인터페이스가 포화**된 것으로 본다. 패킷 교환 방식이거나 다른 매체면 최댓값이 다르니 네트워크
> 아키텍트에게 물어라. 이 목표는 자바와 무관하다 — 자바는 OS의 네트워크 파라미터를 그대로 쓴다.

## 2부. 자바 모니터링 도구

JDK에 딸려 오는 도구들:

| 도구 | 용도 |
|---|---|
| `jcmd` | 클래스·스레드·VM 기본 정보. **스크립트에 적합** |
| `jconsole` | JVM 활동의 그래픽 뷰 (스레드·클래스·GC) |
| `jhat` | 힙 덤프 분석 (후처리 유틸리티) |
| `jmap` | 힙 덤프와 메모리 사용 정보. 스크립트 가능(덤프는 후처리 필요) |
| `jinfo` | 시스템 프로퍼티 조회, **일부 프로퍼티 동적 설정**. 스크립트 가능 |
| `jstack` | 스레드 스택 덤프. 스크립트 가능 |
| `jstat` | GC와 클래스 로딩 정보. 스크립트 가능 |
| `jvisualvm` | GUI. 모니터링 + 프로파일링 + 힙 덤프 분석 |

기능 영역: 기본 VM 정보 / 스레드 정보 / 클래스 정보 / 실시간 GC 분석 / 힙 덤프 후처리 / 프로파일링.
**도구와 영역이 1:1이 아니다.**

### 기본 VM 정보

```bash
jcmd <pid> VM.uptime              # 가동 시간
jcmd <pid> VM.system_properties   # System.getProperties()
jinfo -sysprops <pid>             # 같은 것
jcmd <pid> VM.version             # JVM 버전
jcmd <pid> VM.command_line        # 명령행
jcmd <pid> VM.flags [-all]        # 튜닝 플래그
```

**튜닝 플래그 다루기 — 이 절이 실용적으로 가장 중요하다.**

- `VM.command_line` — 명령행에 **직접 지정한** 플래그
- `VM.flags` — 명령행 지정 + **JVM이 ergonomic하게 결정한** 플래그
- `VM.flags -all` — JVM 안의 **모든** 플래그

플랫폼별 기본값을 알고 싶다면:

```bash
java <other_options> -XX:+PrintFlagsFinal -version

uintx InitialHeapSize        := 4169431040     {product}
intx  InlineSmallCode         = 2000           {pd product}
```

**⚠️ 쓰려는 다른 옵션을 반드시 함께 줘야 한다.** 특히 GC 관련 플래그는 **다른 옵션의 최종값에
영향을 준다.**

**출력 읽는 법**
- `:=` (콜론 있음) → **기본값이 아닌 값**이 쓰이고 있다. 이유는 세 가지:
  ① 명령행에서 직접 지정 ② 다른 옵션이 간접적으로 변경 ③ **JVM이 ergonomic하게 계산**
- `=` (콜론 없음) → 이 JVM 버전의 기본값
- 마지막 열: `product`(모든 플랫폼 동일), `pd product`(**플랫폼 의존**),
  `manageable`(**런타임에 동적 변경 가능**), `C2 diagnostic`(컴파일러 진단용)

> **정보가 너무 많다?**
> `PrintFlagsFinal` 은 수백 개를 뱉는다(JDK 7u40에 **668개**). **대부분은 지원 엔지니어가
> 오작동하는 애플리케이션에서 정보를 더 얻으려고 만든 것이다.**
> `AllocatePrefetchLines`(기본 3) 같은 걸 발견하면 프리페칭이 나아질까 싶어 바꿔 보고 싶어진다.
> 하지만 **그런 식의 감으로 하는 튜닝은 무의미하다.** 애플리케이션의 프리페치 성능, CPU 특성,
> 그 변경이 JVM 코드에 미치는 영향을 다 알지 않는 한 **정당한 이유 없이 바꾸지 마라.**

`jinfo` 의 장점은 **실행 중 일부 플래그 값을 바꿀 수 있다**는 것이다.

```bash
jinfo -flags <pid>                    # 모든 플래그
jinfo -flag PrintGCDetails <pid>      # 개별 조회 → -XX:+PrintGCDetails
jinfo -flag -PrintGCDetails <pid>     # 끄기
```

**⚠️ 함정**: `jinfo` 는 **어떤 플래그든 값을 바꿀 수 있지만, JVM이 그 변경에 반응한다는 뜻은
아니다.** GC 알고리즘 동작에 영향을 주는 대부분의 플래그는 **시작 시점에** 컬렉터 동작을 정한다.
나중에 바꿔도 JVM은 초기화된 대로 계속 실행한다. **`manageable` 로 표시된 플래그에만 통한다.**

### 스레드 / 클래스 / GC 정보

```bash
jstack <pid>              # 스레드 스택
jcmd <pid> Thread.print   # 같은 것
```
스레드 스택은 **블로킹 여부 판단**에 매우 유용하다(9장).
클래스 정보는 `jconsole`·`jstat`(컴파일 정보도). 12장·4장 참조.
GC는 거의 모든 도구가 보고한다 — `jconsole` 실시간 그래프, `jcmd` GC 수행, `jmap` 힙 요약/덤프,
`jstat` 다양한 뷰. 5장 참조.

힙 덤프 후처리는 **서드파티가 전통적으로 JDK보다 한 발 앞서 있어서**, 7장에서는
**Eclipse Memory Analyzer Tool**을 쓴다.

## 3부. 프로파일링 도구

> **프로파일러는 성능 분석가의 도구 상자에서 가장 중요한 도구다.**

**여러 도구를 함께 쓰는 것이 말이 되는 영역**이다 — 특히 샘플링 프로파일러라면. **같은
애플리케이션에서도 프로파일러마다 다른 문제를 찾아낸다.**

거의 모든 자바 프로파일러는 그 자체가 자바로 작성돼 있고 대상 애플리케이션에 "붙어서"(소켓 등으로)
동작한다. **그래서 프로파일링 도구 자체도 튜닝해야 한다.** 큰 애플리케이션을 프로파일링하면
데이터가 많이 전송되므로 **프로파일러에 충분한 힙**이 필요하고, **동시 GC 알고리즘으로 돌리는 게
좋다** — 프로파일러에서 때 안 맞는 full GC가 나면 데이터 버퍼가 넘칠 수 있다.

### 샘플링 프로파일러

기본 모드이고 **오버헤드가 가장 적다.** 중요하다 — **측정을 도입하는 것 자체가 성능 특성을
바꾸기 때문**이다.

> 그래도 프로파일링은 해야 한다. **안 그러면 프로그램 안의 고양이가 아직 살아 있는지 어떻게 알겠나.**
> (슈뢰딩거 농담)

**동작 방식**: 타이머가 주기적으로 발화하면 각 스레드가 어떤 메서드를 실행 중인지 본다. 그 메서드가
직전 발화 이후의 시간을 **전부 청구받는다.**

**가장 흔한 샘플링 오류**: 스레드가 `methodA`(음영)와 `methodB`(흰색)를 번갈아 실행하는데,
**타이머가 우연히 항상 `methodB` 구간에서만 발화**하면 프로파일은 모든 시간을 `methodB` 가 썼다고
보고한다. 실제로는 `methodA` 가 더 많이 썼는데도.

**완화 방법**: 더 오래 프로파일링하고, 샘플 간격을 줄인다. 하지만 간격을 줄이면 오버헤드를 최소화한다는
목표와 충돌한다. **균형의 문제이고, 프로파일러마다 이 균형을 다르게 잡는다. 이것이 도구마다
결과가 크게 다른 이유 중 하나다.**

**GlassFish 시작 프로파일 예시** — `defineClass1()` 이 19%로 1위, `getPackageSourcesInternal()` 이 2위.

> **여기서 이 장에서 가장 중요한 교훈이 나온다.**
>
> 개선해야 할 것은 `defineClass1()` **메서드의 성능이 아니라 클래스로딩의 성능**이다.
> 프로파일을 볼 때 흔한 가정이 "맨 위 메서드를 최적화해야 한다"인데, **너무 제한적인 접근이다.**
> `defineClass1()` 은 JDK의 네이티브 메서드다 — JVM을 다시 쓰지 않는 한 빨라지지 않는다.
>
> 게다가 **보통은 맨 위 메서드가 전체의 2~3%** 다. 그걸 절반으로 줄여도(대개 엄청나게 어렵다)
> 전체는 1% 빨라진다. **맨 위 핫스팟만 보는 것으로는 큰 이득을 얻지 못한다.**
>
> 대신 **맨 위 메서드들은 "어느 영역을 뒤져야 하는지"를 가리키는 표지판**으로 써야 한다.
> GlassFish 엔지니어는 클래스 정의를 빠르게 만들려 하지 않는다 — **클래스를 덜 로드하거나 병렬로
> 로드하는 식으로 클래스로딩 전반을 개선**한다.

### 계측 프로파일러 (Instrumented Profiler)

훨씬 침습적이지만 더 유용한 정보를 준다. **같은 GlassFish 시작을 계측 모드로 보면 완전히 다른
그림이 나온다.**

- 핫 메서드가 `getPackageSourcesInternal()` 로 바뀌고 **4% → 13%**
- **`defineClass1()` 은 아예 나타나지 않는다**
- **호출 횟수**를 보고하고 호출당 평균 시간을 계산해 준다

> 어느 쪽이 더 정확한가? **알 수 없다.** 다만 **호출 횟수는 확실히 정확**하고 그 정보가 아주 유용하다.
> 예에서 `ImmutableMap.get()` 이 전체의 12%를 쓰는데 **470만 번** 불린다.
> → **구현을 빠르게 하는 것보다 호출 횟수를 줄이는 편이 훨씬 효과가 크다.**

**단점**: 클래스 로드 시 **바이트코드를 변경**해서 동작한다(호출 카운터 삽입 등). 그래서 성능 차이를
만들 가능성이 샘플링보다 훨씬 크다. 대표적으로 **인라이닝**(4장) — JVM은 코드 크기를 보고 작은
메서드를 인라이닝하는데, 계측하면 **인라이닝 대상에서 빠질 수 있다.** 그러면 계측 프로파일러가
특정 메서드의 기여도를 **과대평가**한다. **코드를 많이 계측할수록 실행 프로파일이 달라질 가능성이
커진다.**

> **`ImmutableMap.get()` 이 샘플링에는 안 나오고 계측에만 나온 기술적 이유**
> 자바의 샘플링 프로파일러는 스레드가 **세이프포인트(safepoint)** 에 있을 때만 샘플을 딸 수 있다
> — 본질적으로 **메모리를 할당할 때**다. `get()` 은 세이프포인트에 영영 도달하지 않을 수 있고
> 그러면 절대 샘플링되지 않는다. **샘플링 프로파일러가 그 메서드의 기여도를 과소평가할 수 있다.**

> **요약**
> 1. 계측 프로파일러는 더 많은 정보를 주지만 애플리케이션에 더 큰 영향을 줄 수 있다.
> 2. **작은 범위(몇 개 클래스나 패키지)만 계측하도록 설정**해서 영향을 제한하라.

### 블로킹 메서드와 스레드 타임라인

NetBeans 프로파일러로 같은 것을 보면 `park()`·`parkNanos()`·`read()` 가 실행 시간을 지배한다.

**이 메서드들은 CPU 시간을 쓰지 않는다.** 스레드가 `parkNanos()` 안에서 632초 동안 **코드를 실행한
게 아니라 632초 동안 무언가를 기다린 것**이다. 그래서 **대부분의 프로파일러는 블로킹된 메서드를
보고하지 않고 유휴로 표시한다.**

이 예에서는 그게 옳다 — 파킹된 스레드는 서블릿 요청을 처리할 스레드 풀의 스레드고, 시작 중에는
요청이 없으니 블로킹 상태가 **정상**이다.

**하지만 보고 싶은 경우도 있다.** `wait()` 안에서 다른 스레드의 통지를 기다린 시간은 많은
애플리케이션에서 **전체 실행 시간의 중요한 결정 요인**이다. 대부분의 프로파일러에 필터 설정이 있다.

**더 유익한 대안은 스레드 실행 패턴을 보는 것이다.** Oracle Solaris Studio의 타임라인 뷰는
가로줄 하나가 스레드 하나이고, 색 막대가 메서드 실행, 빈 구간이 비실행이다. 스레드 1.2가 한참
실행하고 1.3을 기다리고, 1.3이 다시 1.2를 기다리는 **상호작용**이 보인다.

> **요약**
> 1. 블로킹된 스레드는 성능 문제일 수도 아닐 수도 있다. **왜** 블로킹됐는지 봐야 한다.
> 2. 블로킹 메서드로 식별하거나 **타임라인 분석**으로 식별한다.

### 네이티브 프로파일러

**JVM 자체를 프로파일링**한다. 애플리케이션이 네이티브 라이브러리를 쓴다면 그것도 보인다.
일부 도구는 자바와 C/C++ 코드를 **함께** 프로파일링한다.

GlassFish 예에서 총 CPU 25.1초 중 **20초가 `JVM-System`** 이다 — JVM 자체의 컴파일러 스레드와
GC 스레드. 파고들면 대부분이 컴파일러다(시작 시에는 컴파일할 코드가 많으니 당연).

> **이 도구에서만 얻을 수 있는 핵심 정보는 GC에 쓴 시간이다.** 자바 기반 도구에서는 **GC 스레드의
> 영향이 어디에도 나타나지 않는다.**
> (CPU에 묶인 머신이 아니라면 컴파일러 스레드의 큰 시간은 상관없다. CPU 하나를 많이 먹지만
> CPU가 더 있는 한 컴파일은 백그라운드에서 일어나므로 애플리케이션에 영향이 없다.)

네이티브 코드를 필터링하고 나면 다시 `defineClass1()` 이 최상위지만 **11%(5.041초 중 0.67초)** 로,
앞의 샘플링 프로파일러(19%)보다 **훨씬 낮다.** 그리고 새 정보가 보인다 — **JAR 파일 읽기와 압축
해제**(`inflateBytes()`). 다른 도구는 이걸 보여 주지 않았다. **자바 ZIP 라이브러리의 네이티브 코드가
블로킹 호출로 취급되어 필터링됐기 때문**이다.

> **요약**
> 1. 네이티브 프로파일러는 JVM 코드와 애플리케이션 코드 **양쪽**을 보여 준다.
> 2. **GC가 CPU를 지배한다면 컬렉터 튜닝이 옳다. 컴파일 스레드에 시간이 많이 든다면 대개
>    애플리케이션 성능에 영향이 없다.**

## 4부. Java Mission Control과 Java Flight Recorder

Java 7u40 이상 상용 릴리스에 포함. JRockit JVM에서 온 기술이며 **오픈소스가 아니고 상용
라이선스가 필요**하다.

`jmc` 를 띄우면 머신의 JVM 프로세스 목록이 나오고 하나 이상을 골라 모니터링한다.

**핵심 특징**: CPU 그래프가 **머신 전체 CPU**를 포함한다. 모니터링 중인 JVM이 70%를 쓰는데도
그래프는 100%에 가깝게 나온다. **선택한 JVM만이 아니라 시스템 전체를 모니터링할 수 있다**는
것이 핵심이다.

### Java Flight Recorder (JFR)

**Java Mission Control의 핵심 기능.** 이름 그대로 **JVM 이벤트의 이력**이며, JVM의 과거 성능과
동작을 진단하는 데 쓴다.

**동작 방식**: 특정 이벤트 집합을 활성화한다(예: "스레드가 락을 기다리며 블로킹됨"). 그 이벤트가
발생할 때마다 데이터를 저장한다(메모리나 파일에). 데이터 스트림은 **순환 버퍼**에 담기므로
**가장 최근 이벤트만 남는다.**

> **기본 설정에서 오버헤드는 1% 미만**이다. 이벤트를 더 켜거나 임계치를 낮추면 늘어난다.

#### JFR 화면들

**Memory 뷰** — 영 제너레이션이 비워지며 메모리가 규칙적으로 오르내리는 그래프. 흥미롭게도
이 애플리케이션은 **힙이 전혀 증가하지 않는다 — 올드 제너레이션으로 승격되는 게 없다.**
각 컬렉션의 지속 시간과 종류(여기서는 항상 `ParallelScavenge`), 이벤트를 고르면 **그 컬렉션의
모든 세부 단계와 각 단계 소요 시간**까지 보인다.

정보가 방대하다 — 참조 객체가 몇 개 얼마나 오래 정리됐는지, 동시 컬렉터에서 **승격 실패나 대피
실패**가 있었는지, GC 알고리즘 설정(세대 크기, 서바이버 공간 구성), 할당된 객체의 구체적 종류까지.

> **5·6장을 읽으면서 이 도구를 떠올려라.** CMS가 왜 포기하고 full GC를 했는지(승격 실패 때문인가?),
> JVM이 **테뉴어링 임계치**를 어떻게 조정했는지 — GC가 왜 그렇게 동작했는지에 대한 거의 모든
> 데이터를 JFR이 알려 준다.

**Code 뷰** — **패키지 이름별 집계**라는, 다른 프로파일러에 흔치 않은 기능이 있다. 예제 주식
애플리케이션은 41%를 `java.math` 에서 쓴다(당연하다 — `BigDecimal`).
- **Throwables 탭** — 예외 처리 뷰 (12장에서 과도한 예외 처리가 왜 나쁜지 다룬다)
- 컴파일러가 뭘 하는지, **코드 캐시** 뷰(4장)

**Event 패널** — 가장 강력한 뷰. 66초 구간에 **JVM에서 10,612개, JDK 라이브러리에서 1,536개** 이벤트.
- 소켓 쓰기 40초 — 4 CPU(가용 264초)에서 무리한 숫자는 아니지만, **클라이언트에 데이터를 덜 쓰면
  개선 여지가 있다**는 표시(10장)
- 소켓 읽기 143초 — 나빠 보이지만, 관리 요청을 블로킹 I/O로 기다리는 스레드들이라 **정상**이다.
  프로파일러를 쓸 때와 마찬가지로 **많은 스레드가 I/O에 블로킹된 것이 예상된 일인지 판단하는 건
  당신 몫**이다
- **monitor-blocked 이벤트** — 여기가 JFR만의 가치다. 락 경합은 두 단계로 진행된다(9장):
  먼저 스레드가 **스핀**하며 기다리고, 그다음 **락 인플레이션** 과정을 거쳐 CPU/OS 코드로 기다린다.
  일반 프로파일러는 스핀 시간이 CPU 시간에 포함되므로 힌트만 준다. 네이티브 프로파일러는
  인플레이션된 락 정보를 줄 수 있지만 들쭉날쭉하다(**Solaris에서는 Oracle Studio가 잘 하지만
  Linux에는 필요한 OS 훅이 없다**). **JVM은 이 데이터를 JFR에 직접 줄 수 있다.**

#### JFR 이벤트 종류 (Java 7u40 기준 77종)

각 항목의 **첫 줄은 다른 도구로도 얻을 수 있는 것**, **둘째 줄은 JFR 없이는 얻기 어려운 것**이다.

| 이벤트 | 기본 정보 | **JFR만의 정보** |
|---|---|---|
| 클래스로딩 | 로드·언로드된 클래스 수 | **어느 클래스로더가 로드했는지, 개별 클래스 로드 시간** |
| 스레드 통계 | 생성·소멸 수, 스레드 덤프 | **어느 스레드가 어느 락에 블로킹됐는지** |
| Throwables | 사용된 Throwable 클래스 | **예외·에러가 몇 개 던져졌는지와 생성 스택 트레이스** |
| TLAB 할당 | 힙 할당 수, TLAB 크기 | **구체적으로 어떤 객체가 어디(스택 트레이스)서 할당됐는지** |
| 파일·소켓 I/O | I/O에 쓴 시간 | **읽기/쓰기 호출당 시간, 오래 걸린 특정 파일·소켓** |
| Monitor blocked | 모니터를 기다리는 스레드 | **특정 스레드가 특정 모니터에 얼마나 오래 블로킹됐는지** |
| 코드 캐시 | 크기와 내용량 | **캐시에서 제거된 메서드, 코드 캐시 설정** |
| 코드 컴파일 | 컴파일된 메서드, OSR, 컴파일 시간 | JFR 고유는 아니지만 **여러 소스를 통합** |
| GC | GC 시간(단계별 포함), 세대 크기 | JFR 고유는 아니지만 **여러 도구의 정보를 통합** |
| 프로파일링 | 계측·샘플링 프로파일 | 진짜 프로파일러만큼은 아니지만 **좋은 상위 개요** |

#### JFR 켜기

```bash
# 기능 자체 활성화 (상용 JVM에서 기본 비활성)
-XX:+UnlockCommercialFeatures -XX:+FlightRecorder
```

**녹화 모드 두 가지**
- **고정 시간(fixed duration)** — **선제적(proactive) 분석**용. 녹화를 시작하고 부하를 만들거나,
  JVM이 워밍업된 뒤 부하 테스트 중에 시작한다
- **연속(continuous)** — **사후 대응(reactive) 분석**용. 순환 버퍼에 최근 이벤트를 유지하다가
  어떤 사건에 반응해 덤프한다. WebLogic은 "처리에 5분 넘게 걸린 요청" 같은 비정상 이벤트에
  반응해 녹화를 덤프하도록 트리거할 수 있다

**명령행 옵션** (`-XX:+FlightRecorderOptions=`):
`name`, `defaultrecording=<true|false>`, `settings=<path>`, `delay=<time>`, `duration=<time>`,
`filename=<path>`, `compress=<true|false>`, `maxage=<time>`, `maxsize=<size>`

**실행 중 제어** (`jcmd`):
```bash
jcmd <pid> JFR.start [options]    # 시작
jcmd <pid> JFR.dump  [options]    # 순환 버퍼를 파일로 덤프
jcmd <pid> JFR.check [verbose]    # 진행 중인 녹화 목록
jcmd <pid> JFR.stop  [options]    # 중단 (discard=true 로 버릴 수 있음)
```

#### 이벤트 선택 — 템플릿

이벤트는 두 종류다.
- **주기적 이벤트** — 수 밀리초마다 발생(프로파일링 이벤트는 샘플링 기반)
- **임계치 기반 이벤트** — 지속 시간이 임계치를 넘을 때만(예: `read()` 가 지정 시간 이상 걸릴 때)

**기본 제공 템플릿 두 개**
- **default** — **가장 비싼 이벤트 6개는 꺼져 있고** 시간 기반 임계치가 다소 높다. 오버헤드 **1% 미만**
- **profile** — 대부분의 임계치 기반 이벤트를 **10ms**마다 트리거. 추정 오버헤드 **2%**
  (저자는 실제로는 훨씬 낮게 관측한다고 덧붙인다)

**추가 오버헤드가 값어치를 하는 경우**: **TLAB 이벤트**를 보면 객체가 올드 제너레이션에 직접
할당되고 있는지 알 수 있는데, 기본 녹화에는 없다. 프로파일링 이벤트는 기본 녹화에 있지만
**20ms 간격이라 샘플링 오류가 생길 수 있다.**

템플릿은 `$HOME/.jmc/<release>` (사용자별)와 `$JAVA_HOME/jre/lib/jfr` (JVM 전역)에 저장된다.
**단순한 XML 파일**이므로 어떤 이벤트가 켜졌는지 확인하는 가장 좋은 방법은 XML을 읽는 것이고,
**한 머신에서 만들어 팀 전체에 복사**할 수 있다.

이벤트별로 **스택 트레이스 생성 여부**도 설정할 수 있다. 오버헤드가 늘어나므로 **설정 가능한
옵션으로 되어 있다.**

> **JFR은 확장 가능하다.** 애플리케이션이 자체 이벤트를 정의할 수 있다. WebLogic은 JDBC 작업,
> HTTP 작업 등의 이벤트를 추가한다. 이들도 다른 이벤트처럼 개별 활성화·임계치 설정이 된다.

> **요약**
> 1. JFR은 **JVM 자체에 내장돼 있어서** 가능한 최고의 가시성을 준다.
> 2. 모든 도구처럼 오버헤드가 있다. **일상적 사용에서는 낮은 오버헤드로 상당한 정보를 모을 수 있다.**
> 3. 성능 분석뿐 아니라 **프로덕션에 켜 두면 장애로 이어진 이벤트를 사후에 조사**할 수 있다.

## 이 장을 우리 랩에 비춰 보면

| 이 장의 도구 | 우리 랩에서의 대응 |
|---|---|
| `PrintFlagsFinal` 로 ergonomic 기본값 확인 | `JVM-07` 이 `UseContainerSupport` 기본 활성(Java 10+)을 확인한다 |
| 프로파일러의 세이프포인트 한계 | 우리는 프로파일러 대신 `StatementInspector`·`ThreadMXBean` 등 **결정론적 관측점**을 쓴다 |
| 네이티브 프로파일러만 GC 스레드를 본다 | 우리 케이스는 GC 영향을 `expectFlaky` 로 **인정**할 뿐 분리 측정하지 않는다 |
| JFR의 monitor-blocked 이벤트 | `CON-05` 는 `ThreadMXBean.findDeadlockedThreads()` 로 대신한다 |
| 실행마다 OS 지표를 함께 수집 | **우리 리포트에는 CPU·디스크·네트워크 지표가 없다** — 2장의 "모든 것을 측정하라"에 미달 |

마지막 줄이 정직한 고지 대상이다. 우리 리포트는 **소요 시간(ms)만** 남기고 그 시간 동안 시스템이
어떤 상태였는지는 남기지 않는다. 그래서 `INCONCLUSIVE` 가 났을 때 **"머신이 바빴는가"를 사후에
확인할 방법이 없다.**

## 장 요약

- **완벽한 도구는 없고, 경쟁 도구마다 상대적 강점이 있다.** 프로파일러 X가 많은 앱에 잘 맞아도
  프로파일러 Y가 명확히 짚어 주는 것을 놓치는 경우가 반드시 있다. **접근을 유연하게 유지하라.**
- **명령행 모니터링 도구는 중요한 데이터를 자동으로 모을 수 있다.** 자동화 성능 테스트에
  이 수집을 반드시 포함시켜라.
- **도구는 빠르게 진화한다.** 이 장에서 언급한 도구 중 일부는 이미 구식이거나 더 나은 것으로
  대체됐을 것이다. **이 영역은 최신 상태를 유지하는 것이 중요하다.**
