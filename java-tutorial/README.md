# java-tutorial — 실행되는 자바 튜토리얼

`manuscripts/java-면접/` 의 145문항 중 **직접 실행해서 확인할 수 있는 것들**만 골라
레슨으로 만든 모듈입니다.

읽는 교재가 아닙니다. **레슨 하나가 JUnit 테스트 하나**라서, 문장이 맞는지
직접 돌려서 확인할 수 있습니다.

```bash
./gradlew :java-tutorial:test
```

현재 **7개 레슨 / 54개 테스트, 전부 통과**합니다 (JDK 17.0.19).

---

## 1. 왜 이렇게 만들었나

이 저장소의 원칙은 `docs/00` §8 — **"검증한 척"을 만들지 않는다** 입니다.
면접 답변집은 그 자체로는 검증되지 않은 문장 묶음입니다. 그래서 그중
**순수 자바만으로 판정 가능한 주장**을 골라 테스트로 옮겼습니다.

- DB·브로커·프레임워크가 필요한 주장은 여기 없습니다 → `verify-labs*` 모듈 소관
- 성능 비교(시간 측정)가 필요한 주장도 여기 없습니다 → `verify-labs-perfbook` 소관
  (`docs/02` §1-2 의 해상도·최소 마진 규칙을 지켜야 하기 때문)
- 남은 것 — **동작이 결정적이어서 단정할 수 있는 주장**만 이 모듈에 있습니다

의존은 JUnit 과 AssertJ 둘뿐입니다.

## 2. `fact` / `observe` / `lesson`

`Lesson` 클래스에 도구가 세 개 있습니다. 이 구분이 이 튜토리얼의 핵심입니다.

| 도구 | 뜻 | 판정에 쓰이나 |
|---|---|---|
| `fact(라벨, 값)` | 확인된 값을 콘솔에 남긴다 | 아니오 (기록용) |
| `observe(라벨, 값)` | **환경에 좌우되는 값**. 단정하지 않는다 | 아니오 |
| `lesson(문장)` | 레슨의 결론 한 줄 | 아니오 |

판정은 오직 `assertThat` 이 합니다.
저장소의 `expect`(→REFUTED) / `expectFlaky`(→INCONCLUSIVE) 구분과 같은 발상입니다.

**즉, 테스트가 초록이라고 해서 `observe` 로 찍힌 줄까지 증명된 것은 아닙니다.**
현재 `observe` 는 5곳입니다 — 레슨 5(동시성)에 4곳, 레슨 2에 1곳.

예를 들어 레슨 5-1 은 이렇게 나옵니다.

```
 · 기대값                        = 400000
 · AtomicInteger 결과            = 400000
 ~ 일반 int++ 결과                = 365910  (갱신 손실 34090건)   (환경 의존 — 단정하지 않음)
```

여기서 단정한 것은 **`AtomicInteger` 는 정확하다**와
**일반 `int` 는 기대값을 넘지 못한다** 둘뿐입니다.
"반드시 손실이 난다"는 단정하지 않았습니다 — 스케줄링은 우리가 정하지 못하니까요.

## 5. 정직한 고지

- **145문항 중 54개만 레슨이 되었습니다.** 나머지는 실행으로 판정할 수 없거나
  (설계 논의·용어 설명), 이 모듈의 범위(순수 자바)를 벗어납니다. 커버리지가
  아니라 **판정 가능성**으로 골랐습니다.
- **`observe` 로 찍힌 5줄은 검증되지 않았습니다.** 콘솔에서 눈으로 볼 수는 있지만
  테스트가 초록인 근거는 아닙니다.
- **5-6 의 데드락 재현은 하지 않았습니다.** 위 §레슨 5 참고.
- **JDK 17.0.19 에서만 돌려봤습니다.** 1-6(Integer 캐시 상한)이나 2-3(문자열
  결합 최적화)처럼 JDK 판올림에 영향받을 수 있는 항목이 있습니다.
  다른 JDK 에서 결과가 다르면 그건 이 튜토리얼의 버그가 아니라 관찰 대상입니다.
- 여기 실린 성능 관련 주장(3-6, 7-2)은 **시간을 재지 않았습니다.**
  시간 기반 검증은 `verify-labs-perfbook` 의 PERF-12B·PERF-12C 에 있습니다.
